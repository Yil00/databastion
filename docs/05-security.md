# Security & best practices – DataBastion

A security tool that reads sensitive data is itself a target. These rules are non-negotiable.

## Security invariants
1. **Outbound-only**: no inbound port to the agents or to the databases.
2. **No raw sensitive value leaves the agent.** Only: location, detected type, confidence, volume, masked sample, HMAC fingerprint ([ADR-0003](adr/0003-data-minimization-at-source.md)).
3. **Database credentials never leave the agent host.** The console neither stores nor receives them.
4. **Least privilege**: the agent connects with a dedicated **read-only** account.
5. **No secrets in images or in the repository**: environment variables, Docker secrets, mounted files.
6. **Console audit log**: every user action (login, policy change, incident acknowledgment, agent enrollment or revocation) is logged.

## Threat model (summary)
| Compromise | What the attacker gets | What they do not get |
|---------------|----------------------------|------------------------|
| Console | The map of sensitive locations, masked samples, access-event metadata (account names, client addresses, application names, objects, volumes; no query text or value), notification channel secrets (webhook URLs and signing secrets, SMTP passwords, with the server key), with OIDC on the client secret and the stored refresh tokens (with the server key) | The data itself, database credentials, network access to the databases |
| An agent | Its own secret, the read-only account of its targets, its local HMAC key (so it can confirm guesses of low-entropy fingerprinted values, see below), the audit log files it was given read access to (CAS: every end user's login and address) | The other agents, the console secrets |
| Network between agent and console | Nothing (TLS 1.3) | |

The map remains sensitive information: the console must be protected (HTTPS, authentication, public exposure not recommended).

## Masking and fingerprints
*Implemented in the `classifiers` crate (#34); details in `agent/crates/classifiers/README.md`.*

- **Masked sample**: `jane.doe@example.com` → `j***@e***.com`; IBAN → `FR** **** **** **** **** ***0 189`; card → `**** **** **** 1111`; birth date → `****-**-**`. Every sample is checked against the contract `MaskedSample` rules (at least one `*`, no run of more than 4 letters or digits, at least 50 % `*`) and keeps **at most 4 digits in total**; a sample that fails the checks falls back to `***`.
- **Sample selection**: masked samples are not the first rows and are not row-aligned. Each column keeps the 5 distinct samples with the smallest `HMAC(agent key, "sample-order" 0x00 column_name 0x00 value)`: a keyed order, deterministic for an agent but independent from one column to the next, so the console cannot line up the samples of several columns into partial records.
- **Fingerprint**: `hmac-sha256:` + hex of `HMAC-SHA256(agent_local_key, "databastion/fp/v1" 0x00 domain 0x00 normalized_value)`, where `domain` is the classifier id, or `db_user` for an account-name fingerprint. The domain separation keeps the same string under two classifiers, or as an account name, from correlating. Fingerprints allow deduplication and equality checks without revealing the value. The key (`<state_dir>/hmac.key`, 32 bytes) is generated at enrollment and **never leaves the agent**; the value normalization is agent-local and not part of the contract, so the console treats fingerprints as opaque. Phone numbers written without `+` are only normalized to international form when the target declares `phone_region` in `agent.yaml` (`fr` today); otherwise their digits are fingerprinted as they are, so the national and international forms of one number do not match.
- **Local tags** (since #97): the agent also derives a sub-key `HMAC(agent_key, "databastion/local-tag/v1" 0x00 purpose)` for integrity tags it keeps on its own host; the only purpose today is `audit-tail-cursor`, the keyed fingerprints of the audit log bytes before a saved read position ([08-engine-capabilities.md](08-engine-capabilities.md#audit-log-files-and-failing-streams-every-engine)). These tags are local only, never sent, and never contract `Fingerprint`s: made with another key, they cannot equal one, and the log bytes themselves are not stored.
- **Low-entropy values**: an HMAC does not protect a value with few possible inputs against someone who **holds the key**. Phone numbers, birth dates and NIRs can be enumerated, so a holder of the agent key can recover them from their fingerprints by brute force. Without the key (the console, the network) this is not possible. The agent state directory and **all its backups** are therefore sensitive: protect them like the target credentials, and exclude `hmac.key` from backups that leave the agent host where possible.
- **Names** (tables, fields, LDAP containers) can embed values: the agent normalizes them before the uplink and sanitizes each item rather than dropping the batch ([ADR-0009](adr/0009-name-normalization-and-item-sanitization.md)).
- Masking is implemented in a single crate (`classifiers`/`masking`) and covered by unit and property tests (contract conformance, no raw value or 5-digit run survives, keyed and domain-separated fingerprints, no raw value in `Debug`).

**Residual risks of name normalization.** Normalization (`agent/crates/classifiers/src/names.rs`, #39) replaces segments with more than 6 digits, UUIDs and long hex keys, e-mail addresses, percent-encoded bytes, segments matched by a classifier (including values split across dots) and words from a list of common first names. Since #42, `%uXXXX` escapes are treated as values like `%XX` (`%u0040` read as `@`); CJK numerals count as digits in the digit bounds and in the final `NormalizedName` check: the ideographic digits `零〇一二三四五六七八九`, the financial forms `壹贰叁肆伍陆柒捌玖` and `貳參陸`, `两` / `兩` and `拾` (short CJK words such as `一月` are kept; Hangul numerals are deliberately not counted, as they are ordinary syllables); and a document-path key that cannot be folded (NFKC) within the input bound makes the whole path `*`. Normalization cannot recognize every value written as a name. Known gaps, confirmed against the current code:
- **E-mail local part in the previous key.** With the real keys of a document path, a key that contains a dot and an `@` (`x@example.com`) becomes `*` on its own, and the keys before it are kept: `contacts` / `pdupont` / `x@example.com` / `phone` gives `contacts.pdupont.*.phone`. The previous key is only masked when it is itself recognized (e.g. a listed first name).
- **Spelled-out e-mails.** An address written without `@` (`pdupont_at_example_com`) matches no detector and passes unchanged.
- **Encoded names.** A base64-encoded value without padding (`cGR1cG9udEBleGFtcGxlLmNvbQ`) passes unchanged; with `=` padding the segment becomes `*` only because `=` is a forbidden character. Other encodings are not decoded either.
- **Person names.** A surname alone (`archive_dupont`) or a first name missing from the list passes; no detector recognizes arbitrary person names in identifiers, and such a name also passes the contract's `Identifier` pattern.

Name-based leaks are the subject of the P2-E invariant test.

**Invariant I2 test (P2-E).** An automated end-to-end test that runs a Discovery scan of a seeded PostgreSQL target and checks that no seeded sensitive value, including values embedded in object and field names, is stored in clear by the console. It runs in the E2E job (#50, `e2e/i2_check.py`); since #55 it also covers MySQL and MariaDB targets and runs in `ci.yml`, required through the `CI result` gate. It scans the whole console database dump, every console and agent log and the rendered findings page (the only place masked samples are decrypted); no rendered masked sample may keep more than 4 digits. Matching is case-, accent- and normalization-form-insensitive, also after JSON / URL / HTML / SQL unescaping, with digit-only and national / international forms for numbers; values under 4 characters are excluded and counted. The agent must report an empty spool before the check, so no batch is still in flight. Known blind spots: base64 / hex encodings, camelCase-embedded names, values split across columns. Since #66 it also covers the Audit path on the PostgreSQL and MariaDB Audit targets (`i2_check.py audit` and the same scan on the Audit artifacts): stored access events, incidents, notification payloads, baselines and Audit settings; the events, principal, incident, notification, agent and Audit settings pages; the notification e-mails; and the query literals of the test, which must appear nowhere. Since #82 it also covers a MongoDB target (Discovery, and the Audit path from the server log: a real `mongodump` raises an incident) and an OpenLDAP target (Discovery, and the Audit path from `cn=accesslog`: a bulk `ldapsearch` raises an incident, every OpenLDAP principal must be a fingerprint), and password-bearing DCL on PostgreSQL (`CREATE USER`, `ALTER ROLE … PASSWORD`) and MariaDB (`CREATE USER`, `ALTER USER … IDENTIFIED BY`): the DCL passwords must appear nowhere on the console side, nor in clear in the targets' own logs. Known gaps of that test: in the local `E2E_PG_AUDIT=pss` mode (`pg_stat_statements`, which keeps DCL passwords in clear) there is no positive control of the agent's own DCL redaction; the scan does not look at hex encodings of short windows. It complements the masking property tests of the `classifiers` crate, per-item sanitization in the agent and strict schema validation in the console.

## Classifiers
*Implemented in the `classifiers` crate (#34, #48); semantics of classifier set `2026.09.1` in [ADR-0016](adr/0016-classifier-semantics-2026-09-1.md); detection and decision rules in `agent/crates/classifiers/README.md`.*

- **Values decide, names only lower thresholds.** A column is reported on the evidence found in its sampled values; a column-name hint lowers the thresholds. A name of something other than a person (`pet_name`, `hostname`, `company.name`) turns `pii.person_name` off, and an order / tracking / IMEI / barcode name turns `pii.card_number` off.
- **Unicode**: values are put in NFC before detection; tokens, masked samples and fingerprints are taken from the NFC value (fingerprint label `databastion/fp/v1` unchanged). NFKC applies to names only. Typographic spaces and hyphens (U+00A0, U+2000–U+200A, U+202F, U+2010–U+2013, U+2212) are read as ASCII space and `-` by the column classifier before detection and, since v0.1.x item (g), by the value normalization behind masking and fingerprints as well, so a value written with them has the masked sample and fingerprint of its ASCII form for every caller. Fingerprints sent by the agent do not change: Discovery, their only producer, already folded these characters before masking and hashing. The detection and masking temporaries holding a whole value (the normalized value, the digits of a phone number, the characters of a card number or IBAN) are zeroized on drop and sized up front so that no reallocation leaves a copy; the internal buffers of the Unicode normalization library (used beyond 4 combining marks in a row) are not zeroized, a residual risk for an attacker who can read the agent's memory.
- **Detection temporaries** holding a value or part of it (the NFC copy of a value, digit and alphanumeric extractions, lowercased e-mail parts) are zeroized on drop, like `RawValue`, `HmacKey` and the normalized values used for fingerprints.
- **Held-out gate**: the phase 2 exit criterion (recall ≥ 90 %, precision ≥ 85 % per classifier, Wilson 95 % lower bound on `dev/holdout/`) is a blocking CI step since #48. Classifiers are never tuned against the holdout (independence rule, `dev/holdout/README.md`).

**Residual recall and precision limits**, known and accepted for this classifier set:
- **Placeholders**: values on a fixed list (`N/A`, `na`, `null`, `-`, `unknown`, `x`, `xx`, `0`, `0000-00-00`…) are not informative; a real value equal to one of them (a person called `Na`) is ignored.
- **Single address repeated**: a column holding one e-mail address repeated is not reported as personal e-mail, even if that address is a person's.
- **Checksum columns**: IBAN, card and NIR columns are reported only if at least half of their checksum-shaped candidates are valid. A column mixing many invalid numbers with a few real ones is missed.
- **Children's birth dates** without a column-name hint are missed (the age distribution needs a median birth year of 2002 or earlier).
- **Reference year drift**: the age heuristic uses the fixed reference year 2026 of the set. As time passes, real populations include more recent birth dates, and recall without a hint decreases until a later set moves the reference year.
- **Person names without a hint** rely on a lexicon of given names, surnames and surname endings: names from cultures poorly covered by it, or rare names, are missed without a hint.
- **Person names under a non-person hint** (`pet_name`, `product_name`, `team_name`…) are never reported, even when the column holds real person names.
- The dev ground truth and the synthetic evaluation are in-sample (the detectors were written with them in view); only the held-out corpus measures generalization.

## Encryption
- **In transit**: TLS 1.3 mandatory. No additional application-level AES-GCM encryption on top: without a key held outside the console, it adds nothing to TLS.
- **At rest (console)**: sensitive columns are encrypted with the console server key `DATABASTION_ENCRYPTION_KEY(_FILE)`, provided via Docker secret. The key derives independent HKDF-SHA256 subkeys: agent known-good fingerprints (`agent-known-good.v1`), login device cookies (`login-device.v1`), masked samples (`masked-samples.v1`), notification channel secrets (`notification-channels.v1`, see [Alerting](#alerting)), rate-limit keys (`rate-limit-keys.v1`, see [Shared rate limits](#shared-rate-limits)), and the OIDC state cookie (`oidc-state.v1`) and refresh tokens (`oidc-tokens.v1`, see [Console login with OpenID Connect](#console-login-with-openid-connect)).
- **Masked samples** (#36) are stored only encrypted: AES-256-GCM under the `masked-samples.v1` subkey, a random 96-bit nonce per encryption, and AAD = label ‖ format version ‖ finding id, so a ciphertext copied onto another finding row, or relabelled with another format version, does not decrypt. Decryption happens server side for the findings view; a wrong key or a tampered row shows no sample rather than an error. Without a usable key, samples are neither stored nor shown (fail closed). **Changing the key** makes the stored samples unreadable (they are not re-encrypted); they come back with the next scan of each target, which replaces them. It also invalidates the known-good fingerprints and device cookies.
- **`DATABASTION_ENCRYPTION_KEY` is required in production** (#37). Without a usable key (unset, shorter than 32 characters or unreadable), the web and worker processes **refuse to start** in production (fatal log, exit code 1). `DATABASTION_ALLOW_MISSING_ENCRYPTION_KEY=1` overrides this (not recommended): the processes then start, known-good fingerprints, device cookies and masked samples are disabled (fail closed), the login rate limits keyed by username are per process only, and an **error** naming the disabled protections is logged at startup.
- Agent secrets are stored **hashed** (argon2id) on the console side.

## Agent secret management
Normative details: [`shared/protocol/openapi.yaml`](../shared/protocol/openapi.yaml) (`/enroll`, `/rotate`, `agentSecret` security scheme); overview in [09-agent-protocol.md](09-agent-protocol.md#secret-rotation).

- **Enrollment token**: single use, valid 24 h, generated in the console. The console stores only its SHA-256 hash and consumes it **atomically** (one conditional update: unused and not expired → used), so two concurrent enrollments with the same token cannot both succeed. `/enroll` is rate limited per source IP (IPv6 bucketed by /56), and hashes the new secret in its own argon2id pool of 2 concurrent operations: when it is full, the console answers `503` + `Retry-After` and the token is not consumed.
- At enrollment, the agent receives `agent_id` + a 256-bit secret; it stores them in a `0600` file, then generates its local HMAC key (never transmitted).
- **Secret storage**: argon2id hash on the console side. The bodies of `/enroll` and `/rotate` are excluded from every request, APM and error log, on both sides.
- **Authentication**: failed authentications are rate limited per agent id **and** per source IP (when known, see [Authentication rate limits](#authentication-rate-limits)) **before** the argon2id verification runs, so the hash cost cannot be used for denial of service. A cache of verified secrets, if any, keeps entries less than 30 s and is purged on revocation and on rotation.
- **Rotation** ([ADR-0008](adr/0008-agent-generated-secret-rotation.md)): the **agent generates** the new secret, persists it as pending before any network call, and registers it with `POST /rotate`, authenticated with the current secret. Retries resend the same secret and are idempotent. The console rejects a new secret equal to the current one or obviously low-entropy (`invalid_secret`). A different new secret while one is pending, or use of the old secret after a **60 s tolerance window** following promotion, is a `rotation_conflict`: the console locks the agent, revokes all its secrets and raises a security incident; the agent stops and must be re-enrolled. [ADR-0010](adr/0010-rotation-conflict-window.md) makes the window precise: only a `/rotate` authenticated with the previous secret and carrying a different new secret can be a conflict inside the window (the same new secret is an idempotent `duplicate`), and a `/rotate` authenticated with the current secret always starts a new rotation while no secret is pending. [ADR-0011](adr/0011-late-rotation-retry.md) adds the late retry: a `/rotate` authenticated with the previous secret whose new secret matches the current (promoted) one is an idempotent `duplicate` at any time, bounded to 10 per agent per 5 min; any other `/rotate` outcome with the previous secret after the window locks the agent. When the outcome of a `/rotate` is unknown, the agent first probes its pending secret with a heartbeat before re-sending `/rotate` with the previous one (#20).
- **Security events** (#21): a `rotation_conflict` lock writes a `critical` row to the `security_events` table (console-computed kind, severity and scalar details, never a secret or hash) in addition to the console audit log. Since P3-C (#49), security events are notified to the channels flagged `system_alerts` (see [Alerting](#alerting)); they are not incidents, which only policies raise ([ADR-0014](adr/0014-policy-and-incident-model.md), [ADR-0017](adr/0017-alerting.md)). The table is insert-only for the runtime role, except the acknowledgement columns (`acknowledged_at`, `acknowledged_by`): migration `0010` revokes `UPDATE`, `DELETE` and `TRUNCATE`, so a compromised console process cannot erase or rewrite an integrity alert.
- **Revocation** invalidates the current and the pending secret and closes the agent's held long-polls. It is effective in **less than 60 s**.
- **Suspected compromise** of an agent secret is not handled by rotation (whoever holds the secret could rotate it too): the administrator revokes the agent and re-enrolls it.
- Vault integration: later

## Console internal database
*Introduced by P1-A (#17); details in `console/README.md` ("Database roles").*

### Database roles
The console uses three PostgreSQL roles, so that a compromised console process can neither remove the append-only trigger on `audit_log` nor plant code that migrations would run:
- a bootstrap superuser, used only by the init script that creates the two roles below;
- an **owner** role (not superuser, no `CREATEROLE`) used only for migrations: it owns the database, the `public` and `pgboss` schemas and every console table and trigger; its `search_path` is pinned to `public`;
- a **runtime** role used by the web and worker processes: DML only on the console tables, only `SELECT` and `INSERT` on `audit_log`, only `SELECT`, `INSERT` and `UPDATE (acknowledged_at, acknowledged_by)` on `security_events` (migration `0010`), no `DELETE` and only lifecycle / re-match column `UPDATE` on `incidents` (migrations `0015`, `0016`, `0022`, `0024`; [ADR-0014](adr/0014-policy-and-incident-model.md)), only `SELECT`, `INSERT` and `UPDATE` of the evaluation columns (`evaluated_at`, `sensitivity`, `score`, `anomaly`, `baseline_rows`) on `access_events`, only `SELECT` and `INSERT` on `events_batches` and `incident_events`, no `DELETE` or `TRUNCATE` on `principal_baselines` and `audit_configs` (migration `0022`; see [Access events](#access-events-ingestion-and-correlation)), `USAGE` and `CREATE` on schema `pgboss` for the pg-boss tables, and no `CREATE` on the database or on `public`.

The owner role never runs SQL against objects inside `pgboss`: they are created by the runtime role, so a trigger or function planted there would run with the owner's rights. Migration `0009` refuses to migrate when schema `pgboss` exists and is owned by a role other than the migration role; the whole run is rolled back, and a superuser must fix the ownership (after checking the schema for planted objects) before `migrate` runs again. Since #37, `migrate` also repeats the check as a pre-flight on every run, before any migration SQL. In a single-role setup (development), the audit log is append-only against the application code only.

### Metrics endpoint (#21)
`GET /metrics` requires `Authorization: Bearer <DATABASTION_METRICS_TOKEN>` (at least 32 characters, constant-time comparison, `401` otherwise). When the token is unset or too short, the endpoint answers `404`. It is meant for the internal network only. Since #27, setting `DATABASTION_METRICS_PORT` serves it on a dedicated listener of the web process, bound to `DATABASTION_METRICS_HOST` (an IP address, `127.0.0.1` by default), and the main port then answers `404` on `/metrics`. Without a dedicated port, `/metrics` stays on the main port: block the path on the public reverse proxy (a production start warns about it).

### Web UI headers (#21)
UI pages get a `Content-Security-Policy` with a per-request nonce: `script-src 'self' 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`. It is not applied to `/api/*` and `/metrics`, which serve no HTML.

### Authentication rate limits
Every login or agent authentication that needs an argon2id verification is counted **before** the verification runs and refunded on success, so concurrent requests cannot exceed the limits. Logins, agent authentications and enrollments use separate, bounded argon2id pools (4, 8 and 2 concurrent operations per process; `503` + `Retry-After` when full), plus a pool of 4 reserved for agents presenting a known-good secret, so a login flood or a flood of wrong agent secrets cannot block a legitimate agent. Per-IP limits apply only when the client IP is known, that is behind a trusted reverse proxy explicitly configured (`DATABASTION_TRUST_PROXY` / `DATABASTION_TRUSTED_PROXY_HOPS`); otherwise only the per-user / per-agent limits and the pool caps apply. The argon2id pools are per process; the rate limits are shared by every console process (see [Shared rate limits](#shared-rate-limits)). Details: `console/README.md` ("Brute-force protection").

**Agent authentication** (all windows 5 min; #27, #32):
- **Per IP, argon2-backed only**: 50 failures per source IP, counting only failures that ran an argon2id verification.
- **Per IP, cheap failures**: a separate counter of 500 per source IP (IPv6 bucketed by /48, the other agent limits use /64) covers failures that need no argon2id work (missing or malformed headers or secret, unknown or inactive agent, `/rotate` body missing its read deadline). It only gates reaching the argon2id path.
- **Per agent**: 10 argon2-backed failures per (agent id, source IP), or per agent id alone when the IP is unknown.
- **Exemptions**: a secret verified less than 25 s ago (verified cache) or known good (current or pending) is held by none of these limits, so junk requests from a shared NAT or proxy IP, which need no secret, cannot block the agents behind it. The exemptions never authenticate: the secret is still checked against the hash-bound cache or a full argon2id verification.
- **Known-good fingerprints**: the console remembers which secrets it has verified for an agent as an HMAC-SHA256 fingerprint keyed with an HKDF-SHA256 subkey (`agent-known-good.v1`) of `DATABASTION_ENCRYPTION_KEY`, bound to the stored hash, valid 24 h and persisted across restarts. A known-good secret uses the reserved agent pool. Without a usable key, nothing is stored and nothing matches (fail closed); only the 25 s cache exemption remains.
- **Pending secret (`S1`)**: a pending secret registered by `/rotate` is recognized as known good in the same way, so the agent's `S1` probe is exempt too.
- **Previous secret (`S0`)**: attempts authenticated with the previous secret go through the same argon2id path and count against the per-agent and per-IP failure limits like a wrong secret. They are refunded only when `/rotate` answers an idempotent `duplicate`.
- **`/rotate` body**: a cheap precheck (protocol headers, secret format, failure limits) runs before the body is read. The body is capped at 64 KiB and must arrive within 10 s; a body that misses the deadline is answered `400` before any argon2id work, never causes a lock, and counts against the cheap per-IP counter only.
- **Known limitation (N4)**: the known-good exemption is checked first against an in-memory copy of the agent row, then against the row itself; that database read is skipped while the source IP is over the cheap limit. Right after a console restart (empty in-memory copy), a known-good agent behind an IP over the cheap limit can therefore wait up to 5 min, until the window expires, like the other clients of that IP.

**Logins** (all windows 15 min; #32):
- 20 failures per source IP (IPv6 addresses bucketed by /56 for logins, /64 elsewhere).
- 5 failures per (username, IP bucket): a failure flood from one IP answers `429` from that IP only and never locks the account out for other IPs.
- 100 failures per username across all IPs. Reaching this global cap never refuses the login: the username degrades to a slow-down (2 s before the verification) with one attempt in flight at a time; other concurrent attempts for that username get `503` + `Retry-After`. Wrong passwords still answer `401`.
- With an unknown client IP (no trusted proxy), the per-username counter is shared by every client: reaching it never answers `429`, the login degrades to the same slow-down path, and the slow-down grows with the username's failed degraded attempts: 2 s, doubling per failure, capped at 30 s (#37). With a known IP it stays at 2 s.
- Failures on unknown usernames share a global budget of 30 per 5 min (shared by every console process). Every login reserves it, and a known username gives it back, so the store use does not reveal whether a username exists ([ADR-0024](adr/0024-shared-rate-limits.md) decision 5).
- **Device cookies** (OWASP "device cookies"): every successful login sets a 90-day `HttpOnly`, `SameSite=Strict` cookie (`__Host-` prefixed and `Secure` in production, unless `DATABASTION_INSECURE_COOKIES=1`) carrying the user id, the issue time and a random nonce, signed with HMAC-SHA256 under the HKDF subkey `login-device.v1` of `DATABASTION_ENCRYPTION_KEY`; nothing is stored server side. A valid cookie for the username being tried bypasses **only** the global per-username cap and the degraded slot, so a distributed guessing attack cannot keep the real user out. It never replaces the password and stays subject to the per-(username, IP) limit, the login argon2id pool and a per-cookie limit of 5 failures per 15 min (beyond, it gives no bypass). Failures made with a device cookie still count toward the global per-username cap (#37). Without the server key, no device cookie is issued or accepted.

### Console login with OpenID Connect
*Introduced by P8-A; decisions in [ADR-0038](adr/0038-console-oidc-login.md); configuration and details in `console/README.md` ("Single sign-on (OIDC)").*

- **Flow**: Authorization Code with PKCE (S256), confidential client (`client_secret_basic` by default), `query` response mode only; an `id_token` is required. Discovery from the issuer with an exact `issuer` match, `https://` endpoints only (plain HTTP on loopback outside production), TLS always verified (`DATABASTION_OIDC_CA_FILE` adds a CA, there is no "skip verify"). Every provider call follows no redirect, times out after 5 s and is size capped before parsing. A provider down at startup does not stop the console; discovery is retried with backoff.
- **`id_token`**: algorithms = `DATABASTION_OIDC_ID_TOKEN_ALGS` ∩ the provider's list, never `none` or `HS*`; the JWK selected by `kid` must match the algorithm (`kty`, curve, `alg` when present, `use` absent or `sig`); `iss`, `aud`, `azp`, `exp`, `nbf`, `iat` at most 10 minutes old, 60 s of skew, `nonce`. JWKS refetched at least hourly, at most once a minute on an unknown `kid`.
- **State**: 256-bit `state` and `nonce` and the PKCE verifier in a `__Host-`, `HttpOnly`, `SameSite=Lax`, 10-minute cookie encrypted under `oidc-state.v1`; single use enforced server side (SHA-256 of consumed states). The callback lands on `/agents` through a same-origin page (no `return_to`), so the `SameSite=Strict` session cookie is sent; a provider `error` shows a generic page, its description is never echoed.
- **Identity key (`iss`, `sub`)**, never the e-mail: no automatic linking by e-mail or username (CVE-2023-3128 class); linking is self-service from the user's own local session; administrators approve pending logins only as **new** users. A login claim equal to an existing username is refused.
- **Authorization** reads provider-controlled claims only (groups, roles), through bounded JMESPath expressions; anything but exactly `admin` / `analyst` is no role; strict mode (default) refuses such logins. Allowed domains need `email_verified: true` and an exact domain after the last `@`. Sign-up is off by default and, when on, requires a group filter or a strict role expression (else the console refuses to start). The role is synced at each login (and refresh); a demotion ends the user's other sessions. A disabled user cannot log in by any method.
- **Local login** (`DATABASTION_LOCAL_LOGIN`): `enabled` (every local user), `admins` (local administrators only, the default while OIDC is on; other local users get the same `401` as a wrong password) or `disabled` (only when set explicitly: `/api/auth/login` answers `404`, recovery needs host access). **Break-glass**: while OIDC is on, each successful local administrator login raises the `user.local_login` system alert (within the hourly system-alert budget, [ADR-0033](adr/0033-system-alert-budget.md)) and its `user.login` entry carries `break_glass: true`; the web process logs an error at startup when `admins` is set and no enabled local administrator with a password exists. Single sign-on users have no local password. The local login keeps its own limits ([Authentication rate limits](#authentication-rate-limits)).
- **Users page** (introduced with P8-A): administrators create local users, change roles and disable accounts; the console refuses to disable or demote the last enabled administrator (`409 last_admin`), an administrator's own account (`409 self`), and a role change of a single sign-on user while role sync is on (`409 role_managed_by_provider`). Disabling ends the user's sessions.
- **Sessions**: same server-side sessions (`SameSite=Strict`, 2 h idle), tagged with their method and the provider `sid`, at most `DATABASTION_OIDC_SESSION_MAX_AGE` (default and maximum 12 h). With `DATABASTION_OIDC_USE_REFRESH_TOKEN=1` the refresh token is stored encrypted (AES-256-GCM under the HKDF subkey `oidc-tokens.v1`, bound to the session by its AAD) and used at most every 5 minutes on activity; a failed refresh, provider outage included, ends the session. Access and ID tokens are never stored. Logout (`POST` + CSRF) deletes the session, revokes a held refresh token at the provider (RFC 7009) when it advertises a revocation endpoint, then performs RP-initiated logout (`client_id`, `logout_hint`).
- **Role sync guards**: role sync never demotes the last enabled administrator (role kept, refusal audited, `user.role_sync` system alert), and demoting an administrator that holds a local password (break-glass) raises the same alert. A demotion ends the user's other sessions.
- **Linking and unlinking**: linking is self-service from the user's own **local** session only (`409 local_session_required` otherwise) and requires a fresh authentication at the provider (`prompt=login`, `max_age=0`, `auth_time` no older than the start of the link). An administrator can unlink an identity (its sessions end, `user.identity_unlink`), never the last login method of a user: the only identity of a single sign-on user (`409 last_identity`), or the only identity of a local user whom the current local login mode keeps out (`409 no_other_login_method`). Pending logins are kept at most 7 days and 1000 rows (the least recent is evicted, evictions counted and shown), and store mapped attributes only, never raw claims or tokens.
- **Refresh tokens of ended sessions** (disable, demotion, unlink, expiry, failed refresh) are revoked at the provider in the background, scheduled only after the change is committed, best effort (two attempts, at most 100 per action and 8 jobs at a time per process, beyond which they are skipped and logged); the local action never waits for the provider.
- **Rate limits** (shared by every console process, failing closed, [ADR-0024](adr/0024-shared-rate-limits.md)): per client IP and 5 minutes, 60 starts (`/api/auth/oidc/start` and the link start) and 30 callbacks; a start is given back and a callback refunded when the flow succeeds, so many users behind one NAT address are not throttled. Globally, 300 failed callbacks per 5 minutes, counting only `id_token` refusals after a successful code exchange (`id_token`, `nonce`, `iss`, a stale `auth_time` on a link), which need a code the provider issued, and checked only once the state cookie is valid: cookie-less or forged callbacks, codes the token endpoint rejects and transport errors cost their sender's per-IP budget only, so they cannot block single sign-on for everyone (P8-A security review M1).
- **Audit log**: `user.login` (`method: oidc`), `user.login_denied` with a closed reason list (`state`, `nonce`, `iss`, `token`, `id_token`, `provider_error`, `rate_limited`, `group`, `domain`, `email_unverified`, `role`, `sign_up`, `disabled`, `username`), `user.signup`, `user.pending_login_approve` / `_discard`, `user.identity_link` (with the session method and (`iss`, `sub`)), `user.identity_unlink`, `user.role_change` (source `oidc` or `user`), `user.create`, `user.disable`, `user.enable`, keyed by user id. The client secret and `_FILE` contents never appear in errors or logs; tokens, codes, the state, the nonce and raw claims are never logged nor stored (only the encrypted refresh token).
- **Residual risks**:
  - without refresh (or back-channel logout, planned), a user disabled at the provider keeps the console until the session's maximum age (12 h by default);
  - a provider compromise, or a provider administrator, gives console access up to the mapped role; the break-glass local administrator does not prevent this;
  - the role, group and domain expressions are operator-written: an expression that reads a user-editable claim (`email`, `preferred_username`, `name`) lets users choose their role. The dev realm and the end-to-end scenario test a user who edits these attributes (#139), not the operator's own expression;
  - provider metadata is cached for the life of the process: after the provider changes its endpoints or algorithms, restart the console; after a failed JWKS refetch, keys are kept up to their `max-age`, at most 24 h;
  - refresh-token revocation is best effort: a provider that is down, or a revocation job skipped at the per-process cap, leaves the refresh token valid at the provider until it expires there;
  - `client_secret_post` (opt-in) sends the client secret in the request body, where proxies and provider logs are more likely to record it;
  - a rate-limit store failure blocks OIDC starts and callbacks (fail closed), and the global budget can still be spent by someone able to obtain codes from the provider (an account there).

### Shared rate limits
*Introduced by P4-D (#69); decisions in [ADR-0024](adr/0024-shared-rate-limits.md); details in `console/README.md` ("Shared rate limits").*

Every console rate limit (agent authentication failures, `/enroll`, `/rotate` and its late retries, the `/findings` and `/events` request and stored-batch rates, the agent-integrity and failed-enrollment audit budgets, failed logins, channel test sends) keeps its counters in the console PostgreSQL (table `rate_limit_counters`), so N web processes enforce one limit, not N.
- **Keys**: stored only as HMAC-SHA256 under the server-key subkey `rate-limit-keys.v1`, never in clear (IPs, usernames as typed, device nonces, agent ids). Without a usable server key (in production only with the `DATABASTION_ALLOW_MISSING_ENCRYPTION_KEY=1` override), the limits keyed by the typed username stay per process and are never stored; the other keys are stored as a domain-separated, unkeyed SHA-256, so a database dump allows testing guesses of them.
- **Atomicity**: each decision is one statement; a reservation is guarded by `count < limit`, so concurrent requests from any process cannot overrun a limit. Each process also pre-checks its own hits in memory and remembers keys the store reported at their limit until the end of the window; this can only refuse earlier, never admit more.
- **Isolation**: the counters use a dedicated pool of 3 connections (`lock_timeout` 1.5 s, `statement_timeout` 2 s, 2 s to get a connection), so a hot counter row cannot starve the rest of the console.
- **Store failure**: an error, a timeout or no free connection opens a per-process circuit breaker for 1.5 s. Authentication and user actions **fail closed** (`429` + `Retry-After: 5`): agent authentication failures, `/enroll`, `/rotate`, logins, channel test sends. During an outage only an agent secret verified by this process less than 25 s ago, or known good per its in-memory hint, still authenticates. Ingest rates and audit budgets (`/findings`, `/events`, integrity and failed-enrollment budgets) and the `/rotate` late-retry limit fall back to the per-process counters (the pre-P4-D behavior), so a limiter hiccup neither makes every agent back off nor locks an agent irreversibly. Failures are counted in `databastion_console_rate_limit_store_errors_total` and logged at most once per minute per limiter, never with the key.
- **Pruning**: the worker job `rate_limits.prune` deletes expired windows every 5 minutes; the table size is exported as `databastion_console_rate_limit_counters_rows`, to alert on floods of distinct keys.
- **Residual risks** ([ADR-0024](adr/0024-shared-rate-limits.md#residual-risks)): a flood of distinct keys can saturate the dedicated pool, and the fail-closed limiters then answer `429` until it recovers; an agent known good only per its database row (e.g. first request to a freshly started replica) gets `429` while the store fails; a server-key rotation resets the counters.

## Findings ingestion
*Introduced by P2-D (#36, #37); normative checks in [`shared/protocol/openapi.yaml`](../shared/protocol/openapi.yaml) ("Console-side checks"), overview in [09-agent-protocol.md](09-agent-protocol.md#console-side-checks-on-findings).*

- **Rate bounds per agent** (shared by every console process, per-process fallback if the shared store fails, see [Shared rate limits](#shared-rate-limits)): 60 **stored** findings batches per minute (duplicates and rejected batches give their slot back), and 300 `POST /findings` requests per minute whatever their outcome, which bounds the validation and database work of rejected batches. Beyond either: `429` + `Retry-After`.
- **Per-job cap**: at most 50 000 findings per scan job over all its batches, enforced atomically (one agent's batches are ingested one at a time).
- **Late window**: a scan job accepts findings while it runs, up to `first_delivered_at + max_duration_s + 1 h` (anchored on the first delivery since #94), and for 24 h after it finished (counted from that deadline at the latest); later batches get `404`, so an agent cannot keep writing into old jobs.
- **Integrity events**: a rejected (`400`) findings batch, a `batch_conflict` and a finding for a target the agent does not own cannot come from a conforming agent. Each writes an audit-log entry and a `security_events` row (with a bounded write budget, so a hostile agent cannot flood the table); the body is never logged.
- **Classifier registry and console downgrades** (operator note, console registry checks, #41): the console serves a `discovery.scan` job only if its `classifiers_version` is in the console's classifier registry (`classifiers.json`) and its `params.classifiers` ids belong to that version. If the console is downgraded to a build whose registry no longer contains a version, pending scan jobs carrying that version fail closed: they are marked `failed` with `internal` when claimed and never sent to the agent. Launch the scans again once the agents report a version the console knows.
- **False positives**: only administrators can mark or unmark a finding as a false positive (CSRF-protected, audited). The mark records `matched` and `classifiers_version`; a later scan that matches more values or uses another classifier set clears it automatically (audited as a system action), so a mark cannot silently hide a growing exposure.

## Access events ingestion and correlation
*Introduced by P4-C (#54); decisions in [ADR-0021](adr/0021-access-event-correlation.md); details in `console/README.md` ("Audit correlation"). The PostgreSQL agent produces access events since P4-A (#58, see [08-engine-capabilities.md](08-engine-capabilities.md#postgresql-audit)), MySQL / MariaDB since P4-B (#64, see [08-engine-capabilities.md](08-engine-capabilities.md#mysql--mariadb-audit)).*

- **I2 for events** ([ADR-0007](adr/0007-mask-access-events.md)): the contract has no field for query text, bound parameters or returned values, every object is closed, and unknown fields are rejected (`400`) before anything is stored. The console stores exactly the contract fields. The metadata ADR-0007 allows in clear (`db_user` or its `hmac-sha256:` fingerprint, `client_addr`, `application`, normalized object names, counts, signals) is stored in plain columns and shown as text (escaped on display). Grouping keys are SHA-256 hashes, never agent text. Signal ids and target-note codes are closed by form (letters and `_` only, no digit, so an id cannot carry a number) and registered append-only in `shared/protocol/signals.json` and `target-notes.json` (#60); the console stores an unregistered but well-formed id and shows it raw. Notifications carry this metadata and the score, never a value. The I2 end-to-end test covers this path since #66 (see "Invariant I2 test" above).
- **Ingestion checks** (`POST /events`): authentication, 4 MiB body cap (`413`), schema then `checkSemantics` (patterns of names and account names, 1 MiB batch, `ts_last < ts` → `400`, `/events/<i>/ts_last`, `formatMinimum`); then, in one transaction serialized per agent, the idempotency check on (`agent_id`, `batch_id`), target ownership (`404`, `notFound`), timestamps more than 5 min ahead (`400`, `formatMaximum`), and `ts` older than the retention period (`400`, `/events/<i>/ts`, `formatMinimum`). Rejected batches, conflicts, foreign targets and future timestamps are agent-integrity events; expired events are counted only, since a conforming agent with an old spool can send them. Events of a target that is no longer reported, or whose Audit is disabled, are stored and flagged `unexpected_target`.
- **Rate bounds and back-pressure**: 300 requests and 60 stored batches per minute per agent (shared by every console process, per-process fallback if the shared store fails; `429`), and `429` + `Retry-After: 30` while the agent has more than 20 000 events not evaluated yet (read from the database). The agent keeps its batches spooled.
- **Insert-only events**: the runtime role cannot rewrite or delete what an agent reported; it only writes the evaluation columns. Incidents raised from events are not deletable either (ADR-0014).
- **Owner-defined functions**: the only deletions the runtime role can make go through two `SECURITY DEFINER` functions owned by the migration role, with `search_path` pinned to `pg_catalog, pg_temp`, `EXECUTE` revoked from `PUBLIC` and granted to the runtime role only, and clamped parameters:
  - `databastion_purge_access_events(retention_days, max_rows)` (migrations `0022`, `0024`): retention clamped to [7, 3650] days, chunk to [1, 100 000]; deletes evaluated events older than the retention (never an event not evaluated yet), replay records 30 days after that, and baselines idle for longer than the retention. A compromised console process can at worst purge evaluated events older than 7 days.
  - `databastion_evict_principal_baselines(agent_id, target_id, cap)` (migration `0026`): cap clamped to at least 10; deletes only the baselines of that target beyond the cap, least recently updated first, at most 1000 per call.
- **Hostile agents**: baselines are fed only by events with `rows` that are neither `connect` nor `auth_failure`, and are capped per target; in the dedup scope, failed logins (`auth_failure`) are grouped by client network (/24, /64), and every other event is keyed by its principal (the account name or its fingerprint), so two fingerprinted users, OpenLDAP ones included, never share an incident (#81, [ADR-0031](adr/0031-openldap-principals-dedup-and-stream-alerts.md) decision 1); after a false positive, a later event of the key within the hour opens a new incident only when it is clearly worse (a new `signature.*` signal, a higher score, or more rows linked since the mark than the incident's own total; ADR-0031 decision 2); a policy opens at most a configured number of incidents per target and hour, beyond which matches go to one overflow incident (severe events still open their own). Details and residual risks (baseline slow-ramp poisoning, rows-only volume, table-level sensitivity): [ADR-0021](adr/0021-access-event-correlation.md#residual-risks).
- **Audit settings** (`audit.configure`, admin): a change that disables Audit, empties `sensitive_objects` or removes many objects needs a confirmation of the exact settings, is audited, and leaves a warning on the target.

**Residual risks** (end-of-phase-4 review):
- **Account names in clear.** `db_user` and `application` are sent unmasked by design ([ADR-0007](adr/0007-mask-access-events.md)): they identify who reads, not what is read. When the server's accounts are e-mail-shaped IAM names or carry personal identifiers, those values reach the console, its views and the `incident.opened` notifications. They are stored as account names, not as findings.
- **Failed-login flood (MySQL / MariaDB Audit).** A client that can reach the database port, even without credentials, can try many made-up user names. Each name creates its own `auth_failure` event group, which always passes the `audit.configure` filter. At the console's rate bounds (60 batches of 500 events per minute per agent, back-pressure at 20 000 pending events), the batches of a later dump queue behind the flood and its detection is delayed. Once the spool is full, the oldest batches, findings included, are evicted. The console can store about 30 000 such rows per minute per agent, kept for the event retention (90 days by default). The flood shows in the spool's dropped counters and the back-pressure metric. Since #75 the console also alerts when an agent's dropped counter rises: an `agent.batches_dropped` security event (`medium`), notified to the `system_alerts` channels at most once per agent and hour (see [Alerting](#alerting)); the alert reports the loss, it does not prevent it. Details in [08-engine-capabilities.md](08-engine-capabilities.md#known-limits-1) and [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) (consequences, in the scope of [ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md)). Since #88 the agent caps the flood ([agent/README.md, "Failed-login flood"](../agent/README.md#failed-login-flood)): per target and aggregation window, at most 100 named `auth_failure` groups; further attempts are first counted per principal in a folded table of at most 256 entries (the least attempted leave first; among ties, the most recently added entry is evicted, so fresh junk names evict each other rather than an older account), and a principal attempted more often than the least attempted named group takes its place. Everything beyond goes into **overflow** events (an `auth_failure` of an unidentified account, per client address for at most 16 addresses, then one without address, with the attempt count), so a flood gives at most 117 `auth_failure` events per window and no attempt goes uncounted (`auth_failures_overflowed_total` counts the failed logins beyond the 100 named groups). The cap is in the engine-agnostic agent core: it applies to the `auth_failure` events of every engine. The spool evicts by priority: findings and events each keep up to 3/4 of the bounds, and batches with a `signature.*` signal are dropped last (`spool_rejected_batches_total` counts new batches dropped on arrival). Each class can grow to 3/4 of the spool bounds, so the other always keeps at least 1/4: an events flood can still evict findings down to that quarter. Known limit: an attacker can keep 100 junk names above root's per-window count and so keep root out of the named groups, at about 100 times root's volume, visible in the overflow count.
- **False-positive row rule and missing row counts** (PR #81 review L2). The "more rows than the false positive" rule of ADR-0031 decision 2 does nothing on sources that report no row counts (MySQL / MariaDB audit-log files, the MongoDB `auditLog`, OpenLDAP compares and binds): there, after a false positive, only a new `signature.*` signal or a higher score opens a new incident within the hour ([ADR-0033](adr/0033-system-alert-budget.md) residual risks).
- **Concurrent close.** When an event finds its open incident closed meanwhile (a user marked it after the evaluation chunk read it), the event is only linked to the closed incident, without the "clearly worse" check; a new incident can open only from the next event of the key.
- **MySQL / MariaDB audit-log grouping** (#93, refines [ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md), [08-engine-capabilities.md](08-engine-capabilities.md#one-event-per-statement-audit-log-files)). Records are grouped per connection and query id in bounded state (1024 connections, 64 tables per statement, 16 MiB pending, 8 MiB of hashes for statements reported early, kept 10 minutes); held statements are replayed from a rewound cursor after a restart, and evictions are counted (`audit_pending_evicted_total`). Residuals: statements held in an already-rotated file are lost when the agent stops; the memory of statements reported early is not persisted, so a late statement record is counted alone after a restart or a graceful end of the stream; without query ids (`audit_log_filter`), repeats of one statement text on a connection can merge into one event (undercount). A client that floods the grouping state forces early reports (counted); the later tables of a statement reported early are still reported, as a continuation.
- **Whole-second times on some sources.** The console stores event times in milliseconds, but OpenLDAP `reqStart` (whole seconds and a per-second operation counter) and MariaDB `server_audit` give whole seconds only: events of the same second from those sources cannot be ordered by time. The pgaudit `jsonlog`, MongoDB and `performance_schema` sources keep sub-second times.

## Alerting
*Implemented in P3-C (#49); decisions in [ADR-0017](adr/0017-alerting.md); details in `console/README.md` ("Alerting").*

- **Payloads carry no sampled value**, masked or not (I2): identifiers, counts, normalized names and a console link only. The masked samples stay encrypted on the finding.
- **Webhook signature**: `X-DataBastion-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(signing secret, "<t>.<raw body>")>`; receivers compare in constant time, reject a `t` older than 5 minutes and deduplicate on `X-DataBastion-Delivery` (delivery is at least once). In `incident.opened`, the principal is the database account name reported by the agent, as a JSON string. Any client of the database can choose that name, for example with a failed login. Receivers must escape it wherever they render it (HTML, chat markup, shell, spreadsheets). The same holds for the principal in an access-incident e-mail (plain text, not HTML-escaped) when a consumer turns it into HTML, and, with a narrower character set, for the other names in a payload (#75; details in `console/README.md`, "Alerting").
- **Channel secrets**: the webhook signing secret is generated by the console (256 bits) and shown once; SMTP passwords are entered by an administrator. Both, and the full webhook URL, are encrypted with AES-256-GCM under the HKDF subkey `notification-channels.v1`, with the channel id and type in the AAD. They are never returned by the API, logged or written to the audit log. Changing an e-mail channel's host, port, TLS mode or user requires its password again.
- **SMTP**: implicit TLS or mandatory STARTTLS (no downgrade; bytes received in clear after the STARTTLS `220` abort the session), certificates always verified, AUTH only over TLS. Plain-text SMTP only towards a loopback relay, or with the development flag.
- **Outbound address policy (SSRF)**: only the worker connects out. Every resolved address is checked, the socket connects only to the checked addresses (in resolver order, falling back on a connection error), and IPv4 addresses embedded in IPv6 transition addresses are checked as IPv4. Link-local and metadata addresses, unspecified, multicast, broadcast and reserved ranges are always refused. Loopback, private, CGNAT, ULA, documentation and benchmarking ranges and the transition prefixes are refused for webhooks and allowed for SMTP relays. Webhooks require `https://`, redirects are never followed, and no HTTP proxy is used.
- **Development flag**: `DATABASTION_ALERTING_INSECURE_DEV=1` allows `http://` webhooks, internal webhook destinations and plain-text SMTP to a non-loopback relay (link-local and metadata stay refused). In production the web and worker processes refuse to start with it unless `DATABASTION_ALERTING_INSECURE_DEV_I_UNDERSTAND=1` is also set.
- **Silent agent**: an agent that was online and has sent no heartbeat for `DATABASTION_SILENT_AGENT_INTERVALS` × 30 s (default 5 minutes) raises one alert per silence episode, recorded in `security_events` (insert-only for the runtime role) and notified to the channels flagged `system_alerts`. Agent-integrity events are notified to the same channels, at most once per agent, kind and hour per channel. The same holds since #75 for **dropped batches**: when the `spool.dropped_batches` counter reported in the heartbeats rises (batches the agent dropped because its spool was full or the console refused them with a non-retryable `4xx`), the console records an `agent.batches_dropped` security event (`medium`) and an audit entry, and notifies the `system_alerts` channels, at most once per agent and hour; drops within the hour are counted in the next alert. The alert carries only console-computed numbers, timestamps and ids, no agent-provided text. Revoked and locked agents are not alerted. Since #81, a target that reports `audit.stream_stopped` (its Audit stream stopped after repeated internal errors, see [Connector obligations](#connector-obligations)) raises an `agent.audit_stream_stopped` security event (`medium`), an audit entry and a notification, at most once per agent and hour and **again every hour while the stream stays stopped** ([ADR-0031](adr/0031-openldap-principals-dedup-and-stream-alerts.md) decision 3). These system alerts extend decision 5 of [ADR-0017](adr/0017-alerting.md); details in `console/README.md` ("Alerting").
- **Volume bounds**: at most `DATABASTION_NOTIFY_MAX_PER_HOUR` (default 30) incident notifications per channel and hour, then one digest; channel tests limited to 10 per administrator and 3 per channel per 10 minutes (shared by every console process, fail closed; see [Shared rate limits](#shared-rate-limits)).
- **System-alert budget** (#81, [ADR-0033](adr/0033-system-alert-budget.md)): every system alert (silent agent and recovery, integrity, dropped batches, stopped Audit stream) is charged to a budget of `DATABASTION_SYSTEM_ALERTS_MAX_PER_HOUR` (default 20) per channel and UTC clock hour, all agents together, of which one agent may use at most `max(2, ceil(limit / 4))`. Both counts live in PostgreSQL and are charged in the transaction that records the alert, so they hold across console processes. Beyond them, the delivery is skipped and counted in one `system_alerts.suppressed` digest per channel and hour; the security event is still recorded. Only `agent.integrity` alerts of kind `agent.rotation_conflict` and severity `critical` bypass the budgets (an allowlist of kinds, never the severity alone).

**Residual risks** ([ADR-0017](adr/0017-alerting.md#residual-risks), [ADR-0033](adr/0033-system-alert-budget.md#residual-risks)): only the well-known NAT64 prefix has its embedded IPv4 address checked (the local-use prefix `64:ff9b:1::/48` is internal as a whole, so allowed for SMTP; operator-chosen prefixes are not recognized); the system-alert budget and the per-agent share hold only when every console process (web and worker) uses the same `DATABASTION_SYSTEM_ALERTS_MAX_PER_HOUR`, since each process computes the limit from its own environment; silent-agent alerts are now counted in that budget, so a large outage or several misbehaving agents can push non-critical alerts into the hourly digest; e-mails are plain text only.

## Agent local state and results path
*Introduced by P1-B (#16, #20); details in `agent/README.md`.*

- **State directory**: must be owned by the agent user and not group / world writable (`0700` expected, another mode warns). State files (`identity.json`, `hmac.key`, spool batches) are `0600`, written atomically, opened with `O_NOFOLLOW` and checked on the handle (regular file, owner, no group / other access).
- **Spool**: bounded by `spool.max_bytes` (default 256 MiB) and `spool.max_batches` (default 10000), oldest dropped first. A file that cannot be parsed or fails the state-file checks is moved to `spool/quarantine/` (32 kept), counted and never logged; it does not crash the agent. A response that is not a contract answer (e.g. an HTML page from a middlebox) keeps the batch, so an intermediary cannot empty the spool.
- **Name normalization** ([ADR-0009](adr/0009-name-normalization-and-item-sanitization.md)): array indices of up to 6 digits become `[]`; any segment with more than 6 digits, UUIDs and e-mail addresses become `*`; an LDAP entry DN is reduced to its parent container. Since #39, segments matching a classifier (including values split across dots) and common first names also become `*`; see the residual risks under [Masking and fingerprints](#masking-and-fingerprints).
- **Per-item sanitization**: every finding or event is checked against the contract before spooling; an item still invalid is dropped and counted, not the whole batch. An account name that does not conform is replaced by its HMAC fingerprint (`db_user` domain, #39); an event is dropped and counted only if no conforming principal can be built.
- **Local engine detection** ([ADR-0006](adr/0006-target-discovery.md)): read-only and local, no network I/O. The agent checks a fixed list of Unix socket paths (never connects), `LISTEN` entries of `/proc/net/tcp{,6}` for the default engine ports (addresses not reported) and process names in `/proc/<pid>/comm` (never the command line); at most 16 entries. In a container without host networking, it sees only its own network namespace and processes, so detection finds little or nothing on the host.

## Connector obligations
Requirements for every connector (acceptance criteria of P2-B and P2-C, in addition to the PostgreSQL obligations of [ADR-0012](adr/0012-postgresql-agent-grants.md)):
- **No database resource held across `FindingSink::submit().await`.** `submit()` can block for a long time: the findings channel is bounded, and while `/findings` is parked after a `501` the scan worker holds its chunk and stops reading, possibly until the scan deadline ([09-agent-protocol.md](09-agent-protocol.md#agent-side-handling-of-job-parameters)). A connector collects the findings of one table or sample, closes the transaction and any server-side cursor, then submits; it never keeps a transaction or cursor open while awaiting `submit()`.
- **Panic isolation in the core** (#79, security review H1, every engine). Connectors parse what a possibly hostile server sends; a bug there must not stop the agent. The core runs every connector call (`check`, `discover`, `audit_stream`) through a panic guard: a panic fails that call and is counted (`connector_panics_total`). Since #83 ([ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md)), Audit is protected at three levels:
  - **Per record.** The log-file sources (PostgreSQL pgaudit, MySQL / MariaDB audit logs including their connection lines, the MongoDB `auditLog` and server log), the MongoDB profiler and the OpenLDAP accesslog parse and convert each record in isolation (PostgreSQL and the MySQL / MariaDB log files: each statement's group of records). Since #88 the polled sources are isolated per statement too: `performance_schema` (its conversion) and `pg_stat_statements` (its text's analysis and its conversion). On `pg_stat_statements`, the result of a statement's analysis is cached per (`userid`, `dbid`, `queryid`, `toplevel`). Since #90, a statement whose analysis or conversion panics is cached as poisoned (not analyzed or converted again; the panic is counted once in `audit_record_panics_total` while the statement stays in the analysis cache (cleared beyond 20 000 entries, after which it is analyzed or converted again and counted again)), and each of its later deltas is **reported as a read of unknown objects (`*`)** with the delta's calls and rows. That event is built from the counters, the role and the database only (no statement text, I2), is never treated as the agent's own activity and is never charged to a row budget. It is always a read whatever the statement did: it over-reports on purpose (a write or DDL shows up as a read of `*`) rather than let a client that finds a statement shape that makes the agent panic repeat it unreported. This fallback event refines [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decisions 1 and 4 (per-record isolation; a failed unit is dropped and its loss counted) for `pg_stat_statements`, where the isolation was added by #88; ADR-0032 itself is not amended. On the other sources, a record whose handling panics still only reaches the counters: [ROADMAP](ROADMAP.md#phase-7--hardening--v010-release) phase 7 follow-up, a masked "conversion failed" access event. On the isolated sources, a record whose handling panics is dropped alone and counted as dropped (`audit.records_dropped`; not a poisoned `pg_stat_statements` statement, which is reported, not dropped, and since #93 no longer counted there), and the heartbeat metric `audit_record_panics_total` counts one per failed unit (a record or a statement group). The stream goes on.
  - **Exact skip, OpenLDAP only.** A panic that still ends a stream restarts it. The OpenLDAP stream restarts in isolation mode: it saves its position after every entry for one read round, so a panic that comes again is at the exact entry. After 3 panics at that exact position, that one entry is skipped, counted as dropped and in `audit_records_skipped_total`. The file sources do not skip: their record handling is already isolated.
  - **Stop.** A stream is stopped after 7 panics at one saved position with no progress, more than 8 skips or 64 panics within an hour, or 3 panics in a row for a source whose position is not persisted (`pg_stat_statements`; since #88 the `performance_schema` cursor and the MongoDB profiler positions are persisted). A stopped stream reports the level None with the note `audit.stream_stopped`, and the console raises the `agent.audit_stream_stopped` system alert every hour while it stays stopped ([Alerting](#alerting)). Reconfiguring Audit or restarting the agent restarts it from its persisted cursor.

  Records dropped or skipped this way lose their events (except on `pg_stat_statements`, above): a client that can get a record written that crashes a parser hides that record. On PostgreSQL and the MySQL / MariaDB log files, a conversion panic drops the whole statement group. These losses are counted (target note and heartbeat metrics), but the console raises no alert on them and they reach no policy (ROADMAP follow-up: a masked "conversion failed" access event). The process-wide panic hook, installed by the binary right after logging is set up, logs the code location, the thread name and a panic id, never the panic message (which can quote the data being parsed). Connector crates must still not panic on input: the OpenLDAP crate denies unchecked string slicing and indexing outside tests.
- **Discovery goes through the core's pacing** (I4, database impact; #93, [ADR-0035](adr/0035-discovery-pacing.md), proposed). A connector runs each unit of work against the target (an object's sampling, a catalog read, a listing) through `ScanJob::paced`, which charges `busy × (100 − d) / d` (failed and timed-out units included) as a debt paid before the next unit (`ScanJob::turn`), never after the last one. The agent's time in queries stays at most `d` % of the scan's time, so a scan costs the server at most about `d` % of one core (one connection per scan, one scan at a time per agent). `d` is the local limit `limits.discovery_duty_cycle_percent` (default 1, range 1 to 100, `100` disables pacing); the console cannot set or raise it. A connector releases what a unit held before the pause (a MySQL / MariaDB idle session is closed when the debt reaches 45 s).
  - **Deadline stop.** The bound is never relaxed to finish in time: when the debt, plus the last unit's time and a 2 s margin, would reach the scan's deadline, the next unit does not run, the objects left are reported as `skipped_limit` and the scan succeeds. A database, naming context or whole MySQL / MariaDB target left out before its introspection counts as 1 there (its objects are unknown). When the console does not take the coverage counters (`job_progress.coverage`), such a scan is reported `failed` with `timeout` instead, so a gap never shows as a plain success. The console flags a succeeded scan with an actionable gap (`skipped_limit`, `skipped_error`, `skipped_not_readable`, `skipped_row_level_security`, objects never reached, or a `skipped_*` reason it does not know) as "partial coverage" on the agent page (#95); the by-design reasons `skipped_unsupported` and `skipped_remote` are listed without the badge. The badge is UI only: no incident, notification or alert.
  - **Rotation at two levels.** Seeded from the job id, each scan rotates first its databases (PostgreSQL, MongoDB) or naming contexts (OpenLDAP), then the objects inside each, so a slow or hostile object cannot make every scan skip the same tail or the same later databases.
  - **Stop and refusal.** A pause ends as soon as the scan is stopped (cancel token: end of its window, suspension, shutdown), and the connector then returns `Cancelled`. A scan whose `running` acknowledgement the console refuses (`404` / `409`: cancelled, expired, timed out or not the agent's) does not run.
  - **Residuals.** Not paced: connection setup and the reconnections after pauses longer than 45 s (MySQL / MariaDB) or 60 s (MongoDB, OpenLDAP), a handful per scan at most. On PostgreSQL, parallel query workers are not disabled.

  Every connector (PostgreSQL, MySQL / MariaDB, MongoDB, OpenLDAP, and since P8-B the CAS connector, one registry file per unit of work) paces through it; a new connector must too.
- **Idle timeouts on the server side** as a safety net for the same reason: `idle_in_transaction_session_timeout` on PostgreSQL (also set on the role, see below), and the equivalent idle-session and cursor timeouts on MySQL / MariaDB and MongoDB, so a paused connector cannot keep locks, snapshots or cursors open on the target.

## PostgreSQL connector
*Implemented in P2-B (#47), `agent/crates/connector-postgres`; decisions in [ADR-0015](adr/0015-postgresql-connector-decisions.md), obligations in [ADR-0012](adr/0012-postgresql-agent-grants.md); details in `agent/README.md`.*

- **TLS** (`targets[].postgres.tls`, rustls only): `verify_full` by default (certificate verified against a pinned CA file or the system store, host name checked). `disable` is accepted only for a Unix socket or a loopback IP literal. `disable_insecure` is an explicit opt-in for a network connection without TLS: the connector warns at every connection that samples and statements travel in clear and that read-only is not guaranteed.
- **Authentication without TLS**: the connector reads the server's authentication requests before the driver answers, and refuses cleartext and MD5 password requests and SCRAM with fewer than 4096 iterations. Only SCRAM, or password-less peer / trust authentication on a local socket, is accepted. The target password is read from its `agent.yaml` reference into zeroized memory and never logged (I3).
- **Read-only and bounded** (I4): every unit of work in `BEGIN TRANSACTION READ ONLY` with `SET LOCAL` `statement_timeout` (from the clamped job parameter, never `0`, at least 100 ms), `lock_timeout` (2 s) and `idle_in_transaction_session_timeout` (10 s); `search_path = ''`; no expression on sampled columns (values decoded in Rust). A statement whose future is dropped (job cancelled, deadline, shutdown) gets a server-side cancel request. Transactions are committed before `FindingSink::submit().await`.
- **Sampling bounds**: at most `sample_rows` rows per object (`TABLESAMPLE SYSTEM` on large relations, `LIMIT` otherwise), at most 32 MiB of values per relation (checked per row; the statement is then cancelled, not drained), values truncated to 4096 bytes, at most 64 leaves per partitioned root (reported under the root). Every relation is read `FROM ONLY`, a partitioned root is never read directly (its leaves are), and foreign tables and foreign leaves are never read (I5).
- **RLS policy allow-list**: a row-level security table is sampled only if its `SELECT` policy expressions, walked locally, use allow-listed node types, no relation other than the table itself, and only immutable `pg_catalog` functions outside a denylist (functions that run SQL text or resolve names at run time, and those with side effects) plus `current_setting`, `now`, `current_database` and `current_schema`. Otherwise the table is skipped and reported as not covered. The expression text is never logged or sent.
- **Honest `check()`**: audit level Full or Partial from a readable pgaudit log declared in `agent.yaml` (Full also needs `pgaudit.log_rows` proven on, [ADR-0037](adr/0037-postgresql-full-requires-pgaudit-log-rows.md), and a pgaudit record parsed in the last 24 h; P4-A, #58; since #65 the pgaudit library must be proven loaded by its `pgaudit.log_catalog` row in `pg_settings`, since placeholder `pgaudit.*` settings are readable without it), Limited with `pg_stat_statements` and `pg_read_all_stats`, None otherwise ([08-engine-capabilities.md](08-engine-capabilities.md#postgresql-audit)). Over-privilege (warned, not refused) and coverage (schemas without `USAGE`, relations without `SELECT`, skipped RLS relations) are logged by the agent and, since #68, reported to the console as `TargetStatus.notes` (closed codes from `shared/protocol/target-notes.json` with bounded counts and labels, never free text, at most 16 per target, sent only while the console lists `target_status.notes`, [ADR-0022](adr/0022-protocol-capability-negotiation.md)).
- **The agent's own activity on the Audit path** ([08-engine-capabilities.md](08-engine-capabilities.md#the-agents-own-account)): the connector's own table-less statements are left out only on an exact match. On `pg_stat_statements` (since #90), an entry is the agent's own only when all of these hold: its stored text is exactly one of the connector's statements (constants shown as `$n`, the connector's own bound parameters present), its `userid` is the oid of the agent's role, it is a top-level entry, its database is one where the connector runs that statement, and its `queryid` is the first one seen in that slot. Everything else is reported. Residual: a client holding the agent's credentials whose entry is the first one with a delta that the poller sees in the agent's own slot (after a stream start; within one poll, row order decides) gets its `queryid` pinned: the client's entry is then left out as the agent's own, and the agent's own executions of that statement are reported instead (loud), from its first execution in that slot. Only the allow-listed table-less statements (settings calls, the client-address call, the text query in the poller's database) can be hidden this way, and only by a holder of the agent's credentials. Since `queryid` ignores constant values, such a client can also share the agent's own entry whatever the constant values (setting names, the text query's length and `LIMIT`), within the 10 000-row signal per poll; on PostgreSQL 13 and older there is no `toplevel` column, so nested executions by the agent's role are not told apart. The own-account row counters are persisted with a periodic 30 s flush of unsaved charges (#90) and when a stream ends: a crash or a kill loses at most about the last 30 s of charges (when a state directory is set).
- **Server messages** are reduced to a SQLSTATE and a stage; notices are discarded.

**Residual risks** ([ADR-0015](adr/0015-postgresql-connector-decisions.md#residual-risks)):
- one row is received whole by the driver before the byte budget is checked, so a single row (a field can reach about 1 GiB) is the memory peak;
- the driver's copy of the password and its row buffers are not zeroized;
- no SCRAM channel binding: without TLS, an attacker on the path can relay the SCRAM exchange and act as the agent's role (hence the `disable_insecure` warning); with `verify_full`, server authentication rests on the certificate;
- no TCP keepalive on target connections: a silently dropped connection is only detected by the timeouts;
- RLS policy expressions (which may hold literals) are read into agent memory for the check.

## MongoDB connector
*Discovery implemented in P5-A (#74), `agent/crates/connector-mongodb`; decisions in [ADR-0026](adr/0026-mongodb-connector.md). Audit implemented in P5-B / P5-C (#76); decisions in [ADR-0027](adr/0027-mongodb-audit.md); levels and limits in [08-engine-capabilities.md](08-engine-capabilities.md#mongodb-audit). Details in `agent/README.md` and the crate README.*

- **Own client** (ADR-0026 decision 1): a closed subset of the wire protocol (`OP_MSG` only, no compression, no exhaust), a closed command set built in code (no write command, no `getMore`, no user-supplied filter or pipeline), the reply length checked on the header before the body is read (at most 16 MiB + 64 KiB), BSON parsed by a bounded reader that fails closed. Minimum server: MongoDB 5.0.
- **One declared host, direct connection** (I5): a standalone, one replica-set member or a `mongos`. The hosts named by the server in `hello` are never contacted, `mongodb+srv` is not supported (no DNS SRV / TXT lookups), and there is no pool or monitoring connection. To scan a replica set, declare the member to read from.
- **TLS** (`targets[].mongodb.tls`, rustls only), placed as for PostgreSQL: `verify_full` by default, TLS 1.2 or 1.3 from the first byte, certificate verified against a pinned CA file (`mongodb.ca_file`) or the system store, host name or IP SAN checked; no client certificate. `disable` is accepted only on a Unix socket or a loopback IP literal (never `localhost`). `disable_insecure` is an explicit opt-in on a network: a warning at every connection and the `security.tls_disabled` note, since samples travel in clear and read-only is not guaranteed (see the residual risks).
- **Authentication: SCRAM-SHA-256 only, mutual.** The mechanism is fixed by the client, never taken from the server's list. The password is read from its `agent.yaml` reference into zeroized memory and SASLprepped; the server's iteration count must be between 4096 and 100 000, its nonce must extend the client's, and its signature is verified before any other command runs. SCRAM-SHA-1, `PLAIN` (LDAP), X.509, Kerberos, AWS and OIDC are refused or not implemented. `authSource` comes from `mongodb.auth_source` (default `admin`).
- **Read-only and bounded** (I4). MongoDB has no read-only session mode: the command set and the role are the only controls. `maxTimeMS` (from the clamped job parameter, never `0`) on every command that reads data or metadata, plus a client-side deadline on every exchange. The only pipeline is `[{$sample: {size: n}}]` with `allowDiskUse: false`. No cursor is left open (`singleBatch`, or a batch of `n + 1`, and `killCursors` on any reply with an open cursor); no session id is sent, so no server session or transaction exists. Each collection is read by one command parsed whole before `FindingSink::submit().await`.
- **Scope**: views are never read (their pipeline could read other collections or run JavaScript); `admin`, `local`, `config`, `system.*` and queryable-encryption state collections (`enxcol_.*`) are never read. Encrypted, UUID, compressed, sensitive and vector binaries are never read.
- **Server messages** are reduced to the numeric error code and a closed stage; `errmsg`, `codeName` and any other server text are never kept, logged or sent.
- **Audit sources hold other users' literals** (I2). The `auditLog` (`param.args`), the server log (`command`, `originatingCommand`, `errMsg`) and the profiler hold whole command documents: filters, inserted and updated documents. The connector keeps closed-shape facts only (command name from a closed list, normalized namespace, `name@authdb`, client IP, application name, document counts, a failure flag, the number of filter keys, a numeric `limit`, aggregation stage operators from a closed list). In the files, command documents are skipped by a `serde` visitor without being copied; records go through the core tailer (zeroized buffers, bounded records), and failed-authentication names are held in zeroized buffers. On the profiler, the facts are computed by a fixed server-side projection, so command documents never cross the wire. Nothing else is kept, logged or sent.
- **Audit reads are bounded** (I4): the profiler is read by one `find` per database and poll, built in code (`ts` filter, fixed projection, `limit: 1000`, `singleBatch`, `maxTimeMS` never `0`), at most 64 databases per poll, never `admin`, `local` or `config`; the only command added to the ADR-0026 set is `whatsmyuri` (no privilege, no data). Profiling itself (`profile`, `slowms`) needs `enableProfiler`, which the agent never holds.

**Residual risks** ([ADR-0026](adr/0026-mongodb-connector.md#residual-risks), [ADR-0027](adr/0027-mongodb-audit.md#residual-risks)):
- the connector parses BSON and `OP_MSG` from a possibly hostile server with its own code: bounded and fail-closed, exercised by property tests, but not fuzzed yet (ROADMAP follow-up);
- one reply (up to 16 MiB + 64 KiB) is received whole before its documents are walked: that is the memory peak per collection;
- interrupting a running operation on disconnect is the server's behavior; `maxTimeMS` remains the bound, and no `killOp` is sent;
- **dynamic map keys** (review M3): object levels keyed by data are collapsed to `*` when the sample shows them (more than 16 distinct keys, or at least 3 keys each seen in one document only across at least 2 documents). Not caught: a map with at most 16 keys that recur across the sampled documents, fewer than 3 distinct keys, or a sample of one document with at most 16 keys; such keys, if they do not look like values, reach the field path. Conversely, a genuine sub-document with more than 16 fields, or with optional fields each present in one sampled document, loses its field names (`profile.*`). The top level (the collection's fields) is never collapsed ([ADR-0026](adr/0026-mongodb-connector.md) decision 8), so a collection keyed by data at the top level reaches the field path. Since #83, object levels the shape learner never observed are treated as keyed by data (collapsed to `*`), and a key it never saw on a static level becomes `*` (end-of-phase-5 review L2, fail closed);
- collections the account holds no privilege on are not listed (`authorizedCollections`), so they cannot be reported as not covered; data reachable only through a view is not covered;
- a generic binary that is valid UTF-8 is classified as text; one that is not is skipped;
- no SCRAM channel binding (MongoDB offers no `-PLUS` mechanism): with `disable_insecure`, an attacker on the path can relay the exchange and act as the agent's account; with `verify_full`, server authentication rests on the certificate and the SCRAM signature;
- **own-account exclusion** (Audit): someone holding the agent's credentials on the agent host, spoofing its application name (`databastion-agent`) and reading at most the Discovery budget per collection and day stays unreported (on the `auditLog`, with `find`s whose limits add up to the budget). On the profiler source, a read with the agent's exact profiler-poll shape is not charged only up to the number of polls the agent actually sent to that database (unused credits capped at 64): such a client can at most take the place of the agent's own polls (a few batches of 1000 entries, literals included) before its reads are charged and reported. Behind a proxy or NAT every client has the same address. Writes, DDL and DCL with the agent's identity are always reported, on every engine (#76);
- **heuristic signals**: `signature.mongodump` / `signature.mongoexport` rely on the client-declared application name, and `shape.full_table_read` is evaded by a filter that selects everything or by many small filtered reads ([08-engine-capabilities.md](08-engine-capabilities.md#signals-2));
- **`auditLog` level proven by records** (end-of-phase-5 review L1, fixed in #83 by [ADR-0030](adr/0030-mongodb-auditlog-freshness.md)): a readable `auditLog` reports None (`audit.limited_pending_first_record`) until a valid record is parsed in the last 24 h, so a stale file no longer shows Limited. Residual: a file written only by the agent's own authentications (every other event filtered out) shows Limited; only Partial claims that reads are logged;
- **log literals on the agent host**: the agent's OS user can read files that hold other users' literals; a compromised agent host can read them through the file ACL it was given.
- **abandoned authentications** (since #100, from its security review): an authentication abandoned before any proof (result 337, `AuthenticationAbandoned`) gives no `auth_failure` event. A client that knows account names can therefore confirm they exist, and collect their SCRAM salt and iteration count, through abandoned handshakes without being reported. It cannot verify a password without sending a proof, and every wrong proof (18) or unknown user (11) is reported. Floods of unfinished handshakes no longer feed the volume signals. Informational: this refines [ADR-0027](adr/0027-mongodb-audit.md), which stays Accepted and is not amended ([08-engine-capabilities.md](08-engine-capabilities.md#known-limits-2)).

## OpenLDAP connector
*Discovery, `check()` and Audit implemented in phase 6 (#79), `agent/crates/connector-openldap`; decisions in [ADR-0029](adr/0029-openldap-connector.md); levels and limits in [08-engine-capabilities.md](08-engine-capabilities.md#openldap-audit). Details in `agent/README.md` and the crate README.*

- **Own client** (ADR-0029 decision 1): a closed subset of LDAPv3. The client can encode a simple or SASL `EXTERNAL` bind, a search, the StartTLS and Who am I? extended operations and an unbind, nothing else: no add, modify, delete, modify DN, compare or other extended operation exists in the code (I4). Filters and attribute lists are built in code; console-provided names are never put in a filter. BER is read by a bounded reader (definite lengths, at most 4 length octets, each message checked against 16 MiB before its body is read, fixed nesting, zeroized buffers) that fails closed; an unexpected message id, an unsolicited notification or an unexpected operation ends the connection.
- **One declared server** (I5): referrals and continuation references are never followed (counted as not covered), aliases are never dereferenced (`neverDerefAliases`).
- **TLS** (`targets[].openldap.tls`, rustls only): `verify_full` by default (LDAPS, TLS from the first byte, port 636) or `start_tls` (StartTLS on port 389, no fallback when refused, and any byte sent by the server between the StartTLS response and the handshake is refused), certificate verified against a pinned CA file (`openldap.ca_file`) or the system store, host name or IP SAN checked. `disable` is accepted only on an `ldapi://` Unix socket or a loopback IP literal (never `localhost`). **There is no `disable_insecure`**: a simple bind sends the password itself, so cleartext on a network is refused outright.
- **Authentication: a dedicated service DN, never anonymous.** `openldap.bind: simple` (default) binds with `account` and its password, read from its `agent.yaml` reference into zeroized memory; an empty password is refused client-side (it would be an unauthenticated bind, which servers may accept as anonymous). `openldap.bind: sasl_external` uses SASL `EXTERNAL` over `ldapi://` only, with no `secret`: slapd authenticates the agent's Unix uid / gid from the socket's peer credentials, mapped to a DN by `olcAuthzRegexp`. After binding, Who am I? must return a DN (anonymous fails with `authentication_failed`), equal to `account` with `sasl_external`. Anonymous binds, other SASL mechanisms, client certificates and proxied authorization are not supported.
- **Password attributes are never read**: `userPassword`, `authPassword`, their subtypes and a closed list of other credential attributes (Samba NT / LM hashes and history, Kerberos keys, `pwdHistory`, `userPKCS12`) are never requested, whatever the ACL. Their presence and hash schemes are not reported either (the scheme is part of the value). `check()` only flags an account that could read them (`privilege.password_attributes_readable`, from an attributes-only search: the values never cross the wire).
- **Entry DNs never leave the agent** and are never logged: locations carry the naming context and the entry's parent container reduced by the name normalization, where a value that looks like data becomes `*` ([09-agent-protocol.md](09-agent-protocol.md#location-mapping-per-engine)).
- **Server messages**: `diagnosticMessage`, `matchedDN` and referral URIs are never kept, logged or sent; only the numeric result code and a closed stage are.
- **Audit source holds other users' values** (I2). `cn=accesslog` records hold search filters with their assertion values, entry DNs, compare assertions and modified values. The connector never requests `reqMod`, `reqOld`, `reqAssertion`, `reqMessage` or the controls; `reqFilter` and `reqDN` are reduced in memory (zeroized buffers) to closed facts (whether the filter selects entries by value, whether it is one of the agent's own filters, the naming context, the normalized container, a keyed hash of the base for paged totals) and are never kept, logged or sent.
- **Principals are fingerprinted** (security review M2): a principal DN usually names a person, so Audit events carry it in clear (`db_user`) only for `anonymous`, the agent's own DN and the DNs listed in `openldap.clear_principals` (service and administrator accounts, at most 64); every other principal is sent as the agent's keyed fingerprint (`db_user_fingerprint`). The operator maps a fingerprint back on the agent host.

**Residual risks** ([ADR-0029](adr/0029-openldap-connector.md#residual-risks)):
- the connector parses BER and LDAP responses from a possibly hostile server with its own code: bounded and fail-closed, exercised by property tests, still code to maintain; a log entry that makes it panic is dropped alone, and one that ends the stream repeatedly is skipped after 3 panics at its exact position; the events of a dropped or skipped entry are lost (counted, no console alert; see [Connector obligations](#connector-obligations), [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md));
- **own-account exclusion without an address check**: the log records no client address, so the agent recognizes its own reads by its DN, its exact search shapes and a row budget. Someone holding the agent's DN and password can bind from anywhere unreported and read up to the Discovery budget per object and day with the agent's sampling shape; the agent's container listing and check probes are never charged (they return container DNs, at most 64 entry DNs with attribute types, or one DN). Writes with the agent's identity are always reported. Restricting the service DN to the agent's address in `olcAccess` (below) is the only control against stolen credentials;
- **principals**: every principal other than `anonymous`, the agent's own DN and `openldap.clear_principals` is a fingerprint, so the console cannot show who it is;
- **incidents per fingerprint** (end-of-phase-6 review M1, fixed in #81 by [ADR-0031](adr/0031-openldap-principals-dedup-and-stream-alerts.md) decisions 1 and 2): each fingerprinted user has its own incident key. Residuals: per-user keys reach the per-target hourly cap sooner, so several noisy accounts can push other users' non-severe events into the overflow incident; every unidentified principal of one agent (a SASL bind) shares one key; OpenLDAP compares and binds have no row count, so after a false positive only a new signal or a higher score opens a new incident for them;
- **container names** (end-of-phase-6 review L4): the normalized container (`schema`) keeps `ou`, `o`, `dc`, `c`, `l` and `st` values that do not look like data; a container named after a person or a customer that the normalization does not recognize (for instance `ou=Smith Family`) reaches the console, in findings and in events;
- **audit proofs**: since #83 ([ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 6), the failed-operation probe runs at every privilege report (at most every 10 minutes, at most 8 naming contexts per report) with a DN unique to the probe, and only its latest answer counts; a record under a deeper naming context no longer proves its parent. Residuals: a change of `olcAccessLogSuccess` is seen at the next report that probes the context (later with more than 8 contexts); the proof that reads are logged is still kept up to 24 h, so a change of `olcAccessLogOps` can go unseen as long;
- **at-least-once after a caught panic**: a restarted Audit stream resumes from its persisted cursor, so the events of at most one search round may be sent twice; otherwise delivery is at most once, as for the other connectors;
- **log gaps**: records purged by `olcAccessLogPurge` before the agent read them are lost; on first start, a server clock behind the agent's by more than 60 s skips records until it catches up;
- **records committed out of CSN order** (end-of-phase-6 review L3, reduced in #83): the persisted position keeps the CSNs read within the 10 s overlap (at most 1000), so after a restart the overlap is read again and only unread entries are reported. A record committed more than 10 s below the cursor, or beyond the 1000 persisted CSNs, is still lost;
- **heuristic signals**: `shape.bulk_search` and `volume.large_result` are evaded by selective filters that match everything, per-entry base-scope reads or pages spread over several connections ([08-engine-capabilities.md](08-engine-capabilities.md#openldap-audit));
- **other users' filters and DNs in memory**: the agent reads `reqFilter` and `reqDN` (zeroized, reduced at once); a compromised agent host holding the service DN's password can read the whole log anyway.

## Apereo CAS connector
*Introduced by P8-B (#138, #140, #141, #143); decisions in [ADR-0041](adr/0041-cas-connector.md) and [ADR-0043](adr/0043-audit-logs-opened-without-following-a-final-symlink.md); behaviour per source in [08-engine-capabilities.md](08-engine-capabilities.md#apereo-cas); reference: [the connector README](../agent/crates/connector-cas/README.md).*

- **Local files only** (ADR-0041 decision 2): a `cas` target is a JSON service registry directory and a JSON audit log declared in `agent.yaml`, nothing else. `connector-cas` has no network client of any kind (no HTTP, database or LDAP client; checked by an architecture test), stores no credential (`account` and `secret` are refused for `cas`), and is never detected locally (I5). No CAS actuator endpoint is used (decision 9): their read operations return live credentials (client secrets, ticket-granting ticket ids) and CAS secures them per endpoint, not per operation, so a role able to read them could also write (I4).
- **The CAS configuration is never read**: a registry directory holding CAS configuration or key material (`cas.properties`, `cas.yml`, `application*.yml`, keystores, `*.pem`, `*.key`, `*.jwk(s)`…) is refused as a whole (`privilege.config_readable`), and those files are never opened.
- **File open rules** (ADR-0041 decision 3, ADR-0043). Paths are absolute, resolved when `agent.yaml` is loaded, and refused under `/proc`, `/sys`, `/dev` and the agent's `state_dir`; a source whose path later resolves elsewhere is refused until the next reload. Registry entries are opened with `openat(O_NOFOLLOW)` and checked on the descriptor: regular file, one hard link, same device as the directory, at most 1 MiB, at most 4096 files. The audit log is opened by the core tailer with `O_NOFOLLOW`, at the first open and at every reopen after a rotation (detected with `lstat`), and refused with more than one hard link; the CAS checks then run on the tailer's own handle, so a symlink or a hard link swapped in at rotation is never read. Anything the agent's account could write is refused (owner, group or world write bit, `faccessat(W_OK)` with ACLs, a writable ancestor directory): `privilege.registry_writable`, or `audit.log_not_readable` for the log.
- **Ticket ids are never sampled, kept, logged, fingerprinted nor sent.** The audit record's `what` (which holds the ticket id) is read only for service ticket records and reduced at parse time to the service URL's scheme and host, used only to select a registry entry: only that entry's normalized name, or `*`, leaves the agent. CAS 8.0 writes `what` as an object (`{"service": …, "ticketId": …}`): only its string `service` is read, every other key is skipped unread, and a duplicate `service` drops the record (#143). Discovery never samples `what`, request headers, user agents, addresses, nor the names typed at failed logins (possibly passwords). In the service registry, `clientSecret` is never sampled (its clear or encrypted form is counted, `security.client_secrets_in_clear`), nor any key whose name suggests a credential (`secret`, `password`, `key`, `token`, `credential`, `private`, `cookie`…) with everything below it; URLs lose their userinfo, query string, fragment and `;` parameters before classification.
- **Principals** (I2): every `who` is sent as a keyed fingerprint, except the service and administrator accounts listed in `cas.clear_principals`; failed authentications are always fingerprinted. The `*` "several accounts" principal exists only on `cas` `auth_failure` events carrying `volume.failed_logins_many_accounts`.
- **Client addresses** (ADR-0041 open question 8, refining [ADR-0007](adr/0007-mask-access-events.md)): IP literals only, anything else omitted, then reduced per target with `client_addr`: `truncated` by default (IPv4 `/24`, IPv6 `/56`), `clear` or `omitted`. A CAS audit trail holds the address of every end user, far more people than the clients of a database. Signals are computed on the full address in memory before the reduction; the failed-login windows hold at most 4096 entries each, keyed by tags of a random per-stream key, never persisted nor sent.
- **Parsers**: closed serde visitors on a fixed key set (other keys skipped unread, a duplicate key drops the record), values in zeroizing buffers, property tests and the `cas_registry` / `cas_audit_log` fuzz targets; the crate denies `clippy::string_slice` and `clippy::indexing_slicing` outside tests. A record that makes the parser panic is dropped alone (`audit.records_dropped`).
- **Protocol**: `cas` targets, findings and events reach only a console that lists the `engine.cas` capability; until then they are held in the spool ([ADR-0042](adr/0042-hold-items-of-unlisted-engines.md)).
- **CAS stores in other engines** (JPA tables in PostgreSQL / MySQL / MariaDB, MongoDB collections, the LDAP service registry) are read by that engine's connector under the **CAS store guard** (ADR-0041 decision 5, #141), on by default and not configurable off: recognition by name, by `cas_stores`, by column shape and by a ticket-id value tripwire that drops values before classification; ticket registries are never sampled (one `type, count(*)` aggregate); the audit trail's ticket-id, header and extra-info columns are never selected and `AUD_USER` keeps no masked sample; a service registry body keeps no masked sample nor `secret.*` fingerprint. `check()` reports `privilege.ticket_credentials_readable` at every heartbeat when the account can read a credential column, through roles and `PUBLIC` included. Details: [08-engine-capabilities.md](08-engine-capabilities.md#cas-store-guard-postgresql-mysql--mariadb-mongodb-openldap); grants: [Recommended database accounts](#recommended-database-accounts-read-only) below.

**Residual risks** ([ADR-0041](adr/0041-cas-connector.md#residual-risks), [08-engine-capabilities.md](08-engine-capabilities.md#apereo-cas)):
- **client addresses** come from `X-Forwarded-For` by default: when CAS is reachable without a proxy that overwrites the header, attackers choose their logged address, poison per-address baselines and can rotate it to evade `volume.failed_logins_many_accounts`; `volume.failed_logins_one_account` still sees guessing against one account;
- **never Full**: the audit trail logs authentications and ticket issuance, not reads through the management endpoints (`registeredServices`, `ssoSessions`: no signal) nor reads of the stores; the action filters and destinations are in the CAS configuration the agent must not read, so excluded actions show only through the "not seen" notes, after a day (a week for failures). OIDC / OAuth-only deployments stay Limited until the token issuance actions are mapped ([ROADMAP](ROADMAP.md#phase-8-follow-ups));
- **stores matching no guard rule** (unknown name, unexpected shape, no ticket-id-shaped value yet) are sampled like any table until the tripwire fires on the first ticket id read; ticket ids under a prefix outside the named list and the generic shape, or stored encoded (percent-encoded, JSON-escaped, base64), are not recognized; only masked samples of classified values leave, and ticket ids match no classifier;
- **ticket registry encryption** is inferred from the encoded-ticket class name in `type`; a backend storing tickets differently is reported as not evaluated rather than guessed. With crypto on, the JPA registry still stores unsalted SHA-512 digests of principal ids: whoever reads the table can confirm a guessed user name (the agent never reads those columns);
- **credential form detection**: a clear client secret that looks like the encrypted form is counted as encrypted;
- **no version check**: an unmaintained CAS line is not refused at run time; only the documentation and the tests state the supported lines (8.0.x);
- **parent directories**: symlinks above the declared paths are followed when `agent.yaml` is loaded; a later change of where a path resolves, or an ancestor directory the agent can write, is refused;
- **the audit log on the agent host** holds every end user's login and address (and cookies when CAS logs request headers, `security.audit_headers_logged`): the agent's OS user can read it, and so can whoever compromises the agent host. While parsing, values of a record are in the agent's memory; the scratch buffer that unescapes an escaped `service` string is not zeroized yet (the service URL only; [phase 8 follow-ups](ROADMAP.md#phase-8-follow-ups));
- **delivery** is at most once; a failed-login aggregate in progress is lost when the stream stops, and the windows are not kept across restarts.

## Recommended database accounts (read-only)
**PostgreSQL** ([ADR-0012](adr/0012-postgresql-agent-grants.md), minimal variant, recommended default). Discovery through explicit per-schema grants; Audit through `pg_read_all_stats` only.
```sql
-- Once per cluster. Set the password with psql's \password: it is hashed client-side and only
-- the SCRAM verifier reaches the server. Never use PASSWORD '...' with a cleartext value.
-- Requires password_encryption = 'scram-sha-256' (the default since PostgreSQL 14).
-- CONNECTION LIMIT: 4 for Discovery or pgaudit Audit; 5 with pg_stat_statements as the Audit
-- source; plus 1 per additional target on this account running Audit (ADR-0025 decision 11).
-- Since #88 Audit holds one connection at a time (the re-probe runs on the held session), so
-- these values leave one connection of margin.
CREATE ROLE databastion_agent LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
  CONNECTION LIMIT 4;
\password databastion_agent
-- Safety net for any session on this account; the connector sets its own values.
ALTER ROLE databastion_agent SET default_transaction_read_only = on;
ALTER ROLE databastion_agent SET statement_timeout = '30s';
ALTER ROLE databastion_agent SET lock_timeout = '2s';
ALTER ROLE databastion_agent SET idle_in_transaction_session_timeout = '60s';

-- Per monitored database
GRANT CONNECT ON DATABASE app TO databastion_agent;

-- Discovery: per application schema, and per role that creates tables in it
GRANT USAGE ON SCHEMA crm TO databastion_agent;
GRANT SELECT ON ALL TABLES IN SCHEMA crm TO databastion_agent;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA crm
  GRANT SELECT ON TABLES TO databastion_agent;

-- Audit (Full and Limited): other users' statements. Omit for a Discovery-only target.
GRANT pg_read_all_stats TO databastion_agent;
```
- Every new application schema, and every role that creates tables in it, needs the Discovery grants above. The connector's `check()` lists the schemas it cannot read as not covered (ADR-0012, obligation 6), in the agent's logs for now (see [PostgreSQL connector](#postgresql-connector)).
- Set the password of **every** role with psql's `\password`, not `PASSWORD '...'`: with `pg_read_all_stats`, statement text written by other users (including `ALTER ROLE ... PASSWORD` literals) is readable by the agent account, and the connector must drop it (ADR-0012, obligation 5).
- For clusters with many or dynamically created schemas, ADR-0012 also defines an opt-in **extended variant** (`pg_read_all_data`, `pg_read_all_settings`), which exposes credential-bearing catalogs to the account; read the ADR before choosing it. Never grant `pg_monitor`, `SUPERUSER`, `BYPASSRLS` or any write privilege (full list in the ADR).
- The dev environment (`dev/`, per-schema grants on `crm`, `billing`, `ops`) and the end-to-end harness (`e2e/`: `CONNECT` and `pg_read_all_stats` since #31, plus `USAGE` and `SELECT` on the seeded `crm`, `billing` and `ops` schemas with matching default privileges since #50) use the minimal variant. As a test-only deviation, they set the role password with a `PASSWORD` literal in a session that does not record it.

**MySQL / MariaDB** ([ADR-0018](adr/0018-mysql-mariadb-grants-and-connector.md), minimal variant, recommended default). Discovery through per-database `SELECT` only.
```sql
-- Restrict the host to the agent's address; require TLS. MAX_USER_CONNECTIONS (ADR-0025
-- decision 11): 4 for Discovery only (a scan and a check, each with its KILL QUERY connection);
-- 5 with an audit log file as the Audit source; 6 with performance_schema as the Audit source
-- (its held session, plus a re-probe, reconnect or KILL QUERY connection); plus 1 per additional
-- target on this account running Audit.
CREATE USER 'databastion'@'10.0.0.15' IDENTIFIED BY '...'
  REQUIRE SSL WITH MAX_USER_CONNECTIONS 4;
-- MariaDB only: a safety net, the connector sets its own statement timeout.
-- ALTER USER 'databastion'@'10.0.0.15' WITH MAX_STATEMENT_TIME 30;

-- Discovery: per application database
GRANT SELECT ON app.* TO 'databastion'@'10.0.0.15';

-- Audit with performance_schema as the source only: statement history.
-- Omit for a Discovery-only target and when an audit log file is the source.
-- GRANT SELECT ON performance_schema.* TO 'databastion'@'10.0.0.15';
```
- Never grant `SELECT ON *.*` in the minimal variant: it reads `mysql.user` / `mysql.global_priv` (password hashes; a `mysql_native_password` hash is enough to log in), `mysql.servers` (`FEDERATED` credentials) and the general and slow log tables. No `PROCESS` (other sessions' statement text) and no `SHOW VIEW` either. `check()` reports any global privilege, any privilege beyond `SELECT`, `WITH GRANT OPTION`, `SELECT` on `mysql` / `sys` (a database grant is a `LIKE` pattern, so `%` or `m%` counts) and `init_connect` as over-privilege. Since #70 the same rules apply to the privileges held through roles ([ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md)): a role granting only the minimal variant is not over-privilege. MySQL evaluates every applicable role (`SHOW GRANTS FOR CURRENT_USER() USING …`, at most 16 direct and mandatory roles, allow-listed names). MariaDB shows a least-privilege account the grants of its current (default) role only, so every other role is reported as not evaluated (`privilege.roles_not_evaluated`). Grant the Discovery privileges directly or through the default role. The agent never uses `SET ROLE`. Roles that cannot be evaluated, and privilege lists cut at their limit or with unreadable rows, are reported as not evaluated, never assumed harmless. Since #88, the privileges granted to MariaDB `PUBLIC` (10.11+, held by every account) are read with `SHOW GRANTS FOR PUBLIC` and evaluated the same way; when they cannot be read or parsed, or `PUBLIC` is granted a role, `PUBLIC` counts as a role not evaluated. Not covered: roles on MySQL before 8.0.19 (no `APPLICABLE_ROLES`).
- **Audit grant** ([ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md) decision 3, P4-B #64): `SELECT ON performance_schema.*` only, and only while an Audit stream runs for the target with `performance_schema` as its source; nothing else (no `PROCESS`, no global privilege). `check()` reports it as over-privilege when no Audit stream runs (`SELECT on performance_schema without Audit enabled`) and as unused when an audit log file is the source (`SELECT on performance_schema unused`: on MariaDB it exposes clear-text passwords for nothing). The audit-log sources need no database grant, and the plugin probes need no privilege.
- **Audit log file ACL.** With `mysql.audit_log`, the agent reads the file through the file system on its own host (the path never goes through SQL). Give the agent's OS user read access to the log directory only, never to the data directory, for example an ACL `u:databastion:rx` on the directory and a default ACL `u:databastion:r` for the files the server creates. Setting this ACL is the operator's job; the `0644` files of the dev environment are a dev-only convenience. The configured path is opened by name; since P8-B a symlink as its last component is refused (`O_NOFOLLOW`, at every open and every reopen after a rotation; `audit.log_not_readable`), while symlinked directories above it are still followed. Since #83 ([ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 8), the agent refuses, on the opened handle, a log file its own account could have written: owned by the agent's effective uid, world-writable, or group-writable by one of the agent's groups (`audit.log_not_readable`). **Run the agent as a dedicated non-root user**: an agent running as root while the log belongs to root, or as the database server's user, cannot use the file. The check reads mode bits and the owner uid / gid only: a POSIX ACL entry granting the agent write access is not detected, nor an agent running as root or with `CAP_DAC_OVERRIDE` (which can write a `0640` file owned by the server). Keep the log directory writable by the database server only.
- **Statement text** carries literals, and MariaDB `performance_schema` `SQL_TEXT` keeps passwords in clear. The connector reads `DIGEST_TEXT` first and `SQL_TEXT` only for a statement without a digest, relies on no server-side password mask, replaces every literal with the query normalizer, and sends no statement text (the contract has no field for it; ADR-0012 obligation 5, ADR-0023 decision 4).
- **Multibyte character sets fail closed.** In gbk, big5, sjis, cp932 and gb18030, `\` and a backtick can be the trail byte of a two-byte character, which the server and a byte-level lexer read differently. Statement text that is not UTF-8, or that has a byte >= 0x80 directly followed by `\` or a backtick, keeps only its statement kind: the event names `*`, never names or literals. The second rule is not applied to `performance_schema` texts, already transcoded to UTF-8 by the server. Residual: on the audit log files, a client can use this rule to strip text-derived signals from its own statement (see [08-engine-capabilities.md](08-engine-capabilities.md#mysql--mariadb-audit)).
- ADR-0018 also defines an **extended variant** (global `SELECT`) behind an explicit per-target opt-in, `extended_grants: true` in the `mysql` block of `agent.yaml` (default `false`, [ADR-0020](adr/0020-mysql-mariadb-connector-as-merged.md)). With it, `check()` reports the global `SELECT` as an expected warning instead of over-privilege; every other item above is still over-privilege, and the system schemas are never sampled. The account can still read the password hashes: read ADR-0018 before choosing it.
- **Several targets on one account.** The heartbeat runs the targets' `check()` concurrently, but targets that reach the same account (engine, host or socket, port, account) take turns, one check at a time (#70, [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md)). The turns cover checks only. Audit streams hold their own connections, so size `MAX_USER_CONNECTIONS` as in the comment above, adding one per additional target on the account that runs Audit. An account created with 4 must be raised before Audit is enabled. At the limit, a check, scan or Audit reconnect is refused and fails; no privilege changes. Since #88 the account key recognizes aliases ([agent/README.md](../agent/README.md#uplink-tls-and-state-files), `agent/crates/core/src/checks.rs`): an omitted port and the engine's default one, host-name case and a trailing dot, IP literal forms, `localhost` and the loopback addresses, a socket path through symlinks, and host names that resolve to a shared address. A check that misses the deadline takes the last turn of its account at the next heartbeats, so the other targets of the account rotate ahead of it. **Name resolution and I5**: names are resolved only when two targets of one engine family, account and port name different hosts, and only the **declared target names**, through the system resolver the connectors use anyway (no scan, no other lookup); at most 1 s within the heartbeat deadline, results cached 5 minutes; a name not resolved in time keeps its literal key and the timeout is cached 60 s.
- The connector (P2-C, #52) samples base tables of local storage engines only (never `FEDERATED`, `CONNECT`, `SPIDER`, `S3`, `SPHINX`, NDB or `MERGE` tables, views or virtual generated columns), reads no statistics column during introspection and asks for a table's `TABLE_ROWS` only after reading its engine alone and finding a local one (computing `TABLE_ROWS` opens the table's handler, so a `FEDERATED` table would connect to its remote server; [ADR-0020](adr/0020-mysql-mariadb-connector-as-merged.md)), refuses cleartext, PAM, `sha256_password`, `client_ed25519` and RSA key retrieval, and does not support proxies (ProxySQL, MaxScale). Details and residual risks in ADR-0018. ADR-0025 narrows its "role privileges are not evaluated" risk to MariaDB non-default roles, `PUBLIC` grants and MySQL before 8.0.19; `PUBLIC` grants are evaluated since #88.
- The dev accounts (`dev/mysql/`, `dev/mariadb/`) use the minimal variant (#52): `SELECT` on the seeded application database only, `REQUIRE SSL`, `MAX_USER_CONNECTIONS 5` (raised from 4 in #72, matching [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) decision 11 for audit-log-file Audit; the MySQL Audit tests create their own `performance_schema` account), and `MAX_STATEMENT_TIME 30` on MariaDB. As a dev-only deviation, the host is `'%'` (the agent connects through a published port). They have no `performance_schema` grant, also after P4-B; the Audit integration tests create a dedicated account with it (ADR-0023).

**MongoDB** ([ADR-0026](adr/0026-mongodb-connector.md) decision 5, Discovery). A custom role with `find` and `listCollections` on each monitored database; nothing cluster-wide.
```js
// mongosh, in the admin database. One privilege per monitored database.
db.getSiblingDB("admin").createRole({
  role: "databastionDiscovery",
  privileges: [
    { resource: { db: "app", collection: "" }, actions: ["find", "listCollections"] }
    // Only if the server refuses the time-series collections (see below):
    // , { resource: { db: "app", system_buckets: "" }, actions: ["find"] }
  ],
  roles: []
});
// passwordPrompt() keeps the password out of the shell history.
// SCRAM-SHA-256 credentials only: the agent refuses SCRAM-SHA-1.
// authenticationRestrictions (recommended): the agent's address(es) only.
db.getSiblingDB("admin").createUser({
  user: "databastion",
  pwd: passwordPrompt(),
  mechanisms: ["SCRAM-SHA-256"],
  roles: [{ role: "databastionDiscovery", db: "admin" }],
  authenticationRestrictions: [{ clientSource: ["10.0.0.15"] }]
});
```
- `collection: ""` covers every collection of the database except `system.*` ones. Nothing else is needed: databases and collections are listed with `authorizedDatabases` / `authorizedCollections` (no `listDatabases` privilege), the size estimate is a `count` (covered by `find`), and a user can always kill its own cursors.
- Never grant `read` (it includes `changeStream`, every future write with its values, `dbHash` and `find` on `system.js`), `clusterMonitor` (`inprog`: other sessions' operations with their literals; `system.profile` of every database; `getCmdLineOpts`), `readAnyDatabase`, any privilege on `admin`, `local` or `config`, or any write or administration action. `check()` evaluates the account's resolved privileges (`connectionStatus` with `showPrivileges`, inherited roles included) and reports, as closed notes with counts: write or administration actions (`privilege.write_actions`), read actions beyond `find` / `listCollections` (`privilege.read_beyond_discovery`), cluster-wide actions (`privilege.cluster_actions`), privileges on every database (`privilege.any_database`) and system collections or the `admin` / `local` / `config` databases (`privilege.system_collections`). A resource it cannot parse counts as a privilege on every database (fail closed); privileges it cannot read are reported as `privilege.not_evaluated`.
- **Time-series collections** are read through their view (`find` with a limit). `collection: ""` does not cover their bucket collections (`system.buckets.*`). If the server refuses the read, the scan counts the collection as not readable and `check()` reports `coverage.timeseries_not_readable` with the count observed in the last scan (never predicted from the privileges). The fallback grant, shown commented above, reads the time-series collections' own documents only and is not reported as over-privilege.
- Accounts without SCRAM-SHA-256 credentials (SCRAM-SHA-1 only, LDAP, Kerberos, X.509, AWS, OIDC) cannot be used by the agent.
- **Audit: prefer a file source** ([ADR-0027](adr/0027-mongodb-audit.md) decision 5, P5-B / P5-C #76). The `auditLog` JSON file (Enterprise, Percona Server for MongoDB) and the structured JSON server log are read by the agent on its own host and need **no database grant**.
- **Audit log file ACL**, as for MySQL / MariaDB above: give the agent's OS user read access to the log directory only (`systemLog.path`, `auditLog.path`), never to the data directory (`dbPath`), for example an ACL `u:databastion:rx` on the directory and a default ACL `u:databastion:r` for the files the server creates, or `0640` with a dedicated group. Both files hold other users' literals: never make them world-readable. Setting this ACL is the operator's job; the permissive files of the dev environment are a dev-only convenience. The same rules apply: the configured path is opened by name (a symlink as its last component is refused since P8-B), and a file the agent's own account could have written is refused (`audit.log_not_readable`).
- **Audit through the profiler** (optional, only when the agent cannot read the files, for instance when it does not run on the database host): `find` on `system.profile` of each database to audit, in a role of its own, and nothing else:
  ```js
  db.getSiblingDB("admin").createRole({
    role: "databastionAuditProfiler",
    privileges: [
      { resource: { db: "app", collection: "system.profile" }, actions: ["find"] }
    ],
    roles: []
  });
  db.getSiblingDB("admin").grantRolesToUser("databastion", [{ role: "databastionAuditProfiler", db: "admin" }]);
  ```
  Least privilege versus coverage: this grant lets anyone holding the agent's credentials read every profiled command of the database, **literals included, over the network**. The agent's projection limits what the agent fetches, not what the credentials allow. The file sources carry the same literals but stay on the database host behind a file ACL, which is why they are preferred. `check()` counts this grant as the Audit grant only while an Audit stream reads the profiler, and reports it as `privilege.system_collections` otherwise; every other privilege on `system.profile` stays over-privilege. Never grant `clusterMonitor`, `read` or `enableProfiler` for Audit.
- The dev account (`dev/mongo/initdb/`) uses this role on the seeded `app` database with SCRAM-SHA-256 only. As a dev-only deviation, it has no `authenticationRestrictions` (the agent connects through the published port, from the Docker gateway).

**OpenLDAP** ([ADR-0029](adr/0029-openldap-connector.md) decision 4, refined by [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 9). A dedicated service DN with `read` on the monitored tree except the credential attributes, and `read` on `cn=accesslog` for Audit. In `cn=config` (adapt the suffix and the DN):
```
# Data database: credentials first, then the tree.
olcAccess: {0}to attrs=userPassword,userPKCS12 by self =xw by anonymous auth by * none
olcAccess: {1}to dn.subtree="dc=example,dc=org" by dn.exact="cn=databastion,ou=services,dc=example,dc=org" read by * break
# Log database (Audit only).
olcAccess: {0}to dn.subtree="cn=accesslog" by dn.exact="cn=databastion,ou=services,dc=example,dc=org" read by * none
# Result sizes: at least limits.max_sample_rows on the tree, 1000 on the log.
olcLimits: dn.exact="cn=databastion,ou=services,dc=example,dc=org" size=1000 time=60
```
- **Name every credential attribute your schemas define in rule `{0}`.** The rule above is for a stock `slapd` with the `core`, `cosine` and `inetorgperson` schemas (`userPassword`, `userPKCS12`). Add `authPassword` only where the server defines it (built with `SLAPD_AUTHPASSWD`), `sambaNTPassword`, `sambaLMPassword`, `sambaPasswordHistory` and `sambaClearTextPassword` where the Samba schema is loaded, `krbPrincipalKey` and `krbExtraData` where the Kerberos schema is loaded, and `pwdHistory` where the ppolicy overlay module is loaded: `slapd` refuses an `olcAccess` clause that names an attribute it does not know, so the ADR-0029 rule naming `authPassword` does not load on a stock server.
- **Never grant access to the credential attributes**, not even `search` or `compare`: that would make the account an oracle on the hashes. The agent never requests them anyway; `check()` reports `privilege.password_attributes_readable` when an attributes-only search of the first 64 entries of a naming context discloses `userPassword` or `authPassword` (an over-privilege limited to entries further down is not seen; readable `userPKCS12` or other credential attributes are not flagged).
- `read` includes `search` and `compare`. Never grant `write`, `manage` or `auth`, and no access to `cn=config` (`check()` reports `privilege.config_readable`: ACLs, root password hashes, every setting). Grant `cn=accesslog` only while Audit runs for the target (`privilege.accesslog_without_audit` otherwise): the log holds other users' filters, assertion values and old values. OpenLDAP shows a read-only account neither its ACLs nor its effective rights, so write access cannot be evaluated: `check()` always reports `privilege.write_not_evaluated`, and the operator checks `olcAccess`.
- **Restrict the service DN to the agent's address** (recommended, security review L4). The log records no client address, so this is the only control that keeps stolen agent credentials from being used elsewhere. Before rule `{1}` on the data database (and likewise on the log database), for an agent at `10.0.0.15`:
  ```
  olcAccess: {0}to * by dn.exact="cn=databastion,ou=services,dc=example,dc=org" peername.ip=10.0.0.15 break by dn.exact="cn=databastion,ou=services,dc=example,dc=org" none by * break
  ```
- **SASL `EXTERNAL` over `ldapi://`** (`openldap.bind: sasl_external`, agent on the directory host): map the agent's Unix uid to the service DN with `olcAuthzRegexp` and set that DN as `account`; no password is stored. The same ACL applies to the mapped DN.
- **TLS**: `verify_full` (LDAPS) or `start_tls`; cleartext only on `ldapi://` or loopback. There is no `disable_insecure` for OpenLDAP.
- The dev environment (`dev/openldap/`) uses this ACL (the service DN reads the tree except `userPassword` and `userPKCS12`, and `cn=accesslog`; #82). As a dev-only deviation, it has no `peername.ip` restriction (the agent connects through the published port).

**Apereo CAS** ([ADR-0041](adr/0041-cas-connector.md) decision 6). The `cas` target needs no account at all (no CAS credential, no actuator); its files are read through the file system. The CAS stores held in a database or directory are read by that engine's target, under the CAS store guard, with the grants below.

- **Files.** Run the agent as its own non-root user and give it read access through a group without write permission: the registry directory owned by the CAS user, group `databastion`, mode `0750`, its definitions `0640`; the audit log directory `2750` (setgid, so that the files CAS creates and rotates get the agent's group) and the audit log `0640`. With log4j2, set `filePermissions="rw-r-----"` on the audit `RollingFile` appender and a `%m%n` layout (as in [dev/cas/config/log4j2.xml](../dev/cas/config/log4j2.xml)). Nothing on the path may be writable by the agent's account (refused), and the agent must have **no access to the CAS configuration** (`/etc/cas/config`, `cas.properties`, `cas.yml`, keystores): never put the service registry in the configuration directory. Example (adapt the paths and the CAS user):
  ```sh
  chown -R cas:databastion /etc/cas/services
  chmod 0750 /etc/cas/services && chmod 0640 /etc/cas/services/*.json
  chown cas:databastion /var/log/cas && chmod 2750 /var/log/cas
  ```
- **Ticket registry table** (JPA, PostgreSQL / MySQL / MariaDB): **column privileges only**, never the table; `type` is what the guard's aggregate reads, the creation and expiration times are harmless metadata. The ticket id, `body`, `parent_id`, `principal_id`, `service` and `attributes` columns stay unreadable. The names below are those of the CAS 8.0.2 JPA ticket registry of the dev service (#142); check them against your schema:
  ```sql
  -- PostgreSQL (in the CAS database; CONNECT on the database and USAGE on the schema as above)
  REVOKE ALL ON cas_tickets FROM PUBLIC;
  GRANT SELECT (type, creation_time, expiration_time) ON cas_tickets TO databastion_agent;
  -- MySQL / MariaDB
  GRANT SELECT (type, creation_time, expiration_time) ON cas.cas_tickets TO 'databastion'@'10.0.0.15';
  ```
  A CAS upgrade or schema update that recreates the table drops these column grants: grant them again. Until then the guard reads nothing of the table (its aggregate needs `type`), and a table grant put in their place is reported at the next heartbeat (`privilege.ticket_credentials_readable`).
- **Audit trail table** (`COM_AUDIT_TRAIL`): `SELECT` on its columns except `AUD_RESOURCE` (ticket ids), `AUD_HEADERS` (cookies) and `AUD_EXTRA_INFO`, e.g. `GRANT SELECT (AUD_USER, AUD_CLIENT_IP, AUD_ACTION, AUD_DATE) ON …`. The guard never selects those three columns anyway, and reports them when they are readable.
- **Service registry table** (`RegisteredServices`): `SELECT` on the table (its `body` is the definition, client secrets included; classified without masked samples nor `secret.*` fingerprints). Encrypt the client secrets in CAS.
- **Grant scope in a database or schema holding CAS stores**: `SELECT` **per table**, never `GRANT SELECT ON ALL TABLES IN SCHEMA`, `GRANT SELECT ON db.*` nor an `ALTER DEFAULT PRIVILEGES` covering the CAS owner's tables, unlike the per-schema Discovery grants above: a ticket table CAS creates later would be readable in full. The PostgreSQL extended variant (`pg_read_all_data`) and MySQL / MariaDB `extended_grants` have the same effect there. Better still, keep the CAS stores in a database or schema of their own. `check()` reports a schema- or database-wide grant covering a guarded table as `privilege.ticket_credentials_readable`, privileges held through roles and `PUBLIC` included.
- **MongoDB**: there is no field-level privilege, so `find` on a ticket registry or audit collection makes every ticket readable by the agent's account, and `check()` reports `privilege.ticket_credentials_readable`. Leave those collections out of the agent's role (the guard then gives no ticket counts nor encryption note for them); the projected view of ADR-0041 decision 6 is not verified yet.
- **OpenLDAP service registry**: the service DN's `read` access as above; registry entries are classified without masked samples nor `secret.*` fingerprints.
- **CAS settings** that reduce what the files hold: ticket registry `crypto.enabled: true`, encrypted OAuth / OIDC client secrets, and an audit trail without request headers (`auditable-fields` without `headers`); see the [user guide](10-user-guide.md#6-declare-targets).

## Deployment recommendations
- Agents and console run as a **non-root** user, read-only file system, `cap_drop: ALL`, `no-new-privileges`
- Console behind a reverse proxy (Traefik / Nginx / Caddy) with HTTPS
- The reverse proxy must not log the `X-CSRF-Token`, `Authorization` or `Cookie` request headers. Caddy redacts only `Authorization`, `Cookie` and `Set-Cookie` by default; add a log filter for `X-CSRF-Token` (see [e2e/Caddyfile](../e2e/Caddyfile)). Check the equivalent settings on other proxies
- The console's internal database is never exposed outside the Docker network
- Enable the databases' native logs (pgaudit, MariaDB audit plugin, OpenLDAP `accesslog`…)

## Points of attention
- **Performance**: bounded sampling (N rows per column, `TABLESAMPLE` when possible), `statement_timeout` on every agent query, and Discovery paced to `limits.discovery_duty_cycle_percent` of the scan's time (default 1 %: scans take about 100 times their query time, and objects that do not fit the scan's budget are reported as `skipped_limit`; [Connector obligations](#connector-obligations), [ADR-0035](adr/0035-discovery-pacing.md))
- **False positives**: per-finding marking by administrators, reset automatically when a rescan matches more values (see [Findings ingestion](#findings-ingestion)); policy exceptions per agent, target, classifier or location (#45, [ADR-0014](adr/0014-policy-and-incident-model.md))
- **Upgrades**: the agent stays compatible with protocol version N-1; the console advertises the minimum expected version
