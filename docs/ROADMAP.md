# Roadmap – DataBastion

The MVP (v0.1.0) was built in phases 0 to 7; phases 8 and later, [after the MVP](#after-the-mvp), plan what comes next. Each phase is divided into independent **workstreams**, assignable to different agents working in parallel (see [AGENTS.md](../AGENTS.md#multi-agent-work)).

Legend: `[ ]` to do · `[~]` in progress · `[x]` done. Update this file at the end of every task.

Items prefixed with **Gate** come from a security review: they block the completion of the workstream they sit in, which cannot be checked off while a gate is open.

**Current phase: 0.4.0 released; next: phase 9 and the phase 8 follow-ups.** v0.4.0 was released on 2026-10-07 (release PR #153, tag `0.4.0` on `main`, back-merged into `dev` by #156) with phase 8 – OIDC login & CAS connector (end-of-phase-8 security review at `684966d`: no Critical or High finding); all [0.4.0 release gates](#phase-8-follow-ups) are closed. Next: [phase 9](#phase-9--engine-scope-wave-1-microsoft-sql-server-redis-valkey) (Microsoft SQL Server, Redis, Valkey) and the open [phase 8 follow-ups](#phase-8-follow-ups). v0.1.0 was released on 2026-09-30, v0.2.0 and v0.3.0 on 2026-10-03, v0.3.1 on 2026-10-04 and v0.4.0 on 2026-10-07 (tags `0.1.0` to `0.4.0`); phases 0 to 8 are closed. Open items tagged v0.1.x stay in the phase 7 list; the remaining release follow-ups, all for the maintainer, are in [v0.1.x follow-ups](#v01x-follow-ups).

## After the MVP

The phases below replace the former "After the MVP" table. Each phase keeps the MVP rules: independent workstreams with one owner each, so parallel tasks do not touch the same directories ([AGENTS.md](../AGENTS.md#multi-agent-work)); every task that touches `shared/protocol/`, the uplink, masking or authentication ends with a `security-reviewer` review; every phase ends with an end-of-phase security review whose gates block the exit. A decision that contradicts an invariant or an accepted ADR gets a new ADR first.

Decisions that frame these phases:
- [ADR-0038](adr/0038-console-oidc-login.md) (Accepted, defaults confirmed 2026-10-04): console login with OpenID Connect. Its proposed defaults (`DATABASTION_OIDC_ALLOW_SIGN_UP=0`, `DATABASTION_OIDC_ROLE_ATTRIBUTE_STRICT=1`, `DATABASTION_LOCAL_LOGIN` `admins` when OIDC is on, `enabled` otherwise) were **confirmed by the maintainer on 2026-10-04**.
- [ADR-0039](adr/0039-engine-scope-expansion.md) (Proposed): the new engines and their honest ceilings. **End-of-life engine versions are not supported** (decided by the maintainer on 2026-10-04): PostgreSQL 12 and 13, MySQL 5.7 and MongoDB 4.x are out of scope, for security (no upstream fixes) and because the agent relies on features they lack (`pg_stat_statements_info` from PostgreSQL 14, MySQL 8 roles, MongoDB wire version 13 = 5.0, all enforced or required today).
- [ADR-0040](adr/0040-prevention-mode-scope.md) (Accepted): "Prevention mode (proxy)" is not a Community feature. Community gets recommended actions and response hooks, never in the data path; the blocking proxy, session kill and grant revocation are Enterprise, outside this repository (I4, I7, [EDITIONS.md](EDITIONS.md)).

Order: phase 8, then phases 9 and 10 (engines), phase 11 (platform) and phase 12 (response). Phases 11 and 12 touch mostly `console/` and `deploy/`, and can run alongside the engine phases, which touch mostly `agent/` and `dev/`.

## Phase 8 – OIDC login & CAS connector
*Objective: console users sign in through an OpenID Connect provider (Keycloak in dev and CI), and the agent covers a first CAS (Central Authentication Service) target. The console and agent workstreams run in parallel.*

**CAS here means an Apereo CAS server**, an identity service like OpenLDAP. What DataBastion can look at is to be settled by the connector ADR (P8-B), from these candidates:
- *Discovery*: the stores CAS keeps, which hold personal data or secrets: the **service registry** (registered services with their attribute release policies, i.e. which personal attributes go to which application, and OAuth / OIDC client secrets), the **ticket registry** (tickets carry the authenticated principal and its attributes; `check()` can report whether the registry's signing and encryption are on), and the **audit trail store** itself (user names and client addresses). Those stores are JSON / YAML files on the CAS host or tables and collections in engines DataBastion already reads (PostgreSQL, MySQL / MariaDB, MongoDB, Redis, LDAP); the ADR decides between a CAS profile over the existing connectors and local file reading.
- *Audit*: the CAS **audit trail** (who authenticated, from where, which service tickets were issued, failures) and the authentication events, mapped to `connect` and `auth_failure` access events, with signals for credential stuffing and for bulk reads of the administrative endpoints (registered services, SSO sessions). The level ceiling is decided in the ADR from what CAS actually records; reads of the underlying stores are audited by their engine's connector.
- *I5*: CAS targets are declared in `agent.yaml` (base URL and / or file paths); no network discovery. *I2*: principals follow the existing rules (account names reported, failed-login names fingerprinted).
