## Phase 8 – OIDC login & CAS connector
*Objective: console users sign in through an OpenID Connect provider (Keycloak in dev and CI), and the agent covers a first CAS (Central Authentication Service) target. The console and agent workstreams run in parallel.*

**CAS here means an Apereo CAS server**, an identity service like OpenLDAP. What DataBastion can look at is to be settled by the connector ADR (P8-B), from these candidates:
- *Discovery*: the stores CAS keeps, which hold personal data or secrets: the **service registry** (registered services with their attribute release policies, i.e. which personal attributes go to which application, and OAuth / OIDC client secrets), the **ticket registry** (tickets carry the authenticated principal and its attributes; `check()` can report whether the registry's signing and encryption are on), and the **audit trail store** itself (user names and client addresses). Those stores are JSON / YAML files on the CAS host or tables and collections in engines DataBastion already reads (PostgreSQL, MySQL / MariaDB, MongoDB, Redis, LDAP); the ADR decides between a CAS profile over the existing connectors and local file reading.
- *Audit*: the CAS **audit trail** (who authenticated, from where, which service tickets were issued, failures) and the authentication events, mapped to `connect` and `auth_failure` access events, with signals for credential stuffing and for bulk reads of the administrative endpoints (registered services, SSO sessions). The level ceiling is decided in the ADR from what CAS actually records; reads of the underlying stores are audited by their engine's connector.
- *I5*: CAS targets are declared in `agent.yaml` (base URL and / or file paths); no network discovery. *I2*: principals follow the existing rules (account names reported, failed-login names fingerprinted).
