# Capabilities by engine

DataBastion can only audit what the engine logs. This page states **honestly** what is possible for each engine and each edition. The console shows the level reached for each target: a "Limited" audit must never pass for a full audit.

## Audit levels
| Level | Meaning |
|--------|---------------|
| **Full** | Every access is logged with the user, the object, and the volume returned |
| **Partial** | Accesses are visible, but some information is missing (volume, exact object) or depends on sampling |
| **Limited** | Only slow accesses, or aggregated statistics, are visible. Export detection is likely, not guaranteed |
| **None** | Discovery only |

**Discovery** (data classification) works the same way on every engine: it only needs a read-only account.

## Discovery load on the monitored database (every engine)

Sampling is bounded per object (rows, bytes, statement timeout), and since #93 the agent also paces every scan ([ADR-0035](adr/0035-discovery-pacing.md)). Each unit of work against the target (an object's sampling, a catalog read, a listing) is charged a pause of `busy × (100 − d) / d`, where `busy` is the agent's wall-clock time for that unit (failed and timed-out units included) and `d` is `limits.discovery_duty_cycle_percent` in `agent.yaml` (default 1, range 1 to 100, `100`: no pacing). The pause is a debt paid before the next unit, never after the last one. A scan uses one connection, and scans run one at a time per agent, so a scan costs the server at most about `d` % of one core. The MVP criterion is under 2 % of the server's CPU while a scan runs ([04-mvp-scope.md](04-mvp-scope.md)).

- **Scans take longer.** A scan lasts about `100 / d` times its query time. Measured on MariaDB 11.4 with 200 tables (debug build): 120 s and 0.35 % of one core paced, against 6.6 s and 5.4 % unpaced. The #92 harness measured 20 to 25 % of one core per server without pacing; with pacing, the final CI load run on #93 measured at most 0.33 % of a 2-CPU server ([Load and database impact, measured](#load-and-database-impact-measured)).
- **Scan budget: a stop, not a relaxed bound.** The job's `max_duration_s` (console default 3600 s since #94, capped by `limits.max_scan_duration_s`, default 3600 s) should cover the scan: at 1 %, 3600 s covers about 36 s of query time (some 7 000 objects at 5 ms each). When the debt, plus the last unit's time and a 2 s margin, would reach the deadline, the next unit does not run: the objects left are reported as `skipped_limit` in the scan's coverage and the scan succeeds (a database, naming context or whole MySQL / MariaDB target not reached counts as 1). On a console that does not take the coverage counters, such a scan ends `failed` with `timeout` instead. The console flags such a succeeded scan as "partial coverage" on the agent page (#95; [10-user-guide.md](10-user-guide.md#9-discovery-scans-and-findings)). With a seed derived from the job id, each scan rotates first its databases (PostgreSQL, MongoDB) or naming contexts (OpenLDAP), then the objects inside each, so successive scans do not skip the same tail. Sizing: [10-user-guide.md](10-user-guide.md#9-discovery-scans-and-findings).
- **Sessions during pauses.** A unit's resources are released before its debt is paid. The MySQL / MariaDB connector closes its idle session before a pause that reaches 45 s; the MongoDB and OpenLDAP connectors reconnect after a pause of more than 60 s, MySQL / MariaDB after 45 s. The PostgreSQL connector keeps its idle session (no transaction open).
- **Limits of the bound.** It is conservative (network, I/O and lock waits count as busy time). Connection setup and the reconnections after long pauses are not paced (a handful per scan at most). On PostgreSQL, parallel query workers are not disabled, so a query the planner runs in parallel can use more than one core during its busy time.

## Audit log files and failing streams (every engine)

- **Log files the agent could write are refused.** Every file source (PostgreSQL pgaudit log, MariaDB `server_audit`, the MySQL / Percona JSON logs, the MongoDB `auditLog` and server log, the CAS audit log) must be written and owned by the database server (CAS: the CAS server). Since 0.4.0 (P8-B) the configured path is opened with `O_NOFOLLOW`, at the first open and at every reopen after a rotation: a path whose last component is a symlink is refused (`audit.log_not_readable`; configure the file itself, symlinked directories above it still work), so a symlink swapped in at rotation cannot redirect the agent (security review of #138 L2, [ADR-0043](adr/0043-audit-logs-opened-without-following-a-final-symlink.md); a CAS `audit_log.path` is resolved once when `agent.yaml` is loaded). A file with more than one hard link is refused the same way, at every open and reopen (`audit.log_not_readable`): a hard link put at the path at rotation could be any other file the agent can read (security review of #140 L1). The agent refuses, on the opened handle, a file owned by its own effective uid, world-writable, or group-writable by one of its groups (mode bits and owner only: POSIX ACL write entries, and an agent running as root or with `CAP_DAC_OVERRIDE`, are not detected): `check()` reports `audit.log_not_readable` (#83, [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 8). An agent running as root while the log belongs to root, or as the database server's user, cannot use the file: run it as a dedicated non-root user with group or ACL read access ([05-security.md](05-security.md#recommended-database-accounts-read-only)).
- **Records that crash a parser.** On the log-file sources, the MongoDB profiler and the OpenLDAP accesslog, each audit record is parsed and converted in isolation: a record whose handling panics is dropped alone (on PostgreSQL and the MySQL / MariaDB log files, conversion is isolated per statement, so the whole statement's group of records is dropped), counted in `audit.records_dropped` and in the heartbeat metric `audit_record_panics_total`. The events of such a record are lost (except on `pg_stat_statements`, below); the console raises no alert on these counters. Since #88 the polled sources are isolated per statement as well: `performance_schema` (its conversion) and `pg_stat_statements` (its text's analysis and its conversion). On `pg_stat_statements`, the result of a statement's analysis is cached per (`userid`, `dbid`, `queryid`, `toplevel`). Since #90, a statement whose analysis or conversion panics is cached as poisoned: it is not analyzed or converted again, and the panic is counted once in `audit_record_panics_total` while the statement stays in the analysis cache (cleared beyond 20 000 entries, after which it is analyzed or converted again and counted again). It is not counted in `audit.records_dropped`, since nothing is dropped (#93: the poller counts it apart and logs it as reported against `*`). Its later deltas are **still reported**, each as a read of unknown objects (`*`) with the delta's calls and rows (and `volume.large_result` above 10 000 rows), built from the counters, the role and the database only, never from the statement text. Such an event is never treated as the agent's own activity and never charged to a row budget. It is always a read, whatever the statement did: it over-reports on purpose (a write or DDL shows up as a read of `*`) rather than hide the executions of a statement shape that makes the agent panic (`queryid` ignores constants and comments). On the other sources, records dropped by isolation still reach no policy: [ROADMAP](ROADMAP.md#phase-7--hardening--v010-release) phase 7 follow-up, a masked "conversion failed" access event.
- **Positions kept across restarts** (#88). Every Audit read position is saved under `<state_dir>/audit/` (`0600`; they hold normalized object names, times, offsets and hashes, never a statement text): the file offsets, the OpenLDAP CSNs, and since #88 the MySQL / MariaDB `performance_schema` cursor and the MongoDB profiler positions, as well as the agent's own-account row counters. An agent restart resumes where it stopped, within what the source still holds; `pg_stat_statements` counters are not persisted. Details: [agent/README.md](../agent/README.md#audit-state-kept-across-restarts).
- **Truncation while the agent is stopped** (since #97). The saved read position of a log file keeps a keyed fingerprint (HMAC-SHA256 with a sub-key of the agent's local key, [05-security.md](05-security.md#masking-and-fingerprints); never the log bytes) of the 256 bytes before it, and before the end of what was read when statements were held for replay. At restart, if the log at the same inode was truncated in place (`copytruncate`, `log_truncate_on_rotation`) or rewritten, even if it has grown back past the saved position, the position and any replay are discarded and the file is read from its start; this is logged and counted in the heartbeat metric `audit_cursor_reset_total`. Nothing written after the truncation is skipped; events from the re-read part of the new file are reported once. A position saved by an agent older than this change carries no fingerprint and resumes as before. After a new agent key (`enroll --new-hmac-key`), a saved position keeps only the position checks (like one saved by an older agent) until its next save; a truncation during that stop is not detected. A truncation between the last read and the cursor save is detected at save time, by comparing the 32 bytes before the position with what was read, and forces a re-read at the next start; residual: such a truncation that grows back to the same 32 bytes before the position is not seen. Before #97, a log truncated in place while the agent was stopped and grown back past the saved position was read from the middle of the new content, and with held statements the new records up to the saved end could be taken for records already reported.
- **Streams that keep failing.** A panic that still ends a stream restarts it after a backoff (at least the poll interval). The OpenLDAP stream then locates the entry at fault and skips it after 3 panics at that exact position (`audit_records_skipped_total`); the file sources do not skip. A stream is stopped, with level None and the note `audit.stream_stopped`, after 7 panics at one position with no progress, more than 8 skips or 64 panics within an hour, or 3 panics in a row on a source whose position is not persisted (`pg_stat_statements`). The console then raises an `agent.audit_stream_stopped` alert every hour while it stays stopped ([05-security.md](05-security.md#alerting)). Reconfiguring Audit or restarting the agent starts it again from its persisted cursor.
- **Event times.** The console stores event times in milliseconds, but OpenLDAP (`reqStart`: whole seconds and a per-second operation counter) and MariaDB `server_audit` give whole seconds only: events of the same second from those sources cannot be ordered by time. The pgaudit `jsonlog`, MongoDB and `performance_schema` sources keep sub-second times.

## PostgreSQL Audit

What the PostgreSQL connector does, as merged in P4-A (#58) and fixed in #65. The reference is [the connector README](../agent/crates/connector-postgres/README.md).

### Sources and level

The connector reads one source at a time, chosen with the same probe and rule as `check()`, and re-evaluates the choice every 5 minutes.

| Level | Condition | Source |
|-------|-----------|--------|
| **Full** | The log declared in `agent.yaml` is readable by the agent, pgaudit is loaded with the `read` class, `pgaudit.log_rows` is proven on (its records carry row counts), `log_min_messages` and `log_min_error_statement` are proven `error` or lower (failed statements are logged with their text) in the agent's session **and for every role** (no per-role, per-database or per-function override above `error`, and, on PostgreSQL 15+, no `SET` or `ALTER SYSTEM` grant on them to another role than the agent's and superusers: [Failed and cancelled statements](#failed-and-cancelled-statements)), **and** the stream has parsed a pgaudit record in the last 24 h | pgaudit log |
| **Partial** | Log readable and pgaudit logging reads (or object audit through `pgaudit.role`), but `pgaudit.log_rows` off or not defined (no row counts), `log_min_messages` or `log_min_error_statement` above `error` or not read, an override of them or a grant on them found or not read, or no record parsed in the last 24 h | pgaudit log |
| **Limited** | No usable pgaudit log; `pg_stat_statements` installed, loaded and showing other roles' statements | `pg_stat_statements` |
| **None** | None of the above | none |

- **pgaudit loaded is proven, not assumed.** A `pgaudit.*` value set in `postgresql.conf`, `ALTER DATABASE` or `ALTER ROLE` without the library loaded is a placeholder that `current_setting()` still returns. The probe therefore requires the library's own `pgaudit.log_catalog` setting, typed `bool`, in `pg_settings` (which hides placeholders); `shared_preload_libraries` itself is not readable without `pg_read_all_settings`. Settings without the library give no pgaudit level (at best Limited), with the note "pgaudit settings are set but the pgaudit library is not loaded". Like every setting the probe reads, the proof reflects the agent's own session in each monitored database: a library loaded or `pgaudit.*` values set for some roles or databases only may differ for other roles.
- **pgaudit log.** Declared per target as `targets[].postgres.audit_log` in `agent.yaml`, with `path` (absolute path of the current log file, fixed `log_filename`) and `format` (`jsonlog`, PostgreSQL 15+, or `csvlog`). The agent reads the file locally and incrementally, never through SQL, with a cursor persisted by the core; rotation by rename or truncation is followed. Only `AUDIT:` records and the `ERROR` / `FATAL` lines of client backends ([Failed and cancelled statements](#failed-and-cancelled-statements)) are parsed. `volume.large_result` on this source needs `pgaudit.log_rows = on`, which pgaudit defines from 1.6 (PostgreSQL 14) on: with pgaudit 1.5 (PostgreSQL 13), a value set for it is a placeholder, which `check()` does not count (proven through `pg_settings`, like the library itself).
- **Full needs `pgaudit.log_rows`** ([ADR-0037](adr/0037-postgresql-full-requires-pgaudit-log-rows.md)). The stream reads one source at a time: at Full and Partial the pgaudit log, never `pg_stat_statements` alongside it. `pg_stat_statements` is therefore no volume source for Full. With pgaudit logging reads but `pgaudit.log_rows` off or not defined, the level is **Partial**, even when `pg_stat_statements` is usable: the events still come from the pgaudit log (principal, client, application, objects, `signature.*` and `shape.*` signals) but carry no row count, so `volume.large_result` and the console's `volume.*` policies never fire on that target. `check()` explains it in the agent's local detail (which names the setting) and, since ROADMAP v0.1.x item (n), with the closed note `audit.log_without_row_counts`, so the console shows why the target is Partial (before, the reason was in the local detail only); the note is sent only while the readable pgaudit log is the source, not when an unconfigured or unreadable log leaves `pg_stat_statements`, which counts rows, as the source. A database whose pgaudit settings could not be read gets no note: nothing is proven about its row counts either way, so the cap is explained in the local detail only. Agents up to 0.2.0 reported such a server Full; set `pgaudit.log_rows = on` for the monitored databases to reach Full. The level is otherwise the best over the monitored databases, but one monitored database where pgaudit logs reads without row counts caps the whole target at Partial, as does one whose pgaudit settings could not be read (the local detail names it). Settings are read as seen from the agent's session: a per-role override for other roles is not visible.
- **`pg_stat_statements` (degraded mode).** The counters are polled and the deltas between two polls become events; the first poll is a baseline only. This source attributes the role, the database, the number of calls and the rows returned or affected in the poll interval, and the relations named by the normalized text. It sees no client address, no application name, no per-execution time or row count, no statement evicted between polls (`pg_stat_statements.max`), and no utility statement when `pg_stat_statements.track_utility` is off. Unqualified names carry no schema. The level stays Limited. Needs PostgreSQL 14+: the extension is proven loaded through its `pg_stat_statements_info` view, which PostgreSQL 13 does not have, so this mode is unavailable there.

Statement text never leaves the agent: it is analyzed locally to name objects the log does not name and to compute the signals. An access whose objects cannot be told (a function body without `pgaudit.log_relation`, text that does not parse) is reported against the object `*`, never dropped, and since ADR-0048 always reported (never dropped by `min_rows` or `sensitive_objects`, which it can never match; security review of #199, M2). `*` is a literal name, not a wildcard: console policy globs match it only as the string `*` ([09-agent-protocol.md](09-agent-protocol.md#the-object-)), so policies scoped to named objects do not see these accesses. Statements that name only catalogs are skipped. What counts as a catalog:

- relations in `pg_catalog`, `information_schema`, `pg_toast` and the temporary schemas, whether the text or pgaudit (`pgaudit.log_catalog`, `log_relation`) names them, except the [statistics catalogs](#statistics-catalogs), which are reported, and the [credential-bearing catalogs](#credential-bearing-catalogs) read outside their no-secret shape;
- `pg_stat_statements` and `pg_stat_statements_info` **only in the extension's schema** of that database, as probed from the agent's session. A `pg_stat_statements_x`, or a `pg_stat_statements` in another schema, is application data (any role with `CREATE` can make one). A database the target does not list has no known extension schema;
- an **unqualified** `pg_*` name, whose schema the text does not tell: with pgaudit and `pgaudit.log_catalog = off` (as the agent's session sees it), it is a catalog only when pgaudit names it in `pg_catalog` for the same statement, otherwise it is reported as a relation without schema; with `log_catalog` on (the pgaudit default) or unknown, and with `pg_stat_statements`, it counts as a catalog. An unqualified `pg_stat_statements` / `pg_stat_statements_info` counts as a catalog when the extension is installed in the database.

With `pgaudit.log_statement_once = on`, only the first record of a statement and substatement carries the text; later ones carry `<previously logged>`. The connector analyzes those with the first record's text of the same substatement when it read it. When it did not (the first record fell before the cursor, or in another read), the record's objects are unknown (`*`, fail safe), and the text-derived signals come only from the records whose text is known.

### Statistics catalogs

Since 0.7.0 ([ADR-0048](adr/0048-statistics-catalogs-as-reads.md)), reads of the five statistics relations that hold column values are reported, from every role, the agent's included:

| Relation | Values | Readable by |
|---|---|---|
| `pg_catalog.pg_stats` (view) | `most_common_vals`, `histogram_bounds`, `most_common_elems`: up to the statistics target (100 by default) values per column, every distinct value of a low-cardinality column, 101 raw values of a unique one | any role with `SELECT` on the column |
| `pg_catalog.pg_stats_ext`, `pg_stats_ext_exprs` (views) | the most common value combinations of `CREATE STATISTICS … (mcv)`, and the statistics of expressions | the table owner |
| `pg_catalog.pg_statistic` (table) | `stavalues1` to `stavalues5`, behind `pg_stats` | superusers and `pg_read_all_data`, past row-level security |
| `pg_catalog.pg_statistic_ext_data` (table) | `stxdmcv`, `stxdexpr` | superusers and `pg_read_all_data` |

- **Recognized** in pgaudit relation records (`pgaudit.log_relation`), and in the statement text on both sources, qualified with `pg_catalog` or unqualified; an unqualified name is reported as `pg_catalog.<name>` (`pg_catalog` comes first in the search path unless a session lists it later: a relation shadowing it is over-reported, never missed). Names are compared after the analyzer's identifier folding, and `U&"…"` identifiers after decoding their escapes (`U&"\0070g_stats"` is `pg_stats`; an escape the server would refuse makes the text unreadable, so `*`): a quoted `"PG_STATS"` or a `public.pg_stats` is an ordinary relation. With `pgaudit.log_relation = on`, a read of the views also names the tables behind them (`pg_stats` with `pg_statistic`, `pg_stats_ext` with `pg_statistic_ext_data`; seen on PostgreSQL 16). When relation records name a statement's objects, the statistics relations its text names are added to its events too, in every action class (`INSERT INTO t SELECT * FROM pg_stats`, `CREATE TABLE t AS SELECT * FROM pg_stats`), whatever `pgaudit.log_catalog` says; an unqualified one is left out only with `pgaudit.log_catalog = on`, when a record of the same substatement names a relation of that name in another schema (a relation shadowing the catalog's in the search path) and none names it in `pg_catalog`. Otherwise it is over-reported, as the catalog's.
- **Every read counts**, whole-row ones (`SELECT s FROM pg_stats s`, `TABLE pg_stats`) and those that name no value column (the `avg_width` and `null_frac` of bloat checks) included: a column test would fail open on whole-row references.
- **Always reported**: the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops these events. The row count, when the source has one, counts statistics rows. No signal is added, and these relations set no `shape.*` signal.
- **Never the agent's own**: the connector never names them ([ADR-0012](adr/0012-postgresql-agent-grants.md) obligation 1, checked by a unit test over every connector statement), so a read with the agent's identity is reported and never charged to the row budget.
- **Drift test.** On every engine-matrix image, a test fails when a `pg_catalog` relation with a column of type `anyarray`, `pg_mcv_list` or `pg_statistic[]`, or named `most_common_vals`, `histogram_bounds` or `most_common_elems`, is not listed (the one commented exception is `pg_attribute`, whose `attmissingval` holds the default of a column added with `ALTER TABLE … ADD COLUMN … DEFAULT`).
- **The analyzer's relation bound.** The text analysis keeps 16 relations per statement, catalogs included. When the text decides (`pg_stat_statements`, pgaudit without relation records, or relation records with `pgaudit.log_catalog` not proven on or naming no `pg_catalog` relation of the substatement), a statement at that bound, DDL included (`CREATE TABLE … AS`), may name a statistics relation past it: it adds `*`, is always reported and is never the agent's own, also when every relation kept is a catalog (16 catalogs, then `pg_stats`). **Application statements with 16 or more relations therefore now carry `*` and are always reported** on `pg_stat_statements`, on pgaudit without relation records, and, since the re-review of #199 (N-L1), on pgaudit with relation records whenever the substatement has no `pg_catalog` record: every large join of application tables only, whatever `pgaudit.log_catalog` says. No connector statement reaches the bound (unit test).
- **`pgaudit.log_catalog`.** With `log_catalog = on` (the pgaudit default, and the recommended setting: [10-user-guide.md](10-user-guide.md)) pgaudit logs statements on catalogs only, and their relation records name the statistics relations. With `log_catalog = off`, a statement whose relations are all in `pg_catalog` is not logged, so a read of `pg_stats` alone gives no event on that source; a statement that also reads an application table is logged, and the statistics relations its text names are reported with it. `check()` says so in the agent's local detail (it names the setting and the database) when pgaudit is the source; the level is unchanged and no target note is sent.
- **Noise.** Scheduled bloat checks (check_postgres, pgwatch and the widely copied bloat queries read `pg_stats`), monitoring helpers and DBAs on demand now produce events. Aggregation bounds each principal to one event per object set, action and source and `aggregation_window_s` (60 s by default); there is no agent-side allow-list, and the console can scope or exclude principals.

### Statement-text views

Since 0.7.0 ([ADR-0049](adr/0049-postgresql-statement-text-views-as-reads.md)), reads of the views and functions that hold other sessions' statement texts are reported, from every role, the agent's included, unless the statement provably selects no text:

| Name in the text | Named in events as | Text |
|---|---|---|
| `pg_stat_activity` (view), `pg_stat_get_activity(…)` (set-returning function), qualified with `pg_catalog` or unqualified | `pg_catalog.pg_stat_activity` | the column `query`: each backend's current or last statement, literals included; a role sees its own role's sessions, `pg_read_all_stats` members (and `pg_monitor`) and superusers every session |
| `pg_stat_get_backend_activity(…)` | `pg_catalog.pg_stat_activity` | the result is the text: always a text read |
| `pg_stat_statements` (view), `pg_stat_statements(…)` (function), qualified with the extension's schema or unqualified while the extension is installed in that database | `<schema>.pg_stat_statements` | the column `query`: normalized texts, utility statements as sent (`ALTER ROLE … PASSWORD '…'` and SCRAM verifiers in clear; verified on PostgreSQL 14 to 18); the view is readable by `PUBLIC`, other roles' texts only with `pg_read_all_stats` |
| `pg_stat_monitor`, `pg_store_plans`, `pg_show_plans`, `pg_qualstats*` (extension list), in any schema or unqualified | the name as the text gives it; a call: `*` | texts, plans, predicate constants: always a text read |

- **The no-text shape** (core list only). A statement that names a core-list view or set-returning function stays a catalog read (no event when everything else it names is a catalog) only when all of these hold on its whole text: it lexes, is not cut (the 8 192-character read bound of `pg_stat_statements`, a `<previously logged>` record without its first record) and stays below the analyzer's 16-relation bound; every relation and `FROM` function it names is a catalog or a core-list entry; no identifier is `query` (quoted, `U&`-escaped, in any clause, `query(a)`, `AS query`); no `*` but `count(*)`; no whole-row reference (an alias of a listed item, the unaliased view or function name, or a parenthesized join's alias, used other than as `<name>.<column>`: `row_to_json(a)`, `a::text`, `(a).*`, `SELECT a`, `NULL::pg_stat_activity`, an alias equal to a column name); no column alias list anywhere (a table, subquery, parenthesized join, function, `ROWS FROM`, `WITH ORDINALITY` or CTE column list, whatever the alias's word: `pg_stat_activity zone (c1, …)`, `AS set (c)` and `AS second (c)` are refused like `AS a (c)`), except on a parenthesized `VALUES` list of constants ([refinement of 2026-10-11](adr/0049-postgresql-statement-text-views-as-reads.md#refinement-2026-10-11-verified-server-facts-and-implementation), accepted, which keeps `postgres_exporter`'s activity query quiet); no `NATURAL`; no call of a schema-qualified function outside `pg_catalog` and the lists (`SELECT a.pid, public.f() FROM pg_stat_activity a` is a text read: refinement item 7, accepted, kept with decision 8 as defence in depth; unqualified calls are decision 8's, [below](#user-code-next-to-catalogs)); the set-returning function only as a `FROM` item (or in `ROWS FROM`); no `TABLE pg_stat_activity`. So `SELECT state, count(*) FROM pg_stat_activity GROUP BY state`, `postgres_exporter`'s activity query, `SELECT pid FROM pg_stat_activity WHERE state = 'idle'` and `SELECT queryid, calls FROM pg_stat_statements` give no event; anything the shape cannot prove is a read naming the view. The shape is decided on the text, on both sources; it over-reports (`CAST(x AS varchar(10))` outside a `CAST`, a type with modifiers after `AS`, unusual syntax) and never misses a form it knows.
- **pgaudit relation records** (`pgaudit.log_relation = on`; verified on PostgreSQL 16 with pgaudit 16.0: a read of `pg_stat_activity` gets records of the view and of `pg_database` and `pg_authid`; a user view over it adds the view's record in the same substatement; an SQL function's body gets its own substatement with its text). A record of a listed entry that the substatement's text does not name (a user view, a function body, another search path) makes the event a text read naming it; a record of a core-list view the text names keeps the text's shape decision, unless the same substatement also has a record of a view, materialized view or foreign table outside `pg_catalog`. With `log_catalog = off` the `pg_catalog` records are left out (verified), so a user view over `pg_stat_activity` is named by itself only.
- **Always reported**, in every action class (`CREATE TABLE t AS SELECT query FROM pg_stat_activity`, `INSERT … SELECT`, `COPY (…) TO`): the `audit.configure` filter never drops a text read. The row count, when the source has one, counts rows of the view. No signal is added, and these views set no `shape.*` signal.
- **Functions that read past the statement's relations** (decision 7): a call, qualified with `pg_catalog` or unqualified, of `query_to_xml`, `query_to_xmlschema`, `query_to_xml_and_xmlschema`, `cursor_to_xml`, `cursor_to_xmlschema`, `table_to_xml*`, `schema_to_xml*`, `database_to_xml*`, `ts_stat`, `ts_rewrite`, `pg_read_file`, `pg_read_file_old`, `pg_read_binary_file`, `pg_logical_slot_get_changes`, `pg_logical_slot_peek_changes` and their `_binary_` forms, `lo_get`, `loread`, `lo_export` or `lo_import` adds `*` to the statement, always reported, never the agent's own, also when every relation it names is a catalog (`SELECT pg_read_file('log/postgresql.log') FROM pg_class LIMIT 1`).
- **The agent's own account.** The connector's `pss_counters` reads `pg_stat_statements(false)` in the no-text shape, a catalog read for every account; its `pss_texts` (the text query of the `pg_stat_statements` source) is a text read left out uncharged only by exact text (below); every other text read with the agent's identity is reported. The connector reads `pg_stat_activity` nowhere (unit test over every connector statement).
- **Drift and pinning tests** (every engine-matrix image): every relation of `pg_catalog`, `information_schema` and the extension's schema with a column named `query`, `statement`, `query_text`, `current_query`, `ident`, `plan` or ending in `_query` / `_statement`, and every such function, is listed or a commented exception (`pg_prepared_statements`, `pg_cursors`, `pg_backend_memory_contexts` and their functions: the reading session's own; `pg_stat_get_backend_activity_start`: a timestamp; `information_schema.triggers.action_statement`: trigger definitions); every `pg_catalog` function returning text, `bytea` or records whose name suggests files, slots, decoded changes or large objects is on the decision 7 list or a commented exception. One assertion each pins: `<insufficient privilege>` for another role's `query` without `pg_read_all_stats` and the role's own texts in clear; `PUBLIC` reads the `pg_stat_statements` view; an `ALTER ROLE … PASSWORD` literal kept as sent in `pg_stat_statements`; with pgaudit, `log_catalog = off`, `SELECT … FROM pg_stat_get_activity(NULL)` logged (it names no relation) while a read of the view alone is not; the relation records above.
- **Noise.** Query-sampling tools (Datadog Database Monitoring, pganalyze, PMM, PoWA, pgAdmin's dashboard) and DBAs' scripts that read `query` now produce events, one per principal, object set, action and source per `aggregation_window_s` (a reader every 10 s is at most 1 440 events per day and target), under the console's per-target hourly cap. Exporters, pools and health checks that read `pg_stat_activity` without the text stay quiet. There is no agent-side allow-list; the console can scope or exclude principals.
- **`pg_read_all_stats` with pgaudit.** When pgaudit is the source (Full or Partial), the agent's `pg_read_all_stats` serves only the `pg_stat_statements` fallback and still lets whoever holds the agent's credentials read every role's texts: `check()` says so in the agent's local detail (no target note). Who else reads statement texts: [05-security.md](05-security.md#recommended-database-accounts-read-only).

### Credential-bearing catalogs

Since 0.7.0 ([ADR-0050](adr/0050-postgresql-credential-and-value-bearing-catalogs-as-reads.md)), reads of the catalogs that hold credentials and stored values are reported, from every role, the agent's included, unless the statement provably selects no secret column. Verified on PostgreSQL 14.24, 15.19, 16.13, 17.11 and 18.6 (`it_secrets.rs`; the pgaudit facts on 16.13 with pgaudit 16.0):

| Name in the text | Named in events as | Secret columns | Readable by |
|---|---|---|---|
| `pg_authid` | `pg_catalog.pg_authid` | `rolpassword` (SCRAM verifiers, MD5 hashes) | superusers, `pg_read_all_data` |
| `pg_shadow` | `pg_catalog.pg_shadow` | `passwd`, `useconfig` | superusers, `pg_read_all_data` |
| `pg_roles` | `pg_catalog.pg_roles` | `rolconfig` (role settings in clear) | every role |
| `pg_user` | `pg_catalog.pg_user` | `useconfig` | every role |
| `pg_db_role_setting` | `pg_catalog.pg_db_role_setting` | `setconfig` (every role, database and role-in-database setting in clear) | every role |
| `pg_user_mapping` | `pg_catalog.pg_user_mapping` | `umoptions` (FDW user names and passwords) | superusers, `pg_read_all_data` |
| `pg_user_mappings` | `pg_catalog.pg_user_mappings` | `umoptions` | the mapped role for its own mapping, server owners, superusers |
| `pg_foreign_server` | `pg_catalog.pg_foreign_server` | `srvoptions` | every role |
| `pg_subscription` | `pg_catalog.pg_subscription` | `subconninfo` (the publisher's connection string, password included) | superusers, `pg_read_all_data` |
| `pg_proc` | `pg_catalog.pg_proc` | `proconfig` (function `SET` clauses in clear) | every role |
| `pg_largeobject` | `pg_catalog.pg_largeobject` | every column | superusers, `pg_read_all_data` |
| `pg_file_settings`, `pg_show_all_file_settings()` | `pg_catalog.pg_file_settings` | every column (`postgresql.auto.conf` included) | superusers |
| `pg_hba_file_rules`, `pg_hba_file_rules()` | `pg_catalog.pg_hba_file_rules` | every column (`radiussecrets`, `ldapbindpasswd` in clear, verified on 14 to 18) | superusers |
| `information_schema.user_mapping_options`, `_pg_user_mappings`, `foreign_server_options`, `_pg_foreign_servers` | as named (no schema when the text gives none) | every column | as `pg_user_mappings` / the server's `USAGE`; `_pg_*` revoked from `PUBLIC` |

- **The no-secret shape** (the first ten entries). A statement that names one stays a catalog read (no event when everything else it names is a catalog) only when, on its whole text: it lexes, is not cut and stays below the analyzer's 16-relation bound; every relation and `FROM` function it names is a catalog, an entry of this list or a statement-text view; no identifier equals a secret column of an entry it names (in any clause, a comparison `WHERE rolpassword LIKE 'md5%'` and an alias `AS setconfig` included); no `*` but `count(*)`; no whole-row reference (`SELECT r FROM pg_roles r`, `row_to_json(r)`, `r::text`, `(r).*`, `TABLE pg_roles`); no column alias list (except on a `VALUES` list of constants), no `NATURAL`, no `COPY <entry>`; and no call of a function that is not built in (a schema-qualified call outside `pg_catalog` and `information_schema`, or an unqualified call, operator or cast that [decision 8](#user-code-next-to-catalogs) does not prove built in). A CTE the text defines before using it (`WITH me AS (SELECT r.oid FROM pg_roles r) …`) counts as a catalog: its query is held to the same rules. So `psql`'s `\du`, `SELECT r.rolname FROM pg_roles r WHERE r.rolsuper`, `SELECT subname, subenabled FROM pg_subscription`, `SELECT p.proname FROM pg_proc p` and `SELECT count(*) FROM pg_authid` give no event; anything else that names an entry is a **secret read** naming it, in every action class (`CREATE TABLE t AS SELECT rolpassword FROM pg_authid`, `COPY (SELECT …) TO STDOUT`). An unqualified `pg_*` name of the list is the catalog's (with pgaudit and `log_catalog = off`, unconfirmed by a record, it is a secret read). A quoted `"PG_AUTHID"` or a `public.pg_authid` is an ordinary relation.
- **pgaudit relation records.** With `log_relation = on`, a read of a built-in view names the tables behind it (`pg_roles` gets `pg_authid` and `pg_db_role_setting`, `pg_stat_activity` gets `pg_authid`; verified): those records alone do not make a secret read. A record of an entry the text does not name makes the event a secret read naming it only next to a record of a user view, materialized view or foreign table (outside `pg_catalog` and `information_schema`) in the same substatement, or when the text names no relation (`EXECUTE` of a prepared read). So a user view `public.v_pw AS SELECT rolname, rolpassword AS p FROM pg_authid` is reported as a secret read of `pg_catalog.pg_authid`, and **a user view over `pg_roles` without a secret column is too** (an accepted over-report: the records do not say which columns the view exposes).
- **Always reported**: the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops a secret read; one row is one credential. The row count, when the source has one, is kept. No signal is added.
- **Never the agent's own**, except its two-key reads (below): any other secret read with the agent's identity is reported and never charged to the row budget. The connector's statements on `pg_roles` and `pg_proc` (`check()`'s role and ownership checks, the parameter grants, Discovery's introspection and row-level security policy check, the collision probe of decision 8) have the no-secret shape (unit test over every connector statement).
- **The agent's two-key reads** ([ADR-0012 refinement of 2026-10-12](adr/0012-postgresql-agent-grants.md#refinement-2026-10-12-accepted-a-two-key-read-of-pg_db_role_setting)): `check()` reads the two log settings in `pg_db_role_setting.setconfig` and `pg_proc.proconfig`, filtered by the server ([Failed and cancelled statements](#failed-and-cancelled-statements)). They are left out as the agent's own **on pgaudit only**, by their whole text as sent (constants included), from the agent's account, `application_name` and client address, with no signal and no record of another entry of the list. They are never left out on `pg_stat_statements`, which stores their constants as `$n` (verified on 14 to 18: a replay with other keys would have the same stored text), and they are not sent while a `pg_stat_statements` stream of the target runs.
- **`pgaudit.log_catalog = off`.** A read of a `pg_catalog` entry alone is not logged, and a user view over one is logged with its own record only: it is an event naming the view, under the filters. The `information_schema` entries are logged. `check()`'s local detail says so; keep `log_catalog = on`.
- **Drift and pinning tests** (every engine-matrix image): every relation of `pg_catalog` and `information_schema` with a column whose name holds `password`, `passwd`, `conninfo`, `config` or `options`, or ends in `_value`, and every `bytea` column of `pg_catalog`, is listed or a commented exception (storage, tablespace, FDW wrapper, table and column options, sequence bounds, server constants, `pg_extension.extconfig`, `pg_trigger.tgargs`, the statistics relations of ADR-0048, `pg_settings`, `pg_stat_wal_receiver.conninfo`, whose password the server obfuscates); every view whose definition reads a secret column is listed or excepted (`pg_stat_activity`, `information_schema.user_mappings` and `foreign_servers` read them for names only). One assertion each pins the readers of the table above, the pgaudit records of a `pg_roles` read and of a user view over `pg_authid`, the `log_catalog = off` behaviour, and the `pg_stat_statements` form of the two-key read.
- **Noise.** Events come from what really reads secrets: `pg_dump` and `pg_dumpall`, PgBouncer's default `auth_query` on `pg_shadow` (one event per pooler principal and aggregation window, at most 1 440 a day under the console's per-target hourly cap), admin tools that read `rolconfig`, `proconfig`, `pg_roles.*` or `pg_proc.*` (pgAdmin's properties, DBeaver), `psql`'s `\drds`, `\deu+`, `\dRs+`, and reads of user views over `pg_roles`. Reads without secret columns, the bulk of `pg_roles` and `pg_proc` traffic, stay quiet. There is no agent-side allow-list; the console can scope or exclude principals.
- **Load.** No query against the server for the list; the shape test runs only on texts that name an entry, as a pass over tokens the analyzer already reads.

### User code next to catalogs

Since 0.7.0 ([ADR-0049](adr/0049-postgresql-statement-text-views-as-reads.md) decision 8), a statement whose relations are all catalogs (otherwise no event) is a read of `*`, always reported and never the agent's own, when it runs code that is not built in for that database. This includes the statements that wrap a query (`PREPARE … AS`, `EXPLAIN [ANALYZE]`, `DECLARE … CURSOR FOR`, `CREATE [TEMP] TABLE … AS`, `CREATE MATERIALIZED VIEW … AS`, judged on their query; the `DDL` event of a `CREATE … AS` gets the `*` too), and any other statement of such a text, judged on its whole text:

- a call of a function qualified with a schema other than `pg_catalog` (`SELECT crm.f() FROM pg_class`), of a `pg_catalog` function not on the built-in list of the server's major version (an extension created in `pg_catalog`), or of an unqualified function that is not built in or that a user overload shadows in that database (`SELECT my_f() FROM pg_class`; `SELECT length(42) FROM pg_class` once a role has created `"$user".length(integer)`);
- an operator written `OPERATOR(<schema>.<op>)` outside `pg_catalog`, or an unqualified one, written or implied by `LIKE`, `ILIKE`, `SIMILAR TO`, `BETWEEN`, `IN`, `IS DISTINCT FROM`, a simple `CASE`, `NULLIF`, `USING (…)` or `NATURAL`, that is not built in or that a user overload shadows;
- a cast (`::t`, `CAST(… AS t)`, a typed literal `t '…'`, `RETURNING t`, a column definition list) to a type that is not built in: a user type or domain, a user type named like a built-in one, or the target of an explicit user-function cast between built-in types.

The functions of the [statement-text lists](#statement-text-views) and of decision 7 keep their own rules. Details and verified server facts: the ADR's [part 2 refinement](adr/0049-postgresql-statement-text-views-as-reads.md#refinement-2026-10-11-part-2-decision-8-as-implemented) (accepted on 2026-10-11).

- **Built-in lists**, one set per major version 14 to 18 (functions, operators, types, keywords), generated from the engine-matrix images ([`agent/crates/connector-postgres/builtins/`](../agent/crates/connector-postgres/builtins/generate.sh)); a drift test compares them with every engine-matrix image, both ways. A newer server uses the newest lists and the agent logs a warning: names added since are reported. `information_schema` functions and types are built in when qualified (`information_schema._pg_expandarray`, as pgJDBC calls it).
- **The collision probe.** At every heartbeat, `check()` runs one bounded query in each declared database, from catalogs every role can read (at most 20 000 names, kept in the agent's memory only: never logged, never sent). It lists the built-in function and operator names that a user overload (outside `pg_catalog` and `information_schema`) shadows for the values and literals of a catalog-only statement (the CVE-2018-1058 class: `"$user".length(integer)`, a `public` `+` on `integer`, an overload on a type that a built-in type casts to implicitly, an overload a literal reaches through PostgreSQL's type resolution, a defaulted argument), the user types named like built-in ones, and the user-function casts between built-in types: an implicit or assignment one (superuser only) makes **every** catalog-only statement of that database `*`, the agent's own included. With a bound parameter in the statement (on `pg_stat_statements`, a constant too: they are both `$n` there), any user overload whose code is not C is a collision too, since the client types the parameter; and in a database with a user domain whose `CHECK` calls code that is not C, every catalog-only statement with a parameter is `*`, except the connector's own statements recognized by their exact text from the agent's identity.
- **Extensions.** `citext` adds no collision; with `hstore`, the operator `->` collides (`'a=>1' -> ARRAY['a']` reaches hstore's `->(hstore, text[])`) and is `*` unqualified next to catalogs only; citext's SQL-language wrappers (`regexp_replace` and the other `regexp_*`, `replace`, `split_part`, `strpos`, `translate`) are `*` unqualified with a parameter or a constant.
- **Stale, missing and old probes.** When the stream sees `CREATE`, `ALTER` or `DROP` of a function, procedure, aggregate, operator, type, domain, cast or extension (or `DROP OWNED`, `DROP SCHEMA`, a `DROP … CASCADE`) in a database (pgaudit's `ddl` class; `pg_stat_statements.track_utility`), that database's probe is stale until two heartbeats have probed it again; on pgaudit this follows log order, on `pg_stat_statements` it applies to the whole poll that shows the DDL. While a probe is stale, before the first one, when it fails, is cut or is more than 15 minutes old, and in a database the target does not declare (never probed), every unqualified call, operator and cast next to catalogs only is `*`; qualified `pg_catalog` names stay quiet.
- **Noise.** `psql`'s describe queries (`\d` and friends) and `postgres_exporter`'s catalog queries stay quiet, also in a database with `citext`, `hstore` and 3 000 relations (integration test). Expect events from catalog queries that call extension or user functions, use user operators or cast to user types; a burst after migrations that create functions or types, until two heartbeats have probed again; from tools connected to a database the target does not declare (declare the databases monitoring tools use); and, in a database with an explicit user cast to a built-in type such as `text`, from the agent's own casts to that type.
- **The agent's own statements** use `pg_catalog`-qualified functions and types and `OPERATOR(pg_catalog.…)` only, as `psql` does, so none of them triggers this rule whatever the probe finds and while it is unknown (unit test over every connector statement), except under a user cast between built-in types.
- **Cost.** One query per declared database and heartbeat, whose cost does not grow with the number of relations (12 to 35 ms on PostgreSQL 16 with `citext`, `hstore` and 3 000 relations); the scan of a statement text reuses the analyzer's lexer.
- **Residuals.** Code in a statement that also names an application relation (the event names that relation), and remote-query functions such as `dblink`; a function, operator, type or cast created without the stream seeing its DDL (`pgaudit.log` without `ddl`, `track_utility = off`, a DDL run by a function body or a `DO` block on `pg_stat_statements`) and used before the next heartbeat, or created in a transaction that commits after a heartbeat's probe; a domain `CHECK` that calls a `pg_catalog` function directly (no dependency is recorded on initdb's objects); a `search_path` that lists `pg_catalog` after a user schema is covered (the probe lists overloads whatever their schema).

### Statements that wrap a query

Since 0.7.0 (phase 8 follow-ups, lot F; [ADR-0048 refinement of 2026-10-12](adr/0048-statistics-catalogs-as-reads.md#refinement-2026-10-12-accepted-statements-that-wrap-a-query), accepted on 2026-10-12; security review of #199, L3), `EXPLAIN [ANALYZE]`, `DECLARE … CURSOR … FOR` and `PREPARE … AS` are reported as the query they wrap, on both sources. Before, `pg_stat_statements` gave no event for them, so a read through a cursor (`DECLARE … CURSOR FOR SELECT …` then `FETCH`, what psql's `FETCH_COUNT` sends), an `EXPLAIN ANALYZE` and the `EXECUTE`s of a prepared statement (which `pg_stat_statements` counts under the `PREPARE` text) were not reported there, statistics catalogs and statement-text views included.

- **Objects**: the relations the query names, with every rule of a bare query: catalogs only give no event, [statistics catalogs](#statistics-catalogs) are named, [statement-text views](#statement-text-views) are text reads unless the query has the no-text shape, [user code next to catalogs](#user-code-next-to-catalogs) is `*`. A query the text does not show (`EXPLAIN EXECUTE p`) is a read of `*`.
- **Action**: a plain `EXPLAIN` (no `ANALYZE`, or `ANALYZE false` / `off` / `0` in its option list) is a **read**, explained writes included: the query is not run, but the plan shows row estimates from the statistics (a value guess answered from `pg_statistic`), the partitions pruning keeps, and the planner folds immutable and stable calls, as [ADR-0047](adr/0047-mysql-mariadb-explain-as-a-read.md) found on MySQL / MariaDB. pgaudit's `WRITE` record of a plain `EXPLAIN DELETE …` is a read too. `EXPLAIN ANALYZE`, a cursor and a prepared statement **act as their query**: `EXPLAIN ANALYZE DELETE` is a write, `EXPLAIN ANALYZE CREATE TABLE … AS` DDL, anything else a read.
- **Row counts**: explains and cursors carry none (an explain sends no row; a cursor's rows go out through `FETCH`, which names no relation, and pgaudit counts 0 on the `DECLARE` record) and are **always reported**, whatever `min_rows` and `sensitive_objects` say. A prepared statement's executions keep their row counts (and `volume.large_result`) and the filters. pgaudit also writes a record when the statement is prepared (0 rows, nothing run): a read of 0 rows under the filters.
- **Signals**: a cursor's or a prepared statement's query keeps its `shape.full_table_read`; an explain has no `shape.*` or `signature.*` signal.
- **`FETCH`, `MOVE`, `CLOSE`, `DEALLOCATE`** give no event: they name no relation, and the `DECLARE` event names what the cursor reads. pgaudit logs them in its `misc` class only; their `pg_stat_statements` row counts are not attributed.
- **Never the agent's own**: the connector sends none of these statements (unit test over every connector statement), so one with the agent's identity is reported and never charged.
- **Once**: pgaudit gives one event per class and statement, as before. `pg_stat_statements` with `track = all` also keeps a nested entry of the query (under the first explain text seen for it), whose event the core aggregates with the top-level one.
- **Limits**: with `pg_stat_statements.track_utility = off`, cursors and explains leave no entry at all; a cursor read has no row count on either source, so volume policies do not see it; a cursor opened inside a function is the function body's.

### Failed and cancelled statements

With `pgaudit.log_rows = on` (needed for Full), pgaudit writes a statement's records when the statement ends, so a statement that fails or is cancelled has no `AUDIT:` record. Since 0.7.0 and the [ADR-0037 refinement of 2026-10-12](adr/0037-postgresql-full-requires-pgaudit-log-rows.md#refinement-2026-10-12-accepted-failed-and-cancelled-statements), when the pgaudit log is the source (Full or Partial), the connector also reads the server's `ERROR` lines, and the `FATAL` lines that carry a statement (a connection lost or terminated in the middle of a statement), of client connections, from the same file. Verified on PostgreSQL 16 with pgaudit 16.0, jsonlog and csvlog (integration tests `it_wrapped::failed_reads_and_what_is_reported` and `it_wrapped::forced_25p02_and_42601_through_user_code`): a failed cast whose error quotes the value read (22P02), a read that sends 59 of its 60 rows and then fails on purpose (22012), a read cancelled by `statement_timeout` or by the client (57014) and a read whose client closes the connection in the middle of the result (`FATAL` 08006) are each reported, from any role, the agent's included.

- **What is read.** The severity, the SQLSTATE, the user, database, application, client address, session, virtual transaction, time, and the statement text, which is analyzed locally and never leaves the agent. The message, detail, hint, context and internal query, which can quote values (22P02 quotes the value read, a 23505 detail quotes a key, a PL/pgSQL `RAISE` can say anything), are **never copied, logged or sent** (I2); of the context, only its presence is used. Lines of the server's own processes (a closed list: autovacuum, parallel workers, whose errors their leader re-raises, the checkpointer, the WAL writer, logical replication workers…; replication connections, extensions' background workers and unknown types are read) and `LOG` lines (the `LOG` 08006 "could not send data to client" before a `FATAL` 08006) are not read.
- **Classes, by SQLSTATE only, never the message:**

  | Class | Codes | Event |
  |-------|-------|-------|
  | Refused | `25P02` without a context whose text calls only built-in code (a statement sent in an aborted transaction, rejected before parsing); `28xxx` / `3D000` without a statement (connection refused); `42601` without a context whose text does not lex and holds no call, cast or operator character | none |
  | Quiet | every other code of classes `42`, `3F`, `0A`, `25`; `57014` (timeout, a client's cancel), `57P01` to `57P05`, `40001`, `40P01`, `55P03`; classes `53`, `54`, `08`, `58` | a read of the statement's relations (a DDL or DCL keeps its action), with no row count, **always reported**; from the agent's identity, charged the whole own-read budget like an unknown row count |
  | Telling | every other code (`22`, `23`, `27`, `44`, `P0`, `XX`…), and a missing or unknown one | the statement's action, with no row count, **always reported** (a plain `INSERT … VALUES`, whose message quotes only its own values, is an ordinary write under the filters), **never the agent's own** |

  A user function can raise any SQLSTATE after rows were sent (`RAISE … USING ERRCODE`), also through code the text does not show (a view, a row-level security policy, a user operator or cast, a domain `CHECK`): such a line has a context, so a `25P02` or `42601` with a context is never refused, and nothing is refused when the text calls code that is not built in ([User code next to catalogs](#user-code-next-to-catalogs) decides what is built in).
- **The event** is built from the statement text with every rule of a statement that succeeds: relations named, catalogs skipped (an unqualified `pg_*` name is not a catalog here: no pgaudit record confirms it), [statistics catalogs](#statistics-catalogs), [statement-text views](#statement-text-views), [user code next to catalogs](#user-code-next-to-catalogs), [statements that wrap a query](#statements-that-wrap-a-query) and the `shape.*` / `signature.*` signals. It never has a row count (the rows sent before the error are not known), so `volume.*` policies do not see them; it is always reported instead. `DO`, `CALL`, `EXECUTE`, `FETCH` and other statements whose code or rows the text does not name add `*`; transaction control, `SET`, `SHOW` and the like give no event. An `ERROR` line without a statement text is a read of `*`. A `FATAL` line without one ends an idle session (an idle timeout, `pg_terminate_backend`) and gives no event, but only in a database where the settings below are proven, for that line's role; elsewhere (a setting above `error` or not read, an override for that role, a database the target does not declare) it is a read of `*` too.
- **Not twice.** With `pgaudit.log_rows = off` (Partial, or for some roles), pgaudit writes the record when the statement starts and the failed read is reported from it: the line that follows in the same session, with the same text and virtual transaction, is not reported again.
- **Settings.** `check()` reads `log_min_messages` (above `error`, no `ERROR` line is written) and `log_min_error_statement` (above `error`, the line has no statement text), both readable by every role, in each monitored database where pgaudit is loaded. Either one above `error`, or not read, caps the target at **Partial**, and the agent's local detail names the setting and the database (no target note). The defaults (`warning`, `error`) are fine.
- **Overrides for other roles** (since 0.7.0, [ADR-0012 refinement of 2026-10-12](adr/0012-postgresql-agent-grants.md#refinement-2026-10-12-accepted-a-two-key-read-of-pg_db_role_setting)). The agent's session does not see another role's `ALTER ROLE … SET` or `ALTER ROLE … IN DATABASE … SET`, nor a function's `SET` clause (verified: with `ALTER ROLE other SET log_min_messages = fatal`, a failed read by `other` wrote no `ERROR` line). So, in each monitored database whose level would be Full, and only while no `pg_stat_statements` stream of the target runs, `check()` and the stream's 5-minute probe read three catalogs every role can read: the two keys of `pg_db_role_setting` (role-wide, database-wide and role-in-database entries that apply to the database) and of `pg_proc.proconfig`, **filtered by the server in the same statement** (no other setting, which can hold a secret, reaches the agent), and, on PostgreSQL 15+, the `SET` and `ALTER SYSTEM` grants on the two settings (`pg_parameter_acl`) to roles other than the agent's and superusers, `PUBLIC` included. Any override above `error`, any such grant, a statement refused (for instance `pg_db_role_setting` revoked from `PUBLIC`: grant `SELECT` on it to the agent's role) or a result cut at 1 000 rows caps the target at **Partial**; the agent's local detail names the database, the setting and the roles (or "every role", or the functions, normalized, at most 10 then a count, never a level or another value). While a `pg_stat_statements` stream of the target runs, the database is not proven. Reset the overrides (`ALTER ROLE … RESET log_min_messages`) and revoke the grants to get Full back at the next heartbeat. Three statements per monitored database and probe (two on PostgreSQL 14), measured at 0.2 ms, 5 ms and 0.2 ms on PostgreSQL 16 with 3 000 relations; nothing when the target is not at Full.
- **`FATAL` lines without a statement, per role.** Such a line gives no event only where the database is proven for the line's role: a role with an override of `log_min_error_statement` above `error`, or a `SET` grant on it, writes its `FATAL` lines without the statement even while one runs, so its lines are reads of `*`; so are every role's in a database with a database-wide override, a function `SET` clause on it, a `PUBLIC` or `ALTER SYSTEM` grant on it, or a proof not read. When the stream reads an `ALTER ROLE`, `ALTER DATABASE`, `ALTER SYSTEM`, a parameter `GRANT` / `REVOKE` or a function's `CREATE` / `ALTER`, the proof is stale (every database, or the function's) until two probes that start later, and every such line is a read of `*` meanwhile (over-reported, never missed).
- **Load.** An error line costs about what an `AUDIT:` record costs (one parse and one analysis of its text, about 50 µs on one core in a release build); the last text's analysis is reused, so a storm of one failing statement (an application looping on a missing table, 42P01) costs about 15 µs per line, and its events are merged by the agent into one per principal, action, objects and aggregation window before they are sent.

### Signals

The signal ids are registered in [`shared/protocol/signals.json`](../shared/protocol/signals.json) (append-only, #60).

| Signal | When it is set |
|--------|----------------|
| `signature.pg_dump` | `application_name` is `pg_dump` or `pg_dumpall` (pgaudit only; spoofable), or one session (with `pg_stat_statements`: one role within one poll) copied at least 3 distinct whole relations to the client (`COPY … TO STDOUT`) |
| `signature.copy_to_file` | `COPY … TO '<file>'`; also a pgaudit `COPY` record whose text does not show the `COPY` (dynamic `EXECUTE`, `format()`, nested `DO`), since PL/pgSQL cannot copy to the client |
| `signature.copy_to_program` | `COPY … TO PROGRAM` |
| `shape.full_table_copy` | `COPY` out of a whole relation, or of a query without filter, aggregation or small limit |
| `shape.full_table_read` | A read (`SELECT`, `TABLE`) of a non-catalog relation without a top-level `WHERE`, `GROUP BY` or aggregate-only list, or derived table, and with no limit or a limit above 10 000 rows |
| `volume.large_result` | More than 10 000 rows returned or affected, by one statement (pgaudit with `pgaudit.log_rows`) or in one `pg_stat_statements` counter delta |

Both 10 000 thresholds sit just above the largest Discovery sample (`limits.max_sample_rows` is at most 10 000), so the agent's own Discovery statements never carry these signals. The `shape.*` and `signature.*` signals are heuristics, evadable by design (`WHERE true`, `LIMIT 10000` pages, a spoofed `application_name`); the volume × sensitivity score computed by the console is the robust signal.

`DO` blocks: the body is analyzed (one level deep) only when it is PL/pgSQL, meaning no `LANGUAGE` clause or `LANGUAGE plpgsql`. A body in any other language (`plv8`, `plperl`, `plpython3u`…), a `LANGUAGE` clause that cannot be read, or a body whose reading depends on `standard_conforming_strings` is not lexed as SQL at all (fail closed): no object name is taken from it, and the event carries only what pgaudit names, or `*`.

### The agent's own account

The agent's own Discovery reads would otherwise show up as access events. An event of the agent's account is left out only when **all** of these hold:

- it is a read or a connection: **writes, DDL and DCL of the agent's account are always reported** (the agent never writes, I4, so such an event with its identity is someone else using it; #76, commit `35c6459`, [ADR-0027](adr/0027-mongodb-audit.md) decision 7);
- it comes from the agent's `application_name` (`databastion-agent`; checked with pgaudit only);
- it comes from the agent's own client address as the server sees it (`inet_client_addr()`, probed at stream start; checked with pgaudit only). When the agent's address cannot be read, or a record carries no address, nothing is left out;
- it carries no signal: events with a signal are always kept;
- the agent's reads of each object stay within `limits.max_sample_rows` rows over a rolling 24 h. A statement with an unknown row count (no `pgaudit.log_rows`) is charged the whole budget. A second Discovery scan of the same table within 24 h therefore shows up as events of the agent's account. Since the phase 8 follow-ups **every statement is charged at least one row** (with `pg_stat_statements`, one per call of the entry's delta), on every engine that uses this rule (PostgreSQL, MySQL / MariaDB, MongoDB, OpenLDAP): a read that returns no row can still show values (a conversion warning or an error that quotes them, or the bare fact that a filter matched nothing), and was charged nothing before, so a walk of such reads with the agent's identity went unreported without limit. One row each caps it at the budget per object and 24 h; past it, the reads are reported (security review of #196, Low), as far as the console's `audit.configure` settings let them through: a read of 0 rows passes only when the object is in `sensitive_objects` or no `min_rows` is set ([09-agent-protocol.md](09-agent-protocol.md)). An aggregated event (a `pg_stat_statements` delta of `n` calls and `r` rows) is charged `max(r, 1) + n - 1`, the most the calls can cost one by one. Budget keys ignore case on every engine (Unicode lowercase of database, schema and object; security review of #197, M2): `crm."T"` and `crm.t` share one budget, which only reports sooner. The agent's own Discovery sends few such reads per object and scan (the sample of an empty table, a short `TABLESAMPLE` before the plain read, an empty registry's ticket type count), and since the review of #197 (L3) the plain read after a short `TABLESAMPLE` takes only what the sample left of the row limit (counting it at least one row) and of the byte budget, so one scan stays within the budget. **What it does not cover**: the charge applies to the reads the source records. `pg_stat_statements` counts no statement that failed, so on that source a value walk through error messages (a failed cast that quotes the value it read) gives no event for any account, the agent's or another. With pgaudit, since the [failed statements](#failed-and-cancelled-statements) are read from the server's `ERROR` lines, a failure whose code can carry a value (telling) is always reported and never the agent's own, and a quiet failure from the agent's identity is charged the whole budget (the agent cancels its own sampling statements at the byte budget, 57014). Until 0.6.x, with `pgaudit.log_rows = on`, such reads gave no event either.

With `pg_stat_statements`, application and address are not visible: only the action, signal and row-budget rules apply.

**The connector's own table-less statements** (#65). The connector sends a few statements that read no relation: the per-connection and per-transaction `pg_catalog.set_config(…)` / `current_setting(…)` (one per transaction, about 90 per Discovery scan), `pg_catalog.host(pg_catalog.inet_client_addr())`, and, in `pg_stat_statements` mode, its text query through the extension's `pg_stat_statements(true)` function. Since [ADR-0049](adr/0049-postgresql-statement-text-views-as-reads.md) the text query is a read of every role's statement texts ([above](#statement-text-views)), left out only by exact text under its own kind: with `pg_stat_statements`, in its own slot (below); with pgaudit, from the agent's identity with no signal and no other listed object, and only for records written while a `pg_stat_statements` stream of the target ran (its start and end, plus the statement timeout, less a 5 s clock-skew tolerance, kept in memory): after an agent restart, or outside such a period, the record is reported. Record times are the server's log clock and the period is the agent's clock: a server clock behind the agent's by more than 5 s widens the window after a stream stopped by the excess (residual; the offset is not measured), and one ahead of it makes the agent's last text queries of a period reported ([ADR-0049](adr/0049-postgresql-statement-text-views-as-reads.md#refinement-2026-10-11-verified-server-facts-and-implementation) refinement item 8, accepted). They form a closed allow-list (a unit test fails on any other connector statement that names no relation). Such a statement of the agent's account that passes the identity and signal rules above is never reported and is not charged to any row budget. It is recognized by its exact text: as sent with pgaudit (bound parameter values are not part of it), and, since #90, as `pg_stat_statements` stores it with `pg_stat_statements`. There an entry is the connector's own only when all of these hold: its stored text is exactly one of the connector's statements, with constants (booleans included) shown as `$n` and the connector's own bound parameters present (the same statement sent with literal constants has another `queryid` and another text, and is reported); its `userid` is the oid of the agent's role (read once per connection); it is a top-level entry (`toplevel`); its database is one where the connector runs that statement (the session and transaction statements in the declared databases, the text query only in the poller's database); and its `queryid` is the first one seen for that statement in that database (the pin is kept in memory for the life of the stream, and set again when a stream starts, after an agent restart included). Every other entry with the same text is reported: another role, a database the connector does not use for it, a nested execution, or another `queryid` (the stored text prepared by a client with every constant bound as a parameter). Anything else of the agent's account whose objects are unknown (`*`: any other function call, including `pg_catalog` functions that run SQL such as `query_to_xml`, text that does not parse, several statements) is **always reported and never budgeted**, so no traffic can use up a `*` budget. The same statements from any other role, or from the agent's account under another application or address, are reported against `*`.

Limits of these rules:
- Behind a connection pooler (PgBouncer…) every client has the pooler's address, and another process on the agent host shares the agent's address: there the address check only separates remote clients.
- Someone holding the agent's credentials on the agent host (or behind the same pooler), spoofing its `application_name` and reading at most the budget per object and day with filtered queries stays unreported. Writes, DDL and DCL with the agent's identity are always reported.
- Someone holding the agent's credentials who passes the identity checks can run the allow-listed table-less statements unreported. They read no row of any relation (`set_config` changes their own session only, `current_setting` reads settings the role may read, and the text query returns statement texts, as a read of the view `pg_stat_statements` does). With `pg_stat_statements`, where constants are not visible, the settings read by `current_setting(…)` are not checked: `queryid` ignores constant values, so a client holding the agent's credentials that sends the connector's statement shares the agent's entry, and is left out with it, whatever the constant values (setting names, the text query's length and `LIMIT`, whose rows are summed with the agent's own), within the 10 000-row `volume.large_result` signal per poll. A client holding the agent's credentials whose entry with an own text is the first one with a delta that the poller sees in the agent's own slot (its role, a declared database, top level) after a stream starts (within one poll, row order decides) gets that `queryid` pinned: the client's entry is then left out as the agent's own, and the agent's own executions of that statement are reported instead (loud), from its first execution in that slot. Only the allow-listed table-less statements (settings calls, the client-address call, the text query in the poller's database) can be hidden this way, and only by a holder of the agent's credentials. The rule depends on how PostgreSQL numbers the `$n` placeholders; if that numbering changes, the stored text no longer matches and the agent's own statements are reported (fails loud). The text query is recognized in pgaudit records written during a `pg_stat_statements` period only if the agent did not restart in between.
- The row counters are kept per target. Restarting a stream (a failure, a source switch, the agent's sessions terminated on purpose) does not reset them, and since #88 they are persisted across **agent restarts** (a periodic flush every 30 s saves charges not saved yet, even with no further activity, since #90, and a stream end saves them too), so a restart no longer gives a fresh budget per object. A crash or a kill loses at most about the last 30 s of charges (when a state directory is set).

The agent's database credentials never leave its host (I3).

### Known limits

- **Statistics catalogs** ([above](#statistics-catalogs)). With pgaudit and `pgaudit.log_catalog = off`, a read of the statistics catalogs alone gives no event. A read through a user view, a function or a procedure over a statistics relation is named by what the statement shows (the view, or `*` for a function; with pgaudit relation records, the relations a view reads are logged too), and with `pg_stat_statements.track = top` (the default) a function's body is not recorded at all. A read through a cursor or an explain is reported as its query since lot F ([Statements that wrap a query](#statements-that-wrap-a-query)). The event names the catalog, not the table the statistics describe. Selectivity estimates (`EXPLAIN` row estimates) answer value guesses from the same statistics without reading them. `pg_read_all_data` reads `pg_statistic` past row-level security: the remedy is in the grants ([05-security.md](05-security.md#recommended-database-accounts-read-only)).
- **Credential-bearing catalogs** ([above](#credential-bearing-catalogs)). With pgaudit and `pgaudit.log_catalog = off`, a read of a `pg_catalog` entry alone gives no event, and a user view over one is named by the view, under the filters. On `pg_stat_statements`, a user view, an SQL or PL/pgSQL function or a procedure over an entry is named by what the statement shows (the view, or `*`), and function bodies are not recorded with `track = top`. The no-secret shape lets every role read the other columns unreported: role names and attributes, which subscriptions and servers exist, which roles and databases have settings, large object ids. The session's own settings (`current_setting()`, `SHOW`, `pg_settings`: a database-level custom setting is readable by every role of that database; `primary_conninfo` by `pg_read_all_settings` members), FDW options at wrapper, table and column level, and function bodies (`pg_proc.prosrc`, where a hard-coded password would sit) are not listed ([05-security.md](05-security.md#recommended-database-accounts-read-only) gives the remedies). Up to 0.6.x none of these reads gave an event.
- **Statement-text views** ([above](#statement-text-views)). With pgaudit and `pgaudit.log_catalog = off`, a read of `pg_stat_activity` alone gives no event (verified), and a user view over it is named by itself only. A user view, an SQL or PL/pgSQL function or a procedure over a listed entry is named by what the statement shows unless pgaudit relation records name the entry; dynamic SQL (`EXECUTE`) is seen only in pgaudit's substatement records, and a `DO` block gives no event on `pg_stat_statements`. The no-text shape lets every role read the other columns of `pg_stat_activity` (user names, client addresses, application names, states, times) unreported. Own-session views behind a transaction-mode pooler (`pg_prepared_statements`, `pg_cursors`) are not listed. Extension-list names on user relations are over-reported. User functions, operators and casts next to catalogs only are reported since decision 8, with [their own residuals](#user-code-next-to-catalogs); a statement that names no relation at all is a read of `*`, as before.
- **Failed and cancelled statements.** Reported since 0.7.0 when the log settings are proven ([above](#failed-and-cancelled-statements)). **Up to 0.6.x**, at Full (pgaudit with `pgaudit.log_rows = on`), a read that ended in an error or a cancel, including one that already streamed rows to the client, was not reported, from any role (pgaudit writes no record for it); the workaround there is `pgaudit.log_rows = off` (Partial, no row counts). What remains: a failed read has no row count (the rows sent before the error are not known); `pg_stat_statements` (Limited) counts no failed statement; a backend that crashes during a read (out-of-memory killer, `SIGKILL`, a segmentation fault) writes nothing itself, and the postmaster's line, whose detail holds the query, is not read; any role can add false events with `RAISE … USING ERRCODE`; native code (C extensions, untrusted languages) that raises a `25P02` or `42601` without a context, after rows were sent through a statement that calls only built-in code, is refused; the per-role, per-database and per-function overrides of the log settings and the grants on them are read since 0.7.0 ([above](#failed-and-cancelled-statements)), but a superuser's session `SET` or startup option (`options=-c log_min_messages=fatal`) is not seen, an override or a function `SET` clause created between two probes (5 minutes at most) hides failures until the next probe unless the stream reads its record, and up to 0.6.x such overrides were not read at all (the target showed Full); and the agent merges a failed read with no row count into a successful read of the same principal and objects in the same window, whose row count then stands for both.
- **At-most-once delivery.** The log cursor advances once events are handed to the core, which aggregates them for up to `aggregation_window_s` before spooling. An agent crash within that window loses those events; they remain in the database's own log.
- **First start, rotation while stopped.** Without a cursor, reading starts at the end of the log (no history). If the log was rotated while the agent was stopped, the rest of the previous file is not read. A log truncated in place while the agent was stopped (`copytruncate`, `log_truncate_on_rotation`) is read from its start since #97 ([Truncation while the agent is stopped](#audit-log-files-and-failing-streams-every-engine)).
- **Forged records.** Any role can write `AUDIT: …` lines into the server log (`RAISE LOG` in PL/pgSQL). The connector drops records whose severity is not `pgaudit.log_level` or that carry an error context (pgaudit hides its context; `RAISE` always has one). Native code that hides its context (C extensions, untrusted languages) can still forge records. `log_error_verbosity = terse` does not remove the context from jsonlog nor csvlog (verified on PostgreSQL 16.13). A forged record can add false events; it cannot remove real ones, except that such native code could also write a record with no row count and the text of a statement that fails next in its own session, which is then reported from the forged record rather than from its `ERROR` line. Records dropped because of their severity (likely genuine, when the setting differs per database or role) are counted, logged, and noted in `check()` for 24 h, reported to the console as the target note `audit.records_dropped_severity` (#68, sent while the console lists `target_status.notes`).
- **Shadowing an unqualified catalog name.** When an unqualified `pg_*` name counts as a catalog (above), a role that can create a relation named `pg_*` in a schema of its search path (`CREATE TABLE public.pg_loot AS SELECT …`) and later reads it by its unqualified name is not reported for that later read; the copy itself reads the source relation and is reported. With pgaudit, `pgaudit.log_relation = on` (every relation named with its schema) closes this, and keeps the [statistics catalogs](#statistics-catalogs) visible with `pgaudit.log_catalog = on`; `log_catalog = off` is no longer advised for it, since it hides reads of the statistics catalogs alone. The same residual applies to a relation shadowing `pg_stat_statements` earlier in the search path.
- **Per-role pgaudit settings.** The level says what holds for the agent's session (see "pgaudit loaded" above), not that every role is audited alike.
- **Passwords in DCL text.** pgaudit writes `<REDACTED>` in place of the text after the `password` token of `CREATE ROLE` / `ALTER ROLE` (checked by the end-to-end test, #82). `pg_stat_statements` keeps the text of such statements, passwords in clear, and the agent's account (`pg_read_all_stats`) can read it: on that source, the agent's own redaction of DCL text is the only thing that keeps the password out of what the agent derives from the text (statement text itself never leaves the agent, but it is read into its memory). The end-to-end test has no positive control of that redaction yet (ROADMAP follow-up). Set role passwords with psql's `\password` ([05-security.md](05-security.md#recommended-database-accounts-read-only)), but note that `\password` sends `ALTER USER … PASSWORD 'SCRAM-SHA-256$…'`: `pg_stat_statements` then keeps the SCRAM verifier, open to an offline dictionary attack by anyone holding the agent's `pg_read_all_stats` credentials. Where `pg_stat_statements` is not the Audit source, set `pg_stat_statements.track_utility = off`.
- **Role statements on `pg_stat_statements`.** Since #88, `CREATE` / `ALTER` / `DROP` `ROLE` / `USER` / `GROUP` (and the other role and account statements) are classified `dcl` on every source, as pgaudit's `ROLE` class, so `dcl` policies see them on `pg_stat_statements` too.
- **Audit connections.** The `pg_stat_statements` stream holds one session; its 5-minute re-probe runs on that session (with several declared databases, the session is closed first and reopened after the probe). A pgaudit stream holds no session; its re-probe opens one per database, one at a time. Audit therefore holds one connection at a time (#88). The recommended `CONNECTION LIMIT` of [05-security.md](05-security.md#recommended-database-accounts-read-only) is kept as is and leaves one connection of margin.
- **Heuristic signals.** `shape.*` and `signature.*` are evadable by design; see [the classifiers README](../agent/crates/classifiers/README.md).

## MySQL / MariaDB Audit

What the MySQL / MariaDB connector does, as merged in P4-B (#64). Decisions in [ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md); the reference is [the connector README](../agent/crates/connector-mysql/README.md).

### Sources and level

`check()` and the Audit stream choose the source with the same probe and rule, re-evaluated every 5 minutes. In order of preference:

| Level | Condition | Source (`audit_source`) |
|-------|-----------|--------|
| **Partial** | The audit log declared in `agent.yaml` is readable by the agent, its plugin is active and logs statements in a supported format, **and** the stream has parsed a record of it in the last 24 h (**Limited** until then) | `mariadb_server_audit` or `mysql_audit_log` |
| **Partial** | `performance_schema` on, `events_statements_history_long` enabled together with the consumers it depends on (`events_statements_current`, `global_instrumentation`, `thread_instrumentation`), and readable by the account | `performance_schema` |
| **Limited** | With the same dependent consumers enabled, only `events_statements_history` or `events_statements_current` enabled and readable | `performance_schema` |
| **None** | The dependent consumers off, nothing readable, or `performance_schema` off | none |

**Full is never reported for MySQL / MariaDB.** Neither the MariaDB `server_audit` log nor the Percona `audit_log` plugin or `audit_log_filter` component logs the rows a statement returned; `performance_schema` has row counts but is a ring buffer (statements pushed out between two polls are lost), and the account, client host and `program_name` of a session are only readable while it is connected.

- **Audit log.** Declared per target as `mysql.audit_log` in `agent.yaml`, with an absolute `path` and a `format`: `server_audit` (MariaDB `server_audit`, with `server_audit_output_type = file` and `server_audit_events` including `QUERY` or `QUERY_DML`, and `TABLE`) or `json` (Percona `audit_log` with `audit_log_format = JSON` and `audit_log_policy = ALL` or `QUERIES`; Percona `audit_log_filter` with `audit_log_filter.format = JSON` and a filter logging the accounts to audit; MySQL Enterprise Audit JSON). The agent reads the file locally and incrementally, never through SQL. The XML and CSV `audit_log` formats and the syslog outputs are not supported: the configuration refuses them, and a server writing them is noted by `check()` and not used. The general log is never used as a source.
- **`performance_schema`.** Statement history from `events_statements_history_long`, otherwise `events_statements_history`, otherwise `events_statements_current`, polled at `poll_interval_s`; a wrap of the ring buffer between two polls is logged. MariaDB leaves `events_statements_current` off by default: enable it. The source needs `SELECT ON performance_schema.*` ([05-security.md](05-security.md#recommended-database-accounts-read-only)); the audit-log sources need no database grant.
- **No row counts on the file sources.** The console scores an event without `rows` 0 ([ADR-0021](adr/0021-access-event-correlation.md)): on those sources only signatures, shapes and object or principal conditions raise incidents, and `volume.large_result` is never set.

### Statement text and passwords

Statement text never leaves the agent (the `AccessEvent` contract has no field for it). In the JSON audit logs it is read as a raw value of the record and unescaped by the agent into a wiped buffer, never by the JSON library (whose buffers are not wiped). From `performance_schema`, the connector reads `DIGEST_TEXT` (literals already replaced by the server), and `SQL_TEXT` only for a statement without a digest, with a digest that may have been cut at its token storage (any digest of at least a third of the digest limit minus 263 bytes: 253 bytes at the default 1024), or of the agent's own sessions (the polling session's login user **and** client host, from `USER()`); when it reads an uncut `SQL_TEXT` and the digest is whole too, it analyzes **both** and the event takes the objects and signals of both (literals are replaced by the agent's normalizer), so that neither text can hide a table the other names; the agent's exact-text matches use `SQL_TEXT` only. **The agent relies on no server-side password mask**: measured on the dev images, MariaDB `performance_schema` `SQL_TEXT` keeps passwords in clear (`CREATE USER … IDENTIFIED BY`, `SET PASSWORD`, `GRANT … IDENTIFIED BY` and the other forms listed in the README), MySQL 8.4 `performance_schema` and the Percona logs write `<secret>`, and `server_audit` writes `*****`. DCL coverage of `server_audit` depends on its event set: with `QUERY_DML` (one of the recommended sets) it logs no DCL at all; with `QUERY_DCL` (as in the end-to-end test, MariaDB 11.4) it logs `CREATE USER` but **not `ALTER USER`**, so a password change by `ALTER USER` is not audited. Whether `QUERY` logs `ALTER USER` has not been tested. Every literal is replaced by the query normalizer whatever the statement, and a statement that does not lex (for example a password cut at the server's text limit) keeps no text and no names.

Because the session `sql_mode` of a logged statement is unknown, the normalizer reads ambiguous text under each possible mode (`NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES`, version comments). Text that is not UTF-8, or that has a byte >= 0x80 directly followed by `\` or a backtick (the trail byte of a two-byte character in gbk, big5, sjis, cp932 or gb18030), is not lexed; this last rule is not applied to `performance_schema` texts, which the server has already transcoded to UTF-8. **A text whose readings differ, or that does not lex, keeps only a statement kind, and is reported against `*` (fail closed)**:

- its kind is the most reportable of every reading (DCL, then DDL, then a write, then a read): `/*M! SELECT * FROM hr.customers */` (a read that MariaDB runs and MySQL skips) is a read of `*`, `SET /*M! GLOBAL */ server_audit_excl_users = …` is DDL;
- a reading that does not lex gives the kind of its code up to its first quote, comments skipped, under both readings of version comments; a `SET` (after `SET STATEMENT … FOR`) cut at that quote is DDL, because what it assigns cannot be told;
- such a text is reported whatever its kind, unlike a text that lexes to a statement that touches nothing (`SELECT 1`, `SET NAMES`), and with the agent's identity it is never left out as the agent's own.

Before the security review of #168, readings that differ kept no kind at all, and a text that kept no kind and had no table record produced no event, from any account.

**Cut texts (security fix, security review of #181).** A statement text the source cut (`server_audit_query_log_limit`, `performance_schema_max_sql_text_length`, or a `performance_schema` digest that filled `performance_schema_max_digest_length`) is **reported as a read of `*`** (with the objects its table records or, without records, its visible part name; a write of them and of `*` when its records write), always (never dropped by the `audit.configure` minimum rows), from every account, and **never left out as the agent's own**. What followed the cut cannot be told: padding (spaces, a `-- …` comment, repeated tokens such as `AND TABLE_NAME = TABLE_NAME`) pushed a `UNION ALL SELECT … FROM hr.customers` past the cut, and a visible part that read only `information_schema` (or `SELECT 1`) produced **no event before**, from any account, on `server_audit` with `QUERY` events only and on `performance_schema` (`SQL_TEXT`, and `DIGEST_TEXT` for token padding). **Table records do not change this (security review of #184, M1):** they name the tables the statement read, not a server file that a `LOAD_FILE` call past the cut read (`SELECT a,<1100 spaces>, LOAD_FILE('/var/lib/mysql/hr/customers.ibd') FROM hr.t` with a `READ hr.t` record produced no event from the agent's account before, and a plain read of `hr.t`, not always reported, from any other). A cut text is never the agent's own whatever its records: every statement the agent sends stays within 900 bytes, so it is cut only when the limits are lowered under 1024 (and then reported).

**Cut digests (security review of 914c9d2).** The server stops a digest when its token storage is full, at the smaller of `max_digest_length` (a startup variable) and `performance_schema_max_digest_length`; the agent reads both. A full digest has no `...` marker (measured on MySQL 8.4 and MariaDB 11.4), and the rendered text is not a measure of the storage: an identifier takes 4 bytes plus its name in the storage but its name plus 3 in the text, so one-letter identifier padding (`WHERE a IN (a,a,a,…)`) fills a 1024-byte storage with an 895-byte text, and with `max_digest_length = 300` a 275-byte one. The agent estimates the storage from the text (4 bytes plus the name per identifier, 2 per other token, 4 plus its length for a token holding `` ` `` or `@`), and takes a digest as possibly cut when the estimate is within one largest token (260 bytes) of the limit, or when the text is within 4 bytes of the limit or longer. A possibly cut digest is replaced by `SQL_TEXT` when that is not cut (the statement is then analyzed whole); when `SQL_TEXT` is cut too, or not available, the statement is a cut text, as above.

**Client character sets (security review of 09e93da, R1).** MySQL keeps `SQL_TEXT` and the digest's identifiers in the **client** character set, applies its limits to those bytes, and converts them to utf8mb4 only when the row is read. With `SET NAMES gb18030` (any account can), `Ā` takes 4 bytes stored and 2 read: measured on MySQL 8.4, a `SQL_TEXT` cut at 1024 stored bytes reads as 535 bytes, and `Ā` identifiers fill the digest storage with a 737-byte text. The agent therefore measures texts as stored in the worst case, 1 byte per ASCII character and 4 per other character (every allowed client character set is ASCII-compatible with at most 4 bytes per character), for `SQL_TEXT` and for the digest's identifiers, and takes a `SQL_TEXT` ending in `...` as cut (MySQL 8.4 appends it to a cut `SQL_TEXT` in every character set; MariaDB 11.4 too: measured with an sjis client and unmappable byte pairs in a `--` comment, its cut `SQL_TEXT` reads as 1021 bytes of utf8mb4 ending in `?@?...`, bytes `3F 40 3F 2E 2E 2E`, or `???...` for mapped pairs, while the whole digest names the table read after the cut, and the agent reports that read). **Noise:** a statement with many non-ASCII characters sent in utf8mb4 (2 or 3 bytes each) can be taken as cut while it is whole: with a whole digest, the digest is analyzed alone; otherwise it is reported as a read of `*`. A statement that really ends in `...` is taken as cut too. The same holds for a cut statement of a quiet kind (`SHOW … WHERE`, `SET`). A cut DDL or DCL text is reported as DDL / DCL, as before (a read hidden behind it is not added). A cut text with table records (`server_audit` `TABLE` events) is decided by its records, as before.

DDL and DCL events take no object names from the statement text; objects come from the log's table records when it has them (`server_audit` `TABLE`, `audit_log_filter` `table_access`), otherwise from the text for reads and writes. A failed statement is reported unless the server refused it before reading anything (syntax, unknown object and access errors), it sent no row, and the audit log has no table read record for it.

**System schemas and server configuration.** Objects in `information_schema`, `performance_schema` and `sys`, the internal statistics tables (`mysql.table_stats`, `column_stats`, `index_stats`, `innodb_table_stats`, `innodb_index_stats`) and `DUAL` are left out of the objects of **reads** only ([Known limits](#known-limits-1)), except the [statement-text tables](#statement-text-tables) and the [statistics tables](#statistics-tables), which reads name. Since #168, **writes to them are reported, from every account, the agent's included**:

- an `INSERT`, `UPDATE`, `DELETE` or `REPLACE` names every table its text or its table records name, system tables included: `UPDATE performance_schema.setup_consumers …` or `setup_instruments …`, which turn the `performance_schema` source off, is a `write` of `performance_schema.setup_consumers`; `INSERT INTO t SELECT … FROM performance_schema.events_statements_history_long` names both tables;
- a table record that writes or changes a system schema table names it whatever the statement's action (a `CALL` of a procedure that writes it is a `read` naming it);
- a MariaDB `SET STATEMENT … FOR <statement>` is analyzed as the statement after `FOR` (before, it produced no event on a source without table records, `performance_schema` and the plugin format of the `audit_log` JSON file, nor with `server_audit` `QUERY` records alone);
- nested `SET STATEMENT … FOR SET STATEMENT … FOR <statement>` is unwrapped up to 8 levels; a deeper nesting is DDL (fail closed);
- a text with several statements takes the action of its most reportable statement (`SET @a = 1; UPDATE performance_schema.setup_consumers …` is a write), and keeps the [signals](#signals) of its reads whatever that action: `SELECT * FROM hr.customers INTO OUTFILE '/tmp/x'; UPDATE shop.t …` is a `write` with `signature.into_outfile` and `shape.full_table_read` (the contract allows any registered signal on any action). **A policy whose `event_actions` is limited to `read` does not match such an event**: include `write` (or no action condition) in policies on these signals;
- `LOAD DATA` / `LOAD XML … INTO TABLE t` is a write of `t` (system tables included; without `LOCAL`, of `*` too, always reported: it reads a server file, below), `INSERT` / `REPLACE` without `INTO` name their table, and `RENAME TABLE` is DDL;
- a double-quoted name (`"hr"."customers"`, an identifier under `ANSI_QUOTES`, which any session can set without an event) in a name position (after `FROM`, `JOIN`, `STRAIGHT_JOIN`, `UPDATE`, `INTO`, `TABLE` or `HANDLER`, after a comma in a table list, followed per parenthesis level so that `FROM (SELECT 1) x, "t"` and `USE INDEX (i), "t"` count, alone between parentheses in a table list (`FROM ("t")`), next to a `.`, or right before `(`) is not resolved: the statement is reported against `*` (with the tables it names otherwise), always reported (below), and never left out as the agent's own. **Backstop:** any other read or write that holds a `"…"` token, a double-quoted string literal included (`WHERE a = "x"`, `VALUES ("x")`), also adds `*` and is never left out as the agent's own (the agent never sends `"`), but is not marked always reported, so `min_rows` still applies to it: **with double-quoted string literals, events add `*`**: operators should expect one extra, unmarked `*` object on the events of applications that use double-quoted strings, and `SELECT "x"` alone is reported as a read of `*`. Before the reviews of #168, `SELECT * FROM "hr"."customers"` produced no event on the sources without table records. The content of a `"…"` token is never kept, only whether it is an audit function name;
- a read inside a statement of no read kind is a read of its tables, never left out as the agent's own, and since the phase 8 follow-ups always reported with no row count ([Reads into variables](#reads-into-variables-and-create--as-select)): `SET @x = (SELECT GROUP_CONCAT(email) FROM hr.customers)` (then `SELECT @x`), `SET @x := …`, `DO (SELECT … FROM hr.customers)`; a subquery inside a function call names its tables too (`SELECT CONCAT((SELECT … FROM hr.customers))`), while `FROM` inside a call (`EXTRACT(YEAR FROM d)`) is not a table. Before the re-review of #168, these reads produced no event on the sources without table records, from any account;
- **statements of no known kind fail closed.** A statement that is not a read, a write, DDL or DCL (after the wrappers below) produces no event only when it is on a closed allow-list of statements that can neither read nor change data and hold no subquery: a session `SET` without a table, a schema-qualified function call, an audit function call or a `LOAD_FILE` call (`SET NAMES`, `SET CHARACTER SET`, `SET TRANSACTION`, `SET autocommit = 1`, `SET @x = NOW()`, Connector/J's `SET sql_mode = CONCAT(@@sql_mode, …)`; an unqualified call of a name that is not built in is a read of `*` there ([Unqualified function calls](#unqualified-function-calls))), `USE`, `BEGIN` / `BEGIN WORK` (not `BEGIN NOT ATOMIC`), `START TRANSACTION`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`, `SHOW` (except `SHOW [FULL] PROCESSLIST`, `SHOW ENGINE … STATUS` and `SHOW INNODB STATUS`, `SHOW EXPLAIN`, `SHOW ANALYZE`, `SHOW BINLOG EVENTS` and `SHOW RELAYLOG EVENTS`: [statement-text tables](#statement-text-tables)), the metadata forms of `EXPLAIN` / `DESCRIBE` / `DESC` (`DESCRIBE t [column | 'pattern']`, `DESC t`, `EXPLAIN t`: column definitions only) and the literal probe shape `EXPLAIN SELECT 1 FROM performance_schema.<table>` ([Explains of a statement](#explains-of-a-statement): any other `EXPLAIN` of a statement is a read), `LOCK` / `UNLOCK TABLES`, `FLUSH`, `ANALYZE` / `OPTIMIZE` / `CHECK` / `CHECKSUM` / `REPAIR [NO_WRITE_TO_BINLOG | LOCAL] TABLE`, `KILL`, `DEALLOCATE PREPARE`. `FLUSH TABLES … FOR EXPORT` is quiet: it reads no row through SQL, and copying the exported tablespace files needs file-system access on the server. ### One event per statement (audit log files)

The audit log files write a statement as several records: its table records (`server_audit` `TABLE` events, `audit_log_filter` `table_access`) and its statement record (`QUERY`). Since #93 the agent groups them per connection id and query id (without query ids, `audit_log_filter`: per connection and statement text), not by their position in the log, because concurrent sessions interleave their records (`READ a`, `READ b`, `QUERY a`, `QUERY b`). These rules refine [ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md), which stays Accepted:

- **When a statement is reported.** At its statement record; otherwise, without it, at the connection's next statement, at its disconnect (or a new connect with the same connection id), after 11 minutes (longer than the longest `statement_timeout_ms`, 10 minutes, so that an agent sample still running is not flushed without its statement record; security review of #188, N1), when it is evicted (the grouping state is full: the oldest first, logged and counted in the heartbeat metric `audit_pending_evicted_total`), and when the file stream ends gracefully (source change, unreadable log). A waiting statement is kept across polls and log rotations, so a statement split by the poll bound or a rotation is one event. **`server_audit` table records reported without their statement record** are a statement the event set does not log (a `SET`, DDL or `CALL` under `QUERY_DML`), a lost record, or one still running after 11 minutes: what its text would have shown (a function call, a server file) is unknown, so the event is a read or write of the tables **and of `*`**, always reported and never the agent's own, as a cut text is (security review of #188, M2). An agent statement evicted while pending (more than 1024 pending connections or 16 MiB) is reported the same way, as a read with the agent's credential: keep the audited servers within those bounds. With `QUERY_DML`, expect these for every non-DML statement that touches a table; an event set with `QUERY` (or `QUERY_DDL` and `QUERY_DCL` too) logs those statements and lowers this noise, and `server_audit_events` without any `QUERY` class leaves every statement in this case.
- **Kept across restarts.** The saved cursor is moved back to the first record of the oldest statement still waiting in the current file, with the end read so far and the waiting connections. After a restart, a crash, a stream restart or a reconfiguration, the stream re-reads from there and replays only the waiting statements' records, so they are neither lost nor counted twice. A replayed statement is timed from its log timestamp, not from the restart: its 11-minute timeout still runs out, so frequent agent restarts no longer pin the cursor to it. When the stream ends gracefully, the waiting statements are reported and the cursor is saved without them.
- **Bounds.** At most 1024 connections with a statement waiting, 64 distinct tables per statement and 16 MiB of waiting records in all (names of at most 1 KiB each, statement text, which only JSON `table_access` records carry, zeroized, and a fixed overhead per record).
- **Statements reported early.** A statement reported before its statement record is remembered for 22 minutes by its query id, with the tables already reported (at most 16 384 statements of 64 tables, kept as keyed 8-byte hashes, 8 MiB). A late table record of one of those tables is ignored; a late table record of another table starts a continuation of the statement, reported with the statement record or at the next flush. A late statement record alone yields a second event only when its text shows a signal (for example a whole-table read by a dump that ran longer than 11 minutes).
- **Stored procedures.** MariaDB 11.4 (checked on 11.4.13) gives each statement of a procedure its own query id, with its own table and statement records, and logs the `CALL` last with none: each statement is reported on its own, the `CALL` against `*`. The continuation rule above does not depend on it.
- **Residuals.** Statements waiting in a rotated (earlier) file are lost if the agent stops before their statement record: the old file is not re-read. The memory of statements reported early is not persisted and does not survive a new stream: after a restart, or after a graceful end of the stream, their late statement record is reported on its own, with the objects its text names. Without query ids (`audit_log_filter`), two consecutive statements of one connection with the same text, whose table records are not separated by the first one's statement record, are merged into one event: such repeats are undercounted.

`performance_schema` has one row per statement (deduplicated on thread and event id), so it needs no grouping.

Before #93, records were merged only when adjacent: the #92 load harness measured about 12 % of the statements of interleaved MariaDB sessions counted twice, and the end of a poll batch or a connect / disconnect record also split a statement.

### Signals

The signal ids are registered for `mysql` and `mariadb` in [`shared/protocol/signals.json`](../shared/protocol/signals.json).

| Signal | When it is set |
|--------|----------------|
| `signature.mysqldump` | A whole-table read by a client whose `program_name` is `mysqldump`, `mariadb-dump`, `mysqlpump` or `mydumper`, or carrying `SQL_NO_CACHE`, or in a session that took a consistent snapshot, a global read lock or `LOCK TABLES`, or of a table the session ran `SHOW CREATE TABLE` on (session state from successful statements only) |
| `signature.into_outfile` | `SELECT … INTO OUTFILE` / `INTO DUMPFILE`, also when the server refused it |
| `shape.full_table_read` | A read without top-level `WHERE`, aggregation or derived table, and with no limit or a limit above 10 000 rows |
| `volume.large_result` | More than 10 000 rows returned or affected by one statement (`performance_schema` only) |

`signature.mysqldump` is a heuristic and can be evaded. Known evasions: a plain `SELECT *` per table (no `SQL_NO_CACHE`, no dump `program_name`, no snapshot or lock); `mysqldump --skip-lock-tables` without `--single-transaction` (only `SQL_NO_CACHE` and the program name remain, which a modified client or another tool does not send); chunked reads (`mydumper` with a chunk size, `WHERE` ranges: no whole-table read); a statement padded past `server_audit_query_log_limit` or the `performance_schema` text limit (the cut text gives no shape). `server_audit` with `QUERY_DML` logs no `SHOW`, `FLUSH`, `LOCK` or `START TRANSACTION`, so only the `SQL_NO_CACHE` and program-name rules apply there, and `server_audit` has no `program_name`. On `performance_schema`, a session that ended before the poll (a short `mysqldump` run) is reported as an unidentified account.

### The agent's own account

As for PostgreSQL, an event of the agent's account is left out only when **all** of these hold:

- it is a read or a connection: **writes, DDL and DCL of the agent's account are always reported** (the agent never writes, I4, so such an event with its identity is someone else using it; #76, commit `35c6459`, [ADR-0027](adr/0027-mongodb-audit.md) decision 7). Since #168 this covers writes to system schema tables, and a statement whose text holds a write, DDL or DCL, or whose table records write or change a table other than an internal statistics table, is never left out, whatever the action of its event; nor is a `CALL`, an `EXECUTE` or `PREPARE`, a schema-qualified function call, an unqualified call of a name that is not built in, a call of a non-ASCII function name, a `LOAD_FILE` call, a server-side `LOAD DATA` / `LOAD XML`, an `EXPLAIN` past its 32-token bound, an [explain of a statement](#explains-of-a-statement) other than the literal probe shape, a cut text (whatever its table records), or a text that cannot be read (opaque, ambiguous or not lexable) unless the source's table records all read: the agent never sends these. **Noise:** on the file sources, a statement of the agent that names a table or column ending in a non-ASCII character (`` `café` ``) trips the multibyte rule and keeps no text; with `server_audit` `TABLE` events (or `audit_log_filter` `table_access` records) that all read, the records decide and the read is charged to the budget as usual, but without table records (`server_audit` with `QUERY` events only, the `audit_log` plugin's JSON) every Discovery sample of such a table is reported as a read of `*` by the agent's account;
- it comes from the agent's client address as the server sees it (`USER()`, read at each re-probe). Only an IP literal counts: a host name there, such as `localhost` for a Unix socket, leaves nothing out;
- it comes from the agent's `program_name` (`databastion-agent`) when the source shows one;
- it carries no signal;
- the agent's reads of each object stay within `limits.max_sample_rows` rows over a rolling 24 h. The audit-log sources have no row count, so each statement is charged the whole budget: a second read of a table within 24 h is reported. On `performance_schema`, each statement is charged its `ROWS_SENT`, and **at least one row** since the phase 8 follow-ups ([as for PostgreSQL](#the-agents-own-account)): a 0-row read with the agent's identity can show a value through a warning (`SELECT 1 FROM t WHERE id = 1 AND email = 0` gives warning 1292 with the `email` value), on success or before one of the failures the agent's own statements may have (3024, 1969, 1317, 1205), and such a walk is now reported once it passes the budget of statements per table and day (security review of #196, Low; checked against the dev servers by an integration test), when the console's `audit.configure` settings let a 0-row read through (the table in `sensitive_objects`, or no `min_rows`). Budget keys ignore case (`` `HR`.`Customers` `` and `hr.customers` share one budget, as they are one table with `lower_case_table_names` 1 or 2; security review of #197, M2). **Ended Discovery sessions (security review of #197, M3; phase 8 follow-ups):** on `performance_schema`, a Discovery session has usually ended when the next poll reads its statements, and a row of an ended session has no account (the poll reads its digest only). Before, its samples were reported as reads by an unidentified principal, whatever the budget. Now, while a target's stream polls `performance_schema`, each of its Discovery sessions **pins** its own thread at its start: it sets a session user variable to a random nonce (`SET @databastion_pin = '<32 hex digits>'`, quiet) and reads, in one statement, the `THREAD_ID` of `performance_schema.user_variables_by_thread` holding it **and** equal to its own thread (`threads` by `CONNECTION_ID()`: a nonce copied into another session never pins that session), with the server's identity (`@@hostname`, `@@port`, `@@server_id`, and `@@server_uuid` on MySQL) and its start time computed by the server (`UNIX_TIMESTAMP()` minus `Uptime` from `performance_schema.global_status`: the agent's clock plays no part). MariaDB has no `PS_CURRENT_THREAD_ID()`. The pin needs exactly one row. A row of an ended session whose thread is pinned is attributed to the agent's identity (the pinning target's account, the agent's address as the server sees it, its `program_name`) and takes the usual path: reads are **charged to the own-read budget** (left out within it, reported past it), and writes, DDL and DCL, statement-text and statistics reads stay always reported. Pins are kept in memory, per server run, for every stream of the agent on that server (a sibling target's too: with another account the reads are named with the pinning account and reported), and expire two poll intervals of the target's stream after the scan ends (30 s to 15 min). **Fail closed:** a thread id is matched only together with its server run, the identity and the start time within 2 s (a restarted server counts thread ids from 1 again); nothing is pinned on a server up for less than 10 s, nor when the nonce, the identity or the start time cannot be read; a session connected under another account is never attributed. Since the poll reads no `SQL_TEXT` of an ended session, a pinned session's digests are compared by their **shape** (tokens, with literals and user variables as placeholders; checked against the MySQL and MariaDB digests) with **two kinds of text only**: the pin statement (then its own `performance_schema` read, uncharged) and the target's live sampling credits (an extra batch consumes its credit, below). On a pinned session the poll and probe texts are not matched by shape; they are matched by shape only to drop the rows of the agent's own ended poll sessions ([Statement-text tables](#statement-text-tables), "Ended poll sessions"). This refines [ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) decision 4 (refinement of 2026-10-11, accepted). **Residuals:** pins and the poll sessions below are in memory only, so after an agent restart the statements of its earlier sessions that the persisted cursor reads again are still reported as unidentified (a few per restart); the per-thread tables of the Limited level drop a thread's statements when it ends, so a scan between two polls is not seen there at all; and a server misidentified as another (same host name, port, server id and, on MySQL, server UUID, started within 2 s, and a thread id in use by the agent there) would have that thread's statements attributed to the agent.

The agent keeps its own statements within 900 bytes as `server_audit` logs them **and** as `performance_schema` may store them (4 bytes per non-ASCII character, the measure of the cut rule; security review of cea63c5), so that they are never cut, nor taken as cut, at the default limits; this holds for names of 64 four-byte characters too: the fixed statements, the CAS store guard statements, the `SHOW GRANTS … USING` role statements (below), the catalog queries per table, and the Discovery samples, whose columns are split into batches (one sampling statement per batch; at most 850 bytes of digest text measured). On `performance_schema` their uncut `SQL_TEXT` is read and analyzed (agent's account, or a long digest), so a digest the estimate judges possibly cut never makes them reads of `*`.

**Sampling batches and the own budget (security review of 914c9d2, N3).** A table whose sampled columns do not fit one 900-byte statement is sampled in several batches. The first is charged to the budget as any read; before each further batch, the scan grants a **credit** to the target's Audit stream holding the batch's exact text and table. A statement record with that exact, uncut text, the agent's identity (account, address, application, no signal) and no table record other than a read of that table consumes the credit, once, and is left out without a charge. Credits are granted only while the target's Audit stream runs, kept in memory for two poll intervals plus the scan's statement timeout (at least 30 s, at most 15 min), at most 4096 per target (the oldest dropped first); an expired, dropped or already used credit leaves the statement to the usual budget, so one scan of a table is charged once, and a replayed or forged batch text is charged and, past the budget, reported. **Residual:** a credit is granted before its batch is sent; when the source does not log the statement (a failed connection, a statement the server refused before logging it), the credit stays live until it expires, and a replay of that exact batch text from the agent's identity (account, address, application) within that time is left out once, without a charge. It reads at most the batch's `LIMIT` rows of the columns the agent itself samples. Each batch may read a share of the table's 32 MiB byte budget in proportion to its columns (what earlier batches left is shared again), and at least one row while the budget lasts; a batch stopped on its share is killed and the next batches run on a new session. When some columns of a table got fewer rows than others, or none, the scan counts the table under `skipped_limit` (partial coverage) and logs `object partly covered`. **Role statements (security review of 914c9d2, Low).** On MySQL, `check()` reads the privileges of the account's roles with `SHOW GRANTS FOR CURRENT_USER() USING …` (at most 16 direct and mandatory roles, [05-security.md](05-security.md#recommended-database-accounts-read-only)). Since the phase 8 follow-ups the role list is split over several statements, each within 900 bytes by both measures, and `check()` takes the union of the privileges they show: MySQL combines the privileges of an account and of its roles as a union, partial revokes included (a restriction of one role is lifted where another source grants the privilege), and the agent ignores `REVOKE` lines (which over-reports, never under-reports), so the split changes no result; any statement that fails or has a line the agent does not understand leaves every role not evaluated (`privilege.roles_not_evaluated`). Before, with many long role names (16 direct roles of about 60 bytes as `'name'@'host'`) the single statement passed 1024 bytes and was cut, then reported at every heartbeat as a read of `*` by the agent's account on the sources that only have its text. Every agent statement is still cut, and reported, when the limits are lowered under 1024.

Not charged to the budget (same identity rules): the CAS store guard's catalog queries that `check()` sends at every heartbeat ([ADR-0041](adr/0041-cas-connector.md) decision 6), recognized only by their **whole, exact text**, in a record the source does not mark as cut, and with no table record outside `information_schema`. They are the table list (schema and table names from `information_schema.TABLES`), one column query per CAS store name key found in that list, and the column-shape query; each reads `information_schema` metadata and nothing else, every text is fixed by the target's configuration (never by the catalog), and each is kept at most 900 bytes as `server_audit` logs it, so that it is never cut at the default limits. **Keep `server_audit_query_log_limit` and `performance_schema_max_sql_text_length` at 1024 or more** (otherwise the agent logs a warning and, while the Audit stream reads that source, `check()` reports the target note `audit.statement_text_limit_low` with the limit as its count): a cut guard text is never matched, and a cut text with no table record is a read of `*`, so the agent's guard reads (and its other cut statements) are reported as reads of `*` at every heartbeat.

Not charged either (same identity rules, [ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) decision 4): the connector's own `performance_schema` statements, recognized the same way by their **whole, exact text**, uncut, with table records (if any) of the tables that text names only. They are the own-thread probe (`threads` with `global_status`, once per Audit session and after a server restart, with the server's identity and start time; when it fails, a `threads`-only probe of the thread id, and none of the agent's ended sessions is then recognized), the Discovery pin (`user_variables_by_thread`, `threads` and `global_status`, by the session's nonce, at the start of each Discovery session while the target's stream polls `performance_schema`; [above](#the-agents-own-account-1)), the consumer probe (`setup_consumers`), and the poll statements: one stats text per statement table and one poll text per table with or without the `program_name` subquery, 3 + 6 texts. The poll texts are **constant**: the end timer to read from is a session user variable, set by one `SET @databastion_from = …` on the same session right before each (a session `SET` is quiet: no event); the server computes the rest inside the text from its own state, so that whoever sets the variable chooses only where to read from (security review of #186, H1): the poll session's own thread (left out by `NOT t.PROCESSLIST_ID <=> CONNECTION_ID()` on the joined `threads` row; the stats texts find it by `CONNECTION_ID()`) and the `SQL_TEXT` threshold (`(GREATEST(LEAST(@@performance_schema_max_digest_length, @@max_digest_length), 263) - 263) DIV 3`, the agent's own rule, checked against it on each server by an integration test); the `LIMIT` is the constant 2000. Each text is at most 900 bytes by both measures above. They are never matched by prefix, digest or shape. The readability probes of `check()` and of the re-probe are `EXPLAIN SELECT 1 FROM performance_schema.events_statements_history_long` (and `_history`, `_current`): `EXPLAIN` needs the same `SELECT` privilege and reads no row there (no condition, so no const table, and a literal select list), and they have the literal probe shape of [ADR-0047](adr/0047-mysql-mariadb-explain-as-a-read.md), quiet for every account on every source, digests included ([Explains of a statement](#explains-of-a-statement)); a `SELECT` there would be seen by a `performance_schema` poll after the short heartbeat session ended, with no account and a digest only, and could not be told from anyone else's read. **Any other read of a [statement-text table](#statement-text-tables) with the agent's identity is reported, always, and never charged to the budget**: the agent sends no other statement to these tables, and a budget would let a stolen agent credential read up to `limits.max_sample_rows` statement texts per table and day unseen.

**Residual: replaying the poll.** Whoever holds the agent's credential, at the agent's address and with its `program_name`, can send the exact poll text (after their own `SET @databastion_from = 0`) and is left out like the agent: they read **what the poll reads**, the whole statement history from any point, without an event. That is the digests, and `SQL_TEXT` (with its literals, and on MariaDB clear-text passwords) of statements with no digest, a long digest, or of the agent's own sessions. **With the `statements_digest` consumer disabled, no statement has a digest and that is every statement's text**: `check()` says so in its detail and with the target note `audit.digest_consumer_disabled` (whenever `performance_schema` is on and its consumers are readable by the agent's account, whatever the Audit source); keep that consumer enabled. The same identity residual as for the budget above applies (an address behind a proxy, another process on the agent host).

Behind a proxy every client has the proxy's address, and another process on the agent host shares the agent's address. Someone holding the agent's credentials on the agent host, spoofing its `program_name` and reading at most the budget per table and day with filtered queries stays unreported. The uncharged guard rule adds nothing to that: a cut or longer text never matches (and a cut text with no table record is always reported), so the same person can only replay the exact guard statements, which read nothing but `information_schema.TABLES` names and `information_schema.COLUMNS` metadata. Writes, DDL and DCL with the agent's identity are always reported.

### Statement-text tables

Some system tables hold **the statement texts of other sessions with their literal values** (`WHERE email = 'alice@example.org'`; on MariaDB `performance_schema` `SQL_TEXT`, the clear-text passwords of `CREATE USER` / `SET PASSWORD`), or the values of locked index records. Since [ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) part (a) (accepted on 2026-10-09; since 0.6.0), a read of one of them is a **read event naming it**, from every account:

| `performance_schema.events_statements_current`, `_history`, `_history_long` | `SQL_TEXT` | yes | yes |

| `information_schema.PROCESSLIST` | `INFO` (and `INFO_BINARY` on MariaDB) | yes | yes |
| `information_schema.INNODB_TRX` | `trx_query` | yes | yes |

Confirmed on MySQL 8.0.46, 8.4.11 and 9.7.2, Percona Server 8.4.11, and MariaDB 10.11.19, 11.4.13 and 11.8.9 (default configuration) by a drift test of the engine matrix (`connector-mysql` `it::stmt_text_it`): it lists every `information_schema`, `performance_schema` and `sys` column named `SQL_TEXT`, `QUERY_SAMPLE_TEXT`, `INFO`, `INFO_BINARY`, `PROCESSLIST_INFO`, `trx_query`, `STATEMENT_TEXT`, `current_statement`, `last_statement`, `waiting_query`, `blocking_query` or `LOCK_DATA`, or ending in `_query` / `_statement`, and fails when its table is not on the list for that flavor. Two matches are not statement texts and are excepted: `information_schema.TRIGGERS.ACTION_STATEMENT` (trigger definitions) and `sys.[x$]statements_with_temp_tables.avg_tmp_tables_per_query` (a number). The drift test only sees the column names of its set: a table whose statement texts or values sit in a column named otherwise (`VARIABLE_VALUE`, `WORD`, `LAST_ERROR_MESSAGE`, `DATA`) is not caught by it, and is listed or documented by review. Not listed: tables holding digests only (`DIGEST_TEXT`, literals replaced by the server; `sys.statement_analysis` and the other `sys` statement views), the other summaries, the `setup_*` tables (whose writes are reported) and the dictionary views.

- **Named, as listed.** The tables are compared ASCII-case-insensitively on the resolved schema and name (an unqualified name is in the statement's current database), from the statement text or the table records, and the event names them as the server lists them (`information_schema.PROCESSLIST`, `performance_schema.threads`), so that a console policy or a per-principal baseline can scope them. The other objects of the statement are named as usual; other system tables are still left out of reads. Only `events_statements_summary_by_digest` depends on the flavor (from the server's version string): on MariaDB, where it holds digests only, a read of it stays quiet; with the flavor unknown it counts. Tables that one flavor lacks are listed for both, since a proxy can rewrite the version string. On a source that logs no current database (the `audit_log_filter` JSON general records, a `performance_schema` row with no current schema), an unqualified name equal to a listed table's name counts as one: always reported, never the agent's own, named as the source shows it.
- **Always reported.** These events are never dropped by the `audit.configure` `min_rows` filter (the file sources have no row count, and a monitoring poll may return few rows). No signal is added: `volume.large_result` keeps its meaning.
- **`SHOW [FULL] PROCESSLIST`** is a read of `information_schema.PROCESSLIST`, whatever the server reads it from.
- **Statements that show statement texts without naming a table** are reads of `*`, always reported, never the agent's own: `SHOW ENGINE INNODB STATUS` (its transaction and deadlock sections; any `SHOW ENGINE` except `PERFORMANCE_SCHEMA STATUS` and `… MUTEX`, and the older `SHOW INNODB STATUS`), and the plan of another connection's statement: MariaDB `SHOW EXPLAIN` / `SHOW ANALYZE [FORMAT=JSON] FOR id` and `EXPLAIN` / `DESCRIBE [FORMAT=…] FOR CONNECTION id` (verified on MariaDB 10.11.19, 11.4.13 and 11.8.9: the result carries the other session's whole statement text as a note, and the JSON plan its conditions with their literals), and MySQL `EXPLAIN … FOR CONNECTION` (MySQL 8.4.11: `FORMAT=TREE` shows the conditions with their literals); and the statements of the binary and relay logs, `SHOW BINLOG EVENTS` and `SHOW RELAYLOG EVENTS`.
- **`USE` with another statement in one text** (either order, a multi-statement packet): unqualified names may resolve in the database it sets rather than the one the source logs, so the text is a read of what it names and of `*`, always reported, never the agent's own. MariaDB 11.4 `server_audit` and Percona 8.4 `audit_log_filter` log each statement of such a packet as its own record (with the database current at it on `server_audit`; `audit_log_filter` logs no database, see above).
- **The agent's own account**: only its constant probe and poll texts are left out ([above](#the-agents-own-account-1)); any other read of these tables with its identity is reported.
- **Bounds fail closed.** The statement analysis keeps 16 table names per statement and 64 statements per text: a statement naming 16 tables or more, or a text with more statements, may hide a listed table past the bound, and is a read of what it names and of `*`, always reported, never the agent's own.
- **Monitoring tools.** PMM (Query Analytics, and `mysqld_exporter` with the `info_schema.processlist` collector), Datadog DBM, `sys`-based Grafana dashboards and MySQL Workbench performance reports read these tables on a schedule: their accounts show regular reads of the named tables (aggregated per principal, objects, action and window: at most a few thousand events per target and day for one monitoring account polling three tables). The per-principal baselines learn that pattern; a console policy can match these objects by name and exclude a known monitoring principal ([10-user-guide.md](10-user-guide.md#10-audit-enabling-it-and-reading-events) has a sample). There is no agent-side allow-list: monitoring credentials are often shared and hold exactly these grants.
- **Several targets on one server.** Each target's stream sees the polls of the others. With one agent account for the server they are its own constant texts, left out; with a different account per target, each stream reports the others' polls as reads of the statement tables by another account. Declare the targets of one server with one account. Do not exclude an agent account from a console policy to quiet this: the exclusion also hides the reads made with a stolen copy of that credential. Scope such an exclusion by object (the statement tables the poll reads), or use one account per server. **Ended poll sessions.** The rows of a poll session that has ended have no `threads` row, so the next poll sees them with no account and digest text only. Before, they were reported as reads of the statement tables by an unknown principal, for the other streams on the same server and for the same stream after each reconnection of its poll session (security review of #186, L1). Since the phase 8 follow-ups, each poll session reads its own thread id with the server's identity when it attaches (the own-thread probe) and the agent keeps it in memory per server run (identity and start time, as for the Discovery pins [above](#the-agents-own-account-1)): every stream of the agent on that server run drops the rows of that thread whose whole text (or digest) has the shape of one of the connector's own `performance_schema` probes and polls, unless the thread is connected under another account. Any other statement of that thread takes the usual path (security review of #205, L1), so that a server run mistaken for another hides nothing but such poll texts. After an agent restart the earlier sessions' threads are unknown: the few statements of the last polls that the persisted cursor reads again are still reported. **Two agents sharing one account on one server** (two hosts, or two agents on one host) do not know each other's sessions: each reports the other's ended poll and Discovery sessions as unidentified reads (the statement tables, the sampled tables). That is noise, not a hole; give each agent its own account.
- **Residuals.** A read through a user view, a stored function or a trigger over these tables is named by what the statement shows (the view, or `*` for a function call that is not built in, qualified or not, or a `CALL`). `mysql.general_log` and `mysql.slow_log` (`log_output = TABLE`) were already reported as reads of the `mysql` schema. Not listed: `information_schema.OPTIMIZER_TRACE` (the session's own trace only). Not listed, and **not reported** when read, although they can show statements or values: MySQL `performance_schema.error_log` (`DATA`: server error log messages, which can quote a statement or a value), and on replicas `performance_schema.replication_applier_status_by_worker` / `replication_applier_status_by_coordinator` (`LAST_ERROR_MESSAGE`) and `SHOW REPLICA STATUS` / `SHOW SLAVE STATUS` (`Last_Error`, `Last_SQL_Error`), whose replication errors quote the failing statement with its values. `mysqlbinlog --read-from-remote-server` reads the binary log over the replication protocol (`REPLICATION SLAVE` / `REPLICATION REPLICA`), not through a statement: no audit source shows it as a read; the connection is logged.

### Unqualified function calls

The servers resolve an unqualified name followed by `(` to a built-in function first, then to a loadable function (UDF, component function), then to a stored function **of the default database**. A name that is not built in may therefore run code whose reads no statement text names. Since [ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) part (b) (accepted on 2026-10-09; since 0.6.0), such a call is an **unknown call**: a read of `*`, always reported, never the agent's own.

- **Where.** In any statement and position: a select list, `WHERE`, `SET @x = f()`, `DO f()`, a `VALUES` list, a `CALL` argument, a `SHOW … WHERE`, inside an executable comment, after `SET STATEMENT … FOR`. Plain, backquoted, or as a `"…"` name (`ANSI_QUOTES`; both readings of the double quotes are checked, as for the other names). On `performance_schema` digests, `` `f` ( `` is a call and an unquoted `COUNT (` the keyword (a digest backquotes every identifier). A call followed by an alias is a call (`SELECT f() AS x`, `CAST(f() AS CHAR)`; security review of #188, H1). In a text that does not lex, an executable comment between the name and `(` is read both ways, as code and skipped (`f/*!99999 abs*/()` runs `f()` on an older server; L2). Not a call: a qualified name (`hr.f()`, already reported against `*`), a table before a column list (`INSERT INTO t (a)`, `REFERENCES t (id)`, `CREATE INDEX i ON t (a)`, `IF NOT EXISTS t (a INT)`), a common table expression's column list (`WITH x (a) AS (`, and `, y (b) AS (` in the same `WITH`), a name after `AS`, `)` or a literal (a derived table's column list, `OVER (`, `AGAINST (`, `COLUMNS (`), a type (`CAST(x AS DECIMAL(10, 2))`, after the first comma of `CONVERT(`, after `RETURNING` in parentheses, in `JSON_TABLE` `COLUMNS`), and `JSON_TABLE` where a table list starts.
- **The event.** `*` is added to the objects: a table-less statement becomes a read of `*` (in the default database when the source shows it, `*.*` otherwise), and a statement that names tables, or whose table records name them, keeps them plus `*`. The routine's name is never an object nor kept: event objects are tables in the contract, and a name from a statement is untrusted text. The event is never dropped by `min_rows` and never left out as the agent's own; a unit test checks that no statement the agent sends has an unknown call on any list.
- **Keyword functions with whitespace before `(`.** `NOW`, `COUNT`, `SUBSTR`, `CURDATE` and the other keyword functions of the parser's `sql_functions` set are built in only when `(` follows the name right away: with a space or a comment before `(` (and without `IGNORE_SPACE`), or backquoted, the server runs a stored function of that name in the default database. Checked on every engine-matrix image: a stored function `now()` is what `SELECT now ()` and ``SELECT `now`()`` run. The session's `sql_mode` is unknown to the agent, so these forms are unknown calls, with `IGNORE_SPACE` too (a false positive there).
- **Loadable functions** cannot take a listed name: every engine-matrix image refuses `CREATE FUNCTION <name> RETURNS … SONAME …` for each name on its list before opening any library (error 1585, or 1064 for a keyword), and a loadable function under another name is not built in, so it is reported.
- **What the sources show.** `performance_schema`: one event per calling statement, with its rows sent. MariaDB `server_audit`: the function's own table reads come as `TABLE` records of the calling statement, so the event names those tables and `*` (checked on 10.11.19, 11.4.13 and 11.8.9). With `server_audit_events = QUERY_DML` a `SET` statement is not logged as a query: `SET @x = f()` shows only as its `TABLE` records, a read of the tables and of `*`, always reported ([table records without their statement](#one-event-per-statement-audit-log-files)), and nothing at all when the function reads no table; `QUERY` logs it. Percona `audit_log_filter` JSON: every call, as a read of `*.*`.
- **The lists.** One list of built-in names per flavor and release series, generated by `agent/crates/connector-mysql/builtins/extract.py` from the server parser sources at a pinned tag (the native function registry, the parser's keyword functions, MariaDB's geometry functions and the functions of its plugins built in by default, `type_inet` and `type_uuid`), each name with the form the server accepts (native: plain, spaced or quoted; keyword: plain or spaced; keyword function: plain only). Names built in only under MariaDB `sql_mode=ORACLE` are not listed (fail closed: the session's `sql_mode` is unknown).

  | List | Source tags | Names |
  |---|---|---|
  | MySQL 8.0 | `mysql-8.0.11` and `mysql-8.0.46` (union) | 575 |
  | MySQL 8.4 | `mysql-8.4.11` | 579 |
  | MySQL 9.7 | `mysql-9.7.2` | 588 |
  | MariaDB 10.11 | `mariadb-10.11.19` | 582 |
  | MariaDB 11.4 | `mariadb-11.4.13` | 589 |
  | MariaDB 11.8 | `mariadb-11.8.9` | 597 |

  The connector picks the list from the flavor and version it reads at connect; Percona Server takes the MySQL list of its series. A series between two lists (MySQL 8.1 to 8.3 and 9.0 to 9.6, MariaDB 11.0 to 11.3 and 11.5 to 11.7) takes the names on both, each in the stricter form; a series newer than the newest list of its flavor takes that list, and the agent logs a warning once; an older series (end of life) takes the oldest list. The flavor and series come from the handshake and must match `VERSION()` read after TLS, or the session is refused (security review of #188, L1). Never a union of series: a stored function named after a function of a later series would hide behind it.
- **Drift test**, in the engine matrix on each image (`connector-mysql` `it::builtins_it`): every function name of `mysql.help_topic` (the function, operator and geometry help categories) is on the list or on a commented exception list, whose names must resolve to a stored function or not parse (help pages that are no call, MariaDB's geometry constructors, the Spider engine's functions, and names the help tables list but the server does not have: `MD5`, `SHA1` and `DISTANCE` on MySQL 9.7.2, `TRUNC` and `MBRCoveredBy` on MariaDB 10.11.19); and every listed name, called with no argument in an empty schema, is built in in each form its list accepts and resolves to a stored function in the forms it does not (the list is exact, so a server change fails the test). A new series gets its list in the PR that adds it to the engine matrix.
- **False positives, by design (fail closed).** Every call of a stored or loadable function is reported, one aggregated event per principal and window: applications that call stored functions in most statements get one more always-reported event per window, UDFs and component functions (`version_tokens_*`, `keyring_*`, the Spider functions) included; there is no allow-list ([ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) open question 7). Also reported: a built-in added by a server newer than its list; MariaDB's geometry constructors (`POINT(…)`, `LINESTRING(…)`, `POLYGON(…)`…, which MariaDB resolves to a stored function when the argument count is wrong, so they are not listed); keyword functions written with a space before `(` under `IGNORE_SPACE`; `JSON_TABLE(` outside a table list; and a name that is not a call in a position the analysis does not know.
- **Residuals.** The function's body is invisible on sources that do not log its statements: the event says that a function ran, and who ran it, not what it read. Within MySQL 8.0 only, a stored function named after a function added in a later 8.0 patch release, or removed in a later one, is taken as built in on the patch releases without it (the 8.0 list is the union of 8.0.11 and 8.0.46; open question 8). **On a series newer than the newest list** (MySQL 9.8 and later, MariaDB 12 and later until the agent gets their lists), a stored function named after a built-in that the newer server removed is taken as built in, so its calls are not reported: functions are removed upstream (`MD5`, `SHA` and `SHA1` are on the MySQL 8.4 list and not on the 9.7 one). The agent logs a warning for such a series; upgrade the agent when you upgrade the server (security review of #188, M1). In a DDL statement, a name in the table position of `CREATE … INDEX … ON t (` or `IF NOT EXISTS t (` is taken as a table, as for non-ASCII names ([above](#statement-text-and-passwords)); such a position holds no call in valid SQL. A trigger's or an event's body is not a call and is not covered.

### Explains of a statement

Since 0.7.0 ([ADR-0047](adr/0047-mysql-mariadb-explain-as-a-read.md); security review of #186, M2), **an `EXPLAIN` / `DESCRIBE` / `DESC` of a statement is a read of the relations that statement names**, on every source. The optimizer reads `const` tables (an equality on a primary or unique key, also through `ON` conditions, derived tables and common table expressions) and `system` tables (a one-row MyISAM table, with no condition) while it plans, and evaluates uncorrelated scalar subqueries. Verified on MySQL 8.0.46, 8.4.11 and 9.7.2, Percona Server 8.4.11-11 and MariaDB 10.11.19, 11.4.13 and 11.8.9: the values reach the client in the warning note (`SHOW WARNINGS`, Note 1003, with every column of the row: MySQL traditional and JSON formats, MariaDB `EXPLAIN EXTENDED`), in the JSON result itself (MySQL 9.x), in the conditions of other tables (TREE and JSON plans), or as a yes / no answer in the plan ("Impossible WHERE noticed after reading const tables", no warning needed). A loop of `EXPLAIN SELECT * FROM hr.customers WHERE id = n` reads a table row by row. An `EXPLAIN` never reads what the account could not read with `SELECT`.

- **What counts**: `EXPLAIN`, `DESCRIBE` or `DESC`, with no `ANALYZE` and no `FOR` before its statement (other than MySQL's `FOR SCHEMA | DATABASE name`, below; a word right after `@` or `@@` is a variable name, so `INTO @analyze` and `INTO @for` are not keywords), and its statement keyword (`SELECT`, `TABLE`, `WITH`, `VALUES`, `(`, `UPDATE`, `DELETE`, `INSERT`, `REPLACE`) within its first 32 tokens, whatever options come before it (`EXTENDED`, `PARTITIONS`, `FORMAT = TRADITIONAL | JSON | TREE`, `INTO @var`); also behind `SET STATEMENT … FOR`, and the same in `performance_schema` digests. With MySQL's `EXPLAIN FOR SCHEMA | DATABASE name <statement>`, unqualified relations are named in `name`, and the event adds `*` (what the server resolves is not proven) (`EXPLAIN SELECT * FROM hr . customers WHERE id = ?`; MariaDB digests `DESCRIBE SELECT` as `EXPLAIN SELECT`).
- **The event**: a `read` of every relation the explained statement names, explained writes included (`EXPLAIN UPDATE` / `DELETE` / `INSERT … SELECT` / `REPLACE` name their target too: the plan uses its index for the `WHERE`, and the account needs `SELECT` on the columns that `WHERE` reads), resolved and filtered as for a read: system tables other than the [statement-text tables](#statement-text-tables) and `DUAL` are dropped, and an explain left with no object (`EXPLAIN SELECT 1`) gives no event. With table records (`server_audit` `TABLE` events, `audit_log_filter` `table_access`), the objects are the records' tables and the relations of the text. **Always reported** (never dropped by `min_rows` or the sensitive-objects filter), with **no row count** on any source (a plan's `ROWS_SENT` counts plan rows, and the const reads that matter examine none), and no signal of the explained statement (it does not run: no `shape.full_table_read`, `signature.mysqldump`, `signature.into_outfile` or `volume.large_result`). Aggregation is unchanged: one event per principal, object set and window, whose `aggregated_count` is the number of explains merged, so a key walk shows as one event per window with a large count. **Never the agent's own**: the agent sends no explain but the probe shape below.
- **Quiet**: the metadata forms, which show column definitions and messages, not rows: `DESCRIBE t [column | 'pattern']`, `DESC t`, `EXPLAIN t` (and its digest `EXPLAIN hr . customers`, which is how both servers digest `DESCRIBE hr.customers`), `SHOW [FULL] COLUMNS` / `SHOW FIELDS`, `SHOW INDEX`, `SHOW CREATE TABLE`, `SHOW WARNINGS`. And **the literal probe shape**, from any account, on every source, including a digest-only `performance_schema` record with no account: a statement that is exactly `EXPLAIN | DESCRIBE | DESC`, `SELECT`, one integer literal (or the digest placeholder `?`), `FROM`, one **schema-qualified `performance_schema` table**, the schema written in lower case (`performance_schema.t`, `` `performance_schema`.`t` ``; `PERFORMANCE_SCHEMA.t` is a read naming that table), and an optional `;`. With no condition there is no const table and the select list is a literal: it shows no column value on any server above. The table must be in `performance_schema` (security review of #195, H1, decided by the maintainer on 2026-10-10): no account can create a view there, while `EXPLAIN SELECT 1 FROM v` on a view anywhere else plans the view's own `ON` / `WHERE` const reads (verified on MySQL 8.4.11 and MariaDB 11.4.13: the base table is planned `const`, and a view whose condition guesses a value gives "Impossible WHERE noticed after reading const tables"). The agent's readability probes (`EXPLAIN SELECT 1 FROM performance_schema.events_statements_history_long`, `_history`, `_current`) have this shape. Table records, when the source has them, must read only that table, or the statement is an explain of a statement. Anything more (a `WHERE`, a second table, a join, an alias, a column, `*`, a string or decimal literal, an option such as `FORMAT`, a subquery, a version comment that a server may run) and any other table, qualified or not, is an explain of a statement.
- **`EXPLAIN ANALYZE` / MariaDB `ANALYZE`** run their statement and are analyzed as it (action, objects, signals), and since the security review of #195 (M2) they are also always reported, with no row count: they show the same const values, and their row count is the plan's. **Unchanged**: `EXPLAIN … FOR CONNECTION`, `SHOW EXPLAIN` / `SHOW ANALYZE` and an explain with no statement keyword in its first 32 tokens are reads of `*`, always reported; the unqualified-call, `LOAD_FILE` and failed-statement rules apply as to any statement (an `EXPLAIN` refused before reading anything, error 1142 or 1143, gives no event; an `EXPLAIN` of a view without `SHOW VIEW`, error 1345, is reported). A text that cannot be read but starts with `EXPLAIN`, `DESCRIBE` or `DESC` (after whitespace, parentheses and comments, inside executable comments) and whose table records all read is handled as an explain: always reported, no row count, never the agent's own. `EXPLAIN (SELECT …)` reads as a call of `EXPLAIN` and adds `*`.
- **Noise**: events now come from accounts that run `EXPLAIN` on statements naming application tables: developers and DBAs (MySQL Workbench visual explain, phpMyAdmin, Adminer, DBeaver, on demand), ORM explain helpers and debug toolbars (Django `QuerySet.explain()`, Rails `explain`, Laravel Debugbar), and query analysers that explain sampled statements (PMM Query Analytics' Explain tab, `pt-query-digest --explain` / `pt-index-usage`: a burst). There is no agent-side allow-list: tools that explain real statements with their literals do read the rows those statements select. Scope the policies by object, or exclude the analyser's principal there.

### Reads into variables and `CREATE … AS SELECT`

Two phase 8 follow-ups (since 0.7.0), in the style of [ADR-0045](adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) and [ADR-0047](adr/0047-mysql-mariadb-explain-as-a-read.md) ("always reported"):

- **Reads into variables** (security review of #195, M2). A read whose values go into session variables rather than to the client sends at most one row: on `performance_schema` the `ROWS_SENT` of a `SELECT … INTO @v` is 1 (MySQL 8.4.11, MariaDB 11.4.13) and that of a `SET @v = (SELECT …)` or a `DO` is 0, and the file sources have no row count, so a `min_rows` setting dropped a key walk that keeps each value in a variable (`SELECT email INTO @v FROM hr.customers WHERE id = n`, then `SELECT @v`). These reads are **always reported and never left out as the agent's own**; a read that sent no row carries no row count, while one that sent rows (a `SELECT *, @x := 1 FROM t` dump, a text that adds a `SET` after its read) keeps them, and `volume.large_result` with them (the agent sends none; a unit test checks every statement it sends):
  - `SELECT … INTO @v` / `INTO @a, @b` (not `INTO OUTFILE` / `INTO DUMPFILE`, which keep `signature.into_outfile`), in the classic form `SELECT … INTO @v FROM t` and the trailing form `SELECT … FROM t WHERE … INTO @v` (MySQL 8.0.20+, MariaDB), with locking clauses, `UNION`, `TABLE t … INTO`, behind `SET STATEMENT … FOR`, and in `performance_schema` digests (`INTO @v`, `INTO ?`). The variables are never taken for relations;
  - `INTO` local variables (`DECLARE`d, without `@`): they only exist inside stored programs, whose `CALL` is already reported as code that runs out of sight; a statement of a stored program that a source logs on its own (`server_audit` logs them) is handled the same way;
  - an `@v := …` assignment in any expression of a read (`SELECT @v := email FROM t …`, `SELECT 1 FROM t WHERE id = n AND (@v := email) IS NULL`, which sends no row); a write with one keeps its affected rows but is always reported too;
  - a `SET` or `DO` that reads tables through a subquery: `SET @v = (SELECT email FROM t WHERE id = n)`, `SET @v := (…)`, `DO @v := (…)`, `DO (SELECT …)` (before, a read of its tables that `min_rows` could drop). `SET` and `DO` without a table or subquery stay as they were (`SET @v = 1` is quiet, `DO 1` a read of `*`). On `server_audit` with `QUERY_DML`, a `SET` is not logged as a query: its table records make it a read of its tables and of `*`, always reported (as before).
- **`CREATE … AS SELECT`** (security review of #186, L4). `CREATE [OR REPLACE] [TEMPORARY] TABLE x [IF NOT EXISTS] [(…)] [options] [IGNORE | REPLACE] [AS] <query>` (a `SELECT`, `TABLE t`, `VALUES`, `WITH …` or a parenthesized query; MariaDB's `CREATE OR REPLACE TABLE … SELECT`), `CREATE [OR REPLACE] [ALGORITHM = …] [DEFINER = …] [SQL SECURITY …] VIEW v [(columns)] AS <query>` and `ALTER … VIEW v … AS <query>` are **one `ddl` event naming the created table or view and the source relations of the query**, as the `write` event of an `INSERT … SELECT` names its target and its sources (`write ["shop.t", "performance_schema.events_statements_history_long"]`). The sources are filtered as a read's: system tables other than the [statement-text tables](#statement-text-tables) (named as listed) and `DUAL` are dropped, and the common table expressions of the query are not tables. With table records, the event names their tables and the text's. A call of code that runs out of sight, a cut text or a statement at the relation bound adds `*`. DDL events are never dropped by the `audit.configure` filter, and these are never the agent's own (the agent sends no DDL). These statements hold no program body, so their names are taken from the text: a refinement of [ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md) decision 7 (see its refinement note). `CREATE TABLE … LIKE`, a `CREATE TABLE` without a query and every other DDL statement keep no name from the text. A view's creation reads no row; it is named so that later reads through the view can be traced to its sources. On `server_audit` with `QUERY_DML` (the dev configuration), DDL is not logged as a query: `CREATE TABLE … AS SELECT` shows as its table records (`CREATE` of the copy, `READ` of the source), a read of both and of `*`, and `CREATE VIEW … AS SELECT` as the `READ` record of its source, a read of it and of `*`, both always reported (checked on MariaDB 11.4.13); add `QUERY_DDL` to `server_audit_events` to get the `ddl` event naming the view. A common table expression may be named `system` (`AS WITH system AS (…)`); only MariaDB's `WITH SYSTEM VERSIONING` option is not a query. A text whose readings differ (a version comment a server may skip, `CREATE /*!99999 TEMPORARY*/ TABLE … AS SELECT …`) keeps only its kind; when one of its readings is a `CREATE … AS <query>`, its `ddl` event names the relations that every reading names (never a name that only one reading has: it may be the content of a literal or a comment in another) and `*`. Likewise, a text whose explain word only a server may run (`/*!99999 EXPLAIN */ SELECT …`) keeps its row count, since a server that skips the comment runs the `SELECT`.
- **Failed reads that sent no row** (security review of #196, L3). A failed statement that is still reported (not refused before reading anything: [above](#statement-text-and-passwords)) and sent no row can carry the values it read in its error or warning text (`SELECT EXTRACTVALUE(1, CONCAT(0x7e, (SELECT email FROM t WHERE id = n)))` fails with error 1105 showing the value; JSON functions with 3141). Such a read, and a failed write holding a subquery, is always reported, and is never the agent's own unless its error is one of the ways the agent's own statements fail, which show no value: its statement timeout (`max_execution_time`, 3024; MariaDB `max_statement_time`, 1969), its server-side cancel (`KILL QUERY`, 1317) and its lock wait timeouts (1205). With 0 rows, it would otherwise be charged nothing and left out indefinitely. A failed write without a subquery (a duplicate key on a plain `INSERT`) stays under `min_rows`.
- **`SET STATEMENT` values** (MariaDB): the server refuses a subquery or a stored function in the assignments of `SET STATEMENT … FOR` (error 1970, checked on 11.4.13, `(SELECT 1 FROM t …)`, `1 + (SELECT …)`, `LENGTH((SELECT …))`, `f()` and `db.f()`), before reading anything, so they need no event; the statement after `FOR` is analyzed as usual.

### Statistics tables

Since 0.7.0 ([ADR-0048](adr/0048-statistics-catalogs-as-reads.md)), reads of the two statistics tables that hold column values are reported, from every account, the agent's included:

| Table | Values | Readable by |
|---|---|---|
| `information_schema.COLUMN_STATISTICS` (MySQL, Percona) | `HISTOGRAM`: every distinct value of a singleton histogram, the bucket bounds of an equi-height one (strings base64-encoded with their type, numbers in clear), after `ANALYZE TABLE … UPDATE HISTOGRAM` | any account with any privilege on the table, for every column of it |
| `mysql.column_stats` (MariaDB) | `min_value`, `max_value` in clear, and with `histogram_type = JSON_HB` (the default from 11.4) the raw bucket start values, after `ANALYZE TABLE … PERSISTENT FOR …` | `SELECT` on it (`mysql.*`, global `SELECT`) |

- **Named from the statement text** on every source (resolved in the current database when unqualified, compared ASCII-case-insensitively; both are listed for both flavors, since a proxy can rewrite the version string), including the `performance_schema` digests (`` `mysql` . `column_stats` ``). Every read counts, whole-row ones and those that name no value column included.
- **Table records are not enough.** MariaDB writes `READ,mysql,column_stats` (and `table_stats`, `index_stats`) `server_audit` records under the reader's account whenever the server loads a table's statistics (after `FLUSH TABLES`, or on any first open of an analyzed table): such a record is dropped, whatever the statement does, when it comes with the `table_stats` record of that load and a text that can be read whole. Otherwise it names `mysql.column_stats`, always reported and never the agent's own (security review of #199, H2): a text that cannot be read whole (opaque, versioned or ambiguous readings, cut), code out of sight (`CALL`, `EXECUTE`, a schema-qualified or unknown function call, double-quoted names), a `HANDLER … READ` (whose text names an alias), a record without the load's `table_stats` record, or a text naming a relation outside the server's schemas that has no table record of its own (a view: the server writes no record of a view, only of the tables it reads; security re-review of #199, N-H1). A record counts for a relation only when it names it exactly and the text writes that name in no other case (`server_audit` logs names as stored, and with `lower_case_table_names = 0`, the Linux default, `hr.V_stats` and `hr.v_stats` are two relations); with `lower_case_table_names = 1`, a text writing a table name in another case than stored therefore over-reports, a statistics load then naming `mysql.column_stats`, always reported. A text that creates or drops a temporary table counts no relation as recorded (a temporary table may hide a permanent one of the same name). A view the server materializes in a temporary table (`ALGORITHM=TEMPTABLE`) is no exception: MariaDB 10.11.19, 11.4.13 and 11.8.9 write no `server_audit` record under its own name either, only the `column_stats` record (checked by `it::statistics_it`, also joined with a table whose statistics the server loads), so its reads name it and `mysql.column_stats`, always reported (security review of #199, Low); a server that wrote one would make the view count as recorded, its `column_stats` record then dropped next to a statistics load's `table_stats` record, and the integration test fails then. In the last case the event names that relation too: a read of a view over `mysql.column_stats` names the view and `mysql.column_stats`, also when the view reads `table_stats` too, next to a `table_stats` subquery, or joined with a table whose statistics the server loads. Percona's `audit_log_filter` writes no `table_access` record for `information_schema` nor `performance_schema`: the text names the statistics and statement-text tables there, also next to the records of other tables (a join). Code out of sight adds `*` whatever its table records, on both file sources.
- **Always reported**, never dropped by `min_rows` or `sensitive_objects`, named first in the event (16 objects at most). No signal is added, and the statistics tables set no `shape.*` signal (a view over them may). Cut texts, table records without a statement record and code out of sight add `*`; an unreadable text whose table records all read is decided by its records, as before, but keeps its `mysql.column_stats` record (above).
- **Never the agent's own**: the connector names neither table in any statement (unit test over every connector statement, its `performance_schema` polls and probes included). Its own Discovery sampling after a statistics load gives `server_audit` records of `column_stats` that stay dropped, so it gives no new event.
- **Not listed**: `mysql.table_stats`, `index_stats`, `innodb_table_stats`, `innodb_index_stats` and `information_schema.STATISTICS` (counts and names only), and `mysql.column_statistics` (refused to every account, root included, error 3554). A drift test of the engine matrix fails when a relation of `information_schema`, `performance_schema`, `sys` or `mysql` with a column named `HISTOGRAM`, `min_value` or `max_value` is neither listed nor a commented exception (`performance_schema.variables_info` / `variables_metadata` and `sys.schema_auto_increment_columns` hold setting and type bounds).
- **Noise**: `mysqldump --column-statistics` (MySQL 8.0+) reads `COLUMN_STATISTICS` for each dumped table; `mariadb-dump --system=stats` reads `mysql.column_stats`; DBAs on demand. Aggregation bounds each principal to one event per object set, action and source and window.

### Known limits

- **Never Full; no row counts on the file sources** (above).
- **Statistics tables** ([above](#statistics-tables)). A read through a user view over a statistics table is named by the view on `performance_schema` and on `audit_log_filter`, and by the view and `mysql.column_stats` on `server_audit` (the view from the text, as the server writes no record of it; checked on MariaDB 10.11, 11.4 and 11.8). A read through a stored function or a procedure is `*`, plus `mysql.column_stats` on `server_audit`. The event names the statistics table, not the table it describes. On MySQL any privilege on a table shows the histograms of all its columns, including columns the account cannot `SELECT`: the remedy is in the grants and in which columns get histograms ([05-security.md](05-security.md#recommended-database-accounts-read-only)). Selectivity estimates (`EXPLAIN`'s `filtered`) answer value guesses from the same statistics without reading them.
- **Signal stripping on the audit log files.** A client can make its own statement keep only its kind by putting a non-ASCII character right before a backslash or a backtick (`` 1 AS `é` ``, `/* é\ */`), through the fail-closed multibyte rule. The event is still reported, against `*` (with the tables named by the log's table records where it has them), but without text-derived signals (`signature.*`, `shape.*`).
- **Dump heuristic evasions** (above).
- **Reads of the other system tables are not reported.** A read whose objects are all dictionary views, `setup_*` tables, digest summaries or other tables of `information_schema`, `performance_schema` or `sys` outside the [statement-text tables](#statement-text-tables) and the [statistics tables](#statistics-tables) (or the other internal statistics tables, or `DUAL`) produces no access event; writes to them are reported ([System schemas and server configuration](#statement-text-and-passwords)). Reads of the statement-text tables are reported since ADR-0045 part (a).
- **At-most-once delivery**, as for PostgreSQL: an agent crash within the aggregation window loses the events the cursor has already passed.
- **Unqualified calls: false positives and residuals** ([Unqualified function calls](#unqualified-function-calls)). Every call of a stored or loadable function is reported as a read of `*`, built-ins added by a server newer than its list and MariaDB's geometry constructors too; on `server_audit` with `QUERY_DML`, every non-DML statement with table records is a read or write of its tables and of `*`; the function's body is not named; MySQL 8.0 takes the union of its patch releases; on a server series newer than the agent's lists, a stored function named after a removed built-in is not reported (upgrade the agent).
- **Cut texts are reads of `*`** ([above](#statement-text-and-passwords)): with or without table records, a long statement of any account (and of the agent's, see the noise above) is an always-reported read of `*` with no text-derived signal.
- **Explains name relations, not rows** ([Explains of a statement](#explains-of-a-statement)). An explain event names the relations its statement names, not how many rows the optimizer read (one per const table and statement, or a whole subquery's input): `volume.*` signals and console volume policies never fire on it. A source that does not log the statement (a `server_audit` event list without `QUERY` / `QUERY_DML` and `TABLE`, an `audit_log_filter` filter that excludes the account, the `performance_schema` history overrun between two polls) misses it, as for any read. The literal probe shape tells whether a `performance_schema` table holds exactly one row. `SELECT … INTO @var` is always reported since the phase 8 follow-ups ([Reads into variables](#reads-into-variables-and-create--as-select)).
- **`CREATE … AS SELECT` names, it does not count** ([above](#reads-into-variables-and-create--as-select)). The `ddl` event names the sources of the query, not the rows copied; a read through a view later is named by the view.
- **A cut DDL or DCL text does not name the read it hides.** A `CREATE TABLE … AS SELECT` or `CREATE VIEW … AS SELECT` cut before its query starts (padding in its column definitions or options), or any other DDL or DCL, is reported as DDL without objects (always reported); cut after its query starts, it names what its visible part names and `*`. An `INSERT … SELECT` padded past the cut is a write of `*`.
- **Reads into variables that send no row carry no row count** ([above](#reads-into-variables-and-create--as-select)): a key walk shows as one always-reported event per principal, object set and window, whose `aggregated_count` is the number of statements; `volume.*` signals never fire on it. A failed read that sent no row is marked (below), but two cases of a value shown through a message are not, and `min_rows` applies to them: a warning on a statement that succeeds (a failed conversion of a column value, warning 1292, read with `SHOW WARNINGS`), and a failed read that sent rows before its error (its row count stands).
- **Session `SET`s with a cut text are DDL.** A `SET` whose text does not lex (a non-ASCII character before a backslash in a literal, on the file sources) is reported as DDL, since it may set a global variable.
- **Grouping residuals** ([One event per statement](#one-event-per-statement-audit-log-files)): waiting statements in an already-rotated file are lost when the agent stops; a late statement record after a restart or a graceful end of the stream is counted alone; repeats of one statement text without query ids (`audit_log_filter`) are undercounted.
- **Cursors and counters after a restart.** Since #88 the `performance_schema` cursor (end timers and ids of the statements read, with the server's start time) and the own-account row counters are persisted: an agent restart resumes after the last statement read when the server did not restart. What `events_statements_history_long` no longer holds (it wrapped while the agent was stopped) is lost and counted, and a statement of a session that ended while the agent was stopped is reported as an unidentified account. Without a cursor, a log file is read from its end; a log rotated while the agent was stopped is read from the start of the new file. A log truncated in place while the agent was stopped is read from its start since #97, held statements included ([Truncation while the agent is stopped](#audit-log-files-and-failing-streams-every-engine)).
- **A file source is Limited until a record is parsed**: after the log is configured, after an agent restart (the time of the last record is not persisted), and when nothing was written to the log for 24 h.
- **`server_audit` times are local**, converted with the server's time-zone offset read at each re-probe; a DST change in between shifts times until the next re-probe.
- **Forged and dropped records.** The audit logs are written by the server only; a client cannot put a newline in a record, so it cannot add records. A damaged record is dropped and the following ones are kept; dropped records are counted by `check()` for 24 h, logged by the agent and reported to the console as the target note `audit.records_dropped` (#68, sent while the console lists `target_status.notes`).
- **The audit-log file ACL is the operator's job** ([05-security.md](05-security.md#recommended-database-accounts-read-only)).
- **Failed-login flood.** A client that can reach the database port, even without valid credentials, can try many made-up user names. Each name becomes its own `auth_failure` event group: the aggregation key includes the account name, and `auth_failure` always passes the `audit.configure` filter. The agent flushes every 10 000 groups and keeps spooling while the console answers `429`. The console accepts at most 60 batches of 500 events per minute per agent and applies back-pressure at 20 000 pending events. The effects are:
  - the batches of a later dump queue behind the flood, so its incident is delayed;
  - once the spool is full, the oldest batches, findings included, are evicted;
  - the console can store about 30 000 rows per minute per agent, kept for the event retention.
  The flood shows in the spool's dropped counters and the console's back-pressure metric. When the agent drops batches, the console raises an `agent.batches_dropped` alert to the `system_alerts` channels, at most once per agent and hour (#75, [05-security.md](05-security.md#alerting)); the dropped events are still lost. This is a residual of the Audit design ([ADR-0023](adr/0023-mysql-mariadb-audit-sources-and-levels.md)), recorded in [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md).
  Since #88 the agent caps it: at most 100 named `auth_failure` groups per target and window, a folded table of at most 256 principals beyond them (ties evict the most recently added entry), then overflow events per client address (at most 16, then one without address) carrying the attempt count, so at most 117 `auth_failure` events per window and every attempt counted (`auth_failures_overflowed_total` counts the failed logins beyond the 100 named groups). The spool evicts by priority (each class, findings or events, can grow to 3/4 of the bounds, so the other always keeps at least 1/4; `signature.*` batches dropped last), so a later dump's signature batches are kept, though they still queue behind earlier batches; an events flood can still evict findings down to their quarter. The cap is in the engine-agnostic agent core and applies to the `auth_failure` events of every engine. The remaining known limit (junk names kept above root's count) is described in [agent/README.md, "Failed-login flood"](../agent/README.md#failed-login-flood).
- **Audit uses its own connections.** A `performance_schema` stream holds a session on the agent's account. Since #88 it re-probes its prerequisites every 5 minutes **on that session** and closes a stale session before opening its replacement, so it holds one connection at a time; a file-source stream opens a session for its re-probe and closes it. The `KILL QUERY` connection that cancels a guarded Audit statement takes the same slot as the re-probe and the reconnect ([ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) decision 11), so the sizing is unchanged: size `MAX_USER_CONNECTIONS` as in [05-security.md](05-security.md#recommended-database-accounts-read-only): 6 with `performance_schema`, 5 with an audit log file, plus one per additional Audit target on the account ([ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) decision 11). A connection refused at the limit fails the check or scan that needed it. For an Audit stream, the stream restarts after a backoff, counted in `audit_stream_failures_total`, and it can miss what ran in between.
- **Role privileges only partly visible on MariaDB.** `check()` evaluates the privileges held through roles, including a `performance_schema` grant held through a role, with the rules for direct grants (#70, [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md)). MySQL (8.0.19+) shows every applicable role; when `APPLICABLE_ROLES` cannot be read (older MySQL, or an error), the roles are counted from the account's own `SHOW GRANTS` role lines and `mandatory_roles`, all as not evaluated, or the privileges are reported as `privilege.not_evaluated` when those cannot be read either (fail closed, #83). MariaDB shows a least-privilege account the grants of its current (default) role only: every other role is reported as `privilege.roles_not_evaluated`. Since #88 the grants to `PUBLIC` (MariaDB 10.11+) are read (`SHOW GRANTS FOR PUBLIC`) and evaluated like direct grants; unreadable or role-granting `PUBLIC` counts as a role not evaluated. This narrows the ADR-0025 residual that `PUBLIC` grants are not read.
- **Level of a target whose check timed out.** Targets that share an account take turns within the heartbeat's 10 s deadline. A target whose `check()` did not finish in time, or waited for its turn behind a slow check of the same account, is reported unreachable (`timeout`, `check.timed_out`) with level None for that heartbeat. This does not mean its Audit stream stopped. Since #88 a timed-out check takes the last turn of its account at the next heartbeats, so it no longer uses up the deadline of the others every time, and the two cases are counted apart in the heartbeat metrics `checks_timed_out_total` and `checks_account_busy_total` (the contract has no other status).
- **Heuristic signals.** `shape.*` and `signature.*` are evadable by design; see [the classifiers README](../agent/crates/classifiers/README.md).

## MongoDB Discovery

What the MongoDB connector does, as merged in P5-A (#74, [ADR-0026](adr/0026-mongodb-connector.md)). The reference is [the connector README](../agent/crates/connector-mongodb/README.md); the account is in [05-security.md](05-security.md#recommended-database-accounts-read-only).

### Scope
- **One declared host**: a standalone, one replica-set member or a `mongos`, reached directly. The other replica-set members are never contacted and `mongodb+srv` is not supported: to scan a replica set, declare the member to read from (a secondary spares the primary). Reads carry `secondaryPreferred`. MongoDB 5.0 or later; SCRAM-SHA-256 accounts only.
- **Databases and collections** the account holds privileges on (`authorizedDatabases`, `authorizedCollections`), at most 1024 databases and 4096 collections per database, filtered by the job's filters. `admin`, `local`, `config`, `system.*` and queryable-encryption state collections (`enxcol_.*`) are never read. Collections the account cannot see are not listed, so they cannot be reported as not covered.
- **Views are not sampled** (their pipeline could read other collections or run JavaScript): counted as `skipped_unsupported`, with the note `coverage.views_not_sampled`. Data reachable only through a view is not covered.
- **Time-series collections** are read through their view with `find` and a limit, without a size estimate. If the server refuses the read to the account, the collection is counted as `skipped_not_readable` and `check()` reports `coverage.timeseries_not_readable` with the count observed in the last scan; the fallback grant is in [05-security.md](05-security.md#recommended-database-accounts-read-only). Reading through the unpacking view costs more than reading a plain collection.

### Sampling
- The size estimate is a `count` without a filter (collection metadata), reported as the object's estimated rows; on a sharded cluster it may include orphaned documents.
- Above 20 times `sample_rows` documents (and above 100), `$sample` picks `sample_rows` documents at random (random cursor, no collection scan). Otherwise the first `sample_rows` documents in natural (storage) order are read.
- One reply per collection, at most 16 MiB + 64 KiB: a batch cut by the server gives a smaller sample, never a second read.
- Per document: at most 20 levels of nesting, the first 16 elements of each array, 512 values. Per collection: at most 1024 distinct field paths and `sample_rows` values per path; values cut to 4096 bytes.
- Values classified: strings; `int32` / `int64` as digits; integral doubles below 2^53; finite `Decimal128`; dates as `YYYY-MM-DD`; generic and user-defined binaries only when they are UTF-8 text. Never read: UUID, encrypted, compressed, sensitive and vector binaries, ObjectIds, booleans, JavaScript code, timestamps, non-integral doubles.

### Field paths
A finding's location is the database, the collection (`object`) and a normalized field path (`field`); there is no schema. `_id` is a field like any other.

- An embedded document adds a key; an array adds `[]` (`orders[].items[].sku`, arrays of arrays included).
- Keys that are digits only, contain a dot, or look like values (e-mail addresses, phone or card numbers, UUIDs…) become `*`: `contacts.*.phone`.
- Object levels that the sample shows to be maps keyed by data (more than 16 distinct keys across the sampled documents, or at least 3 keys each seen in one document only, across at least 2 documents) have their keys replaced by `*`: `acl.*.role`. The collection's top-level fields are never collapsed.
- The values of every raw path with the same normalized path are pooled before classification.
- Limits of the key rule: a small map whose keys recur across the sampled documents (at most 16), a map with fewer than 3 keys, or a sample of one document can leave data-derived keys in the path when they do not look like values; conversely, a sub-document with more than 16 fields, or with optional fields each present in one sampled document, is reported as `parent.*`.

## MongoDB Audit

What the MongoDB connector does for Audit, as merged in P5-B / P5-C (#76). Decisions in [ADR-0027](adr/0027-mongodb-audit.md); the reference is [the connector README](../agent/crates/connector-mongodb/README.md#audit).

### Sources and level

`check()` and the Audit stream choose one source per target with the same rule, re-evaluated every 5 minutes. In order of preference:

| Level | Condition | Source (`audit_source`) |
|-------|-----------|--------|
| **Partial** | The `auditLog` JSON file declared in `agent.yaml` (`format: audit_log`) is readable by the agent, `buildInfo` reports MongoDB Enterprise or Percona Server for MongoDB, **and** the stream has parsed a successful `authCheck` record in the last 24 h | `mongodb_audit_log` |
| **Limited** | The same `auditLog`, and the stream has parsed a valid record of it in the last 24 h, but no successful `authCheck` (note `audit.authcheck_success_pending`); **None** until any record is parsed (notes `audit.limited_pending_first_record` and `audit.authcheck_success_pending`; the file is still read meanwhile) | `mongodb_audit_log` |
| **Limited** | The structured JSON server log declared in `agent.yaml` (`format: server_log`) is readable by the agent, on any edition, **and** the stream has parsed a record of it in the last 24 h (**None** until then) | `mongodb_log` |
| **Limited** | No usable file; the target is not a `mongos`; the account holds `find` on `system.profile` of at least one database, **and** the stream has read a profiler entry in the last 24 h (**None** until then) | `mongodb_profiler` |
| **None** | None of the above (note `audit.source_not_configured`; `audit.log_not_readable` when a declared file cannot be read) | none |

**Full is never reported for MongoDB.** The `auditLog` logs every authorized command (with `auditAuthorizationSuccess`) but no document count (note `audit.log_without_row_counts`); the server log and the profiler have counts, but only for the operations the server records (slower than `slowms`, sampled by `slowOpSampleRate`; the profiler is a capped collection that overwrites itself), with the note `audit.slow_operations_only`. The agent cannot read `slowms`, `slowOpSampleRate`, the profiling level or `auditAuthorizationSuccess` without cluster privileges, so a level is proven from records read, never predicted from settings: an `auditLog`, a server log or a profiler that recorded nothing in the last 24 h reports **None** with the note `audit.limited_pending_first_record` (the source is still read meanwhile; [ADR-0030](adr/0030-mongodb-auditlog-freshness.md) for the `auditLog`, since #83). Any valid `auditLog` record counts, the agent's own `authenticate` at each check included, so a written file reaches Limited within one poll of the first check; a stale file falls to None within 24 h of its last record. The proof is in memory: after an agent restart the level is None until the next record is parsed.

- **`auditLog`.** `auditLog.destination: file`, `format: JSON`, the `mongo` schema. The BSON format, the OCSF schema and the `syslog` / `console` destinations are not supported: their records do not parse and are counted as dropped (`audit.records_dropped`). An `auditLog` declared on a Community server is not used (`audit.auditlog_on_community`). An `auditLog.filter` that leaves reads out cannot be detected, and `auditAuthorizationSuccess` turned off is only noticed after 24 h without a successful `authCheck`. Since #90 this source is tested in CI against a real Percona Server for MongoDB 8.0 (the opt-in dev service `psmdb`: JSON `auditLog` file, `auditAuthorizationSuccess`): a read and a failed authentication are reported, the level reaches Partial, the agent's own Discovery reads are left out, and no ground-truth value appears in the events or logs. MongoDB Enterprise is tested with recorded samples only. Whether PSMDB audits the client metadata that carries the dump tools' application name (`signature.mongodump`) is not asserted yet.
- **Server log.** `systemLog.destination: file` (JSON, MongoDB 4.4 and later). Operations come from the slow-query lines; a slow-query line has no user, so the connector follows connections by `ctx` (accept, client metadata and authentication lines, at most 4096). An operation on a connection that authenticated before the agent started reading the log is reported as an unidentified account.
- **Profiler.** Per database and poll, one bounded `find` on `system.profile` (`ts` filter, fixed server-side projection, `limit: 1000`, `singleBatch`, `maxTimeMS`), at most 64 databases per poll, never `admin`, `local` or `config`. Since #88 the position is persisted per database (a time and hashes of the entries read at it); a database without a saved position starts at its newest entry. An entry whose `command` the server truncated (`{$truncated: …}`) or that is not a document has an **unknown shape** (no whole-read signal from a filter that was cut off); when its command name was lost too, it is reported as a write if it wrote documents, else as a read if it returned documents, never dropped. An entry that does not parse is skipped and counted as dropped (`audit.records_dropped`); it never fails the whole poll (#83, [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 7). Profiling itself is set by the operator; level 2 is costly ([below](#cost-for-the-monitored-database)).
- **One node.** The log and the profiler are per node, and the connector never follows the replica-set topology: only the declared node's activity is seen.

### What is kept

Closed-shape facts only (I2, [ADR-0007](adr/0007-mask-access-events.md)): the time, the command name (compared with a closed list), the normalized namespace, the user (`name@authdb`), the client IP (port dropped), the application name, the document counts, the kind of a failure (from its numeric error code only), whether the filter has keys (a count, never a key or a value), a numeric `limit`, the aggregation stage operators compared with a closed list, and whether the command runs server-side JavaScript (key names compared with three names, [below](#what-is-kept)). Command documents (`param.args`, `command`, `originatingCommand`), `errMsg`, `planSummary` and every other field hold other users' literals: they are skipped without being copied in the files, and never fetched from the profiler (the facts are computed by the server's projection). A failed operation keeps its count when it returned documents first; how failures are reported is described below.

**Failed operations without documents** (since 0.7.0; security review of #197, L1; phase 8 follow-ups, mirroring the MySQL / MariaDB [failed reads that sent no row](#reads-into-variables-and-create--as-select)). An error text can show the values an operation read: `{$toInt: "$email"}` fails with `ConversionFailure` (241), "Failed to parse number '<the address>' in $convert", and so do other expression errors, a JavaScript `throw` in `$where` or `$function` (139), a duplicate key built from a stored value (11000) and many location-coded errors; such a read returns no document, so before this change it gave no event at all, for any account. On the **profiler and the server log**, a failed operation (`errCode` other than 0, or `ok: 0`) is now classified by its numeric code only (`errMsg` and `errName` are never read nor projected; refinement of [ADR-0027](adr/0027-mongodb-audit.md#refinement-2026-10-11-accepted-207), pending the maintainer's acceptance):

| Kind | Codes | Event |
|---|---|---|
| Refused before reading anything | `Unauthorized` (13), `NamespaceNotFound` (26, its text names only the namespace the client sent), `CommandNotFound` (59), the command parser's unknown or missing field (40414, 40415) | none when no document was returned |
| Quiet: the text names no value read | time limits (`MaxTimeMSExpired` 50, `ExceededTimeLimit` 262, `LockTimeout` 24; not the network time limits 89 and 202, whose text can embed the remote command on sharded paths), interruptions (`Interrupted` 11601, 11600, 11602, `ClientDisconnect` 279, `ShutdownInProgress` 91), cursors and plans killed (43, 237, 175), concurrency (`WriteConflict` 112, `NoSuchTransaction` 251), the node's role (189, 10107, 13435, 13436), memory limits (146, 292) | an operation of 0 documents (or its count), under the `audit.configure` filters; for the agent's identity, a read charged at least one document |
| Telling: any other code, an unknown one, a code that is not an integer, or `ok: 0` without a code | (fails closed; such a line is classified, never dropped) | reads (`find`, `aggregate`, `getMore`, `count`, `distinct`, `mapReduce`), writes that select or compute from stored documents (`update`, `delete`, `findAndModify`, `bulkWrite`, `$out` / `$merge`) and DDL (an index build quotes a duplicate key): **always reported**, whether or not they returned documents first (with their count, 0 when none), and **never the agent's own**; a failed `insert` (it quotes only its own documents; a `DuplicateKey` on it is an existence oracle, filtered by `min_rows` outside `sensitive_objects`) and DCL (which always passes the filters): an ordinary event |

A failed operation of no document whose source logged no count is given 0 rows. A profiler entry whose command the server truncated and whose name is lost is reported as a read of unknown shape when it failed with a telling code. The agent's own operations fail only in quiet ways (its `maxTimeMS`, a closed connection) or are refused (a privilege it lacks): a telling failure with its identity is someone else using it. The **`auditLog`** is unchanged: it logs authorization checks (a refused one read nothing) and completed DDL / DCL, never how a command ended, so a failed record there gives no event and an authorized read that then fails is reported as a read (no count). Integration tests (`it_audit::failed_reads_without_documents_*`) run a `$toInt` read of an e-mail address and a `maxTimeMS` read, from another account and from the agent's identity, against MongoDB 8.0 (server log and profiler) and Percona Server for MongoDB 8.0 (profiler): the telling failures are always reported, the agent's quiet one is left out, the other account's quiet one is an ordinary event, and no address of the error texts reaches the events or the logs.

**Server-side JavaScript** (since 0.7.0; security review of #207, M3; [ADR-0027 refinement of 2026-10-12](adr/0027-mongodb-audit.md#refinement-2026-10-12-accepted), accepted on 2026-10-12). An operation that runs JavaScript is **always reported, from every account, and never left out as the agent's own** (the agent never sends any), with its usual action and objects and its count (0 when it returned nothing or stopped on its `maxTimeMS`): JavaScript can throw, loop, sleep or log what it reads, and a conditional sleep under `maxTimeMS` is a one-bit oracle whose two outcomes both read 0 documents, which `min_rows` used to filter. It runs JavaScript when its command documents (`command`, `originatingCommand` for a `getMore`, `resolvedViews` for the views it reads, the `auditLog` `param.args`) hold a key `$where`, `$function` or `$accumulator`, or one starting with `$_internalJs` (`$_internalJsEmit`, `$_internalJsReduce`: what `mapReduce` compiles to, which MongoDB 7.0 and 8.0 accept from a client), at any depth below 64 (filters, `$expr`, projections, `$match` and `$group` stages, `$lookup` / `$facet` / `$unionWith` sub-pipelines, update pipelines, `findAndModify`, `count`, `distinct`, `explain`, `$out` / `$merge`), when it is a `mapReduce` or an `explain` of one, or when it touches `<db>.system.js`. An `insert` never does (its documents are stored, not run). Fail closed: a non-empty object or array at depth 64 or more counts; so do command documents of more than 64 KiB together (`$bsonSize` on the profiler, the JSON length on the files; not examined, which bounds the cost per entry: a `getMore` of a large `find` or a read through a view with a large pipeline is always reported), a `getMore` whose `originatingCommand` is not shown (profiler and server log), and a command the server cut where a key could have been cut (a profiler `$truncated` text that ends with `...` or is 51 184 bytes long or more, or a whole one that holds one of the names; a server-log `truncated` report that names an omitted element or a cut element that is not a string). The pipelines of the views an operation reads are examined through `resolvedViews` (a `$lookup` or `$unionWith` into a view, a view of a view); the `auditLog` shows a view's name only. Detection reads key names only: the files are scanned byte by byte without decoding values, and on the profiler the projection computes one boolean on the server (byte operators only on the truncated text, where a cut can split a UTF-8 character). A command of another name that runs JavaScript (`explain`) is a read of unknown shape. Whether the server allows JavaScript (`security.javascriptEnabled`) cannot be read by the agent's account (`getCmdLineOpts` and `getParameter` are refused, and `buildInfo` names the compiled engine either way), so `check()` does not show it. Integration tests (`it_audit::javascript_*`) run a `$where` that sleeps past its `maxTimeMS` (50), a 0-document `$function` match, a `$function` in a `$lookup` sub-pipeline, a filter nested past the bound, a client-written `$_internalJsEmit` and (profiler and server log) a `$unionWith` into a view whose pipeline has `$function`, from another account and from the agent's identity, against MongoDB 8.0 and 7.0 (server log and profiler) and Percona Server for MongoDB 8.0 (profiler and `auditLog`): all are reported, always, and no JavaScript code or seeded value reaches the events or the logs; `the_profiler_projection_flags_javascript` checks the server's flag on every form, `$_internalJsEmit` and `$_internalJsReduce`, views (through `$lookup`, `$unionWith` and a view of a view, each shown in `resolvedViews`), the depth and size bounds, a `getMore` of a cursor opened without JavaScript (not flagged), cut, whole and near-cut truncated commands (a cut inside a UTF-8 character included) and the agent's own poll.

**Failed logins.** A refused authentication is an `auth_failure` event: `authenticate` records of the `auditLog`, and in the server log "Failed to authenticate" lines (id 5286307, MongoDB 7.0 and later) or "Authentication failed" lines (id 20249, MongoDB 5.0 and 6.0, which log "Failed to authenticate" at debug level 3 only). Since #100, an authentication **abandoned** before any proof (result 337, `AuthenticationAbandoned`: the client disconnected before sending a proof, for example a driver closing its pool while a connection is still in its speculative SCRAM handshake) is not a failed login: such lines and records are valid but give no event. The code is read as the numeric `result` of the line or record; a server-log line without one (MongoDB 5.0 and 6.0 at debug level 3) is recognized by its status string, which is never copied. At the default verbosity, MongoDB 5.0 and 6.0 do not log abandoned authentications at all (asserted on 6.0 by the engine-matrix workflow), so the agent gets the same outcome there: no event. A wrong password (result 18, `AuthenticationFailed`) and an unknown user (result 11, `UserNotFound`) are still reported on every version. On 5.0 and 6.0 with the access-control log verbosity at 3 or more, a refused authentication is written twice (20249 and the debug 5286307 line) and is reported twice. This refines [ADR-0027](adr/0027-mongodb-audit.md), which stays Accepted and is not amended.

### Signals

The signal ids are registered for `mongodb` in [`shared/protocol/signals.json`](../shared/protocol/signals.json).

| Signal | When it is set |
|--------|----------------|
| `signature.mongodump` | A read of a collection (`find`, `aggregate`, `getMore`) by a client whose application name (`appName`) is `mongodump`, alone or followed by a space, `/`, `-` or a digit |
| `signature.mongoexport` | The same with `mongoexport` |
| `shape.full_table_read` | A `find` whose filter has no key, without a limit or with a limit above 10 000; an `aggregate` with no stage or only pass-through stages (`$project`, `$addFields`, `$set`, `$unset`, `$sort`, `$replaceRoot`, `$replaceWith`); a `getMore` of such a cursor when the source shows the command that opened it (log, profiler) |
| `volume.large_result` | More than 10 000 documents returned or written by one operation (server log and profiler only) |

These are heuristics, evadable by design. The application name is declared by the client: a dump tool run under another name carries no signature, and any client can declare the tools' names. The shape rule is cheap to evade: a filter that selects everything (`{_id: {$exists: true}}`), an `aggregate` with `{$match: {}}` or a large `$sample`, or a dump in many small filtered reads is not a whole-collection shape; `getMore` batches split a large read into operations below the volume threshold. On the `auditLog`, `getMore` records carry no filter, so only the application-name signatures apply to them. The volume × sensitivity score computed by the console remains the robust signal, and it needs row counts: `auditLog` events have none and score 0 ([ADR-0021](adr/0021-access-event-correlation.md)).

### The agent's own account

As for PostgreSQL and MySQL / MariaDB, an event of the agent's account is left out only when **all** of these hold:

- it is a read or a connection: writes, DDL and DCL of the agent's account are always reported;
- the account is `<account>@<auth_source>` of the target;
- the application name is `databastion-agent` when the source shows one;
- the client address is the agent's own address as the server sees it (the `whatsmyuri` command, read at each re-probe). Only an IP literal counts: a Unix socket leaves nothing out;
- it carries no signal;
- the documents it read stay within `limits.max_sample_rows` per collection over a rolling 24 h, each read charged **at least one document** since the phase 8 follow-ups, so a walk of successful reads that return nothing (a filter that matches nothing) is capped at the budget too ([as for PostgreSQL](#the-agents-own-account), with the same `audit.configure` caveat and case-insensitive collection names). Walks through error messages are reported: on the profiler and the server log, a failed read of no document whose code may show values is always reported and never left out, and a quiet failure is charged one document ([above](#what-is-kept)). An operation that runs server-side JavaScript is never left out, on every source ([above](#what-is-kept)). On the `auditLog`, which has no counts, only a `find` with a numeric limit in `1..=max_sample_rows` is left out, charged that limit; any other read (an `aggregate`, including the agent's own `$sample`, a `find` without a limit) is reported.

Not charged to the budget (same identity rules): the agent's `count` without a filter (it reads no document), and, **on the profiler source only**, the agent's own profiler polls with their exact shape: a `find` on `system.profile` with a one-key filter and `limit: 1000`, or the newest-entry probe with no filter and `limit: 1`. Any other read of `system.profile` with the agent's identity is charged like any read, and a read of it by any other account is reported. The [CAS store guard](#cas-store-guard-postgresql-mysql--mariadb-mongodb-openldap)'s key probe, recognized by its exact pipeline (`$sample` of 1, then a `$project` of the key names only; on the profiler, compared whole by the server), is not charged either: it returns no value, so it never pushes a fully sampled collection over the budget. The guard's ticket type count (`$group` on `type` with `$sum: 1`, `$limit` 256, exact shape) is charged its rows, or 256 when the source logs no count (`auditLog`). Any other pipeline is charged as before.

Limits of these rules: behind a proxy or NAT every client has the same address. Someone holding the agent's credentials on the agent host, spoofing its application name and reading at most the budget per collection and day stays unreported (on the `auditLog`, with `find`s whose limits add up to the budget); on the profiler source, a read with the agent's exact poll shape is uncharged only up to the number of polls the agent actually sent to that database (unused credits capped at 64), so such a client can at most take the place of the agent's own polls before its reads are charged and reported. Such a client can also repeat the guard's exact key probe uncharged: it reveals the top-level key names of random documents (a value only where a schema uses data as key names, for example documents keyed by e-mail address or user id). Since #88 the row counters are persisted across agent restarts.

### Notes

`check()` Audit notes for MongoDB targets: `audit.authcheck_success_pending`, `audit.auditlog_on_community`, `audit.log_without_row_counts`, `audit.slow_operations_only`, `audit.limited_pending_first_record`, `audit.source_not_configured`, `audit.log_not_readable`, `audit.records_dropped`. `check()` counts `find` on `<db>.system.profile` as the Audit grant only while a stream reads the profiler; otherwise it reports it as `privilege.system_collections`.

### Known limits

- **Never Full; no document counts on the `auditLog`** (above).
- **Slow operations only on the server log and the profiler.** A fast `mongodump` of a small collection, or any read under `slowms`, is not seen; a sampled log misses operations at random.
- **Log files while the agent is stopped.** For the `auditLog` and the server log, a file rotated by rename while the agent was stopped is read from the start of the new file (the rest of the old one is not read); one truncated in place is read from its start since #97 ([Truncation while the agent is stopped](#audit-log-files-and-failing-streams-every-engine)).
- **Profiler ring buffer.** Entries overwritten between two polls are lost without a trace.
- **Abandoned authentications** (since #100, security review of #100). Handshakes abandoned before any proof give no event. A client that knows account names can therefore confirm that they exist, and collect their SCRAM salt and iteration count, through abandoned handshakes without being reported. It cannot verify a password without sending a proof, and every wrong proof is reported. Floods of unfinished handshakes no longer feed the volume signals.
- **Failed operations** ([What is kept](#what-is-kept), since the phase 8 follow-ups). The kinds are closed lists of error codes: a server version that gives a quiet code to an error whose text shows a value would hide that failure under the filters (and, from the agent's identity, charge it one document); any code not listed is telling, so a new code fails closed. A telling failure that returned documents first keeps its count and is always reported. A `DuplicateKey` on a failed `insert` confirms that a stored document holds the guessed value: such inserts stay under the filters. A quiet failure without JavaScript can still be a timing channel (an expression or a catastrophic `$regex` that runs long when a guess is right and hits `maxTimeMS`): it stays under the `audit.configure` filters, and from the agent's identity each is charged one document, so a walk is capped at the budget (a ROADMAP follow-up, deferred by the maintainer to after 0.7.0); with server-side JavaScript it is [always reported](#what-is-kept). Failed `insert`s and DCL stay under the `audit.configure` filters. On the `auditLog`, failures are not visible (the agent's own `find`s with a limit stay charged their limit).
- **Heuristic signals** and **own-account residuals** (above).
- **Log literals on the agent host.** The files the agent reads hold other users' literals; the agent keeps none (zeroized buffers, never logged or sent), but a compromised agent host can read them through the file ACL it was given ([05-security.md](05-security.md#recommended-database-accounts-read-only)).
- **At-most-once delivery**, as for the other engines. Since #88 the profiler position is persisted per database (a time and hashes of the entries read at it): an agent restart resumes there, within what the capped `system.profile` collection still holds.

## OpenLDAP Discovery

What the OpenLDAP connector does, as implemented in phase 6 (#79, [ADR-0029](adr/0029-openldap-connector.md)). The reference is [the connector README](../agent/crates/connector-openldap/README.md); the account is in [05-security.md](05-security.md#recommended-database-accounts-read-only).

### Scope
- **One declared server**, over LDAPS, StartTLS, or cleartext on `ldapi://` / loopback only. Referrals and continuation references are never followed (counted as `skipped_remote`); aliases are never dereferenced.
- **Naming contexts** from the root DSE (at most 64), filtered by the job's `databases`; the Audit log base (`openldap.accesslog_base`, default `cn=accesslog`) is never scanned.
- **Containers**: per naming context, one subtree listing of `organizationalUnit`, `organization`, `dcObject`, `domain`, `country` and `locality` entries (DNs only, at most 1024; a cut listing counts `skipped_limit`), filtered by the job's `schemas`. Entries whose parent is not a container (`uid=x,cn=group,ou=a,…`) and the root entry of each naming context are not read.
- **Attributes**: from the server's schema (subschema subentry, `SUP` chains resolved), only `userApplications` attributes of a text syntax: Directory String, IA5 String, Printable String, Numeric String, Country String, Telephone Number, Postal Address, Generalized Time, Integer. Custom attributes are covered like standard ones. DN-valued attributes (group members, `seeAlso`), octet strings, binaries, certificates, photos, UUIDs and unknown syntaxes are never requested (fail closed). At most 1024 attributes.
- **Password attributes are never read**: `userPassword`, `authPassword`, their subtypes and a closed list of other credential attributes (Samba, Kerberos, `pwdHistory`, `userPKCS12`) are never requested, whatever the ACL grants, and no finding is produced for them; their presence and hash schemes are not reported. `check()` only flags an account that could read them (`privilege.password_attributes_readable`, from an attributes-only search of the first 64 entries of each naming context: the values never cross the wire).

### Sampling
- Per container (and the naming context itself), one one-level search, filter `(objectClass=*)`, `sizeLimit` = the job's `sample_rows`, `timeLimit` from the job's statement timeout (at least 1 s). No paged results: a server size limit below `sample_rows` gives a smaller sample.
- The sample is the first entries of each container **in server order** (entry id order on `back-mdb`: oldest entries first), not a random sample.
- Containers whose DNs normalize to one name share one sample of at most `sample_rows` entries per scan, searches of empty containers counting one each; the others are not searched (`skipped_limit`, [The agent's own account](#the-agents-own-account-3)).
- Entries are grouped by normalized container and structural object class; per group at most `sample_rows` values per attribute, values cut to 4096 bytes, values that are not UTF-8 skipped, Generalized Time read as `YYYY-MM-DD`, attribute options (`;lang-fr`) pooled with the base attribute. Each search is read to its end before any finding is submitted.

### Locations
`database` = the naming context, `schema` = the entry's container, `object` = the structural object class, `field` = the attribute (lowercased). The container is the entry's parent DN reduced to container RDNs, a value that looks like data becoming `*` (`ou=Oliver O'Connor,ou=teams,…` → `ou=*,ou=teams,…`). **Entry DNs never leave the agent** and are never logged ([09-agent-protocol.md](09-agent-protocol.md#location-mapping-per-engine)). A container named after a person or a customer that the normalization does not recognize keeps its name.

### Coverage counters and notes
| Counter | Meaning |
|---------|---------|
| `objects_sampled` | (container, structural object class) groups read |
| `skipped_not_readable` | A container the server refuses (`insufficientAccessRights`, or `noSuchObject` hiding it) |
| `skipped_remote` | Continuation references (referrals, never followed) |
| `skipped_limit` | Container listing cut at its bound, or a container not searched because the pooled sample of its normalized name is full |
| `skipped_error` | Any other failure of one search |

`check()` notes for OpenLDAP targets, Discovery part: `coverage.cas_guard_tripped` (the [CAS store guard](#cas-store-guard-postgresql-mysql--mariadb-mongodb-openldap): service registry entries without masked samples nor `secret.*` fingerprints, ticket object classes listed in `cas_stores` never read); `privilege.password_attributes_readable`, `privilege.config_readable` (`cn=config` readable: ACLs, root password hashes), `privilege.accesslog_without_audit` (`cn=accesslog` readable while no Audit stream runs), `privilege.write_not_evaluated` (always: OpenLDAP shows a read-only account neither its ACLs nor its effective rights, so write access is never evaluated; check `olcAccess`), `check.stage_failed`, `check.timed_out`. The privilege report is recomputed at most every 10 minutes per target.

## OpenLDAP Audit

What the OpenLDAP connector does for Audit, as implemented in phase 6 (#79, [ADR-0029](adr/0029-openldap-connector.md) decisions 7 to 10). The reference is [the connector README](../agent/crates/connector-openldap/README.md#audit).

### Source and level

One source: the `slapo-accesslog` database (`audit_source` `openldap_accesslog`), read over LDAP with the agent's service DN and transport. Recommended overlay settings on each monitored database: `olcAccessLogOps: reads writes session`, `olcAccessLogSuccess: FALSE` (failed operations logged too), a purge (`olcAccessLogPurge`), and `olcDbIndex: entryCSN eq` on the log database.

- **Incremental by `entryCSN`** (commit order). `reqStart` is not used as the cursor: a long search is written at its end with an early `reqStart`, so a `reqStart` cursor would skip exactly the long exports. Each poll reads the records from the cursor minus a 10 s overlap (records already read are recognized by their CSN), `sizeLimit` 1000 per search, repeated at most 16 times while the server cuts the result. The cursor is persisted with the CSNs read within the overlap (at most 1000), so after a restart only the overlap entries not read yet are reported; the first start reads from one minute back (no history replay).

| Level | Condition |
|-------|-----------|
| **Full** | For **every** scanned naming context: a successful search record in `cn=accesslog` from the last 24 h (reads are logged) **and** a logged failed operation from the last 24 h (failed operations are logged, so a search cut by a size, time or administrative limit after returning entries leaves a record) |
| **Partial** | Reads proven logged for some contexts only (`audit.reads_not_logged`, count of contexts), or reads proven for every context but failed operations not proven for at least one (`audit.failed_operations_not_logged`, count of contexts) |
| **Limited** | `cn=accesslog` readable, but no context shows a search record (`audit.reads_not_logged`); binds and writes may still be logged |
| **None** | `cn=accesslog` not readable or absent (`audit.accesslog_not_readable`), or the Audit stream stopped after repeated internal errors (`audit.stream_stopped`, [below](#audit-log-files-and-failing-streams-every-engine)) |

How the level is proven: `check()` looks, per naming context, for a search record under the context; when there is none, it runs one base-scope search on the context (attributes `1.1`) and looks again, so a server that logs reads proves it at once. Records under a deeper naming context (held by another database) do not count for the parent context. For failed operations, `check()` reads, at every privilege report (at most every 10 minutes per target, at most 8 naming contexts per report, the oldest answers first), an entry that does not exist below the context, `cn=databastion-absent-probe-<suffix>,<context>` with a suffix unique to that probe (`noSuchObject`, which reads nothing), and looks for that probe's own failed-search record. Only the latest answer counts: it replaces the previous one (#83, [ADR-0032](adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 6). With `olcAccessLogSuccess: TRUE`, only successful operations are logged: the level is capped at Partial from the next report that probes the context. A context whose failed-operation proof is missing or not known yet (a probe refused, a context not probed yet, a report cut by its time bound) also caps the level at Partial. The stream's own search records renew the proof that reads are logged; a failed search that returned entries, seen by the stream, counts as a logged failed operation until the next probe of that context.

Limits of the Full proof:
- **Freshness**: a change of `olcAccessLogSuccess` is seen at the next report that probes the context (10 minutes, longer with more than 8 naming contexts). The proof that reads are logged is kept up to 24 h, so a later change of `olcAccessLogOps` can go unseen for as long.
- **Probe records**: each probe leaves one failed-search record in `cn=accesslog` per context and report.
- An `olcAccessLogBase` that covers only part of a naming context cannot be seen: the proof may fall inside it.

Full means docs/08's definition is met (every search logged with its authorization identity, base, scope and entry count); what the log does not have is listed below.

### What is kept

Read from each record: `reqType`, `reqStart`, `reqSession`, `reqAuthzID`, `reqDN`, `reqResult`, `reqScope`, `reqFilter`, `reqAttr`, `reqAttrsOnly`, `reqEntries`, `reqSizeLimit`, `entryCSN`. Never requested: `reqMod`, `reqOld`, `reqAssertion`, `reqMessage`, the controls and the other value-bearing attributes. `reqFilter` (which carries assertion values) and `reqDN` are reduced in memory to closed facts: whether the filter selects entries by value, whether it is one of the agent's own filters, the naming context, the normalized container and a keyed hash of the base (for paged totals). Neither is kept, logged or sent.

- **Actions**: search and compare are `read` (`rows` = `reqEntries` for a search); add, modify (password changes included), delete and modrdn are `write`; bind is `connect`, or `auth_failure` when it failed. Unbind, abandon and extended operations give no event. A failed search that returned entries is reported; other failed operations are not.
- **Principal**: the authorization DN (`reqAuthzID`), `anonymous` when empty; the bind DN for a bind. Sent in clear only for `anonymous`, the agent's own DN and the DNs listed in `openldap.clear_principals`; **every other principal is a keyed fingerprint** (an entry DN usually names a person). Failed binds are always fingerprinted.
- **Objects**: the naming context of `reqDN`, and the console's `sensitive_objects` of that context the operation could reach (from the base's container, and for a subtree search every container below it; at most 16, the first ones in the console's most-sensitive-first order, [ADR-0031](adr/0031-openldap-principals-dedup-and-stream-alerts.md) decision 4). With none, the object is `*` with the container as `schema`: the log does not give the object class of the entries a search returned.
- **Missing from the log**: the client address (events carry none) and the application name.

### Signals

The signal ids are registered for `openldap` in [`shared/protocol/signals.json`](../shared/protocol/signals.json).

| Signal | When it is set |
|--------|----------------|
| `shape.bulk_search` | A search with scope one-level, subtree or children whose filter selects no entry by value: only presence tests (`(objectClass=*)`, `(mail=*)`) and `objectClass` equality assertions, combined with `&` / `|`. The shape of an LDIF export or a bulk `ldapsearch` |
| `volume.large_result` | More than 10 000 entries returned by one search, **or by the pages of one paged search**: the records of one connection with the same base and scope are summed, and the record crossing 10 000 and the later ones carry the signal |

There is no `signature.*` for OpenLDAP: `ldapsearch` declares nothing, and `slapcat` (an offline LDIF export on the server host) performs no LDAP operation, so it leaves no `cn=accesslog` record and is not seen. These are heuristics: a selective filter that matches everything (`(uid=a*)` … `(uid=z*)`, `(!(uid=nobody))`), per-entry base-scope reads, or pages spread over several connections evade them. The volume × sensitivity score remains the robust signal, and it works here (`reqEntries` on every search).

### The agent's own account

An event is left out only when it is a read or a connection of the agent's identity (the DN returned by Who am I?), carries no signal, and the agent's reads of each object stay within `limits.max_sample_rows` entries over a rolling 24 h, each search charged **at least one entry** since the phase 8 follow-ups, so a filter walk of searches that return nothing is capped at the budget too ([as for PostgreSQL](#the-agents-own-account)); the one-level search of an empty container by Discovery costs one entry per scan. Containers whose DNs differ only in case share one budget. **Collapsed containers:** containers whose DNs normalize to one name (a value-like RDN or an escaped DN becomes `*`) share one budget too. Since the phase 8 follow-ups (security review of #197, L3) Discovery **caps their pooled sample at `sample_rows`** (at most `limits.max_sample_rows`, the budget): each search of one of them asks for at most what is left of it (`sizeLimit`), each counts at least one entry as the stream charges it (a search that fails counts its whole size limit), and once the cap is reached the other containers of the name are not searched in that scan (counted `skipped_limit`, one warning per name); within each name the containers are rotated by the scan's seed, so those left out are sampled by later scans (refinement of [ADR-0029](adr/0029-openldap-connector.md#refinement-2026-10-11-accepted-207) decision 5). One scan therefore never charges more than the budget of any object, so its own searches are not reported, however many containers share a name, empty or not (checked by a unit test with 120 containers and an integration test with 30 against slapd). The budget is not split per raw container instead: that would let the agent's credentials read the budget once per container unreported, and would put raw container DNs in the persisted budget keys. The cost is coverage: the containers past the cap are not sampled by that scan (the pooled group has `sample_rows` values per attribute either way, but an attribute present only in those containers is missed until a later scan's rotation reaches them). The log has no client address, so **no address rule applies** (unlike the other engines). The agent's exact container listing and check probes are not charged to the budget; its entry sampling is. Writes, and anything else with the agent's identity, are always reported.

Limit: someone holding the agent's DN and password can bind from anywhere unreported and read up to the budget per object and day with the agent's sampling shape. Restricting the service DN to the agent's address in `olcAccess` (`peername.ip`, [05-security.md](05-security.md#recommended-database-accounts-read-only)) is the recommended control.

### Notes

`check()` Audit notes for OpenLDAP targets: `audit.accesslog_not_readable`, `audit.reads_not_logged`, `audit.failed_operations_not_logged`, `audit.records_dropped` (log entries that do not parse, counted for 24 h), `audit.stream_stopped`.

### Known limits

- **No client address** in the log: principals carry none.
- **Incidents per fingerprint** (end-of-phase-6 review M1, fixed in #81 by [ADR-0031](adr/0031-openldap-principals-dedup-and-stream-alerts.md)): each fingerprinted user has its own incident key; every unidentified principal of one agent (SASL binds) shares one.
- **Records committed out of CSN order** (review L3, reduced in #83): the persisted overlap CSNs cover restarts; a record committed more than 10 s below the cursor, or beyond the 1000 persisted CSNs, is lost.
- **Container names** (review L4): the normalized container (`schema`) keeps `ou`, `o`, `dc`, `c`, `l` and `st` values that do not look like data; a container named after a person or a customer that the normalization does not recognize reaches the console.
- **Log gaps**: records purged by `olcAccessLogPurge` before the agent read them (agent stopped longer than the purge age) are lost; on first start, a server clock behind the agent's by more than 60 s skips records until it catches up.
- **`slapcat` and other offline exports** are not visible.
- **Heuristic signals** and **own-account residuals** (above).
- **Delivery**: at most once, as for the other engines; after a caught internal error (panic), the stream restarts from its persisted cursor and the events of at most one search round may be sent twice. A log entry that makes the connector panic is dropped alone; one that ends the stream repeatedly is located (isolation mode: position saved after every entry) and skipped after 3 panics at its exact position. Its events are lost (counted in `audit.records_dropped` and `audit_records_skipped_total`). The stream stops only on the thresholds of [Audit log files and failing streams](#audit-log-files-and-failing-streams-every-engine), with a console alert.

## CAS store guard (PostgreSQL, MySQL / MariaDB, MongoDB, OpenLDAP)

Apereo CAS can keep its stores in engines DataBastion already reads: the **ticket registry** (live SSO bearer credentials), the **service registry** (definitions with client secrets) and the **audit trail** (ticket ids, request headers, names typed at failed logins). The connector of that engine reads them, with its own account, grants, TLS and pacing, and applies the CAS store guard ([ADR-0041](adr/0041-cas-connector.md) decisions 5 and 6). It is **on by default** and cannot be turned off.

**Recognition.** A table, collection or LDAP entry is a CAS store:
- **by name**, compared case-insensitively on ASCII letters and digits only (the part after the last `.`), whatever the schema or database: `CasTickets` / `cas_tickets` (ticket registry), `RegisteredServices` (service registry), `COM_AUDIT_TRAIL` (audit trail), the MongoDB defaults of CAS 8.0.2 (verified against its jars: the ticket collections `ticketGrantingTicketsCollection`, `serviceTicketsCollection`, `proxyTicketsCollection`, `proxyGrantingTicketsCollection`, `transientSessionTicketsCollection`, and the default storage names the MongoDB ticket registry also uses as collection names for the OAuth 2.0 / OIDC and SAML2 IdP tickets, `oauthCodesCache`, `oauthAccessTokensCache`, `oauthRefreshTokensCache`, `oauthDeviceTokensCache`, `oauthDeviceUserCodesCache`, `oidcCibaRequestsCache`, `oidcPushedAuthzRequestsCache`, `samlArtifactsCache`, `samlAttributeQueryCache`, and `wsSecurityTokenTicketsCache` for WS-Federation; the legacy names `oauthCodesCollection`, `oauthAccessTokensCollection`, `oauthRefreshTokensCollection`, `oauthDeviceTokensCollection`, `oauthDeviceUserCodesCollection` and `casTicketsCollection`, assumed before the check and possibly set by an operator, are still recognized, fail closed; the service registry `cas-service-registry`; the audit trail `MongoDbCasAuditRepository`) and the LDAP object class `casRegisteredService` (CAS 8.0.2 default). A storage name changed in the CAS configuration (`cas.authn.oauth.access-token.storage-name`…) is matched by shape or by `cas_stores` only;
- **by the target's `cas_stores`** in its engine block (`postgres`, `mysql`, `mongodb`, `openldap`): `ticket_registry`, `service_registry` and `audit_trail` lists of table, collection or object class names (at most 64 each), for stores under custom names;
- **by column shape** (a renamed table): `id`, `type`, `body` (MongoDB: or `json`), `principal_id` / `principalId` (MongoDB: or `principal`) and `parent_id` or an expiration column is a ticket registry. An audit trail is `AUD_ACTION` with `AUD_RESOURCE`, or with `AUD_USER` and `AUD_CLIENT_IP` or `AUD_DATE` (the table as MySQL / MariaDB show it to an account without a privilege on `AUD_RESOURCE`), or, in MongoDB, `resourceOperatedUpon` or `actionPerformed` with `principal` or `clientInfo` (Inspektr documents). MySQL / MariaDB show an account only the columns it holds a privilege on, so a renamed ticket table whose credential columns are not granted is not recognized there (nothing of it is readable either). MongoDB first reads the top-level field **names** of one random document (`$sample` of 1, projected to its keys with `$objectToArray`, no value), so a renamed collection is recognized before any document is read; the shape of the documents read afterwards is checked again, and documents of a store recognized only then are dropped unclassified;
- by an LDAP `description` that is a CAS service definition (a JSON object whose `@class` is a CAS service class);
- by the **ticket-id value tripwire**, in the sampling path every connector shares, before classification:
  - a value that starts (after white space) with a named CAS ticket prefix, `TGT`, `ST`, `PT`, `PGT`, `PGTIOU`, `TST`, `OC`, `AT`, `RT`, `ODT`, `ODUC`, `CIBA`, `OPAR`, `SART`, `SATQ` or `STS` followed by `-<digits>-` (`TGT-12-…`), drops its **whole column**, document field or attribute (no finding, sample or fingerprint; not read further in the scan), counted in `coverage.cas_guard_tripped`. The prefixes are the ticket prefix constants of CAS 8.0.2 (core, OAuth 2.0, OIDC, SAML2 IdP and WS-Federation modules, verified against its jars); CAS 8.0.2 has no `CT` prefix (listed until the check). Prefixes of other optional modules are not verified and fall under the generic shape below;
  - a value that only has the generic shape `^[A-Z]{2,8}-[0-9]+-` (a prefix outside the list, or an unrelated identifier such as the invoice number `INV-2026-000001`), or that holds a named ticket id anywhere inside it (a URL `…?ticket=ST-1-…`, a JSON document, a quoted value), is dropped **on its own**: never classified, masked nor fingerprinted (whole-value analyzers never see it), counted in the scan log only; the other values of the column are classified as usual. The `coverage.cas_guard_tripped` description counts columns not read further, so these per-value drops are not a target note.
  - Names too: a ticket id in a column name, field path, MongoDB key or LDAP DN is replaced by `*` from where it starts to the end of the name.

A store that matches none of these rules is sampled like any table (residual risk, ADR-0041); the tripwire then fires on the first ticket id it reads. **Tripwire residuals**: a ticket id under a prefix outside the named list and outside the generic shape (lower case, more than 8 letters, a non-ASCII letter) is classified like any value (only masked samples and fingerprints of classified values leave; ticket ids match no classifier); values that merely share the generic shape are lost to classification (they no longer hide the rest of their column). A ticket id stored in an encoded form (percent-encoded `ST%2D1%2D…`, JSON-escaped, or base64 inside a blob) is not recognized either. The guard notes of a target are replaced per database only by a scan that completes that database: on a large target whose scans keep running out of time (`skipped_limit`), `coverage.cas_guard_tripped` and `security.ticket_registry_unencrypted` can stay up after the store is fixed, until a scan completes (they over-report, never under-report).

**What is read.**

| Store | Discovery |
|-------|-----------|
| Ticket registry | Never sampled: one bounded aggregate, the ticket count per `type` (`SELECT type, count(*) … GROUP BY type`; MongoDB `$group` on the `type` field found by the key probe, any ASCII case), under the statement timeout and the Discovery pacing, when the account can read `type`. Counted as `skipped_unsupported`. Ticket counts per kind are logged locally; tickets whose `type` is not the encoded-ticket class (CAS `crypto.enabled: false`) give `security.ticket_registry_unencrypted` with their count. |
| Audit trail | `AUD_RESOURCE`, `AUD_HEADERS`, `AUD_EXTRA_INFO` (MongoDB: `resourceOperatedUpon`, `what`, `headers`, `clientInfo.headers`, `extraInfo`, excluded by projection or never classified) never selected; `AUD_USER` (MongoDB `principal`) classified without masked samples (counts and fingerprints); the other columns as usual. |
| Service registry | `body` (MongoDB: every field; OpenLDAP: every attribute of a registry entry) classified without masked samples, and without fingerprints for `secret.*` classifiers. The other columns as usual. CAS-aware parsing of these bodies is a later item. |

**`check()`, at every heartbeat** (not only every 10 minutes like the other privilege notes), so a ticket table recreated by a CAS upgrade with a table grant is reported at once: `privilege.ticket_credentials_readable` (count of ticket registries and audit trails) when the agent's account can read a credential column, that is any ticket registry column but the metadata (`type`, creation, use and expiration times), or `AUD_RESOURCE` / `AUD_HEADERS` / `AUD_EXTRA_INFO`:
- **PostgreSQL**: `has_column_privilege` on every column of the relations named or shaped like a ticket registry or an audit trail, so direct grants, roles (with `INHERIT`), `PUBLIC`, table grants and `pg_read_all_data` all count. `ALTER DEFAULT PRIVILEGES` is not read as such, but a table recreated under default privileges is reported at the next check (its grants are then in place). At most 256 candidate relations and 20 000 columns per database, relations matched by name first; a list cut at its limit, a name that is not UTF-8, or a failed check query, gives `privilege.not_evaluated` (as on MySQL / MariaDB and MongoDB), never least privilege;
- **MySQL / MariaDB**: the columns the account can see with `SELECT` (direct grants, enabled roles, `PUBLIC`), and the `SELECT` grants of `SHOW GRANTS` for the roles the account could enable and `PUBLIC` (as [ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md)): a table grant without a column list or with a credential column, or a database-wide or global grant over a recognized table. Fail closed: when a role or `PUBLIC` cannot be evaluated (on MariaDB, every role but the default one), a grant line is not understood, the column list is cut at 20 000 rows (tables matched by name first), or the table list holds more than 1 000 000 tables, the check adds `privilege.not_evaluated`;
- **MongoDB**: `find` (or `anyAction`) on a ticket registry or audit trail collection, from the resolved privileges of `connectionStatus` (MongoDB has no field-level privilege), against the collections named like CAS stores, those the last scan recognized by shape, and, for a database-wide `find` (or a `find` on any database, which lists the databases first), the collections of those databases: at most 16 databases per check; more, or a database or collection list cut or not readable, adds `privilege.not_evaluated`.

**Check-time cost on MySQL / MariaDB** (measured on the dev MySQL 8.4.11 and MariaDB 11.4.13, unconstrained containers, a catalog of 5 000 tables in 50 schemas, 5 columns each, all visible to the agent's account, plus the three CAS 8.0.2 JPA tables; `cas_guard_readable` timed in the connector, roles and `SHOW GRANTS` included, median of 5, two runs after the change; per-statement times, server CPU and status deltas from the `mysql` / `mariadb` client; opt-in test `cas_guard_cost` in `connector-mysql`). Since #165, `check()` matched the name keys in SQL with a 900-byte limit per statement, so it sent 3 statements with the built-in names and 67 with three 64-name `cas_stores` lists of 128 characters, each a full walk of the catalog (10 to 20 ms at 5 000 tables). It now reads the table names once (12 ms on MariaDB, 20 to 40 ms on MySQL, no table definition opened), matches the name keys in the agent, and sends a column query only for each key present:

| Guard phase at 5 000 tables | MySQL 8.4 before → after | MariaDB 11.4 before → after |
|-----------------------------|--------------------------|-----------------------------|
| Built-in names | 0.16 s → 0.22 s | 0.41 s → 0.48 to 0.53 s |
| 3 × 64 `cas_stores` names of 128 characters | 1.00 s → 0.24 to 0.29 s | 1.11 s → 0.50 to 0.66 s |
| Server CPU for the statements, 3 × 64 names | 1.14 s → about 0.2 s | 1.04 s → about 0.35 s |

The rest is the column-shape query, which must read the column names of every table: 0.15 to 0.2 s on MySQL (data dictionary reads) and 0.3 to 0.5 s on MariaDB, where it opens every table definition, twice (6 000 to 10 000 `Opened_table_definitions` per heartbeat at 5 000 tables, which also churns a `table_definition_cache` smaller than the catalog: 400 by default on MariaDB). It grows with the catalog, about 0.1 s per 1 000 tables on MariaDB: about 5 s of the 10 s heartbeat deadline ([ADR-0025](adr/0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md)) at 50 000 tables. Halving it needs per-table column queries whose text depends on the catalog, which the Audit stream cannot recognize by a fixed text; not done.

The core adds `coverage.cas_guard_tripped` and `security.ticket_registry_unencrypted` from the latest **completed** Discovery scans, kept per database (MySQL / MariaDB schema, LDAP naming context): a scan replaces the tallies of the databases it covered once it succeeds (a scan with a schema or object filter, or stopped out of time, only raises them), so the notes do not change while a scan runs. On `cas` targets the tripwire also runs (the CAS connector shares the sampling path), but `coverage.cas_guard_tripped` is not registered for the `cas` engine: its drops are logged only. Ticket ids, principals, bodies and attributes are never read, logged, sampled nor fingerprinted.

## Apereo CAS

What the CAS connector does, as implemented in phase 8 ([ADR-0041](adr/0041-cas-connector.md), P8-B; since 0.4.0). Besides unit, property, fuzz and runtime tests on files, it is tested end to end against the CAS 8.0.2 dev service (CI job `e2e-cas`, #145, part of the required `CI result` check) and under load (job `load-cas`, [figures](#load-and-database-impact-measured)); CAS is not in the engine matrix. The reference is [the connector README](../agent/crates/connector-cas/README.md); the target settings are in [10-user-guide.md](10-user-guide.md#6-declare-targets). Maintained CAS lines only (8.0.x; 7.3.x is not supported); the agent cannot read the CAS version, so it is not checked at run time.

### Sources
- **Local files only**, declared in `agent.yaml`: the JSON or YAML service registry directory (`cas.service_registry.json_dir` or `yaml_dir`, exclusive) and the JSON audit log (`cas.audit_log.path`). No network connection of any kind (no HTTP, database or LDAP client), no credential, no actuator endpoint; never detected locally (I5). The CAS configuration (`cas.properties`, `cas.yml`) is never read.
- **CAS stores held in another engine** (JPA tables in PostgreSQL / MySQL / MariaDB, MongoDB collections, the LDAP service registry) are read by that engine's target, at that engine's level, under the [CAS store guard](#cas-store-guard-postgresql-mysql--mariadb-mongodb-openldap): ticket registries metadata only, ticket ids never sampled.
- **File checks**: anything the agent's account could write is refused (owner, group or world write bit, `faccessat(W_OK)` with ACLs, a writable ancestor directory); registry entries are opened with `openat(O_NOFOLLOW)` and checked on the descriptor (regular file, one hard link, same device as the directory, at most 1 MiB, at most 4096 files); a directory holding CAS configuration or key material (`application*.yml`, `cas*.properties`, `bootstrap*.yml`, `thekeystore`, `*.jks`, `*.p12`, `*.pkcs12`, `*.pem`, `*.der`, `*.key`, `*.jwk(s)`, `*.p8`…) is refused as a whole; the audit log must be a regular file with one hard link, checked on the core tailer's own handle after every (re)open. A declared path that no longer resolves where it did when `agent.yaml` was loaded is refused until the next reload.

### Discovery
- **Service registry**: each `.json` file (`json_dir`) whose top-level object has a CAS `@class` and a `serviceId`, or each `.yml` / `.yaml` file (`yaml_dir`) that starts with a CAS class hint (`--- !<org.apereo.cas.…RegisteredService>`, the form CAS 8.0.2 requires) and has a `serviceId` (other files are skipped and none of their values is classified). Blank lines may precede the `---` (CAS trims the content); a comment or indentation before it refuses the file. Unquoted YAML integers (`phone: 33612345678`, a card number) are classified as their decimal text (a leading `+` is lost; floats are not classified); JSON numbers are not classified. A YAML file is first **pre-scanned on its raw bytes** and refused before any parsing when it holds an anchor or an alias in node position, a tag other than a Java class hint after `:` or `-` (`!!str`, `!!python/…`, `!foo`), a merge key (`<<`), a directive, a second document, an explicit or complex key, flow collections nested deeper than 4, collections nested deeper than 32, more than 32 768 lines or 196 608 tokens (the parser builds the whole document's events before the visitor's bounds apply), or anything the pre-scanner does not follow (a tab outside a quoted scalar, a comment or a block scalar; an indentation indicator); `&`, `*`, `!` and `#` inside quoted, plain and block scalars and comments are text. An accepted file is read by the same visitor as JSON, so it gives the same findings as its JSON form; single-line credential values on their key's line are blanked first (the form of the top-level `clientSecret` is taken before). Since [ADR-0046](adr/0046-cas-yaml-registry-parser-without-unsafe-libyaml.md), the YAML parser is the agent's own (no `unsafe` code, no `unsafe-libyaml` on this path): the pre-scanner, run again on the blanked copy, tokenizes it as libyaml does, and the agent reads exactly the subset, the values and the errors of the former `serde_yaml_ng` path, which stays in the tests as a differential oracle (property tests and the `cas_registry_yaml_diff` fuzz target). Values the visitor skips (credential fields, structural keys) are never decoded; the others are borrowed from the wiped copy of the file or decoded into buffers wiped after use, so no copy of a value scalar is left unwiped (keys, the field names, are copied into ordinary strings, as before). A class hint must be on the line of the `:`, `-`, `[` or `,` it follows, as CAS writes it; a hint alone on a later line refuses the file. JSON definitions are read as raw values unescaped by the agent into wiped buffers, and must be UTF-8 as a whole. String values are pooled per (service type, field path) across services and classified; only masked samples and fingerprints leave. Locations: `database` = `service_registry`, `schema` = the service type (`cas`, `oauth`, `oidc`, `saml`, `ws_federation`, `other`), `object` = the service name when every value of the pool comes from services of that one name, else `*`, `field` = the JSON path in snake case (`contacts[].email`, `properties.*.values[]`).
- **Never sampled**: `clientSecret` (only its form is recorded: services holding it in clear are counted in `security.client_secrets_in_clear`), and every key whose name contains `secret`, `password`, `pass`, `pwd`, `key`, `token`, `credential`, `jwk`, `private`, `keystore`, `auth`, `cookie`, `bearer`, `salt`, `cipher`, `signing` or `header`, with everything below it. URLs lose their userinfo, query string, fragment and `;` parameters before classification.
- **Audit log**: the `who` of `AUTHENTICATION_SUCCESS` records in the last MiB of the log (at most `sample_rows`), as `audit_trail` / `audit_log` / `who`. The names typed at failed logins (possibly passwords), `what` (ticket ids), headers, user agents and addresses are never sampled.
- **Coverage**: a file read counts in `objects_sampled`; unreadable or refused in `skipped_not_readable`; not a service definition or unparsable in `skipped_unsupported`; too large or beyond a bound in `skipped_limit`; a parser failure in `skipped_error`.

### Audit: source and level
One source, the JSON audit log (`audit_source` `cas_audit_log`), tailed like the other log files (rotation, truncation fingerprints, persisted position; first start at the end of the file). The `DEFAULT` (`WHO: … WHAT: …`) format is not supported.

| Level | Condition |
|-------|-----------|
| **Partial** | An `AUTHENTICATION_SUCCESS` record **and** a ticket or token issuance record (`SERVICE_TICKET_CREATED`, or `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED`) parsed in the last 24 h; with `audit.auth_failures_not_seen` when no `AUTHENTICATION_FAILED` was parsed in the last 7 days (check that failures are not excluded from the audit) |
| **Limited** | A valid record in the last 24 h, but not both kinds: `audit.auth_records_not_seen` or `audit.service_ticket_records_not_seen` |
| **None** | No record yet (`audit.limited_pending_first_record`), none in the last 24 h, the log not readable or refused (`audit.log_not_readable`), not in the JSON format (`audit.log_format_unsupported`), or the stream stopped (`audit.stream_stopped`) |

`check()` reads at most the last 64 KiB of the log and lists the registry directory (never its files' content), within 5 s. Partial means "authentications and service tickets are logged", not "every read of personal data is logged": reads of the stores are audited by their engine's target.

### What is kept
- Read from each record: `action`, `when`, `who`, `clientIpAddress`, `userAgent` and, for `SERVICE_TICKET_CREATED`, `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` and `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` only, `what`; for the last two, also `serverIpAddress`, as an IP literal for their correlation key only, never sent ([ADR-0044](adr/0044-cas-token-only-grants-client-naming.md)); every other key (`headers`, `application`, `geoLocation`, `tenant`, unknown keys) is skipped unread. From the object-form `what` of `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED`, only the strings `grant_type` and `service` are read: `code` (the authorization code or the refresh token id), `scope`, `response_type`, other keys and nested values are skipped unread, and a duplicate `grant_type` or `service` drops the record. A record with a duplicate key is dropped. `what` is a string or, as CAS 8.0 writes it, an object (`{"service": "https://…", "ticketId": "ST-1-…"}`; ADR-0041 decision 7 assumed a string, the object form is read since #143): from an object only the string `service` is read, every other key (`ticketId`, `principal`, `credential`…) and nested value is skipped unread, and a duplicate `service` drops the record. `what`, which can hold a ticket id (a live SSO bearer credential), is reduced at parse time to the service URL's scheme and host, used only to pick a registry entry, then dropped: ticket ids are never kept, logged, fingerprinted nor sent. For any other action `what` is not decoded at all. The audit log must be UTF-8 (the log4j appender's charset, the default): a line with invalid UTF-8 in a kept key's value is dropped and counted as not JSON (`non_json`). The kept strings are unescaped by the agent into buffers wiped after use, never by the JSON library (whose internal buffer is not wiped).
- **Actions**: `AUTHENTICATION_SUCCESS` → `connect`; `AUTHENTICATION_FAILED` → `auth_failure`; `SERVICE_TICKET_CREATED` → `read` of the matching service (`rows` 1; `*` when no registry entry matches, the registry is not declared, or a `serviceId` pattern that cannot be evaluated, such as Java-only regular expression syntax, comes first in evaluation order); `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` (OAuth 2.0 / OIDC tokens issued by the token endpoint, every grant type) → `read`, `rows` 1, of the client's registry entry for the token-only grants when the correlation below names it, of `*` otherwise; `SAVE_SERVICE_SUCCESS`, `DELETE_SERVICE_SUCCESS` → `dcl` on `service_registry`. Other actions give no event.
- **OAuth 2.0 / OIDC, as CAS 8.0.2 writes it** (verified on the dev service: authorization code, implicit, `refresh_token`, `client_credentials` on `/oidc/token` and `/oauth2.0/accessToken`, `password`): a login through the authorization or implicit flow writes `SERVICE_TICKET_CREATED` with the client's redirect URI as `service` (a `read` of its registry entry when its `serviceId` matches `scheme://host/`; a pattern anchored on a path, such as `^https://app\.example\.org/oidc/callback$`, never matches the reduced URL, so the object is `*`); the token endpoint then writes `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` (`who` `audit:unknown`; `what` holds the code or refresh token, masked by CAS, and the redirect URI or client id), `OIDC_ID_TOKEN_CREATED` (OIDC only; `what` holds the ID token and the token request's HTTP attributes, **including its `Authorization` header, that is the client id and secret in Basic form, in clear**), and `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` (`who` the user, or the client id for `client_credentials`; `what` holds the token values, masked by CAS, and no service). The last one is the issuance mapped above: an authorization code login therefore gives two `read` events (the service ticket's and the token response's `*`), the other grants, which write no service ticket, one. `OAUTH2_AUTHORIZATION_RESPONSE_CREATED`, `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED`, `OIDC_ID_TOKEN_CREATED` and `OAUTH2_USER_PROFILE_CREATED` give no event and their `what` is never read. The implicit flow writes no token response record (its login's service ticket is its issuance). The device authorization grant was not exercised.
- **Token-only grants name their client** (`refresh_token`, `client_credentials`, `password`; [ADR-0044](adr/0044-cas-token-only-grants-client-naming.md)): for these grants the token request's `service` is the client id. The agent keeps each `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` record pending for 5 s (at most 1024 per audit stream, the oldest evicted; in memory only, lost on a restart), keyed by a keyed tag of its client address, server address and whole user agent, and matches its `service` against the `clientId` of the OAuth / OIDC registry entries by keyed tag (exact, case-sensitive bytes; a client id shared by two entries matches none; raw client ids are not kept). The next token response with the same key is then a `read` of that entry (its type as `schema`, its normalized name as `object`, as for a service ticket), only when every pending request of that key selects the same entry and, for `client_credentials`, the response's `who` is the client id; otherwise it stays `*`. A pending request that cannot name (an `authorization_code` exchange, the device grant, an unknown grant or client id) only makes a response of its key `*`. The `authorization_code` token response stays `*` (its login's service ticket already names the client when its `serviceId` matches); the device grant stays `*` until verified. **Losses fail towards `*`**: when a pending request is evicted, a line of a read is dropped (over 1 MiB, unparsable, a parser panic), the log is rotated or truncated, the service index is replaced, or the audit stream starts (after an agent restart too), every pending request stops naming and no token response within 5 s of that read is named. **Keep the file of the CAS audit appender JSON-only** (layout `%m%n`, no other logger writing to it): any other line in a read taints it and reduces naming; when a registry file is skipped (unreadable, too large, refused, out of time) or more than 4096 services are declared, no client is named until a scan or a stream restart indexes a complete registry. A pending request more than 5 s away from a record, before or after it, is dropped; a duplicate `serverIpAddress` drops the token record. Responses left `*` (no request, ambiguous), evicted requests and losses are counted in the agent log, at most one line per 10 minutes, counts only. The audit levels are unchanged.
- **Principals**: every `who` is sent as a keyed fingerprint except the names listed in `cas.clear_principals`; failed authentications are always fingerprinted; a credential object's string form or `audit:unknown` is reported as the fingerprint of a fixed `unidentified` token.
- **Client addresses**: IP literals only, reduced per `client_addr` (default `truncated`: IPv4 `/24`, IPv6 `/56`, IPv4-mapped and -compatible addresses as IPv4, 6to4 to `/40`; `::` and `::1` as is). They come from `X-Forwarded-For` by default and are only as trustworthy as the proxy in front of CAS. `application` is the first product token of the user agent, reduced to `[A-Za-z0-9._:/+-]` and 64 characters.

### Signals
The signal ids are registered for `cas` in [`shared/protocol/signals.json`](../shared/protocol/signals.json). Both are computed on the full client address, before the reduction.

| Signal | When it is set |
|--------|----------------|
| `volume.failed_logins_many_accounts` | One client address with failed authentications for 16 distinct principals within 10 minutes: the 16th failure carries it, and the further failures of that address are aggregated into one `auth_failure` event per address and minute with the principal `*` ("several accounts", `aggregated_count` = failures merged) |
| `volume.failed_logins_one_account` | One principal with at least 20 failed authentications within 10 minutes, whatever the addresses |

The failed-login windows hold at most 4096 addresses and 4096 principals, keyed by keyed tags (never the name), in memory only. A failure that would need a new entry in a full window joins one aggregate per minute without client address, principal `*`, with `volume.failed_logins_many_accounts`, and is counted in the heartbeat metric `audit_window_overflow_total`. Failures without a parseable address share one window. Credential stuffing and password spraying are indistinguishable (the passwords are never seen); an attacker who controls the logged address can rotate it and evade the per-address signal, not the per-principal one.

### Notes
`check()` notes for CAS targets: `audit.log_not_readable`, `audit.log_format_unsupported`, `audit.limited_pending_first_record`, `audit.auth_records_not_seen`, `audit.auth_failures_not_seen`, `audit.service_ticket_records_not_seen`, `audit.records_dropped` (count), `audit.stream_stopped`, `coverage.registry_files_skipped` (count, from the last scan), `security.client_secrets_in_clear` (count of services), `security.audit_headers_logged` (records carry request headers, so the log holds cookies), `privilege.registry_writable`, `privilege.config_readable`, `check.stage_failed`, `check.timed_out`. A target with no readable source is reported with the failure `permission_denied` when a source is refused because the agent's account could write it (the registry: `privilege.registry_writable`; the audit log: `audit.log_not_readable`, no privilege code covers it) or because the registry directory holds CAS configuration (`privilege.config_readable`), and `target_unreachable` otherwise (missing or unreadable files).

### Known limits
- **Never Full**, and the action filters (`supported-actions`, `excluded-actions`) and destinations are in the CAS configuration the agent must not read: excluded actions show only through the "not seen" notes, after a day (a week for failures).
- **No reads of the management endpoints** (`registeredServices`, `ssoSessions`): not in the audit trail, no signal.
- **OAuth 2.0 / OIDC token responses name a client only for the token-only grants, when the token request record is logged and the correlation is unambiguous** (CAS 8.0.2 writes no service in the response record, and no identifier shared by the request and the response): the `authorization_code` and device grants, a response whose request record is missing (excluded from the audit, a line over 1 MiB, an agent restart between the two records) or older than 5 s, and responses of several clients behind one address and user agent within 5 s stay `*`. **Do not exclude `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED`** from the audit (`cas.audit.engine.excluded-actions`): without it every token response is `*`. Residual risk: when a token request record is lost where the agent cannot see it (an agent restart between the request and the response, a record CAS did not write) while another request of the same client address, server address and user agent is still pending, its response can be **attributed to the wrong client** within 5 s (a false incident on one application, or a read hidden under another); for `client_credentials`, the response's `who` must also be the client id. Losses the agent sees (above) leave the response `*`. **Flows not verified on CAS 8.0.2**: the implicit flow (`id_token token`) writes no token response record (checked); the hybrid flows, other `response_type=token` variants, the device grant, token exchange and refused client authentications were not exercised. If one of them writes a token response without a token request record, the response stays `*` unless a token-only request of the same key is pending within 5 s, in which case it can be named after that request's client (the same residual risk). A forged token request (the address comes from `X-Forwarded-For`, the user agent from the client) can only turn a named `read` into `*`. The client secret in the `Authorization` header of `OIDC_ID_TOKEN_CREATED` records stays in the audit log file (the agent never reads it): protect the file like the registry ([05-security.md](05-security.md#apereo-cas-connector)).
- **Service names** come from the registry indexed at the last Discovery scan, or at the stream's start when no scan ran since the agent started: a service added later reads as `*` until the next scan.
- **Aggregates in progress** (the current minute of a flood) are lost when the stream stops; window state is not kept across restarts.
- **YAML registries** accept the subset above only: anchors, aliases, merge keys and tags other than class hints refuse the file (counted in `coverage.registry_files_skipped`), even where CAS would load it. **JSON with comments** is not accepted.
- **`X-Forwarded-For`** (above): per-address signals and baselines are only as good as the proxy.
- **Delivery**: at most once, as for the other engines; a record that makes the parser panic is dropped alone (`audit.records_dropped`).

## Redis / Valkey Discovery

What the Redis / Valkey connector does, as implemented in phase 9 (P9-B lot 1, #237, [ADR-0052](adr/0052-redis-valkey-connector.md)). **In development, not released yet**: merged on `dev`, not in 0.7.0. The account is in [05-security.md](05-security.md#redis--valkey-connector); the `agent.yaml` block in the [user guide](10-user-guide.md#redis--valkey-targets).

### Scope
- **One declared node** (I5): a `host` / `port` or a Unix `socket`, and optionally a separate Discovery node (`redis.discovery_node`, a replica, recommended so Discovery loads a replica). Cluster nodes are read alone: `MOVED` / `ASK` are never followed (counted `skipped_remote`) and the note `coverage.cluster_node_only` is set; Sentinel is refused. To scan a cluster, declare each node.
- **Versions**: Redis 6.2.7 and later, Valkey 7.2 and later; older servers are refused (`unsupported`). The Redis floor of 6.2.7 comes from the ADR-0052 refinement of 2026-10-14 (accepted on 2026-10-15): Redis 6.2.0 logs other clients' `CONFIG SET masterauth` and `MIGRATE … AUTH2` passwords in clear in its slow log, 6.2.7 and 6.2.24 redact them, and 6.2.1 to 6.2.6 were not measured ([measurements](measurements/phase9-engine-facts.md#redis-and-valkey-adr-0052)). Redis 8.0 is accepted but not tested (not maintained).
- **Redis 6.2 is refused unless opted in.** It has no `ACL DRYRUN`, so the agent cannot evaluate its account (below). With `redis.unevaluated_acl: accept` on the agent host, a 6.2 target runs with the note `privilege.not_evaluated` shown permanently; the declared patterns and the CAS guard's key privilege are then not evaluated either. On Redis 7.0+ or Valkey, `unevaluated_acl` is a configuration error.
- **Engine identification**: Valkey when `INFO server` has `server_name:valkey` or `valkey_version` (Valkey keeps `redis_version` at 7.2.4), Redis otherwise. A Valkey server declared as `redis` (or the reverse) is checked as what it is, with the note `check.server_is_valkey` (or `check.server_is_redis`).
- **Databases**: those `INFO keyspace` lists (at most 16), filtered by `redis.databases` and the job's `databases` (`db<index>`), rotated per scan.
- **Declared key patterns**: `redis.key_patterns` (globs with the server's syntax, default `["*"]`). `SCAN` returns every key name whatever the ACL's key patterns (measured on Valkey 9.0.6 and Redis 8.10.2), so the agent filters names locally against the declared patterns before any other command, and never sends a command the ACL would refuse (each refusal would write an `ACL LOG` entry, the log Audit reads). A declared pattern the account cannot read gives `privilege.declared_keys_not_readable`; the first unexpected `NOPERM` ends the walk of that database (counted `skipped_not_readable`).

### Keyspace walk and sampling
- **Walk**: `SCAN <cursor> COUNT 500` from cursor 0, then `TYPE` of each remaining key in one pipeline; each batch is one paced unit ([ADR-0035](adr/0035-discovery-pacing.md)). Per database at most `redis.max_keys` keys (default 100 000, 1 000 to 10 000 000, a local limit the console cannot raise) and at most `4 × max_keys / 500` `SCAN` calls; a walk stopped by either bound or by the scan's time budget counts the database 1 in `skipped_limit`. Successive scans start at the same cursor, so a walk cut by its bounds sees the same first keys each time.
- **Sampling per pattern**, on the first `sample_rows` keys of the pattern met by the walk:
  - string: `GETRANGE key 0 4095`;
  - hash: `HRANDFIELD key 17`, `HSTRLEN` of the fields, `HMGET` of at most 16 fields of at most 4 KiB. A hash with more than 16 fields reports every field name as `*`: field names are then treated as data (a hash keyed by e-mail address), even when it is the pattern's only key;
  - list: `LRANGE key 0 15`; set: `SRANDMEMBER key 16`; sorted set: `ZRANDMEMBER key 16` (members only); stream: `XREVRANGE key + - COUNT 16`;
  - module types (`ReJSON-RL`, `vectorset`, any type outside the six above): not read, `skipped_unsupported`, note `coverage.module_types_not_sampled`.
  Values are cut to 4 096 bytes and must be UTF-8 (otherwise skipped). `CLIENT NO-TOUCH ON` is sent where the server has it and the account holds it (every supported version but Redis 6.2), so sampling does not change the keys' LRU / LFU data. Lazy expiration still applies: on a primary, reading an expired key deletes it, one more reason to declare a replica for Discovery.
- **Merged families share one sampling budget.** Key families that the normalization merges into one pattern (often `*:*`, below) share its `sample_rows` keys, and the walk takes the first keys it meets: a family met late in the walk may never be sampled. Round-robin sampling across merged families is a [phase 9 follow-up](ROADMAP.md#phase-9-follow-ups).

### Key patterns and locations
Key names are often the most sensitive strings of the server (`user:jane@example.com:profile`). Only **normalized key patterns** leave the agent, never a raw key name nor a fingerprint of one:
- A key name is split into segments on `:`, `/`, `|` and `.` (and the content of a `{…}` hash tag), and segments into tokens on `_`, `-` and `#`. A token becomes `*` when it holds a digit (any record id: `user:42:email` gives `user:*:email`), looks generated (hexadecimal, mixed case or high entropy, 16 characters or more), is a common first name, holds a character the contract forbids, or looks like a value; every segment a classifier match touches becomes `*`. A first segment naming a URL scheme becomes `*`; a name that is not UTF-8 is `*` as a whole.
- Across the walk of a database, a position becomes `*` when it holds more than 16 distinct values (cardinality), or when 2 or more distinct values precede the same suffix (record-id rule, at every position, the first included).
- **Over-masking.** The record-id rule applies to the first segment too, so many two-segment names collapse to `*:*`: `phone:1` and `addressbook:2` give `*:*`, and so do fixed names that share a suffix shape. This is accepted under ADR-0052 decision 7 (a lost name is a smaller harm than a leaked value); the console then shows fewer, coarser patterns than the application uses.
- Every pattern passes a final check identical to the contract's `KeyPattern` (no digit runs, IP or MAC addresses, `%XX` escapes, URL scheme as first segment; at most 256 characters), else it is `*`.
- **Values found in key names are findings**: a matched e-mail, phone number… in a key name is classified like a value (masked sample, fingerprint of the value) under the field `#key` of the pattern; in a hash field name, under `#field`.
- **Location**: `database` = `db<index>`, `schema` = the Redis type (`string`, `hash`, `list`, `set`, `zset`, `stream`), `object` = the key pattern, `field` = `value` (strings, list, set and sorted-set members), the normalized field name (hashes, streams), `#key` or `#field`. The row estimate is the number of keys of the pattern seen by the walk.

### CAS store guard
A key whose name holds the ticket-id shape (`[A-Z]{2,4}-<digits>-`, `TGT-…`, `ST-…` among them) anywhere, contains `CAS_TICKET` (case-insensitive), or matches a `redis.cas_stores.ticket_registry` pattern is never read and never reported, not even as a pattern (`skipped_unsupported`, note `coverage.cas_guard_tripped`). A value holding the ticket-id shape in its first 4 KiB guards that key: its values are dropped before classification. `check()` reports `privilege.ticket_credentials_readable` when `ACL DRYRUN` shows the account could read a guarded key. **The CAS Redis ticket registry's key prefix is not confirmed** (ADR-0052 open question 9; the CAS dev image has no Redis registry): the `CAS_TICKET` family is assumed, and a registry under another prefix with digested ticket ids is protected only if listed in `cas_stores`.

### Coverage counters and notes
| Counter | Meaning |
|---------|---------|
| `objects_sampled` | Patterns sampled |
| `skipped_not_readable` | Declared patterns or databases the account cannot read; a database whose walk an unexpected `NOPERM` ended |
| `skipped_unsupported` | Module types; keys under the CAS store guard |
| `skipped_limit` | Key and `SCAN` call budgets, the scan's time budget, oversized key names (over 64 KiB) and replies |
| `skipped_remote` | `MOVED` / `ASK` on a Cluster node |
| `skipped_error` | Any other failure on one key |

`check()` notes for Redis / Valkey targets: `privilege.write_actions`, `privilege.read_beyond_discovery`, `privilege.admin_commands`, `privilege.scripting`, `privilege.pubsub_channels` (from `ACL DRYRUN`, at most every 10 minutes per target), `privilege.not_evaluated` (Redis 6.2), `privilege.declared_keys_not_readable`, `privilege.ticket_credentials_readable`, `security.default_user_nopass` (the server's `default` user answers without a password; reported, not refused), `coverage.cluster_node_only`, `coverage.module_types_not_sampled`, `check.server_is_valkey`, `check.server_is_redis`, `check.stage_failed` (also: the declared Discovery node does not report a replica role), `check.timed_out`, and the Audit notes below. **An account that holds a refusal-list command** (`CONFIG SET`, `MODULE LOAD`, `DEBUG`, `ACL SETUSER`, scripting, `REPLICAOF`, `MIGRATE`…, [05-security.md](05-security.md#redis--valkey-connector)) stops Discovery and Audit for the target. A command whose evaluation is not understood counts as allowed: a future server version whose `ACL DRYRUN` texts the agent does not know is refused until an agent release learns them. When `redis.discovery_node` is declared, `check()` evaluates both nodes, and **a Discovery node that cannot be reached makes the whole target unreachable**, Audit included (a [phase 9 follow-up](ROADMAP.md#phase-9-follow-ups)).

## Redis / Valkey Audit

As implemented in P9-B lot 2 (#239, ADR-0052 decision 8). **In development, not released yet.** Redis and Valkey have no audit log; the agent reads the servers' own diagnostic logs, so the level is **Limited at best**.

### Sources and level
| `audit_source` | Read | What it gives |
|----------------|------|---------------|
| `redis_slowlog` | `SLOWLOG GET 512` (Redis, Valkey before 8.1), `COMMANDLOG GET 512 slow` (Valkey 8.1+, the same log) | Commands slower than the threshold (10 ms by default): command, key arguments (at most 32 arguments of 128 bytes, cut by the server), client address and name; no user, no database, no reply size |
| `redis_commandlog` | `COMMANDLOG GET 512 large-reply` (Valkey 8.1+ only) | Commands whose reply exceeded the server's threshold, with the reply size as the event's `bytes` and the signal `volume.large_reply` |
| `redis_acl_log` | `ACL LOG 128` | Failed authentications (`auth_failure`, the name tried fingerprinted), and denials of the agent's own user from other connections |
| `redis_sync` | `INFO stats` `sync_full` | Full synchronizations, one read of `*` per poll with the count, signal `signature.full_sync` |

- Each read is sent only when `ACL DRYRUN` says the account may run it; on Redis 6.2 (no `DRYRUN`, opt-in only), a read refused once is not sent again by the stream. Polls run every `poll_interval_s` of the Audit settings (default 10 s, at least `limits.min_audit_poll_interval_s`), 5 s per command.
- **Positions**: per log, the highest entry id read is persisted; a gap between it and the oldest entry returned (ring buffer overrun, or a `RESET`) is counted in `audit.records_dropped`. A server restart is detected through a hash of `run_id` and resets the positions. The first start reads from the newest entry (no history replay).
- **Levels**: Limited once a slow-log or command-log entry of another client was read in the last 24 h (note `audit.slow_operations_only`); None before (`audit.limited_pending_first_record`), with `ACL LOG` only (`audit.acl_log_only`), with no readable source (`audit.log_not_readable`), or when Audit is not configured or refused (`audit.stream_not_available`). Setting `slowlog-log-slower-than 0` makes every command visible until the ring buffer overruns, still without account or volume: Limited.

### What is kept
- **Reduction at parse time**: from a log entry the agent keeps the command name (closed table; any other name is a `read` of `*`), the objects of the key arguments at the positions the table gives (checked against the servers' `COMMAND GETKEYS` per version in the engine matrix), a `SCAN`'s `COUNT` when it sets a signal, the client address and name, the ids, times and sizes. Every other argument (values, `AUTH` / `HELLO` / `ACL SETUSER` / `MIGRATE … AUTH` arguments, script bodies, channel names, the globs of `KEYS` and `SCAN … MATCH`) is dropped in the parser and never logged. A command missing from the table, that does not fit its entry, or whose arguments the server cut, gives `*`.
- **Objects are learned patterns, never normalizer output alone**: a key argument is matched against the patterns learned by the last Discovery scan of the database; without a match it becomes the longest learned literal prefix followed by `*` (`session:*`), else `*`. **Without a completed Discovery scan, every object is `*`.** The database is `db<index>` when a single database holds keys, `*` otherwise (slow-log entries carry no database).
- **Actions**: reads, writes, `ddl` (`CONFIG SET`, `MODULE LOAD`, `FUNCTION LOAD`, `SCRIPT LOAD`), `dcl` (`ACL SETUSER`, `ACL DELUSER`); scripts (`EVAL*`, `FCALL*`) are a `write` of `*` and always reported. **No row count**: events carry no `rows`, so the volume × sensitivity score is 0 for them; incidents come from signals, objects and principals, and, on Valkey 8.1+, `bytes`.

### Principals
- Slow-log and command-log entries record no user. When a poll finds new entries, the agent runs one `CLIENT LIST` and maps each entry's `addr:port` to the user of the connection still open there, **only if that connection is older than the entry** (2 s margin, measured with the server clock from `INFO`). Otherwise the event's principal is `account_not_recorded` (with the client address when known): connections closed before the poll, and every `sync_full` event.
- **Unix-socket clients are never attributed**: all of them share one address. Their events have `account_not_recorded` and client `local`.
- **NAT and proxies**: behind a NAT or a proxy, the server sees the translated `addr:port`. Attribution still follows the connection that holds that address at poll time, so a short connection is gone before the poll and its entries are not attributed. The agent recognizes its own connections by connection id, or by the address the server reports for them; it uses its own local address only after the server was seen to report the agent's connections at their local addresses (no NAT between them).

### The agent's own account
An entry is the agent's only when its connection is one of the agent's own (connection id, or the address the server reports for it, within the connection's lifetime and the same server run), never by user or client name. Such an entry is left out only when it is one of the agent's own command shapes, within the own-read row budget and the agent's own reply bound; every other command with the agent's user, from any connection, is reported. `ACL LOG` denials from the agent's own connections are counted in `check()` notes, not reported as incidents. The own-read budget is kept per learned pattern: when several databases hold keys, an own sampling entry is charged to the pattern its key matches whole in each database where it does (`db<n>` / pattern), never to a learned prefix followed by `*`; when no database matches, it is charged to the event's object `*`. The reported object does not change. Since the [refinement of 2026-10-16](adr/0052-redis-valkey-connector.md#refinement-2026-10-16-accepted-own-read-budget-scale-for-redis--valkey), a pattern's budget is `max_sample_rows × per_key_max` rows per 24 h (`per_key_max` is 49: the most one sampled key costs, its `TYPE`, members and per-field calls), enough for one scan; the `*` fallback keeps the plain `max_sample_rows`. No scan frequency is assumed: a second scan of the same pattern within 24 h gets the agent's reads reported once the budget is spent, and so does a pattern with more keys than about the budget (the walk's `TYPE` of each key is charged to it).

Slow-log and command-log entries carry an address, not a connection id, so the agent records the address the server reports for each of its sessions when it opens it: right after the handshake, each session to the target's node sends `CLIENT LIST ID <its own id>` and keeps the `addr` of its own line. A session that closes before the stream's next `CLIENT LIST` (a `check()` session, a short or paced Discovery) is then still recognized, for its lifetime plus 2 s, and its entries are left out under the rules above. This needs `+client|list` (already an Audit grant) and is done only while an Audit stream reads the target: the command is sent only once `ACL DRYRUN` reported it granted or the stream's `CLIENT LIST` was answered, not after a refusal of a real call until the server restarts or the account changes, and not after any other failure until the server restarts; a failure never fails the session (it is replaced). Without it, behind NAT or Docker's port publishing, such a session's own entries come back as events with `account_not_recorded` and the agent's client name. Before this fix (engine-matrix flake of 2026-10-15), every session relied on a `CLIENT LIST` of the stream seeing it open.

**On a Unix-socket target, the agent's own entries cannot be recognized** (socket peers are never attributed): when its own commands are slow enough to be logged (always with `slowlog-log-slower-than 0`), they come back as events with `account_not_recorded` and client `local` (#239 re-review N1). A loopback TCP target does not have this limit.

### Signals
| Signal | When |
|--------|------|
| `signature.full_sync` | `sync_full` grew: a replica's full synchronization, or a full copy of the dataset. Routine replica syncs are reported too; `redis.replicas` lists the known replicas, and the one undeclared replica seen syncing at poll time gives the event's client address |
| `volume.large_reply` | A `large-reply` command-log entry (Valkey 8.1+) |
| `shape.keyspace_enumeration` | `KEYS`, or a `SCAN` with a `COUNT` above 1 000, seen in a log entry (`redis-cli --scan` uses `COUNT 10` and does not set it) |
| `signature.cas_ticket_read` | A logged read of a key under the CAS store guard's name rule or a strict ticket prefix; the object is `*` |

### Known limits
- **Every fast read is invisible.** With the default 10 ms threshold, almost every `GET`, `HGETALL` and `SCAN` of an export by `redis-cli --scan` and `GET` in a loop leaves no entry.
- **Ring buffers**: entries overwritten between polls are lost (`audit.records_dropped`); a client that floods the slow log can push entries out before the poll.
- **No account** for connections closed before the poll, for Unix-socket clients, or for full synchronizations; attribution through `CLIENT LIST` is best effort.
- **No database** for log entries on a server with keys in several databases; **no row count** for any event.
- **Not measured**: whether `redis-cli --rdb` increases `sync_full` (to verify per version); a `--rdb` transfer that ended before the poll gives no client address.
- **Redis 6.2 opt-in**: `ACL LOG` entries have no id before Redis 7.2, so they are keyed by identity and position in the 128-entry ring, and a grown `count` is reported as its delta; an eviction from the ring shifts the positions, so entries can be reported again or missed (#239 re-review N2).
- **Cluster and replicas**: each log is per node; reads on nodes that are not declared targets are not seen.
- **Excluded sources**: `MONITOR` (every argument, values included, and a throughput cost), keyspace notifications (writes only, through pub/sub) and `LATENCY` (no client, no key).
- **Not yet tested end to end** nor in the load harness: no Redis / Valkey target in `e2e/` and no load run yet (ROADMAP P9-D).

## Microsoft SQL Server Discovery

What the SQL Server connector does, as implemented in phase 9 (P9-A lot 1, #242 and #243, [ADR-0051](adr/0051-sqlserver-connector.md) and its refinement of 2026-10-14). **In development, not released yet**: merged on `dev`, not in 0.7.0. Measured on SQL Server 2022 Express ([phase 9 engine facts](measurements/phase9-engine-facts.md)) and tested on 2019, 2022 and 2025 Express. The account is in [05-security.md](05-security.md#microsoft-sql-server-connector); the `agent.yaml` block in the [user guide](10-user-guide.md#microsoft-sql-server-targets).

### Scope and sampling

- **One declared `host` / `port`** (default 1433), over TCP with TLS; no SQL Server Browser, no routing, no named-instance resolution (I5). SQL logins only.
- **Databases**: the user databases the login can access and that are online (`master`, `model`, `msdb`, `tempdb`, `distribution`, `SSISDB`, `ReportServer*`, snapshots and distributor databases left out), at most 1 024, filtered by `sqlserver.databases` and the job's `databases`, rotated per scan. At most `sqlserver.max_tables` user tables per database (default and maximum 16 384); the rest counts 1 in `skipped_limit`.
- **Session**: autocommit at `READ UNCOMMITTED` with `LOCK_TIMEOUT 2000`, settings read back after login. Per table one statement: `TOP (n)` with `OPTION (MAXDOP 1)`, and `TABLESAMPLE SYSTEM` for a table estimated above 20 × `n` and 1 000 rows (never on a memory-optimized table). The per-table deadline is the job's statement timeout, **bounded at 30 s**. At most 32 MiB of sampled values per table, checked value by value (the statement is then stopped, `skipped_limit`). Each unit of work is paced ([ADR-0035](adr/0035-discovery-pacing.md)). `READ UNCOMMITTED` means the agent takes no shared row or page lock and never waits for a writer, but an uncommitted value can be sampled.
- **Column types sampled**: `char`, `varchar`, `nchar`, `nvarchar` and `text` / `ntext` (cut to 4 000 characters), `int`, `bigint`, `decimal`, `numeric`, `date`, `datetime`, `datetime2` and `smalldatetime` (alias types as their base type). **Not sampled**: `binary`, `varbinary` and `image`, `money` and `smallmoney`, `float` and `real`, `uniqueidentifier`, `tinyint`, `smallint`, `bit`, `time`, `datetimeoffset`, `timestamp` / `rowversion`, `xml`, `sql_variant`, `json`, `vector`, CLR types (`hierarchyid`, `geometry`, `geography`, user CLR types), column sets and graph columns. A value stored in a type that is not sampled (a card number in a `float`, an identifier in `binary`) is not found.
- **At most 512 columns per table**: the columns past the 512th sampled one are not read, and the table counts 1 in `skipped_limit` as well as in `objects_sampled`.
- **Column permissions**: a column the account cannot `SELECT` (column `GRANT` or `DENY`) is left out of the statement. A table the account cannot read at all counts in `skipped_not_readable`; a table whose readable columns are all of types not sampled counts in `skipped_unsupported`.
- **Not sampled by design**:
  - **views** and **synonyms**: counted in `skipped_unsupported`, and views in the note `coverage.views_not_sampled`;
  - **external tables** and **Stretch** tables: `skipped_remote`, never read (I5); FileTables are not listed;
  - **computed columns**: never selected, counted in the note `coverage.computed_columns_not_sampled`;
  - **Always Encrypted columns**: never selected (the server holds ciphertext only), counted in the note `coverage.encrypted_columns`;
  - columns under **dynamic data masking** are sampled as the agent's account sees them, masked, and counted in the note `coverage.masked_columns`.
- **CAS store guard**: as on the other SQL engines ([below](#cas-store-guard-postgresql-mysql--mariadb-mongodb-openldap)); a ticket registry is counted (`type` only), never sampled.

### Schema-stability locks (ADR-0051 obligation L9)

`READ UNCOMMITTED` takes no shared data lock, but every sampling statement still holds a **schema-stability (Sch-S) lock** on its table for its duration. A schema-modification (Sch-M) lock waits for it: `ALTER TABLE`, an offline index rebuild or a partition switch on a table the agent is sampling waits up to the per-table deadline (30 s at most), and statements queued behind that DDL statement wait too. `LOCK_TIMEOUT 2000` makes the agent give up when it is the one waiting (error 1222 skips the table, `skipped_error`), not when it holds the lock. Schedule scans outside maintenance windows that run such DDL, or lower the scan's statement timeout.

### Row-level security and the opt-in

No table-level flag tells a table with a row-level security policy from one without, and the minimal account cannot see the policy catalog. **Without the local opt-in `sqlserver.rls_visibility: view_definition` (database `VIEW DEFINITION` in each monitored database, proven effective and not hidden by a `DENY` at database or server scope), Discovery samples nothing**: every table of the database is skipped (`skipped_row_level_security`) and `check()` reports `coverage.rls_not_verifiable` from the first heartbeat. The opt-in makes the module bodies of the database (procedures, views, functions, triggers) readable by whoever holds the agent's credentials; the connector itself never reads them.

### TLS modes and the "strict seen" mark

`sqlserver.tls` is `auto` (default), `strict` (TDS 8.0, TLS from the first byte) or `mandatory` (TDS 7.x, the TLS handshake inside `PRELOGIN` packets, then the whole session encrypted); there is no unencrypted mode ([ADR-0051](adr/0051-sqlserver-connector.md) decision 2 and refinement item 3). On Linux, strict encryption exists from SQL Server 2025 only (`network.forcestrict`): against 2019 and 2022, `auto` falls back once to `mandatory`, then connects in `mandatory` directly for an hour before trying strict again (in memory only), and `strict` fails with the local detail "strict encryption not available on this server". Use `tls: mandatory` for SQL Server 2022 on Linux. Tested in CI on each version (`agent-sqlserver` on 2022, the engine matrix on 2019, 2022 and 2025 with strict forced).

Once `auto` has completed one authenticated strict session with a target, the agent persists a **"strict seen" mark** and from then on never falls back to `mandatory` for that target (a strict failure fails the connection):

- File: `<state_dir>/sqlserver-strict-seen/<target_id>`, mode `0600` in a `0700` directory, holding the target's declared host and port. A mark for another host or port, a file that is not private or not owned by the agent's user, or one larger than 4 KiB counts as "not seen".
- The mark is also **held in memory** by the running agent, so deleting the file alone changes nothing until the agent restarts.
- Cleared, on disk and in memory, at the next connection attempt of the target once its `tls` is set to `strict` or `mandatory` (after an agent restart or a configuration reload), or made void by changing its `host` or `port`.
- To clear it by hand (for example after moving the server to a version or configuration without strict encryption while keeping `tls: auto`): stop the agent, delete the file and start it again; or set the target's `tls` to `strict` or `mandatory`, let it attempt a connection, then set it back to `auto`. The next connection in `auto` tries strict first again, with the one fallback. Until then, the target is reported unreachable with a TLS-stage detail.

**How a TLS problem shows in the console**: there is no TLS-specific failure code. The target is unreachable with `target_unreachable` (a certificate that does not verify, the self-signed fallback certificate, strict encryption not available), `timeout`, or `unsupported` (a server that does not encrypt the whole session, a malformed `PRELOGIN`), together with the note `check.stage_failed` labelled `stage_tls`; that label is the reliable sign. The exact reason is in the agent's log.

### What a stolen agent credential reads

Measured with the minimal account, beyond the tables it is granted:

- **Always Encrypted key metadata**, through `public`'s default `VIEW ANY COLUMN ENCRYPTION KEY DEFINITION` and `VIEW ANY COLUMN MASTER KEY DEFINITION`: the encrypted column encryption key values (`sys.column_encryption_key_values`) and the column master key paths (`sys.column_master_keys`). The keys stay encrypted by the column master key, which is outside the server. `check()` accepts these two permissions only when they come from `public`; granted to the agent's login, user or roles they are reported as `privilege.beyond_select`.
- **Linked servers' `sys.servers.data_source`** (host names of linked servers; `provider_string` was empty in the measurement and is never read by the agent).
- With the RLS opt-in: the module bodies of the monitored databases (`sys.sql_modules.definition`) and the security policies.
- Not readable: password hashes of other logins, credentials, linked logins, keys and certificates, logon triggers, `msdb` mail and proxy tables, other sessions.

## Microsoft SQL Server Audit

*In development (P9-A lot 2, #247, and lot 3, #249; [ADR-0051](adr/0051-sqlserver-connector.md) decision 6, its refinement of 2026-10-14, option (a'), accepted on 2026-10-15, and its Extended Events refinements accepted on 2026-10-15 and 2026-10-16), not released yet. Measured on SQL Server 2019 (15.0.4500.2), 2022 (16.0.4305.5) and 2025 (17.0.5015.4, strict encryption), all Express, with the dev audit and Extended Events session (`dev/sqlserver/initdb/30-audit.sql`). The SQL Server Audit source comes first below; the Extended Events source has its own subsections from [Extended Events: source and grants](#extended-events-source-and-grants).*

### Source and level

The agent reads the operator's **server audit** (`FILE` target) through `sys.fn_get_audit_file` over its own connection, `audit_source` `sqlserver_audit`. The operator creates the audit and its specifications; the agent never creates, alters, starts or stops them. `agent.yaml`: `sqlserver.audit: {source: sqlserver_audit, audit_name: <name>}`; `source: auto`, the default, reads the named audit too, and with both `audit_name` and `xe_session` named it applies the preference rule below.

**Source preference** (ADR-0051 decision 6, one rule shared by `check()` and the stream): SQL Server Audit when it is usable, that is SQL Server 2022 or later, its two grants held and the named `FILE` audit found; otherwise the Extended Events session named in `xe_session` ([below](#extended-events-source-and-grants)). A found audit that fails a later proof (disabled, filtered, a missing specification) stays the source, at Limited or None: it does not hand over to the session. The rule is applied again at each 5-minute re-probe; a stream whose choice changes ends and is restarted on the other source, and that switch is a gap (`audit.records_dropped`, Limited for 24 h).

Grants (refinement item 1, option (a'), SQL Server 2022 and later): `GRANT VIEW SERVER SECURITY AUDIT TO databastion_agent; GRANT VIEW ANY SECURITY DEFINITION TO databastion_agent;` in `master`. `VIEW SERVER SECURITY STATE` is not needed: the audit's own start and stop records prove its restarts (below). While an Audit stream reads the target, these two permissions are expected; otherwise `check()` reports them as `privilege.audit_grant_without_audit`, like any other Audit permission the agent does not use (`VIEW SERVER SECURITY STATE` always; the Extended Events grant, `VIEW SERVER STATE` on 2019 or `VIEW SERVER PERFORMANCE STATE` on 2022+, unless an Extended Events stream uses it; `VIEW SERVER STATE` on 2022+).

**Partial** when all hold; never Full. When one of the first two fails, or the named audit is missing, the level is **None**. Otherwise the level is **Limited** when only the last proof fails (no record yet, or no stream running) or when a record was read in the last 24 h, and **None** when another proof fails and no record was read in the last 24 h:

| Proof | Read from | When it fails |
|---|---|---|
| SQL Server 2022 or later, `VIEW SERVER SECURITY AUDIT` held, the account outside the refusal list | version, `fn_my_permissions` | None: `audit.sqlserver_audit_needs_control_server` (2019), `audit.source_not_configured` (no grant), `privilege.refused` |
| The audit catalogs visible | `VIEW ANY SECURITY DEFINITION` held | None, `privilege.not_evaluated` (`view_any_security_definition`): the audit's folder, which the poll needs, cannot be read either |
| The named audit is a `FILE` audit, enabled, without `WHERE` predicate | `sys.server_file_audits` (whether `predicate IS NULL`, never the predicate's text) | `audit.source_not_configured` (missing or disabled), `audit.server_audit_filtered` |
| Reads logged in every monitored database | an enabled server specification with `SCHEMA_OBJECT_ACCESS_GROUP`, else per database an enabled database specification with it or `SELECT` on the database by `public` (counted on the server) | `audit.reads_not_logged` (count of databases) |
| Audit changes logged | `AUDIT_CHANGE_GROUP` in an enabled server specification | `audit.audit_changes_not_audited` |
| No gap in the last 24 h | the stream: a file lost to rollover, the audit recreated (new GUID) or restarted | `audit.records_dropped`, Limited for 24 h |
| A record read in the last 24 h, by a stream that still runs | the stream (any record, the agent's own polls included) | `audit.partial_pending_first_record`, Limited; Limited at most while no stream runs |

Always noted for this source: `audit.log_without_row_counts` (`affected_rows` and `response_rows` are always 0 on boxed SQL Server). Not required for Partial: `FAILED_LOGIN_GROUP` (`audit.failed_logins_not_audited`). With `ON_FAILURE = CONTINUE`, the counter of records lost to a failing target lives in `sys.dm_server_audit_status`, which this grant set does not read: `privilege.not_evaluated`, with the label `other` until the contract has one for it.

### What the Audit grants expose (measured)

With `VIEW SERVER SECURITY AUDIT` and `VIEW ANY SECURITY DEFINITION` (2022 and 2025, the same results): `fn_get_audit_file` reads **any** `.sqlaudit` file the server's service account can read (measured in P9-D), which is why the poll's file pattern is built from the catalog and written as a literal of the poll's text, never a parameter; the audit and specification catalogs; the names (not the hashes: `password_hash` stays `NULL`) of every login, server principals and role memberships; certificate and symmetric key metadata of `master` (`sys.certificates`, `sys.symmetric_keys`, `sys.key_encryptions`, whose `crypt_property` stays `NULL`). Not opened: any statement-text view (`dm_exec_query_stats`, `dm_exec_sql_text`, cached plans, Query Store, `fn_xe_file_target_read_file`, `dm_xe_session_targets`: refused), other sessions or connections, `sys.dm_server_audit_status`, credentials, linked logins, module bodies, security policies, logon triggers (`sys.server_triggers` stays empty: logon triggers stay not evaluated, `privilege.not_evaluated` `logon_trigger_probe`), and `msdb`'s mail, proxy and job tables. `VIEW SERVER SECURITY STATE` alone or with the two (option (a)) opens `sys.dm_server_audit_status` only, no statement text and no other session.

### Polls and position

- One `sp_executesql` RPC per read, whose text is constant for a given catalog state (the file pattern `<folder><name>_<GUID>_*.sqlaudit`, built from the catalog's folder, name and GUID, is a literal of the text; an audit name with `/` or `\` is refused); the file, the buffer offset and the row bound are parameters. At most 500 records per read (halved after a response over 12 MiB), each turned into a record as its row arrives; a full read is followed by another, for at most 20 s per cycle (and 20 reads while the first start skips the audit's history); then the stream waits for the poll interval. Each statement has a 15 s client deadline. The proofs are read again every 5 minutes, and at once after an `AUDIT_CHANGE_GROUP` record.
- **Position**, persisted: the file and offset of the last buffer read whole, how many records of the next buffer were handled (at most 500; a larger buffer's rest is dropped, a gap), and the file pattern it belongs to. A read from `(file, offset)` starts **after** that buffer (measured), so a buffer a full read may have cut is read again and its handled records skipped.
- **Gaps**: another file pattern (the folder moved, the audit renamed or recreated: another GUID) is another file set, read from its start; a position the server refuses (error 33225) in the same set (the file rolled over) restarts at the oldest file, leaving out what was read by the files' order (partition and timestamp of the name) and offset, never by path; an unreadable cursor file starts at the end; the audit's own `AUDIT_SESSION_CHANGED` records (`AUSC`) after the position mean the audit stopped or started (measured: written at `STATE = OFF` on 2022 and 2025, at `STATE = ON` on 2022 but not on 2025, and at every service start, clean or after a kill; no record at a clean shutdown); a recreated audit (another GUID) restarts its file set. Each is `audit.records_dropped` and Limited for 24 h.
- The first start skips the audit's history (no replay).

### What is kept

- One event per statement: the records of one statement (one per object of its permission checks: a join gives one record per table, a catalog view several, measured) are grouped by session, transaction, time, action and text. Objects come from the records, never from the text; internal helpers every catalog view also checks (`master.sys.syspalvalues`, `syspalnames`, `objects$`) are left out. Statement texts longer than 4 000 characters are rebuilt from their parts (`sequence_number`) up to 64 KiB, then cut.
- **Statement text never leaves the agent.** For reads and writes it goes through the T-SQL mode of the query analyzer (`classifiers::query::tsql`): every literal kept without content, comments removed (they nest), `[…]` identifiers, `"…"` ambiguous (kind only where a name is read), and every `EXEC` argument a value. DDL, DCL and failed logins never have their text analysed. Password-bearing statements (logins, users, application roles, credentials, external data sources, keys and certificates, `EXEC sp_addlogin`, `sp_password`, `sp_addlinkedsrvlogin`, `sysmail_*_account_sp`…) keep their class only, from their first tokens; measured: SQL Server Audit writes `PASSWORD = '******'` itself, which the agent does not rely on.
- Actions: `SL`, `RC`, `EX`, `DBCC`, `BA` / `BAL` reads (an `EXEC` names its procedure); `IN`, `UP`, `DL` writes; `CREATE` / `ALTER` / `DROP` of principals and credentials, grants, role memberships, password changes DCL; other `CREATE` / `ALTER` / `DROP` and `RESTORE` DDL; `LGIF` failed logins (the name tried fingerprinted; a connection closed before its login packet, error 17830 with no name, such as a TCP health check, is dropped); `LGIS` connections. Refused reads are reported as reads (a permission-denied `SELECT` leaves a record, `succeeded = 0`); a read refused by a missing **server** permission leaves no record at all (measured in P9-D).
- **Always reported** (`audit.configure` filters never drop them): reads of the statement-text objects (`dm_exec_sql_text`, `dm_exec_input_buffer`, `dm_exec_query_stats`, cached plans and query plans, `fn_get_sql`, Query Store texts and plans, `fn_get_audit_file` and 2025's `fn_get_audit_file_v2`, `fn_xe_file_target_read_file`, `dm_xe_session_targets`, `fn_trace_gettable`, `DBCC INPUTBUFFER`, `sp_readerrorlog` / `xp_readerrorlog`, `msdb.dbo.sysjobsteps`, `sysmail_mailitems`, `fn_sqlagent_jobsteps`), of the credential-bearing objects (`sql_logins`, `syslogins`, `LOGINPROPERTY`, credentials, linked logins, `sys.servers`, external data sources, key and certificate catalogs, `CERTPRIVATEKEY`, `PWDCOMPARE`, `msdb` mail, proxies and SSIS packages, `fn_getproviderstring`…) and of value-bearing statistics and storage (`DBCC SHOW_STATISTICS`, `dm_db_stats_histogram`, `DBCC PAGE`, `fn_dblog` and its variants, `dm_db_page_info`, `DBCC CLONEDATABASE`), whether named by the records or in the text; dynamic SQL in text, calls of user functions (a schema-qualified call outside the `sys` built-ins of 2019, 2022 and 2025), four-part names and remote data access (these name `*`); cut, unreadable or ambiguous texts (`*`); calls of password-taking functions; backups; and changes of the audit itself (a `ddl` event naming the audit or specification).

No `volume.*` signal: the source has no row count.

### The agent's own statements

A record is the agent's own only when it comes from one of the agent's **own sessions** within its lifetime: every session reads, right after its login, its `@@SPID`, its `login_time` and the client address the server sees; its lifetime runs on the server's clock to its clean close (no grace) or, for a lost connection, to the loss plus the statement timeout and 5 s. Sessions are kept 48 h after their end and persisted with the stream, so a restarted agent still recognizes them (a session open at a crash is closed at the restart). Both principals (`server_principal_name` and `session_server_principal_name`: never under `EXECUTE AS`) must be the agent's login, the client address the session's, and the application name `databastion-agent` when logged. Then only:

- its exact constant statements and catalog templates filled with quoted names (`check()`, Discovery's catalog reads, the Audit proofs), plus the statement `sys.fn_my_permissions` runs inside the server (measured text on 2022, 2025); the one-bit `password_hash` probe is the only statement reading a credential-bearing object that is left out;
- with a **credit** of that session for exactly its text, whose window (on the server's clock) holds the record's time: sampling and CAS ticket counts (charged the whole per-object own-read budget, as on the other sources without row counts) and the stream's polls (their records name `fn_get_audit_file`); a credit covers the records of one execution only. Poll credits are persisted, so the last polls before a restart are recognized.

Its writes, DDL and DCL, anything else it reads, and the same login from any other session are reported. Measured in the integration test on 2019 (no source), 2022 and 2025: about a hundred exact-text statements, ten sampling statements and every poll of a test run left out, and the agent's login from a session that is not its own reported, its own constant statements and the server's internal `fn_my_permissions` statement included.

Credits (security review of P9-A lot 2, L3): a credit's window is on the server's clock, from 1 s before the statement was sent to its timeout plus 5 s, and is checked against the record's `event_time`; it covers the records of one execution (transaction id; a record without one consumes it once). A session still open at the stream's last save ends, after an agent restart, at that save plus 35 s.

### Known limits

- **SQL Server 2019 has no SQL Server Audit source** (`CONTROL SERVER` would be needed): Audit there uses the [Extended Events source](#extended-events-source-and-grants), and a 2019 target that names only `audit_name` reports None (`audit.sqlserver_audit_needs_control_server`).
- **No row count**: no `volume.*` signal, a score of 0 in the console; incidents come from signals, objects and principals.
- **Ownership chaining**: a read through a view or a procedure owned by the table's owner is recorded on the view or procedure only; a procedure reading statement-text objects (`sp_WhoIsActive`) is reported by its own name, not as an always-reported read.
- **Reads refused by a missing server permission leave no record** (P9-D), and so do statements refused before any permission check (feature switches, compile errors).
- **History**: the first start skips what the audit already holds; a restart of the agent resumes from the persisted position. A first start with a large backlog can count old records as dropped: see the [first-start floor](#extended-events-polls-and-position), which both sources share.
- **Restart residual**: sampling credits are not persisted, so a Discovery sample whose record is read only after an agent restart is reported (loud); a session's lifetime after a crash ends at the restart.
- A statement whose records fall in two reads (a full read cut inside it) gives two events.
- **Password-bearing calls in a batch**: only the call's own `EXEC` record keeps the class (DCL, kind only); a read or write record of a text that also calls a password-taking procedure keeps its action, names `*` and is always reported.
- **Own-session residuals**: the records of a session's last statement were stamped up to 2.5 ms after its computed clean end (2022, about one run in five; re-measured in #249 on 2019, 2022 and 2025: the audit's `event_time` never fell outside two `SYSUTCDATETIME()` reads around a statement; Windows not measured), so the records of a session's last statement are matched up to 250 ms after its clean end, that statement's exact text only; a long-lived session's end drifts with the server's clock against the agent's (fail closed: its last records may be reported); a session's computed end is late by at most one round trip (the agent's clock runs from before its read-back); if the server's clock goes backwards, an ended own session's window can cover a later session reusing its SPID (the principals, the client address and the exact text or a credit must still match).
- **Isolation mode**: the core's save after every record is not followed (the position is a file buffer); panics are caught per row and per statement.
- The `STATE = ON` start record was not seen on 2025 (the `STATE = OFF` records were): an audit stopped and started is still detected through the stop records.
- **Not measured**: Windows servers, the Developer edition, ownership chaining, `xp_dirtree` / `xp_fileexist` with a remote path, `sp_execute_external_script`, `sp_invoke_external_rest_endpoint`, `CREATE CREDENTIAL … SECRET` in the audit; not yet tested end to end nor in the load harness.

### Extended Events: source and grants

*P9-A lot 3, #249; [ADR-0051](adr/0051-sqlserver-connector.md) decision 6, its Extended Events implementation notes and its refinements of 2026-10-15 and 2026-10-16 (accepted). Measured on SQL Server 2019 (15.0.4500.2, `mandatory`), 2022 (16.0.4305.5, `mandatory`) and 2025 (17.0.5015.4, strict), all Express, with the dev session `databastion_xe` ([measurements](measurements/phase9-engine-facts.md)).*

The agent reads an operator-created **Extended Events session** with an `event_file` target through `sys.fn_xe_file_target_read_file` over its own connection, `audit_source` `sqlserver_xevents`. It is the only Audit source on SQL Server 2019, and the source on 2022 and 2025 when SQL Server Audit is not usable ([source preference](#microsoft-sql-server-audit)). The operator creates and starts the session; the agent never creates, alters, starts or stops it (the event-session rights are on the refusal list). `agent.yaml`: `sqlserver.audit: {source: sqlserver_xevents, xe_session: <name>}` (`xe_session` required), or `source: auto` (the default) with `xe_session`, alone or with `audit_name`. The file pattern of the poll comes from the session's current file as the server names it, never from `agent.yaml`. Setup: [user guide](10-user-guide.md#sql-server-audit-through-extended-events).

Grants, in `master`: `VIEW SERVER STATE` on SQL Server 2019, `VIEW SERVER PERFORMANCE STATE` on 2022 and later. Without it the level is None (`audit.source_not_configured`, the missing grant in the agent's log). While an Extended Events stream reads the target, the grant is expected; otherwise `check()` reports it as `privilege.audit_grant_without_audit`. On 2022 and later, `VIEW SERVER STATE` is not the source's grant and is reported the same way.

**What these grants expose.** Measured on 2022 with each of the two grants: **every statement text on the server, with its literals**, through the statement-text views (`sys.dm_exec_query_stats` with `sys.dm_exec_sql_text`, cached plans and query plans, Query Store texts, `DBCC INPUTBUFFER`); **the Extended Events files** through `sys.fn_xe_file_target_read_file`, whose `rpc_completed` events hold the parameter values of every RPC (measured); and the other sessions in `sys.dm_exec_sessions`. Which paths `fn_xe_file_target_read_file` accepts beyond the sessions' folders was not measured. A stolen agent credential with this grant therefore reads what every client sent to the server, the values of parameterized queries included. That is the cost of Audit on SQL Server 2019, comparable to `pg_read_all_stats` on PostgreSQL. The agent's own use is bounded: its reads of these objects are exact constant texts from its own sessions, and the same reads from any other session, the agent's login included, are reported as always-reported reads. Grant it only where Audit runs, and protect the password like the data.

### Extended Events: proofs and level

| Proof | Read from | When it fails |
|---|---|---|
| The grant for the version held, the account outside the refusal list | `fn_my_permissions` | None: `audit.source_not_configured`, or `privilege.refused` |
| The named session exists and is running, with an `event_file` target whose current file name gives a file pattern | `sys.dm_xe_sessions`, the target's status (its current file only) | None, `audit.source_not_configured` |
| `sql_statement_completed`, `sp_statement_completed` and `rpc_completed`, each with the actions `server_principal_name`, `session_server_principal_name`, `client_app_name`, `database_name` and `session_id`; statement collection on for the first two | `sys.dm_xe_session_events`, their actions and `collect_statement` columns | `audit.xe_events_missing` (count of what is missing) |
| No predicate on those three events | `sys.dm_xe_session_events` (whether a predicate exists, never its text) | `audit.xe_session_filtered` |
| The session catalogs read completely | the reads above | not proven (the agent's log says which read failed or was cut) |
| No gap in the last 24 h | the stream ([below](#extended-events-polls-and-position)) | `audit.records_dropped`, Limited for 24 h |
| An event read in the last 24 h, by a stream that still runs | the stream (any event, the agent's own polls included) | `audit.partial_pending_first_record`, Limited; Limited at most while no stream runs |

**Partial** when all hold; **never Full**. When one of the first two fails, the level is **None**. Otherwise the level is **Limited** when only the last proof fails, or when another proof fails but an event was read in the last 24 h, and **None** when another proof fails and no event was read in the last 24 h.

Noted, without effect on the level:
- `audit.xe_causality_off`: the session has `TRACK_CAUSALITY = OFF`. Statements are then grouped into requests by session and event order, and the [statistics exclusions](#extended-events-statistics-builds) of cases 1 and 2 do not apply.
- The **retention mode** (`EVENT_RETENTION_MODE`: `ALLOW_SINGLE_EVENT_LOSS`, the default, `ALLOW_MULTIPLE_EVENT_LOSS` or `NO_EVENT_LOSS`) is written in the agent's log only. It does not cap the level: a loss that happens shows in the drop counters, which the gap proof reads. A lossy mode is one reason Full is never reported.
- A session without `error_reported` (error 18456) does not record failed logins: the agent's log says so. `audit.failed_logins_not_audited` is not sent for this source, because its registry text names SQL Server Audit's `FAILED_LOGIN_GROUP`; a source-neutral text is a [phase 9 follow-up](ROADMAP.md#phase-9-follow-ups) (P9-C).
- On 2019, a target that also names `audit_name` keeps `audit.sqlserver_audit_needs_control_server` next to the Extended Events level.
- `audit.log_without_row_counts` is not noted: this source has row counts.

### Extended Events: polls and position

- One `sp_executesql` RPC per read, whose text is constant for a given catalog state: the file pattern `<folder>/<stem>_<n>_*.xel`, built from the target's current file, is a literal of the text; the file, the buffer offset and the row bound are parameters. A current file of another form, or one whose folder or stem holds `*`, `?` or a control character, or longer than 260 characters, gives None (`audit.source_not_configured`).
- **Exact reads**: `event_data` is converted to bytes on the server and read as 17 `varbinary(8000)` slices, joined and decoded once, and checked against its size. No `max` column is used, so the session's `TEXTSIZE 8000` cannot cut an event without a sign (measured on 2019), and the result does not depend on the server's collation. The bound is **64 Ki characters (128 KiB of UTF-16) per event**; a larger event comes without its XML.
- The event XML is read by a bounded reader: no DTD, only the five predefined entities and character references, depth 8, 1 024 elements, 8 attributes of 256 bytes each, a closed set of fields. RPC parameter values, batch texts and error messages are never stored.
- At most 500 events per read, halved after a response above 12 MiB, with `OPTION (MAXDOP 1)`. A read starts after a buffer, and one buffer can hold hundreds of events (up to 943 measured on 2022): the events of a buffer already handled are skipped on the server (`OFFSET … FETCH`), so no event is read twice. The proofs are read again every 5 minutes.
- **Position**, persisted (cursor `sqlserver_xevents`): the file and offset, the buffer being walked and its handled count, the file pattern, and the session's `create_time`. Files are ordered by the key in their name (timestamp, then `<n>`), never by path.
- **Gaps**, each `audit.records_dropped` and Limited for 24 h: the session's `create_time` moved by more than 500 ms (the session was stopped and started; the value jitters by up to 10 ms between reads of one start, measured on 2019 and 2025); `dropped_event_count` or `dropped_buffer_count` grew; a position the server refuses (error 25722, an offset that is not a buffer; 25717, a file gone to rollover), after which the stream restarts at the oldest file and leaves out what it had read by file key and offset; another file pattern (the folder or file name changed), read from its start; an unreadable cursor; a switch from or to SQL Server Audit; a buffer holding more than 1 000 000 events.
- **First start**: the stream skips the session's history (no replay). Events stamped before the first start, plus the 20 ms clock skew below, are history and are not reported, even when they reach the file late. This **floor is bounded**: the history phase lasts while the source's delivery delay has not passed since the first start, measured on the agent's clock (the session's `MAX_DISPATCH_LATENCY` plus 20 ms, read from `sys.server_event_sessions`; 5 minutes for `INFINITE` or when it cannot be read; never more than 5 minutes). After that, an event stamped below the floor is not reported and is counted as dropped (`audit.records_dropped`, with a warning in the agent's log). The floor ends after a read that reached the end of the files and started once the delay had passed, and at once if the agent's clock went back. Within the delay, a server clock stepping back below the floor is not told apart from late history. SQL Server Audit has the same floor, with its `QUEUE_DELAY`.
- **Known residual of the floor**: on a first start whose files already hold a large backlog, the stream skips it in bounded reads (at most 20 per cycle), and the old events it reads after the delivery delay are counted as dropped: the target shows an `audit.records_dropped` note with their count for 24 h. The level is unchanged (no gap is recorded), and none of those events is reported. The same holds for SQL Server Audit. An order-based history boundary, so that a normal first start reports no drop however large its backlog, is a [phase 9 follow-up](ROADMAP.md#phase-9-follow-ups).

### Extended Events: what is kept

- **One event per statement**: only `sql_statement_completed` and `sp_statement_completed` produce access events. `rpc_completed` and `sql_batch_completed` are context only and their texts are dropped when parsed (an `rpc_completed` text holds the parameter values, measured). An `rpc_completed` of a user procedure (not `sp_executesql`, `sp_prepexec`, `sp_execute`, `sp_prepare`, `sp_unprepare`, `sp_reset_connection` or `sp_cursor*`) adds the procedure as an object to the statement events of its request, **only when both are in the same read** (requests told apart by causality activity, else by session and event order).
- Kept per event: `row_count`, the statement text (for the analysis only, zeroized, never sent), the five actions, and the causality activity. `client_hostname` is not collected. The source records no client address.
- **Objects come from the statement text**, not from the server's catalog: the T-SQL analyzer's relation pass reads the names after `FROM`, `JOIN`, `APPLY`, `INTO`, `UPDATE`, `DELETE`, `MERGE … USING` and the procedure of an `EXEC` (parenthesized join groups and `FOR SYSTEM_TIME` included; common table expressions, aliases, table variables and `#temp` tables left out), in the database of a three-part name or the event's `database_name`. **The event names `*` and is always reported whenever the text may not name every object**: an unknown token or a call that is not a rowset built-in in a table position, `READTEXT`, more than 64 names, or a text that is cut, unlexable, ambiguous (`"…"` read both ways), dynamic SQL, a user function call, a four-part name, remote data access or a password-taking function. **DDL and DCL** keep their kind and name `*`, always reported (this source has no object field). A statement that names no table and has none of these flags (`SET`, `PRINT`, `BEGIN TRAN`, a `SELECT` of constants) is no event. A write whose targets are only table variables or `#temp` tables is a read of its sources. A grammar-driven property test checks that every generated table is named or the list is marked not complete.
- **Placeholders**: Extended Events record some statements as a comment instead of their text (measured on 2019 and 2022): `-- CREATE LOGIN`, `-- CREATE CREDENTIAL`, `-- sp_addlogin` (password-bearing: DCL), `-- SELECT` (a read calling a password-taking function: a read), `-- Encrypted text` (each statement of an encrypted module: a read). Only those words are read; the event names `*` and is always reported. No fake password marker appeared in any event.
- **Unreadable events**: a statement event whose row cannot be read (slices that do not add up to its size, a lone surrogate, malformed XML, a panic of the reader) or that is above the 64 Ki-character bound is never dropped: it is a read of `*` by an unidentified principal, always reported. A malformed row of another event type, or a row without its name, position or time, is dropped and counted (`audit.records_dropped`).
- **Failed logins**: from `error_reported` with error 18456 (also 18452, 18470, 18486, 18487 and 18488 when the session records them). The server writes two events per failure (measured), **counted once**; the name tried is taken from `session_server_principal_name` and fingerprinted; the message is never read.
- **Always reported**: the statement-text, credential-bearing and value-bearing objects listed for SQL Server Audit ([above](#microsoft-sql-server-audit), "What is kept"), here named from the text, backups, and the `*` cases above. Statements run inside procedures and functions produce their own `sp_statement_completed` events (ADR-0051 decision 6), so reads that ownership chaining hides from SQL Server Audit can show here; RPC calls of user procedures were not measured.
- **Signals**: `shape.full_table_read` (as for SQL Server Audit), `volume.large_result` (`row_count` above 10 000), `signature.bcp` (by client application name), `signature.backup_database` and `signature.remote_data_access` (from the text).
- **A refused `xp_cmdshell` is invisible**: an `EXEC master.dbo.xp_cmdshell` refused before it runs leaves no statement event (measured on 2019 and 2022), so it raises no `signature.remote_data_access` on this source.

### Extended Events: statistics builds

When a statement's compilation needs missing or stale statistics, the server builds them inside the caller's request: an `sp_statement_completed` `SELECT StatMan(…) FROM [schema].[table] …`, attributed to the caller, followed by one to three internal statements with an empty text. Counted, each first read of a column would also give a whole-table read with `shape.full_table_read` and always-reported reads of `*`. The exclusions below (ADR-0051 refinement item 4, refinements of 2026-10-15 and 2026-10-16) apply **only on the builds where users were shown unable to call `StatMan`** (error 195 for a minimal login and for `sa`, as a batch and inside `sp_executesql`): 15.0.4500.2, 16.0.4305.5 and 17.0.5015.4. On any other build they are off, and statistics builds are counted (a known duplicate).

- **The build** is left out when its whole text, complete, matches the server's statistics grammar token by token, and the same request holds a statement, reported or the agent's own, naming the same table in the same database.
- **Case 1, the build's internal statements**: an `sp_statement_completed` with an empty complete text, `object_type` `ADHOC`, both offsets 0, at the build's nest level minus one (the build being at nest level 2 or more), in the same causality activity as a left-out build, at contiguous sequence numbers, at most three. Requires `TRACK_CAUSALITY = ON` (no fallback on session order) and a drift fixture for the image.
- **Case 2, the agent's own builds on system base tables**: the agent's catalog reads make a new server build statistics on system base tables that none of its statements names. Such a build is left out only when it comes from one of the agent's own sessions (the full own-session rule), in the same causality activity as one of the agent's catalog reads (a closed list of its constant texts), on one of the measured tables `sys.sysschobjs`, `sysrowsets`, `syscolpars`, `sysobjvalues`, `sysidxstats`, `sysclsobjs`, `sysmultiobjrefs`, `syssingleobjrefs`, `sysprivs` and `sysdbreg`.
  - `sys.sysowners` and `sys.sysxlgns` hold credential columns and **stay off the list** (maintainer decision of 2026-10-16): a build on them stays reported as a read of the table by the agent's login, which a new server can show until those statistics exist.
  - `sys.sysguidrefs` (a build paired with the agent's audit-file proof, measured on a new 2022 server): its addition to the list was accepted by the maintainer on 2026-10-16 and is being added. Until that change is merged, such a build is reported.
- **Bounded deferral**: when a read holds one of the agent's case 2 builds whose pair is not in the read yet, the read ends just before the build, so that the next read starts at it and can pair it. Once per build, for at most the smaller of the session's `MAX_DISPATCH_LATENCY` and two poll intervals, never more than 60 s; after that the build is reported. Deferrals are kept in memory only (an agent restart can defer a build once more), never apply to another session's event, and at most 4 096 are remembered. A row of the cut buffer that could not be read can make the next read start one row early, so one event can be reported twice (never lost).
- **Without causality** neither case applies: the internal statements are reported as reads of `*`, always reported, and the agent's own builds as reads of the base tables by its login. **Asynchronous statistics updates** (`AUTO_UPDATE_STATISTICS_ASYNC = ON`) run in background sessions and are never left out (counted, noise).
- Measured on a new data volume of each image: the agent's own `check()` and Discovery gave 14 statistics statements left out and none of the agent's reported.

### Extended Events: the agent's own statements

The SQL Server Audit rules apply ([above](#the-agents-own-statements)): only from one of the agent's own sessions within its lifetime, both principals the agent's login, the application name `databastion-agent` when recorded, then only its exact constant texts or a credited sampling, ticket-count or poll text, without the client address, which this source does not record. A credit covers one event. The read of the session's status (`sys.dm_xe_session_targets`) is one of the exact texts. Measured on 2019, 2022 and 2025 strict: on a new server, the agent's own reads raise no event.

**Clock skew.** Extended Events' `timestamp_utc` ran up to 0.9 ms (2019), 3.5 ms (2022) and 2.8 ms (2025) after a `SYSUTCDATETIME()` read taken after the statement, the clock a session's end is computed on. After a **clean end**:
- the session's last statement is matched up to 250 ms after the end, for its exact text only (as on SQL Server Audit);
- the **last 16 texts the session sent** are matched up to **20 ms** after the end; the set is kept as keyed hashes, in memory only, never logged nor persisted;
- nothing else: a lost end (its grace only) and a session restored after an agent restart get no tolerance.

Residual: another session that reuses the SPID within those 20 ms, with both of the agent's principals and one of its last 16 texts, would be taken for the agent's.

### Extended Events: known limits

- **Lossy by design**: with the default `ALLOW_SINGLE_EVENT_LOSS`, the server may drop events under load; the agent sees a loss only through the drop counters (a gap). Never Full.
- **The session belongs to the operator**: a restart is detected through `create_time`, and a change of its events, actions or predicates at the next re-probe (every 5 minutes); events not recorded in between are not reported. A restart of a session that had run less than 500 ms since its previous start is not told apart from `create_time` jitter.
- **Names from statement text are chosen by the client**: an Extended Events object is a name a client wrote, not checked against the catalog. A client can write a name that does not exist or that looks like another object; the only protection of what is sent is the [ADR-0009](adr/0009-name-normalization-and-item-sanitization.md) normalization.
- **File pattern**: the poll reads `<folder>/<stem>_<n>_*.xel`. Another session whose files are named `<stem>_<n>_…` in the same folder would match it; give the session a folder of its own.
- **RPC procedure names** are attached to a statement only when its `rpc_completed` is in the same read.
- **A refused `xp_cmdshell` leaves no event**, and password-bearing statements leave only a placeholder or nothing.
- **Statistics builds** are counted on builds outside the allow-list, and asynchronous statistics updates always ([above](#extended-events-statistics-builds)).
- **First start with a large backlog**: old events read after the delivery delay are counted as dropped ([above](#extended-events-polls-and-position)).
- **Plan cache source** (`sqlserver_query_stats`, ADR-0051 open question 11): not implemented. With neither SQL Server Audit nor the session usable, the level is None.
- **Not measured**: Windows servers, the Developer edition, an `event_file` rollover while the agent reads, `sql_batch_completed`, RPC calls of user procedures; not yet tested end to end nor in the load harness.

## Known export signatures
| Tool | Observable signature | Engine |
|-------|---------------------|--------|
| `pg_dump` / `pg_dumpall` | `application_name = 'pg_dump'`, `COPY … TO STDOUT` on every table, `REPEATABLE READ` transaction | PostgreSQL |
| `COPY … TO` / `\copy` | Outbound `COPY` statement | PostgreSQL |
| `mysqldump` | `SELECT /*!40001 SQL_NO_CACHE */ * FROM`, `SHOW CREATE TABLE` in sequence, `FLUSH TABLES WITH READ LOCK` | MySQL / MariaDB |
| `SELECT … INTO OUTFILE` | Explicit statement | MySQL / MariaDB |
| `mongodump` / `mongoexport` | Tool's `appName`, unfiltered `find` over the whole collection | MongoDB |
| LDIF export / bulk `ldapsearch` | One-level or subtree search with an unselective filter (`(objectClass=*)`, presence tests), high `reqEntries` | OpenLDAP |
| `redis-cli --rdb`, a rogue replica | A full synchronization (`sync_full` grows) | Redis / Valkey |
| `redis-cli --scan` + `GET`, `KEYS *` | `KEYS` or a `SCAN` with a large `COUNT` in the slow log; fast reads are not logged | Redis / Valkey |
| `bcp out` | Application name `bcp`, `sp_describe_first_result_set` then whole-table reads | SQL Server |
| `BACKUP DATABASE`, `DBCC CLONEDATABASE` | `BACKUP_RESTORE_GROUP` record or statement | SQL Server |

As implemented: on PostgreSQL (P4-A) the agent uses the `application_name` and the whole-relation `COPY … TO STDOUT` parts of the `pg_dump` signature (not the `REPEATABLE READ` transaction) and the outbound `COPY` signatures; see [PostgreSQL Audit](#postgresql-audit). On MySQL / MariaDB (P4-B) the agent uses the `SQL_NO_CACHE`, `SHOW CREATE TABLE` and `FLUSH TABLES WITH READ LOCK` parts of the `mysqldump` signature, plus the dump tools' `program_name`, consistent snapshots and `LOCK TABLES`, as one heuristic `signature.mysqldump`, and the `INTO OUTFILE` / `INTO DUMPFILE` signature; see [MySQL / MariaDB Audit](#mysql--mariadb-audit). On MongoDB (P5-B / P5-C, #76) the agent uses the tools' `appName` (`signature.mongodump`, `signature.mongoexport`) and, separately, the whole-collection `find` shape (`shape.full_table_read`); see [MongoDB Audit](#mongodb-audit). On OpenLDAP (#79) there is no tool signature (`ldapsearch` declares nothing): the agent uses the search shape (`shape.bulk_search`) and the entry count summed over the pages of a paged search (`volume.large_result`); `slapcat` leaves no log record; see [OpenLDAP Audit](#openldap-audit). On Redis / Valkey (P9-B, not released yet) the agent uses full synchronizations (`signature.full_sync`), `KEYS` and large `SCAN` counts in the slow log (`shape.keyspace_enumeration`) and, on Valkey 8.1+, large replies (`volume.large_reply`); see [Redis / Valkey Audit](#redis--valkey-audit).

Signatures are easy to forge (`application_name` and `program_name` are chosen by the client). They are only **one** of the three signals; the volume × sensitivity combination remains the primary signal (see [02-architecture.md](02-architecture.md#exfiltration-detection-audit)). The console computes it from the row count the source reports ([ADR-0021](adr/0021-access-event-correlation.md)): an event without `rows` scores 0 and feeds no baseline (the contract has an optional `AccessEvent.bytes` since #60; only the Valkey large-reply source produces it, on `dev` since #239, and the console stores and shows it but does not use it in the score, #62), so on a source that gives no volume only signatures, shapes and object or principal conditions can raise an incident. Sensitivity is per object (table, collection), not per column.

| pgaudit (`read` class) | Medium: log volume | Restrict to sensitive roles and objects (`pgaudit.role`) |
| MariaDB `server_audit` | Low to medium | Filter out service accounts |
| `performance_schema` | Low | OK |
| MongoDB profiler level 2 | **High** | Avoid in production; level 1 with a suitable `slowms` |
| MongoDB profiler polling by the agent | Low to medium: each poll scans `system.profile` from the start in natural order (no `ts` index), bounded by `maxTimeMS` (at most 30 s); the server-side JavaScript walk of each entry's commands costs about 6 ms for a 50 KiB entry of nested arrays, less for ordinary ones, nothing for inserts, and is capped at 64 KiB per entry | A failing poll (for example a `maxTimeMS` expiry) is logged by the agent; with no entry read for 24 h the target shows the level None |
| OpenLDAP `accesslog` | Low | Purge with `olcAccessLogPurge` |
| Redis / Valkey slow log and command log, polled by the agent | Low: a poll reads at most 512 entries per log (capped at 4 MiB) every poll interval, plus one `CLIENT LIST` (capped at 4 MiB) when there are new entries; a lower `slowlog-log-slower-than` costs server memory per entry | Not measured in the load harness yet |
| Redis / Valkey Discovery | `SCAN COUNT 500`, `TYPE`, bounded reads of at most 16 members or 4 KiB per key, paced | Declare a replica as the Discovery node; not measured in the load harness yet |
| SQL Server Audit, polled by the agent | A `fn_get_audit_file` read of at most 500 records per read (each read scans the files after its position), the catalog proofs every 5 minutes | Size `MAXSIZE` and `MAX_ROLLOVER_FILES` so a file outlives a few poll intervals; not measured in the load harness yet |
| Discovery scan (every engine) | Paced: at most about `limits.discovery_duty_cycle_percent` % (default 1 %) of one core while a scan runs, one scan at a time per agent | Raise the duty cycle only where the server has spare cores, and size the scan's `max_duration_s` ([above](#discovery-load-on-the-monitored-database-every-engine)) |
