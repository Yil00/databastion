# Phase 10 Firebird facts (P10-B measurements)

Facts that [ADR-0060](../adr/0060-firebird-connector.md) (Firebird connector) marked "to verify", measured on 2026-10-25 against throwaway containers of the two pinned official images, run locally on loopback only. These results decide implementation details of P10-B; they do not edit the ADR. Where a result contradicts a decision, the "ADR impact" column states the refinement needed, for the maintainer and the docs-keeper to carry into the ADR.

Images: `firebirdsql/firebird` `5.0.4` (`sha256:1529560400fc7847f015c57fc9d70729c44d9a9d8f9000df19c5ce1950b4c202`, `LI-V5.0.4.1812`) and `4.0.7` (`sha256:456aeb748f6f70a4adbc910a2adc56f4d43270bcdf12808c47ca6e9603c6b17e`, `LI-V4.0.7.3271`), amd64, extracted from the Docker Hub layers and run under `chroot` as uid 84 (`firebird`) on loopback (`RemoteBindAddress = 127.0.0.1`), `WireCrypt = Required`, `ServerMode = Super` unless noted. Probe accounts were throwaway users with fake passwords; no value from any ground truth was used as a marker. Base `firebird.conf` keys were set from the measurements; the audit trace configuration logged statements, procedures, functions, triggers, BLR, connections and transactions with `time_threshold = 0` and `print_perf = true`.

Accounts (as ADR-0060 decision 4 names them): `min` (minimal variant: a reader role with `SELECT` on one table, granted `DEFAULT`), `ext` (extended variant: a role `SET SYSTEM PRIVILEGES TO SELECT_ANY_OBJECT_IN_DATABASE`, granted `DEFAULT`), `none` (a user with no grant), and `SYSDBA`.

## Obligation 4 — transactions

`SET TRANSACTION READ ONLY READ COMMITTED READ CONSISTENCY` → `RDB$GET_CONTEXT('SYSTEM','READ_ONLY')` = `TRUE`, `RDB$GET_CONTEXT('SYSTEM','ISOLATION_LEVEL')` = `READ COMMITTED`. **Confirms** decision 4: the TPB is honoured and the context variable names (`READ_ONLY`, `ISOLATION_LEVEL`) are correct. (The "a read-only read-committed transaction does not hold the oldest active transaction back" part is a load-time check, not run here.)

## Obligation 5 — conversions and `FIRST n`

- `SELECT FIRST 1 CAST(SUBSTRING(col FROM 1 FOR 4000) AS VARCHAR(4000) CHARACTER SET UTF8)` works on `VARCHAR`, on a `WIN1252` column (transliterated to UTF8), and the `CHARACTER SET OCTETS` form works on `BLOB SUB_TYPE TEXT`. **Confirms** decision 5's conversion forms on 5.0.
- `FIRST n` stops the natural scan early: `SELECT FIRST 1 ID FROM CUSTOMERS` on a 2-row table recorded `Natural = 1` in the per-table block (not 2). **Confirms** decision 5's storage-order early-stop assumption.

## Obligation 6 — audit log file modes

The server creates the audit log `-rw------- (0600)` owned by `firebird:firebird` (uid/gid 84). **Impact**: an agent that is only in the `firebird` **group** cannot read it (no group read under the default umask). The operator must grant the agent read access explicitly (a supplementary ACL, or group ownership plus `chmod g+r` / `UMASK`); docs/08 and the user guide must state it.

## Obligation 7 — per-table counters (nested reads)

**Confirms** the key assumption (and answers open question 13 affirmatively). With `print_perf = true` each finish record carries the `Table / Natural / Index / Update / Insert / Delete / Backout / Purge / Expunge` block. A `SELECT N FROM CALLER` where `CALLER` calls `READTWO` which reads `CUSTOMERS` and `NONEC` produced, on the **top-level** `EXECUTE_STATEMENT_FINISH`, a per-table block naming **both** `CUSTOMERS (2)` and `NONEC (1)` — i.e. the counters include relations read two call levels deep. Separate `EXECUTE_PROCEDURE_FINISH` records (with `log_procedure_finish`) carry the same aggregated block, so the agent must avoid double-counting the same read across the statement and procedure records. | **Confirms** decision 6 / open question 13: name the procedure plus the counters' relations (no forced `*`), **because** the counters include reads inside called code. |

## Obligation 8 — header tokens `(pid:address)`

**Contradicts the ADR's token model; an ADR refinement is needed before Audit ships (as decision 6 anticipated).**

- The token is `(server_pid : plugin-instance heap address)`. In **SuperServer** the server pid is constant within a run (e.g. `21608`) but the **address is per attachment** — the one log held 21 distinct tokens with a single pid, one per attachment/thread. There is therefore **no single "current token per database path"**: many coexist concurrently for the same database.
- The pid changes only at server restart (distinct pids in the log correspond to restarts).
- `TRACE_INIT` / `TRACE_FINI` (`SESSION_1 Firebird Audit`) bracket the **whole server run** in SuperServer, but in **SuperClassic** each attachment emits its **own** `TRACE_INIT` / `TRACE_FINI`.

**ADR impact**: decision 6 fix 4/7 ("keeps a token per database path … changed only at a `TRACE_INIT`/`TRACE_FINI` boundary; a record whose token is not the current one for its database marks records ambiguous") cannot stand as written — it would mark almost every record ambiguous. The refinement should treat the **pid** as the stable per-run discriminator (constant across attachments, changes at restart) and the **address** as per-attachment, not per-database, and must accept per-attachment `TRACE_INIT`/`TRACE_FINI` in SuperClassic/Classic. The forged-header defence must be re-derived on that basis.

## Obligation 9 — trace text facts and failed logins

- **`CREATE USER … PASSWORD` is written verbatim** in the statement text: `CREATE USER MARKERUSER PASSWORD 'MARKERSECRET12345' USING PLUGIN Srp` appeared in clear in the trace (the server does **not** mask it, unlike SQL Server). The internal `plg$srp_view` update that follows carries the verifier and salt as `param0`/`param1` (binary), and the user name as a parameter. **Confirms** decision 6 and the password-bearing-statements rule: the agent must keep the kind only and the #82 marker test must cover `CREATE USER`.
- **Attachment line format** (4.0 and 5.0, identical): `<path> (ATT_<n>, <USER>:<ROLE>, <charset>, <protocol>:<address>/<port>)`, e.g. `/data/app.fdb (ATT_78, AGENT_MIN:NONE, NONE, TCPv4:127.0.0.1/41370)`; then the client line `<process path>:<pid>` and the transaction line `(TRA_<n>, READ_COMMITTED | READ_CONSISTENCY | WAIT | READ_WRITE)`. **Confirms** decision 6's format.
- **Failed login**: a wrong password gives SQLSTATE `28000` "Your user name and password are not defined…" (GDS `isc_login`), and a `FAILED ATTACH_DATABASE` record is written (with `log_connections`), the attempted user in the attachment line. **Confirms** the mapping `isc_login → authentication_failed` (decision 1).
- **Delay after repeated failures**: five rapid wrong-password attempts from the same loopback source were fast (~30 ms) for the first three, then the **fourth was delayed ~8 s**; later attempts fast again; a correct login immediately afterwards **succeeded** (no permanent lockout). **Impact**: Firebird throttles repeated failed logins per source with a delay, not a lockout; the connector's "stop retrying until the next heartbeat" (decision 1) already avoids tripping it.

## Obligation 10 — attachment ids

`CURRENT_CONNECTION` was 133 on the live database; on a `gbak` backup+restore to a new file it was **7**. **Confirms** the ADR: the attachment-id counter is **reset by a restore**, so an id seen after a restore is not the agent's earlier one (the own-attachment set must account for restores).

## Obligation 11 — when the audit configuration is read

Changing `log_statement_finish` to `false` in the live trace configuration **without a restart** had no effect: a fresh attachment's statement was still logged (both `START` and `FINISH`). **Confirms** decision 6 / M3: the system-audit configuration is read at **trace-session (server process) start**, not at each attach. The "files changed after the server process started = not proven" rule (proof 2) is the correct one.

## Obligation 12 — database paths in the trace

- **symlink, `..`, `//`**: all three attach forms are **canonicalised to the real path** `/data/app.fdb` in both `MON$DATABASE.MON$DATABASE_NAME` and the trace `ATTACH_DATABASE` line. **Confirms** exact-path matching is safe for these.
- **alias** (a `databases.conf` name): the trace prints the **alias string verbatim** (`appalias`), while `MON$DATABASE_NAME` returns the resolved path `/data/app.fdb`. **They differ.**
- **hard link**: `MON$DATABASE_NAME` and the trace both print the **hard-link path** used to attach (`/data/app_hard.fdb`, same inode as `/data/app.fdb`); hard links are not resolved to a canonical name.

**ADR impact (refinement candidate for decision 6 / M4)**: the trace path is the **attach string as the client gave it** (a `databases.conf` alias stays an alias; a path is canonicalised), so a path learned from `MON$DATABASE_NAME` will **not** match records of a client that attached through an alias (or through a different hard link). The agent must match against the declared `attach` **alias string too**, not only the resolved path, and the inode-based ambiguity rule (M4) is justified by the hard-link case.

## Obligation 13 — section matching in the trace configuration

With a disabled default section and two named sections, `database = /data/app.fdb` (exact full path) and `database = %[\\/]app.fdb` (a `SIMILAR TO` pattern), a query on `/data/app.fdb` was logged **only to the first section's log** (`exactpath.log`), not the second. **Confirms**: section patterns are matched against the **full database path**, and **only the first matching section applies** (the default section is processed first, then search stops at the first matching named section — sections do not accumulate). This supports decision 6 proof 3 (evaluate only the default section and plain full-path/file-name sections without `SIMILAR TO` metacharacters; cap at Limited otherwise, open question 12).

## Obligation 14 — `MON$ATTACHMENTS` remote fields on loopback

For a loopback attachment: `MON$REMOTE_PROTOCOL` = `TCPv4`, `MON$REMOTE_ADDRESS` = `127.0.0.1/<client port>` (address and port combined in one field), `MON$REMOTE_PROCESS` / `MON$REMOTE_PID` set, `MON$WIRE_CRYPT_PLUGIN` = the negotiated plugin (`ChaCha64`), `MON$AUTH_METHOD` = `Srp256`. **Confirms** decision 3's forwarder check reads (`MON$REMOTE_ADDRESS` carries the client address and port; compare with the socket). The tunnel/forwarder variants are to confirm with a `socat` forwarder in the P10-D integration test.

## Obligation 15 — I4 measurement plan

Executed above (obligations 3/4; accounts `min`, `ext`, `none`, `SYSDBA`). A `sysdba_mapped` account via `RDB$AUTH_MAPPING` was not exercised (no mapping defined on these images; `RDB$AUTH_MAPPING` was empty and readable); to add on the engine matrix with an explicit mapping. **Confirms** the plan is runnable and the probes behave as decision 4 expects.

## Summary of contradictions to carry into ADR-0060

1. **Obligation 8 (header tokens)** — the token's address is **per attachment**, not per database (many coexist for one database); the pid is the per-run constant; SuperClassic emits per-attachment `TRACE_INIT`/`TRACE_FINI`. Decision 6's "one current token per database path" rule must be refined before Audit ships.
2. **Obligation 12 (alias paths)** — the trace prints a `databases.conf` **alias verbatim** while `MON$DATABASE_NAME` gives the resolved path; the agent must match the declared `attach` alias string as well as the resolved path.
3. **Obligation 3 (extended variant)** — `SELECT_ANY_OBJECT_IN_DATABASE` exposes `RDB$CONFIG` (the whole server configuration) beyond user tables; keep the extended variant opt-in and documented.

All other obligations measured here **confirm** the ADR's assumptions.

### Lot 3: summary of contradictions

To carry into an ADR-0060 refinement before the Audit lot:

1. **8c, `TRACE_INIT` / `TRACE_FINI` in SuperServer** — per attachment, as in SuperClassic, on 4.0.7 and 5.0.4; nothing brackets the server run. R1 rule 2's SuperServer handling (a `TRACE_INIT` with the current pid triggers a stop; a second one is ambiguous) would stop or mark every attachment.
2. **8e, the Garbage Collector** — in SuperServer, each database open creates a Garbage Collector attachment that writes transaction records with no `ATTACH_DATABASE`, above the watermark: ambiguous under R1 rule 5 at every open.
3. **8e, attach-order tolerance** — 4.0.7 SuperServer wrote `ATTACH_DATABASE` records up to 30 ids (a whole burst) out of order, about 1 s late, when a burst opened the database; the proposed constant tolerance of 16 does not hold.
4. **3b, records without a per-table block** — reads of virtual relations only (`RDB$CONFIG`, `MON$*`, the agent's `MON$SERVER_PID` read) have no block: R3's own-read condition cannot hold as written, and H1 fix 2 / R1 rule 7 would open a split window at every such statement.
5. **3b and the self-security database** — `ext` reads every verifier in `PLG$SRP`, so R3's "server configuration, not user data" does not hold there (decision 4 refuses `ext` there, as it should); and `PUBLIC`'s own-row `PLG$SRP_VIEW` makes decision 4's one-bit probe refuse **every** account on a self-security database.
6. **Failed logins** — a wrong password writes no `FAILED ATTACH_DATABASE` (any `AuthServer`); the first round's obligation 9 note and decision 6's failed-login counting from those records do not hold. Wrong passwords are visible only in the security database's records, if at all.

Confirmed: 7b; 8a; 8b; 8d; 8f (no field escapes line breaks except conversion-error values, so the misattribution residual stands and rule 9 applies); 12b (version-dependent, covered fail closed), 12c and 13b; Classic (Limited, peer uid holds); residual A (not filtered). Still open: `PLG$USERS` in a self-security database (needs a legacy-schema security database), Classic under socket activation, and the `sysdba_mapped` and `op_cancel` items listed by the refinement.

### Second round: summary of contradictions

To carry into an ADR-0060 refinement before the Audit lot:

1. **Statements that touch no record have no per-table block** (3d), for persistent tables, views and system tables alike, with any `records fetched` (an aggregate over an empty table fetches 1). R8 item 1 keeps such records ambiguous on the premise that "a block was expected": every lookup that finds nothing would open a split window. The agent's own `AUTH_MAPPINGS` is block-less on every database without a local mapping, so it is ambiguous at every `check()` under R8 item 4.
2. **The relation set of one constant text varies with the data and the account** (3d: `OBJECT_GRANTS`, `OWNED_OBJECTS`, `RELATIONS`, `AUTH_MAPPINGS`). R8 item 4's "exactly the expected set" cannot hold; a subset of the text's relations plus the metadata-loading set, possibly empty, can.
3. **Executable procedures, functions and triggers never write `records fetched`** (3e). H1 fix 2 as written makes all their finish records ambiguous; their trailer is the performance line, with a block when they touched records.
4. **Database-trigger records are not folded** (3e): `ON CONNECT` and `ON DISCONNECT` never, transaction triggers rarely or into an unrelated statement. Under R8 item 2 each opens a split window: at every attachment of a database with a connect or disconnect trigger.
5. **The Garbage Collector takes the id after the Cache Writer, after the opener** (`n + 2`), not before, and writes its first record only when it has garbage, up to at least 20 s after the open (8h). R6 item 2's structural binding cannot be built from "the next `ATTACH_DATABASE` has the internal id plus 1 or 2", and its interim id rule makes a late Garbage Collector ambiguous. Its `COMMIT_TRANSACTION` carries a performance line, which R6 item 1's "no trailer" must allow.
6. **`MON$SEC_DATABASE` is `CHAR(7)`** (3c): `Self` and `Other` come padded with trailing spaces; R9 rule 1's comparison must ignore them.

Confirmed: 3c (the three values, readable by the minimal account); 3d (the `RDB$DATABASE` / `RDB$RELATIONS` metadata-loading set, sampling texts block exactly the sampled table, the row bound of 1 for own-row reads and probes, `SET SESSION IDLE TIMEOUT` as case (b)); 3e (R4 folding for routines called by a statement, nested records first, innermost first); 7c (reads through `EXECUTE STATEMENT`, `ON EXTERNAL` and a UDR appear as their own statement records or attachments, the outer record block-less: R8 case (c)); 8h (the fixed session line; the Garbage Collector's attachment line; the Cache Writer writes nothing; SuperClassic has neither; the automatic sweep's internal shape recorded). Not covered here: 8g (P10-D load run), and the earlier open items (`PLG$USERS` with the legacy schema, Classic under socket activation, `sysdba_mapped`, `op_cancel`).

### 3f — `records fetched` after an early cursor close

Table `BIG`, 10 000 rows, read by the minimal account. "Counted" is what the connector reports (`Fetched.rows`, or the rows returned by `query`); "requested" is the sum of the row counts of the `op_fetch` messages the connector sent.

| Case (connector path) | Counted → `records fetched` in the record | ADR impact |
|---|---|---|
| Full read (`SELECT FIRST 777 …`, read to its end) | 777 → **777** | Exact, as R13 item 3 says |
| `Flow::Stop` after k rows (`sample`, the byte budget; `FIRST 5000 + k`) | k = 1, 10, 63, 64 → **128**; 65, 100, 128 → **192**; 129 → **256**; 200 → **320**; 1 000 → **1 088**; 4 999 → **5 120** | **Contradicts** R13 item 3's tolerance ("between the counted rows and the counted rows plus 64"): up to counted + 127 |
| Row limit (`max_rows` below the result, the cut path) | 1 → **4**; 10 → **22**; 62 → **126**; 63 → **128**; 64 → **129**; 65 → **130**; 100 → **165**; 127 → **192**; 128 → **193**; 129 → **194**; 500 → **565**; 9 999 → **10 000** (end of the table) | **Contradicts** R13 item 3 by one row at the round boundary (64 → 129 = counted + 65) |
| Client deadline during a multi-round fetch (slow consumer, 400 ms) | 128 handed → **256** | **Contradicts** R13 item 3 (counted + 128) |
| Client deadline while the server computes the rows (1.5 s) | 0 returned → **704** (5.0.4), **640** (4.0.7) | Same |

**The rule behind the numbers.** After answering an `op_fetch` for n rows, the server fetches the next n rows of the cursor ahead (to send them with the next request), so `records fetched` = the rows the connector requested (capped by the end of the result) plus the size of its last request, again capped by the end of the result. The connector does not see those rows. In the `Flow::Stop` path it has also read and dropped the rest of the round it stopped in (up to 63 rows), and in the cut path it asked for one row more than its limit. ### Third round: summary of contradictions

To carry into an ADR-0060 refinement before the Audit lot:

1. **3f, `records fetched` after an early close** — the server fetches one request ahead of the client, so `records fetched` lies between the rows the connector requested and that number plus its last request (at most + 64). Measured from the rows the connector counted, the record exceeded them by up to 127 (`Flow::Stop`), 65 (the row limit) and 128 (the deadline): R13 item 3's "counted rows plus 64" does not hold. The connector knows the rows it requested, so a credit can carry that number. Two own-attachment record kinds have no rule yet: the `FAILED EXECUTE_STATEMENT_FINISH` and `ERROR` pair of the server's statement timeout, and an `ERROR AT JResultSet::fetchNext` (`request synchronization error`) after a cut read whose last request reached the end of the result. Observation for the connector lot (not an ADR point): a client deadline in the middle of a multi-round fetch dropped the attachment instead of sending `op_cancel`. The server then wrote the finish, rollback and detach records only 5 to 6.5 s later.
2. **3d row of the `RDB$CONFIG` read** — the first read on an attachment that returns rows names `RDB$CHARACTER_SETS` and `RDB$COLLATIONS` (never `RDB$CONFIG`), whatever the cast; R13 item 2 would reject the agent's own read. Its row needs a per-text metadata-loading set.
3. **3g, transaction-end records** — after DDL, `COMMIT_TRANSACTION` carries a block of system relations; R20's "a performance line" is not the whole trailer.
4. **3g, transaction statements and transaction triggers** — on a database whose transaction triggers read a table, `SET TRANSACTION`, `COMMIT` and `ROLLBACK` statement records carry the trigger's block, so R20 / R8 case (b) makes them ambiguous.
5. **3g, per-row routines** — R14 item 4 counts only block-less pending records, but block-ful per-row records come in the same numbers (10 000 per statement here) and need the same treatment (a per-relation maximum). Other bindings' records interleaved behind them reached 203, near R8 item 2's bound of 256, within 79 ms.
6. **3g, DDL trigger name lines** — the kinds `BEFORE DDL` and `AFTER DDL` must join R14 item 2's closed list, with an optional ` FOR <relation>` that names a table the body wrote to.
7. **3g, BLR and `gbak`** — `gbak` (over TCP, through `service_mgr`, embedded) writes no BLR record, so the BLR trailer stays unmeasured, and a `gbak` backup's reads appear in no record: a new residual for docs/08, or a decision.
8. **3h, external-file tables** — they never write a block, even when they return rows; R12 item 4's premise does not hold for them, and each such read opens a window (fail closed).

Confirmed: the read-back probe's record (proof 7); the `MON$SEC_DATABASE` candidate's row (R13, R19); R15 (all 416 database-trigger records met its conditions; `ON CONNECT` comes after `ATTACH_DATABASE`, which removes R15's residual); R14's trailers and folding for per-row and DDL triggers; M1's exclusions (an aggregate over a view of a virtual relation or over an external-file table returns 1 row with no block) and R12 item 5's premise (reads behind views of virtual relations write no block); GTTs write blocks as persistent tables do (R12 item 1 could admit types 4 and 5); 7d's complete sequence (R18 item 3 can bind these attachments by their own `ATTACH_DATABASE`), with the note that a local embedded process writes the same line under another pid; 8i (the Garbage Collector ends at the close, or 15 s after the last detach with a linger, with no second instance; the lowest-id condition rejected 1 of 69 real Garbage Collectors, loud, on 5.0.4). Not covered here: 8g (P10-D load run), the BLR trailer (no tool tried writes one), and the earlier open items (`PLG$USERS` with the legacy schema, Classic under socket activation, `sysdba_mapped`).

### 3i — the connector's deadline, cut and cancel paths (R22)

The connector's attachment line is `<db> (ATT_n, DATABASTION_AGENT:NONE, UTF8, TCPv4:127.0.0.1/<port>)`, with the client line `databastion-agent:0` (the process name the connector sets; the character-set field is `UTF8`, not `NONE`). "Counted" is what the connector reports; "requested" (Q) is the sum of the row counts of the `op_fetch` messages it sent; M = 64 is the largest request.

| Connector path | Counted → `records fetched` | Record written | ADR impact |
|---|---|---|---|
| Full read (`SELECT FIRST 777 …`) | 777 → **777** | plain `EXECUTE_STATEMENT_FINISH` | **Confirms** R22 **end** (N = C) |
| Byte budget (`sample`, `Flow::Stop` at k) | 1 → **128**; 64 → **128**; 65 → **192**; 129 → **256** | plain `EXECUTE_STATEMENT_FINISH` | **Confirms** R22 **early** (Q ≤ N ≤ Q + M): Q = 64, 64, 128, 192, N = Q + 64 |
| Row-limit cut not reaching the end (`max_rows` = 64, 100) | 64 → **129**; 100 → **165** | plain `EXECUTE_STATEMENT_FINISH`, **no** error | **Confirms** R22 **early** (Q = 65, 101; N = Q + 64) |
| Row-limit cut reaching the end (`max_rows` = 9999) | 9999 → **10000** | `EXECUTE_STATEMENT_FINISH` (block `BIG`, 10 000) **then** `ERROR AT JResultSet::fetchNext`, sole code `335544364 : request synchronization error`, no trailer | **Confirms** R22 item 6; **locates the cause** |
| Client deadline while the server computes (400 ms, a cross-join + `ORDER BY`) | 0 returned; `op_cancel` answered `isc_cancelled` in **321 ms** (5.0.4) / **249 ms** (4.0.7); session **not** broken | `FAILED EXECUTE_STATEMENT_FINISH` (the text, `0 records fetched`, a performance line and a partial block `BIG Natural 838934`) **then** `ERROR AT JStatement::openCursor`, sole code `335544794 : operation was cancelled` | **New** own-attachment shape for the client-cancel path (R22 items 3–5) |

**The request synchronization error is conditional.** It was written only when the cut's extra request (the connector asks for `max_rows + 1`) reached the **end** of the result (`max_rows` = 9999 on a 10 000-row table): both versions, every run. The 64- and 100-row cuts, which do not reach the end, produced **no** error. This confirms R22 item 6's cause and supports its proposed connector fix: not asking for one row beyond the limit when the end can be reached would remove the error (and with it the follow-up).

**The follow-up `ERROR` shapes, per R22 item 7** (identical on 4.0.7 and 5.0.4), each a bare record — header, attachment line, client line, transaction line where present, location line, one line per code, **no trailer**:

- server statement timeout (3f, re-confirmed): `ERROR AT JResultSet::fetchNext`, codes **335544794** and **335545129**;
- client `op_cancel` at the deadline (this round): `ERROR AT JStatement::openCursor` (cancel while computing) or `JResultSet::fetchNext` (cancel during a fetch), **sole** code **335544794**;
- row-limit cut reaching the end: `ERROR AT JResultSet::fetchNext`, **sole** code **335544364**.

So the client-cancel `FAILED` finish is distinguishable from the server statement timeout: the server timeout carries **both** `335544794` and `335545129` at `JResultSet::fetchNext`, while the client cancel carries **only** `335544794` (and may be located at `JStatement::openCursor`). R22 item 4's caution — a `FAILED` finish on an **early** credit is not the agent's own until this form is recorded — is now satisfied by this row.

**On a stale cancel (R22 item 3, L7) and the drop delay (N5).** In every `op_cancel` run the cancel was answered by `isc_cancelled` and consumed in step; the attachment stayed usable (`broken = false`) and the next statements (on fresh sessions) saw no residual, so **no evidence was seen that a cancel can outlive the answered fetch**. The deliberate stale-cancel race (an `op_cancel` sent after the fetch was already answered by rows, reaching the next request or the `DSQL_drop`) was not reproduced here; it stays for the connector lot to force, and R22 item 3's clean-end rule stands until it does. The op_cancel path here wrote its records **at** the cancel (no delay); the 5–6.5 s delay between a dropped attachment and the server's records (N5) is the third round's drop path (no cancel answered) and is unchanged.

### 3j — BLR requests, the utility attach and `gbak` (R27, R29)

| Client / case (both versions) | Result | ADR impact |
|---|---|---|
| **Ordinary account (`ORD`), BLR read of a table, arbitrary process name, `log_blr_requests = true`** | **The read is traced.** `COMPILE_BLR` (Statement n, `0 ms`, no block) then `EXECUTE_BLR` (Statement n, performance line `0 ms, 2 fetch(es)`, **and a block naming the scanned relation** — `CUSTOMERS Natural 1`, `BIG Natural 1`). No `records fetched` line. The block's counters are those at request start (`EXECUTE_BLR` is logged at the start of execution), so the `Natural` count is 1 whatever the loop later reads (3 or 10 000 rows); the relation name is always present | **Decisive: R27 item 4 (ii) does NOT apply.** An ordinary account cannot read a table through BLR **without** a record that names the read. **Partial is NOT withheld.** The parser must handle the `COMPILE_BLR` and `EXECUTE_BLR` event kinds (block-ful `EXECUTE_BLR`, a performance line, **no** `records fetched`; R14 item 5 / H1 fix 2 must allow this trailer, which differs from "records fetched expected") |
| Ordinary account with the backup/utility DPB tag (`isc_dpb_gbak_attach`) | **Refused at attach**: `FAILED ATTACH_DATABASE` + `ERROR AT JProvider::attachDatabase`, codes `335544788` ("Unable to perform operation") and `335545112` ("System privilege USE_GBAK_UTILITY is missing") | The untraced path is **not** open to an ordinary account |

| `SYSDBA` (owner + `RDB$ADMIN`) with the utility tag | Attach allowed, the BLR read **succeeds** (3 rows), and it is **NOT traced**: the attachment writes only `ATTACH_DATABASE`, `START_TRANSACTION`, `COMMIT_TRANSACTION`, `DETACH_DATABASE` — **no** `COMPILE_BLR`/`EXECUTE_BLR`, no block | The utility/backup attach **suppresses BLR request tracing**. | `gbak -b` through `service_mgr` and over TCP | The DB attachment writes only `ATTACH_DATABASE`, `START_TRANSACTION`, `COMMIT_TRANSACTION` (a performance line, no block), `DETACH_DATABASE`; **no BLR or statement record**. **Utility-attachment privileges** (both versions): an ordinary account is refused (`USE_GBAK_UTILITY` missing); a role granting `USE_GBAK_UTILITY` is sufficient for the attach; `SYSDBA` (owner and `RDB$ADMIN`) is allowed. A plain user's `CREATE DATABASE` was itself refused, so a non-admin owner could not be isolated here; the owner path is documented behaviour and `SYSDBA` exercises it as owner.

### Fourth round: summary

- **3i confirms R22** on both versions: `records fetched` fits requested ≤ N ≤ requested + 64 for full, byte-budget and row-limit reads (full read N = counted); the **request synchronization error** (`335544364`, `JResultSet::fetchNext`, no trailer) appears **only** when the cut's `max_rows + 1` request reaches the end of the result; a client deadline that races a pending fetch is answered by `op_cancel` (`isc_cancelled` `335544794`, ~250–320 ms) and the session stays usable, writing a `FAILED EXECUTE_STATEMENT_FINISH` + `ERROR AT JStatement::openCursor` (sole `335544794`) at the cancel. The client-cancel `FAILED` finish is distinguishable from the server statement timeout (which carries `335544794` **and** `335545129` at `JResultSet::fetchNext`). No stale cancel outliving an answered fetch was reproduced; the N5 drop delay stays as 3f measured it.
- **3j is decisive for R27 item 4: an ordinary account's BLR read IS traced** (`COMPILE_BLR` + a block-ful `EXECUTE_BLR` naming the relation), so **Firebird Partial is not withheld**. The **untraced** BLR-read path exists only under the **utility/backup attach** (`isc_dpb_gbak_attach`), which requires the owner, `RDB$ADMIN` or `USE_GBAK_UTILITY` (an ordinary account is refused) — exactly R27 item 3 (i)'s residual. `gbak` (through `service_mgr`, over TCP) writes no BLR or statement record, only `START_SERVICE "Backup Database"` and a counter-less `COMMIT_TRANSACTION`; the transaction-end page counters do **not** expose the backup's reads (R27 item 5 confirmed over-reporting only, ineffective against `gbak`). Two agent-side follow-ups for the Audit lot: the parser must handle `COMPILE_BLR`/`EXECUTE_BLR` (a block-ful `EXECUTE_BLR` with a performance line and **no** `records fetched`), and no `blr_reads_not_traced` label is needed (R27 item 4 does not apply, so the `signals.json` text change of "Protocol" is the only contract change).
- **3k**: user DML on system tables is refused on both versions (confirms R24 item 2); an API commit's `COMMIT_TRANSACTION` does **not** carry a commit trigger's block (the trigger's read is its own R15 record). **One contradiction**: `ALTER SESSION RESET` on a database with connect/disconnect triggers fires both triggers and its statement record **carries their summed block**, so R24 item 3 must add `ALTER SESSION RESET` to the kinds that may carry a block (otherwise every such reset is ambiguous).
