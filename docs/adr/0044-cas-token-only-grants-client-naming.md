# ADR-0044: CAS Audit names the OAuth client of token-only grants from the token request record

- **Status**: Accepted (2026-10-09; the maintainer accepted the recommended answers to the six open questions)
- **Date**: 2026-10-09
- **Refines**: [ADR-0041](0041-cas-connector.md) decision 7 (which stays Accepted), including its refinement of 2026-10-08 ("Token-only grants therefore never name the client; a follow-up may name it … which needs a further refinement of this decision"). Decision 10 (levels) is unchanged.
- **Context references**: review of the CAS follow-ups (#165), finding L6; ROADMAP [phase 8 follow-ups](../ROADMAP.md#phase-8-follow-ups); `agent/crates/connector-cas/fixtures/README.md` and `cas-8.0.2-oauth-oidc-audit.jsonl` (records written by the CAS 8.0.2 dev service on 2026-10-08, redacted); `agent/crates/connector-cas/src/parse/record.rs` (closed record visitor), `src/registry.rs` (`ServiceIndex`); [08-engine-capabilities.md](../08-engine-capabilities.md#apereo-cas)

## Context
Since #165, the CAS token endpoint's issuance record `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` is mapped to a `read` of `*`, `rows` 1 (ADR-0041 decision 7, refinement of 2026-10-08). Its `what` holds the token values (`access_token`, `refresh_token`, `id_token`, `scope`, `token_type`, `expires_in`) and no service; its `who` is the user, or the client id for `client_credentials`. An authorization code login also writes `SERVICE_TICKET_CREATED` for the client's redirect URI, so that grant already gives one `read` of a named registry entry when the entry's `serviceId` matches the reduced URL. The **token-only grants** (`refresh_token`, `client_credentials`, `password`) write no service ticket: their only `read` event is of `*`, so a policy or a per-principal baseline scoped to a named application never sees them. A `client_credentials` grant is a machine reading released attributes with no user present; a `refresh_token` grant extends a release without a login.

What CAS 8.0.2 writes around a token response (verified on the dev service; the fixture records, in file order):

| Record | `who` | `what` (keys, CAS 8.0.2) |
|---|---|---|
| `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` | `audit:unknown` | `code` (the authorization code or the refresh token id, masked by CAS; `N/A` for `client_credentials` and `password`), `grant_type`, `service`, `scope` (absent when none was requested), `response_type` |
| `OIDC_ID_TOKEN_CREATED` (only when the `openid` scope was requested) | the user, or the client id for `client_credentials` | `authn_methods`, `service` (an object whose `attributes` hold the token request's HTTP attributes: every header including **`Authorization`, the client id and secret in Basic form, in clear**, and for the implicit flow `Cookie` with the `TGC`, plus `client_id` and `org.apereo.cas.services.RegisteredService`, the entry's numeric id), `scope`, `id_token` (the signed ID token), `txn`, `client_id`, `username` |
| `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` | the user, or the client id for `client_credentials` | the token values, no service |

The token request's `service` is the redirect URI for `authorization_code` and the **client id** for `refresh_token`, `client_credentials` and `password` (fixture records 9, 12, 16 and 19: `"service": "scratch-m2m"`). No record carries an identifier shared by the request and the response: the request's `what` has no `txn`, the response's `what` has no client or request id. In the fixture, request and response share `clientIpAddress`, `serverIpAddress` and `userAgent` and follow each other in the file within 32 to 206 ms, with at most an `OIDC_ID_TOKEN_CREATED` record in between. A `client_credentials` request without the `openid` scope (records 19 and 20) writes no ID token record. The `password` grant writes `AUTHENTICATION_SUCCESS` (with `registeredServiceName` and the client id as `service` in its `what`) **before** the token request record. The device authorization grant was not exercised, and whether CAS writes a token request record for a request whose client authentication fails was not verified.

`clientId` is a field of the OAuth and OIDC service definitions the registry parser already reads (ADR-0041 decision 4: classified as a value, pooled per path). A client id is not a secret, but it is free text chosen by the operator and may be a person's or a customer's name, so it is handled like service names are: it selects a registry entry, and only that entry's normalized name ([ADR-0009](0009-name-normalization-and-item-sanitization.md)), or `*`, leaves the agent.

## Options

**(a) Correlate the token request with the token response, and match the request's `service` against the registry's `clientId`.**
- *Reads beyond today*: from `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` (today counted, `what` never decoded), the string values of `grant_type` and `service` in the object-form `what`; `code`, `scope`, `response_type`, unknown keys and nested values skipped unread with `IgnoredAny`, as `ticketId` is today. Optionally `serverIpAddress` (skipped today) as part of the correlation key. From the registry, each entry's `clientId`, kept for lookup.
- *I2 and zeroization*: `code` holds the refresh token id (masked by CAS, but the agent must not depend on CAS masking, ADR-0041 decision 7) and is never decoded. `grant_type` and `service` are unescaped by `jtext` into zeroizing buffers, as `service` is today; the client id is reduced at once to a registry entry reference and a keyed tag (a local tag key, as the failed-login windows use), then dropped. Nothing new leaves the agent: the event's object is the entry's normalized name, as for a service ticket.
- *Coverage*: every token-only grant, OAuth 2.0 and OIDC endpoints alike, with or without the `openid` scope.
- *Cost*: a small, bounded correlation state per stream; a wrong or missing correlation is possible (below).

**(b) Read `client_id` from the `OIDC_ID_TOKEN_CREATED` `what`.**
- *Reads beyond today*: the `what` of a record that today is never decoded and that holds, next to `client_id`, the clear `Authorization` header (the client secret), the signed `id_token` (a bearer credential with the user's claims), for the implicit flow the `TGC` cookie, and the request's other headers. The visitor would have to walk past the nested `service.attributes` object without copying any of it.
- *I2 and zeroization*: the secret and the tokens are already in the zeroized line buffer today, but nothing decodes this `what`. Option (b) puts a parser on the one record of the trail that holds a client secret in clear: a later change that reads one more key (`service.id`, a header) or a CAS version that moves `client_id` into `service.attributes` (it is already there too) brings secret-bearing values into kept buffers.
- *Coverage*: OIDC requests with the `openid` scope only; `client_credentials` or `password` on the OAuth 2.0 endpoint without `openid` write no ID token record, so they stay `*`.
- *Correlation*: still needed. The ID token record is a separate record before the response; it is closer in time (1 to 12 ms in the fixture) and shares `who` with the response, but it is not the issuance record.

**(c) Keep `*`.**
- *Reads beyond today*: none.
- *Consequence*: token-only grants stay invisible to policies and baselines scoped to a named application; they still count as issuance for decision 10 and still reach per-principal baselines (the user, or the client id fingerprinted for `client_credentials`). The limitation stays documented in [08-engine-capabilities.md](../08-engine-capabilities.md#apereo-cas).

### Correlation reliability (options (a) and (b))
- **Interleaved requests.** CAS handles requests concurrently, so two token requests can be written before either response. The correlation key, `clientIpAddress` + `userAgent` (+ `serverIpAddress`), separates distinct clients, but machine clients behind one NAT or proxy often share both address and user agent. Responses may be written out of request order. Rule: the response is named only when **every** pending request that matches its key within the window resolves to the **same** registry entry; then the oldest is consumed. Concurrent requests of the same client (the common case for a replicated service) stay named; concurrent requests of different clients behind one address become `*`. Never a guess between two entries.
- **Multiple CAS nodes.** Each node writes its own audit log on its own host, so request and response of one HTTP request are in the same file and the correlation is per stream, never across targets. A log shared by several nodes (a network file system, an aggregated file) interleaves nodes: `serverIpAddress` in the key keeps them apart.
- **Missing records.** An `excluded-actions` setting that drops `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` leaves every response `*` (today's behaviour). A request with no response (a refused grant) expires from the state when its window ends. A lost request record (a line over 1 MiB, a parser panic, a restart between the two records, since the state is not persisted) leaves its response `*`, unless another pending request with the same key is still in its window: then the response can be **attributed to the wrong client**. The window bounds that case, and for `client_credentials` the response's `who` must also equal the request's client id (compared as keyed tags).
- **Forged records.** The client address comes from `X-Forwarded-For` by default and the user agent is chosen by the client (ADR-0041 decision 7, residual risk), so an attacker may be able to get a token request for client X logged with a victim's address and user agent (if CAS logs requests whose client authentication fails, not verified). Under the rule above this only turns the victim's named `read` into `*` (two entries in the window), never renames it, as long as the victim's own request record is logged.

## Decision
Option (a), for the three token-only grants only:

1. **Token request record.** For `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` with an object-form `what`, the closed visitor reads the string values of `grant_type` and `service` only; every other key and nested value is skipped unread, a duplicate `grant_type` or `service` drops the record, and a string-form or non-object `what` gives no pending entry. The record still gives no event. `serverIpAddress` is read as an IP literal for the correlation key only and never sent.
2. **Registry lookup.** The service index gains a map from the keyed tag of each OAuth / OIDC entry's `clientId` (exact, case-sensitive bytes) to the entry; a client id shared by two entries maps to none. Raw client ids are not kept in the index.
3. **Pending state.** When `grant_type` is `refresh_token`, `client_credentials` or `password` and the tag of `service` selects one entry, the stream keeps a pending entry (entry reference, grant, client id tag, correlation key tag, `when`, file order). `authorization_code`, the device grant and unknown grants add none that can name: the authorization code login keeps its service ticket `read` and its `*` token `read`. At most 1024 pending entries per stream (oldest evicted, counted), each expiring 5 s after its `when`; not persisted.
   - **As implemented (2026-10-09).** Every token request record is kept pending, also those that cannot name (`authorization_code`, the device grant, an unknown grant, a client id that selects no entry or is shared, a `what` that is not an object): such an **unnamed** entry never names a response, it only makes a response of the same key `*` while it is pending (a token response of an authorization code exchange is not attributed to another client's pending `refresh_token` request behind the same address and user agent); a response whose pending entries are all unnamed consumes the oldest and stays `*`, as before. The correlation key is a keyed tag of the client address, the server address and the whole `userAgent` (not only the first product token sent as `application`). The client id tags are made with a fresh random key of each service index; the pending entries are dropped when the service index is replaced (a registry reload).
4. **Token response record.** `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED` is still a `read`, `rows` 1, and still issuance for decision 10. Its object is the selected entry's type and normalized name (decision 4) when the pending entries with the same key, earlier in the file and within the window all select that entry, and, for a `client_credentials` entry, the response's `who` tag equals the client id tag; the oldest matching entry is consumed. Otherwise the object is `*`, and the case is counted (unmatched, ambiguous).
   - **As implemented (2026-10-09).** The entry consumed is the oldest the response can belong to: when the response's `who` tag equals the client id tag, the oldest `client_credentials` entry (else the oldest entry); otherwise the oldest entry that is not `client_credentials`. A response that only `client_credentials` entries of another client id than its `who` match stays `*` (counted as unmatched) and consumes nothing; an ambiguous response consumes nothing either (its candidates expire with their window). The counts (named, unmatched, ambiguous, evicted) are written to the agent log at most once per 10 minutes, without any value (question 5).
5. **Levels.** Decision 10 is unchanged: a named or unnamed token response counts the same.

## Consequences
- **Code** (`agent-engineer`, `security-reviewer` review): `connector-cas` `parse/record.rs` (the request visitor and `serverIpAddress`), `parse/definition.rs` (the top-level `clientId` kept exact, its sampling unchanged), `registry.rs` (the `clientId` tag map), `audit/events.rs` (the pending state and the response mapping). No protocol change: objects are registry entry names as for service tickets. The counters stay local (agent log, open question 5).
- **Tests**: the CAS 8.0.2 fixture with a registry entry whose `clientId` is `scratch-m2m`: the `refresh_token`, `client_credentials` (with and without `openid`) and `password` responses are named, the `authorization_code` response stays `*`; interleaving tests (two requests of the same client named, of two clients behind one key `*`, out-of-order responses), a missing request, an expired request, a duplicated `clientId`, a `client_credentials` response whose `who` differs; an I2 property test that no byte of `code` or of any skipped key reaches an event, a log line or the state; the `cas_audit_log` fuzz target extended to a short sequence of lines so the correlation state is fuzzed (and run by the nightly ASan campaign); the `e2e-cas` scenario gains a `client_credentials` request and asserts the named object.
- **[08-engine-capabilities.md](../08-engine-capabilities.md#apereo-cas)** (`docs-keeper`, after the implementation): the "read from each record" list gains the token request's `grant_type` and `service` and the `serverIpAddress`; the known limit "OAuth 2.0 / OIDC token responses name no service" becomes "named for token-only grants when the token request record is logged and unambiguous, `*` otherwise", with the wrong-client residual below and a recommendation not to exclude `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED`.
- **Residual risk**: a lost token request record with another request of the same key still pending can attribute a response to the wrong client within 5 s (a false incident on one application, or a read hidden under another); a forged request can only turn a named `read` into `*`.

## Rejected alternatives
- **Option (b)**: decodes the only trail record that holds a client secret in clear, covers OIDC requests with `openid` only, and still needs a correlation.
- **Option (c)**: leaves `client_credentials`, the grant with no user in the loop, outside every application-scoped policy.
- **Mapping the token request itself to the `read`** (no correlation): whether CAS writes it for a request it then refuses (client authentication, grant checks) was not verified, so a refused request could count as a read; and its `who` is `audit:unknown`, so the user would be lost.
- **The `AUTHENTICATION_SUCCESS` `what` of the `password` grant** (`registeredServiceName`, client id as `service`): `password` only, and that `what` holds the credential objects.
- **`OAUTH2_USER_PROFILE_CREATED`** (`client_id` in `what`): written when the client calls the profile endpoint, not at issuance, and not for every grant.
- **Naming the `authorization_code` token response too**: its service ticket `read` already names the client when its `serviceId` matches; a second named `read` per login would double the volume charged to the entry (open question 1).

## Open questions (answered)
Each answer is the recommendation of this ADR, accepted by the maintainer on 2026-10-09.
1. Restrict the naming to the three token-only grants, as proposed, or also name the `authorization_code` token response (two named `read` events per login), or drop that response's `read` of `*` since the service ticket already records the release?
   **Answer (decided by the maintainer on 2026-10-09)**: the three token-only grants only (`client_credentials`, `refresh_token`, `password`); the `authorization_code` token response keeps its `read` of `*`.
2. The window (5 s) and the bound (1024 pending entries per stream): acceptable, or tighter (the fixture shows 32 to 206 ms)?
   **Answer (decided by the maintainer on 2026-10-09)**: 5 s and 1024 pending entries per stream.
3. Read `serverIpAddress` for the correlation key (one more field read, an IP literal never sent), or rely on one log file per node and leave it skipped?
   **Answer (decided by the maintainer on 2026-10-09)**: read it, as an IP literal, for the correlation key only (token request and response records); never sent.
4. A new closed target note (for example `audit.token_requests_not_seen`, appended to `target-notes.json`) when token responses were parsed in the last 24 h but no token request record, or documentation only?
   **Answer (decided by the maintainer on 2026-10-09)**: no new target note; documentation only ([08-engine-capabilities.md](../08-engine-capabilities.md#apereo-cas): do not exclude `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED`).
5. Report the unmatched and ambiguous counts as heartbeat metrics, or keep them in the agent log?
   **Answer (decided by the maintainer on 2026-10-09)**: in the agent log only (rate limited, counts only); no heartbeat metric, no protocol change.
6. The device authorization grant was not exercised on CAS 8.0.2: leave it `*` until verified, as proposed?
   **Answer (decided by the maintainer on 2026-10-09)**: yes, `*` until verified.
