## Context
Phase 8 adds a first **Apereo CAS** target. CAS is an identity service, like OpenLDAP: it holds no business tables, but it keeps three stores that hold personal data or secrets, and it writes an audit trail of who authenticated, from where, and which application received a ticket. Unlike the engines supported so far, CAS has no query protocol of its own: its stores are files on the CAS host or tables and collections in engines DataBastion already reads.

This ADR is a design spike. Facts marked **(verified)** were read from the CAS 8.0.2 sources published on Maven Central (`*-sources.jar` of `cas-server-core-api-configuration-model`, `cas-server-core-audit-api`, `cas-server-core-audit`, `cas-server-core-tickets-api`, `cas-server-support-jpa-ticket-registry`, `cas-server-support-jpa-service-registry`, `cas-server-support-oauth-services`, `cas-server-support-oauth-api`, `cas-server-core-services-api`), from the documentation sources on the CAS `master` branch (`docs/cas-server-documentation/…`, read on 2026-10-04), and from the `apereo/cas` tags on Docker Hub. The rendered documentation site (apereo.github.io) and the GitHub API were not reachable from the spike's environment. Facts marked **(to verify against CAS 8.0 docs)** come from knowledge of CAS and must be checked before or during the implementation; none of the decisions below relies on one of them for a security property without saying so.

**Versions (verified).** CAS adopters may expect six months of maintenance from a feature release, then six months of security patches only (CAS maintenance policy). On 2026-10-04 the EOL schedule lists **8.0.x** (security-patch mode from 2027-01-17, end of life 2027-07-17) and **7.3.x** (security-patch mode since 2026-06-30, end of life 2026-12-31); every other line is end of life. 8.1.0 is at RC2. Patch releases 8.0.2 and 7.3.8.3 were published on 2026-10-04. 7.3 will most likely be end of life before this connector ships.

**Stores (verified unless marked).**
- **Service registry**: one definition per registered application: `@class` (`CasRegisteredService`, `OidcRegisteredService`, `OAuthRegisteredService`, `SamlRegisteredService`…), `id`, `name`, `serviceId` (a URL pattern), `description`, `contacts[]` (`name`, `email`, `phone`, `department`, `type`: personal data), `attributeReleasePolicy` (which principal attributes the application receives; some policies, such as static release, carry attribute **values** (to verify against CAS 8.0 docs)), `accessStrategy` (required attributes with their expected values, such as group names or user names (to verify)), `properties` (free name / values pairs), and for OAuth / OIDC `clientId` and **`clientSecret`**. The secret may be plain, a Spring expression resolved at run time, or encrypted (the validator runs it through a cipher executor before comparing it, `DefaultOAuth20ClientSecretValidator`); the encrypted form's text shape is to verify. OIDC services can also carry an inline JWKS (to verify whether private keys can be inline). Backends: JSON files (`cas.service-registry.json.location`, one file per service, `Name-Id.json`; the parser accepts comments, Hjson style (to verify for 8.0)), YAML files, JPA (table `RegisteredServices`: `id`, `serviceId`, `name`, `evaluationOrder`, `evaluationPriority`, `body` = the definition as JSON), MongoDB, LDAP (the JSON body in one attribute, `description` by default (to verify)), Redis, and others.
- **Ticket registry**: live tickets. A ticket-granting ticket id (`TGT-…`) is the SSO session's bearer credential, a service ticket (`ST-…`) is a one-time credential for an application, and tickets carry the authenticated principal and its attributes. Backends: in-memory (default), JPA (table `CasTickets`: `id`, `parentId`, `principalId`, `service`, `type`, `body`, `attributes`, creation, expiration and last-used times), Redis (keys built from ticket ids (to verify)), MongoDB, Hazelcast, and others. Every backend has `cas.ticket.registry.<backend>.crypto.*` (signing and encryption of the ticket body), and **its `enabled` defaults to false** on JPA, Redis, MongoDB, Hazelcast and in-memory. With crypto on, the JPA registry stores the SHA-512 digest of the ticket id, of the principal id and of attribute names and values, the encrypted ticket as body, and the encoded ticket's class name as `type`; with crypto off, ids, principal ids, attributes and body are in clear.
- **Audit trail** (Inspektr, merged into CAS): records with `who`, `what` (the resource: for ticket actions **the ticket id itself**, e.g. `TGT-9-…` in the file sample of the documentation), `action`, `application`, `when`, `clientIpAddress`, `serverIpAddress`, `userAgent`, `geoLocation`, `headers`, `tenant`. The client address is taken from the `X-Forwarded-For` header by default (`cas.audit.engine.alternate-client-addr-header-name`). `cas.audit.engine.http-request-headers` defaults to `*` (every request header, so the `Cookie` with the ticket-granting cookie, captured for the stores that keep headers). `cas.audit.engine.supported-actions` / `excluded-actions` filter actions by regular expression. `cas.audit.engine.audit-format` is `DEFAULT` (multi-line `WHO: … WHAT: …` blocks, or one line with `|` when `cas.audit.slf4j.use-single-line`) or `JSON`; `cas.audit.slf4j.auditable-fields` defaults to `who,what,when,action,client_ip,server_ip,geo_location`. Destinations: log file (`cas_audit.log`, through the logging configuration), JDBC (table `COM_AUDIT_TRAIL`: `AUD_USER`, `AUD_CLIENT_IP`, `AUD_SERVER_IP`, `AUD_RESOURCE`, `AUD_ACTION`, `APPLIC_CD`, `AUD_DATE`, `AUD_USERAGENT`, `AUD_HEADERS`, `AUD_EXTRA_INFO`…), MongoDB, Redis, DynamoDB, REST and others, several at once. Action names are a base (`AUTHENTICATION`, `TICKET_GRANTING_TICKET`, `SERVICE_TICKET`, `SERVICE_TICKET_VALIDATE`, `SAVE_SERVICE`, `DELETE_SERVICE`, `LOGOUT`, `CHANGE_PASSWORD`, `OIDC_ID_TOKEN`…) plus a suffix chosen by the action's resolver (`_SUCCESS` / `_FAILED` for authentication and validation, `_CREATED` / `_NOT_CREATED` for ticket creation, `_TRIGGERED`…); the exact pairing per action is to verify. Reads through the management (actuator) endpoints are not, to the spike's knowledge, recorded by Inspektr (to verify).
- **Actuator endpoints** (Spring Boot, plus CAS endpoints such as `registeredServices`, `ssoSessions`, `auditLog`): access is set **per endpoint**, not per HTTP method (`cas.monitor.endpoints.endpoint.<id>.access`: `PERMIT`, `ANONYMOUS`, `DENY` by default, `AUTHENTICATED`, `ROLE`, `AUTHORITY`, `IP_ADDRESS`). Several of these endpoints combine read operations with write or delete operations (importing or deleting services, destroying SSO sessions (to verify per endpoint)); Spring Boot 3.4+ can restrict an endpoint to its read operations with `management.endpoint.<id>.access: read-only` (to verify which Spring Boot line CAS 8.0 uses). Their read operations return client secrets (`registeredServices`), ticket-granting ticket ids (`ssoSessions`) and audit records with ticket ids (`auditLog`).

## Decision
1. **Versions in scope.** Maintained CAS lines only ([ADR-0039](0039-engine-scope-expansion.md) decision 1): **8.0.x** at the time of writing, 8.1.x once released; 7.3.x (end of life 2026-12-31) is not supported (open question 1, answered by the maintainer). A line is dropped from the engine matrix at the next DataBastion minor release after its CAS end of life. The connector never contacts CAS (decision 2), so it cannot read the version: it parses the record and definition shapes of the maintained lines, counts what it cannot parse (`audit.records_dropped`, `coverage.registry_files_skipped`), and the engine matrix runs the integration tests against one image per maintained line (`apereo/cas:8.0.x`, then each later maintained line). No version field in `agent.yaml`: a declared version that cannot be checked would only give a false assurance.

2. **Shape: a `connector-cas` crate for the local files, and a CAS store guard in the existing connectors for the stores they already read.**
   - **`connector-cas`** (engine `cas`) reads **local files only**: a JSON or YAML service registry directory and the JSON audit log file, declared in `agent.yaml` (decision 3). It opens **no network connection of any kind** (no HTTP client, no database client): no new network surface, no credential, nothing for I5 to bound beyond the declared paths. It reuses the core's file machinery: the tailer (`audit/tail.rs`: rotation, keyed truncation fingerprints, persisted positions), the refusal of files the agent could write ([ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 8), the per-connector panic guard ([ADR-0029](0029-openldap-connector.md) decision 1) and per-record panic isolation (ADR-0032), Discovery pacing ([ADR-0035](0035-discovery-pacing.md), one file = one unit of work).
   - **CAS stores held in an engine DataBastion supports** (JPA tables in PostgreSQL, MySQL or MariaDB; MongoDB collections; the LDAP service registry) are read by **that engine's connector**, with the account, grants, TLS, pacing and own-account rules it already has, never by a second client in `connector-cas`. What changes there is the **CAS store guard** (decision 5): ticket registry and audit trail credentials are never sampled, and the ticket registry gets a metadata-only probe. The guard is on by default, by name, so it also protects existing deployments where an operator already declared the CAS database as a target.
   - The parsers of CAS data (service definition, audit record) live in one I/O-free module of `connector-cas`, so the existing connectors can later reuse the service definition parser for a JPA, MongoDB or LDAP service registry (decision 4, last item) without a dependency on file reading.

3. **Target declaration (I5, I3).** A `cas` target is a set of absolute local paths, nothing else:

   ```yaml
   targets:
     - id: cas-prod
       engine: cas
       cas:
         service_registry:
           json_dir: /etc/cas/services        # or yaml_dir; at most one
         audit_log:
           path: /var/log/cas/cas_audit.log   # JSON audit format (decision 7)
           timezone: UTC                      # zone of the `when` field, default UTC
         clear_principals: [svc-monitoring]   # at most 64, sent in clear (decision 7)
   ```

   - No `host`, `port`, `socket`, `account` or `secret`: the configuration refuses them for `engine: cas` (`account` and `secret` become optional in the schema, required for every other engine as today, OpenLDAP `sasl_external` excepted). At least one of `service_registry` and `audit_log`.
   - Paths are resolved when the configuration is loaded (symlinks followed once) and refused under the agent's own state, identity and spool directories and under `/proc`, `/sys` and `/dev`; a later change of the resolved target refuses the source until the next reload.
   - **File handling** (security review L1). The registry directory is opened once with `O_DIRECTORY | O_NOFOLLOW` and read **non-recursively**; each entry is opened relative to it with `openat(dirfd, name, O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC)` (symlinked entries fail and are counted), and every check is made with `fstat` on the opened descriptor, never on the path: regular file, owner, mode, size, and **`st_nlink` = 1** (a file with several hard links is skipped and counted: it could be a hard link to a file outside the directory, such as the CAS configuration; security review M1). Only the `.json` (or `.yml` / `.yaml`) extension, at most 4096 files, each at most 1 MiB, read to memory in a `Zeroizing<Vec<u8>>` buffer then parsed (no streaming state kept across `submit()`). The audit log is opened the same way by the core tailer.
   - **A registry directory holding CAS configuration is refused** (security review M1): when the directory contains `cas.properties`, `cas.yml`, `application.yml` or `application.properties` (names compared case-insensitively), the whole source is refused with `privilege.config_readable` (`cas` added to that note's engines): the agent's account can read the directory, so it could probably read those files, which hold every CAS secret. Their content is never opened.
   - **A file is processed only if it is a service definition** (security review M1): its top-level object must have an `@class` in decision 4's closed map and a `serviceId`; otherwise it is skipped and counted (`coverage.registry_files_skipped`) and **none of its values is classified**, so a misplaced file (a key store export, a configuration copy) is never sampled.
   - **Agent-writable files and directories are refused** (ADR-0032 decision 8, extended to the registry): a registry file or directory, or an audit log, owned by the agent's uid, world-writable, or group-writable by one of the agent's groups is not read, and `check()` reports it. Writability is also tested with `faccessat(W_OK, AT_EACCESS)`, which takes POSIX ACLs into account, and **no ancestor directory of a declared path may be writable by the agent** (security review L1). For the registry this is also a least-privilege rule (I4): an agent that can write service definitions could change what CAS releases to whom.
   - **The CAS configuration (`cas.properties`, `cas.yml`, `/etc/cas/config`) is never read**: it holds the database passwords, the ticket and cookie encryption keys and the LDAP bind password. The documentation tells the operator not to give the agent's account read access to it.
   - **No local detection of CAS** ([ADR-0006](0006-target-discovery.md)): CAS runs as a `java` process, and recognizing it would mean reading process command lines, which carry `-D` system properties (often secrets). CAS targets are declared only.
   - File names of the registry (`HR-Portal-10000003.json`) never leave the agent and are never logged; locations come from the content (decision 4).

4. **Discovery: the service registry.**
   - **Parser**: the workspace `serde_json` (and the workspace `serde_yaml_ng` for YAML), deserialized directly through a typed, closed visitor, **never through a generic `serde_json::Value`** first: nodes are counted during deserialization (depth at most 32, at most 65 536 nodes and 4096 array items per file), strings cut to 4096 bytes on a character boundary (security review L5). **YAML**: anchors, aliases and the `<<` merge key refused (alias expansion is the "billion laughs" bound), custom tags skipped and counted; the implementation proves each refusal with a test (security review L8). Comments are accepted only if CAS 8.0 still accepts them in JSON definitions (to verify), by a bounded comment stripper in front of `serde_json`, never by a new lenient JSON crate. A file that fails is skipped and counted (`coverage.registry_files_skipped`), never partly reported. In a Discovery scan, a skipped file is also counted in the existing coverage counters: `skipped_not_readable` when it cannot be opened or is refused, `skipped_unsupported` when it is not a service definition or fails to parse (security review L6).
   - **Locations** (engine `cas`): `database` = `service_registry`; `schema` = the service type from a closed map of `@class` (`cas`, `oauth`, `oidc`, `saml`, `ws_federation`, else `other`); `object` = the service `name` normalized ([ADR-0009](0009-name-normalization-and-item-sanitization.md); a name matched by a classifier or not an `Identifier` becomes `*`, then the numeric `id` is used); `field` = the normalized JSON path, array indices as `[]`, and the keys of data-keyed maps (`properties`, release-policy attribute maps, `requiredAttributes`) collapsed to `*` as MongoDB field paths are ([ADR-0026](0026-mongodb-connector.md) decision 8), so `contacts[].email`, `properties.*.values[]`, `attribute_release_policy.allowed_attributes.*`.
   - **Sampled and classified** (through `job.classify`, so masked samples and fingerprints only, I2): every string value of the definition **except** the credential fields below and the structural ones (`@class`, `id`, `evaluationOrder`, booleans, enums, durations). That covers `contacts`, `description`, `properties` values, static release values, required-attribute values, and the URLs (`serviceId`, `logoutUrl`, `informationUrl`, `privacyUrl`, `metadataLocation`…), where a classifier may still match an embedded e-mail address. **URLs are classified only after removing their userinfo (`user:password@`), query string and fragment** (security review M2): those parts carry credentials and tokens. Per (service type, path), values are pooled across services (one "object" may have one value per field, too few for the classifiers' thresholds); `sampled` counts values, `estimated_rows` the services.
   - **Credential fields are never sampled** (security review M2): `clientSecret`, inline `jwks`, and **any key whose raw name contains**, compared case-insensitively as a substring and before any `*` collapsing, one of `secret`, `password`, `passwd`, `key`, `token`, `credential`, `jwk`, `private`, `keystore`. Over-exclusion (`keyAlias`, `tokenExpiration`) is accepted. A matching key's value, and everything below it, is never sampled. For `clientSecret` the visitor records only the value's form, **without allocating the value** (security review L5): absent, a reference (a Spring expression `${…}` / `#{…}`), encrypted (the cipher executor's output shape, to verify), or **clear**. Nothing of it is sampled, masked or fingerprinted (a fingerprint of a low-entropy secret would be a confirmation oracle on the agent's key holder side, and nobody needs to correlate client secrets). What leaves: the count of services with a clear secret as the target note `security.client_secrets_in_clear` (decision 11) and, once the classifier set has them (decision 12), a presence-only finding per (service type, path) with no masked sample and no fingerprint.
   - **Attribute release (which personal attributes go to which application)** is not a finding: findings say "values of type X are stored here" ([ADR-0016](0016-classifier-semantics-2026-09-1.md): value-based decision), and attribute names are not values. Reporting release flows needs a contract object of its own; open question 3.
   - **The audit log as a Discovery location**: the last 1 MiB of the declared audit log (at most `sample_rows` records), field `who` **of `AUTHENTICATION_SUCCESS` records only** (security review M3: the `who` of a failed authentication is whatever was typed, possibly a password), classified as values (`database` = `audit_trail`, `object` = `audit_log`, `field` = `who`). `what`, `headers`, `userAgent` and the addresses are never sampled. Client addresses have no classifier; that the trail holds them is documented, not reported as a finding.
   - **Registries in an engine already supported** (JPA `RegisteredServices.body`, the MongoDB or LDAP service registry): the CAS store guard of decision 5 does **not** add CAS-aware parsing to those connectors in phase 8; they classify the `body` as text, with the reporting limits of decision 5 (no masked samples, no fingerprints for `secret.*` classifiers). Parsing those bodies with the decision-4 parser (findings per JSON path, credential fields excluded) is a later ROADMAP item (open question 4).

5. **The CAS store guard in the PostgreSQL, MySQL / MariaDB, MongoDB and OpenLDAP connectors.** It stays **on by default** (security review M9).
   - **Ticket registry: metadata and configuration only.** Ticket ids, parent ids, bodies, principal ids and attributes are **never sampled, never read, never reported, never fingerprinted**. The guard recognizes (recognition rules in the last item) the JPA ticket table (`CasTickets`, under the physical name the JPA naming strategy gives it, to verify: `cas_tickets` or `CasTickets`) and the MongoDB ticket collections (names to verify), plus any table or collection the operator lists in the engine target's `cas_stores.ticket_registry` (for custom names). For such an object the connector runs only one bounded aggregate, `SELECT type, count(*) … GROUP BY type` (MongoDB: a `$group` on `type` with a fixed projection), under the usual statement timeout and pacing, and reads nothing else. From it: ticket counts per kind (known class names mapped to `tgt`, `st`, `pt`, `pgt`, `oauth_code`, `oauth_access_token`…, else `other`) and whether **encryption is on**: rows whose `type` is the encoded-ticket class (with crypto on, verified: the stored type is the encoded ticket's class name) against the others. Unencrypted tickets give the note `security.ticket_registry_unencrypted` (count) on that engine target; nothing is sampled, so the object counts as `skipped_unsupported` in the coverage (a kind the connector does not sample; its description gains "CAS ticket registries").
   - **Audit trail table (`COM_AUDIT_TRAIL`) and audit collections**: `AUD_RESOURCE` (ticket ids), `AUD_HEADERS` (cookies) and `AUD_EXTRA_INFO` are never sampled. **`AUD_USER` is classified without masked samples** (counts and fingerprints only; security review M3), because it holds the names typed at failed logins, possibly passwords. `AUD_CLIENT_IP` and the other columns are sampled as usual.
   - **JPA service registry body** (`RegisteredServices.body`): until the CAS-aware parsing of decision 4 lands, values of that column are classified as today but **never kept as masked samples**, and **no fingerprint is kept for a `secret.*` classifier** (security review M4), when the column belongs to a recognized service registry (counts, and fingerprints of non-secret classifiers only), because a masked sample of a JSON body can keep the first characters of a secret value next to a classified one.
   - **OpenLDAP service registry** (security review M5): entries with the CAS registry object class (name to verify against the CAS LDAP service registry schema), or whose `description` attribute parses as a service definition with an `@class` of the closed map, are treated like `RegisteredServices.body` (no masked samples, no fingerprints for `secret.*` classifiers); the `cas_stores` override of the OpenLDAP target applies as on the other engines.
   - **Recognition** (security review M9). The guard matches:
     - **by name**: the built-in names (above), matched after normalization, case-insensitively, and the tables, collections or object classes listed in the engine target's `cas_stores`;
     - **by column shape**: a table or collection with the columns `id`, `type`, `body`, `principal_id` (or `principalId`) and either `parent_id` (`parentId`) or an expiration column is a ticket registry whatever its name; one with `AUD_RESOURCE` and `AUD_ACTION` is an audit trail;
     - **by a ticket-id value tripwire** in the shared sampling path of every connector: a value matching `^(TGT|ST|PT|PGT|OC|AT|RT|[A-Z]{2,4})-\d+-` is dropped **before classification**, and its column or field is then treated as guarded for the rest of the scan (no further value read from it, counted in `coverage.cas_guard_tripped`, a new note). The pattern also matches unrelated identifiers of the same shape: that over-exclusion is accepted.
     The guard matches by name (built-in and `cas_stores`), by column shape, and by a ticket-id value tripwire; a store matching none of them is sampled like any table (residual risk).

6. **Least privilege per backend (I4).**
   - **Files**: the agent runs as its own non-root user; read access through a group without write permission or an ACL (`0640`, owner the CAS user, group `databastion`; the registry directory `0750`). Anything the agent could write is refused (decision 3).
   - **PostgreSQL / MySQL / MariaDB ticket table**: **column privileges only**, never the table: `GRANT SELECT (type, creation_time, expiration_time) ON cas_tickets TO databastion` (column names to verify against the JPA mapping). A query that references only `type` works with that grant, the `id`, `body`, `principal_id` and `attributes` columns stay unreadable by the agent's account. `check()` evaluates the column privileges from the catalog (`has_column_privilege` / `information_schema.COLUMN_PRIVILEGES` and the table grant), never by trying, and reports `privilege.ticket_credentials_readable` when any credential column is readable. The table and its column privileges are re-evaluated **at every heartbeat check**, so a ticket table recreated by a CAS upgrade or schema update (which drops the column grants or replaces them with a table grant) is reported at once; privileges held **through roles and `PUBLIC`** count, as in [ADR-0025](0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) (security review M6).
   - **MongoDB ticket collections**: MongoDB has no field-level privilege; the recommended set is a view projecting `type` only, with `find` on the view and not on the collections (whether `find` on a view alone is enough is to verify; otherwise the guard's aggregate needs `find` on the collections, and `check()` reports `privilege.ticket_credentials_readable`).
   - **Audit trail table**: `SELECT` on its columns except `AUD_RESOURCE`, `AUD_HEADERS` and `AUD_EXTRA_INFO`, same report when they are readable.
   - **Service registry table**: `SELECT` on the table: the body is the definition, client secrets included; the clear-secret count (decision 4) tells the operator to encrypt them.
   - **Grant scope in a database holding CAS stores** (security review M6): `SELECT` is granted **per table**, never schema- or database-wide (`GRANT SELECT ON ALL TABLES IN SCHEMA`, `GRANT SELECT ON db.*`), and no `ALTER DEFAULT PRIVILEGES` covering the CAS owner's tables, because a table CAS creates later (a recreated ticket table) would otherwise be readable in full. `check()` reports a schema- or database-wide grant there as `privilege.ticket_credentials_readable` when it covers a guarded table.
   - **CAS itself**: no CAS account at all (no actuator, decision 9).

7. **Audit: the JSON audit log.**
   - **Source** `cas_audit_log`: the audit log file, written by the CAS `Slf4j` audit destination through its logging configuration, with `cas.audit.engine.audit-format: JSON`, one record per line, each line at most 1 MiB (the core tailer's record cap; a longer line is dropped and counted). The parser is a closed serde visitor on the keys `who`, `what`, `action`, `when`, `clientIpAddress`, `userAgent` (security review L3: `application` is not kept, `userAgent` feeds the event's application); every other key (`application`, `headers`, `serverIpAddress`, `geoLocation`, `tenant`, unknown keys) is skipped without being kept, and **a record with a duplicate key is dropped** (a second `who` or `action` could otherwise override the first). A line that is not one JSON object (the logging layout must write the message alone, `%m%n`; to verify against the CAS default `log4j2.xml`) or lacks `action` or `when` is dropped and counted (`audit.records_dropped`). Records are isolated per line (ADR-0032). The `DEFAULT` multi-line format is not supported (open question 6): `check()` reports `audit.log_format_unsupported` when the file has records but none parses as JSON.
   - **`what` is reduced to closed facts at parse time and never kept**: it can hold a ticket id. From it the parser takes only, for a service ticket record, the service URL's scheme and host, **used only to select a registry entry** (security review L2): only that entry's normalized name (decision 4), or `*`, leaves the agent; the host itself never does. Definitions' `serviceId` patterns are compiled with the Rust `regex` crate under a `size_limit`; a pattern that does not compile (Java-only syntax such as look-arounds or possessive quantifiers) never matches. The ticket id, the path and the query string are dropped. When `what` has no recognizable service or the target has no registry, the object is `*`. The `includeValidationAssertion` setting puts principal attributes in validation records; the parser never reads `what` for validation actions.
   - **Mapping** (closed list; any other action is counted per action base, at most 64 bases kept, and gives no event):

     | CAS action | Access event |
     |---|---|
     | `AUTHENTICATION_SUCCESS` | `connect` |
     | `AUTHENTICATION_FAILED` | `auth_failure` |
     | `SERVICE_TICKET_CREATED` (and the OIDC / OAuth token issuance actions, list to verify) | `read`, object = the service (or `*`), `rows` 1: the principal's released attributes go to that application |
     | `SAVE_SERVICE_SUCCESS`, `DELETE_SERVICE_SUCCESS` | `dcl`, object = `service_registry`: a change of what CAS releases to whom |
     | `TICKET_GRANTING_TICKET_CREATED`, `…_DESTROYED`, `SERVICE_TICKET_VALIDATE_*`, `LOGOUT_*`, everything else | no event (counted) |

   - **Refinement (2026-10-08, CAS follow-ups after phase 8, verified on the CAS 8.0.2 dev service).** The OIDC / OAuth issuance action is `OAUTH2_ACCESS_TOKEN_RESPONSE_CREATED`, written by the token endpoint for every grant (authorization code, `refresh_token`, `client_credentials`, `password`): its `who` is the user (the client id for `client_credentials`) and its `what` holds the token values and no service, so it maps to `read` of `*`, `rows` 1, and counts as issuance for decision 10. An authorization code (or implicit) login also writes `SERVICE_TICKET_CREATED` for the client's redirect URI, so one authorization code login gives two `read` events. `OAUTH2_AUTHORIZATION_RESPONSE_CREATED`, `OAUTH2_ACCESS_TOKEN_REQUEST_CREATED` (`who` `audit:unknown`), `OIDC_ID_TOKEN_CREATED` (its `what` holds the token request's `Authorization` header) and `OAUTH2_USER_PROFILE_CREATED` give no event and their `what` is never decoded. Token-only grants therefore never name the client; a follow-up may name it by matching a registry entry's `clientId` against the token request's `service` (which needs a further refinement of this decision, since it reads more than the issuance record's `service`).
   - **Principals.** `who` names an end user (a login, often an e-mail address), never a database account. As on OpenLDAP ([ADR-0029](0029-openldap-connector.md) decision 7), **every principal is sent as `db_user_fingerprint`** except those listed in `cas.clear_principals` (service and administrator accounts). A failed authentication's name is always fingerprinted (the typed name can be a password). A `who` that is a credential object's string form (`…Credentials@6cd7c975`) or the unknown-principal marker (`audit:unknown`, to verify) is reported with the fingerprint of a fixed `unidentified` token, never parsed further. `clear_principals` refuses the entries `*` and `unidentified` (security review L4).
   - **Client addresses** follow the access-event rules ([ADR-0007](0007-mask-access-events.md)), with a per-target reduction proposed in open question 8: an IPv4 or IPv6 literal sent as `client_addr`, anything else omitted. CAS takes it from `X-Forwarded-For` by default, so it is only as trustworthy as the proxy in front of CAS: `check()` cannot evaluate this, and the documentation says so (residual risk). `userAgent` becomes `application` after the contract's sanitization (first product token only, e.g. `python-requests/2.32`).
   - **Times**: `when` read in the declared `timezone` (default UTC; whether CAS writes an offset is to verify), clamped to the agent's clock as every event ([ADR-0021](0021-access-event-correlation.md), #72).
   - **Failed-login floods.** The CAS login page is usually reachable from the internet, so failed logins can arrive at a rate no database sees. Per client address, the first 16 distinct principals failing within 10 minutes give their own `auth_failure` events; beyond that, failures from that address are aggregated into one event per address and minute with `db_user` `*` (several accounts; a contract text clarification of `Principal`, compatible) and the signal `volume.failed_logins_many_accounts`. **The `*` aggregate exists only on `cas` targets, only for `auth_failure` events carrying that signal** (security review L4). The core's failed-login flood cap and spool priorities (#88) still apply after that.
   - **Window state is bounded** (security review M7): the per-address and per-principal windows of this item and of decision 8 hold at most 4096 entries each, keyed by the address and by the principal's fingerprint only (never the raw `who`), and are not persisted. When a window is full, new failures that would need a new entry are aggregated into one event per minute with `client_addr` omitted, `db_user` `*` and the signal `volume.failed_logins_many_accounts`, and counted (`audit_window_overflow_total`, heartbeat metric).
   - **The agent's own account**: the agent performs no CAS action, so nothing is left out.

8. **Signals** (appended to `signals.json`, engine `cas`; heuristics, evadable by design):
   - `volume.failed_logins_many_accounts`: one client address, failed authentications for at least 16 distinct principals within 10 minutes (credential stuffing, password spraying: the two are indistinguishable without the passwords, which are never seen).
   - `volume.failed_logins_one_account`: one principal (fingerprint), at least 20 failed authentications within 10 minutes, whatever the addresses (online guessing against one account, including from many addresses).
   - Thresholds are constants in phase 8; the console's per-principal baselines and policies do the rest. Bulk reads of the administrative endpoints (`registeredServices`, `ssoSessions`) are **not** detectable from the audit trail (to verify that Inspektr records no actuator read): no signal in phase 8, open question 5.

9. **No actuator endpoint is used.**
   - The endpoints the candidates paragraph names return live credentials on their **read** operations (client secrets, ticket-granting ticket ids, audit records with ticket ids and cookies): reading them would put bearer credentials in the agent's memory for no finding the files and stores do not give.
   - CAS secures endpoints per endpoint, not per operation, so a role that can read `registeredServices` can also use its write operations unless the operator also sets Spring Boot's read-only access, which the agent cannot verify without attempting a write (I4 forbids it).
   - It would add an HTTP client towards a target, a base URL, and a CAS credential to store (I3), for metrics (`health`, `info`) the agent does not need.
   A later ADR may revisit a strictly read-only, secret-free endpoint (for example the version from `info`), with a dedicated role, TLS `verify_full` and the credential kept local; this ADR adds no `base_url` to `agent.yaml`.

10. **Audit levels** (`check()` and the stream share one rule; [docs/08](../08-engine-capabilities.md) definitions).
    - **Never Full.** Full needs every access logged with the user, the object and the volume. CAS's trail covers authentications and ticket issuance, but not reads through the management endpoints, nor reads of the stores themselves (those are audited, at their own level, by the store's engine connector); the action filters (`supported-actions`, `excluded-actions`) and the destinations live in the CAS configuration, which the agent must not read (decision 3), so completeness cannot be proven; and `what` must be dropped, so the object of many records is unknown.
    - **Partial** once an `AUTHENTICATION_SUCCESS` record **and** a service-ticket or token issuance record (`SERVICE_TICKET_CREATED`, or an OIDC / OAuth issuance action of decision 7) have both been parsed in the last 24 h (security review M8): the `read` events of decision 7 come only from the latter. Failed authentications cannot be provoked by the agent (that would mean posting to the login form) and may legitimately not occur for days: when none was parsed in the last 7 days, the level stays Partial with the note `audit.auth_failures_not_seen`, which tells the operator to check that `AUTHENTICATION_FAILED` is not excluded.
    - **Limited** once any valid record has been parsed in the last 24 h but not both kinds above: no successful authentication (ticket records only, or authentication actions excluded), with `audit.auth_records_not_seen`; or successful authentications but no service-ticket or token issuance record, with `audit.service_ticket_records_not_seen` (new).
    - **None** before any record (`audit.limited_pending_first_record`), when the file is not readable or refused (`audit.log_not_readable`), when its format is not JSON (`audit.log_format_unsupported`), or after the stream is stopped (`audit.stream_stopped`).
    The freshness rule mirrors MongoDB's `auditLog` ([ADR-0030](0030-mongodb-auditlog-freshness.md)).

11. **`check()` of a `cas` target** (closed notes, counts only, appended to `target-notes.json` with engine `cas`; existing codes get `cas` added to their engines): reachability = at least one declared source readable; `audit.log_not_readable`, `audit.log_format_unsupported` (new), `audit.limited_pending_first_record`, `audit.auth_records_not_seen` (new), `audit.auth_failures_not_seen` (new), `audit.service_ticket_records_not_seen` (new), `audit.records_dropped`, `audit.stream_stopped`, `coverage.registry_files_skipped` (new: unreadable, refused, too large, unparsable), `security.client_secrets_in_clear` (new), `security.audit_headers_logged` (new: records carry a `headers` key, so the log holds cookies; the parser skips it), `privilege.registry_writable` (new: a registry file or the directory is writable by the agent and therefore refused), `privilege.config_readable` (existing code, `cas` added: CAS configuration files in the registry directory, decision 3), `check.stage_failed`, `check.timed_out`. On the engine targets holding CAS stores: `security.ticket_registry_unencrypted` (new) and `privilege.ticket_credentials_readable` (new), re-evaluated at every heartbeat check (decision 6), and `coverage.cas_guard_tripped` (new, decision 5). The check reads at most 64 KiB of the audit log's tail and lists the registry directory; it uses at most 5 s.

12. **Protocol (P8-C, compatible under [ADR-0022](0022-protocol-capability-negotiation.md)).** `cas` is added to `Engine` and `Connector`, `cas_audit_log` to `AuditSource`, and `ConnectorList.maxItems` grows, all behind the capability token of ADR-0039 decision 8 (e.g. `engine.cas`): until the console lists it, the agent reports no `cas` target, finding or event, and `check()` logs that the console is too old. The `Location` description gains the `cas` mapping of decision 4 (text). The two signals of decision 8 are appended to `signals.json` and the notes of decision 11 to `target-notes.json` (form-only registries, no negotiation). The `Principal` description states the `*` aggregate of decision 7. New classifier ids for presence-only credential findings (`secret.client_secret`, `secret.private_key`) go into the next classifier set, following the ADR-0016 process, not into `2026.09.1`.

13. **Client criteria ([ADR-0039](0039-engine-scope-expansion.md) decision 4).** No client: `connector-cas` speaks no protocol. Its dependencies are workspace crates only (`serde`, `serde_json`, `serde_yaml_ng`, `regex`, `zeroize`, the core): no new license, no TLS, no MSRV change, no process spawned. Every parser (service definition JSON / YAML, audit record JSON, the `what` reducer) gets property tests (no input byte sequence survives into an event or a log line except closed facts) and a fuzz target, and the crate denies `clippy::string_slice` and `clippy::indexing_slicing` outside tests, as `connector-openldap` does.

14. **I2 and test obligations** (ADR-0039 decision 9, P8-D).
    - **Dev service**: the `apereo/cas` image of the maintained line, with a mounted JSON service registry (`dev/cas/services/`, fake contacts, a fake OIDC client with a clear secret and one with an encrypted secret, static release values and required-attribute values from the ground truth), static fake users, `audit-format: JSON` to `dev/.state/logs/cas/cas_audit.log` (readable by the agent's group, not writable), and entries in `dev/ground-truth.json` (contact names, e-mail addresses, phone numbers, the fake client secrets, the fake users' logins). Whether the published image accepts mounted configuration and the JSON registry without building a CAS overlay is to verify (open question 7). The JPA ticket table on the dev PostgreSQL, to test the guard, needs the JPA ticket registry module in the image.
    - **I2 check**: no ground-truth value in clear in the console database, including **the client secrets and any ticket id** issued during the run (the test collects the `TGT-` / `ST-` ids it obtained and asserts that none of them, nor their SHA-512, is in the console database, the agent's logs or the spool); principals only as fingerprints except `clear_principals`.
    - **End-to-end**: a CAS target with a Discovery scan (findings on `contacts[].email`, a static release value, the clear-secret note) and an Audit scenario: successful logins (`connect`, Partial), a credential-stuffing burst from one address (`volume.failed_logins_many_accounts`), and a service ticket issued (`read` on the service); the reported level must be Partial with the right notes.
    - **Load**: a run in `e2e/load/` with a CAS login workload (successful and failed authentications at a fixed rate): events stored against records written (within 1 %), the agent's CPU and RSS, and no added CAS latency; there is no database to measure for the file sources. The guard's ticket aggregate is measured on the PostgreSQL ticket table with a scaled ticket count.
    - **Guard tests** (decision 5): integration tests on each engine with a ticket table under a non-built-in name (recognized by its column shape), a plain table holding ticket-id-shaped values (the tripwire drops them before classification and guards the column), a `COM_AUDIT_TRAIL`-shaped table, an OpenLDAP registry entry, and a ticket table recreated after its column grants were set (reported at the next heartbeat); none of the ticket ids reaches a finding, a log line or the spool.
    - Integration tests against `dev/`, and the engine matrix per maintained CAS line (decision 1).

## Consequences
- A new crate, `agent/crates/connector-cas`, with no network code; `agent.yaml` gains `targets[].cas` and `targets[].<engine>.cas_stores`; `account` and `secret` become optional in the schema (refused for `cas`).
- The PostgreSQL, MySQL / MariaDB, MongoDB and OpenLDAP connectors gain the CAS store guard (by name, by column shape, ticket-id value tripwire in the shared sampling path, metadata-only aggregate, column privilege checks at every heartbeat). This touches connectors already released: their behavior changes for tables shaped or named like CAS stores and for columns holding ticket-id-shaped values (no longer sampled), which is a CHANGELOG entry.
- **Forward obligation for phase 9** (security review L7): the Redis / Valkey connector applies the CAS store guard to key names: keys matching the ticket-id shape of decision 5 are never reported, not even as normalized patterns.
- The protocol changes of decision 12 (P8-C, `security-reviewer` review).
- A CAS target never reaches Full, and its Partial means "authentications and ticket issuance are logged", not "every read of personal data is logged"; the store reads are audited by the store's engine connector at that engine's level. The README row and docs/08 must say both.
- docs-keeper (after the implementation): an "Apereo CAS" section in [08-engine-capabilities.md](../08-engine-capabilities.md) (sources, levels, notes, what is never read), recommended file permissions and column grants in [05-security.md](../05-security.md#recommended-database-accounts-read-only), the CAS configuration the agent needs (`audit-format: JSON`, `auditable-fields` without `headers`, a log layout writing the message alone, ticket registry `crypto.enabled: true`, encrypted client secrets) in [10-user-guide.md](../10-user-guide.md).

### Residual risks
- **Client addresses from `X-Forwarded-For`**: when CAS is reachable without a proxy that overwrites the header, attackers choose their logged address, which poisons per-address signals and baselines. Per-principal signals (`volume.failed_logins_one_account`) do not depend on it.
- **Stores matching no guard rule**: a ticket or audit store under an unknown name, with an unexpected column shape and no ticket-id-shaped value in the sample read before the tripwire fires, is sampled like any table (values read in the agent's memory; only masked samples of classified values leave, and ticket ids match no classifier). The tripwire fires only after reading one such value.
- **`X-Forwarded-For` rotation** (security review M7): an attacker who controls the logged address can rotate it per attempt and evade `volume.failed_logins_many_accounts`; `volume.failed_logins_one_account` still sees guessing against one account.
- **Ticket registry encryption probe**: relies on the encoded-ticket class name in `type`; a backend or version that stores tickets differently is reported as "not evaluated" rather than guessed.
- **Unsalted digests with crypto on**: the JPA registry stores SHA-512 of principal ids without a key; a reader of the table can confirm a guessed user name. Not the agent's concern (it never reads those columns), but worth the documentation.
- **Credential form detection**: a clear secret that happens to look like the encrypted form is counted as encrypted.
- **Inspektr filters invisible**: an `excluded-actions` setting that drops failures or ticket records shows only through the notes of decision 10, after days.
- **No version check**: an unmaintained CAS line is not refused at run time; only the documentation and the engine matrix state the supported lines.

## Rejected alternatives
- **`connector-cas` with its own database, MongoDB and LDAP clients** for the stores: a second connection, credential and grant set for engines that already have a hardened connector, duplicated pacing and own-account rules, and a new client surface (ADR-0039 decision 4) for nothing the existing connectors cannot do.
- **A CAS profile of the existing connectors only, no new crate**: the JSON / YAML registry and the audit log are files on the CAS host, often without any database; bolting file reading onto a database connector mixes two engines' semantics in one target and gives no `cas` engine for the console to show the level.
- **The actuator endpoints** (`registeredServices`, `ssoSessions`, `auditLog`): decision 9.
- **Reading the CAS configuration** to prove crypto, audit filters or destinations: it holds every CAS secret; the agent would become the easiest way to steal them.
- **Provoking a failed login to prove failures are logged** (as the OpenLDAP absent-entry probe does): it is an action on the identity service (a lock-out counter, an alert at the customer's SOC), needs a base URL and network access, and still would not prove the other actions are logged.
- **Reading or fingerprinting ticket ids**, even hashed: they are live bearer credentials; a keyed hash still requires reading them, and no use case needs to correlate tickets in the console.
- **Parsing the `DEFAULT` multi-line audit format**: field boundaries depend on the content (a `what` holding a newline shifts the next fields), so a hostile value could forge fields; JSON gives a closed shape. Open question 6.
- **Sending principals in clear**: CAS principals are end users, as OpenLDAP entry DNs are (ADR-0029 decision 7).
- **Local detection of CAS through `java` command lines**: reads `-D` properties, which often carry secrets.
- **Reporting attribute release policies as findings**: misuses the finding model (decision 4).

## Open questions (for the maintainer)
Each question carries the `security-reviewer`'s recommendation as a proposed answer; none is decided until the maintainer confirms it.

1. **7.3.x**: drop it from the start (end of life on 2026-12-31, likely before the connector ships) or test it until that date?
   **Answer (confirmed by the maintainer on 2026-10-04)**: drop it; 8.0.x and later maintained lines only.
2. **Principals of successful authentications**: fingerprint them, or send logins in clear because the console's operators are the identity team anyway?
   **Answer (confirmed by the maintainer on 2026-10-04)**: fingerprint every principal except `clear_principals`, as on OpenLDAP (decision 7).
3. **Attribute release flows** ("application X receives `mail`, `supannEtuId`"): worth a contract object?
   **Answer (confirmed by the maintainer on 2026-10-04)**: later, not in phase 8; attribute names only, from a closed normalized set, through an optional item negotiated under [ADR-0022](0022-protocol-capability-negotiation.md); never values.
4. **CAS-aware parsing of registries held in databases** (JPA `body`, MongoDB, LDAP) and the **JDBC / MongoDB audit trail as an Audit source**: phase 8, or ROADMAP follow-ups?
   **Answer (confirmed by the maintainer on 2026-10-04)**: follow-ups; but the guard parts of decision 5 for those stores (no masked samples and no `secret.*` fingerprints for `RegisteredServices.body` and the OpenLDAP registry entries, security review M4 / M5) are in phase 8. A future JDBC audit source reuses the `what` reducer of decision 7 and never selects `AUD_RESOURCE`, `AUD_HEADERS` or `AUD_EXTRA_INFO`.
5. **Bulk reads of the administrative endpoints**: an optional servlet access log source?
   **Answer (confirmed by the maintainer on 2026-10-04)**: later, in its own ADR: a fixed, declared log layout; only the method and the endpoint id kept, path parameters and query string dropped at parse time; layouts that log `Cookie` or `Authorization` refused.
6. **`DEFAULT` audit format**: support the single-line `|` form with a strict field count, or require JSON?
   **Answer (confirmed by the maintainer on 2026-10-04)**: require JSON. The single-line `|` form can be forged: `who` (typed by the user at a failed login) and `userAgent` are attacker-controlled and can contain the separator.
7. **Dev image**: if `apereo/cas` cannot take the JSON registry, JSON audit and JPA ticket registry by mounted configuration, a CAS overlay build is needed.
   **Answer (confirmed by the maintainer on 2026-10-04)**: a CI overlay build from pinned sources, with a digest-pinned output, is acceptable. A published image is dev-only, never part of the release assets, and carries fake secrets only.
8. **Client addresses**: CAS trails hold every end user's address, many more people than database clients.
   **Answer (confirmed by the maintainer on 2026-10-04)**: an agent-side per-target option `client_addr: clear | truncated | omitted`, default `truncated` for `cas` targets (IPv4 /24, IPv6 /56); signals are computed on the full address before the reduction. It needs a text clarification of `ClientAddress` (a truncated address is still an address literal) and a short refinement of [ADR-0007](0007-mask-access-events.md); no schema change.
9. **Thresholds** of decision 8 (16 accounts, 20 failures, 10 minutes): constants, or `agent.yaml` limits?
   **Answer (confirmed by the maintainer on 2026-10-04)**: constants in phase 8; if they become configurable later, bounded with floors so they cannot be set to silence the signals.
