## Context

### What the agent does today

Read from the code at `42bfd8c` (`dev`).

- **Catalog rule.** A relation in `pg_catalog`, `information_schema`, `pg_toast` or a temporary schema is a catalog (`is_catalog`), and so is an unqualified `pg_*` name under the `pgaudit.log_catalog` rule. A read whose relations are all catalogs gives no event, on both sources, for every account. The exceptions are the five statistics relations of ADR-0048 (`STATISTICS_RELATIONS`, `pg_statistic_ext_data` among them) and the statement-text views and functions of ADR-0049.
- **So these reads give no event today, from any account:** `SELECT rolname, rolpassword FROM pg_authid`, `SELECT passwd FROM pg_shadow`, `SELECT umoptions FROM pg_user_mappings`, `SELECT subconninfo FROM pg_subscription`, `SELECT data FROM pg_largeobject`, `SELECT setconfig FROM pg_db_role_setting`, `SELECT rolconfig FROM pg_roles`. A statement that also names an application table is an event naming that table only, under the `audit.configure` filters.
- **Already handled elsewhere**: `pg_statistic_ext_data` and `pg_statistic` are ADR-0048 relations; `lo_get`, `loread`, `lo_export`, `lo_import`, `pg_read_file`, `pg_read_binary_file`, `pg_read_file_old`, `query_to_xml`, `table_to_xml` and the other functions of ADR-0049 decision 7 add `*`, always reported, also next to catalogs only; a user function next to catalogs only adds `*` (ADR-0049 decision 8).
- **What the connector itself reads.** `sql.rs` reads `pg_catalog.pg_roles` in four `check()` statements (`ROLE_ATTRIBUTES`, `MEMBERSHIPS`, `OWNERSHIP`, `OWN_OIDS`), always through the alias `r` and named columns (`r.rolsuper`, `r.rolname`, `r.oid`…), never `rolpassword` or `rolconfig`, never `*` except `pg_catalog.count(*)`. It names none of `pg_authid`, `pg_shadow`, `pg_user_mapping`, `pg_subscription`, `pg_largeobject`, `pg_db_role_setting`, `setconfig`, `srvoptions`, `rolpassword`, `rolconfig`: the unit test `no_statement_touches_the_catalog_denylist` (ADR-0012 obligation 1) fails on any of them. It also reads `pg_catalog.pg_proc` (the row-level security policy check, `OWNERSHIP`, the audit prerequisites and the per-database collision probe of ADR-0049 decision 8), by named columns, never `proconfig`; the collision probe uses column alias lists (`AS s(f)`, `AS a(t)`, `AS k(k)`, `AS i(i)`, `AS v(u, b)` over a `VALUES` of column references). The ADR-0012 refinement proposed with this ADR adds one statement that reads two keys of `pg_db_role_setting.setconfig` (decision 5).

### What the servers expose (verified on PostgreSQL 16.13 on 2026-10-12)

A throwaway cluster (PostgreSQL 16.13 with pgaudit 16.0, `pg_stat_statements` 1.10 and `postgres_fdw`; `pgaudit.log = 'read,role,ddl,misc_set'`, `log_relation`, `log_rows` and `log_catalog` on, jsonlog), seeded with fake markers: SCRAM passwords for two login roles, a `postgres_fdw` server and two user mappings with passwords, a subscription created with `connect = false` whose connection string holds a password, a large object, `ALTER ROLE app SET app.api_key = '…'`, `ALTER DATABASE postgres SET app.jwt_secret = '…'` (the pattern PostgREST's documentation used for its JWT secret), and per-role log overrides. Roles: `app` (owner of a user mapping, `USAGE` on the server), `other`, `rad` (`pg_read_all_data`), `stats` (`pg_read_all_stats`), `settings` (`pg_read_all_settings`), and `agent` (`pg_read_all_stats` only, the ADR-0012 minimal variant). The cluster was deleted afterwards. After the security review of PR #215, a second throwaway cluster of the same build verified `pg_proc.proconfig`, `pg_hba_file_rules` (with fake `radius` and `ldap` lines) and `pg_parameter_acl`, and was deleted too. **Not run on 14, 15, 17 and 18**: the drift and pinning tests of decision 8 verify them before the implementation is merged.

Considered and **not listed**:

- `pg_largeobject_metadata` (oid, owner, ACL; every role): no value.
- `pg_replication_origin` (`roident`, `roname`, `pg_16440` here; every role): a name, no credential.
- `pg_statistic_ext_data`, `pg_statistic`: values, already ADR-0048 relations; unchanged.
- `pg_read_file` and the other functions of ADR-0049 decision 7, `lo_*`: already `*`; unchanged.
- `pg_settings`, `SHOW`, `current_setting()`: the reading session's own settings. Two facts matter (open questions 6 and 7): `primary_conninfo` (password included) is readable in clear by `pg_read_all_settings` members (`pg_monitor` includes it) through `pg_settings` and `SHOW` (verified); and a database-level custom setting is readable by **every role connected to that database** through `current_setting('app.jwt_secret')` (verified), so `ALTER DATABASE … SET` is no place for a secret whatever this ADR decides.
- `pg_foreign_data_wrapper.fdwoptions`, `pg_foreign_table.ftoptions`, `pg_attribute.attfdwoptions` (every role): FDW, table and column options; credentials only for FDWs that keep them at those levels (not checked; open question 3).
- `pg_stat_wal_receiver.conninfo`: the password is obfuscated (PostgreSQL documentation; not run here, no standby).
- `pg_proc.prosrc` (function bodies, every role): code. A body can hold a hard-coded credential (the `dblink_connect('… password=…')` antipattern), but `prosrc` is read constantly by `psql`'s `\df+` and `\sf`, `pg_dump`, IDEs and migration tools; not listed (open question 10).
- `pg_description` (comments) and `pg_ident_file_mappings` (user name maps, no secret): out of scope.

### What the audit sources record (verified on 16.13)

- **pgaudit, `log_catalog = on`**: a `READ` record with the text as sent, and with `log_relation` one relation record per relation **including the relations behind a view**. A read of `pg_roles` gets `VIEW pg_catalog.pg_roles`, `TABLE pg_catalog.pg_authid` and `TABLE pg_catalog.pg_db_role_setting`, whatever columns it selects (`SELECT rolname FROM pg_roles WHERE rolsuper` included); `pg_shadow` and `pg_user` get `pg_authid` and `pg_db_role_setting`; `pg_user_mappings` gets `pg_user_mapping`, `pg_foreign_server` and `pg_authid`; the `information_schema` views get their `_pg_*` views and the tables behind them. A user view `public.v_pw AS SELECT rolname, rolpassword AS p FROM pg_catalog.pg_authid` gets `VIEW public.v_pw` and `TABLE pg_catalog.pg_authid`. ADR-0049 found the same for `pg_stat_activity` (`pg_authid` behind it).
- **pgaudit, `log_catalog = off`**: a read of `pg_authid` or `pg_shadow` alone is **not logged**; a read of `information_schema.user_mapping_options` **is** logged, with its `information_schema` records only; a read of `public.v_pw` is logged with `VIEW public.v_pw` only (the `pg_catalog` record is left out).
- **`pg_stat_statements`**: one entry per normalized text and role; identifiers kept, constants replaced by `$n`.

### Who reads these catalogs routinely

From the tools' documentation and common practice, not measured here:

- **`pg_roles` and `pg_user`**: very often, without the settings column: `psql`'s `\du`, ORMs and migration tools checking a role, Patroni, exporters, the connector's own `check()`. Admin tools that browse roles read `rolconfig` or `*` (pgAdmin's role properties; DBeaver reads `pg_roles` with `a.*`).
- **`pg_db_role_setting`**: `psql`'s `\drds`, pgAdmin's role and database properties, `pg_dumpall` and `pg_dump --create` (to dump `ALTER ROLE … SET` and `ALTER DATABASE … SET`).
- **`pg_authid` and `pg_shadow`**: `pg_dumpall` reads `rolpassword` unless `--no-role-passwords`; PgBouncer's default `auth_query` is `SELECT usename, passwd FROM pg_shadow WHERE usename=$1` for client logins (its documentation recommends wrapping it in a `SECURITY DEFINER` function); superuser scripts.
- **`pg_user_mappings`, `pg_foreign_server`, `pg_subscription`**: `psql`'s `\deu+`, `\des+`, `\dRs+`, `pg_dump` (which reads `subconninfo` and the mapping options); logical replication monitoring reads `pg_subscription` names and states. `postgres_fdw` and the subscription workers read their options internally, not through SQL.
- **`pg_largeobject`**: rarely by SQL; `pg_dump` and applications use the `lo_*` functions.
- **`pg_proc`**: very often, without `proconfig`: drivers (procedure metadata), ORMs, `psql`'s `\df`, IDEs, and the connector itself (decision 5). `pg_dump` and admin tools that show a function's properties read `proconfig`.
- **`pg_hba_file_rules`**: DBAs and configuration checkers, on demand.

### Who can read, and why reporting them still matters

Most of these need a superuser or `pg_read_all_data`. Reporting their reads is still worth it: `pg_read_all_data` is commonly granted to reporting and backup accounts whose credentials sit in tools and scripts, and a compromised administrator or backup account harvesting SCRAM verifiers (offline cracking; an MD5 hash is a login credential where `md5` authentication remains), FDW and subscription passwords (access to other servers) is credential theft that no source reports today. The event says who read them and when, which the console can alert on. Others need **no privilege at all**: every role reads every role's and database's settings (`pg_db_role_setting`, `pg_roles.rolconfig`), and a mapped role reads its own remote password; there the event shows an application account doing what applications never do.

## Options

- **(a) A closed list, every read reported**, named as objects, always reported, never the agent's own (ADR-0048).
- **(b) The same, but a read that provably selects no secret column stays quiet**, with a fail-closed shape per entry (ADR-0049 decision 2).
- **(c) Report by reader** (only roles that can read the secrets).
- **(d) Document only** (the current state).

(c) does not hold: the sources do not record what the reader held, and for `pg_db_role_setting` and `pg_roles` every role can. (d) leaves credential reads unreported. (a) would make every `pg_roles` read an always-reported event: it is one of the most read catalogs (`\du`, ORMs, exporters, the connector's own `check()` at every heartbeat), mostly without `rolconfig`. (b) keeps (a) for everything it cannot prove.

## Decision: option (b)

1. **The closed list, identical on PostgreSQL 14 to 18** (the drift test of decision 8 confirms it per image). Each entry has its secret columns; entries with a shape exemption stay quiet in the no-secret shape of decision 2.

   | Name in the text | Kind | Named in events as | Secret columns | Shape exemption |
   |---|---|---|---|---|
   | `pg_authid` | table | `pg_catalog.pg_authid` | `rolpassword` | yes |
   | `pg_shadow` | view | `pg_catalog.pg_shadow` | `passwd`, `useconfig` | yes |
   | `pg_roles` | view | `pg_catalog.pg_roles` | `rolconfig` | yes |
   | `pg_user` | view | `pg_catalog.pg_user` | `useconfig` | yes |
   | `pg_db_role_setting` | table | `pg_catalog.pg_db_role_setting` | `setconfig` | yes |
   | `pg_user_mapping` | table | `pg_catalog.pg_user_mapping` | `umoptions` | yes |
   | `pg_user_mappings` | view | `pg_catalog.pg_user_mappings` | `umoptions` | yes |
   | `pg_foreign_server` (uncertain, open question 3) | table | `pg_catalog.pg_foreign_server` | `srvoptions` | yes |
   | `pg_subscription` | table | `pg_catalog.pg_subscription` | `subconninfo` | yes |
   | `pg_proc` | table | `pg_catalog.pg_proc` | `proconfig` | yes |
   | `pg_largeobject` | table | `pg_catalog.pg_largeobject` | every column | no |
   | `pg_file_settings` (uncertain: superusers only, who can read files anyway) | view | `pg_catalog.pg_file_settings` | every column | no |
   | `pg_show_all_file_settings(` (same) | set-returning function | `pg_catalog.pg_file_settings` | every column | no |
   | `pg_hba_file_rules` | view | `pg_catalog.pg_hba_file_rules` | every column | no |
   | `pg_hba_file_rules(` (same; `pg_hba_file_rules()` with no argument on 16.13, the signature to verify on the other majors) | set-returning function | `pg_catalog.pg_hba_file_rules` | every column | no |
   | `information_schema.user_mapping_options` | view | as named | every column | no |
   | `information_schema._pg_user_mappings` | view | as named | every column | no |
   | `information_schema.foreign_server_options` (uncertain, with `srvoptions`) | view | as named | every column | no |
   | `information_schema._pg_foreign_servers` (same) | view | as named | every column | no |

   - Names are compared after the analyzer's identifier folding and `U&"…"` decoding, as in ADR-0048 and ADR-0049: a quoted `"PG_AUTHID"` or a `public.pg_authid` is an ordinary relation, reported as today.
   - An unqualified `pg_*` name of the list is the catalog's (`pg_catalog` comes first in the search path unless a session lists it later): over-reported, never missed. An unqualified name of an `information_schema` entry (a session with `information_schema` in its `search_path`) is a secret read named as the text gives it, with no schema, as ADR-0049's extension list does: a user relation of that name is over-reported.
   - The function form is named by its view (ADR-0049 decision 1, open question 4 there).
   - `pg_statistic_ext_data` stays an ADR-0048 relation, and the functions of ADR-0049 decision 7 stay `*`.
2. **The no-secret shape, quiet for every account** (entries with a shape exemption only). A statement that names such an entry stays a catalog read for it (no object, so no event when the other relations are catalogs too) only when **all** the conditions of ADR-0049 decision 2 hold, as refined by its items 2 and 3 (the `VALUES` alias list of constants, parenthesized join aliases), with the secret columns of **every** listed entry the text names in place of `query`:
   - the text lexes completely, is not cut, and is below the analyzer's 16-relation bound;
   - no identifier token, quoted or not, after folding and `U&` decoding, equals a secret column of the table above, anywhere in the text (a select list, `WHERE`, `ORDER BY`, `USING (…)`, an alias `AS setconfig`: over-reported). A comparison is a read: `WHERE rolpassword LIKE 'md5%'` answers a question about the secret;
   - no `*` token, except the exact sequence `count(*)`;
   - no whole-row reference through the range variables of the listed items (aliases, or the bare name when unaliased, qualified or not), nor through parenthesized join aliases: `SELECT r FROM pg_roles r`, `row_to_json(r)`, `r::text`, `(r).*`, `SELECT pg_db_role_setting FROM pg_db_role_setting`, a cast to the row type;
   - no column alias list anywhere in the text (except ADR-0049 item 2's `VALUES` of constants), no `NATURAL` join, no `TABLE` form on a listed entry;
   - **no `COPY` that names a listed entry** (`COPY pg_catalog.pg_db_role_setting TO STDOUT` copies every column; added here: the ADR-0049 core list has no table that `COPY` accepts);
   - **the text decides only when every relation it names is a catalog, a listed entry of this ADR, or a core-list entry of ADR-0049** (ADR-0049 re-review N2): a statement that also names an application table, a user view, a materialized view or a function in `FROM` outside `pg_catalog` is a secret read whatever its shape;
   - **no call that is not built in** (ADR-0049 item 7 and decision 8: a schema-qualified call outside `pg_catalog` and `information_schema`, or an unqualified call, operator or cast that decision 8 does not prove built in for that database): `SELECT a.rolname, public.f() FROM pg_authid a` is a secret read.

   Anything else that names a listed entry is a **secret read**: the entry's object of decision 1, kept in the event even when every other relation is a catalog, in every action class (`CREATE TABLE t AS SELECT rolpassword FROM pg_authid`, `INSERT INTO t SELECT …`, `COPY (SELECT …) TO STDOUT`). A listed entry read in the no-secret shape **counts as a catalog** for the rest of the rules (the catalog-only skip, ADR-0049 decisions 2 and 8); read outside it, it is a named object, not a catalog, like the ADR-0048 relations.

   The shape covers the common reads (`SELECT r.rolname FROM pg_roles r WHERE r.rolsuper`, `psql`'s `\du`, `SELECT subname, subenabled FROM pg_subscription`, `SELECT srvname FROM pg_foreign_server`, `SELECT p.proname, p.prorettype FROM pg_proc p`) and the connector's statements on `pg_roles` and, after the rewrite of decision 5, on `pg_proc`.
3. **pgaudit relation records** (verified: records name the tables behind every view). A relation record of a listed entry that the statement text does not name makes the event a secret read naming that entry, always reported, **only when** the same substatement also has a record of a view, a materialized view, a foreign table or a function-derived relation **outside `pg_catalog` and `information_schema`** (a user view such as `public.v_pw` can expose a secret column under another name), or when the text names no relation. Records behind the built-in views (the `pg_authid` and `pg_db_role_setting` records of every `pg_roles` read, the `pg_authid` record of every `pg_stat_activity` read) are **not** enough on their own: the text rule judges those views, which are listed themselves when they expose a secret column (`pg_roles`, `pg_user`, `pg_shadow`, `pg_user_mappings`, the `information_schema` entries), and the drift test of decision 8 keeps it so. As in ADR-0048 (MariaDB's internal statistics loads), a record that every read of a common view produces cannot decide alone. A record of a listed entry the text names keeps the shape decision of the text. **Over-report, accepted** (security review of PR #215, L2): a user view over `pg_roles` that selects no secret column (`CREATE VIEW public.v AS SELECT rolname FROM pg_roles`) still gets `pg_roles`, `pg_authid` and `pg_db_role_setting` records next to its `VIEW` record, so every read of it is a secret read naming those three entries. The records do not say which columns the view exposes; the rule fails closed, and the noise is limited to such user views (one event per principal and window). A function body gets its own substatement and text (ADR-0049 refinement item 4) and is judged by the same rules.
4. **Always reported.** A secret read carries the agent-internal always-reported mark (`MaskedEvent::always_report`), so the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops it, as in ADR-0045, ADR-0048 and ADR-0049: one row holds a verifier, a password or a server's connection string, and the pgaudit log without `log_rows` has no row count. The row count, when the source has one, is kept. No signal is added.
5. **The agent's own account.**
   - **The four `check()` statements on `pg_roles`** (`ROLE_ATTRIBUTES`, `MEMBERSHIPS`, `OWNERSHIP`, `OWN_OIDS`) have the no-secret shape (alias `r`, named columns, `count(*)` only, a CTE `me` that selects `r.oid` only, no column alias list): they stay catalog reads for every account, as today. A unit test proves it for each.
   - **The statements on `pg_proc`** must have the no-secret shape too (security review of PR #215, L1 and C1). The policy check, `OWNERSHIP` and the audit prerequisites already have it (aliases, named columns, `count(*)`). The ADR-0049 decision 8 collision probe does not: its column alias lists (`AS s(f)`, `AS a(t)`, `AS k(k)`, `AS i(i)`, `AS v(u, b)`) break decision 2. **The probe is rewritten without column alias lists** (the preferred way, decided by the review): a single-column function alias without a list (`unnest(…) AS f`, `generate_series(…) AS k`), and the `VALUES` of column references as a `UNION ALL` of selects, so that it is quiet as a shape read and needs no own-statement rule. **Only as a fallback**, if a part cannot be rewritten, the probe is left out as an own statement by its exact text, tied to the agent's identity on both sources: on pgaudit, the text as sent from the agent's account, `application_name` and client address; on `pg_stat_statements`, the stored text equal to its `pss_form`, from the agent's role, top level, in a declared database. The fallback is safe on `pg_stat_statements` too, unlike the two-key reads, because the probe's normalized text names no secret column and no whole row, so no change of constants can make it read `proconfig`.
   - **The two-key read of `pg_db_role_setting`** of the [ADR-0012 refinement of 2026-10-12](0012-postgresql-agent-grants.md#refinement-2026-10-12-accepted-a-two-key-read-of-pg_db_role_setting) names `setconfig`: it is a secret read, left out uncharged only **by exact text on pgaudit** (the whole text as sent, with its constants, from the agent's account, `application_name` and client address, with no signal and no relation record of another listed entry), under a new own kind. **It is never left out on `pg_stat_statements`**: there its constants are stored as `$n` (verified: the key list becomes `ANY ($10::pg_catalog.text[])`), so a replay with other keys has the same stored text and would read other settings unseen. The refinement therefore sends it only while pgaudit is the source the target's level depends on and **no `pg_stat_statements` stream of the target runs** (security review of PR #215, L3: otherwise it would be reported there at every probe); one sent while the source changes is reported (loud, never quiet). Its constants are literals in the text, never bound parameters: pgaudit logs the text as sent, and with `log_parameter = off` (ADR-0012) a bound parameter would not be in the record, so a replay with other parameters would match.
   - **The function-`SET` read of `pg_proc.proconfig`** (`FUNCTION_LOG_OVERRIDES`, the ADR-0012 refinement's answer to its question 3, security review C1) names `proconfig`: it follows exactly the rules of the two-key read above. It is left out uncharged only by exact text on pgaudit, with the agent's identity; it is never left out on `pg_stat_statements` (its constants are `$n` there too); it is not sent while a `pg_stat_statements` stream of the target runs; its constants are literals in the text.
   - **Never the agent's own otherwise.** Any other secret read with the agent's identity is reported and never charged to the row budget: the connector sends no other statement to the list. This covers a stolen agent credential of the extended variant (`pg_read_all_data`) reading `pg_authid`, and any role reading `pg_db_role_setting`.
   - **Unit test** over `sql::all_statements()`: every connector statement names no listed entry, has the no-secret shape, or is exactly `ROLE_LOG_OVERRIDES` or `FUNCTION_LOG_OVERRIDES` (or, only if the rewrite fails, the exact collision probe); `no_statement_touches_the_catalog_denylist` keeps refusing every other mention of the denylist (ADR-0012 refinement).
6. **`pgaudit.log_catalog`.** With `log_catalog = off`, a read of a `pg_catalog` entry alone is not logged (verified for `pg_authid` and `pg_shadow`), and a user view over one is logged with its own record only (verified): it is an event naming the view, under the filters, not a secret read. The `information_schema` entries are logged (verified). The `check()` local detail of ADR-0048 decision 5 names this effect too; the level is unchanged and no target note is added. The documentation keeps recommending `log_catalog = on`.
7. **I2.** Only names leave the agent: the fixed names of decision 1 through [ADR-0009](0009-name-normalization-and-item-sanitization.md) normalization, and the unqualified `information_schema` names as the text gives them, as for any relation read today. The analysis reads no column of these catalogs (it decides on tokens of the statement text), takes no name from a literal, and keeps no text beyond what it keeps today. The `AccessEvent` contract is unchanged: no new field, signal or note.
8. **Drift and pinning tests** (integration, engine matrix, every PostgreSQL image):
   - **Drift**: every relation of `pg_catalog` and `information_schema` with a column whose name contains `password`, `passwd`, `conninfo`, `config` or `options`, or ends in `_value`, and every `bytea` column of `pg_catalog`, is listed or on a commented exception list (`reloptions`, `attoptions`, `spcoptions`, `fdwoptions`, `ftoptions`, `attfdwoptions`, `pg_stat_wal_receiver.conninfo`, `pg_settings`…); and every view of `pg_catalog` and `information_schema` whose definition (`pg_get_viewdef`) reads a secret column of decision 1 is listed or on that list with the reason (it does not expose the column).
   - **Pinning**, one assertion each, per major version: the readers of the context table (`pg_read_all_data` reads `pg_authid.rolpassword`, `pg_subscription.subconninfo` and `pg_largeobject.data`; every role reads `pg_db_role_setting.setconfig` and `pg_roles.rolconfig`; a mapped role reads its own `umoptions`, `pg_read_all_data` does not through the view); the pgaudit relation records of a `pg_roles` read and of a user view over `pg_authid`; the `log_catalog = off` behaviour above; the `pg_stat_statements` form of the two-key read.

## Consequences

- **Code** (`agent-engineer`, `security-reviewer` review):
  - `connector-postgres/src/audit/events.rs`: a `SECRET_RELATIONS` list (name, object, secret columns, shape exemption); `is_catalog` false for an entry read outside its shape; the relation-record rule of decision 3 in the pgaudit `flush`; the always-reported mark; the own kind of decision 5 on pgaudit only;
  - `classifiers/src/query.rs`: `PgScan::no_text_shape` takes a set of column names instead of one, and refuses a `COPY` of a listed relation;
  - `connector-postgres/src/sql.rs`: the unit tests of decision 5.

  No `shared/protocol/` change.
- **Tests**:
  - unit tests on both sources (pgaudit with and without `log_relation`, `log_catalog` on and off; `pg_stat_statements`): each entry qualified, unqualified, quoted, `U&`-escaped, in a join with an application table, in a subquery, a CTE, a `CREATE TABLE … AS`, a `COPY (…) TO`, a `COPY <entry> TO`; each condition of decision 2 met (quiet) and broken one at a time (a secret read, always reported with `min_rows` set, never charged to the agent): each secret column in a select list, a `WHERE`, `USING`, an alias; `*`, `r.*`, `row_to_json(r)`, `r::text`, `(r).*`, the bare name as a whole row, a column alias list, `NATURAL JOIN`, `TABLE pg_roles`, a user function next to it, a cut text; `proconfig` read from `pg_proc`, and `SELECT p.proname FROM pg_proc p` quiet; `pg_hba_file_rules` and `pg_hba_file_rules()` read; a pgaudit `public.v_pw` + `pg_authid` record pair (a secret read naming `pg_catalog.pg_authid`), and `pg_roles` + `pg_authid` + `pg_db_role_setting` records for `SELECT rolname FROM pg_roles` (quiet), and a user view over `pg_roles` without a secret column (a secret read, the accepted over-report of decision 3); the connector's statements on `pg_roles` and `pg_proc` quiet; the two-key read left out on pgaudit only on its exact text and identity, reported with one byte changed, from another role, and always on `pg_stat_statements`.
  - integration tests on PostgreSQL 14 to 18 (`pg_stat_statements`) and 16 with pgaudit (jsonlog, csvlog): a `pg_read_all_data` role reads `pg_authid.rolpassword`, `pg_subscription.subconninfo` and `pg_largeobject`; an unprivileged role reads `pg_db_role_setting.setconfig`, `pg_roles.rolconfig`, `pg_proc.proconfig` and its own `pg_user_mappings.umoptions`; a superuser reads `pg_hba_file_rules` with a `radius` or `ldap` line (the options column pinned per major version); a role reads `public.v_pw`: each gives a read event naming the entry; `SELECT rolname FROM pg_roles` and the connector's own `check()` give none. The drift and pinning tests of decision 8.
  - **Load harness** (`e2e/load/`, PostgreSQL scenario): an exporter-like account reading `pg_roles`, `pg_proc` and `pg_subscription` without secret columns every 5 s (zero events), and a PgBouncer-like account running the default `auth_query` every second (at most one event per principal, object set and aggregation window); Audit events still equal to the application statements, agent CPU and memory unchanged beyond noise.
- **Load impact.** No new query against the server for this ADR (the two-key read belongs to the ADR-0012 refinement). The shape test runs only on texts that name a listed entry, as a pass over tokens the analyzer already lexes (`pg_scan`).
- **Noise.** Events come from what really reads secrets: `pg_dump` and `pg_dumpall`, PgBouncer's `auth_query` (one event per pooler principal and window, under the console's per-target hourly cap of [ADR-0021](0021-access-event-correlation.md): at most 1 440 per day), admin tools that read `rolconfig`, `proconfig`, `pg_roles.*` or `pg_proc.*`, `psql`'s `\drds`, `\deu+`, `\dRs+`, and reads of user views over `pg_roles` (decision 3). Reads without secret columns, the bulk of `pg_roles` and `pg_proc` traffic, stay quiet. As in ADR-0045, ADR-0048 and ADR-0049, there is no agent-side allow-list; the console can scope or exclude principals.
- **Documentation** (`docs-keeper`, after the implementation): in [08-engine-capabilities.md](../08-engine-capabilities.md#postgresql-audit), a "Credential-bearing catalogs" section (the list, the shape, the relation-record rule, the always-reported mark, the own two-key read, the noise note); [05-security.md](../05-security.md#recommended-database-accounts-read-only) states that every role reads every role's and database's settings (`pg_db_role_setting`, `pg_roles.rolconfig`, and `current_setting()` for the database's own), that a mapped role reads its own remote password, and that `pg_read_all_data` reads `pg_authid`, `pg_subscription` and `pg_largeobject`; it recommends keeping secrets out of `ALTER ROLE` / `ALTER DATABASE … SET` and `primary_conninfo` (a `passfile` instead); [10-user-guide.md](../10-user-guide.md) gains a sample policy on `pg_catalog.pg_authid` and `pg_catalog.pg_db_role_setting`.
- **Estimated size.** About 200 lines of production code (150 in `connector-postgres`, 50 in the classifiers helper), 500 lines of unit tests, 200 lines of integration tests, the drift and pinning tests and the load scenario; 2 to 3 days with one review round.
- **Residual risks.**
  - With pgaudit and `pgaudit.log_catalog = off`, a read of a `pg_catalog` entry alone gives no event, and a user view over one is named by the view, under the filters (decision 6).
  - On `pg_stat_statements`, a user view, a SQL or PL/pgSQL function or a procedure over a listed entry is named by what the statement shows (the view, or `*`), and function bodies are not recorded with `track = top`; dynamic SQL is analyzed only through pgaudit's substatement records.
  - The no-secret shape lets every role read the other columns unreported: role names and attributes, which subscriptions and servers exist, which roles and databases have settings (`setrole`, `setdatabase`), large object ids. These are metadata.
  - The session's own settings: `current_setting()`, `SHOW` and `pg_settings` return the values that apply to the reading session, database-level custom settings included (every role of that database), and `primary_conninfo` to `pg_read_all_settings` members; not listed (open questions 6 and 7).
  - FDW options at wrapper, table and column level (`fdwoptions`, `ftoptions`, `attfdwoptions`) are not listed (open question 3).
  - Function bodies (`pg_proc.prosrc`) are not listed: a credential hard-coded in a body is read unreported (open question 10). Trigger arguments (`pg_trigger.tgargs`) are not listed either: a credential passed as a trigger argument is read unreported (open question 10).
  - `pg_hba_file_rules.options` in clear and the function's signature were verified on 16.13 only; listing it is fail-closed either way.
  - The server facts were verified on 16.13 only; the pinning tests confirm them on 14, 15, 17 and 18 before the implementation is merged.

## Rejected alternatives

- **Option (a)**, every read reported: `pg_roles` is read at every heartbeat by the connector itself and by `psql`, ORMs and exporters, mostly without `rolconfig`; each would be an always-reported event per principal and window. Kept for the entries without a shape exemption.
- **Option (c)**, by reader: the sources do not record the reader's privileges, and every role reads `pg_db_role_setting`.
- **Option (d)**, document only: credential reads by compromised administrator, backup or application accounts stay unreported.
- **Relation records alone** (any record of `pg_authid` or `pg_db_role_setting` is a secret read): every `pg_roles`, `pg_user` and `pg_stat_activity` read produces them (verified), whatever its columns.
- **A column test that looks for the secret columns only**: whole-row references, `*`, column alias lists, `COPY` and natural joins read them without naming them; decision 2 refuses each.
- **Leaving the agent's two-key read out on `pg_stat_statements` by its stored text**: constants are `$n` there, so a replay with other keys would be spared.
- **Listing `pg_settings`**: it is read by drivers, exporters and tools for every setting; its secrets are the session's own settings and `primary_conninfo`, which a row-level rule on a text cannot follow (`SHOW`, `current_setting()`).

## Open questions (answered)

Each question has the answer this ADR recommends. **Decided on 2026-10-12: the maintainer accepted the recommended answers to questions 1 to 10** (question 10: neither `prosrc` nor `tgargs` is listed; `tgargs` decided on 2026-10-12 after the review of #217).

1. Scope: the list of decision 1, including `pg_roles` and `pg_user` (whose `rolconfig` / `useconfig` are `pg_db_role_setting`'s role-wide entries, readable by every role), `pg_proc.proconfig` (function `SET` clauses, readable by every role) and `pg_hba_file_rules` (added by the security review of PR #215, L1)?
   **Recommended**: yes. Without `pg_roles` and `pg_user`, `SELECT rolconfig FROM pg_roles` reads what `pg_db_role_setting` holds, a dodge through a view; `proconfig` holds settings in clear like `setconfig`; `pg_hba_file_rules` can show authentication secrets and is read rarely.
2. Column precision: the no-secret shape for the ten entries marked in decision 1, `pg_proc` among them (option (b)), every read for `pg_largeobject`, `pg_file_settings`, `pg_hba_file_rules` and the `information_schema` entries; or every read for all (option (a), as ADR-0048)?
   **Recommended**: (b). `pg_roles` traffic without `rolconfig` is constant, the connector's own `check()` included; the shape is ADR-0049's, reviewed four times, and anything it cannot prove is (a). The entries without an exemption are rarely read, and their columns are all secret or not worth a proof.
3. FDW options: list `pg_foreign_server.srvoptions` and its `information_schema` forms (credentials only for some FDWs; `postgres_fdw` refuses a password there), and leave `fdwoptions`, `ftoptions` and `attfdwoptions` on the drift test's exception list?
   **Recommended**: yes to both. Server options are where several FDWs keep their endpoint, and some their keys; the other levels hold paths and table names in the common FDWs. Revisit if an FDW in use keeps credentials there.
4. Always report secret reads, whatever `min_rows` and `sensitive_objects` say?
   **Recommended**: yes, as ADR-0045, ADR-0048 and ADR-0049. One row is one credential.
5. The pgaudit relation-record rule of decision 3 (a record of a listed entry counts only with a user view, materialized view, foreign table or function-derived relation outside the built-in schemas in the same substatement, or a text that names no relation)?
   **Recommended**: yes. Every `pg_roles` and `pg_stat_activity` read produces `pg_authid` records (verified), so records alone would make them all secret reads; the built-in views that expose a secret column are listed by name and kept so by the drift test.
6. `primary_conninfo` and other secrets in server settings (`pg_settings`, `SHOW`, `current_setting()`, readable by `pg_read_all_settings` members): report, or documentation only?
   **Recommended**: documentation only. The reads are session-level and often table-less (`SHOW`), `pg_settings` is read by every driver and exporter, and the remedy is a `passfile` on the standby; ADR-0012 already keeps `pg_read_all_settings` out of the minimal variant.
7. Database- and role-level custom settings readable in the session through `current_setting()` (verified: every role of the database reads `ALTER DATABASE … SET app.jwt_secret`): documentation only?
   **Recommended**: documentation only, in 05-security: such a setting is not a secret from any role of that database, whatever the agent reports.
8. Verify the server facts on 14, 15, 17 and 18 in the implementation PR, or before the ADR is accepted?
   **Recommended**: in the implementation PR, before merge, as ADR-0048 and ADR-0049 did; a fact that differs is recorded as a refinement of this ADR.
9. Order with the ADR-0012 refinement: if the two-key read lands first, it is a catalog read (quiet) until this ADR is implemented; acceptable?
   **Recommended**: yes. Its text returns only the two keys, so being quiet before this ADR leaks nothing; once this ADR is implemented, decision 5 matches it exactly on pgaudit and reports it on `pg_stat_statements`.
10. Function bodies (`pg_proc.prosrc`) and trigger arguments (`pg_trigger.tgargs`, added by the security review of PR #217, L2): list them with the no-secret shape, or leave them out? Both are readable by every role and both can carry a credential: a hard-coded password in a body, a webhook key or token passed as a trigger argument (`CREATE TRIGGER … EXECUTE FUNCTION notify('<key>')`). Both stay on the drift test's exception list (implementation refinement item 6), so the maintainer decides them together.
    **Recommended**: leave them out. A password in a body (`dblink_connect('… password=…')`) is an antipattern worth reporting, but `prosrc` is read constantly by `psql`'s `\df+` and `\sf`, `pg_dump`, IDEs and migration tools, so every such read would be an always-reported event with little signal; 05-security recommends a user mapping or a `passfile` instead. Revisit with a value test on bodies (a classifier run on the agent side) if it turns out to matter.

## Refinement (2026-10-12, accepted): implementation

**Status: accepted by the maintainer on 2026-10-12**, items 1 to 7 (found while implementing decisions 1 to 8 on `feat/p8-pg-secret-catalogs`; every item is a code fact, stricter than the text or fails closed; no server fact differs from the context). Verified on PostgreSQL 16.13 with pgaudit 16.0 (`dev/postgres/local-cluster.sh`, jsonlog and csvlog) and on the engine-matrix images 14.24, 15.19, 17.11 and 18.6 with `pg_stat_statements` (pulled by digest from `mirror.gcr.io`, Docker Hub's pull limit being reached; no pgaudit there, so the pgaudit facts are verified on 16 only and run on the engine matrix in CI).

1. **Server facts, per major.** Every reader of the context table, the function forms (`pg_hba_file_rules()` and `pg_show_all_file_settings()` take no argument on 14 to 18), `pg_hba_file_rules.options` in clear (a `radius` and an `ldap` line with fake secrets), the `$n` form of the two-key read in `pg_stat_statements` and the drift test give the same result on 14.24, 15.19, 16.13, 17.11 and 18.6 (`it_secrets.rs`). The pgaudit relation records and the `log_catalog = off` behaviour are as the context says on 16.13.
2. **Decision 5: three more connector statements did not have the shape.** The row-level security policy check (`POLICY_REFS_REJECTED`: `unnest(…) AS f(o)`, `AS x(o)`, `AS t(o)`) and Discovery's introspection (`INTROSPECT`: a CTE column list `anc(rel, ancestor)`, and the alias `x` given to `pg_proc` and to three other catalogs, a whole-row reference for the shape) read `pg_proc` outside the no-secret shape, which the context did not say; the collision probe also had a CTE column list (`chain(root, cur, depth)`) and gave the alias `b` to `pg_proc` and to `pg_operator`. All three are rewritten (single-column function aliases without a list, CTE columns named in their first query, the `VALUES` of column references as a `UNION ALL` of selects, one alias per `pg_proc` item): **no exact-text fallback is needed**. The collision probe returns the same rows on 14 to 18 (`it_user_code.rs`), and its planner estimate and time are unchanged (27 417.8 before and after with 3 000 relations, `citext` and `hstore` on 16.13; median 11.5 ms after, 12.8 ms before, 10 runs).
3. **CTE references.** Decision 2's "every relation it names" is read as the analyzer does: a CTE is not a relation. In the no-secret shape, a `FROM` item that is an unqualified reference to a CTE the text defines earlier (`WITH me AS (SELECT r.oid FROM pg_roles r) … FROM pg_class c, me`) counts as a catalog: its query is part of the text and is held to the same rules (secret columns, `*`, whole rows, aliases, other relations). A name used before any CTE of that name is defined (`WITH a AS (SELECT … FROM b), b AS …`) is a relation, and so is a name outside the scope of the `WITH` that defines it: only the statement's own `WITH` and the `WITH` of an enclosing query count, never one of a sibling subquery (security review of PR #217, L1: in `… FROM (WITH v AS (SELECT 1) SELECT 1) q, pg_roles r, v x`, `v` is a user relation, so the statement is a secret read; unit test `the_no_secret_shape`). The ADR-0049 no-text shape is unchanged (a CTE reference stays an item it cannot decide on).
4. **A list entry followed by `(`** (`COPY pg_authid (rolname) TO STDOUT`, `INSERT INTO pg_authid (…)`) is the entry, not a call (a user function of that name is over-reported).
5. **A text the scan cannot read** (a `pg_stat_statements` text cut inside a literal) names the entries of the list among the analysis's relations as secret reads (fail closed).
6. **Drift exceptions found on 14 to 18** (the same set on each), commented in `it_secrets.rs` beyond the decision 8 examples: sequence bounds and positions (`information_schema.sequences`, `pg_sequences`), server constants (`information_schema.sql_implementation_info`, `sql_sizing`), `pg_extension.extconfig` (oids), FDW column options (`information_schema.column_options`, `_pg_foreign_table_columns.attfdwoptions`, open question 3), and `pg_trigger.tgargs` (`bytea`: trigger arguments, readable by every role, which can carry a credential such as a webhook key; left out with `prosrc`, open question 10, which now names both).
7. **The two-key reads on the server's `ERROR` lines.** A quiet-class `ERROR` or `FATAL` line (a timeout, a refused read) whose statement is exactly one of the two-key reads, from the agent's identity, is left out uncharged like the record, as the `pg_stat_statements` text query is (ADR-0049 decision 5); any other secret read in a line is reported.
