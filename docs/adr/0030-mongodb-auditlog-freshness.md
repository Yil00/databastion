# ADR-0030: MongoDB `auditLog` freshness: None until a record is read

- **Status**: Proposed
- **Date**: 2026-09-29
- **Refines**: [ADR-0027](0027-mongodb-audit.md) (which stays Accepted), decision 2 (levels), `auditLog` bullet
- **Context references**: end-of-phase-5 review L1, phase 7 (`agent/crates/connector-mongodb/src/audit/mod.rs`: `choose`, `explain`, `file_state`, `parse_all`)

## Context
ADR-0027 decision 2 proves every MongoDB level from records the agent has read, never from settings it cannot see, with one exception: the `auditLog` JSON file reports **Limited** as soon as it is readable on an Enterprise or Percona server, and Partial once a successful `authCheck` was parsed in the last 24 h. The server log and the profiler, by contrast, report **None** with `audit.limited_pending_first_record` until the stream has parsed a record of them in the last 24 h (the freshness rule of ADR-0023 decision 2).

The end-of-phase-5 review (L1) noted the consequence: an `auditLog` file that is readable but no longer written (auditing turned off, `auditLog.path` moved to another file, a filter that now drops everything, a stale copy left on disk) keeps showing Limited indefinitely. A readable file that records nothing proves nothing, exactly as for the other two sources.

The proof is cheap for the `auditLog`: `authenticate` records are written whatever `auditAuthorizationSuccess` and are rarely filtered out, and the agent itself authenticates at every `check()` (every heartbeat) and every Audit re-probe. On a written file, the stream therefore parses at least the agent's own `authenticate` record within one poll interval of the first check.

## Decision
1. **`auditLog` levels.** The `auditLog` source (Enterprise or Percona Server for MongoDB, file readable) reports:
   - **Partial** when the stream parsed a successful `authCheck` record in the last 24 h (unchanged);
   - **Limited** when it parsed any valid `auditLog` record in the last 24 h, but no successful `authCheck`, with the note `audit.authcheck_success_pending` (unchanged);
   - **None** otherwise, with the notes `audit.limited_pending_first_record` and `audit.authcheck_success_pending`. The source is still chosen and read meanwhile (the heartbeat `audit_source` stays `mongodb_audit_log`), as ADR-0027 does for the server log and the profiler.
2. **What counts as a record.** Any record the `auditLog` reader accepts as valid JSON of the `mongo` schema counts, including those that yield no event (`logout`, `clientMetadata`, an `atype` outside the closed list): the proof is that the file is written, not that it carries reads. The agent's own `authenticate` record counts; it is still left out of the events under ADR-0027 decision 7. A record that does not parse (dropped, `audit.records_dropped`) does not count.
3. **No new code.** `audit.limited_pending_first_record` is already registered for `mongodb`; its registry description, which names the server log and the profiler only, stays as is in this change (see Consequences). No protocol change.

## Consequences
- A stale or no longer written `auditLog` falls to None within 24 h of its last record, and a fresh agent (or one restarted) shows None until the first poll after its first check, typically a few seconds; the console shows it from the existing notes.
- Heartbeats between an agent restart and the first parsed record report None instead of Limited: an incident policy on "audit level below Limited" can fire once after a restart if the file is quiet and the first check comes before the stream's first poll. The same already holds for the server log and the profiler.
- The level in memory is still per agent process (ADR-0027 decision 11): a restart loses the 24 h proof and rebuilds it from the next records.
- Other owners: the description of `audit.limited_pending_first_record` in `shared/protocol/target-notes.json` could be reworded to name the `auditLog` too (a compatible rewording, with the console's generated catalog regenerated by `console-engineer`); `docs/08-engine-capabilities.md` (MongoDB levels paragraph), `docs/05-security.md` (the "stale `auditLog` level" residual) and `docs/adr/README.md` (index) are updated by `docs-keeper`.

### Residual risks
- A file written only by the agent's own authentications (every other event filtered out by an `auditLog.filter`) shows Limited: Limited still means "reads may be missing", with `audit.authcheck_success_pending`; only Partial claims that reads are logged.
- The proof covers the last 24 h: auditing turned off after the last record is detected at most 24 h later, as for the other sources and for the Partial proof.

## Rejected alternatives
- **Keep Limited for a readable `auditLog`** (ADR-0027 as accepted): a readable but unwritten file overstates the coverage indefinitely, unlike the two other sources.
- **Count only records that carry events** (operations, authentications): `logout` or `clientMetadata` records prove the file is written just as well; excluding them only delays the proof.
- **Read the server's audit settings** (`getCmdLineOpts`, `getParameter auditAuthorizationSuccess`): cluster privileges the agent must not hold (ADR-0026 decision 5, ADR-0027 rejected alternatives).
- **A shorter freshness window**: the agent's own authentication at every heartbeat would allow minutes, but the server log and the profiler cannot (a quiet server writes nothing to them); one 24 h rule for the three sources keeps the levels comparable.
- **Edit ADR-0027 in place**: the ADR convention does not allow editing an accepted ADR.
