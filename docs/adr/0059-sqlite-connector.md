# ADR-0059: SQLite connector: the bundled SQLite C library through `rusqlite` as a scoped exception, declared files only, read-only access that never writes a side file, hardened against hostile files, Discovery only

- **Date**: 2026-10-24
- **Relies on**: [ADR-0039](0039-engine-scope-expansion.md) decision 1 (accepted: end-of-life versions not supported) and decision 8 (accepted: new engines as capability tokens, with [ADR-0042](0042-hold-items-of-unlisted-engines.md)). ## Context
Phase 10 adds SQLite ([ROADMAP](../ROADMAP.md#phase-10--engine-scope-wave-2-sqlite-firebird)). SQLite is not a server: it is a C library linked into each application, and a database is a file (plus, while in use, a `-wal` and a `-shm` file, or a `-journal` file, next to it). Every rule of the other connectors still applies: read-only and bounded (I4), declared targets only (I5), masking before the uplink (I2), honest `check()`, closed notes ([ADR-0022](0022-protocol-capability-negotiation.md)). SQLite raises questions the other engines did not:

- **No server, no account, no access log.** There is nothing to authenticate to and nothing that records reads: reads happen inside the applications that open the file. Audit is **None by nature** (ADR-0039 decision 3). Least privilege is the agent's Unix account and the file's permissions.
- **The reader is in the agent's process.** For every other engine, the server parses its own files and the agent parses only a bounded protocol. Here the agent's process parses the file itself. The file is written by an application, so its content (pages, records, and the schema SQL that SQLite compiles when it reads the file) may be **attacker-controlled**. A memory-safety bug reachable from a file would run in the process that holds the console secret, the HMAC key and the credentials of every other target.
- **Reading a live file without writing to it** is harder than it looks (WAL databases, below).
- **The path is data.** A path such as `/srv/clients/jdupont/notes.db` holds personal names (ADR-0039 decision 7).

### Facts verified for this ADR
Read on 2026-10-24 in the sources of `rusqlite` 0.40.2 and `libsqlite3-sys` 0.38.2 (downloaded from crates.io) and in the SQLite **3.53.2** amalgamation that `libsqlite3-sys` 0.38.2 bundles (`sqlite3/sqlite3.c`, `sqlite3/sqlite3.h`). The sqlite.org pages (`security.html`, `wal.html`, `uri.html`, `pragma.html`, `compile.html`) could not be fetched from the ADR's environment (the egress proxy answers `403` for sqlite.org); facts that only those pages state are marked **(to verify against sqlite.org)**. Nothing was built.

- **Open flags and URI parameters.** `SQLITE_OPEN_READONLY`, `SQLITE_OPEN_URI`, `SQLITE_OPEN_NOFOLLOW` ("the database filename is not allowed to contain a symbolic link") and `SQLITE_OPEN_EXRESCODE` exist. The documented URI parameters are `vfs`, `mode` (`ro`, `rw`, `rwc`, `memory`), `cache`, `psow`, `nolock` ("disables file locking in rollback journal modes … corruption might result if two or more processes write") and `immutable` ("SQLite assumes that the database file cannot be changed … all locking and change detection is disabled … can result in incorrect query results and/or `SQLITE_CORRUPT` errors" on a file that does change). `readonly_shm` is **not** in that documented list, but the unix VFS reads it (`sqlite3_uri_boolean(…, "readonly_shm", 0)` in `unixOpenSharedMemory`).
- **Symlinks.** `unixFullPathname` `lstat`s every component and counts symlinks; with `SQLITE_OPEN_NOFOLLOW` any symlink **in any component** fails the open (`SQLITE_CANTOPEN_SYMLINK`). Every file the unix VFS opens (database, `-wal`, `-journal`, `-shm`) gets `O_NOFOLLOW` on its final component.
- **What a read-only connection still tries to write.**
  - The `-wal` file is always opened with `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE` (`sqlite3WalOpen`), even by a read-only connection; the unix VFS tries `O_RDWR | O_CREAT` and falls back to `O_RDONLY` only when that fails (`unixOpen`).
  - The `-shm` file is opened `O_RDWR | O_CREAT` unless the URI has `readonly_shm=1`, and `O_RDONLY` only when that fails (`unixOpenSharedMemory`).
  - When the database has 0 pages and a `-wal` exists, the pager **deletes** the `-wal` (`pagerOpenWalIfPresent`).
  - New `-wal` and `-journal` files are created with the database file's permission bits (`findCreateFileMode`, then `fchmod` past the umask); the `-shm` likewise (`st_mode & 0777`).
  So whether SQLite writes, creates or deletes a side file is decided by the operating system's permissions, not by the read-only flag.
- **A WAL database read with a read-only `-shm`.** When another process (a writer) holds the `-shm` "DMS" lock, the read-only mapping is reliable and the reader uses it. When nobody holds it, `unixLockSharedMemory` returns `SQLITE_READONLY_CANTINIT` and the WAL module builds a **private heap copy of the WAL index by reading the whole `-wal` file** (`walBeginShmUnreliable`), then checks again at every read transaction whether a writer has attached. A read-only reader that finds no usable read mark returns `SQLITE_READONLY_CANTINIT` or `SQLITE_BUSY`, and a corrupt WAL index header gives `SQLITE_READONLY_RECOVERY` (`walIndexReadHdr`, `walTryBeginRead`).
- **A WAL database whose `-wal` and `-shm` are absent** (the last application connection closed cleanly and deleted them): the file header still says WAL (byte 19 = 2), `lockBtree` calls `sqlite3PagerOpenWal`, which must create the `-wal`; in a directory the agent cannot write, the open fails (`SQLITE_READONLY_DIRECTORY` or `SQLITE_CANTOPEN`; the exact code is to verify by test). sqlite.org's WAL page states the same rule, "the `-shm` and `-wal` files already exist or those files can be created or the database is immutable" (to verify against sqlite.org).
- **A hot rollback journal** on a read-only connection gives `SQLITE_READONLY_ROLLBACK`.
- **POSIX advisory locks.** SQLite's own comment: "POSIX advisory locks are broken by design": closing **any** descriptor of a file releases **every** lock the process holds on it. The unix VFS shares its own descriptors per inode to cope; a descriptor the agent's own code opens and closes on the same file would silently drop SQLite's locks.
- **Locking.** In rollback-journal modes a reader holds a `SHARED` lock for the length of its read transaction, and a writer cannot commit (it needs `EXCLUSIVE`) until it is released; a writer without a busy timeout gets `SQLITE_BUSY`. In WAL mode readers do not block writers, but an open read transaction pins a read mark, so checkpoints cannot reset the WAL past it (the WAL grows).
- **The schema is SQL compiled by SQLite.** It is read lazily at the first statement; the authorizer is not called while it is read (`sqlite3AuthCheck` returns early when `db->init.busy`). **`PRAGMA table_list` prepares `SELECT * FROM "<name>"` for every view and virtual table whose column count is not known yet** (so it compiles views and connects virtual-table modules), and `PRAGMA table_info` on a view compiles it (`sqlite3ViewGetColumnNames`).
- **Limits** (`SQLITE_LIMIT_*`): `LENGTH`, `SQL_LENGTH`, `COLUMN`, `EXPR_DEPTH`, `COMPOUND_SELECT`, `VDBE_OP`, `FUNCTION_ARG`, `ATTACHED`, `LIKE_PATTERN_LENGTH`, `VARIABLE_NUMBER`, `TRIGGER_DEPTH`, `WORKER_THREADS`, and `PARSER_DEPTH` (new in 3.53). Some are enforced by the parser ("too many terms in compound SELECT" is raised in the grammar actions), so they also apply when the file's schema is read. `OP_Column` refuses a value longer than `SQLITE_LIMIT_LENGTH` with `SQLITE_TOOBIG`; `typeof()`, `length()` and `octet_length()` have column flags that avoid loading the value. `BTCURSOR_MAX_DEPTH` is 20.
- **Memory.** `sqlite3_hard_heap_limit64` and the `hard_heap_limit` / `soft_heap_limit` pragmas apply to "all database connections within a single process". The default page cache is 2 000 KiB (`SQLITE_DEFAULT_CACHE_SIZE -2000`); memory-mapped I/O is off unless `mmap_size` is raised (`SQLITE_DEFAULT_MMAP_SIZE` 0, `SQLITE_MAX_MMAP_SIZE` 0x7fff0000 on Linux).
- **`sqlite3_db_config` options** in 3.53.2 include `DEFENSIVE` (no `writable_schema`, no `journal_mode=OFF`, no `schema_version=N`, no writes to `sqlite_dbpage` or shadow tables), `TRUSTED_SCHEMA` (off: no function in triggers, views, `CHECK`, `DEFAULT`, expression or partial indexes or generated columns unless it is innocuous, and no virtual table in triggers or views unless innocuous), `ENABLE_TRIGGER`, `ENABLE_VIEW`, `ENABLE_ATTACH_CREATE` and `ENABLE_ATTACH_WRITE` (3.49), `NO_CKPT_ON_CLOSE`, `REVERSE_SCANORDER` (the same as `PRAGMA reverse_unordered_selects`), `DQS_DML` / `DQS_DDL`. `SQLITE_TRUSTED_SCHEMA=0` also exists as a compile-time default.
- **The file header**: `"SQLite format 3\0"`; byte 18 (write version) and 19 (read version) are 1 for rollback and 2 for WAL, a read version above 2 is refused (`SQLITE_NOTADB`) and a write version above 2 makes the file read-only; the schema format number has a maximum of 4 (`SQLITE_MAX_FILE_FORMAT`).
- **`libsqlite3-sys` 0.38.2's bundled build** (`build.rs`) compiles `sqlite3.c` with `cc` and `links = "sqlite3"`, with `SQLITE_CORE`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`, `SQLITE_ENABLE_API_ARMOR`, `SQLITE_ENABLE_COLUMN_METADATA`, `SQLITE_ENABLE_DBSTAT_VTAB`, `SQLITE_ENABLE_FTS3` (and `_PARENTHESIS`), `SQLITE_ENABLE_FTS5`, `SQLITE_ENABLE_JSON1`, **`SQLITE_ENABLE_LOAD_EXTENSION=1`**, `SQLITE_ENABLE_MEMORY_MANAGEMENT`, `SQLITE_ENABLE_RTREE`, `SQLITE_ENABLE_STAT4`, `SQLITE_SOUNDEX`, `SQLITE_THREADSAFE=1`, `SQLITE_USE_URI`; the environment variable `LIBSQLITE3_FLAGS` adds `-D…` / `-U…` flags after these. With `SQLITE_ENABLE_LOAD_EXTENSION`, a new connection has the C API `sqlite3_load_extension` enabled but **not** the SQL function `load_extension()` (`SQLITE_LoadExtFunc` stays off). The amalgamation uses no `__DATE__` / `__TIME__`.
- **`rusqlite` 0.40.2's safe API** has what the connector needs: `Connection::open_with_flags` (with `OpenFlags::SQLITE_OPEN_NOFOLLOW`, `SQLITE_OPEN_EXRESCODE`), `set_db_config` (`DbConfig` lists every option above except `ENABLE_LOAD_EXTENSION`, which is commented out), `set_limit` (feature `limits`), `progress_handler` and `authorizer` (feature `hooks`), `busy_timeout`, `get_interrupt_handle` (an `InterruptHandle` usable from another thread), `Connection::path()`. Extension loading needs the `load_extension` feature; installing a log callback (`trace::config_log`) is an `unsafe fn`.

## Decision
1. **The agent reads SQLite through the bundled SQLite C library, with `rusqlite`, as a reviewed exception to "no C client library", scoped to one crate** (ADR-0039 decision 4).
   - **Options weighed.**
     - *Bundled SQLite through `rusqlite` (`bundled`)*: the reference implementation of the file format, its lock protocol and its WAL index, so reads of a live file are as correct as the applications' own; mature and heavily fuzzed upstream; a public-domain C library compiled into the agent, so `unsafe` lives inside two dependencies and a memory-safety bug in SQLite would run in the agent's process.
     - *The system `libsqlite3` (dynamic link)*: security updates come with the distribution, but the version differs per host (Debian 12 ships 3.40, older than the 3.42 / 3.43 / 3.49 features this ADR uses), the build stops being reproducible across hosts, compile options are the distribution's (load extensions, modules), and the `.deb` gains a dependency. Rejected.
     - *An own pure-Rust reader*: no C, panic-free and bounded like the project's own clients, but it must reimplement what makes reads of a **live** file correct: SQLite's POSIX lock protocol, the WAL index format with its read marks and recovery cases, the hot-journal rule, overflow chains, `WITHOUT ROWID` b-trees, and a parser for `CREATE TABLE` text (column names exist only in the schema SQL). A reader that gets the lock protocol wrong reads torn pages of a file being written. Rejected for phase 10; kept as the fallback if the review or the fuzz campaign rejects the C library (open question 2).
     - *`turso_core`* (pre-1.0, its own engine, multi-process access to a file written by SQLite to verify) and *`sqlite-core`* (a small forensics reader without locking or WAL): not mature enough for live files. Rejected.
   - **Recommendation: the bundled C library**, because correctness on live WAL files and maturity against hostile files weigh more than the absence of C, and because SQLite documents the use of untrusted database files as a supported case with the defenses decision 4 applies (to verify against sqlite.org's `security.html`). The cost, C code parsing attacker-controlled input inside the agent, is contained by decision 4 (defensive settings, limits, an authorizer, a closed statement list, no view, trigger or virtual-table execution), by fuzzing (decision 4), by the OS (decision 2), and recorded as the main residual risk.
   - **Crates.** `connector-sqlite` (new crate `agent/crates/connector-sqlite`, Cargo feature `sqlite`) depends on `rusqlite` **0.40.x** with `default-features = false, features = ["bundled", "hooks", "limits"]`, nothing else (no `load_extension`, `loadable_extension`, `functions`, `vtab`, `serialize`, `backup`, `blob`, `trace`, `session`, `preupdate_hook`, `sqlcipher`, `bundled-sqlcipher*`, `buildtime_bindgen`, `column_decltype`, `modern-full`, `bundled-full`, `chrono` / `serde_json` / `url` / `uuid` / `time` / `jiff` integrations). Only `connector-sqlite` depends on `rusqlite`; nothing depends on `libsqlite3-sys` but `rusqlite`. `rusqlite` 0.41.0 declares `rust-version` 1.89, above the workspace MSRV 1.88; moving to it is a separate decision (open question 4). Dependabot's agent group proposes updates as for any crate.
   - **Compile options.** `agent/.cargo/config.toml` (new) sets, under `[env]`, `LIBSQLITE3_FLAGS = "-USQLITE_ENABLE_LOAD_EXTENSION -DSQLITE_TRUSTED_SCHEMA=0 -DSQLITE_MAX_MMAP_SIZE=0 -DSQLITE_MAX_ALLOCATION_SIZE=33554432 -USQLITE_ENABLE_FTS3 -USQLITE_ENABLE_FTS3_PARENTHESIS -USQLITE_ENABLE_FTS5 -USQLITE_ENABLE_RTREE -USQLITE_ENABLE_DBSTAT_VTAB -USQLITE_ENABLE_STAT4 -USQLITE_ENABLE_COLUMN_METADATA -USQLITE_SOUNDEX"`: no extension loading compiled in, schemas untrusted by default, no memory-mapped I/O, no single allocation above 32 MiB, and no virtual-table module or optional feature the connector never uses (a schema that declares an FTS or R-tree table still parses; such tables are never read, decision 4). JSON functions are part of the core since 3.38 and stay. Because `.cargo/config.toml` applies only to a `cargo` run started under `agent/`, the connector **checks the compile options at start** (`PRAGMA compile_options` on an in-memory connection, before any target is opened) against the expected set: `ENABLE_LOAD_EXTENSION`, `ENABLE_FTS3`, `ENABLE_FTS5`, `ENABLE_RTREE`, `ENABLE_DBSTAT_VTAB` absent; `MAX_MMAP_SIZE=0`, `TRUSTED_SCHEMA=0`, `THREADSAFE=1` present (the option names as `PRAGMA compile_options` prints them, to verify). A mismatch disables the connector (fail closed): its targets report `unsupported` with `check.stage_failed` (`stage_session_setup`) and the agent logs it once. A unit test runs the same check in CI. That every build path (the agent `Dockerfile`, `release.yml`, `publish.yml`, the fuzz workflow, the engine matrix) runs `cargo` under `agent/` is checked when the crate lands.
   - **`agent/deny.toml`** gains, under `[bans] deny`, in the same form as the `serde_yaml_ng` rules of ADR-0046:

     ```toml
     # ADR-0059 decision 1: the bundled SQLite C library, only through rusqlite,
     # and rusqlite only in the SQLite connector. A reviewed exception to
     # "no C client library" (ADR-0039 decision 4); widening it needs an ADR.
     { crate = "rusqlite", wrappers = ["databastion-connector-sqlite"], reason = "ADR-0059 decision 1: SQLite connector only" },
     { crate = "libsqlite3-sys", wrappers = ["rusqlite"], reason = "ADR-0059 decision 1: bundled SQLite only through rusqlite" },
     ```

     and, under `[bans] features`, an allow-list for both crates (cargo-deny's `allow` key of a `features` entry: only these features may be enabled; the exact keys are checked against the cargo-deny version CI uses):

     ```toml
     { crate = "rusqlite", allow = ["bundled", "modern_sqlite", "hooks", "limits"] },
     { crate = "libsqlite3-sys", allow = ["bundled", "bundled_bindings", "cc", "min_sqlite_version_3_34_1", "pkg-config", "vcpkg"] },
     ```

     The licenses are already allowed (MIT); the SQLite public-domain dedication is listed with the agent's third-party notices. Advisories against `libsqlite3-sys` (RustSec tracks some bundled-SQLite CVEs, to verify which) are covered by the existing advisories job.
   - **`agent/crates/agent/tests/architecture.rs`** gains:
     - `connector-sqlite` in `CONNECTORS` (no HTTP client, no protocol types, no uplink reference);
     - **`c_code_is_allow_listed`**: from `cargo metadata --locked --filter-platform` for each release target (`x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`), every package of the normal graph that has a `links` key or a `cc` build dependency is in a closed list: `ring` (its `links` value starts with `ring_core_`) and `libsqlite3-sys` (`links = "sqlite3"`). This makes the "no C client library" rule mechanical: any new C code needs this list changed, so a review;
     - **`only_connector_sqlite_uses_rusqlite`**: in the resolved graph, the only normal dependent of `rusqlite` is `databastion-connector-sqlite` and the only one of `libsqlite3-sys` is `rusqlite` (the `deny.toml` rule's second guard, as `only_core_depends_on_protocol_types` does for the protocol);
     - **`sqlite_connector_opens_no_network_connection`**, the CAS test's twin: no TLS crate, no tokio `net` feature, no socket type in its sources;
     - **`sqlite_connector_statements_are_closed`**: the crate's statement templates (decision 4) are listed by an exported function, as SQL Server's `statement_allow_list`; none contains `ATTACH`, `load_extension`, `writable_schema`, `immutable`, `nolock`, `mode=rw`, `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `CREATE`, `DROP`, `ALTER`, `VACUUM`, `REINDEX`, `ANALYZE`, `BEGIN`, `SAVEPOINT`, `table_list` or `sqlite_dbpage`; and no source line of the crate (comments left out) names `rusqlite::ffi`, `libsqlite3_sys`, `config_log`, `load_extension` or `Connection::handle`.
   - **`#![forbid(unsafe_code)]`** stays in `connector-sqlite`: the `unsafe` code is inside `rusqlite` and `libsqlite3-sys`. The crate denies `clippy::indexing_slicing` and `clippy::string_slice` outside tests, as `connector-openldap` and `connector-redis` do.
   - **Build.** A C compiler is already required by `ring`. The added build time and binary size are measured in the implementation PR (not measured here); the reproducible `.deb` test must stay green with the bundled C code.

2. **Targets are declared files; the path never leaves the agent; every file is checked before SQLite sees it** (I5, I3, I4; ADR-0039 decisions 5 and 7; the CAS rules of [ADR-0041](0041-cas-connector.md) decision 3 and [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md)).
   - **Declaration.** One target is one database file:

     ```yaml
     targets:
       - id: crm-app            # what the console sees (TargetId)
         engine: sqlite
         sqlite:
           path: /srv/crm/data/crm.db
           max_statement_ms: 500   # optional, 50..5000 (decision 3)
     ```

     No `host`, `port`, `socket`, `account` or `secret`: the configuration refuses them for `engine: sqlite`, as for `cas`. **No directory, no glob, no search**: a directory of files would make the agent read files that appear later and that nobody declared one by one, which is what I5 forbids; several files are several targets. The agent never looks for SQLite files (no local detection, ADR-0006: there is no process or port to detect, and scanning the file system is the rejected alternative of ADR-0039).
   - **The path never leaves the agent.** The target is identified to the console by its `id` only (`TargetStatus.target_id`, the `TargetId` slug, which cannot hold a path). The path, the file name and the side-file names are never sent, never written to the agent's logs (which may be shipped off the host), and never kept in an error: logs name the target id. `Location.database` is a constant (decision 5), never the file name.
   - **Path rules, checked when `agent.yaml` is loaded and at every open.**
     - Absolute, already canonical (no `.` or `..` component, no `//`, no trailing `/`), valid UTF-8, at most 1 024 bytes, no control character.
     - **No symlink in any component.** This is stricter than ADR-0039 decision 5 ("symlinks are resolved when the configuration is loaded") and than ADR-0043 (which follows parent symlinks): SQLite derives the side-file names from the path and resolves symlinks itself component by component, and `SQLITE_OPEN_NOFOLLOW` refuses a symlink in any component (Context). One rule for both sides is simpler to review: the operator declares the real path. A symlink is refused with `unsupported`.
     - Not under the agent's state, identity or spool directories, nor under `/proc`, `/sys`, `/dev` or `/run/user`.
     - Two targets may not name the same file: the loader and every open compare the files' `(st_dev, st_ino)`; a duplicate refuses both.
   - **Open procedure** (blocking, on the connector's thread, in this order; any failure refuses the file before SQLite opens it, with the code and note of decision 6):
     1. Every ancestor directory is `lstat`ed from `/` down: a directory, not a symlink, not writable by the agent (owner = the agent's uid, a group-write bit for one of its groups, the other-write bit, or `faccessat(W_OK, AT_EACCESS)` true, which covers POSIX ACLs), and **not writable by every local user unless it has the sticky bit**.
     2. `fstatfs` on the parent directory: a **network or FUSE file system is refused** (decision 3): `f_type` in the closed list NFS (`0x6969`), SMB (`0x517B`), CIFS (`0xFF534D42`), SMB2 (`0xFE534D42`), FUSE (`0x65735546`), 9P (`0x01021997`), Ceph (`0x00C36400`), AFS (`0x5346414F`), Coda (`0x73757245`), and the values for Lustre and GPFS, checked against the kernel's `magic.h` at implementation.
     3. The agent's **check descriptor**: `open(path, O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_NOCTTY | O_CLOEXEC)` (`rustix`, no `unsafe`), then on that descriptor (`fstat`): a regular file; `st_nlink` = 1 (a hard link could make the agent read another file it can read, ADR-0043 decision 4); not writable by the agent (the step 1 rules); a size of at least 512 bytes (a 0-byte file is refused: SQLite would treat it as an empty database and delete a `-wal`, Context).
     4. **Header pre-check in Rust**, on the first 100 bytes read through the check descriptor, before SQLite parses anything: the magic `"SQLite format 3\0"`; a page size that is a power of two from 512 to 65 536 (the value 1 meaning 65 536); write and read versions 1 or 2; the payload fractions 64, 32, 32; a schema format number from 1 to 4; a text encoding 1, 2 or 3; a page count in the header consistent with the file size when the header says it is valid. Anything else is refused as `coverage.unrecognized_file_format` (decision 6), so an encrypted, compressed or misplaced file, or one of the agent's own secret files, is never handed to the C library.
     5. **Side files** `<path>-wal`, `<path>-shm`, `<path>-journal` are `lstat`ed: each one present must be a regular file with `st_nlink` = 1, not a symlink, not writable by the agent, and owned by the database file's owner or belonging to its group (the application). Otherwise the file is refused (`privilege.database_file_writable` when writable, `unsupported` otherwise).
     6. SQLite opens the file (decision 4's setup).
     7. **Binding SQLite's descriptor to the checked file.** SQLite opens by path, so the checked file could have been swapped in between. After the first statement (which reads page 1), the connector lists `/proc/self/fd` and counts the descriptors whose target (`std::fs::metadata` through the magic link) has the checked `(st_dev, st_ino)`: it must be **exactly 2** (the check descriptor and SQLite's). With only the check descriptor, SQLite opened another file: the connection is closed and the file refused. The count is reliable because nothing else in the agent opens that file (the same-file rule above and the per-target lock below). `Connection::path()` must also equal the declared path.
   - **Descriptor lifetime (POSIX locks).** The check descriptor stays open for the whole life of the SQLite connection and is closed only **after** the connection is closed; the agent's code opens no other descriptor on the database or its side files while a connection on it is open. All access to one target (scan units, `check()`) goes through one **per-target lock**, held until the blocking task that uses the connection has returned (decision 3), so a `check()` can never close a descriptor under a running scan. Path-based checks (`lstat`, `fstatfs`, `faccessat`) open no descriptor and are allowed at any time.
   - **Recommended permissions** (for [05-security.md](../05-security.md#recommended-database-accounts-read-only) and the user guide): the database owned by the application, mode `0640`, group `databastion` (or a group the agent's account is a supplementary member of, `SupplementaryGroups=` in a systemd drop-in); its directory `0750` or `2750` with the same group and the **setgid bit**, so that the `-wal`, `-shm` and `-journal` files the application creates (with the database's permission bits, Context) belong to that group and stay readable by the agent; or a POSIX default ACL granting the agent's group read access on the directory. The agent needs search (`x`) permission on every ancestor directory and read permission on the files; never write. A file under `/home` needs `ProtectHome=read-only` (or a `BindReadOnlyPaths=`) in the drop-in.
   - **The parent-directory rule differs from ADR-0039 decision 5**, which refuses "a path whose parent directory is writable by another non-root user". A SQLite application must create and delete its journal files in that directory, so the rule would refuse almost every live database. The rule here: the directory and its ancestors may be writable by their owner and group (the application), never by the agent, and never by every local user without the sticky bit. Whoever can write the directory can replace the file between two opens; steps 3 to 7 bind each open to a checked regular file, and the residual (decision 9) is that the application's own account can present another SQLite file that the agent can read.

3. **Read-only access that never writes, creates or deletes a file, WAL databases, locking and file systems** (I4).
   - **The guarantee comes from the operating system, in three layers**, because SQLite's read-only flag alone does not keep it from creating or opening side files read-write (Context):
     1. the agent cannot write the file, its side files or any ancestor directory (decision 2, checked at every open; a file that fails is refused, never opened "read-only anyway");
     2. the systemd unit's `ProtectSystem=strict` makes the database's file system read-only in the agent's mount namespace (any write fails with `EROFS`), unless an operator adds the path to `ReadWritePaths=`, which the user guide forbids;
     3. SQLite itself is opened read-only: `SQLITE_OPEN_READONLY | SQLITE_OPEN_URI | SQLITE_OPEN_NOFOLLOW | SQLITE_OPEN_EXRESCODE | SQLITE_OPEN_NO_MUTEX | SQLITE_OPEN_PRIVATE_CACHE` with the URI `file:<path>?mode=ro&readonly_shm=1`, where every byte of the path outside the RFC 3986 unreserved set and `/` is percent-encoded (so `?`, `#`, `&`, `=` and `%` cannot reach SQLite's URI parser), with `PRAGMA query_only=ON`, `SQLITE_DBCONFIG_DEFENSIVE`, `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` and the authorizer of decision 4.
     With layers 1 and 2, every `O_RDWR | O_CREAT` attempt of the unix VFS fails and it falls back to `O_RDONLY`, and the `-wal` deletion of an empty database cannot happen (the 0-byte file is also refused). The integration tests prove it: the directory and side files are byte-for-byte and `mtime`-unchanged after a scan, on rollback and WAL databases, with and without a concurrent writer, and the tests read the access mode of every descriptor SQLite holds on the database and its side files (`/proc/self/fdinfo/<n>`, `flags`): read-only, always.
   - **`immutable=1` is rejected.** It disables locking and change detection: on a file an application is writing it gives wrong results or `SQLITE_CORRUPT`, and it ignores the `-wal`, so the most recent commits (often the most recent personal data) are invisible. It is also not needed for static files: a file no one writes reads correctly with the normal locks.
   - **Writing the `-shm` is rejected.** It breaks I4 (the agent would write a file that belongs to the application), and a reader with a writable `-shm` may run WAL-index recovery, which writes to the memory the application's connections share.
   - **`readonly_shm=1` is adopted**, with the outcomes below. Because `readonly_shm` is not in SQLite's documented URI list (Context), layer 1 remains the guarantee and the integration tests pin the behaviour at every library update.

     | Journal mode (header byte 19) | Side files present | Outcome |
     |---|---|---|
     | rollback (1) | none, or a `-journal` that is not hot | read normally, under `SHARED` locks |
     | rollback (1) | a hot `-journal` | `SQLITE_READONLY_ROLLBACK`: not read, note `coverage.hot_journal_pending`, retried at the next check (the application recovers it at its next open) |
     | WAL (2) | `-wal` and `-shm`, a writer connected | read through the read-only `-shm` |
     | WAL (2) | `-wal` and `-shm`, no writer connected | read through SQLite's private heap index built from the `-wal`; a `-wal` larger than **128 MiB** is not read (that build reads the whole file and its time is not bounded by the progress handler), note `coverage.wal_files_not_readable` |
     | WAL (2) | neither (the application closed cleanly) | cannot be opened read-only without creating the `-wal` (Context): not read, note `coverage.wal_files_not_readable`, retried at the next check; the user guide explains that the file is read while the application holds it open (open question 3) |
     | WAL (2) | only one of them, or one unreadable | not read, note `coverage.wal_files_not_readable` |
     | any | a `-wal` next to a rollback-mode header | SQLite opens it in WAL mode (`pagerOpenWalIfPresent`): the WAL rows above apply |

   - **Locking so writers are not held up.**
     - **Autocommit statements only**: the connector never issues `BEGIN`; each statement is its own read transaction, so a lock or read mark is held only while one statement runs. A statement is stepped to completion (or reset) before the next one; no statement is left open across a pause or across `FindingSink::submit().await` (rows are copied into zeroized buffers first, [05-security.md](../05-security.md#connector-obligations)).
     - **Statement deadline** `sqlite.max_statement_ms` (default 500 ms, range 50 to 5 000, a local limit the console cannot raise), and never more than the job's clamped statement timeout. It is enforced by the progress handler (every 1 000 virtual-machine instructions it checks the deadline and the scan's cancel flag, and interrupts the statement) and by `InterruptHandle::interrupt` from the async side when the deadline passes or the scan future is dropped (the blocking task then ends within one progress interval; the per-target lock is released only then). In rollback mode this bounds how long one statement can delay a writer's commit; with the default 1 % duty cycle ([ADR-0035](0035-discovery-pacing.md)), the agent holds a lock at most about 1 % of a scan's time.
     - **Busy timeout 100 ms**: when a writer holds `PENDING` or `EXCLUSIVE` (or WAL recovery runs), the agent waits at most 100 ms and gives way. A unit that gets `SQLITE_BUSY` is retried once at its next paced turn, then counted `skipped_error`; a `check()` that gets it reports the last known state with `check.timed_out`.
     - **One connection per scan**, opened with decision 2's procedure, closed before any pause longer than 30 s and reopened afterwards with the full procedure (an idle WAL connection keeps the `-shm` mapped and its `DMS` read lock, which stops the last application connection from cleaning up the WAL at close). A file whose `(st_dev, st_ino)` changed since the scan started ends the scan for that target: the remaining objects are counted `skipped_error`. `check()` uses its own short connection (decision 6).
   - **Network file systems are refused** (decision 2, step 2), with no opt-in in this ADR (open question 5): POSIX locks are unreliable on many of them, so readers can see torn pages; the WAL index (`-shm` in shared memory) only works when every process is on one host; and a scan would turn into network I/O towards a file server the agent was never told about.

4. **Hardening against hostile files.**
   - **Threat model.** The file is application data; whoever controls the application, or can make it store a crafted file (an upload, a synced file, a compromised application account), controls every byte of it, its schema SQL included, and can write it while the agent reads it. Their goals: code execution or memory disclosure in the agent (the main risk: the agent holds the console secret, the HMAC key and other targets' credentials, I3); making the agent run code from the file (SQL functions, triggers, views, virtual-table modules, extensions); making the agent write (I4); exhausting the agent's memory, CPU or time, or blocking the application; hiding data from Discovery (accepted: whoever writes the file controls what it holds).
   - **Connection setup**, in this order, right after `sqlite3_open_v2` and **before the first statement** (SQLite reads the schema lazily at the first statement, Context):
     1. **Limits** (`set_limit`): `ATTACHED` 0 (no `ATTACH`, whatever else fails), `VARIABLE_NUMBER` 8, `LIKE_PATTERN_LENGTH` 50, `TRIGGER_DEPTH` 1, `WORKER_THREADS` 0, `VDBE_OP` 250 000, `LENGTH` 1 048 576 (a value above 1 MiB fails its statement with `SQLITE_TOOBIG`, the backstop of the sampling bound), `SQL_LENGTH` 1 000 000. **Limits the parser applies to the schema** (`COLUMN`, `EXPR_DEPTH`, `COMPOUND_SELECT`, `FUNCTION_ARG`, `PARSER_DEPTH`) **keep their defaults**: lowering them would make a legitimate schema fail to load, and the whole file would be unreadable. This lowers fewer limits than ADR-0039 decision 5 ("lowered `SQLITE_LIMIT_*` values") suggests; the implementation PR records, with a fixture per limit, which ones apply to the schema.
     2. **`sqlite3_db_config`**: `DEFENSIVE` on; `TRUSTED_SCHEMA` off (also the compile-time default, decision 1); `ENABLE_TRIGGER` off; `ENABLE_VIEW` off; `ENABLE_ATTACH_CREATE` off; `ENABLE_ATTACH_WRITE` off; `NO_CKPT_ON_CLOSE` on; `DQS_DML` off (the connector's own statements; `DQS_DDL` keeps its default, to verify that it does not affect reading an old schema); `REVERSE_SCANORDER` per scan (decision 5); `ENABLE_FTS3_TOKENIZER` and `WRITABLE_SCHEMA` off (their defaults, set explicitly).
     3. **Pragmas**: `query_only = ON`, `cell_size_check = ON` (page-level consistency checks while reading), `mmap_size = 0`, `temp_store = MEMORY` (no temporary file is written), `cache_size = -2048` (2 MiB), `automatic_index = OFF` (no transient index, which would scan a whole table), `trusted_schema = OFF`; and, once per process, `hard_heap_limit = 67108864` (64 MiB). The heap limit is process-wide (Context); in the agent only this connector uses SQLite, so it bounds this connector as a whole. An allocation past it fails with `SQLITE_NOMEM` (`resource_limit`), never the process.
     4. `busy_timeout(100 ms)`, the progress handler (decision 3), then the **authorizer**, installed last so that the setup pragmas above are the only assignments ever made. It allows `SQLITE_SELECT`; `SQLITE_READ` on the one table the statement is for, and on `sqlite_schema` (under either of its names, `sqlite_master` included) and `sqlite_stat1` for the catalog statements; `SQLITE_FUNCTION` for `typeof`, `octet_length`, `substr`, `min`, `max` only; `SQLITE_PRAGMA` for `table_xinfo` with an argument and for `journal_mode`, `schema_version`, `page_size`, `encoding` and `compile_options` **without** an argument; and **denies everything else** (`ATTACH`, `DETACH`, every write, `CREATE` / `DROP` / `ALTER`, `TRANSACTION`, `SAVEPOINT`, `ANALYZE`, `REINDEX`, `RECURSIVE`, any other pragma, any other function). The authorizer is not called while SQLite reads the file's schema (Context), so it guards the connector's own statements and whatever a schema object would add to them (a denied function in a view or a generated column fails the statement, never runs).
   - **A closed list of statements**, built from constant templates in which only identifiers are inserted, each through one quoting function (`"` + the name with `"` doubled + `"`; a name with a NUL byte, more than 1 024 bytes or invalid UTF-8 is never quoted: its object is counted `skipped_unsupported`); numbers are bound parameters:
     - catalog: `SELECT type, name, rootpage FROM main.sqlite_schema WHERE type IN ('table', 'view')` (the `sql` column is never read);
     - columns: `PRAGMA main.table_xinfo(<name>)`, only for a `table` row with `rootpage` > 0 (an ordinary table; a virtual table has `rootpage` 0), reading `name`, `type`, `pk` and `hidden` only (`dflt_value`, which can hold literals, is not read);
     - statistics: `SELECT tbl, stat FROM main.sqlite_stat1 WHERE idx IS NULL OR idx = tbl` when `sqlite_stat1` exists (decision 5);
     - rowid bounds: `SELECT min(<rowid>), max(<rowid>) FROM main.<t>`;
     - sampling: `SELECT <guarded columns> FROM main.<t> WHERE <rowid> >= ?1 ORDER BY <rowid> LIMIT ?2`, its wrap-around `… WHERE <rowid> < ?1 ORDER BY <rowid> LIMIT ?2`, and `SELECT <guarded columns> FROM main.<t> LIMIT ?1` for `WITHOUT ROWID` tables (decision 5);
     - check: `PRAGMA main.journal_mode`, `PRAGMA main.schema_version`, `PRAGMA main.page_size`, `PRAGMA main.encoding`; at start, `PRAGMA compile_options` on an in-memory connection (decision 1).
     **`PRAGMA table_list` and `pragma_*` table-valued functions are never used**: `table_list` compiles every view and connects every virtual table (Context).
   - **Schema objects.**
     - **Views are not sampled** (`ENABLE_VIEW` off; their base tables are sampled; counted in `coverage.views_not_sampled`). Sampling a view would run its SQL, functions included.
     - **Triggers never fire** (no write; `ENABLE_TRIGGER` off).
     - **Virtual tables are never read, listed through a module or connected** (FTS3/4/5, R-tree, and any module, available or not: a schema naming an unknown module parses, and the error would only come at first use, which never happens). Counted in the new `coverage.virtual_tables_not_sampled`. Their **shadow tables** (`<name>_content`, `<name>_data`… for FTS) are ordinary tables in `sqlite_schema` and are sampled like any table: the text an FTS index holds is in them.
     - **Generated columns**: `VIRTUAL` ones (`hidden` = 2) are not sampled, since reading them evaluates an expression from the file (counted in `coverage.computed_columns_not_sampled`); `STORED` ones (`hidden` = 3) are read like any column (their value is stored).
     - `CHECK` constraints, `DEFAULT` clauses, partial and expression indexes, foreign keys and collations are not evaluated by the connector's reads (no write, no `WHERE` on a user column, no `ORDER BY` on anything but the rowid).
     - **Internal tables** (`sqlite_%`: `sqlite_sequence`, `sqlite_stat1` to `sqlite_stat4`) are not sampled. `sqlite_stat4` holds copies of indexed key values (residual risk).
   - **No `PRAGMA quick_check` or `integrity_check`** (decided here, as the P10-A task asks): either reads the whole file under one read transaction, which costs time proportional to the file and, in rollback mode, blocks the application's commits for that whole time. Corruption is caught where it is read (`cell_size_check`, SQLite's own checks, `SQLITE_CORRUPT` per statement, decision 6). Open question 6.
   - **No encryption support.** SQLCipher, SEE and the like are detected by the header pre-check (an encrypted file has no plain header) and refused with `coverage.unrecognized_file_format`; a SQLCipher "plaintext header" file passes the pre-check and fails at its first page read with `SQLITE_NOTADB`, reported the same way. Reading them would need their C crypto (OpenSSL or libtomcrypt) and the key on the agent host: rejected.
   - **Errors and text.** Every SQLite error is reduced to its extended result code (decision 6). The error message (`rusqlite::Error::SqliteFailure`'s `Option<String>`, which can name tables and columns or quote SQL) is dropped where the error is mapped and is never logged, displayed or sent; the connector never installs `SQLITE_CONFIG_LOG` (whose messages carry paths). A text-level test (decision 1) and a unit test of the mapping guard it.
   - **Memory hygiene.** Values are copied out of SQLite into `RawValue` (zeroized on drop) and classified through `ScanJob::classify` / `classify_guarded` and `classifiers::masking` (I2). SQLite's own page cache and the memory it frees are not wiped (residual risk); the unit's `LimitCORE=0` keeps them out of core dumps.
   - **Panics and crashes.** The core's per-connector panic isolation ([ADR-0029](0029-openldap-connector.md) decision 1) covers Rust panics; a crash inside the C library ends the agent process, which systemd restarts (`Restart=on-failure`); a file that crashes the agent at every scan is a denial of service of the agent by the file's author (residual risk; the crash itself is a SQLite bug to report upstream).
   - **Fuzzing** (P10-A "Fuzz target with hostile database files").
     - Target **`sqlite_file`**: the input is split into a main file and an optional `-wal` (a length prefix), written to a private temporary directory (mode `0700`, then made read-only), and run through the connector's real pipeline: the path and file checks, the header pre-check, the connection setup, the catalog, `table_xinfo` and sampling statements, with the production limits and a small statement deadline.
     - Target **`sqlite_header`**: the Rust header pre-check alone (no SQLite).
     - Property tests: the quoting function, the URI encoder (round trip through `Connection::path()`), the header pre-check against SQLite's own verdict on generated headers, the error mapping (no message survives).
     - Seed corpus: the dev seeded files (decision 8), files written by several SQLite versions, page sizes 512 and 65 536, UTF-16 encodings, `auto_vacuum`, overflow pages, freelists, `WITHOUT ROWID`, `STRICT`, generated columns, FTS shadow tables, hot journals and WAL files.
     - Both targets join the nightly AddressSanitizer workflow (#179). The C code is built with `-fsanitize=address` (`libsqlite3-sys`'s `with-asan` feature, fuzz workspace only) and with coverage instrumentation through `CFLAGS` (`-fsanitize=fuzzer-no-link`, to verify with cargo-fuzz), so the fuzzer sees inside SQLite. A crash found in SQLite is reported upstream and fixed by a library update and an agent release.

5. **Discovery** (bounded, I4; paced by the core, [ADR-0035](0035-discovery-pacing.md)).
   - **One database, `main`.** Other databases are never attached (`ATTACHED` limit 0, authorizer, closed statements).
   - **Catalog**: the `table` and `view` rows of `sqlite_schema` (decision 4), at most 10 000 objects read per scan (beyond, `skipped_limit`), rotated per scan (`ScanJob::rotate`, ADR-0035 decision 4). Each unit of work goes through `job.paced` (decision 3's statement deadline is the upper bound of one unit's lock time): the catalog read; then, per table, `table_xinfo` and the sampling statements.
   - **Columns**: every column of an ordinary table (rowid tables, `WITHOUT ROWID`, `STRICT`, FTS shadow tables) except `VIRTUAL` generated columns, at most 64 per sampling statement (a wider table takes several statements, each a paced unit).
   - **Values by storage class**, not by declared type: SQLite types each value, and a column declared `TEXT` may hold integers while one declared without a type may hold anything. `TEXT` values are sampled (SQLite converts UTF-16 databases to UTF-8 on read); `INTEGER` values are sampled as their decimal text (phone and card numbers stored as numbers, as the PostgreSQL connector samples `int8` and `numeric`); `REAL`, `BLOB` and `NULL` values are not (as `bytea` and floats elsewhere; BLOBs holding text are open question 8). Each column is selected as `CASE WHEN typeof(c) IN ('text', 'integer') AND octet_length(c) <= 65536 THEN substr(c, 1, 4096) END`, so a value larger than 64 KiB is never loaded whole into memory by SQLite (`typeof` and `octet_length` read only the record header; to verify by a test with a value above `SQLITE_LIMIT_LENGTH`, which stays the backstop), then cut to 4 096 bytes on a character boundary in Rust, as the other connectors do. These are built-in functions on the agent's own connection: the file cannot redefine them (no function is registered on the connection, and none can be defined by a schema), so the PostgreSQL rule of applying no function to a sampled column ([ADR-0012](0012-postgresql-agent-grants.md) obligation 3, which guards against user-defined overloads) does not apply here. A statement that still fails with `SQLITE_TOOBIG` is retried once column by column; the columns that fail again are counted with the table as `skipped_limit`.
   - **Bounds per table**: at most `job.sample_rows()` rows (clamped by `limits.max_sample_rows`), at most 32 MiB of value bytes read per table (the PostgreSQL connector's per-relation budget; the unit stops there and the table counts `skipped_limit`), each statement under decision 3's deadline.
   - **Row order without a full scan**: a `LIMIT` with no `WHERE` and no `ORDER BY` reads only the rows it returns, but always the same first ones. **Rowid tables**: `min` and `max` of the rowid come from the two ends of the b-tree (`O(log n)`); a start key is drawn uniformly between them from the scan's seed; the sample reads `rowid >= start` in rowid order, then wraps around from the beginning (both are range reads of the table's own b-tree, no sort). The rowid is addressed as `rowid`, `_rowid_` or `oid`, the first one that is not a declared column name; a table that declares all three is sampled from its start (no rotation). **`WITHOUT ROWID` tables**: the plain `LIMIT` read, with `SQLITE_DBCONFIG_REVERSE_SCANORDER` set from the scan seed's parity, so successive scans read the first or the last rows of the primary-key b-tree, never sorting.
   - **`estimated_rows`** from `sqlite_stat1` (the table's row count, the first integer of `stat`, parsed with a bound) when the application ran `ANALYZE`; omitted otherwise. Never `count(*)`, which reads every page of the table.
   - **`Location`** (engine `sqlite`): `database` = `main` (SQLite's own name for the file's database, the same for every target; the target id tells files apart); no `schema`; `object` = the table name; `field` = the column name. Names are normalized as one key each, as on MySQL / MariaDB (`normalize_field_path(&[PathPart::Key(raw)])`: a name containing `.` becomes `*`, a name matched by a classifier becomes `*`; [ADR-0009](0009-name-normalization-and-item-sanitization.md)); the [ADR-0057](0057-identifier-hardening-agent-first.md) rules apply on output, and parts altered by stripping or NFKC carry the [ADR-0056](0056-names-altered-by-normalization-marker.md) marker (`location.altered`), as on every engine. Names come from `sqlite_schema.name` and `table_xinfo`, as the application declared them.
   - **Case semantics: a fixed rule, no `name_case`.** SQLite compares identifiers without case for ASCII letters only, whatever the configuration (`Ä` and `ä` are two names; trailing spaces are significant). The console's rule for an engine outside `CASE_BLIND_EXCEPTION_ENGINES` (exceptions match only when the folded **and** the exact comparisons both match, ADR-0054) is the right one for `sqlite`: SQLite cannot hold two tables whose names differ only by ASCII case, so comparing with case separates nothing SQLite keeps together, while comparing without case, with the console's Unicode fold, would let an exception for `Ärzte` cover a distinct table `ärzte`. Comparing with case can only make an exception typed in another ASCII case cover less (more alerts, never fewer). So `sqlite` stays out of `CASE_BLIND_EXCEPTION_ENGINES` and out of `TRAILING_SPACE_BLIND_ENGINES` (P10-E adds a test that says so), and the agent sends no `TargetStatus.name_case` for it (the contract restricts that field to `mysql`, `mariadb` and `sqlserver`, and a fixed rule needs no report; ADR-0055's consequences ask for this decision).
   - **Coverage counters**: `objects_sampled` (tables sampled); `skipped_not_readable` (a table whose pages fail to read, `SQLITE_CORRUPT` included); `skipped_unsupported` (virtual tables, names that cannot be quoted, CAS stores); `skipped_limit` (the object bound, the byte budget, `SQLITE_TOOBIG`, the scan's time budget); `skipped_error` (`SQLITE_BUSY` twice, an interrupted statement, a table gone since the catalog read, a file replaced during the scan). Views are counted in `coverage.views_not_sampled`, not in the counters.
   - **CAS store guard** ([ADR-0041](0041-cas-connector.md) decision 5): the core's name guard (the built-in CAS ticket registry and audit trail names; the `sqlite` block has no `cas_stores` key, a follow-up if CAS stores in SQLite files appear) and the ticket-id value tripwire of the shared sampling path apply as on the other engines. A recognized CAS store is **not read at all** on SQLite (the metadata aggregate of the other engines is a full table scan here) and counts `skipped_unsupported`; a tripped column is counted in `coverage.cas_guard_tripped`.

6. **`check()` and the target state.**
   - **Audit level `none`**, no `audit_source`, `supports_audit()` false (so an `audit.configure` job ends `unsupported`); `server_version` and `edition` are omitted (there is no server; the version of the SQLite that last wrote the file, header offset 96, goes to the agent's log only). The console shows such targets as "Discovery only" (P10-E).
   - **Reachable** when decision 2's open procedure passes, the connection setup succeeds and the catalog statement reads `sqlite_schema`.
   - **Cost.** A full check (SQLite opened, the schema read, the `journal_mode`, `schema_version`, `page_size` and `encoding` pragmas, the `/proc/self/fd` binding) runs at the first heartbeat, when the file's `(st_dev, st_ino)`, size, `mtime` or header change counter (offset 24) changed, and otherwise at most every 10 minutes per target. Every other heartbeat re-runs only the path and file checks and the header pre-check (no SQLite connection, no lock taken). Budget: 2 s per check, under the heartbeat's 10 s deadline (ADR-0025); a check that cannot take the per-target lock within its budget (a scan unit is running) reports the last result.
   - **File permission checks at every check**: a file, side file or ancestor directory that became writable by the agent turns the target unreachable at once (`privilege.database_file_writable`).
   - **Failure codes** (closed set; `engine_code` = SQLite's extended result code as a decimal number, which fits `EngineCode`; the stage is the `check.stage_failed` label):

     | Cause | `last_error` | Stage | Note |
     |---|---|---|---|
     | path or a component missing (`ENOENT`) | `target_unreachable` | `stage_connect` | |
     | not readable by the agent (`EACCES`) | `permission_denied` | `stage_connect` | |
     | a symlink in the path, not a regular file, `st_nlink` > 1, a duplicate of another target's file, a path under the agent's own or system directories, a side file of the wrong owner | `unsupported` | `stage_connect` | |
     | the file, a side file or an ancestor directory writable by the agent | `unsupported` | `stage_connect` | `privilege.database_file_writable` |
     | a network or FUSE file system | `unsupported` | `stage_connect` | `coverage.network_filesystem_refused` |
     | header pre-check failed, `SQLITE_NOTADB`, a schema the library cannot parse | `unsupported` | `stage_introspection` | `coverage.unrecognized_file_format` |
     | `SQLITE_CORRUPT*` while reading the schema | `unsupported` | `stage_introspection` | |
     | WAL side files missing, unreadable or too large; `SQLITE_CANTOPEN` or `SQLITE_READONLY_DIRECTORY` on a WAL file; `SQLITE_READONLY_CANTINIT`, `SQLITE_READONLY_RECOVERY` | `target_unreachable` | `stage_connect` | `coverage.wal_files_not_readable` |
     | `SQLITE_READONLY_ROLLBACK` (hot journal) | `target_unreachable` | `stage_connect` | `coverage.hot_journal_pending` |
     | `SQLITE_BUSY` / `SQLITE_LOCKED` past the busy timeout, the deadline (`SQLITE_INTERRUPT` from the progress handler) | `timeout` | the stage reached | `check.timed_out` |
     | the scan or check cancelled | `cancelled` | the stage reached | |
     | `SQLITE_NOMEM` (heap limit), `SQLITE_TOOBIG` | `resource_limit` | the stage reached | |
     | the compile-option self-check failed (decision 1) | `unsupported` | `stage_session_setup` | |
     | `SQLITE_AUTH` (the authorizer refused one of the connector's own statements: a bug), anything else | `internal` | the stage reached | |

   - **Notes** (counts only, no label, decision 7): the codes in the table, plus `security.file_world_readable` (the database file is readable by every local user: its data is exposed to every account of the host; open question 9), `coverage.views_not_sampled`, `coverage.virtual_tables_not_sampled`, `coverage.computed_columns_not_sampled`, `coverage.cas_guard_tripped` from the last scan, `check.stage_failed`, `check.timed_out`.

7. **Protocol (P10-C, compatible changes under [ADR-0022](0022-protocol-capability-negotiation.md) with a `security-reviewer` review)**, following ADR-0039 decision 8 and [ADR-0042](0042-hold-items-of-unlisted-engines.md):
   - `Engine` gains **`sqlite`** under the token **`engine.sqlite`**; `Connector` gains **`sqlite`**, sent only when that token is listed. Until a heartbeat response lists it, the agent reports no `sqlite` target or connector, holds findings batches carrying `Location.engine: sqlite` in the spool (ADR-0042 decision 2), and logs that the console is too old. The token functions are exhaustive matches, so the build forces the new value.
   - `ConnectorList.maxItems` is already 16 (8 values with `sqlite`): no change, unlike what ADR-0039 decision 8 anticipated.
   - No `AuditSource` value, no `DetectedTarget` change (no local detection), no `signals.json` entry, no classifier change.
   - The `Location` description gains the SQLite mapping of decision 5 (`database` = `main`, no `schema`, table, column; never a path or file name). `object` stays an `Identifier`.
   - `target-notes.json` (append-only): **new codes** `coverage.unrecognized_file_format`, `coverage.wal_files_not_readable`, `coverage.hot_journal_pending`, `coverage.network_filesystem_refused`, `coverage.virtual_tables_not_sampled`, `privilege.database_file_writable`, `security.file_world_readable`, all with engines `[sqlite]`; **`sqlite` added** to the engines of `check.stage_failed`, `check.timed_out`, `coverage.views_not_sampled`, `coverage.computed_columns_not_sampled` and `coverage.cas_guard_tripped`. Counts only, no new `TargetNoteLabel`, so no label revision token.
   - Every change in `shared/protocol/` (the enums, the `Location` text, the registry, the fixtures and the generated types on both sides) goes through a **`security-reviewer` review**, as AGENTS.md requires.

8. **Versions** (ADR-0039 decision 1).
   - **The library is the agent's, not the file's.** Every SQLite 3 file format is read by the bundled library: files written by any SQLite 3 version, WAL files by 3.7.0 and later writers. The supported range is a **file format** range: magic `"SQLite format 3\0"`, read and write versions 1 and 2, schema format 1 to 4, UTF-8 or UTF-16 (LE or BE), page sizes 512 to 65 536. A file outside it is refused (decision 6). There is no end-of-life version to drop: SQLite has one maintained line (to verify against sqlite.org's support policy).
   - **Bundled library**: SQLite **3.53.2** through `rusqlite` 0.40.2 / `libsqlite3-sys` 0.38.2 at the time of writing; the floor is **3.49.0** (the newest feature used: `SQLITE_DBCONFIG_ENABLE_ATTACH_CREATE` / `_WRITE`; `octet_length` needs 3.43, `REVERSE_SCANORDER` 3.42). The library is kept at the latest release `rusqlite` offers on the workspace MSRV; a SQLite security fix is shipped as an agent patch release, as for any advisory.
   - A schema that uses syntax newer than the bundled library fails to load and is reported `unsupported` (`coverage.unrecognized_file_format`) until a library update.

9. **Dev, CI, end to end and load** (ADR-0039 decision 9, P10-D).
   - **Dev**: `dev/seed/generate.py` writes seeded SQLite files under `dev/.state/sqlite/` (never committed) from the same fake data as the other engines, listed in `dev/ground-truth.json`: a rollback-mode file and a WAL file; rowid, `WITHOUT ROWID` and `STRICT` tables; personal data in `TEXT` and in `INTEGER` columns (phone and card numbers); value-bearing table and column names (so the I2 check covers names); a view, a `VIRTUAL` and a `STORED` generated column, an FTS5 table whose content is in its shadow table (the ground truth expects the finding on the shadow table, none on the virtual table), a BLOB column holding a ground-truth value as bytes (expected: not found), a UTF-16 file, a value above 64 KiB; and the file modes and group of decision 2. A small writer process keeps the WAL file open, so its `-wal` and `-shm` exist, as with a running application. Hostile fixtures (a crafted header, a SQLCipher file, a hot journal, a symlinked path, a hard link, an agent-writable directory) are generated by the integration tests themselves.
   - **CI**: a required job `agent-sqlite` runs the connector's integration tests against those files (no service container needed). The **engine matrix** covers the **writers**, since the reader is always the bundled library: files written by the SQLite of the supported distributions' Python images (pinned by digest; for example Debian 12's 3.40 and Ubuntu 24.04's 3.45, to re-resolve at implementation), and by the bundled version; in `DELETE`, `TRUNCATE`, `PERSIST` and `WAL` journal modes; with page sizes 512, 4 096 and 65 536; `auto_vacuum` off and on.
   - **End to end**: an `e2e-sqlite` job (required through `CI result`, like `e2e-cas`): the seeded files bind-mounted read-only into the agent container, owned by another uid, group-readable by the agent's group; a writer sidecar holding the WAL file open; a Discovery scan with findings; the I2 check on values and names; an `audit.configure` attempt ending `unsupported`; the console showing "Discovery only".
   - **Load** (`e2e/load/`, job `load-sqlite`): there is no server CPU to measure, so the measured impact is on a **concurrent writer**. A writer process runs a fixed workload (for example 200 transactions per second of inserts and updates) on a file of at least 1 GiB while a paced Discovery scan runs, against a baseline without scan, in WAL mode and in rollback mode, with the writer's busy timeout at 0 and at 5 s. Measured: the writer's commit latency (p50, p95, p99), its `SQLITE_BUSY` count, the WAL size at the end (checkpoint starvation), and the agent's CPU share of one core and peak RSS during the scan (the analogue of the < 2 % criterion: SQLite's work happens in the agent's process on the application's host). Criteria proposed for the maintainer: WAL mode, no `SQLITE_BUSY` and a p95 within 5 % of the baseline; rollback mode with a 5 s busy timeout, no failed commit and a p99 increase below `max_statement_ms`; rollback mode without a busy timeout, the `SQLITE_BUSY` rate measured and documented (open question 7); the agent under 2 % of one core.

10. **Invariants.**
    - **I1**: the connector opens no network connection of any kind and no listener (architecture test, decision 1); network file systems are refused, so reads are local I/O.
    - **I2**: sampled values reach the uplink only through `ScanJob::classify` and `classifiers::masking`; names are normalized (ADR-0009, ADR-0056, ADR-0057); the path and file names never leave the agent; SQLite error messages are dropped.
    - **I3**: there is no credential; the agent's own secrets are protected by keeping their files out of SQLite's reach (decision 2's refused directories and header pre-check) and, against a hostile file, by decision 4.
    - **I4**: read-only by three layers (decision 3), autocommit reads with a bounded deadline, the closed statement list and the authorizer.
    - **I5**: declared files only; no directory, glob or search; no local detection.
    - **I6**: the protocol changes go through `shared/protocol/openapi.yaml` and the registries, with generated types.
    - **I7**: SQLite is public domain, `rusqlite` and `libsqlite3-sys` are MIT.

## Consequences
- A new crate, `agent/crates/connector-sqlite`; `agent.yaml` gains `targets[].sqlite` (`path`, `max_statement_ms`), with `account` and `secret` refused for `engine: sqlite`; the core's `TargetEngine` and `Engine` gain `Sqlite`.
- `agent/deny.toml`, `agent/crates/agent/tests/architecture.rs` and a new `agent/.cargo/config.toml` change as decision 1 states; any new C code in the agent's graph now needs a reviewed change of the allow-list.
- The agent binary contains the SQLite C library (size and build time to measure). A SQLite security fix needs an agent release; Dependabot and the advisories job surface it.
- Two fuzz targets join the nightly workflow, and the fuzz workspace builds C code with AddressSanitizer.
- The contract changes of decision 7 (P10-C); the console (P10-E) accepts `engine.sqlite`, renders the new notes and "Discovery only", and keeps `sqlite` out of its case-blind and trailing-space-blind engine lists.
- docs-keeper (P10-G): a "SQLite Discovery" section in [08-engine-capabilities.md](../08-engine-capabilities.md) (Audit None; WAL files read only while the application holds them open; views and virtual tables not sampled; `REAL` and `BLOB` values not sampled; rollback-mode writers and the measured impact), the file permissions recipe in [05-security.md](../05-security.md#recommended-database-accounts-read-only) with the systemd drop-in, a README row, [03-tech-stack.md](../03-tech-stack.md) (the bundled SQLite, the exception to "no C client library").
- In practice SQLite is a Discovery-only engine; its README row says so (ADR-0039 consequences).

### Residual risks
- **C code parsing attacker-controlled files in the agent's process.** A memory-safety bug in SQLite reachable from a file (the record and b-tree decoders, the WAL reader, the schema parser) could run code with the agent's privileges and read its secrets. Contained, not removed: the defensive settings, the limits, `cell_size_check`, no execution of views, triggers, virtual tables or extensions, a small allow-listed set of built-in functions, the header pre-check, the fuzz targets, upstream fuzzing, and the systemd sandbox (no write outside the state directory, no new privileges, no inbound socket). Process isolation is open question 2.
- **A file that crashes the C library** stops the whole agent at each scan until the file changes or the library is fixed (a denial of service of every target of that agent).
- **WAL databases are unreadable while no application holds them open** (no `-wal` / `-shm`), and their newest commits are read through a heap index built from the whole `-wal` when no writer is connected.
- **Rollback-mode writers wait for the agent's reads** (at most `max_statement_ms` per statement, about 1 % of a scan's time at the default duty cycle); an application with no busy timeout can get `SQLITE_BUSY` on a commit during a scan.
- **A WAL reader pins checkpoints** for the length of one statement; a long chain of statements could let the WAL grow while a scan runs (measured by the load run).
- **The application's account can swap the file** between two opens (it can write the directory). Each open is bound to a checked regular file with one link (decision 2), so what it can present is another SQLite file the agent can read (the agent then reports that file's tables under this target). Side files are checked by path before the open, not bound like the main file: a planted `-wal` of the right owner is read as the WAL, but an application that can plant one can already write the database.
- **SQLite's memory is not wiped**: its page cache and freed buffers hold raw pages until reused; core dumps are disabled.
- **`sqlite_stat4`** holds copies of indexed values and is not sampled; neither are `REAL` and `BLOB` values (a BLOB holding text is not found).
- **Hidden data**: whoever writes the file controls what Discovery sees (a corrupt page, a virtual table, data stored in BLOBs).
- **`readonly_shm` is undocumented**: its behaviour could change in a SQLite release; layer 1 of decision 3 still holds and the tests detect the change.
- **The compile-option check** relies on `PRAGMA compile_options`; a build that missed `LIBSQLITE3_FLAGS` is caught at start, but only for the options the check lists.

## Rejected alternatives
- **An own pure-Rust reader, `turso_core`, `sqlite-core`**: see decision 1; the own reader stays the fallback of open question 2.
- **The system `libsqlite3`**: see decision 1.
- **Shelling out to the `sqlite3` command-line tool**: process spawning, output parsing of a tool that prints values, no bounds (ADR-0039 rejected alternatives).
- **`immutable=1`** or **`nolock=1`** on live files: wrong results and missed commits (decision 3).
- **Letting the agent write the `-shm`** (or create side files): breaks I4 (decision 3).
- **Opening through `/proc/self/fd/<n>`** to bind SQLite to the checked descriptor: SQLite derives `<name>-wal` and `<name>-shm` from the name it opened, so WAL databases would not work, and `SQLITE_OPEN_NOFOLLOW` refuses the magic link.
- **Reading a copy** (`sqlite3_deserialize` of the file read into memory): it needs the whole file in memory, cannot see the `-wal`, and a copy taken while the application writes can be torn. Kept only as the possible answer to open question 3 for quiescent WAL files.
- **`PRAGMA table_list`** for the catalog: compiles views and connects virtual tables (Context).
- **Sampling views**: runs SQL from the file.
- **`quick_check` / `integrity_check` before use**: cost and lock time (decision 4; open question 6).
- **Declaring a directory of SQLite files, or a glob**: I5 (decision 2).
- **Following symlinks in the path** (resolved at load, as ADR-0039 decision 5 wrote): SQLite resolves them itself per component and `SQLITE_OPEN_NOFOLLOW` refuses them; one rule is simpler (decision 2).
- **Refusing every database whose directory another user can write** (ADR-0039 decision 5's wording): the application must write its journals there (decision 2).
- **Reporting the path, or a hash of it**: the path holds names, and a hash of a low-entropy path is an oracle; the target id is the operator's chosen name.
- **`TargetStatus.name_case` for SQLite**: the rule is fixed and the console's default is already right (decision 5).
- **SQLCipher support**: its C crypto, OpenSSL in most builds, and a key on the agent host.
- **Lowering every `SQLITE_LIMIT_*`**: limits the parser applies to the schema would make legitimate files unreadable (decision 4).

## Open questions (for the maintainer)
1. **Accept ADR-0039 decisions 3 (SQLite row), 4, 5 (SQLite item), 7 (SQLite part) and 9 for SQLite as refined here** (no symlink in any component, the parent-directory rule, the limits that stay at their defaults, no `ConnectorList` change). *Proposed answer*: accept, so the implementation is held to this ADR and nothing wider.
2. **Process isolation of the SQLite reader.** The agent could run the C library in a child process of its own binary (a fresh `exec`, no secret in memory, no network, a seccomp filter, read-only Landlock rules on the declared paths, `RLIMIT_AS`), returning raw values to the parent over a socket pair for classification. That contains a memory-safety bug in SQLite, at the cost of a process launcher, an IPC protocol (another parser), new dependencies with `unsafe` (seccomp, Landlock) and kernel-version dependencies, and an exception to ADR-0039's "spawns no process". *Proposed answer*: not in the first implementation; the P10-F review of the implementation and the first nightly fuzz campaign decide whether a follow-up ADR is needed, with the own pure-Rust reader as the other fallback.
3. **Quiescent WAL databases** (no `-wal` / `-shm`, application stopped). Options: (a) report `coverage.wal_files_not_readable` and read the file when the application runs again; (b) read a bounded in-memory copy (`sqlite3_deserialize`, `rusqlite`'s `serialize` feature) when no `-wal` exists before and after the copy and the file's size and `mtime` did not change, the header patched to rollback mode in the copy. *Proposed answer*: (a) in the first implementation; (b) as a follow-up only if users report stopped applications as a common case.
4. **`rusqlite` 0.41 and MSRV 1.89.** `rusqlite` 0.41.0 (SQLite 3.54.0) needs Rust 1.89. *Proposed answer*: start on 0.40.x (SQLite 3.53.2) at MSRV 1.88; raise the workspace MSRV to 1.89 in a separate PR when a SQLite fix or a needed feature is only in 0.41 or later (the "Agent MSRV" job and `release.yml` move together).
5. **Network and FUSE file systems**: refused with no opt-in? *Proposed answer*: refused; revisit only with a measured, locked-down case (for example a read-only NFS export of files no one writes).
6. **An optional `PRAGMA quick_check`** (local opt-in, small files only)? *Proposed answer*: no; corruption is handled where it is read.
7. **Rollback-mode databases**: allowed by default with the bounded, paced reads, or only with a local opt-in because an application without a busy timeout can see `SQLITE_BUSY`? *Proposed answer*: allowed by default, documented, and decided again after the load run measures the `SQLITE_BUSY` rate; if it is not negligible, a target note for rollback-mode targets is added (a new code, append-only).
8. **BLOB values that hold text** (some applications store JSON or text as BLOBs): sample BLOBs that are valid UTF-8? *Proposed answer*: not in the first implementation (consistent with `bytea` and `BLOB` elsewhere); a follow-up for every engine together if users ask.
9. **`security.file_world_readable`**: report a database file readable by every local user? *Proposed answer*: yes; it is cheap, it is the kind of exposure a DLP exists to show, and it carries no value.
10. **The `max_statement_ms` default (500 ms) and range (50 to 5 000 ms)**, and the other constants (busy timeout 100 ms, 64 MiB heap, 128 MiB WAL cap, 32 MiB per table, 10 000 objects, 64 columns per statement). *Proposed answer*: constants as written, `max_statement_ms` the only `agent.yaml` key; the load run may revise them.
