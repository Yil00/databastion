## Context
Phase 10 adds SQLite ([ROADMAP](../ROADMAP.md#phase-10--engine-scope-wave-2-sqlite-firebird)). SQLite is not a server: it is a C library linked into each application, and a database is a file (plus, while in use, a `-wal` and a `-shm` file, or a `-journal` file, next to it). Every rule of the other connectors still applies: read-only and bounded (I4), declared targets only (I5), masking before the uplink (I2), honest `check()`, closed notes ([ADR-0022](0022-protocol-capability-negotiation.md)). SQLite raises questions the other engines did not:

- **No server, no account, no access log.** There is nothing to authenticate to and nothing that records reads: reads happen inside the applications that open the file. Audit is **None by nature** (ADR-0039 decision 3). Least privilege is the agent's Unix account and the file's permissions.
- **The reader parses the file itself.** For every other engine, the server parses its own files and the agent parses only a bounded protocol. Here the SQLite library parses the file, its b-trees, its WAL and the schema SQL it compiles, and the file is written by an application, so it may be **attacker-controlled**. A memory-safety bug reachable from a file, run in the agent's process, would run where the console secret, the HMAC key and the credentials of every other target are held. Decision 4 therefore runs the library in a separate, sandboxed process.
- **Reading a live file without writing to it** is harder than it looks (WAL databases, below).
- **The path is data.** A path such as `/srv/clients/jdupont/notes.db` holds personal names (ADR-0039 decision 7).

### Facts verified for this ADR
Read on 2026-10-24 in the sources of `rusqlite` 0.40.2 and `libsqlite3-sys` 0.38.2 (downloaded from crates.io) and in the SQLite **3.53.2** amalgamation that `libsqlite3-sys` 0.38.2 bundles (`sqlite3/sqlite3.c`, `sqlite3/sqlite3.h`); the security review re-checked them in the same sources. The sqlite.org pages (`security.html`, `wal.html`, `uri.html`, `pragma.html`, `compile.html`) could not be fetched from the ADR's environment (the egress proxy answers `403` for sqlite.org); facts that only those pages state are marked **(to verify against sqlite.org)**. Nothing was built.

- **Open flags and URI parameters.** `SQLITE_OPEN_READONLY`, `SQLITE_OPEN_URI`, `SQLITE_OPEN_NOFOLLOW` ("the database filename is not allowed to contain a symbolic link") and `SQLITE_OPEN_EXRESCODE` exist. The documented URI parameters are `vfs`, `mode` (`ro`, `rw`, `rwc`, `memory`), `cache`, `psow`, `nolock` ("disables file locking in rollback journal modes … corruption might result if two or more processes write") and `immutable` ("SQLite assumes that the database file cannot be changed … all locking and change detection is disabled … can result in incorrect query results and/or `SQLITE_CORRUPT` errors" on a file that does change). `readonly_shm` is **not** in that documented list, but the unix VFS reads it (`sqlite3_uri_boolean(…, "readonly_shm", 0)` in `unixOpenSharedMemory`).
- **Symlinks.** `unixFullPathname` `lstat`s every component and counts symlinks; with `SQLITE_OPEN_NOFOLLOW` any symlink **in any component** fails the open (`SQLITE_CANTOPEN_SYMLINK`). Every file the unix VFS opens (database, `-wal`, `-journal`, `-shm`) gets `O_NOFOLLOW` on its final component.
- **What a read-only connection still tries to write.**
  - The `-wal` file is always opened with `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE` (`sqlite3WalOpen`), even by a read-only connection; the unix VFS tries `O_RDWR | O_CREAT` and falls back to `O_RDONLY` only when that fails, whatever the `errno` (`unixOpen`).
  - The `-shm` file is opened `O_RDWR | O_CREAT` unless the URI has `readonly_shm=1`, and `O_RDONLY` only when that fails (`unixOpenSharedMemory`).
  - When the database has 0 pages and a `-wal` exists, the pager **deletes** the `-wal` (`pagerOpenWalIfPresent`).
  - New `-wal` and `-journal` files are created with the database file's permission bits (`findCreateFileMode`, then `fchmod` past the umask); the `-shm` likewise (`st_mode & 0777`).
  So whether SQLite writes, creates or deletes a side file is decided by the operating system, not by the read-only flag.
- **The `-shm` is shared memory.** It is mapped `MAP_SHARED` (`unixShmMap`), so any process that can write the file (the application's account) can change the WAL index while the reader reads it, and a `ftruncate` of it makes the reader's next access raise `SIGBUS`, which kills the reading process.
- **A WAL database read with a read-only `-shm`.** When another process (a writer) holds the `-shm` "DMS" lock, the read-only mapping is reliable and the reader uses it. When nobody holds it, `unixLockSharedMemory` returns `SQLITE_READONLY_CANTINIT` and the WAL module builds a **private heap copy of the WAL index by reading the whole `-wal` file** (`walBeginShmUnreliable`), then checks again at every read transaction whether a writer has attached. A read-only reader that finds no usable read mark returns `SQLITE_READONLY_CANTINIT` or `SQLITE_BUSY`, and a corrupt WAL index header gives `SQLITE_READONLY_RECOVERY` (`walIndexReadHdr`, `walTryBeginRead`).
- **A WAL database whose `-wal` and `-shm` are absent** (the last application connection closed cleanly and deleted them): the file header still says WAL (byte 19 = 2), `lockBtree` calls `sqlite3PagerOpenWal`, which must create the `-wal`; in a directory the reader cannot write, the open fails (`SQLITE_READONLY_DIRECTORY` or `SQLITE_CANTOPEN`; the exact code is to verify by test). sqlite.org's WAL page states the same rule, "the `-shm` and `-wal` files already exist or those files can be created or the database is immutable" (to verify against sqlite.org).
- **A hot rollback journal** on a read-only connection gives `SQLITE_READONLY_ROLLBACK`.
- **POSIX advisory locks.** SQLite's own comment: "POSIX advisory locks are broken by design": closing **any** descriptor of a file releases **every** lock the process holds on it. The unix VFS shares its own descriptors per inode to cope; a descriptor the process's own code opens and closes on the same file would silently drop SQLite's locks. Locks are per process: another process's descriptors do not affect them.
- **Locking.** In rollback-journal modes a reader holds a `SHARED` lock for the length of its read transaction, and a writer cannot commit (it needs `EXCLUSIVE`) until it is released; a writer without a busy timeout gets `SQLITE_BUSY`. In WAL mode an open connection keeps its `SHARED` lock on the database file and its `DMS` read lock on the `-shm` until it closes; readers do not block writers, but an open read transaction pins a read mark, so checkpoints cannot reset the WAL past it (the WAL grows).
- **The schema is SQL compiled by SQLite.** It is read lazily, by the first statement or pragma that needs it: `PRAGMA cache_size`, `journal_mode` and `table_xinfo` carry `PragFlg_NeedSchema`; `query_only`, `cell_size_check`, `trusted_schema`, `automatic_index`, `temp_store`, `encoding` and `schema_version` do not. Schema parsing runs inside `sqlite3_prepare`, outside the progress handler. The authorizer is not called while the schema is read (`sqlite3AuthCheck` returns early when `db->init.busy`). **`PRAGMA table_list` prepares `SELECT * FROM "<name>"` for every view and virtual table whose column count is not known yet** (so it compiles views and connects virtual-table modules); `PRAGMA table_info` / `table_xinfo` on a view, and a `SELECT` naming a view, compute the view's column names (`sqlite3ViewGetColumnNames`, which compiles the view's `SELECT` with the authorizer switched off) **before** the `SQLITE_DBCONFIG_ENABLE_VIEW` check refuses its use ("access to view … prohibited", `selectExpander`).
- **Modules compiled in** with the flags of decision 1: the eponymous `json_each`, `json_tree`, `jsonb_each`, `jsonb_tree` (JSON is part of the core unless `SQLITE_OMIT_JSON`) and the `pragma_*` table-valued functions (`sqlite3PragmaVtabRegister`). `sqlite_dbpage` (`SQLITE_ENABLE_DBPAGE_VTAB`), `carray` (`SQLITE_ENABLE_CARRAY`) and `bytecode` / `tables_used` (`SQLITE_ENABLE_BYTECODE_VTAB`) are compiled only under flags the build does not set.
- **Limits** (`SQLITE_LIMIT_*`): `LENGTH`, `SQL_LENGTH`, `COLUMN`, `EXPR_DEPTH`, `COMPOUND_SELECT`, `VDBE_OP`, `FUNCTION_ARG`, `ATTACHED`, `LIKE_PATTERN_LENGTH`, `VARIABLE_NUMBER`, `TRIGGER_DEPTH`, `WORKER_THREADS`, and `PARSER_DEPTH` (new in 3.53). Several apply when the schema is read: `LENGTH` (to the `sqlite_schema.sql` values) and `SQL_LENGTH` (to each schema statement), and those the parser enforces ("too many terms in compound SELECT" is raised in the grammar actions). `OP_Column` refuses a value longer than `SQLITE_LIMIT_LENGTH` with `SQLITE_TOOBIG`; `typeof()`, `length()` and `octet_length()` have column flags that avoid loading the value. `BTCURSOR_MAX_DEPTH` is 20.
- **Memory.** `sqlite3_hard_heap_limit64` and the `hard_heap_limit` / `soft_heap_limit` pragmas apply to "all database connections within a single process". The default page cache is 2 000 KiB (`SQLITE_DEFAULT_CACHE_SIZE -2000`); memory-mapped I/O is off unless `mmap_size` is raised (`SQLITE_DEFAULT_MMAP_SIZE` 0, `SQLITE_MAX_MMAP_SIZE` 0x7fff0000 on Linux).
- **`sqlite3_db_config` options** in 3.53.2 include `DEFENSIVE` (no `writable_schema`, no `journal_mode=OFF`, no `schema_version=N`, no writes to `sqlite_dbpage` or shadow tables), `TRUSTED_SCHEMA` (off: no function in triggers, views, `CHECK`, `DEFAULT`, expression or partial indexes or generated columns unless it is innocuous, and no virtual table in triggers or views unless innocuous), `ENABLE_TRIGGER`, `ENABLE_VIEW`, `ENABLE_ATTACH_CREATE` and `ENABLE_ATTACH_WRITE` (3.49), `NO_CKPT_ON_CLOSE`, `REVERSE_SCANORDER` (the same as `PRAGMA reverse_unordered_selects`), `DQS_DML` / `DQS_DDL`. Compile-time defaults exist for `SQLITE_TRUSTED_SCHEMA=0` and `SQLITE_DEFAULT_DEFENSIVE`.
- **`PRAGMA compile_options`** prints, among others, `OMIT_LOAD_EXTENSION`, `DEFAULT_CACHE_SIZE=<n>`, `MAX_MMAP_SIZE=<n>`, `TEMP_STORE=<n>`, `THREADSAFE=<n>` and the `ENABLE_*` options; it does **not** print `TRUSTED_SCHEMA`, `MAX_ALLOCATION_SIZE` or `DEFAULT_DEFENSIVE`. `-USQLITE_ENABLE_LOAD_EXTENSION` only changes a connection's default flags; `SQLITE_OMIT_LOAD_EXTENSION` removes extension loading.
- **The file header**: `"SQLite format 3\0"`; byte 18 (write version) and 19 (read version) are 1 for rollback and 2 for WAL, a read version above 2 is refused (`SQLITE_NOTADB`) and a write version above 2 makes the file read-only; the payload fractions at bytes 21 to 23 must be 64, 32, 32; the schema format number has a maximum of 4 (`SQLITE_MAX_FILE_FORMAT`).
- **`libsqlite3-sys` 0.38.2's bundled build** (`build.rs`) compiles `sqlite3.c` with `cc` and `links = "sqlite3"`, with `SQLITE_CORE`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`, `SQLITE_ENABLE_API_ARMOR`, `SQLITE_ENABLE_COLUMN_METADATA`, `SQLITE_ENABLE_DBSTAT_VTAB`, `SQLITE_ENABLE_FTS3` (and `_PARENTHESIS`), `SQLITE_ENABLE_FTS5`, `SQLITE_ENABLE_JSON1`, **`SQLITE_ENABLE_LOAD_EXTENSION=1`**, `SQLITE_ENABLE_MEMORY_MANAGEMENT`, `SQLITE_ENABLE_RTREE`, `SQLITE_ENABLE_STAT4`, `SQLITE_SOUNDEX`, `SQLITE_THREADSAFE=1`, `SQLITE_USE_URI`; the environment variable `LIBSQLITE3_FLAGS` adds `-D…` / `-U…` flags after these. The amalgamation uses no `__DATE__` / `__TIME__`.
- **`rusqlite` 0.40.2's safe API** has what the reader needs: `Connection::open_with_flags` (with `OpenFlags::SQLITE_OPEN_NOFOLLOW`, `SQLITE_OPEN_EXRESCODE`), `set_db_config` (`DbConfig` lists every option above except `ENABLE_LOAD_EXTENSION`), `set_limit` (feature `limits`), `progress_handler` and `authorizer` (feature `hooks`), `busy_timeout`, `get_interrupt_handle`, `Connection::path()`. Extension loading needs the `load_extension` feature; installing a log callback (`trace::config_log`) is an `unsafe fn`.

## Decision
1. **SQLite is read through the bundled SQLite C library, with `rusqlite`, as a reviewed exception to "no C client library", scoped to one crate** (ADR-0039 decision 4), and run only in the reader process of decision 4.
   - **Options weighed.**
     - *Bundled SQLite through `rusqlite` (`bundled`)*: the reference implementation of the file format, its lock protocol and its WAL index, so reads of a live file are as correct as the applications' own; mature and heavily fuzzed upstream; a public-domain C library compiled into the agent's binary, with `unsafe` inside two dependencies.
     - *The system `libsqlite3` (dynamic link)*: security updates come with the distribution, but the version differs per host (Debian 12 ships 3.40, older than the 3.42 / 3.43 / 3.49 features this ADR uses), the build stops being reproducible across hosts, compile options are the distribution's (load extensions, modules), and the `.deb` gains a dependency. Rejected.
     - *An own pure-Rust reader*: no C, panic-free and bounded like the project's own clients, but it must reimplement what makes reads of a **live** file correct: SQLite's POSIX lock protocol, the WAL index format with its read marks and recovery cases, the hot-journal rule, overflow chains, `WITHOUT ROWID` b-trees, and a parser for `CREATE TABLE` text (column names exist only in the schema SQL). A reader that gets the lock protocol wrong reads torn pages of a file being written. Rejected for phase 10; kept as a fallback (open question 2).
     - *`turso_core`* (pre-1.0, its own engine, multi-process access to a file written by SQLite to verify) and *`sqlite-core`* (a small forensics reader without locking or WAL): not mature enough for live files. Rejected.
   - **Recommendation: the bundled C library**, because correctness on live WAL files and maturity against hostile files weigh more than the absence of C, and because SQLite documents the use of untrusted database files as a supported case with the defenses decision 5 applies (to verify against sqlite.org's `security.html`). Its cost, C code parsing attacker-controlled input, is contained by the reader process (decision 4), the defensive settings, limits, authorizer and closed statement list (decision 5), fuzzing (decision 5) and the OS (decisions 2 and 3).
   - **Crates.** `connector-sqlite` (new crate `agent/crates/connector-sqlite`, Cargo feature `sqlite`) depends on `rusqlite` **0.40.x** with `default-features = false, features = ["bundled", "hooks", "limits"]`, nothing else (no `load_extension`, `loadable_extension`, `functions`, `vtab`, `serialize`, `backup`, `blob`, `trace`, `session`, `preupdate_hook`, `sqlcipher`, `bundled-sqlcipher*`, `buildtime_bindgen`, `column_decltype`, `column_metadata`, `modern-full`, `bundled-full`, `with-asan` outside the fuzz workspace, or the `chrono` / `serde_json` / `url` / `uuid` / `time` / `jiff` integrations). Only `connector-sqlite` depends on `rusqlite`; nothing depends on `libsqlite3-sys` but `rusqlite`. The sandbox of decision 4 adds `landlock` and a seccomp filter builder (`seccompiler`, or an equivalent pure-Rust crate; licenses and MSRV checked in the implementation PR), both also scoped to `connector-sqlite`. `rusqlite` 0.41.0 declares `rust-version` 1.89, above the workspace MSRV 1.88; moving to it is a separate decision (open question 5).
   - **Compile options.** `agent/.cargo/config.toml` (new) sets, under `[env]`, with `force = true` (so an inherited `LIBSQLITE3_FLAGS` cannot override it):

     ```toml
     [env]
     LIBSQLITE3_FLAGS = { value = "-DSQLITE_OMIT_LOAD_EXTENSION -USQLITE_ENABLE_LOAD_EXTENSION -DSQLITE_DEFAULT_DEFENSIVE -DSQLITE_TRUSTED_SCHEMA=0 -DSQLITE_MAX_MMAP_SIZE=0 -DSQLITE_MAX_ALLOCATION_SIZE=33554432 -DSQLITE_DEFAULT_CACHE_SIZE=-2048 -DSQLITE_TEMP_STORE=3 -USQLITE_ENABLE_FTS3 -USQLITE_ENABLE_FTS3_PARENTHESIS -USQLITE_ENABLE_FTS5 -USQLITE_ENABLE_RTREE -USQLITE_ENABLE_DBSTAT_VTAB -USQLITE_ENABLE_STAT4 -USQLITE_ENABLE_COLUMN_METADATA -USQLITE_SOUNDEX", force = true }
     ```

     That is: extension loading compiled out, connections defensive and schemas untrusted by default, no memory-mapped I/O, no single allocation above 32 MiB, a 2 MiB page cache and temporary storage in memory only, both at compile time (so no pragma that parses the schema runs before the binding of decision 2), and no virtual-table module or optional feature the reader never uses (a schema that declares an FTS or R-tree table still parses; such tables are never read, decision 5).
   - **Self-check at the start of every reader process** (decision 4), before any target is opened, on a fresh in-memory connection; a failure disables the connector (fail closed): its targets report `unsupported` with `check.stage_failed` (`stage_session_setup`) and the agent logs it once.
     - `sqlite_version()` and `sqlite_source_id()` equal the `SQLITE_VERSION` and `SQLITE_SOURCE_ID` compiled into `libsqlite3-sys` (this also detects a system library linked by mistake).
     - `PRAGMA compile_options` **contains** `OMIT_LOAD_EXTENSION`, `MAX_MMAP_SIZE=0`, `THREADSAFE=1`, `DEFAULT_CACHE_SIZE=-2048`, `TEMP_STORE=3`, and contains none of `ENABLE_LOAD_EXTENSION`, `ENABLE_FTS3`, `ENABLE_FTS5`, `ENABLE_RTREE`, `ENABLE_DBSTAT_VTAB`, `ENABLE_DBPAGE_VTAB`, `ENABLE_BYTECODE_VTAB`, `ENABLE_CARRAY` (positive checks first, since an option the pragma does not print cannot be checked by absence).
     - The options `compile_options` does not print are checked by behaviour: `PRAGMA trusted_schema` reads 0 and `SQLITE_DBCONFIG_DEFENSIVE` reads on, on the fresh connection before the reader sets either; `MAX_ALLOCATION_SIZE` by a unit test in CI (on a connection with `SQLITE_LIMIT_LENGTH` raised, `zeroblob(33554433)` fails with `SQLITE_NOMEM`, `zeroblob(33554432 - 1024)` does not).
     - A **negative-control test** runs the same check against a deliberately wrong expectation and against a connection where `trusted_schema` was set to 1, and asserts that it fails, so the check cannot silently pass everything.
     That every build path (the agent `Dockerfile`, `release.yml`, `publish.yml`, the fuzz workflow, the engine matrix) runs `cargo` under `agent/` is checked when the crate lands; the self-check catches one that does not.

     (and the same line for the seccomp crate chosen), and, under `[bans] features`, an allow-list for both SQLite crates (cargo-deny's `allow` key of a `features` entry: only these features may be enabled; the exact keys are checked against the cargo-deny version CI uses):


     The licenses are already allowed (MIT); the SQLite public-domain dedication is listed with the agent's third-party notices. Advisories against `libsqlite3-sys` (RustSec tracks some bundled-SQLite CVEs, to verify which) are covered by the existing advisories job.
   - **`agent/crates/agent/tests/architecture.rs`** gains:
     - `connector-sqlite` in `CONNECTORS` (no HTTP client, no protocol types, no uplink reference);

2. **Targets are declared files; the path never leaves the agent; every file is checked and every descriptor bound** (I5, I3, I4; ADR-0039 decisions 5 and 7; the CAS rules of [ADR-0041](0041-cas-connector.md) decision 3 and [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md)).
   - **Declaration.** One target is one database file:

     ```yaml
     targets:
       - id: crm-app            # what the console sees (TargetId)
         engine: sqlite
         sqlite:
           path: /srv/crm/data/crm.db
           max_statement_ms: 500   # optional, 50..5000 (decision 3)
           rollback_mode: skip     # optional: skip (default) or read (decision 3)
     ```

     No `host`, `port`, `socket`, `account` or `secret`: the configuration refuses them for `engine: sqlite`, as for `cas`. **No directory, no glob, no search**: a directory of files would make the agent read files that appear later and that nobody declared one by one, which is what I5 forbids; several files are several targets. The agent never looks for SQLite files (no local detection, ADR-0006: there is no process or port to detect, and scanning the file system is the rejected alternative of ADR-0039).
   - **The path never leaves the agent.** The target is identified to the console by its `id` only (`TargetStatus.target_id`, the `TargetId` slug, which cannot hold a path). The path, the file name and the side-file names are never sent, never written to the agent's logs (which may be shipped off the host), and never kept in an error. A refusal of a path rule, at load or later, names the target id and the rule broken (`symlink_component`, `not_regular_file`, `hard_link`, `refused_location`, …), never the path. `Location.database` is a constant (decision 6), never the file name.
   - **Path rules, checked when `agent.yaml` is loaded and at every open.**
     - Absolute, already canonical (no `.` or `..` component, no `//`, no trailing `/`), valid UTF-8, at most 1 024 bytes, no control character.
     - **No symlink in any component.** This is stricter than ADR-0039 decision 5 ("symlinks are resolved when the configuration is loaded") and than ADR-0043 (which follows parent symlinks): SQLite derives the side-file names from the path and resolves symlinks itself component by component, and `SQLITE_OPEN_NOFOLLOW` refuses a symlink in any component (Context). One rule for both sides is simpler to review: the operator declares the real path.
     - **Refused locations**: the agent's state, identity and spool directories; `/etc/databastion`; every file `agent.yaml` references (secret files, client keys and certificates, CA files) and the directories that hold them; `/proc`, `/sys`, `/dev`, `/run/user`.
     - Two targets may not name the same file: the loader and every open compare the files' `(st_dev, st_ino)`; a duplicate refuses both.
   - **Open procedure**, run by the reader process (decision 4) in this order; any failure refuses the file, with the code and note of decision 7:
     1. Every ancestor directory is `lstat`ed from `/` down: a directory, not a symlink, not writable by the reader's account (owner = its uid, a group-write bit for one of its groups, the other-write bit, or `faccessat(W_OK, AT_EACCESS)` true, which covers POSIX ACLs), and **not writable by every local user unless it has the sticky bit**.
     2. The **check descriptor**: `open(path, O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_NOCTTY | O_CLOEXEC)` (`rustix`, no `unsafe`), then on that descriptor:
        - `fstat`: a regular file; `st_nlink` = 1 (a hard link could make the reader open another file, ADR-0043 decision 4); not writable by the reader's account (the step 1 rules); a size of at least 512 bytes (a 0-byte file is refused: SQLite would treat it as an empty database and delete a `-wal`, Context);
        - `fstatfs`: a **network or FUSE file system is refused** (decision 3): `f_type` in the closed list NFS (`0x6969`), SMB (`0x517B`), CIFS (`0xFF534D42`), SMB2 (`0xFE534D42`), FUSE (`0x65735546`), 9P (`0x01021997`), Ceph (`0x00C36400`), AFS (`0x5346414F`), Coda (`0x73757245`), and the values for Lustre and GPFS, checked against the kernel's `magic.h` at implementation;
        - `fstatvfs`: **`f_flag & ST_RDONLY` must be set**: the file system holding the database is mounted read-only in the agent's view (decision 3). Otherwise the file is refused with `coverage.filesystem_not_read_only`.
     3. **Header pre-check in Rust**, on the first 100 bytes read through the check descriptor (`pread`): the magic `"SQLite format 3\0"`; a page size that is a power of two from 512 to 65 536 (the value 1 meaning 65 536); write and read versions 1 or 2; the payload fractions 64, 32, 32; a schema format number from 1 to 4; a text encoding 1, 2 or 3; a page count in the header consistent with the file size when the header says it is valid. Anything else is refused as `coverage.unrecognized_file_format` (decision 7). This is a **filter, not a proof**: an encrypted, compressed or misplaced file, or a secret file, does not reach the C library through this path; a file that passes is parsed by SQLite, in the sandboxed reader only.
     4. **Side files** `<path>-wal`, `<path>-shm`, `<path>-journal` are `lstat`ed and their `(st_dev, st_ino)` recorded: each one present must be a regular file with `st_nlink` = 1, not a symlink, not writable by the reader's account, owned by the database file's owner or belonging to its group (the application), and on the **same file system** as the database (`st_dev` equal, so step 2's read-only mount covers it). Otherwise the file is refused (`privilege.database_file_writable` when writable, `coverage.file_path_refused` otherwise).
     5. SQLite opens the file (`sqlite3_open_v2`, decision 3's flags and URI), which opens the main database file and nothing else yet.
     6. **Binding the main file, right after the open and before any pragma or statement** (`PRAGMA cache_size`, `journal_mode` and `table_xinfo` parse the schema, Context): the reader lists `/proc/self/fd` and counts the descriptors whose target (`std::fs::metadata` through the magic link) has the checked `(st_dev, st_ino)`: it must be **exactly 2** (the check descriptor and SQLite's). With only the check descriptor, SQLite opened another file: the connection is closed and the file refused. `Connection::path()` must also equal the declared path. A fixture with an unparseable schema proves that it fails only after this binding.
     7. The connection setup of decision 5, then the first statement.
     8. **Binding every descriptor, after the first statement and before each later unit of work**: every entry of `/proc/self/fd` must be the IPC socket (decision 4), the check descriptor, SQLite's main descriptor, or a descriptor whose target has the recorded `(st_dev, st_ino)` of a side file checked in step 4 (a side file that appeared since step 4 is `lstat`ed and checked like step 4 first); and every descriptor on the database or a side file must have an access mode of `O_RDONLY` in `/proc/self/fdinfo/<n>` (`flags`). Anything else (an unknown descriptor, a side file that is not the checked one, an `O_RDWR` or `O_WRONLY` descriptor) closes the connection and refuses the file. The count is reliable because nothing else in the reader opens a file (decision 4).
   - **Descriptor lifetime and the per-target lock** (POSIX locks). In the reader, the check descriptor stays open for the whole life of the SQLite connection and is closed only **after** it; the reader's code opens no other descriptor on the database or its side files. In the agent, all access to one target goes through one **per-target lock**, held for the whole life of the target's reader process. **Rule: no code path, in the agent or in the reader, opens a descriptor on a target's database or side files outside that target's lock.** Path-based checks (`lstat`, `faccessat`) open no descriptor and are allowed at any time. Locks are per process, so the agent's descriptors could not drop the reader's SQLite locks in any case; the rule also keeps the descriptor count of step 8 exact and the checks consistent.
   - **Recommended permissions** (for [05-security.md](../05-security.md#recommended-database-accounts-read-only) and the user guide): the database owned by the application, mode `0640`, group `databastion` (or a group the agent's account is a supplementary member of, `SupplementaryGroups=` in a systemd drop-in); its directory `0750` or `2750` with the same group and the **setgid bit**, so that the `-wal`, `-shm` and `-journal` files the application creates (with the database's permission bits, Context) belong to that group and stay readable by the agent; or a POSIX default ACL granting the agent's group read access on the directory. The agent needs search (`x`) permission on every ancestor directory and read permission on the files; never write. **The database's file system must be mounted read-only for the agent** (step 2): under the systemd unit, `ProtectSystem=strict` does it for every path outside `/var/lib/databastion`; a file under `/home` needs `BindReadOnlyPaths=<directory>` in a drop-in (preferred over `ProtectHome=read-only`, which exposes every home directory); in the container image, bind-mount the directory with `:ro`; a manual run needs a read-only bind mount of the directory.
   - **The parent-directory rule differs from ADR-0039 decision 5**, which refuses "a path whose parent directory is writable by another non-root user". A SQLite application must create and delete its journal files in that directory, so the rule would refuse almost every live database. The rule here: the directory and its ancestors may be writable by their owner and group (the application), never by the agent, and never by every local user without the sticky bit. Whoever can write the directory can replace the file between two opens; steps 2 to 8 bind each open to a checked regular file, and the residual is that the application's own account can present another SQLite file that the reader can read.

3. **Read-only access that never writes, creates or deletes a file, WAL databases, rollback-mode files, locking and file systems** (I4).
   - **The guarantee comes from the operating system, in layers**, because SQLite's read-only flag alone does not keep it from creating or opening side files read-write (Context):
     1. the reader's account cannot write the file, its side files or any ancestor directory (decision 2, checked at every open; a file that fails is refused, never opened "read-only anyway");
     2. the database's file system is **read-only in the agent's mount namespace**, checked with `fstatvfs` on the check descriptor (decision 2, step 2). This check is required because `ProtectSystem=strict`, which gives it under the systemd unit, is absent from the distroless container image and from manual runs; there the operator provides a read-only mount (`:ro`, `BindReadOnlyPaths=`);
     3. the reader's Landlock ruleset grants read access only, and its seccomp filter refuses `open` / `openat` / `openat2` with `O_WRONLY`, `O_RDWR`, `O_CREAT` or `O_TRUNC`, `unlink*`, `rename*`, `truncate` / `ftruncate`, `fallocate` and `chmod` / `chown` (with `EPERM`, so SQLite falls back to read-only); `RLIMIT_FSIZE` is 0 (decision 4);
     4. SQLite itself is opened read-only: `SQLITE_OPEN_READONLY | SQLITE_OPEN_URI | SQLITE_OPEN_NOFOLLOW | SQLITE_OPEN_EXRESCODE | SQLITE_OPEN_NO_MUTEX | SQLITE_OPEN_PRIVATE_CACHE` with the URI `file:<path>?mode=ro&readonly_shm=1`, where every byte of the path outside the RFC 3986 unreserved set and `/` is percent-encoded (so `?`, `#`, `&`, `=` and `%` cannot reach SQLite's URI parser), with `PRAGMA query_only=ON`, `SQLITE_DBCONFIG_DEFENSIVE`, `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` and the authorizer of decision 5;
     5. at run time, every descriptor on the database or a side file is checked to be `O_RDONLY` (decision 2, step 8).
     With these, every `O_RDWR | O_CREAT` attempt of the unix VFS fails and it falls back to `O_RDONLY`, and the `-wal` deletion of an empty database cannot happen (the 0-byte file is also refused). The integration tests prove it: the directory and side files are byte-for-byte and `mtime`-unchanged after a scan, on rollback and WAL databases, with and without a concurrent writer.
   - **`immutable=1` is rejected.** It disables locking and change detection: on a file an application is writing it gives wrong results or `SQLITE_CORRUPT`, and it ignores the `-wal`, so the most recent commits (often the most recent personal data) are invisible. It is also not needed for static files: a file no one writes reads correctly with the normal locks.
   - **Writing the `-shm` is rejected.** It breaks I4 (the agent would write a file that belongs to the application), and a reader with a writable `-shm` may run WAL-index recovery, which writes to the memory the application's connections share.
   - **`readonly_shm=1` is adopted**, with the outcomes below. Because `readonly_shm` is not in SQLite's documented URI list (Context), layers 1 to 3 remain the guarantee and the integration tests pin the behaviour at every library update.

     | Journal mode (header byte 19) | Side files present | Outcome |
     |---|---|---|
     | rollback (1) | none, or a `-journal` that is not hot | with `sqlite.rollback_mode: read`, read under `SHARED` locks; by default (`skip`) not read, note `coverage.rollback_mode_not_read` |
     | rollback (1) | a hot `-journal` | `SQLITE_READONLY_ROLLBACK`: not read, note `coverage.hot_journal_pending`, retried at the next check (the application recovers it at its next open) |
     | WAL (2) | `-wal` and `-shm`, a writer connected | read through the read-only `-shm` |
     | WAL (2) | `-wal` and `-shm`, no writer connected | read through SQLite's private heap index built from the `-wal`; a `-wal` larger than **128 MiB** is not read (that build reads the whole file and its time is bounded only by the reader's kill deadline), note `coverage.wal_files_not_readable` |
     | WAL (2) | neither (the application closed cleanly) | cannot be opened read-only without creating the `-wal` (Context): not read, note `coverage.wal_files_not_readable`, retried at the next check; the user guide explains that the file is read while the application holds it open (open question 4) |
     | WAL (2) | only one of them, or one unreadable | not read, note `coverage.wal_files_not_readable` |
     | any | a `-wal` next to a rollback-mode header | SQLite opens it in WAL mode (`pagerOpenWalIfPresent`): the WAL rows above apply |

     The `-wal` size is checked with `lstat` at every open and again **before every unit of work**; past 128 MiB the unit is not run and the rest of the scan is counted `skipped_limit`.
   - **Rollback-mode files are a local opt-in** (`sqlite.rollback_mode: read`; default `skip`): in rollback mode every read delays the application's commits, and an application without a busy timeout gets `SQLITE_BUSY`. A skipped file is reachable, the scan succeeds with the database counted **1** in `skipped_unsupported` (as ADR-0035 decision 3 counts a database left out), and the note `coverage.rollback_mode_not_read` says why. The default is revisited after the load run measures the impact (open question 8).
   - **Locking so writers are not held up.**
     - **Autocommit statements only**: the reader never issues `BEGIN`; each statement is its own read transaction, so a read mark (WAL) or a `SHARED` lock (rollback) taken **for reading** is held only while one statement runs. In WAL mode the connection also keeps, for as long as it is open, its `SHARED` lock on the database file and its `DMS` read lock on the `-shm` (Context); they do not block the application's writers, but they stop the last application connection from deleting the WAL at close, and the connection stays open across pauses of up to 30 s (below). A statement is stepped to completion (or reset) before the next one; no statement is left open across a pause or across `FindingSink::submit().await` ([05-security.md](../05-security.md#connector-obligations)).
     - **Statement deadline** `sqlite.max_statement_ms` (default 500 ms, range 50 to 5 000, a local limit the console cannot raise), and never more than the job's clamped statement timeout. In the reader, the progress handler (every 1 000 virtual-machine instructions) checks the deadline and interrupts the statement; in the agent, the IPC request carries a deadline of `max_statement_ms` plus 2 s, past which the agent **kills the reader with `SIGKILL`** (decision 4). This also bounds what the progress handler cannot: schema parsing inside `prepare`, the WAL heap-index build, a read stuck in the kernel. In rollback mode the deadline bounds how long one statement can delay a writer's commit; with the default 1 % duty cycle ([ADR-0035](0035-discovery-pacing.md)), the reader holds a read lock at most about 1 % of a scan's time.
     - **Busy timeout 100 ms**: when a writer holds `PENDING` or `EXCLUSIVE` (or WAL recovery runs), the reader waits at most 100 ms and gives way. A unit that gets `SQLITE_BUSY` is retried once at its next paced turn, then counted `skipped_error`; a `check()` that gets it reports the last known state with `check.timed_out`.
     - **One reader process and one connection per scan**, opened with decision 2's procedure, closed (the process exits) before any pause longer than 30 s and started again afterwards with the full procedure. A file whose `(st_dev, st_ino)` changed since the scan started ends the scan for that target: the remaining objects are counted `skipped_error`. `check()` uses its own short-lived reader (decision 7).
   - **Network file systems are refused** (decision 2, step 2), with no opt-in in this ADR (open question 6): POSIX locks are unreliable on many of them, so readers can see torn pages; the WAL index (`-shm` in shared memory) only works when every process is on one host; and a scan would turn into network I/O towards a file server the agent was never told about.

4. **The SQLite library runs only in a sandboxed reader process, from the first implementation.** This is the first line of defense against hostile files (decision 5 lists the others).
   - **Why** (security review H1).
     - The agent's process holds the console secret, the HMAC key and every other target's credentials (I3), and SQLite would parse attacker-controlled bytes there: schema SQL, b-trees, WAL recovery.
     - The `-shm` is mapped `MAP_SHARED`, and the application's account can change it while SQLite reads it: a double fetch that fuzzing cannot reach.
     - A `ftruncate` of the `-shm` raises `SIGBUS` in the reading process. In the agent, it would kill the whole agent, and after 5 restarts in 10 minutes systemd leaves it stopped, so every other target would lose its Discovery and its Audit.
     - Schema parsing runs in `prepare`, outside the progress handler, so a hang there would hold a blocking thread and the target's lock for good.
     - `hard_heap_limit` is process-wide.
   - **The reader.**
     1. **A fresh `execve` of the agent's own binary** (`/proc/self/exe`, through `tokio::process::Command`, kill on drop) in a reader mode (`databastion-agent sqlite-reader`, handled first in `main`, before any configuration, state or identity file is read), with the **environment cleared** (`env_clear`) and no argument but the mode. No secret is passed: the path and the limits arrive over the IPC channel. The agent's address space is not inherited (`execve`), so the reader holds no secret.
     2. Standard input is one end of a `UnixStream::pair()` (the IPC channel); standard output and standard error are `/dev/null`; no other descriptor is inherited (`O_CLOEXEC` everywhere). The reader never logs: it reports closed codes over IPC, and the agent logs them under the target id.
     3. First thing in reader mode: `PR_SET_NO_NEW_PRIVS` and `PR_SET_DUMPABLE` = 0 (`rustix`); resource limits `RLIMIT_AS` (512 MiB), `RLIMIT_CPU` (60 s of CPU per process, above any scan's paced CPU), `RLIMIT_NOFILE` (16), `RLIMIT_FSIZE` (0), `RLIMIT_CORE` (0). Process and thread creation is refused by the seccomp filter below rather than by `RLIMIT_NPROC`, which counts every process of the account.
     4. It reads the **open request** (the declared path and the limits), then applies a **Landlock** ruleset that grants **read access only** (`READ_FILE`, `READ_DIR`) **to the declared file's directory**, and read access to its own `/proc/<pid>/fd` and `/proc/<pid>/fdinfo` (for decision 2's binding); everything else, `/var/lib/databastion` and `/etc/databastion` included, is out of reach, and no write right is granted anywhere. Landlock does not cover `stat`-family calls, which decision 2's ancestor checks need.
     5. A **seccomp** filter: `socket`, `socketpair`, `connect`, `bind`, `listen`, `accept*`, `execve`, `execveat`, `fork`, `vfork`, `clone` / `clone3` (the reader is single-threaded), `ptrace`, `process_vm_*`, `mount`, `setns`, `unshare`, `io_uring_*`, and the writing calls of decision 3 layer 3, refused with `EPERM`. On kernels with Landlock ABI 4 or later, Landlock's network rules (no TCP bind or connect) are added as well.
     6. The self-check of decision 1, then decision 2's open procedure and decision 5's connection setup.
     7. **Without Landlock** (an older kernel, or the Landlock LSM not enabled at boot), or when the ruleset cannot be fully enforced, the reader refuses to open anything: the target reports `unsupported` with the note `coverage.reader_sandbox_unavailable`. There is no fallback to an unsandboxed reader by default (open question 3 is the alternative).
   - **The IPC protocol.** Length-prefixed frames (a 4-byte big-endian length) over the socket pair, at most 64 KiB per request and 1 MiB per response, decoded by the crate's own bounded decoder (no `serde` format), with a closed set of messages: requests `open`, `catalog`, `columns`, `sample`, `light_check`, `close`; responses carrying closed codes, counts, raw names (at most 1 024 bytes each) and raw values (at most 4 096 bytes each, at most `sample_rows × 64` per response). A frame over its bound, an unknown message or a malformed field ends the reader (`SIGKILL`) and counts the unit `skipped_error`. Both sides' decoders get property tests (round trips, every split of a stream, arbitrary bytes never panic and never allocate past the bounds) and a fuzz target (`sqlite_ipc`). **Raw values and raw names go to the agent**, which normalizes the names and classifies and masks the values (`ScanJob::classify`, `classifiers::masking`): they stay on the agent host, in zeroized buffers on both sides, so I2 holds; the reader zeroizes its buffers after each response.
   - **Lifecycle and failures.** The agent holds the target's lock for the reader's whole life (decision 2). Every request carries the deadline of decision 3; past it, or when the scan is cancelled, the agent sends `SIGKILL` and reaps the process. A reader that dies (by `SIGBUS`, `SIGSEGV`, `SIGKILL`, an `RLIMIT` signal or an exit) costs **one unit of work**: it is counted `skipped_error`, the next unit starts a new reader; after 3 deaths in one scan the scan stops for that target (the rest counted `skipped_error`) and the note `coverage.reader_process_failed` (count) is raised; the heartbeat metric `sqlite_reader_failures_total` counts them. The agent process is never affected, and the heap limit and `SIGBUS` are per reader.
   - **Consequences for ADR-0039 and the unit.**
     - This is an exception to ADR-0039 decision 4's "spawns no process", limited to the agent's own binary in reader mode: no external tool, no shell, no argument but the mode. An architecture test checks that the only `Command::new` in the workspace is this one, on `/proc/self/exe`.
     - The systemd unit must allow what the reader needs: whether `SystemCallFilter=@system-service` (with `~@privileged`) allows `landlock_create_ruleset`, `landlock_add_rule`, `landlock_restrict_self`, `seccomp`, `prctl` and `execve` is **to verify** on the supported systemd versions, and the unit gains them explicitly if not; `RestrictAddressFamilies` already allows `AF_UNIX` for the socket pair; `MemoryDenyWriteExecute=yes` and `NoNewPrivileges=yes` are compatible. The installation tests (Ubuntu 24.04, Debian 12) run a SQLite target, so a host where Landlock is not enabled is seen; whether Debian 12's default kernel enables the Landlock LSM is to verify. In the container image, Docker's default seccomp profile must allow the Landlock calls (to verify).
     - Spawning one process per scan and per full check costs a few milliseconds; it is paced like any unit.

5. **Hardening against hostile files**, inside the reader.
   - **Threat model.** The file is application data; whoever controls the application, or can make it store a crafted file (an upload, a synced file, a compromised application account), controls every byte of it, its schema SQL included, and can change it, its `-wal` and its `-shm` while the reader reads them. Their goals: code execution or memory disclosure (in the reader, which holds no secret and cannot reach the network or other files, decision 4); making the reader run code from the file (SQL functions, triggers, views, virtual-table modules, extensions); making the agent write (I4); exhausting memory, CPU or time, or blocking the application; hiding data from Discovery (accepted: whoever writes the file controls what it holds).
   - **Connection setup**, in this order, right after decision 2's step 6 binding and before the first statement:
     1. **Limits** (`set_limit`): `ATTACHED` 0 (no `ATTACH`, whatever else fails), `VARIABLE_NUMBER` 8, `LIKE_PATTERN_LENGTH` 50, `TRIGGER_DEPTH` 1, `WORKER_THREADS` 0, `VDBE_OP` 250 000, `LENGTH` 1 048 576 and `SQL_LENGTH` 1 000 000. **`LENGTH` and `SQL_LENGTH` also apply when the schema is read** (security review L3): a `sqlite_schema.sql` value above 1 MiB, or a schema statement above 1 MB, makes the schema fail to load, and the file is refused with `coverage.unrecognized_file_format`; fixtures for both pin it. Above the schema, `LENGTH` fails a sampled value above 1 MiB with `SQLITE_TOOBIG`, the backstop of the sampling bound. **The other limits the parser applies to the schema** (`COLUMN`, `EXPR_DEPTH`, `COMPOUND_SELECT`, `FUNCTION_ARG`, `PARSER_DEPTH`) **keep their defaults**: lowering them would make a legitimate schema fail to load. This lowers fewer limits than ADR-0039 decision 5 ("lowered `SQLITE_LIMIT_*` values") suggests; the implementation PR records, with a fixture per limit, which ones apply to the schema.
     2. **`sqlite3_db_config`**: `DEFENSIVE` on (also the compile-time default); `TRUSTED_SCHEMA` off (also the compile-time default); `ENABLE_TRIGGER` off; `ENABLE_VIEW` off; `ENABLE_ATTACH_CREATE` off; `ENABLE_ATTACH_WRITE` off; `NO_CKPT_ON_CLOSE` on; `DQS_DML` off (the reader's own statements; `DQS_DDL` keeps its default, to verify that it does not affect reading an old schema); `REVERSE_SCANORDER` per scan (decision 6); `ENABLE_FTS3_TOKENIZER` and `WRITABLE_SCHEMA` off (their defaults, set explicitly).
     3. **Pragmas that do not read the schema** (Context): `query_only = ON`, `cell_size_check = ON` (page-level consistency checks while reading), `automatic_index = OFF` (no transient index, which would scan a whole table), `trusted_schema = OFF`; and `hard_heap_limit = 67108864` (64 MiB), now per reader process. The page cache size, temporary storage in memory and the absence of memory-mapped I/O are compile-time settings (decision 1), so no pragma that loads the schema runs before the binding. An allocation past the heap limit fails with `SQLITE_NOMEM` (`resource_limit`); `RLIMIT_AS` is the backstop.
     4. `busy_timeout(100 ms)`, the progress handler (decision 3), then the **authorizer**, installed last so that the setup pragmas above are the only assignments ever made. It returns **`SQLITE_DENY`, never `SQLITE_IGNORE`** (which would silently read `NULL` instead of failing). Its rules:
        - the database-name argument must be `main` or `NULL`, for every action;
        - `SQLITE_SELECT` is allowed;
        - `SQLITE_READ` is allowed only on the table the current statement template is for: the one table of a sampling or rowid-bounds statement, `sqlite_schema` (under either of its names, `sqlite_master` included) for the catalog template only, `sqlite_stat1` for the statistics template only (the agent sets the current template before each `prepare`);
        - `SQLITE_FUNCTION` only for `typeof`, `octet_length`, `substr`, `min`, `max`, compared ASCII-case-insensitively;
        - `SQLITE_PRAGMA` only for `table_xinfo` with an argument and for `journal_mode`, `schema_version`, `page_size`, `encoding`, `trusted_schema` and `compile_options` **without** an argument, compared ASCII-case-insensitively;
        - everything else is denied (`ATTACH`, `DETACH`, every write, `CREATE` / `DROP` / `ALTER`, `TRANSACTION`, `SAVEPOINT`, `ANALYZE`, `REINDEX`, `RECURSIVE`, any other pragma, any other function).
        A property test drives the authorizer with generated action codes, names in mixed case and database names, and checks that only the listed combinations are allowed. The authorizer is not called while SQLite reads the file's schema or computes a view's columns (Context), so it guards the reader's own statements and whatever a schema object would add to them.
   - **A closed list of statements**, built from constant templates in which only identifiers are inserted, each through one quoting function (`"` + the name with `"` doubled + `"`; a name with a NUL byte, more than 1 024 bytes or invalid UTF-8 is never quoted: its object is counted `skipped_unsupported`); numbers are bound parameters:
     - catalog: `SELECT type, name, rootpage FROM main.sqlite_schema WHERE type IN ('table', 'view')` (the `sql` column is never read);
     - columns: `PRAGMA main.table_xinfo(<name>)`, only for a `table` row with `rootpage` > 0 (an ordinary table; a virtual table has `rootpage` 0), reading `name`, `type`, `pk` and `hidden` only (`dflt_value`, which can hold literals, is not read);
     - statistics: `SELECT tbl, stat FROM main.sqlite_stat1 WHERE idx IS NULL OR idx = tbl` when `sqlite_stat1` exists (decision 6);
     - rowid bounds: `SELECT min(<rowid>), max(<rowid>) FROM main.<t> NOT INDEXED`;
     - sampling: `SELECT <guarded columns> FROM main.<t> NOT INDEXED WHERE <rowid> >= ?1 ORDER BY <rowid> LIMIT ?2`, its wrap-around `… WHERE <rowid> < ?1 ORDER BY <rowid> LIMIT ?2`, and `SELECT <guarded columns> FROM main.<t> NOT INDEXED LIMIT ?1` for `WITHOUT ROWID` tables (decision 6); `NOT INDEXED` keeps the planner on the table's own b-tree, never an index;
     - check: `PRAGMA main.journal_mode`, `PRAGMA main.schema_version`, `PRAGMA main.page_size`, `PRAGMA main.encoding`; at start, `PRAGMA compile_options` and `PRAGMA trusted_schema` on an in-memory connection (decision 1).
     **`PRAGMA table_list` and `pragma_*` table-valued functions are never used**: `table_list` compiles every view and connects every virtual table (Context).
   - **Schema objects.**
     - **Views are not sampled** (`ENABLE_VIEW` off; their base tables are sampled; counted in `coverage.views_not_sampled`). Sampling a view would run its SQL, functions included.
     - **A view whose `sqlite_schema` row claims `type = 'table'` and a non-zero `rootpage`** (a hostile file): `table_xinfo` then computes the view's column names, which compiles its `SELECT` but runs nothing (Context), and the sampling statement fails with "access to view prohibited"; the object ends `skipped_unsupported`. A fixture pins it, with a view selecting from `json_each` and from `pragma_table_info`.
     - **Triggers never fire** (no write; `ENABLE_TRIGGER` off).
     - **Virtual tables are never read, listed through a module or connected.** The modules still compiled in are the eponymous `json_each`, `json_tree`, `jsonb_each`, `jsonb_tree` and the `pragma_*` table-valued functions (Context); FTS, R-tree, `dbstat`, `sqlite_dbpage`, `carray` and `bytecode` are not. A schema naming any module, available or not, parses, and the error would only come at first use, which never happens. Counted in `coverage.virtual_tables_not_sampled`. A hostile fixture per compiled module (a `CREATE VIRTUAL TABLE … USING` row naming it, and a view using it) ends `skipped_unsupported` with nothing executed. **Shadow tables** of a virtual table (`<name>_content`, `<name>_data`… for FTS) are ordinary tables in `sqlite_schema` and are sampled like any table: the text an FTS index holds is in them.
     - **Generated columns**: `VIRTUAL` ones (`hidden` = 2) are not sampled, since reading them evaluates an expression from the file (counted in `coverage.computed_columns_not_sampled`); `STORED` ones (`hidden` = 3) are read like any column (their value is stored).
     - `CHECK` constraints, `DEFAULT` clauses, partial and expression indexes, foreign keys and collations are not evaluated by the reader's statements (no write, no `WHERE` on a user column, no `ORDER BY` on anything but the rowid, no index used).
     - **Internal tables** (`sqlite_%`: `sqlite_sequence`, `sqlite_stat1` to `sqlite_stat4`) are not sampled. `sqlite_stat4` holds copies of indexed key values (residual risk).
   - **No `PRAGMA quick_check` or `integrity_check`** (decided here, as the P10-A task asks): either reads the whole file under one read transaction, which costs time proportional to the file and, in rollback mode, blocks the application's commits for that whole time. Corruption is caught where it is read (`cell_size_check`, SQLite's own checks, `SQLITE_CORRUPT` per statement, decision 7). Open question 7.
   - **No encryption support.** SQLCipher, SEE and the like are detected by the header pre-check (an encrypted file has no plain header) and refused with `coverage.unrecognized_file_format`; a SQLCipher "plaintext header" file passes the pre-check and fails at its first page read with `SQLITE_NOTADB`, reported the same way. Reading them would need their C crypto (OpenSSL or libtomcrypt) and the key on the agent host: rejected.
   - **Errors and text** (security review L1). Every `rusqlite` call is wrapped in one module of the reader, whose functions return the crate's own error type; no `rusqlite::Error` leaves that module. One **exhaustive** `match` maps every `rusqlite::Error` variant (`SqliteFailure`, `InvalidPath`, `InvalidColumnName`, `InvalidColumnIndex`, `InvalidColumnType`, `FromSqlConversionFailure`, `IntegralValueOutOfRange`, `Utf8Error`, `NulError`, `InvalidParameterName`, `ExecuteReturnedResults`, `QueryReturnedNoRows`, `ToSqlConversionFailure`, `InvalidQuery`, `MultipleStatement`, `InvalidParameterCount`, `SqlInputError` and the others of the version used, with a final arm for a `#[non_exhaustive]` future variant mapped to `internal`) to the extended result code or a closed reader code, and keeps nothing else: the message of `SqliteFailure`, the path of `InvalidPath`, the column name of `InvalidColumnName`, the value or text inside `FromSqlConversionFailure` and `SqlInputError` are dropped there. The test `sqlite_errors_are_never_formatted` (decision 1), with `clippy::disallowed_methods` on `ToString::to_string` and a text-level check of the module, bans any `Display` or `Debug` formatting of a `rusqlite::Error` (`{}`, `{:?}`, `tracing` fields, `to_string`). The reader never installs `SQLITE_CONFIG_LOG` (whose messages carry paths), and its standard error is `/dev/null`.
   - **Memory hygiene.** Values are copied out of SQLite into zeroized buffers, sent over IPC and wiped; in the agent they become `RawValue` (zeroized on drop) and are classified through `ScanJob::classify` / `classify_guarded` and `classifiers::masking` (I2). SQLite's own page cache and the memory it frees are not wiped (residual risk); the reader is not dumpable and its `RLIMIT_CORE` is 0.
   - **Fuzzing** (P10-A "Fuzz target with hostile database files"; security review L6).
     - Target **`sqlite_file`**: the input is split (length prefixes) into a main file and optional `-wal`, `-shm` and `-journal` files, written to a private temporary directory (mode `0700`, then made read-only), and run through the reader's real pipeline: the path and file checks, the header pre-check, the connection setup, the catalog, `table_xinfo` and sampling statements, with the production limits and a small statement deadline. A **forked helper** process opens the fuzzed WAL database read-write first and holds the `-shm` DMS lock (on a copy, so that the reader's view is the fuzzed content), so that the reliable-`-shm` path is reached as well as the heap-index path.
     - Target **`sqlite_header`**: the Rust header pre-check alone (no SQLite).
     - Target **`sqlite_ipc`**: both IPC decoders.
     - Property tests: the quoting function, the URI encoder (round trip through `Connection::path()`), the header pre-check against SQLite's own verdict on generated headers, the error mapping (no message survives), the authorizer.
     - Seed corpus: the dev seeded files (decision 9), files written by several SQLite versions, page sizes 512 and 65 536, UTF-16 encodings, `auto_vacuum`, overflow pages, freelists, `WITHOUT ROWID`, `STRICT`, generated columns, FTS shadow tables, hot journals and WAL files.
     - The fuzz targets are built with the **production `LIBSQLITE3_FLAGS`** (the fuzz workspace under `agent/fuzz` reads the same `agent/.cargo/config.toml`; the self-check of decision 1 runs in the targets' setup and fails the run otherwise), plus AddressSanitizer for the C code (`libsqlite3-sys`'s `with-asan` feature, fuzz workspace only) and coverage instrumentation through `CFLAGS` (`-fsanitize=fuzzer-no-link`, to verify with cargo-fuzz), so the fuzzer sees inside SQLite. They join the nightly AddressSanitizer workflow (#179). **The harness never runs as root** (root bypasses the permission checks under test and takes SQLite's `fchown` paths); the workflow runs it as an unprivileged user.
     - A crash found in SQLite is reported upstream and fixed by a library update and an agent release.

6. **Discovery** (bounded, I4; paced by the core, [ADR-0035](0035-discovery-pacing.md)).
   - **One database, `main`.** Other databases are never attached (`ATTACHED` limit 0, authorizer, closed statements).
   - **Catalog**: the `table` and `view` rows of `sqlite_schema` (decision 5), at most 10 000 objects read per scan (beyond, `skipped_limit`), rotated per scan (`ScanJob::rotate`, ADR-0035 decision 4). Each unit of work goes through `job.paced` (decision 3's statement deadline is the upper bound of one unit's lock time) and is one IPC request: the catalog read; then, per table, `table_xinfo` and the sampling statements.
   - **Columns**: every column of an ordinary table (rowid tables, `WITHOUT ROWID`, `STRICT`, FTS shadow tables) except `VIRTUAL` generated columns, at most 64 per sampling statement (a wider table takes several statements, each a paced unit).
   - **Values by storage class**, not by declared type: SQLite types each value, and a column declared `TEXT` may hold integers while one declared without a type may hold anything. `TEXT` values are sampled (SQLite converts UTF-16 databases to UTF-8 on read); `INTEGER` values are sampled as their decimal text (phone and card numbers stored as numbers, as the PostgreSQL connector samples `int8` and `numeric`); `REAL`, `BLOB` and `NULL` values are not (as `bytea` and floats elsewhere; BLOBs holding text are open question 9). Each column is selected as `CASE WHEN typeof(c) IN ('text', 'integer') AND octet_length(c) <= 65536 THEN substr(c, 1, 4096) END`, so a value larger than 64 KiB is never loaded whole into memory by SQLite (`typeof` and `octet_length` read only the record header; to verify by a test with a value above `SQLITE_LIMIT_LENGTH`, which stays the backstop), then cut to 4 096 bytes on a character boundary, as the other connectors do. These are built-in functions on the reader's own connection: the file cannot redefine them (no function is registered on the connection, and none can be defined by a schema), so the PostgreSQL rule of applying no function to a sampled column ([ADR-0012](0012-postgresql-agent-grants.md) obligation 3, which guards against user-defined overloads) does not apply here. A statement that still fails with `SQLITE_TOOBIG` is retried once column by column; the columns that fail again are counted with the table as `skipped_limit`.
   - **Bounds per table**: at most `job.sample_rows()` rows (clamped by `limits.max_sample_rows`), at most 32 MiB of value bytes read per table (the PostgreSQL connector's per-relation budget; the unit stops there and the table counts `skipped_limit`), each statement under decision 3's deadline.
   - **Row order without a full scan**: a `LIMIT` with no `WHERE` and no `ORDER BY` reads only the rows it returns, but always the same first ones. **Rowid tables**: `min` and `max` of the rowid come from the two ends of the b-tree (`O(log n)`); a start key is drawn uniformly between them from the scan's seed; the sample reads `rowid >= start` in rowid order, then wraps around from the beginning (both are range reads of the table's own b-tree, no sort). The rowid is addressed as `rowid`, `_rowid_` or `oid`, the first one that is not a declared column name; a table that declares all three is sampled from its start (no rotation). **`WITHOUT ROWID` tables**: the plain `LIMIT` read, with `SQLITE_DBCONFIG_REVERSE_SCANORDER` set from the scan seed's parity, so successive scans read the first or the last rows of the primary-key b-tree, never sorting.
   - **`estimated_rows`** from `sqlite_stat1` (the table's row count, the first integer of `stat`, parsed with a bound) when the application ran `ANALYZE`; omitted otherwise. Never `count(*)`, which reads every page of the table.
   - **`Location`** (engine `sqlite`): `database` = `main` (SQLite's own name for the file's database, the same for every target; the target id tells files apart); no `schema`; `object` = the table name; `field` = the column name. Names are normalized in the agent as one key each, as on MySQL / MariaDB (`normalize_field_path(&[PathPart::Key(raw)])`: a name containing `.` becomes `*`, a name matched by a classifier becomes `*`; [ADR-0009](0009-name-normalization-and-item-sanitization.md)); the [ADR-0057](0057-identifier-hardening-agent-first.md) rules apply on output, and parts altered by stripping or NFKC carry the [ADR-0056](0056-names-altered-by-normalization-marker.md) marker (`location.altered`), as on every engine. Names come from `sqlite_schema.name` and `table_xinfo`, as the application declared them. Because `database` is `main` on every SQLite target, a location exception for SQLite should be scoped to its target, or it covers every SQLite file with the same table and column names (security review N3: the user guide says so, and P10-E offers the target scope by default for `sqlite` exceptions).
   - **Case semantics: a fixed rule, no `name_case`.** SQLite compares identifiers without case for ASCII letters only, whatever the configuration (`Ä` and `ä` are two names; trailing spaces are significant). The console's rule for an engine outside `CASE_BLIND_EXCEPTION_ENGINES` (exceptions match only when the folded **and** the exact comparisons both match, ADR-0054) is the right one for `sqlite`: SQLite cannot hold two tables whose names differ only by ASCII case, so comparing with case separates nothing SQLite keeps together, while comparing without case, with the console's Unicode fold, would let an exception for `Ärzte` cover a distinct table `ärzte`. Comparing with case can only make an exception typed in another ASCII case cover less (more alerts, never fewer). So `sqlite` stays out of `CASE_BLIND_EXCEPTION_ENGINES` and out of `TRAILING_SPACE_BLIND_ENGINES` (P10-E adds a test that says so), and the agent sends no `TargetStatus.name_case` for it (the contract restricts that field to `mysql`, `mariadb` and `sqlserver`, and a fixed rule needs no report; ADR-0055's consequences ask for this decision).
   - **Coverage counters**: `objects_sampled` (tables sampled); `skipped_not_readable` (a table whose pages fail to read, `SQLITE_CORRUPT` included); `skipped_unsupported` (virtual tables, names that cannot be quoted, views posing as tables, CAS stores, a rollback-mode file not read); `skipped_limit` (the object bound, the byte budget, `SQLITE_TOOBIG`, the `-wal` size cap, the scan's time budget); `skipped_error` (`SQLITE_BUSY` twice, an interrupted statement, a killed or dead reader, a table gone since the catalog read, a file replaced during the scan). Views are counted in `coverage.views_not_sampled`, not in the counters.
   - **CAS store guard** ([ADR-0041](0041-cas-connector.md) decision 5): the core's name guard (the built-in CAS ticket registry and audit trail names; the `sqlite` block has no `cas_stores` key, a follow-up if CAS stores in SQLite files appear) and the ticket-id value tripwire of the shared sampling path apply as on the other engines. A recognized CAS store is **not read at all** on SQLite (the metadata aggregate of the other engines is a full table scan here) and counts `skipped_unsupported`; a tripped column is counted in `coverage.cas_guard_tripped`.

7. **`check()` and the target state.**
   - **Audit level `none`**, no `audit_source`, `supports_audit()` false (so an `audit.configure` job ends `unsupported`); `server_version` and `edition` are omitted (there is no server; the version of the SQLite that last wrote the file, header offset 96, goes to the agent's log only). The console shows such targets as "Discovery only" (P10-E).
   - **Reachable** when decision 2's open procedure passes, the connection setup succeeds and the catalog statement reads `sqlite_schema`. A rollback-mode file under the default `skip` is reachable with its note.
   - **Full check**: a short-lived reader runs decision 2's procedure, the connection setup, the catalog statement and the `journal_mode`, `schema_version`, `page_size` and `encoding` pragmas. It runs at the first heartbeat, when the file's `(st_dev, st_ino)`, size, `mtime` or header change counter (offset 24) changed, and otherwise at most every 10 minutes per target.
   - **Light check**, at every other heartbeat (security review M4): the path and file checks and the header pre-check, with no SQLite connection and no lock taken in SQLite's sense.
     - While a reader holds the target (a scan is running), the light check is a `light_check` IPC request: the reader runs `fstat` and `pread` on **its held check descriptor**, and repeats the path checks.
     - Otherwise the agent takes the target's lock **without waiting** and runs the light check itself (it opens, checks and closes a descriptor; the agent holds no SQLite lock, so nothing is released); if the lock is busy, the check is skipped and the last result is reported.
     - Every path follows decision 2's rule: no descriptor on the database or a side file outside the target's lock.
   - **Budget**: 2 s per check, under the heartbeat's 10 s deadline (ADR-0025).
   - **File permission checks at every check**: a file, side file or ancestor directory that became writable by the agent, or a file system no longer mounted read-only, turns the target unreachable at once.
   - **Failure codes** (closed set; `engine_code` = SQLite's extended result code as a decimal number, which fits `EngineCode`; the stage is the `check.stage_failed` label):

   - **Notes** (counts only, no label, decision 8): the codes in the table, plus `coverage.rollback_mode_not_read`, `security.file_world_readable` (the database file is readable by every local user: its data is exposed to every account of the host; open question 10), `coverage.views_not_sampled`, `coverage.virtual_tables_not_sampled`, `coverage.computed_columns_not_sampled`, `coverage.cas_guard_tripped` from the last scan, `check.stage_failed`, `check.timed_out`.

9. **Versions** (ADR-0039 decision 1).
   - **The library is the agent's, not the file's.** Every SQLite 3 file format is read by the bundled library: files written by any SQLite 3 version, WAL files by 3.7.0 and later writers. The supported range is a **file format** range: magic `"SQLite format 3\0"`, read and write versions 1 and 2, schema format 1 to 4, UTF-8 or UTF-16 (LE or BE), page sizes 512 to 65 536. A file outside it is refused (decision 7). There is no end-of-life version to drop: SQLite has one maintained line (to verify against sqlite.org's support policy).
   - **Bundled library**: SQLite **3.53.2** through `rusqlite` 0.40.2 / `libsqlite3-sys` 0.38.2 at the time of writing; the floor is **3.49.0** (the newest feature used: `SQLITE_DBCONFIG_ENABLE_ATTACH_CREATE` / `_WRITE`; `octet_length` needs 3.43, `REVERSE_SCANORDER` 3.42). The library is kept at the latest release `rusqlite` offers on the workspace MSRV; a SQLite security fix is shipped as an agent patch release, as for any advisory.
   - A schema that uses syntax newer than the bundled library fails to load and is reported `unsupported` (`coverage.unrecognized_file_format`) until a library update.

10. **Dev, CI, end to end and load** (ADR-0039 decision 9, P10-D).
    - **Dev**: `dev/seed/generate.py` writes seeded SQLite files under `dev/.state/sqlite/` (never committed) from the same fake data as the other engines, listed in `dev/ground-truth.json`: a rollback-mode file (declared with `rollback_mode: read`) and a WAL file; rowid, `WITHOUT ROWID` and `STRICT` tables; personal data in `TEXT` and in `INTEGER` columns (phone and card numbers); value-bearing table and column names (so the I2 check covers names); a view, a `VIRTUAL` and a `STORED` generated column, an FTS5 table whose content is in its shadow table (the ground truth expects the finding on the shadow table, none on the virtual table), a BLOB column holding a ground-truth value as bytes (expected: not found), a UTF-16 file, a value above 64 KiB; and the file modes and group of decision 2. A small writer process keeps the WAL file open, so its `-wal` and `-shm` exist, as with a running application. Hostile fixtures (a crafted header, a SQLCipher file, a hot journal, a symlinked path, a hard link, an agent-writable directory, a writable mount, a view posing as a table, a virtual table per compiled module, schemas above `LENGTH` and `SQL_LENGTH`, an unparseable schema, a truncated `-shm`) are generated by the integration tests themselves.
    - **CI**: a required job `agent-sqlite` runs the connector's integration tests against those files (no service container needed), on a runner kernel with Landlock enabled, the test directory bind-mounted read-only. The **engine matrix** covers the **writers**, since the reader is always the bundled library: files written by the SQLite of the supported distributions' Python images (pinned by digest; for example Debian 12's 3.40 and Ubuntu 24.04's 3.45, to re-resolve at implementation), and by the bundled version; in `DELETE`, `TRUNCATE`, `PERSIST` and `WAL` journal modes; with page sizes 512, 4 096 and 65 536; `auto_vacuum` off and on.
    - **End to end**: an `e2e-sqlite` job (required through `CI result`, like `e2e-cas`): the seeded files bind-mounted read-only (`:ro`) into the agent container, owned by another uid, group-readable by the agent's group; a writer sidecar holding the WAL file open; a Discovery scan with findings; the I2 check on values and names; an `audit.configure` attempt ending `unsupported`; the console showing "Discovery only"; a `-shm` truncated by the sidecar during a scan, which must cost one unit and leave the agent running.
    - **Load** (`e2e/load/`, job `load-sqlite`): there is no server CPU to measure, so the measured impact is on a **concurrent writer**. A writer process runs a fixed workload (for example 200 transactions per second of inserts and updates) on a file of at least 1 GiB while a paced Discovery scan runs, against a baseline without scan, in WAL mode and in rollback mode (`rollback_mode: read`), with the writer's busy timeout at 0 and at 5 s. Measured: the writer's commit latency (p50, p95, p99), its `SQLITE_BUSY` count, the WAL size at the end (checkpoint starvation), and the CPU share of one core and peak RSS of the agent and its reader processes during the scan (the analogue of the < 2 % criterion: SQLite's work happens on the application's host). Criteria proposed for the maintainer: WAL mode, no `SQLITE_BUSY` and a p95 within 5 % of the baseline; rollback mode with a 5 s busy timeout, no failed commit and a p99 increase below `max_statement_ms`; rollback mode without a busy timeout, the `SQLITE_BUSY` rate measured and documented (open question 8); the agent and its readers under 2 % of one core.

11. **Invariants.**
    - **I1**: neither the connector nor its reader opens a network connection or a listener (architecture test, decision 1; the reader's seccomp filter refuses `socket` and `connect`); the only socket is the pre-created `UnixStream::pair()`; network file systems are refused, so reads are local I/O.
    - **I2**: raw values and names cross only the local IPC channel; they reach the uplink only through the agent's normalization, `ScanJob::classify` and `classifiers::masking`; the path and file names never leave the agent; SQLite error messages are dropped in the reader.
    - **I3**: there is no credential; the agent's secrets are never in the reader's address space (fresh `execve`, cleared environment), and the reader cannot open their files (Landlock, refused locations).
    - **I4**: read-only by the layers of decision 3, autocommit reads with a bounded deadline, the closed statement list and the authorizer.
    - **I5**: declared files only; no directory, glob or search; no local detection.
    - **I6**: the protocol changes go through `shared/protocol/openapi.yaml` and the registries, with generated types.
    - **I7**: SQLite is public domain, `rusqlite` and `libsqlite3-sys` are MIT; the sandbox crates' licenses are checked by cargo-deny.

## Consequences
- A new crate, `agent/crates/connector-sqlite`, with the reader mode (`databastion-agent sqlite-reader`), its sandbox and its IPC; `agent.yaml` gains `targets[].sqlite` (`path`, `max_statement_ms`, `rollback_mode`), with `account` and `secret` refused for `engine: sqlite`; the core's `TargetEngine` and `Engine` gain `Sqlite`.
- An exception to ADR-0039 decision 4's "spawns no process", limited to the agent's own binary in reader mode (decision 4).
- `agent/deny.toml`, `agent/crates/agent/tests/architecture.rs` and a new `agent/.cargo/config.toml` change as decision 1 states; any new C code in the agent's graph now needs a reviewed change of the allow-list.
- The systemd unit may need `SystemCallFilter=` additions for Landlock, seccomp and `prctl` (to verify); SQLite targets need a kernel with Landlock enabled and a read-only mount of the database's directory; the installation tests and the user guide cover both.
- The agent binary contains the SQLite C library (size and build time to measure). A SQLite security fix needs an agent release; Dependabot and the advisories job surface it.
- Three fuzz targets join the nightly workflow, and the fuzz workspace builds C code with AddressSanitizer and the production flags.
- The contract changes of decision 8 (P10-C); the console (P10-E) accepts `engine.sqlite`, renders the new notes and "Discovery only", keeps `sqlite` out of its case-blind and trailing-space-blind engine lists, and scopes SQLite exceptions to their target by default.
- docs-keeper (P10-G): a "SQLite Discovery" section in [08-engine-capabilities.md](../08-engine-capabilities.md) (Audit None; WAL files read only while the application holds them open; rollback-mode files read only with the opt-in; views and virtual tables not sampled; `REAL` and `BLOB` values not sampled; the measured impact), the file permissions, read-only mount and Landlock requirements in [05-security.md](../05-security.md#recommended-database-accounts-read-only) with the systemd drop-in, the target-scoped exceptions in the user guide, a README row, [03-tech-stack.md](../03-tech-stack.md) (the bundled SQLite, the exception to "no C client library", the reader process).
- In practice SQLite is a Discovery-only engine; its README row says so (ADR-0039 consequences).

### Residual risks
- **C code parsing attacker-controlled files.** A memory-safety bug in SQLite reachable from a file (the record and b-tree decoders, the WAL reader, the `MAP_SHARED` `-shm`, the schema parser) runs in the reader: no secret, no network, read access to one directory, bounded resources. What it can still do: return false or extra names and values to the agent over the bounded IPC (the agent classifies and masks whatever it receives, so a compromised reader can forge findings for its target, never read other secrets), read other files of the same directory, and burn its CPU and memory budget. A sandbox escape (a kernel bug in Landlock or seccomp) is out of this ADR's reach.
- **A file that crashes the reader at every scan** costs that target its Discovery (3 deaths per scan, then `coverage.reader_process_failed`); the agent and its other targets are not affected.
- **WAL databases are unreadable while no application holds them open** (no `-wal` / `-shm`), and their newest commits are read through a heap index built from the whole `-wal` when no writer is connected.
- **Rollback-mode writers wait for the reader's reads**, when the operator opts in (at most `max_statement_ms` per statement, about 1 % of a scan's time at the default duty cycle); an application with no busy timeout can get `SQLITE_BUSY` on a commit during a scan.
- **A WAL reader keeps its `SHARED` and `DMS` locks** while its connection is open (up to 30 s idle between units), so the last application connection cannot delete the WAL at close during a scan, and a read mark pins checkpoints for the length of one statement (the WAL can grow while a scan runs; measured by the load run).
- **The application's account can swap the file** between two opens (it can write the directory). Each open, and every side-file descriptor, is bound to a checked regular file with one link (decision 2), so what it can present is another SQLite file of the same directory that the reader can read (the agent then reports that file's tables under this target).
- **SQLite's memory is not wiped**: its page cache and freed buffers hold raw pages until the reader exits.
- **`sqlite_stat4`** holds copies of indexed values and is not sampled; neither are `REAL` and `BLOB` values (a BLOB holding text is not found).
- **Hidden data**: whoever writes the file controls what Discovery sees (a corrupt page, a virtual table, data stored in BLOBs).
- **`readonly_shm` is undocumented**: its behaviour could change in a SQLite release; layers 1 to 3 of decision 3 still hold and the tests detect the change.
- **Hosts without Landlock** cannot have SQLite targets (unless the maintainer picks the alternative of open question 3).
- **The reader runs under the agent's uid in production** (implementation review of 2026-10-24, M3 residual). The seccomp allow-list refuses `kill`, `prlimit64`, `ptrace`, `process_vm_*`, `bpf`, `perf_event_open`, `userfaultfd`, `keyctl`, `fanotify_*`, `flock` and every process, socket and write call, and Landlock (ABI 6+) scopes signals, so a compromised reader cannot signal, trace or re-limit the agent. What it keeps: `stat`-family and `faccessat` calls on any path (Landlock does not cover them: the existence and metadata of files the agent's account can reach, never their content), the reads of its grant, its CPU and memory budget, and locks on its file within one unit of work (the agent kills a reader that holds more than an idle connection's locks between units).

## Rejected alternatives
- **An own pure-Rust reader, `turso_core`, `sqlite-core`**: see decision 1; the own reader stays a fallback (open question 2).
- **The system `libsqlite3`**: see decision 1.
- **Shelling out to the `sqlite3` command-line tool**: process spawning of an external tool, output parsing of a tool that prints values, no bounds (ADR-0039 rejected alternatives). The reader process of decision 4 is the agent's own binary, sandboxed, with a closed IPC.
- **SQLite in the agent's process** (the first draft): see decision 4's reasons; kept only as the opt-in alternative of open question 3.
- **`immutable=1`** or **`nolock=1`** on live files: wrong results and missed commits (decision 3).
- **Letting the agent write the `-shm`** (or create side files): breaks I4 (decision 3).
- **Opening through `/proc/self/fd/<n>`** to bind SQLite to the checked descriptor: SQLite derives `<name>-wal` and `<name>-shm` from the name it opened, so WAL databases would not work, and `SQLITE_OPEN_NOFOLLOW` refuses the magic link.
- **Reading a copy** (`sqlite3_deserialize` of the file read into memory): it needs the whole file in memory, cannot see the `-wal`, and a copy taken while the application writes can be torn. Kept only as the possible answer to open question 4 for quiescent WAL files.
- **`PRAGMA table_list`** for the catalog: compiles views and connects virtual tables (Context).
- **Sampling views**: runs SQL from the file.
- **`quick_check` / `integrity_check` before use**: cost and lock time (decision 5; open question 7).
- **Declaring a directory of SQLite files, or a glob**: I5 (decision 2).
- **Following symlinks in the path** (resolved at load, as ADR-0039 decision 5 wrote): SQLite resolves them itself per component and `SQLITE_OPEN_NOFOLLOW` refuses them; one rule is simpler (decision 2).
- **Refusing every database whose directory another user can write** (ADR-0039 decision 5's wording): the application must write its journals there (decision 2).
- **Reporting the path, or a hash of it**: the path holds names, and a hash of a low-entropy path is an oracle; the target id is the operator's chosen name.
- **`TargetStatus.name_case` for SQLite**: the rule is fixed and the console's default is already right (decision 6).
- **SQLCipher support**: its C crypto, OpenSSL in most builds, and a key on the agent host.
- **Lowering every `SQLITE_LIMIT_*`**: limits the parser applies to the schema would make legitimate files unreadable (decision 5).
- **Checking compile options only by absence in `PRAGMA compile_options`** (the first draft): options the pragma does not print would pass unchecked (decision 1).
- **Rollback-mode files read by default** (the first draft): an application without a busy timeout would get `SQLITE_BUSY` without the operator having chosen it (decision 3).

## Open questions (for the maintainer)
1. **Accept ADR-0039 decisions 3 (SQLite row), 4, 5 (SQLite item), 7 (SQLite part) and 9 for SQLite as refined here** (the reader process as an exception to "spawns no process", no symlink in any component, the parent-directory rule, the read-only mount, the limits that stay at their defaults, no `ConnectorList` change). *Proposed answer*: accept, so the implementation is held to this ADR and nothing wider.
2. **Process isolation of the SQLite reader.** *Answered*: **yes, from the first implementation** (decision 4, security review H1). The own pure-Rust reader stays the fallback if the review of the implementation or the fuzz campaign finds the sandboxed C library insufficient.
3. **An in-process reader as an alternative to decision 4**: keep SQLite in the agent's process, but only with an explicit local opt-in per target (`sqlite.in_process_reader: accept`), the residual accepted in writing by the operator (the agent's secrets in the address space that parses the file, a `SIGBUS` from a truncated `-shm` killing the whole agent, a hang in `prepare` holding a thread and the target lock, a process-wide heap limit), and the `SIGBUS` kill switch documented in [05-security.md](../05-security.md): whoever can write the `-shm` can stop the agent, and with it every other target's Discovery and Audit, after systemd's restart limit. It would also serve hosts without Landlock. *Proposed answer*: **isolate**; no in-process mode.
4. **Quiescent WAL databases** (no `-wal` / `-shm`, application stopped). Options: (a) report `coverage.wal_files_not_readable` and read the file when the application runs again; (b) read a bounded in-memory copy (`sqlite3_deserialize`, `rusqlite`'s `serialize` feature) when no `-wal` exists before and after the copy and the file's size and `mtime` did not change, the header patched to rollback mode in the copy. *Proposed answer*: (a) in the first implementation; (b) as a follow-up only if users report stopped applications as a common case.
5. **`rusqlite` 0.41 and MSRV 1.89.** `rusqlite` 0.41.0 (SQLite 3.54.0) needs Rust 1.89. *Proposed answer*: start on 0.40.x (SQLite 3.53.2) at MSRV 1.88; raise the workspace MSRV to 1.89 in a separate PR when a SQLite fix or a needed feature is only in 0.41 or later (the "Agent MSRV" job and `release.yml` move together).
6. **Network and FUSE file systems**: refused with no opt-in? *Proposed answer*: refused; revisit only with a measured, locked-down case (for example a read-only NFS export of files no one writes).
7. **An optional `PRAGMA quick_check`** (local opt-in, small files only)? *Proposed answer*: no; corruption is handled where it is read.
8. **Rollback-mode databases.** *Decided by this revision* (security review M5): read only with the local opt-in `sqlite.rollback_mode: read`; otherwise skipped with `coverage.rollback_mode_not_read`. *Open*: whether the default changes after the load run. *Proposed answer*: keep `skip` unless the load run shows no `SQLITE_BUSY` and a p99 increase below `max_statement_ms` for writers without a busy timeout.
9. **BLOB values that hold text** (some applications store JSON or text as BLOBs): sample BLOBs that are valid UTF-8? *Proposed answer*: not in the first implementation (consistent with `bytea` and `BLOB` elsewhere); a follow-up for every engine together if users ask.
10. **`security.file_world_readable`**: report a database file readable by every local user? *Proposed answer*: yes; it is cheap, it is the kind of exposure a DLP exists to show, and it carries no value.
11. **The constants**: `max_statement_ms` default 500 ms and range 50 to 5 000 ms, busy timeout 100 ms, 64 MiB heap and 512 MiB `RLIMIT_AS` per reader, 60 s `RLIMIT_CPU`, 128 MiB WAL cap, 32 MiB per table, 10 000 objects, 64 columns per statement, 3 reader deaths per scan. *Proposed answer*: constants as written, `max_statement_ms` and `rollback_mode` the only `agent.yaml` keys; the load run may revise them.

## Implementation note (2026-10-24, P10-A and its security review)

The connector is implemented in `agent/crates/connector-sqlite` (P10-A). Its security review (3d1e9cc..de7fad8) found no Critical or High finding; M1 to M3 and L1 to L12 are fixed before merge. The accepted deviations from this ADR's text, with the reviewer's notes:

1. **The heartbeat light check while a scan runs** reports the last result (the target's lock is busy) instead of a `light_check` request to the scan's reader. The reader re-runs the path, file and descriptor checks before every unit of work, so a file that becomes writable or is replaced stops the scan at its next unit; the heartbeat's view is stale for the length of a scan (accepted, reviewer: acceptable with the per-unit recheck). A light check stuck in the kernel holds its target with one thread at most (review L1).
2. **Sticky ancestors**: an ancestor directory above the file's own directory with the sticky bit, owned by another account, is accepted (`/tmp`, `/var/tmp`); the file's own directory gets the full writability rule. Without it, every file under a sticky world-writable ancestor would be refused.
3. **Row estimates**: the statistics statement of decision 5 (`idx IS NULL OR idx = tbl`) gives no `estimated_rows` for a table that has an index (ANALYZE writes a row with a NULL `idx` only for a table without one). A gap to close with a statement change (follow-up), not a security matter.
4. **Sampling statements select the rowid too**, to continue a read cut by the 1 MiB response bound, with a fourth template `rowid >= ?1 AND rowid < ?2` for the wrap-around; every response is checked against its request (rows, columns, the last rowid inside the range and increasing, review L8).
5. **The self-check's functions**: `sqlite_version()` and `sqlite_source_id()` are allowed by the authorizer only on the self-check's in-memory connection (template `SelfCheck`).
6. **`SQLITE_ERROR` is classified by fixed message prefixes** ("access to view", "no such table", "no such column", "malformed database schema") inside the `db` module; the message is dropped there.
7. **A view whose schema row claims `type = 'table'`** (with a root page or without) makes SQLite 3.53.2 refuse the whole schema as malformed, so the file is `coverage.unrecognized_file_format` before any view is compiled; decision 5 expected `table_xinfo` to compile the view. Stricter, accepted.
8. **The C-code guard** (`c_code_is_allow_listed`) checks the packages the shipped binary is built from (normal and build edges from `databastion-agent`): the codegen tool's dev-dependencies (`prettyplease`, a `links` key without C) are out. A second guard (`linked_libraries_are_allow_listed`, review L11) scans the shipped crates' `src/` and `build.rs` for `#[link(` and `rustc-link-lib` against a closed list.
9. **Test-only switches** (feature `test-support`, called from test code only, checked by the architecture tests): the reader executable of the tests (the agent binary built by Cargo), the reader's uid and gid for tests that run as root, and, with those credentials set, the agent's own light check without the writability rule (the reader still applies it). The in-process tests relax the exact descriptor set of decision 2 step 8 (a test harness holds descriptors of its own); the reader process never does.
10. **A side file that appears after the reader's grant**, or one re-created with another inode (compared by path and `(st_dev, st_ino)`), (review L4: Landlock grants `ReadFile` on the file and the side files present at open, `ReadDir` on the directory, never `Execute`) cannot be read: the unit is lost (`side_file_appeared`) and the next unit gets a new reader with a new grant. A rollback-mode file under `rollback_mode: read` whose application writes often loses such units.

Also recorded:

- **The reader's start-up order** (review M1): `early()` (no new privileges, not dumpable, the limits, no descriptor but 0 to 2), the open request, the path rules of decision 2 (path based), the Landlock grant built from `O_PATH` descriptors opened with `openat2(RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS)` and verified against an `lstat` of their paths after `restrict_self`, then the seccomp filter, the self-check and the open procedure.
- **The seccomp filter is a default-deny allow-list** (reviews M2, M3), measured with strace under the reader tests, documented per system call in `sandbox.rs`; x32 numbers are refused first.
- **Locks between units** (review L3, re-review N1 and N2): after each response the agent stops the reader (`SIGSTOP`), reads `/proc/locks` while it is stopped, and continues it (`SIGCONT`) just before its next request, so a reader cannot drop its locks for the check and take them again during the pause. A reader holding more than an idle connection does is killed: in rollback mode nothing; in WAL mode a read lock on the database's `SHARED` range only (bytes 1073741826 to 1073742335, never the `PENDING` or `RESERVED` byte) and the `-shm` `DMS` byte. The database's identity, the journal mode and the `-shm` inode come from the agent's own file checks, run when each reader opens, and the reader's open answer must match them. A reader that does not stop within 200 ms, or a `/proc/locks` that cannot be read, gets the reader restarted. Chosen over closing the reader at every pacing pause, which at the default 1 % duty cycle would start a reader for nearly every unit.
- **The systemd unit** allows `landlock_create_ruleset`, `landlock_add_rule`, `landlock_restrict_self` and `seccomp` by name (the `@sandbox` group is not known to every supported systemd); the installation tests (Debian 12, Ubuntu 24.04) run the installed binary's reader mode and expect its refusal of a writable mount, which proves its sandbox and self-check on that system (the container shares the host's kernel: Debian 12's own kernel is not covered there).
- **For docs/05** (docs-keeper): under the systemd unit, `ProtectSystem=strict` makes every path outside `/var/lib/databastion` read-only in the agent's mount namespace, which meets the read-only mount rule of decision 2 step 2 for most deployments; a file under `/home` needs `BindReadOnlyPaths=` (with `ProtectHome=yes`), and the container image needs the directory mounted `:ro`.
