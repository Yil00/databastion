## Context

### What the agent does today

Read from the code at `0f64d7d` (`dev`); not run for this ADR.

- **Catalog rule.** A relation in `pg_catalog`, `information_schema`, `pg_toast` or a temporary schema is a catalog, and so are `pg_stat_statements` and `pg_stat_statements_info` in the extension's schema of that database, and an unqualified `pg_*` name (under the `pgaudit.log_catalog` rule of [08](../08-engine-capabilities.md#postgresql-audit)). A read whose relations are all catalogs produces no event, on both sources, for every account. The exception is the five statistics relations of ADR-0048.
- **So these reads produce no event today, from any account:** `SELECT query FROM pg_stat_activity`, `SELECT query FROM pg_stat_statements` (qualified with the extension schema or unqualified), `SELECT * FROM pg_stat_monitor` (an unqualified `pg_*` name), and any read that joins them with other catalogs only.
- **Function forms.** The analyzer does not take a name followed by `(` as a relation (`read_relation`). A statement that names no relation at all (`SELECT * FROM pg_stat_get_activity(NULL)`, `SELECT pg_stat_get_backend_activity(1)`, `SELECT query FROM public.pg_stat_statements(true)`) is therefore a read of `*`, always reported, never the agent's own unless it is one of the connector's exact own texts. The same call in a statement that also names a catalog (`… FROM pg_stat_get_activity(NULL) a JOIN pg_catalog.pg_database d …`) is catalog-only and produces no event.
- **Any function call next to catalogs only is invisible.** For the same reason, a statement whose relations are all catalogs produces no event whatever function it calls: `SELECT pg_catalog.query_to_xml('select query from pg_stat_activity', true, false, '') FROM pg_catalog.pg_class LIMIT 1` (SQL text in an argument), `table_to_xml('crm.customer', …)` (an application table), `SELECT pg_read_file('log/postgresql.log') FROM pg_class LIMIT 1` (server logs hold statement texts), `SELECT data FROM pg_logical_slot_peek_changes('s', NULL, NULL), pg_class LIMIT 1` (decoded rows), `SELECT lo_get(16400) FROM pg_class LIMIT 1` (a large object), and `SELECT my_f() FROM pg_class LIMIT 1` (a user function that reads `crm.customer`). On pgaudit, only relation records of what the function reads can show more; the connector ignores `FUNCTION` class records. Table-less, these calls are reads of `*` (unit test of ADR-0048 for `query_to_xml`).
- **What the connector itself sends** (`sql.rs`, `sql::all_statements()`):

  | Statement | Reads | Text read? | Own-account handling today |
  |---|---|---|---|
  | `pss_counters(schema, toplevel)` (each poll) | `<ext>.pg_stat_statements(false) AS s` joined with `pg_catalog.pg_database d` | no (`showtext => false`) | catalog-only: no event for any account |
  | `pss_texts(schema, toplevel)` (new entries only) | `<ext>.pg_stat_statements(true) AS s`, `s.query` cut at 8 192 characters, `WHERE s.queryid = ANY($1)` | **yes, every role's texts** | table-less: left out uncharged on its exact text (as sent with pgaudit; as stored with `pg_stat_statements`, with the agent's role oid, top level, the poller's database and the pinned `queryid`, #90); registered per target (`PgOwn::allow_statement`), and kept registered after the source switches to pgaudit |
  | `pss_probe(schema)` (`check()`, stream start) | `<ext>.pg_stat_statements_info` | no (`dealloc`, `stats_reset`) | catalog-only |
  | `AUDIT_PREREQUISITES`, `PSS_FUNCTION_SCHEMA` | `pg_extension`, `pg_depend`, `pg_class`, `pg_proc`, `pg_namespace` | no; the names `pg_stat_statements` and `pg_stat_statements_info` appear only as string literals | catalog-only |
  | `PGAUDIT_SETTINGS` | `pg_catalog.pg_settings` | no (settings) | catalog-only |

  No connector statement reads `pg_stat_activity`, `pg_stat_get_activity` or `pg_stat_get_backend_activity`, and `check()` reads none of them. Every function the connector calls is qualified with `pg_catalog` (unit test `functions_are_qualified`). The connector's integration tests (`it.rs`) read `pg_stat_activity` through their own test connections, for counts and states only.

### What the servers expose (PostgreSQL 14 to 18, the engine matrix)

From the PostgreSQL documentation and the system views' definitions as known on 2026-10-11, **not verified on the engine-matrix images for this ADR**. The drift and pinning tests of decision 9 verify them before the implementation is merged.

| Object | Kind | Statement text | Who sees other sessions' text | Versions |
|---|---|---|---|---|
| `pg_catalog.pg_stat_activity` | view over `pg_stat_get_activity(NULL)` | `query`: the current or last statement of each backend, as sent (literals included), cut at `track_activity_query_size` (1 024 bytes by default) | its own role's sessions and those of roles it has the privileges of; every session for superusers and `pg_read_all_stats` members (`pg_monitor` includes it) | 14 to 18 |
| `pg_catalog.pg_stat_get_activity(integer)` | set-returning function | the same `query` column (`NULL`: every backend) | same | 14 to 18 |
| `pg_catalog.pg_stat_get_backend_activity(integer)` | scalar function | the statement text of one backend (by backend id, enumerated with `pg_stat_get_backend_idset()`) | same | 14 to 18 |
| `<ext>.pg_stat_statements` | view of the extension over `pg_stat_statements(true)` | `query`: normalized for planned statements (constants as `$n`, comments kept); utility statements kept as sent on 14 and 15, partly normalized from 16 on (to verify per version), so `ALTER ROLE … PASSWORD` literals and SCRAM verifiers can be in it (ADR-0012) | `SELECT` is granted to `PUBLIC` by the extension script (to verify); other roles' texts need superuser or `pg_read_all_stats`, otherwise `<insufficient privilege>` | extension 1.9 to 1.12 (PostgreSQL 14 to 18) |
| `<ext>.pg_stat_statements(boolean)` | set-returning function | the same `query` column, `NULL` when called with `false` | same | same |
| Extensions `pg_stat_monitor`, `pg_qualstats`, `pg_store_plans`, `pg_show_plans` | views and functions | statement texts (`pg_stat_monitor`: `query`, and literals when its normalization is off), constant values of predicates (`pg_qualstats`), plans with their constants (`pg_store_plans`, `pg_show_plans`) | per extension | not in the dev or engine-matrix images: **nothing verified** |

Not listed, and why:

- `<ext>.pg_stat_statements_info` (counters), `pg_stat_progress_vacuum`, `_analyze`, `_cluster`, `_create_index`, `_basebackup`, `_copy` (relation oids, phases, counters; no text column known on 14 to 18), `pg_locks`, `pg_stat_replication`, `pg_stat_wal_receiver` (`conninfo` with the password obfuscated), `pg_stat_subscription`, `pg_stat_ssl`, `pg_stat_gssapi`, `pg_stat_io` and the other cumulative statistics views: no statement text.
- `pg_prepared_statements` (`statement`), `pg_cursors` (`statement`) and `pg_backend_memory_contexts` (`ident`, which can hold the text of cached plans, 14+): **the reading session's own** statements only. Behind a transaction-mode pooler (PgBouncer with protocol-level prepared statements, 1.21+), one server session carries the prepared statements of several clients; this is a residual (open question 1).
- `pg_log_backend_memory_contexts(pid)` (14+, superuser by default) writes another backend's memory contexts to the server log, not to the client; table-less, it is already a read of `*`.
- Credential- and value-bearing catalogs (`pg_authid.rolpassword`, `pg_shadow.passwd`, `pg_user_mappings.umoptions`, `pg_subscription.subconninfo`, `pg_largeobject`) are read silently too. They hold no statement text and are out of scope: a separate ROADMAP phase 8 follow-up asks for an ADR-0048-style list.

### Who reads these views routinely

From the tools' documentation and common practice, not measured here:

- **Without the text.** Prometheus `postgres_exporter` (its default `pg_stat_activity` metrics: counts and longest transaction per database, state, user and application), pgwatch and check_postgres (`backends`, `txn_idle`), Patroni, connection-pool health checks, and applications that terminate their own idle sessions (`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND …`). `postgres_exporter`'s `pg_stat_statements` collector reads `queryid` and counters; the query text only when asked to.
- **With the text.** pgAdmin's dashboard, Datadog Database Monitoring and pganalyze (query samples from `pg_stat_activity`, normalized texts from `pg_stat_statements`), PMM (`pg_stat_monitor`), PoWA (`pg_qualstats`), and DBAs' scripts (`WHERE query NOT LIKE '%pg_stat_activity%'`).

`pg_stat_activity` is polled far more often than the statistics catalogs of ADR-0048, most often without the text. Every role can read its own role's texts: a shared application account sees the statements of every other session of that account, other end users' literals included.

### What the audit sources record

- **`pg_stat_statements`**: one entry per normalized text and role, `SELECT pid, query FROM pg_stat_activity WHERE state <> $1`. Function bodies are not recorded with `pg_stat_statements.track = top` (the default), and a `DO` block gives no event on this source (a utility statement of no read or write kind).
- **pgaudit**: a `READ` record with the text as sent. With `pgaudit.log_relation`, relation records name `pg_catalog.pg_stat_activity` and, as seen with the statistics views, probably the relations behind it (`pg_database`, `pg_authid`; to verify); a user view over it, or an inlined SQL function, gets a relation record of `pg_stat_activity` that the text does not name (to verify). With `pgaudit.log_catalog = off`, a statement whose relations are all in `pg_catalog` is not logged ([ADR-0048](0048-statistics-catalogs-as-reads.md) decision 5): a read of `pg_stat_activity` alone is invisible there. The `pg_stat_statements` view is in the extension's schema, not in `pg_catalog`, so its reads are logged whatever `log_catalog` says. Whether pgaudit logs a statement that names **no** relation (`SELECT * FROM pg_stat_get_activity(NULL)`) with `log_catalog = off` is to verify (pinning test, decision 9). Dynamic SQL in PL/pgSQL is logged as a substatement with its own text. `FUNCTION` class records are ignored by the connector, as today.

## Options

- **(a) A closed list, every read reported.** The listed views and functions are named as objects in read events, always reported, never the agent's own except its exact poll texts (ADR-0045 part (a), ADR-0048).
- **(b) The same, but a read that provably selects no text stays quiet.** A statement whose only access to the core list is a read that names no text column, no whole row and no column renaming (decision 2) stays a catalog read, for every account. Every other read is (a).
- **(c) Report by reader**: only reads by roles that can see other roles' texts (`pg_read_all_stats` members, superusers).
- **(d) Document only** (the current state).

(c) does not hold: the sources do not say what the reader held at the time, a shared application account reads other sessions' texts of its own role with no special privilege, and checking every reader's grants would need catalog reads per principal. (d) leaves other sessions' literals, and on `pg_stat_statements` passwords and SCRAM verifiers in utility texts, readable with no event. (a) is the ADR-0045 and ADR-0048 answer, and ADR-0048 open question 4 rejected a column test for the statistics catalogs because whole-row references fail open. Here the noise is of another order (exporters, pools and health checks poll `pg_stat_activity` every few seconds, mostly without the text), and the column that matters is one, named `query`, in every relation of the core list. (b) keeps (a) for everything it cannot prove, so it fails closed as (a) does.

## Decision: option (b)

1. **The statement-text list.**

   **Core list**, identical on PostgreSQL 14 to 18 (the drift test of decision 9 confirms it per image), with the no-text shape of decision 2:

   | Name in the text | Kind | Named in events as | Text access |
   |---|---|---|---|
   | `pg_stat_activity` (qualified with `pg_catalog` or unqualified) | view | `pg_catalog.pg_stat_activity` | the column `query` |
   | `pg_stat_get_activity(` (same) | set-returning function | `pg_catalog.pg_stat_activity` | the column `query` |
   | `pg_stat_get_backend_activity(` (same) | scalar function | `pg_catalog.pg_stat_activity` | always (the result is the text) |
   | `pg_stat_statements` (qualified with the extension's schema of that database, or unqualified while the extension is installed there) | view | `<ext>.pg_stat_statements` | the column `query` |
   | `pg_stat_statements(` (same) | set-returning function | `<ext>.pg_stat_statements` | the column `query` |

   - Names are compared after the analyzer's identifier folding and `U&"…"` decoding, as in ADR-0048 (a quoted `"PG_STAT_ACTIVITY"`, a `public.pg_stat_activity` or a `pg_stat_statements` outside the extension's schema is an ordinary relation, reported as today).
   - An unqualified name is the catalog's: `pg_catalog` comes first in the search path unless a session lists it later, so a relation or function shadowing it is over-reported, never missed. An unqualified `pg_stat_statements(` in a database where the extension is not installed is a read of `*` (a user function).
   - **Function forms are named by their view**: the objects of events are relations in the contract, the three `pg_catalog` names read the same data, and policies then need one object per data set (open question 4).
   - `pg_stat_statements_info` stays a catalog (no text).

   **Extension list** (decided by the security review of the proposal, M3): a relation or function named `pg_stat_monitor`, `pg_store_plans`, `pg_show_plans`, or starting with `pg_qualstats` (`pg_qualstats`, `pg_qualstats_all`, `pg_qualstats_pretty`, `pg_qualstats_example_query(…)`…), **in any schema or unqualified**, makes the statement a text read, with **no shape exemption**: their columns are not verified, so no column proof is attempted. The object is the name as the text gives it (schema included when qualified, otherwise no schema), or `*` for a function call that names no relation of the list. A user relation that happens to carry one of these names is over-reported.
2. **The no-text shape, quiet for every account** (core list only). A statement that names a core-list view or set-returning function stays a catalog read for that name (no object, so no event when the other relations are catalogs too) only when **all** of these hold on the whole text:
   - the text lexes completely, is not cut (`pg_stat_statements` texts at the 8 192-character read bound, `<previously logged>` without its first record), and is below the analyzer's 16-relation bound;
   - no identifier token, quoted or not, after folding and `U&` decoding, equals `query`, anywhere in the text: a select list, a `WHERE`, a `FILTER (WHERE …)`, `ORDER BY`, `USING (query)`, the functional notation `query(a)`, an alias `AS query` (the last one over-reports, never misses);
   - no `*` token, except the exact sequence `count(*)`;
   - **no whole-row reference.** The *range variables* of the statement are: the alias of each `FROM` item that is a core-list view or set-returning function; when such an item has no alias, its name, qualified or not (`pg_stat_activity`, `pg_catalog.pg_stat_activity`) for a view, and **the bare function name** for a set-returning function, also inside `ROWS FROM (…)` and with `WITH ORDINALITY`. Every occurrence of a range variable or of a core-list name outside its own `FROM` item must be followed by `.` and a column name other than `query`. So `SELECT a FROM pg_stat_activity a`, `row_to_json(a)`, `a::text`, `(a).*`, `WHERE pg_stat_activity = …`, `SELECT pg_catalog.pg_stat_activity FROM pg_catalog.pg_stat_activity`, `SELECT row_to_json(pg_stat_get_activity) FROM pg_stat_get_activity(NULL)`, `SELECT pg_stat_get_activity::text FROM pg_catalog.pg_stat_get_activity(NULL)` and the same through `ROWS FROM (pg_stat_get_activity(NULL))` or `… WITH ORDINALITY` are text reads. An alias equal to a column name (`FROM pg_stat_activity state`, then `SELECT state`) and a cast to the row type (`NULL::pg_stat_activity`) are text reads too: over-reported, never missed;
   - **no column alias list anywhere in the text**: a table, a subquery, a parenthesized join (`(… JOIN …) AS j (c1, …)`), a function, `ROWS FROM`, a `WITH ORDINALITY` alias, or a CTE column list (`WITH x (c1, …) AS`). Any of them can rename `query` positionally;
   - no `NATURAL` join (a natural join with a relation that has a `query` column compares other sessions' texts without naming them);
   - a core-list set-returning function appears only as a `FROM` item, or inside `ROWS FROM (…)` (`SELECT pg_stat_get_activity(NULL)` returns whole rows);
   - no `TABLE` form on a core-list view (`TABLE pg_stat_activity`);
   - `pg_stat_get_backend_activity(` does not appear (it returns the text itself), and no name of the extension list appears.

   Anything else that names a listed entry is a **text read**: the entry's object of decision 1, kept in the event even when every other relation is a catalog, in every action class, as ADR-0048 does for the statistics relations (`CREATE TABLE t AS SELECT query FROM pg_stat_activity`, `INSERT INTO t SELECT …`, `COPY (SELECT query FROM pg_stat_activity) TO STDOUT`). A text read at the analyzer's relation bound adds `*`, as today.

   **The text decides only when every relation it names is a catalog or a core-list entry** (security re-review N2). A statement that names a core-list entry and any other relation (an application table, a user view, a materialized view, a function in `FROM` outside `pg_catalog`) is a text read whatever its shape: `SELECT a.pid FROM pg_stat_activity a, public.v`, where `public.v` selects `query`, would otherwise name only `public.v`, without the always-reported mark.

   The shape is decided on the statement text on both sources. It covers the common monitoring reads (`SELECT state, count(*) FROM pg_stat_activity GROUP BY state`, `postgres_exporter`'s activity query, `SELECT pid FROM pg_stat_activity WHERE state = 'idle'`, `SELECT queryid, calls FROM pg_stat_statements`), and the connector's own `pss_counters` (decision 4).
3. **pgaudit relation records** (security review M1). A relation record that names a listed entry the statement text does not name (a user view over `pg_stat_activity`, an inlined SQL function, a `pg_stat_monitor` under another search path) makes the event a text read: it names the listed object and is always reported, whatever the shape of the text. ADR-0048's records already work this way for the statistics relations (`statistics_relation` on the record's name, in the pgaudit `flush`). A record of a core-list view the text names keeps the shape decision of the text (records name relations, not columns), with one exception (security re-review N2): when, in the same substatement, a core-list record comes with a record of a view, a materialized view or a function-derived relation outside `pg_catalog`, the statement is a text read, since such a relation can carry `query` under another name. Together with the rule of decision 2 that the text decides only when it names catalogs and core-list entries only, both readings of the same statement fail closed.
4. **Always reported.** A text read carries the agent-internal always-reported mark (`MaskedEvent::always_report`), so the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops it, as in ADR-0045 decision 3 and ADR-0048 decision 3: one row of `pg_stat_activity` is one statement with its literals, and the pgaudit log without `pgaudit.log_rows` has no row count. The row count, when the source has one, counts rows of the view. No signal is added. Shape reads (decision 2) produce no event, so the filter does not apply to them.
5. **The agent's own account** (the counterpart of ADR-0045 decision 4).
   - **`pss_counters`** reads `pg_stat_statements(false) AS s` with no text column: it has the no-text shape of decision 2 (alias `s`, columns `s.userid`… only, no column alias list, `queryid` is not `query`) and stays a catalog-only read for every account, as today. A unit test proves it for both `toplevel` forms.
   - **`pss_texts`** is a text read, left out uncharged only by **exact text**, under a new own kind (`OwnKind::StatementText`):
     - with `pg_stat_statements` as the source: the stored text equals its `pss_form`, and `OwnKeys::admit` holds (the agent's role oid, a top-level entry, the poller's database, the `queryid` pinned for that slot), as #90 does today;
     - with pgaudit as the source (security review L1): the whole text equals `pss_texts(schema, toplevel)` as sent, from the agent's account, `application_name` and client address, with no signal, and with no relation record of another listed entry, **only while a `pg_stat_statements` stream of the target is configured, or for records whose time falls within a period in which one ran** (start and end kept per target in memory, bounded, plus the statement timeout). Today `PgOwn::allow_statement` keeps the text allowed for every later pgaudit stream of the target; after this change, a record of that text written outside such a period is reported. After an agent restart no period is known, so the agent's own earlier polls found in the log are reported (loud), as the existing restart residual says.

     It is never matched by prefix, by normalized shape or by `queryid` alone. The text is already constant per (schema, `toplevel`): the entry list is a bound parameter, and the cut length and `LIMIT` are fixed in the text, so no change of the statement is needed (unlike ADR-0045's MySQL polls).
   - **Never the agent's own otherwise.** Any other text read of a listed entry with the agent's identity is reported and never charged to the row budget: the connector sends no other statement to them. This covers `SELECT query FROM pg_stat_activity` and `SELECT query FROM <ext>.pg_stat_statements` from the agent's role, which a stolen credential with `pg_read_all_stats` reads unreported today. The `*` reads of decisions 7 and 8 are never the agent's own either.
   - **Not listed, unchanged**: `check()` reads `pg_settings` (`PGAUDIT_SETTINGS`) and `pg_stat_statements_info` (`pss_probe`), which hold no statement text; they stay catalog reads. The connector reads `pg_stat_activity` nowhere.
   - A unit test over `sql::all_statements()` proves that every connector statement either names no listed entry, has the no-text shape, or is `pss_texts`; that the names in `AUDIT_PREREQUISITES` and `PSS_FUNCTION_SCHEMA`, which are string literals, are not taken as names; and that no connector statement triggers decision 7 or 8.
6. **`pgaudit.log_catalog`.** With `log_catalog = off`, a read of `pg_stat_activity` alone is not logged, as for the statistics catalogs, and whether a statement that names no relation (`SELECT * FROM pg_stat_get_activity(NULL)`) is logged is pinned by a test (decision 9). The `check()` local detail of ADR-0048 decision 5 names this effect too; the level is unchanged and no target note is added. The documentation keeps recommending `log_catalog = on`.
7. **Functions that read past the statement's relations**, in every statement. A call of one of these `pg_catalog` functions adds `*` to the statement's read, always reported, never the agent's own, **also when every relation the statement names is a catalog**:
   - functions that run SQL text or read a relation named by their argument: `query_to_xml`, `query_to_xmlschema`, `query_to_xml_and_xmlschema`, `cursor_to_xml`, `cursor_to_xmlschema`, `table_to_xml`, `table_to_xmlschema`, `table_to_xml_and_xmlschema`, `schema_to_xml*`, `database_to_xml*`, `ts_stat`, `ts_rewrite` (the names the `policy_function_ok!` macro of `sql.rs` refuses in row-level security policies);
   - server files (security review H3): `pg_read_file`, `pg_read_binary_file` (every overload; server logs hold statement texts);
   - logical decoding: `pg_logical_slot_get_changes`, `pg_logical_slot_peek_changes`, `pg_logical_slot_get_binary_changes`, `pg_logical_slot_peek_binary_changes` (decoded row data);
   - large objects: `lo_get`, `loread`, `lo_export`, and the server-side `lo_import` (one- and two-argument forms).

   Without this, any listed entry can be read through `query_to_xml('select query from pg_stat_activity', …)` next to a catalog, and server logs, slots and large objects next to `pg_class`. The connector calls none of them (unit test; the names appear only in a regular-expression literal and in the denylist test).
8. **Other user code next to catalogs only** (security review M2, the former open question 7; re-review N1, N3). In a statement whose relations are **all catalogs** (the case that gives no event today), each of these adds `*`, always reported, never the agent's own:
   - a call of a function that is schema-qualified outside `pg_catalog`, or unqualified and not built in **for that database** (below). `SELECT my_f() FROM pg_class LIMIT 1` becomes a read of `*`;
   - an operator written `OPERATOR(<schema>.<op>)` with a schema other than `pg_catalog`, or an operator symbol, bare or in `OPERATOR(…)` without a schema, that is not built in for that database;
   - a cast (`::<type>`, `CAST(… AS <type>)`, a typed literal `<type> '…'`) to a type that is not built in for that database: a user domain (whose `CHECK` can call a user function), a user type (whose input function or casts can be user code), or a type name that collides with one of them.

   The functions of decisions 1 and 7 are handled by those decisions and **excluded from this one** (re-review N4): the connector's own `pss_counters`, which calls `<ext>.pg_stat_statements(false)` next to `pg_catalog.pg_database`, has the no-text shape of decision 2 and gives no event; `pss_texts` follows decision 5; `query_to_xml` and the others of decision 7 are `*` there. Functions qualified with `pg_catalog` (`pg_catalog.lower(…)`) resolve in `pg_catalog` only and are built in when they are on the list.
   - **Built-in lists.** One committed, sorted list per major version (14, 15, 16, 17, 18) for each of function names, operator symbols (`oprname` of `pg_operator`) and type names (`typname` of `pg_type`, with the SQL spellings `integer`, `character varying`, `double precision`, `timestamp with time zone`…), written by a script in `agent/crates/connector-postgres/builtins/` from a fresh engine-matrix image with no extension created: every `proname` of `pg_proc`, `oprname` of `pg_operator` and `typname` of `pg_type` in `pg_catalog`, plus, for functions, the SQL forms the grammar writes with a parenthesis without being a `pg_proc` call of that name (`COALESCE`, `NULLIF`, `GREATEST`, `LEAST`, `CAST`, `EXTRACT`, `OVERLAY`, `POSITION`, `SUBSTRING`, `TRIM`, `ROW`, `ARRAY`, `EXISTS`, `IN`, `ANY`, `ALL`, `SOME`, `VALUES`, `FILTER`, `OVER`, `GROUPING`, `CUBE`, `ROLLUP`, `XMLELEMENT` and the other `XML*` forms, the SQL/JSON constructors of 16+, `MERGE_ACTION` on 17+, and type names with modifiers such as `numeric(`, `varchar(`, `timestamp(`). The script records the image digest. The list is picked from `server_version_num`, read at connect; a newer major than the newest list uses the newest list and logs a warning once (names added since are reported: fail closed). Each list must stay **exact per major version** (re-review N5): PostgreSQL adds and removes catalog functions, operators and types only in major releases, and minor releases do not change these names, so one list per major is exact for all its minor versions; the drift test runs on the engine-matrix minor of each major and would show a minor-release change.
   - **Drift test, both ways**, per image: every `pg_proc`, `pg_operator` and `pg_type` name in `pg_catalog` is on its major's lists, and every listed name is in that image's catalogs or on the commented keyword list; a new major gets its lists in the PR that adds it to the engine matrix.
   - **Collision probe, per monitored database** (re-review N1, narrowed by the third review, R1). PostgreSQL resolves an unqualified function or operator by name **and argument types across the whole search path**: `pg_catalog` comes first only among candidates that match equally well. With the default `"$user", public`, a role that can create in its own schema or in `public` can add `"$user".length(integer)` or `public.lower(int)`, which wins on type match (the CVE-2018-1058 class): `SELECT length(42) FROM pg_class LIMIT 1` then runs user code. So the connector reads, in each monitored database, from catalogs every role can read, in one bounded query refreshed at each heartbeat (with the other `check()` catalog reads; at most 20 000 names, one more read to tell a cut):
     - **functions and operators**: the names (`pg_proc.proname`, `pg_operator.oprname`) of objects in every schema other than `pg_catalog` and `information_schema` that are on the built-in lists **and** have an overload that a value or literal of a catalog-only statement can reach. That is the CVE-2018-1058 case and its variants (final check, F1 and F2). An overload is reachable, so its name collides, when every one of its argument types (`proargtypes`, `oprleft`, `oprright`) is, at its position:
       - a built-in type: a type of `pg_catalog`, polymorphic and pseudo-types included;
       - a domain over a built-in type (a domain accepts a value of its base type);
       - a user type that is the `casttarget` of an **implicit** cast (`castcontext = 'i'`) whose `castsource` is built in, with or without a cast function: the type's owner can create one without being a superuser (`CREATE CAST (integer AS mytype) WITH FUNCTION … AS IMPLICIT`), and `length(42)` then reaches `public.length(mytype)`. One cast step is all that function resolution applies. `citext`'s `text → citext` is an assignment cast, not an implicit one, so it adds nothing;
       - any other user type, **when an untyped string literal can resolve to it**: when no built-in overload of the same name and argument count accepts a type of the string category (`typcategory = 'S'`) at that position, or when the user type is itself in the string category and marked preferred (`typispreferred`). The probe computes this from the built-in signatures in `pg_catalog`. So `public.abs(mytype)` collides (no built-in `abs` takes a string-category argument, so `abs('5')` can resolve to it), while `citext`'s `lower(citext)`, `upper(citext)` and `=` do not (built-in `lower(text)` and `=(text, text)` take a string-category type there, and `text` is the preferred type of the category).

       Every other overload on a user or extension type (`citext`, `hstore`, `ltree`, PostGIS `geometry`, `pg_trgm`'s `gtrgm`) is chosen only for a value of that type obtained otherwise: a cast to that type, a user function or a user relation, each already reported. So those extensions do not collide;
     - **types**: the names of user types and domains (`pg_type` outside those two schemas) that collide with a built-in type name, **excluding relation row types (`typrelid <> 0`) and their array types**. A user type whose name is not a built-in name is already not built in by the lists, so it needs no probe;
     - **casts** (third review, R2; final check, F3): the `pg_cast` entries whose `castfunc` is outside `pg_catalog` while both `castsource` and `casttarget` are built-in types (only a superuser can create one). For an explicit cast (`castcontext = 'e'`), the target type's name is not built in for that database. An implicit or assignment cast (`'i'`, `'a'`) can run with no cast and no unqualified name in the text (`pg_catalog.length(42)`, `OPERATOR(pg_catalog.=)`, the type unification of `UNION`, `CASE` and `VALUES`), so while one exists **every catalog-only statement in that database is `*`**, whatever it calls.

     For that database, a colliding function or operator name, and those type names, are **not built in**. A probe that fails, is cut, is stale (below) or has not run yet for the database makes every unqualified call, operator and cast of a catalog-only statement in it `*` (fail closed). With the narrowing above a cut is rare: a probe returns the CVE-2018-1058-style overloads, colliding type names and user-function casts between built-in types, usually none, instead of every relation's row type. The names stay in the agent's memory: never logged, never sent (I2). The rules above follow PostgreSQL's function and operator resolution as documented ("Type Conversion"); the integration test pins them per major version, and a difference is recorded as a refinement.
   - **User casts with a user type.** An implicit cast from a built-in type to a user type is the third case of the function and operator part above. Any other cast to a user type (explicit, or assignment, which function resolution does not apply) is reached only through a value of that type, so through a written cast to a type that is not built in, a user function or a user relation, each reported. Casts between built-in types are the probe's third part.
   - **What is not built in**: functions, operators and types an operator or an extension created in `pg_catalog` after `initdb` are not on the lists, so they are reported (over-reported, never missed). A user function or operator that shares a built-in's name and wins on argument types is covered by the collision probe, up to its refresh (below).
   - **Stale probe on DDL** (third review, R3). When the stream sees a `CREATE`, `CREATE OR REPLACE` or `ALTER` of a `FUNCTION`, `PROCEDURE`, `AGGREGATE`, `OPERATOR`, `TYPE`, `DOMAIN`, `CAST` or `EXTENSION` (and `DROP` of them, which can unmask an overload) in a database, it marks that database's probe stale until a probe that started after that statement completes. On pgaudit this follows log order: a statement logged after the DDL record is analyzed with the probe stale. On `pg_stat_statements` the DDL is seen in the poll that reports it, so the statements of that poll interval may be analyzed before the mark: one poll of lag. The DDL is seen only when the source logs it (pgaudit's `ddl` class; `pg_stat_statements.track_utility = on`).
   - **Between two probes**, a function, operator, type or cast created without the stream seeing its DDL (a source that does not log it, a DDL inside a function body or `DO` block not logged as a substatement, the poll-interval lag on `pg_stat_statements`) and used before the next heartbeat is taken as built in (up to one heartbeat interval; residual). A `search_path` that lists `pg_catalog` after a user schema makes a user object of the same name and argument types win, which the probe covers, since it lists every overload on built-in argument types whatever their exact types.
   - **Out of scope**, left to a follow-up: function calls in statements that also name an application relation (the event names that relation, not what the function read), `dblink` and the other remote-query functions, and the full counterpart of ADR-0045 part (b) for PostgreSQL.
9. **Drift and pinning tests** (integration, engine matrix, every PostgreSQL image, with `pg_stat_statements` created):
   - every relation of `pg_catalog`, `information_schema` and the extension's schema with a column named `query`, `statement`, `query_text`, `current_query`, `ident`, `plan`, or ending in `_query` / `_statement`, and every function of `pg_catalog` and the extension with an `OUT` / `TABLE` argument of those names or whose name matches `pg_stat_get_%activity%`, is listed or on a commented exception list (`pg_prepared_statements`, `pg_cursors`, `pg_backend_memory_contexts` and their functions: the reading session's own; `pg_stat_get_backend_activity_start` and similar: timestamps);
   - every `pg_catalog` function that returns `text`, `bytea` or `setof record` and whose name matches `%file%`, `%slot%`, `%_changes`, `lo\_%` or `%lo_%`, is on the list of decision 7 or on a commented exception list (for example `pg_stat_file`, `pg_ls_*`: metadata; `pg_replication_slot_advance`: no data). The name patterns are a review aid, not a proof: a function outside them is caught only by review;
   - pinning, one assertion each: a role without `pg_read_all_stats` sees `<insufficient privilege>` in another role's `pg_stat_activity.query` and its own texts in clear; `PUBLIC` can read the `pg_stat_statements` view; a utility statement with a literal is kept as sent in `pg_stat_statements` (per version, so that a normalization change is seen); with pgaudit and `pgaudit.log_catalog = off`, whether `SELECT * FROM pg_stat_get_activity(NULL)` is logged (security review Q9); with `pgaudit.log_relation = on`, which relation records a read of `pg_stat_activity` and of a user view over it get (decision 3).
10. **I2.** Only names leave the agent: the fixed names of decision 1 through [ADR-0009](0009-name-normalization-and-item-sanitization.md) normalization (the extension's schema name as probed today), the extension-list names as the text gives them, as for any relation read today, and `*`. No column of these views is read by the analysis, no function name leaves the agent (decisions 7 and 8 use `*`), the agent keeps no statement text beyond what it keeps today, and the `AccessEvent` contract is unchanged: no new field, signal or note.
11. **Readers.**
    - **The agent's role.** `pg_read_all_stats` stays the expected Audit grant (ADR-0012 minimal variant), and `pg_monitor` stays flagged by `privilege.predefined_roles`, as today. When pgaudit is the source (Full or Partial), `pg_read_all_stats` serves only the fallback to `pg_stat_statements` and still exposes every role's texts to whoever holds the agent's credentials: `check()` says so in the agent's local detail, as `privilege.performance_schema_unused` does on MySQL / MariaDB. No new target note in this ADR (open question 5).
    - **Other roles.** `check()` does not report other roles' memberships of `pg_read_all_stats` or `pg_monitor`: it reports on the agent's own account. [05-security.md](../05-security.md#recommended-database-accounts-read-only) gives the catalog query that lists them (open question 6). The events of decisions 2 and 4 do not depend on the reader's privileges: a role that sees only its own role's texts is reported too.

  - Credential- and value-bearing catalogs (`pg_authid`, `pg_shadow`, `pg_user_mappings`, `pg_subscription`, `pg_largeobject`) are read silently: separate ROADMAP follow-up.
  - The server facts of the context table were not run for this ADR; the pinning tests confirm them before the implementation is merged.
## Rejected alternatives

- **Option (a)**, every read reported: the no-text reads of exporters, pools and health checks would each be an always-reported event per principal and window on most targets, for reads that return no statement text. Kept for everything decision 2 cannot prove, and for the extension list.
- **Option (c)**, by reader: the sources do not record the reader's privileges, and a shared application role reads its own sessions' texts with none.
- **Option (d)**, document only: other sessions' literals, passwords and SCRAM verifiers readable with no event.
- **A column test that looks for `query` only** (as ADR-0048 open question 4 rejected): whole-row references (through aliases, unaliased relation and function names, qualified names), column alias lists and natural joins read or compare the text without naming it. Decision 2 refuses each of them, so it proves the absence of text access instead of looking for its presence.
- **A shape exemption for the extension list**: their columns are not verified on any image here, so no proof can be written for them.
- **Every function call in every statement as `*`** (decision 8 without the catalog-only scope, or without a built-in list): `psql`, ORMs and applications call built-ins in most statements.
- **Charging the agent's row budget** for its text query or for other reads of the list: the connector's one text read is matched exactly, and a budget would let a stolen agent credential read up to `limits.max_sample_rows` texts per object and day unseen.
- **Naming the function forms by their own names** (`pg_catalog.pg_stat_get_activity`): two objects for one data set, which policies would both have to name (open question 4).

## Open questions

Each question has the answer this ADR recommends. **Decided on 2026-10-11: the maintainer accepted the recommended answers.** Questions 7 and 8 were decided by the security review of the proposal (PR #204).

1. Scope: is the core list of decision 1 right (`pg_stat_activity`, `pg_stat_get_activity`, `pg_stat_get_backend_activity`, `pg_stat_statements` view and function), with the reading session's own views (`pg_prepared_statements`, `pg_cursors`, `pg_backend_memory_contexts`) left out?
   **Recommended**: yes. The own-session views show what the reading session itself prepared or opened; behind a transaction-mode pooler they can show other clients' prepared texts, which is documented as a residual rather than listed, because every pooled application would then report its own driver's reads.
2. Option (b), the no-text shape quiet for every account, or option (a), every read reported as in ADR-0048?
   **Recommended**: (b). Unlike the statistics catalogs, `pg_stat_activity` is polled every few seconds by exporters, pools and health checks, mostly without the text; the shape refuses every way of reading or comparing `query` without naming it that is known here, and anything it cannot prove is (a).
3. Always report text reads, whatever `min_rows` and `sensitive_objects` say (decision 4), or let the filter apply?
   **Recommended**: always report, as ADR-0045 and ADR-0048 do. One row is one statement with its literals, and the pgaudit log without `log_rows` has no row count.
4. Name the function forms by their view (`pg_catalog.pg_stat_activity`, `<ext>.pg_stat_statements`), by their own names, or as `*`?
   **Recommended**: by their view: one object per data set for policies and baselines, fixed names only (I2).
5. `pg_read_all_stats` held while pgaudit is the source: the agent's local detail only (decision 11), or a new target note mirroring MySQL / MariaDB `privilege.performance_schema_unused` (an addition to `shared/protocol/target-notes.json`, with its console phrase and a security review)?
   **Recommended**: local detail and documentation only in this ADR. The grant is the fallback source ADR-0012 sets in the minimal variant; revisit with a note if operators want the console to show it.
6. Other roles holding `pg_read_all_stats` or `pg_monitor`: a `check()` count note, or documentation only?

## Refinement (2026-10-11): verified server facts and implementation

**Status: items 1 to 6 accepted by the maintainer on 2026-10-11** (items 1 and 2 change what the decisions say; items 3 to 6 are stricter than the text, fail closed, or record facts). **Items 7 and 8 accepted by the maintainer on 2026-10-11** (added after the security review of the implementation, PR #208; both are stricter than the text). Found while implementing part 1 (decisions 1 to 7, 9 to 11; decision 8 is a separate change), on PostgreSQL 16.13 with pgaudit 16.0 (`dev/postgres/local-cluster.sh`) and on the official images of PostgreSQL 14.24, 15.19, 17.11 and 18.6 with `pg_stat_statements` and without pgaudit (the PGDG pgaudit packages could not be fetched here: the egress proxy refuses `apt.postgresql.org` and `deb.debian.org`), so the pgaudit facts below are verified on 16 only and run on the engine matrix in CI.

1. **Decision 7 list: `pg_read_file_old`.** The drift test of decision 9 finds `pg_catalog.pg_read_file_old(text, bigint, bigint)` on PostgreSQL 14, 15 and 16 (the pre-11 C entry point of `pg_read_file`, superuser only; removed in 17, absent on 17.11 and 18.6). It reads server files: it is added to the list of decision 7.
2. **Decision 2: a column alias list on a `VALUES` list of constants is allowed.** `postgres_exporter`'s activity query, which decision 2 says the shape covers, reads `FROM (VALUES ('active'), ('idle'), …) AS tmp(state) CROSS JOIN pg_database LEFT JOIN (SELECT … FROM pg_stat_activity …) AS tmp2`: its `AS tmp(state)` is a column alias list, which decision 2 refuses everywhere. The implementation allows one exception: an alias list on a parenthesized `( VALUES (…), … )` whose rows hold only literals, bound parameters, commas, parentheses and signs (`pg_stat_statements` stores the constants as `$n`). Such rows cannot carry another relation's column; a `VALUES` row with a subquery, a column reference or a function call is still refused. Without it, every `postgres_exporter` poll would be an always-reported event, against the noise estimate of the Consequences and the load harness scenario (zero events).
3. **Range variables also include the aliases of parenthesized joins.** `SELECT row_to_json(j) FROM (pg_stat_activity a CROSS JOIN pg_database d) j` returns every column of both relations, `query` included (verified on 16), with no `*`, no `query` token and no alias of a listed item. The implementation adds every parenthesized join's alias to the range variables of decision 2 (stricter than the text). The join-using alias (`JOIN … USING (pid) AS j`) exposes only the `USING` columns, also as a whole row (`row_to_json(j)` is `{"pid": …}`; verified on 16), so it is not one; `SELECT j.pid … USING (pid) AS j` is quiet.
4. **Decision 3 relation records** (pgaudit 16.0, `log_relation = on`): a read of `pg_stat_activity` gets records of `VIEW pg_catalog.pg_stat_activity`, `TABLE pg_catalog.pg_database` and `TABLE pg_catalog.pg_authid`; a user view over it adds `VIEW public.<view>` in the same substatement; an SQL function's body gets its own substatement, with its own text and records, after a `FUNCTION` record; a read of the extension's view gets a `FUNCTION` record of `public.pg_stat_statements` (substatement 1) and the `VIEW` record (substatement 2); a set-returning function in `FROM` gets no relation record. With `log_catalog = off`, the `pg_catalog` records are left out (a user view over `pg_stat_activity` gets its own record only) and a read of `pg_stat_activity` alone is not logged. **Security review Q9**: with `log_catalog = off`, `SELECT pid FROM pg_stat_get_activity(NULL)` (no relation) **is logged** (so is `SELECT 1`), and is a text read or quiet by its text. The decision 3 rule "a record of a view outside `pg_catalog`" also counts foreign tables.
5. **Other verified facts** (decision 9 pinning, one assertion each, PostgreSQL 14 to 18): a role without `pg_read_all_stats` reads `<insufficient privilege>` in another role's `pg_stat_activity.query` and its own texts in clear; `PUBLIC` reads the `pg_stat_statements` view (`relacl` `=r/postgres`, the function's `EXECUTE` is the default); an `ALTER ROLE … PASSWORD '…'` literal is kept as sent in `pg_stat_statements` on every version (on 16, a `CREATE TABLE … AS SELECT '…'` constant is normalized to `$1`: the "partly normalized from 16 on" of the context table). The drift test of the statement-text columns finds the same set on 14 to 18: the core list, `pg_prepared_statements`, `pg_cursors`, `pg_backend_memory_contexts` and their functions, `pg_stat_get_backend_activity_start`, and `information_schema.triggers.action_statement` (trigger definitions, commented exception). The decision 7 drift finds, beyond the list, only metadata functions (commented exceptions: `pg_current_logfile`, `pg_get_replication_slots`, `pg_hba_file_rules`, `pg_ident_file_mappings`, `pg_ls_replslotdir`, `pg_relation_filepath`, `pg_show_all_file_settings`, `pg_walfile_name`, and `pg_stat_get_replication_slot` on 14).
6. **Analyzer fixes** (`classifiers::query`, needed by the "text decides only on catalogs and listed entries" condition): the first item of a parenthesized join (`FROM (a JOIN b ON …)`) was not named as a relation, on both dialects; and `ROWS FROM (…)` was read as a relation named `rows`. Both are fixed; the first one also names relations that statements of this form read on every source, which were missed before.
7. **A schema-qualified user function next to a listed entry is a text read until decision 8 lands** (security review of PR #208, M1). Part 1 does not implement decision 8, so `SELECT a.pid, public.f() FROM pg_stat_activity a` would be quiet although `f` can read `query` (or another session's text) without the text naming it. Until part 2 is merged, a text that names a core-list entry and calls a schema-qualified function outside `pg_catalog` (and outside the lists of decisions 1 and 7) is a text read: the core-list objects are named and always reported. Unqualified calls are left to decision 8 (they resolve through the `search_path`, which the text does not show). A type modifier written with a qualified type name (`x::app.t(3)`) is over-reported. Part 2 (decision 8) must be merged before the next release that contains part 1 (release gate in the ROADMAP and [RELEASE.md § 7](../../RELEASE.md#7-pre-release-checklist)).
8. **The end of a closed `pg_stat_statements` period is shortened by a skew tolerance of 5 s** (decision 5; security review of PR #208, L2). pgaudit record times are the server's log clock; the period's start and end are the agent's clock. A closed period now ends at the stream's stop plus the statement timeout, less 5 s (never before its start), so a server clock behind the agent's by up to 5 s does not extend the quiet window after the stream stopped. Residual: a skew beyond 5 s in that direction still widens the window by the excess; a skew in the other direction makes the agent's last text queries of a period reported (loud, never quiet). The server offset is not measured.

## Refinement (2026-10-11, part 2): decision 8 as implemented

**Status: accepted by the maintainer on 2026-10-11** (items 9 to 19, found while implementing decision 8 on PostgreSQL 16.13 with pgaudit 16.0, `dev/postgres/local-cluster.sh`, and on the official engine-matrix images of PostgreSQL 14.24, 15.19, 17.11 and 18.6 with `pg_stat_statements`; every server fact below is pinned by `it_user_code.rs` and was run on each of them, except the `strpos(42, 'a')` example of item 10, verified on 16.13 and pinned for the engine matrix). Items 10, 11, 12 and 14 change what decision 8 says or adds to it; the others record facts, are stricter than the text, or fail closed.

9. **The built-in lists.** Four lists per major version, not three: function names (`pg_proc` of `pg_catalog`, and `information_schema.<name>` for the functions of `information_schema`), operator symbols, type names (with `information_schema.<name>`), and the keywords with their category (`pg_get_keywords()`), generated by `builtins/generate.sh` from the engine-matrix image of each major (14.24, 15.19, 16.15, 17.11, 18.6, recorded by digest in each file). The keyword list replaces a hand-written list of the grammar's parenthesized forms: an unquoted reserved or column-name keyword before `(` is grammar (`IN (`, `VALUES (`, `COALESCE (`, `numeric (`), unless it is also a `pg_proc` name of that version (`SUBSTRING`, `OVERLAY`, `POSITION`, `NORMALIZE`, `EXTRACT`…, decided as calls); a type-or-function-name keyword right after an operand is infix syntax (`x LIKE (…)`, `a JOIN (…)`); the SQL type spellings (`integer`, `double precision`, `character varying`, `json` from 16 on…) always mean `pg_catalog` types. A call of `information_schema.<function>` or a cast to `information_schema.<type>` on the lists is built in (pgJDBC's `information_schema._pg_expandarray` next to catalogs); `XMLTABLE` and `JSON_TABLE` declare column types the scan does not read and are always `*`; a `VARIADIC` user overload of a built-in name always collides. The drift test passes both ways on 14.24, 15.19, 16.13 (against the lists of 16.15: re-review N5 holds), 17.11 and 18.6.
10. **Literal resolution, as the servers do it (F2 corrected).** An untyped literal reaches a user type only through PostgreSQL's category rules: with `public.abs(myenum)` (category `E`), `abs('5')` fails with "function abs(unknown) is not unique" (42725) instead of reaching it; with a string-category type it does. The per-position test of F2 is also not enough for overloads of several arguments, where an exact match on another argument favours the user overload (`strpos(42, 'a')` reaches `public.strpos(integer, myenum)` rather than failing on the built-in `strpos(text, text)`). The probe therefore asks, for each argument count the overload accepts (`pronargs - pronargdefaults` to `pronargs`), whether a built-in overload of the same name that accepts that count survives PostgreSQL's resolution whenever the user overload does: the same type at every position where the user type is reachable from a built-in value, and where it is not, a preferred string type (`text`) or a type of the same category at least as preferred. Without such a built-in overload the name collides. Reachable from a built-in value also covers composite types (`ROW(…)` coerces to any composite type, relation row types included) and arrays of reachable types, besides F1's domains and implicit-cast targets. This reports `abs` for the enum case too (over-reported), and keeps `citext` quiet (`lower`, `=`, `~~` and the others have a `text` co-candidate).
11. **hstore's `->` collides.** `'a=>1' -> ARRAY['a']` resolves to `->(hstore, text[])` on 14 to 18 (no built-in `->` takes `text[]` on the right), so `->` is not built in, unqualified, in a database with hstore installed; nothing else of hstore or citext collides (verified with both installed and 3 000 relations, the probe not cut). Decision 8 said these extensions do not collide.
12. **Bound parameters** (not in decision 8; amended after the security review of PR #211, M1). A client types a `$n` itself (extended protocol), so a parameter reaches a user overload of any argument types with no cast in the text. With a parameter in the text (on `pg_stat_statements`, every constant is a `$n` too), a name that has a user overload whose code is neither C nor internal (an aggregate: any support function) is not built in. citext's SQL-language wrappers (`regexp_match`, `regexp_matches`, `regexp_replace`, `regexp_split_to_array`, `regexp_split_to_table`, `replace`, `split_part`, `strpos`, `translate`) are such overloads, so these unqualified names with a parameter or constant next to catalogs only are `*` in a citext database. **A parameter typed as a user domain** runs the domain's `CHECK` with no cast in the text: the probe also reports whether the database has a user domain with a constraint that depends on a function or operator outside `pg_catalog` whose code is neither C nor internal, and there every catalog-only statement with a parameter is `*`, except one that is exactly one of the connector's own statements from the agent's identity (pgaudit: the text as sent, the agent's account, `application_name` and client address; `pg_stat_statements`: the stored text equal to the statement's `pss_form`, from the agent's role, top level, in a declared database). Residuals: a `CHECK` that calls a `pg_catalog` function directly (`query_to_xml(…)`) is not seen, since PostgreSQL records no dependency on the objects initdb creates; PostgreSQL 18's `pg_stat_statements` stores an `ARRAY[…]` or `IN (…)` list of two or more constants or parameters as one `$n /*, ... */` (verified on 18.6: `ALL (ARRAY['pg_catalog', 'information_schema', 'pg_toast']::pg_catalog.name[])` is stored as `ALL (ARRAY[$1 /*, ... */]::pg_catalog.name[])`), so a connector statement with such a list no longer equals its `pss_form` there, and was reported as the agent's read of `*` in such a database (found by the engine matrix on PR #211); the connector's statements therefore hold no such list (an array is one literal, `'{r,p,m}'::pg_catalog."char"[]`, a single constant on every major), a unit test fails on any list a later statement adds, and the exact-text match is unchanged. On `pg_stat_statements` the own exemption is not pinned to a `queryid` (the text, role, top level and database are matched, not the `queryid` the connector's own statement got first), so a holder of the agent's credentials could replay one of the connector's statements with a parameter typed as the checked domain and be spared; this needs both the stolen credential and a checked domain (re-review of PR #211).
13. **Operators the grammar implies.** `LIKE`, `ILIKE`, `SIMILAR TO`, `BETWEEN`, `IN`, `NOT IN`, `IS [NOT] DISTINCT FROM`, a simple `CASE x WHEN`, `NULLIF`, `JOIN … USING (…)` and `NATURAL` look up their operators through the search path: they count as unqualified operators (`~~`, `!~~`, `~~*`, `!~~*`, `~`, `!~`, `>=`, `<=`, `<`, `>`, `=`, `<>`). Operator tokens are split as PostgreSQL's lexer does (`=-1` is `=` then `-`), and `!=` is `<>`; `ORDER BY … USING <op>`, in a query or an aggregate, names its operator (unit tests with a colliding `=`, `<>`, `<` and `>` for each form, security review of PR #211, L3). A function-style cast (`text(42)`) does not reach a user cast function (only binary-coercible and I/O coercions; verified), so it needs no rule of its own.
14. **States of the probe.** A probe that failed, was cut (more than 20 000 rows, or a name not UTF-8), is older than 15 minutes (three of the longest heartbeat intervals), is stale or has not run yet: every unqualified call, operator (implied ones included) and cast of a catalog-only statement is `*`, and qualified `pg_catalog` or `information_schema` names on the lists are kept, as the decision says; before the first probe the server's version is not known, so only what holds on every list counts. A known implicit or assignment user-function cast between built-in types (F3) makes every catalog-only statement of that database `*`, the agent's own included. A `UNION` of `text` and `integer` is still refused under an implicit cast `integer → text` (the types' categories differ; verified): the F3 rule is kept as written. **A database the target does not declare is never probed**: a pgaudit log or `pg_stat_statements` covers every database of the server, and catalog-only statements with unqualified calls, operators or casts in an undeclared database (a monitoring tool connected to `postgres`) are `*`; declare the databases such tools use.
15. **Stale marking as implemented.** The stream marks a database stale on pgaudit DDL records of `CREATE`, `ALTER` or `DROP` of a function, procedure, routine, aggregate, operator (class and family included), type, domain, cast or extension, on `DROP OWNED`, `DROP SCHEMA` and any `DROP … CASCADE` (by command tag, and by text for the last one), and, on `pg_stat_statements`, on the same statements found by their text (a `DO` body included). The mark is the agent's time when the stream reads the statement, and it is cleared once two probes that both started after it have been stored (amended after the security review of PR #211, L1: one probe can still race the DDL's commit): a heartbeat that probes before the stream has read the DDL does not count (over-report, never a miss). On `pg_stat_statements` a DDL marks its database before any statement of the same poll is judged (the order within a poll is not known): there is no poll of lag, and statements polled together with it are judged stale. A DDL in a transaction left open is visible to other sessions only at its commit: if both probes after the mark start before the commit, the object is taken as built in by other sessions until the next heartbeat (residual, as between two probes).
16. **The connector's own statements never trigger decision 8** (decision 5). Every operator of the connector's SQL is written `OPERATOR(pg_catalog.…)`, and `IN`, `NOT IN` and `NOT LIKE` became `OPERATOR(pg_catalog.=) ANY (ARRAY[…])`, `OPERATOR(pg_catalog.<>) ALL (…)` and `OPERATOR(pg_catalog.!~~)`, as `psql` writes its describe queries: a unit test checks every connector statement on the lists of every major version, with every name it uses colliding and with the probe unknown, and with a checked user domain (a parameterized connector statement is then spared only by its exact text, item 12). Every connector statement also stays under the 8 192-character `pg_stat_statements` read bound (a cut text is `*`), and orders or groups by name rather than by position (`pg_stat_statements` keeps `ORDER BY 2` while `pss_form` would replace it); both are unit tests. The agent's session also sets `search_path = ''`, but the text does not show it. **R2 as written** makes the target name of an explicit user-function cast between built-in types not built in whatever the source type, so in a database with an explicit user cast to `text` the connector's own casts to `pg_catalog.text` (of `name` and `pg_node_tree`, which have built-in casts a user cannot replace) are reported (loud; only a superuser can create such a cast).
17. **Item 7 is kept, as defence in depth.** With decision 8, a schema-qualified call outside `pg_catalog` in a statement whose relations are catalogs and core-list entries read in the no-text shape is `*` whatever the probe says; item 7 still makes such a statement a text read naming the core-list view, which tells the reader what the function could reach, and it applies to the text alone.
18. **Cost of the probe.** One statement per declared database and heartbeat, from catalogs every role can read, its plan independent of the number of relations: 11 to 35 ms on PostgreSQL 16 with `citext`, `hstore` and 3 000 relations (median 24 ms over 10 runs in the integration test). Its argument positions come from constant series (a function has at most 100 arguments) and `pg_catalog` is written as its oid, `'11'` (pinned by the facts test), constants that keep the planner's estimate under the default `jit_above_cost`: with an estimate above it, JIT compilation took the probe to 160 ms, and with an estimate above `jit_optimize_above_cost`, to about 2 s. The text is 7 758 characters, under the `pg_stat_statements` read bound.
19. **Statements that wrap a query** (security review of PR #211, H1). `PREPARE p AS <query>` (pgaudit logs it for every `EXECUTE`), `EXPLAIN [ANALYZE] [(…)] <query>` (plain `EXPLAIN` too: the planner folds immutable and stable calls), `DECLARE c … CURSOR … FOR <query>`, `CREATE [TEMP] TABLE … AS <query>` and `CREATE MATERIALIZED VIEW … AS <query>` run the code of their query; pgaudit logs them as `READ` records naming the query's relations (verified on 16.13 with pgaudit 16.0), plus a `DDL` record for a `CREATE … AS`. Decision 8 applies to every statement of a catalog-only text, whatever its kind: the scan starts at the wrapped query (after `AS`, after `FOR`, after `EXPLAIN` and its options; a `PREPARE`'s parameter types are type positions), `COPY` of a relation is not scanned, and any other statement is scanned whole (fail closed); the `*` is added in every action class (a `CREATE … AS` gets it on its `DDL` event too), and on `pg_stat_statements` a statement of no read or write kind (`EXPLAIN`, `PREPARE`, `DECLARE`) that runs user code is a read of `*`. A `DO` body is still not scanned (its statements are logged on their own on pgaudit; on `pg_stat_statements` a `DO` gives no event, an existing residual). CTEs of a wrapped query are recognized as for a bare query (re-review of PR #211, R-M1): the analyzer skips the same prefixes (`EXPLAIN` and its options, `PREPARE … AS`, `DECLARE … FOR`, `CREATE … AS`) before collecting `WITH` names, so `DECLARE c CURSOR FOR WITH x AS (…) SELECT … FROM pg_catalog.pg_class, x` names no relation `x` and stays catalog-only; MySQL / MariaDB naming is unchanged (the MySQL path already extracts the query of `EXPLAIN` and `CREATE … AS` before naming relations).
