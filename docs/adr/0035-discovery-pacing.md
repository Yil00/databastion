# ADR-0035: Discovery pacing to a bounded duty cycle per scan

- **Status**: Proposed
- **Date**: 2026-09-30
- **Context references**: ROADMAP phase 7 "Load / database impact tests"; the load harness of #92 ([e2e/load/README.md](../../e2e/load/README.md)); PR #93 (commits `3c2a0e9`, `3184023`, `af2553d`, `8acb570`, `9fd0472`) and its security review (M3, L1, L5, L6, R1, R2, R3); PR #94 (console lease of queued scans, default scan budget); `agent/crates/core/src/pacing.rs`, `agent/crates/core/src/job.rs` (`ScanJob::paced`, `ScanJob::turn`, `ScanJob::rotate`), `agent/crates/core/src/runtime.rs` (scan worker), `agent/crates/core/src/config.rs`, `console/src/server/jobs.ts`, `console/src/server/scans.ts`; [agent/README.md](../../agent/README.md)

## Context
The MVP criterion in [04-mvp-scope.md](../04-mvp-scope.md) is "impact on the monitored database < 2 % CPU during Discovery". It is read literally, per scan: the share of the server's CPU that the agent adds while a scan runs. It is not relaxed to an average over a longer window.

Sampling was already bounded per object (rows, bytes, statement timeout), but objects were sampled back to back. The #92 harness measured 20 to 25 % of one database core while a scan ran: about 1.5 ms of database CPU per object for 7 to 8 ms of scan time per object. Bounding each query does not bound the scan's share of the server's time; only the time between queries does.

A first version of the pacing paused after each unit of work. Its security review found that a slow or timed-out unit then pushed the rest of the scan past its deadline, at every scan since the object order was fixed, and that the final pause could turn a complete scan into a `timeout` (M3, L1).

## Decision
1. **The core paces every connector's Discovery, as a debt.** Each unit of work against the target (an object's sampling, a catalog read or a listing) runs through `ScanJob::paced`, which charges `busy × (100 − d) / d`, rounded up. `busy` is the agent's wall-clock time for that unit; failed and timed-out units are charged too. The debt is paid **before the next unit**, never after the last one: `ScanJob::turn` pays it ahead of a unit's session check or reconnection. A scan uses one connection and a statement runs on one server core, so `busy` bounds the database CPU the unit used on that connection. The agent's time in queries is then at most `d` % of the scan's time, so a scan costs the server at most `d` % of one core. Every connector (PostgreSQL, MySQL / MariaDB, MongoDB, OpenLDAP) goes through it; none paces itself.
2. **`d` is `limits.discovery_duty_cycle_percent`** in `agent.yaml`: default 1, range 1 to 100, `100` disables pacing. It is a local limit: the console cannot set or raise it. The default of 1 % keeps a one-core server under the 2 % criterion, with margin for what is not paced.
3. **The bound is never relaxed to meet the deadline.** When the debt, plus the last unit's time and a 2 s margin, would reach the scan's deadline, the next unit does not run. The connector reports the objects left as `skipped_limit` in the scan's coverage (no protocol change), and the scan **succeeds**. A database (PostgreSQL, MongoDB), a naming context (OpenLDAP) or a whole MySQL / MariaDB target left out before its introspection counts as **1** in `skipped_limit`: its objects are unknown without the query the scan has no time for. When the console does not take the coverage counters (no `job_progress.coverage` capability, or capabilities forgotten after a `400`), a plain `succeeded` would hide what the scan left out, so the agent reports such a scan `failed` with `timeout` (a code of the contract's `FailureCode` set).
4. **The order is rotated per scan, at two levels.** With a seed derived from the job id (`ScanJob::rotate`), each scan first rotates its outer list, the databases (PostgreSQL, MongoDB) or naming contexts (OpenLDAP), then the objects inside each (OpenLDAP rotates its containers at a boundary between normalized names). A slow or hostile object cannot hide the same tail, or the same later databases or suffixes, at every scan.
5. **Scans run one at a time per agent** (the scan worker), so the scans of several targets on one server cannot add up.
6. **Resources are released before a pause.** Connectors release what a unit held (a poisoned session, the samples) before paying the debt. The MySQL / MariaDB connector closes its idle session when the debt reaches its 45 s staleness bound. A session idle through a long pause is replaced before the next unit: MongoDB and OpenLDAP after a pause of more than 60 s, MySQL / MariaDB after 45 s. The PostgreSQL connector keeps its idle session (no transaction open).
7. **Pauses are cancellable.** The core gives each scan a cancel token, fired when the scan stops (end of its window, suspension after a revocation, agent shutdown) and when it is dropped. A pause selects on it; the paced call then returns `Cancelled` and the connector returns `ConnectorError::Cancelled`.
8. **The agent acknowledges a scan with `running` before it starts it** (contract `pollJobs`: a delivered job without a status is delivered again after the 120 s lease, and the console gives it up after 5 deliveries). When the console refuses that status with `404` or `409` (the job was cancelled, expired or timed out meanwhile, or is not the agent's), the scan does not run and nothing more is reported for it.
9. **The console keeps queued scans and budgets for paced scans (#94).**
   - A queued `discovery.scan` of an online agent (last heartbeat less than 90 s ago) is still delivered again every lease, but it is not given up after 5 deliveries while `now < first_delivered_at + max_duration_s + 600 s`.
   - Every scan deadline and the findings window are anchored on `first_delivered_at`, which a redelivery never moves. An agent that delays its `running` acknowledgement therefore cannot extend them.
   - A `max_duration_s` that is not a plain integer falls back to 900 s (the contract default).
   - The console's default `max_duration_s` is 3600 s, against the contract's 900 s (no contract change). The agent still clamps it to `limits.max_scan_duration_s` (default 3600 s).

## Consequences
- A scan takes about `100 / d` times its query time. Measured on MariaDB 11.4 with 200 tables (debug build): 120 s and 0.35 % of one core paced, against 6.6 s and 5.4 % unpaced. The #92 load job on #93 (`b4aa999`, pgaudit) measured a Discovery impact of 0.30 % on MariaDB, 0.28 % on MongoDB and about 0 % on PostgreSQL.
- A database too large for its scan budget is not scanned in full: the scan succeeds, and the objects left are reported as `skipped_limit` (a database, suffix or MySQL / MariaDB target not reached counts as 1, so the counter underestimates the objects left). The console (PR #95, pending) flags succeeded scans with actionable gaps as "partial coverage"; on a console without the coverage counters, such a scan shows as `failed` / `timeout`. At 1 %, the 3600 s default covers about 36 s of query time (some 7 000 objects at 5 ms). The remedy is a larger `max_duration_s` and `limits.max_scan_duration_s`, or a higher `d` where the server has spare cores. Thanks to the rotation, successive scans skip different objects.
- The bound is conservative: latency (network, I/O and lock waits) counts as busy time, so a slow link or a busy server lengthens the pauses without adding database CPU.
- Not paced: connection setup (once per scan or database), and the reconnections after long pauses (decision 6: at most a handful per scan with pauses that long; security review of #93, L6).
- Residual: PostgreSQL parallel query workers are not disabled for the scan's connection. A sampling query that the planner runs in parallel can use more than one core during its `busy` time, so on PostgreSQL the bound is per connection, not strictly per core.
- A running scan is not delivered again after an agent restart: it has a `running` status. The console marks it `failed` (`timeout`) once `first_delivered_at + max_duration_s + 1 h` has passed (swept when the next scan of that agent is requested).
- A queued scan counts its queue time in its `max_duration_s` window (docs/09, "Scan worker"). A scan queued behind a long one therefore has less budget left, and more of its objects may end as `skipped_limit`.
- **Upgrade.** Per [ADR-0022](0022-protocol-capability-negotiation.md), a console serves agents of several versions (a console `X.Y` accepts agents `X.Y` and `X.(Y-1)`, [RELEASE.md](../../RELEASE.md#compatibility)). The 3600 s console default assumes agents that pace Discovery: an agent that did not pace would hold its target for longer than before under that default. No agent without pacing has been released, so upgrading the console and the agents together is recommended for 0.1.0 (the user guide already asks for it for 0.1.0, for the heartbeat decoding of pre-#60 agents: [10-user-guide.md](../10-user-guide.md#12-upgrading)). ADR-0022 itself does not require it.
- The end of a scan logs its busy and paused time and whether it ran out of time (`scan pacing`).

## Rejected alternatives
- **A per-minute average criterion.** A short unpaced scan spread over one minute is about 0.5 % (#92), but the server still runs at 20 to 25 % of a core while the scan lasts. That reading relaxes the MVP criterion instead of meeting it.
- **Server-side CPU accounting** (reading the engine's own statement or session CPU statistics). No engine exposes it uniformly, some need extra privileges (against I4), and some would count other clients too. The agent's wall-clock time is available on every engine and is an upper bound.
- **Adapting the pause to the remaining budget** (pausing less so the scan finishes within `max_duration_s`). The database impact would then depend on the scan budget and on the database size, and the criterion would no longer hold for large databases. Decision 3 stops the scan instead and reports what it skipped.
- **Capping individual pauses.** A long unit of work (a large sample, a slow catalog read) would then be followed by too short a pause, and the duty cycle would be exceeded exactly on the heaviest objects.
- **Pausing after each unit** (the first version). A slow unit's pause holds the unit's session and samples, the final pause adds time after the work is done, and a timed-out unit can push the scan into `timeout`. The debt paid before the next unit avoids all three.
