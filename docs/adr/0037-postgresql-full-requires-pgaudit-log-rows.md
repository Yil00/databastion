# ADR-0037: PostgreSQL Full audit level requires `pgaudit.log_rows`

- **Status**: Accepted
- **Date**: 2026-10-03
- **Refines**: [ADR-0015](0015-postgresql-connector-decisions.md) (which stays Accepted), decision 4 (audit levels), as implemented by P4-A (#58) and [docs/08](../08-engine-capabilities.md#postgresql-audit)
- **Context references**: security review M1 of #121; ROADMAP v0.1.x item (l); `agent/crates/connector-postgres/src/check.rs` (`AuditProbe::level`, `pgaudit_rows_on`), `agent/crates/connector-postgres/src/audit/mod.rs` (`source_for`, `audit_stream`); [ADR-0012](0012-postgresql-agent-grants.md)

## Context
ADR-0015 decision 4 withheld Full until P4-A. P4-A (#58) then defined Full in [docs/08](../08-engine-capabilities.md#postgresql-audit): the pgaudit log declared in `agent.yaml` is readable, pgaudit is loaded with the `read` class, a pgaudit record was parsed in the last 24 h, and "a volume source exists": `pgaudit.log_rows = on`, **or** `pg_stat_statements` usable by the agent (the Limited prerequisites). In code, `AuditProbe::level` granted Full with `pgaudit_reads && (pgaudit_rows || limited)`.

The stream does not match that rule. At Full and Partial, `source_for` picks the pgaudit log, and the `pg_stat_statements` poller is dropped: the agent reads one source at a time. With pgaudit loaded but without row counts (`pgaudit.log_rows = off`, or pgaudit before 1.6, where the setting does not exist and #121 proves it through `pg_settings`), a server with `pg_stat_statements` was reported Full. Yet no event carried a row count, so `volume.large_result` and every `volume.*` policy of the console could never fire on that target. The console showed Full for a source that misses the volume, which [docs/08](../08-engine-capabilities.md) defines as Partial ("some information is missing (volume, exact object)"). This is an honesty bug in `check()`, recorded as M1 by the security review of #121; it existed since P4-A.

## Decision
1. **Full requires the row counts of the source the Full stream reads.** On PostgreSQL that source is the pgaudit log, so Full requires `pgaudit.log_rows` proven on (`pgaudit_rows_on`: the library loaded, the setting defined as a boolean in `pg_settings`, its value `on` in the agent's session of a monitored database, #121). `pg_stat_statements` no longer counts as a volume source for Full. `AuditProbe::level` becomes:
   - **Full**: log readable, pgaudit loaded, `read` class, `pgaudit.log_rows` on (and, as before, a pgaudit record parsed in the last 24 h, otherwise Partial with `audit.full_pending_first_record`);
   - **Partial**: log readable, pgaudit loaded, and the `read` class without `log_rows`, or object audit only (`pgaudit.role`);
   - **Limited**: no usable pgaudit log, `pg_stat_statements` usable;
   - **None** otherwise.
2. **Partial with pgaudit still reads the pgaudit log** (`source_for(Partial)` is unchanged). Its events keep the principal, client address, application, objects and the `signature.*` / `shape.*` signals; they carry no row count, so `volume.large_result` is absent. The agent's own reads with unknown rows are still charged the whole per-object budget (docs/08, "The agent's own account").
3. **No new protocol note.** The registered `audit.log_without_row_counts` note does not list PostgreSQL, and `shared/protocol/` is not changed by this decision. The reason is given in the local `check()` detail (agent log) and documented in docs/08. Adding `postgres` to that note's engines is a compatible, append-only registry change left as a follow-up.
4. **One database without row counts caps the target at Partial.** The target's level stays the best level over its monitored databases for every other condition, but Full also requires that no monitored database has pgaudit logging reads without row counts: one such database (for example after `ALTER DATABASE … SET pgaudit.log_rows = off`) caps the target at Partial, and the local detail names it (normalized name). A monitored database whose pgaudit settings could not be read caps it too (fail closed). This needs no new catalog read: each monitored database is already probed in its own session (#123 security review L2).

## Consequences
- **Upgrade impact.** A server with pgaudit logging reads, `pg_stat_statements`, and `pgaudit.log_rows` off (or pgaudit before 1.6) reported Full and now reports **Partial** after the agent upgrade. Nothing else changes for it: same source, same events. To get Full back, set `pgaudit.log_rows = on` (pgaudit 1.6+, PostgreSQL 14+) for the monitored databases. Servers that already have `log_rows` on keep Full.
- The console level now matches what `volume.*` policies can see: a Full PostgreSQL target always has row counts in its events.
- A server with pgaudit without `log_rows` and `pg_stat_statements` gets per-statement attribution (pgaudit, Partial) but no volumes, while the `pg_stat_statements` mode alone (Limited) would have volumes per role and poll. The agent keeps preferring pgaudit, as before; the operator turns `log_rows` on to have both.
- The dev environment (`dev/docker-compose.yml`, `dev/postgres/local-cluster.sh`) and the end-to-end target (`e2e/target-initdb/30-audit.sh`) set `pgaudit.log_rows = on`, so they still reach Full. The end-to-end test accepts Partial or Full; the connector integration test asserts Full only when `log_rows` is on in the monitored database, Partial otherwise.

### Residual risks
- **Databases not monitored.** Decision 4 covers the declared databases only: a database the target does not monitor is not probed, as for every other condition (I5).
- **Session view.** Like every setting the probe reads, `log_rows` is read in the agent's session: an `ALTER ROLE … SET pgaudit.log_rows = off` for other roles is not visible to the agent, and their records carry no row count while the target reports Full. Changing `pgaudit.log_rows` per role or per database needs a superuser (or, on PostgreSQL 15+, a `GRANT SET` on it), who can turn pgaudit off altogether. Reading `pg_db_role_setting` to see such overrides is not done: [ADR-0012](0012-postgresql-agent-grants.md) forbids reading its `setconfig`, which can hold secrets.

## Rejected alternatives
- **Option B: poll `pg_stat_statements` volumes alongside the pgaudit stream** (keep Full with `pg_stat_statements` as the volume source, and make the stream read it). Rejected for now:
  - new concurrent query load on the monitored database, on top of the pgaudit log reading, against the < 2 % impact criterion ([ADR-0035](0035-discovery-pacing.md) and the load measurements of docs/08) and the one Audit connection at a time of [ADR-0025](0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) decision 11;
  - two sources of different granularity (per normalized statement text, role and poll interval for `pg_stat_statements`; per record, with client and application, for pgaudit): correlating them, or adding a volume to the right pgaudit event, is not reliable, and reporting both double-counts the same reads in the console's volume × sensitivity score and baselines;
  - more attack and failure surface (a second parser and state machine on the Full path, eviction between polls, `track_utility`), for a gap the operator closes with one setting.

  It can be revisited by a new ADR if servers without `pgaudit.log_rows` turn out to be common.
- **Keep the rule and document it**: the console would keep showing Full for targets where `volume.*` policies cannot fire, against the docs/08 rule that a degraded audit never passes for a full one.

## Refinement (2026-10-10, phase 8 follow-ups)
- **Row counts and the own-account budget** (security reviews of #196 and #197). The engine-agnostic own-account rule of [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md#refinement-2026-10-10-phase-8-follow-ups) (refinement of decision 6) applies here too: every read with the agent's identity is charged at least one row, aggregates `max(r, 1) + n - 1`, and budget keys ignore case.

## Refinement (2026-10-12, accepted): failed and cancelled statements

**Status: accepted by the maintainer on 2026-10-12**, as amended after the security review of PR #213 (A1, A2, F1; ROADMAP [phase 8 follow-ups](../ROADMAP.md#phase-8-follow-ups), lot F; security review of #197, L1). Implemented by `feat/p8-pg-failed-reads` (the integration test `it_wrapped::failed_reads_and_what_is_reported` of `fix/p8-pg-followups` now asserts the events; implementation notes and proposed items 9 to 11 in the [refinement below](#refinement-2026-10-12-proposed-implementation-of-the-failed-and-cancelled-statements)). It mirrors, for PostgreSQL, the failed-read rules of MySQL / MariaDB (#196, [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md#refinement-2026-10-10-phase-8-follow-ups)) and MongoDB ([ADR-0027 refinement of 2026-10-11](0027-mongodb-audit.md#refinement-2026-10-11-accepted-207)), but it needs a record type the connector does not read today, so it is a decision of its own.

- **Context** (verified on PostgreSQL 16.13 with pgaudit 16.0, the local cluster of `dev/postgres/local-cluster.sh`; integration test on every pgaudit log format and `pg_stat_statements`):
  - **With `pgaudit.log_rows = on`** (decision 1: needed for Full), pgaudit writes a statement's records when the statement ends, with its row count. **A statement that fails or is cancelled leaves no `AUDIT:` record.** Seen for a failed cast whose error quotes the value read (`SELECT email::integer FROM … WHERE id = 1`: SQLSTATE 22P02, `invalid input syntax for type integer: "<the address>"`), for a read that streams 59 of its 60 rows to the client and then fails on purpose on the last one (`CASE WHEN id = 60 THEN 1 / (id - 60) END`: 22012; a client reading the extended protocol's rows as they come received the 59 rows), and for a read cancelled by `statement_timeout` after rows were produced (57014). So, at Full, **any read that ends in an error or a cancel is invisible**, from every role, the agent's included: a value walk through error messages, and a whole table read that ends with a deliberate error or a timeout (a client cancel takes the same path; not run).
  - **With `pgaudit.log_rows = off`** (Partial), the record is written when the statement starts: the failed read is reported, with no row count.
  - The server writes an **`ERROR` line** for each of them (jsonlog `error_severity`, `state_code`, `message`, `statement`; csvlog the same columns), with the user, database, application, client address and session. Its `message` can quote the value read (22P02 quotes it; 23505's `detail` quotes a key; a PL/pgSQL `RAISE` can say anything). The `statement` field holds the statement text when `log_min_error_statement` is `error` or lower (the default).
  - **`pg_stat_statements` counts no failed statement**: no entry, no event, on that source, for any role.
- **Decision** (amended after the security review of PR #213: A1, A2, and the level).
  1. **A second record type in the pgaudit log.** When pgaudit is the source (Full or Partial), the connector also parses the server log's `ERROR` and `FATAL` lines, from the same file, cursor and tailer. It reads only the severity, the SQLSTATE, the user, database, application, client address, session id, time, and the statement text (`statement` in jsonlog, `query` in csvlog), analyzed locally as pgaudit's texts are.
  2. **I2: how the lines are parsed** (a requirement on the implementation). The fields that can quote values are **never copied, kept, logged or sent**: in jsonlog, `message`, `detail`, `hint`, `context` and `internal_query` are skipped without being copied (deserialized as `serde::de::IgnoredAny`, as the MongoDB server-log reader does); in csvlog, those columns are skipped inside the zeroized tailer buffer, never copied out of it. The statement text is never logged (as for `AUDIT:` records). A unit test feeds a jsonlog and a csvlog line whose message, detail, hint, context and internal query quote a marked value, and asserts that the value appears in no event, no log line and no state the connector keeps.
  3. **Classes by SQLSTATE only**, as MongoDB's `errCode`, never the message. PostgreSQL raises many codes at run time, per row, after rows were sent (security review A1): `(… || 'x()')::regprocedure` raises 42883, `::regclass` 42P01, `::regnamespace` 3F000, `currval`, `nextval`, `setval` and `lo_get` without privilege 42501; and a user function can raise any SQLSTATE (`RAISE … USING ERRCODE`). So:
     - **Refused** (no event), only: `25P02` (a statement rejected before parsing in an aborted transaction) **when the line has no `context` field**, and connection-level `28xxx` / `3D000` lines that carry no statement text. Optionally, `42601` (syntax error) when the statement text does not lex as a complete statement, also only **without a `context` field**. **Nothing is refused when the text calls a function that is not built in** (ADR-0049 decision 8's lists and collision probe), whatever the code.
     - **Why the context** (security review of PR #213, F1): a user function can `RAISE … USING ERRCODE = '25P02'` (or `'42601'`) after rows were sent, through code the text does not show: a view that calls it, a row-level security policy function, a user operator or cast, or a domain `CHECK`, next to an application table. A genuine `25P02` is raised by the server before parsing, so its line has no context; a PL/pgSQL `RAISE` always carries one. Only the **presence** of the field is tested: its value is skipped without being copied, as item 2 requires (jsonlog: the key is seen, its value read as `IgnoredAny`; csvlog: the column is tested for emptiness inside the zeroized buffer). A line with a context is classed by item 3's other rules (quiet or telling), never refused.
     - **Required tests** for the implementation: a `25P02` (and a `42601`) raised with `RAISE … USING ERRCODE` after rows were sent, from a function called through a view, through a row-level security policy, through a user operator, through a user cast and through a domain `CHECK`, each next to an application table: reported (always reported, the relations named or `*`), from another role and from the agent's role; and a genuine `25P02` (a statement sent in an aborted transaction) and a genuine `42601`: no event.
     - **Quiet** (the code says nothing of a value, but rows may have been sent first): every other code of classes `42`, `3F`, `0A` and `25`, and `57014` (`statement_timeout`, a client's cancel), `57P01` to `57P05`, `40001`, `40P01`, `55P03`, classes `53`, `54`, `08` (`08006` "connection to client lost", below), `58`. A read of the statement's relations (or `*`) with **no row count, always reported** (otherwise a `min_rows` setting would drop it, and a cancel or a run-time class `42` error would replace a deliberate error as the way to read unseen); from the agent's identity, a read charged the whole budget like an unknown row count (the agent cancels its own sampling statements at the byte budget), not left out otherwise.
     - **Telling**, every other code and an unknown one (fail closed): classes `22`, `23`, `27`, `44`, `P0`, `XX`, `2F`, `38`, `39`, … Reads, DDL and writes that read (`UPDATE`, `DELETE`, `INSERT … SELECT`, `MERGE`) are always reported and never the agent's own; a failed plain `INSERT … VALUES` is an ordinary write event under the filters (its message quotes only its own values; a `23505` is an existence oracle, the MongoDB `11000` residual).
  4. **Not twice.** A line is not reported when the same session's last `AUDIT:` record before it, in log order, has the same statement text and **no row count field**: that record was written at the statement's start (`log_rows = off` for that role) and already reported the access. A record with a row count was written at the end of an earlier statement. The `LOG` "could not send data to client" line (08006) that comes before the `FATAL` "connection to client lost" line of the same statement is not reported on its own.
  5. **Without a statement text** (`log_min_error_statement` above `error`, or a line cut by the server), a telling or quiet line is a read of `*`, always reported.
  6. **The settings that decide whether the lines exist** (A2). `check()` reads `log_min_error_statement` and **`log_min_messages`** (both readable by every role): with `log_min_messages` above `error`, no `ERROR` line is written at all, and with `log_min_error_statement` above `error`, no statement text. Either one proven too high, or not proven (unreadable, a database whose settings could not be read), caps the level as the next item says for a server without this reading, and the local detail names the setting and the database.
  7. **Forged lines.** Any role can raise an `ERROR` with any SQLSTATE (`RAISE EXCEPTION … USING ERRCODE`). A forged line can add false events, as forged `AUDIT:` lines do; since item 3 it can no longer remove a real failed read either, because no code a user function can raise is refused while the text calls it. A genuine error inside a function has a context too, so **the context's presence is used only to keep a line** (item 3: a `25P02` or `42601` with a context is not refused), **never to drop one**.
  8. **Level.** Interim decision (C1, maintainer, 2026-10-12): reading the server's `ERROR` lines is a release gate for the next release ([RELEASE.md § 7](../../RELEASE.md#open-release-gates)). Until it lands, Full does not cover failed or cancelled reads (see [Known limits](../08-engine-capabilities.md#known-limits)); operators who need them reported set `pgaudit.log_rows = off` (Partial, no row counts).
- **Verified for this amendment** (PostgreSQL 16.13, pgaudit 16.0, `it_wrapped::failed_reads_and_what_is_reported`): a **client's cancel request** during a read gives an `ERROR` line 57014 with the statement text, no `AUDIT:` record with `log_rows = on`, and no event; a **client that closes its connection in the middle of a result** gives a `LOG` line "could not send data to client: Broken pipe" and a `FATAL` line "connection to client lost", both 08006 and **both with the statement text**, no `AUDIT:` record, and no event, after the client received rows.
- **Residual even with the fix.** A backend that crashes during a read (out of memory killer, `SIGKILL`, a segmentation fault) writes nothing itself: only the postmaster's `LOG` line "server process … was terminated by signal …", whose `DETAIL` holds the query text ("Failed process was running: …"), under the postmaster's session, not the client's. It is not read (its `DETAIL` is a field item 2 never reads), so such a read gives no event.
- **Alternatives considered.** Requiring `pgaudit.log_rows = off` for Full (records at the start) would lose every row count, which decision 1 exists for. Logging every statement (`log_statement = all`) duplicates pgaudit and still gives no row count. Reading the message to recognize value-quoting errors breaks I2.
- **Until then** (0.4.0 to 0.6.x; residual, [08-engine-capabilities.md](../08-engine-capabilities.md#known-limits)): with `pgaudit.log_rows = on`, failed and cancelled statements, and reads whose client closes the connection, give no event, including the rows they sent before; with `pg_stat_statements`, failed statements give none either. An operator can set `pgaudit.log_rows = off` (Partial, no row counts) to have them reported.

## Refinement (2026-10-12, proposed): implementation of the failed and cancelled statements

**Status: proposed** (`feat/p8-pg-failed-reads`), for the maintainer and the `security-reviewer` review. Server facts verified on PostgreSQL 16.13 with pgaudit 16.0 (the local cluster of `dev/postgres/local-cluster.sh`, jsonlog and csvlog); the items above are implemented as written, with these additions.

9. **A `FATAL` line without a statement text gives no event, with item 6 proven for the database; otherwise a read of `*`** (refines item 5 for `FATAL` lines; amended after the security review of #214, M1: the stream's 5-minute probe, the same as `check()`'s, passes a per-database proven flag; a database it does not probe is not proven). Verified: the `FATAL` lines that end an idle session carry no statement (`57P01` from `pg_terminate_backend` on an idle backend, `57P05` `idle_session_timeout`, `25P03` `idle_in_transaction_session_timeout`, and the connection-level `28P01` / `3D000` of item 3), while a `FATAL` line during a statement carries its text (`57P01` during a `pg_sleep` read, `08006` mid-result). With item 6 proven for its database, a `FATAL` line without a statement means that no statement was running, so item 5 would make every idle-session end a read of `*` (noise, nothing read); without that proof (a setting above `error`, unread, or a database the target does not declare), it stays item 5's read of `*`, always reported. A cursor read whose session is then killed is still reported: pgaudit writes the `DECLARE CURSOR` record when the `DECLARE` ends (verified, row count 0), and a failing `FETCH` has its text (a read of `*`). `ERROR` lines without a statement keep item 5.
10. **Item 4 also requires the same virtual transaction.** Verified: the record written at a statement's start and its `ERROR` line carry the same `vxid` (autocommit and inside a transaction block). Without it, a statement whose earlier execution wrote a record (at its start) and whose later execution in the same session fails before its executor starts (no record) would be taken for a repeat. The condition only narrows what item 4 suppresses (fails closed); texts are compared as hashes keyed per stream, 4096 sessions followed.
11. **Lines of the server's own processes are not read** (amended after the security review of #214, L1: a closed list that fails closed). Not read: `backend_type` `autovacuum launcher`, `autovacuum worker`, `archiver`, `background writer`, `checkpointer`, `io worker`, `logger`, the `logical replication` launcher and workers, `parallel worker`, `postmaster`, `slotsync worker`, `startup`, `walreceiver`, `walsummarizer`, `walwriter`. An autovacuum worker's `ERROR` 57014 ("canceling autovacuum task") is no client's statement, and a parallel worker's error is re-raised by its leader, whose line is read (reading both would report the read twice). Every other type is read: `client backend`, `walsender` (replication clients, which can run SQL), `standalone backend`, extensions' background workers (`pg_cron`…), an unknown type and a missing one.
12. **Fact for item 7**: `log_error_verbosity = terse` does not remove the context from jsonlog nor csvlog (a `RAISE` `ERROR` line keeps it under `SET log_error_verbosity = terse`). The earlier documentation (docs/08 "Forged records", the connector README) said a server-wide `terse` removed every context; it is corrected.
13. **Choices within the decision** (no change to it): the target's cap of item 6 is Full to Partial (the level a server without this reading gets: with `log_rows = off` the records at the start report the failed reads); a quiet failure of a DDL or DCL statement keeps its action (item 3 says "a read" for reads and writes); the `42601` refusal requires a text that does not lex (without a backslash, so not an ambiguous one) and holds no `(`, `:`, `$`, `[` or operator character, so that no call, cast or operator can have run from it, whatever a lexer that disagrees with the server's reads; an unqualified `pg_*` name is not a catalog in a line's text (no pgaudit record confirms it); a statement that names only catalogs gives no event, as when it succeeds; a telling failure of a plain `INSERT … VALUES` is under the filters only with one relation, no query, no `RETURNING` or `ON CONFLICT` and built-in code only.
14. **Per-role and per-database overrides of the log settings are not seen** (security review of #214, M2; residual, proposed). Item 6 reads `log_min_messages` and `log_min_error_statement` in the agent's session of each monitored database, so an `ALTER ROLE … SET log_min_messages = fatal` (or `log_min_error_statement`, or `ALTER ROLE … IN DATABASE … SET`) for another role hides that role's failed statements (or their text) while the target reports Full. Only a superuser can set them (both are `superuser` settings, or a role granted `SET` on them since PostgreSQL 15), and such a role can turn pgaudit off as well; the `ALTER ROLE … SET` itself is reported by pgaudit (a `ROLE` record, a `dcl` event). A narrow check of these two keys needs `pg_db_role_setting`, which the connector never reads ([ADR-0012](0012-postgresql-agent-grants.md): its `setconfig` can hold secrets): left to an ADR-0012 refinement ([ROADMAP](../ROADMAP.md#phase-8-follow-ups)), not in this change.
