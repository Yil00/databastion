## Context

### What the agent does today

Read from the code at `66e769e` (`dev`):

- An `EXPLAIN` / `DESCRIBE` / `DESC` of a statement, without `ANALYZE`, with its statement within the first 32 tokens and without `FOR CONNECTION`, is on the closed allow-list of statements that produce no event (`is_quiet`), from every account. The exceptions are already reported: `EXPLAIN ANALYZE` and MariaDB `ANALYZE` run their statement and are analyzed as that statement (#168, #184); `EXPLAIN … FOR CONNECTION` is a read of `*`, always reported (ADR-0045, #186); an `EXPLAIN` with no statement keyword in its first 32 tokens is a read of `*`, always reported (#184); an `EXPLAIN` holding a subquery, an unknown call or `LOAD_FILE` is not on the allow-list.
- That holds on the sources that give only text: `performance_schema`, MariaDB `server_audit` with `QUERY` / `QUERY_DML` and no `TABLE` events, and the Percona `audit_log` plugin's JSON. When the source also writes **table read records** for the statement (`server_audit` `TABLE` events, `audit_log_filter` `table_access` records, both verified below), the records decide the action: the statement becomes a read of the recorded tables, **without** the always-reported mark. On the file sources it carries no row count, so a `min_rows` setting drops it, and with the agent's identity it is charged to the own-account budget. Not run: to confirm by the unit tests of this change.
- The readability probes of `check()` and of the Audit re-probe are `EXPLAIN SELECT 1 FROM performance_schema.events_statements_history_long` (and `_history`, `_current`), chosen in #186 because an `EXPLAIN` is quiet for every account: they run on a short heartbeat session that has ended when a `performance_schema` poll sees them, so the poll has no account and a digest only. Their exact texts are also in `own_performance_schema_reads`, so with an account and a full text they are left out uncharged.

The security review of #186 (M2) found that an `EXPLAIN` reads data.

A loop of `EXPLAIN SELECT * FROM hr.customers WHERE id = n` reads a table row by row. An `EXPLAIN` never reads what the account could not read with `SELECT`: the gap is in the audit, not in the privileges.

## Options

- **(a) Every `EXPLAIN` / `DESCRIBE` / `DESC` of a statement is a read of the relations that statement names**, on every source, whatever its form. The question is how the `audit.configure` `min_rows` filter treats it: the file sources have no row count, and `performance_schema`'s `ROWS_SENT` counts plan rows, not data rows.
- **(b) Only an `EXPLAIN` whose statement can read const tables** (a `WHERE` with an equality) is a read, always reported; the others stay quiet.
- **(c) `SHOW WARNINGS` after an `EXPLAIN` is the read.**
- **(d) Keep it quiet and document it** (the current state).

(b) and (c) do not hold against the verified behaviour. A const table is also reached through a join's `ON` condition, a derived table or a common table expression, and a one-row MyISAM table is read with no condition at all; a lexical "equality in `WHERE`" test misses these and fails open. The values do not need `SHOW WARNINGS`: MySQL 9.x JSON results carry them, TREE and JSON plans carry values taken into other tables' conditions, and the plan's "Impossible WHERE noticed after reading const tables" answers any value guess without a warning. `SHOW WARNINGS` is not logged by `server_audit` with `QUERY_DML`, and the `performance_schema` digest summary cannot tie it to the `EXPLAIN` before it. (d) leaves a table readable row by row with no event.

## Decision: option (a)

1. **What counts.** A statement is an *explain of a statement* when it starts with `EXPLAIN`, `DESCRIBE` or `DESC`, has no `ANALYZE` before its statement, no `FOR` before its statement (`FOR CONNECTION` keeps its rule) and its statement keyword within the first 32 tokens (`runs_statement_at` with `TABLE` allowed: `SELECT`, `TABLE`, `WITH`, `VALUES`, `(`, `UPDATE`, `DELETE`, `INSERT`, `REPLACE`), whatever options come before it (`EXTENDED`, `PARTITIONS`, `FORMAT = x`, `INTO @var`). The analysis already finds that position (`wrapper_level`, `explain_analyze`); a new `StatementInfo` flag (`explain_statement`) records it and the explained statement's relations, so that `is_quiet` no longer lets it pass. Digest texts are analyzed the same way (`EXPLAIN SELECT … WHERE id = ?`, MariaDB's `EXPLAIN SELECT` digest of a `DESCRIBE SELECT`).
2. **A read of the relations the explained statement names.** The event's action is `read`, also for an explained write (`EXPLAIN UPDATE …`, `EXPLAIN DELETE …`, `EXPLAIN INSERT … SELECT …`, `EXPLAIN REPLACE …`): nothing is written, the plan uses the target's index for the `WHERE` of an `UPDATE` / `DELETE`, and the account needs `SELECT` on the columns that `WHERE` reads (verified, error 1143); a multi-table `UPDATE` reads its const tables (verified on MySQL 8.0 and 8.4). Its objects are every relation the explained statement names, resolved and filtered as for a read today: system objects other than the statement-text tables of ADR-0045 are dropped, `DUAL` is dropped, and a read left with no object produces no event. When the source has table records, the objects are those of the records plus the relations of the text (the same union as a read today); a statement that names no relation and has no record (`EXPLAIN SELECT 1`) produces no event. Signals: none added. `signature.*` and `shape.*` signals of the explained statement are **not** set: the statement does not run, so `shape.full_table_read` and `signature.mysqldump` would be false.
3. **Always reported, with no row count.** The event carries the agent-internal always-reported mark (#168), so the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops it. It carries no row count on any source: `ROWS_SENT` of an `EXPLAIN` counts plan rows, and `ROWS_EXAMINED` is 0 for the const reads that matter. Without the mark, a `min_rows` setting would drop every such event on the file sources and almost every one on `performance_schema`, and aggregation cannot rescue it because no row is counted. Aggregation is unchanged: one event per principal, object set, action and source per `aggregation_window_s`, whose `aggregated_count` is the number of `EXPLAIN`s merged, so a key walk shows as one event per window with a large count.
4. **Metadata forms stay quiet.** `DESCRIBE t [column | 'pattern']`, `DESC t`, `EXPLAIN t` (the table form, where the token after the lead word is a name and not a statement keyword; `EXPLAIN TABLE t` is a statement), `SHOW [FULL] COLUMNS` / `SHOW FIELDS`, `SHOW INDEX`, `SHOW CREATE TABLE` and `SHOW WARNINGS` stay on the allow-list: they show column definitions and messages, not rows. The `performance_schema` digest `EXPLAIN hr . customers` of a `DESCRIBE hr.customers` is the table form and stays quiet.
5. **A literal probe shape, quiet for every account.** An explain whose whole token sequence is exactly `EXPLAIN | DESCRIBE | DESC`, `SELECT`, one numeric literal (or the digest placeholder `?`), `FROM`, one table name (unqualified or `schema.table`, plain or backquoted), and an optional trailing `;`, produces no event, from any account, on every source, including a digest-only `performance_schema` record with no account. Table records, when the source has them, must read only that table, or the rule does not apply. Such a statement shows no column value on any server verified above: with no condition there is no const table, the agent's probe tables are planned as full scans with no row read, and the select list is a literal, so even the note of a one-row `system` table is `select 1 AS 1 from dual`; it tells only that the table has exactly one row, which `information_schema.TABLES` shows too. Anything more (a `WHERE`, a second table, a join, a column, `*`, an option such as `FORMAT`, a subquery, a hint or a comment that the lexer keeps) is decision 1. This replaces "quiet because every `EXPLAIN` is quiet" for the agent's three readability probes (ADR-0045 refinement of 2026-10-09), which keep their texts and are also matched by this shape when the poll sees only their digest.
   **Refinement (security review of #195, H1; decided by the maintainer on 2026-10-10)**: the table name of the shape must be a **schema-qualified `performance_schema.<table>`** (plain or backquoted; `?` and the digest spacing as above). Any other table, qualified or not, makes the statement an explain of a statement (decision 1), always reported. A view is merged into the explained statement, so its `ON` / `WHERE` const reads happen while `EXPLAIN SELECT 1 FROM view` is planned (verified on 2026-10-10 on MySQL 8.4.11 and MariaDB 11.4.13: the base table is planned `const`, and a view whose condition guesses a value gives "Impossible WHERE noticed after reading const tables"); a one-row MyISAM table under a view is a `system` table. No account can create a view in `performance_schema`, and the three agent probes, their digests included, keep the shape. The residual risk on one-row tables applies to `performance_schema` tables only.
6. **The agent's own account.** An explain of a statement with the agent's identity is **never** left out as its own and never charged: the agent sends no `EXPLAIN` other than the probe shape of decision 5. The exact-text rule of ADR-0045 decision 4 (`own_ps_read`) keeps the three probe texts, so a probe with an account and a full text is left out uncharged as today; decision 5 covers it when the record has no account or a digest only. A unit test proves that every statement the connector sends is either not an explain or of the probe shape.
7. **Unchanged.** `EXPLAIN ANALYZE` / MariaDB `ANALYZE` (the statement runs, analyzed as that statement), `EXPLAIN … FOR CONNECTION` and `SHOW EXPLAIN` / `SHOW ANALYZE` (reads of `*`, always reported), an explain with no statement keyword in its first 32 tokens (read of `*`, always reported), the subquery, unknown call and `LOAD_FILE` rules, and the failed-statement rule: an `EXPLAIN` refused before reading anything (1142, 1143), with no row and no read record, produces no event (verified: `server_audit` writes no `READ` record for it).
8. **I2.** Only names leave the agent: the relation names the explained statement or the table records give, normalized as today ([ADR-0009](0009-name-normalization-and-item-sanitization.md)). The statement text, its literals and the plan never leave the agent; the agent does not run `EXPLAIN` or `SHOW WARNINGS` to learn anything. The `AccessEvent` contract is unchanged: no new field, signal or note.

## Consequences

- **Code** (`agent-engineer`, `security-reviewer` review):
  - `classifiers/src/query.rs`: the `explain_statement` flag and the explained statement's relations, the probe-shape predicate (`explain_literal_probe`) on tokens, both on full texts and digests;
  - `connector-mysql/src/audit/events.rs`: `is_quiet` no longer passes an explain of a statement; its action, objects, always-reported mark and absent row count (decisions 2 and 3); the probe shape before the table-record action (decision 5); never the agent's own (decision 6);
  - `connector-mysql/src/sql.rs`: no change to the probe texts; their doc comments cite this ADR.

  No `shared/protocol/` change.
- **Tests**:
  - unit tests on every source (`server_audit` with and without `TABLE` records, `audit_log` / `audit_log_filter` JSON with and without `table_access`, `performance_schema` with full text and digest only): each lead word (`EXPLAIN`, `DESCRIBE`, `DESC`), each option (`EXTENDED`, `PARTITIONS`, `FORMAT=TRADITIONAL | JSON | TREE`, `INTO @x`), each explained statement (`SELECT`, `TABLE`, `WITH`, `(SELECT …)`, `VALUES`, `UPDATE`, `DELETE`, `INSERT … SELECT`, `REPLACE`), each a read of the named relations, always reported with `min_rows` set, never charged to the agent; the metadata forms of decision 4 quiet, including the `EXPLAIN t` digest; the probe shape quiet from `app` and `databastion`, with and without account, and each one-step variation (a `WHERE`, a second table, `*`, a column, `FORMAT`, a subquery, a comment) reported; a statement-text table in an explain (`EXPLAIN SELECT * FROM performance_schema.threads`) reported as such; the every-agent-statement test extended to decision 6. The existing tests that expect `EXPLAIN SELECT * FROM hr.customers` and `EXPLAIN SELECT * FROM performance_schema.threads` to be quiet are changed accordingly.
  - integration tests on MySQL 8.4, MariaDB 11.4 and Percona 8.4 (the three sources): a second account walks `hr.customers` with `EXPLAIN SELECT * FROM hr.customers WHERE id = n` and `SHOW WARNINGS` under `min_rows: 100` and gets a read event naming the table, always reported, with `aggregated_count` equal to the number of `EXPLAIN`s; `DESCRIBE hr.customers` gives none; the agent's own probes give none on any source.
  - engine matrix (every image): a pinning test of the verified facts, so that a server change is seen: `EXPLAIN SELECT * … WHERE pk = const` reads the row (Note 1003 with a value on MySQL in the traditional format, with `EXTENDED` on MariaDB), and the probe shape on a one-row MyISAM table shows no value.
- **Noise.** Events now come from accounts that run `EXPLAIN` on statements naming application tables: developers and DBAs (MySQL Workbench visual explain, phpMyAdmin, Adminer, DBeaver, all on demand), ORM explain helpers and debug toolbars (Django `QuerySet.explain()`, Rails `explain`, Laravel Debugbar with its explain option: usually development databases), and query analysers that explain sampled statements: PMM Query Analytics (its Explain tab, on demand), `pt-query-digest --explain` / `pt-index-usage` (every statement of a log: a burst), Datadog Database Monitoring (automatic plan collection; per its documentation through a `datadog.explain_statement` procedure, which is a `CALL` and already reported as a read of `*`; to verify). Aggregation bounds each to one event per principal, object set and window, under the console's per-target hourly cap ([ADR-0021](0021-access-event-correlation.md)). Tools that explain real application statements with their literals do read the const rows those statements select, and some store or send the plans: the events describe a real data flow. As in ADR-0045 (open question 2), there is no agent-side allow-list; the console can scope or exclude principals.
- **Volume.** Zero for applications that never explain; one event per principal, object set and window otherwise.
- **Documentation** (`docs-keeper`, after the implementation): in [08-engine-capabilities.md](../08-engine-capabilities.md#mysql--mariadb-audit), the known limit "`EXPLAIN` is quiet" becomes described behaviour (decisions 1 to 6, the verified server table in short, the noise list); the allow-list paragraph names the metadata forms and the probe shape; [10-user-guide.md](../10-user-guide.md) notes that analysers running `EXPLAIN` appear as readers of the tables they explain.
- **Estimated size.** About 150 lines of production code (70 in `query.rs`, 80 in `events.rs`), 400 lines of unit tests, 150 lines of integration tests and the engine-matrix pinning test; 1.5 days with one review round.
- **Residual risks.**
  - An explain event names the relations, not how many rows were read: one per const table and statement, or a whole subquery's input; `volume.*` signals and console volume policies never fire on it.
  - A source that does not log the statement (a `server_audit` event list without `QUERY` / `QUERY_DML` and without `TABLE`, an `audit_log_filter` filter that excludes the account, the `performance_schema` ring buffer overrun between two polls) misses it, as for any read.
  - The probe shape tells whether a non-InnoDB table (MyISAM verified) holds exactly one row (metadata).
  - The probe shape relies on the lexer's view of the text. A version comment that a supported server may run (`/*!…*/`, `/*M!…*/`) gives readings that differ, which keep only the statement kind (ADR-0023 decision 4) and so never match the shape: the statement is reported.
  - Percona's legacy `audit_log` plugin (8.0), MySQL 8.0 and 9.7 `performance_schema` digests and the multi-table `UPDATE` plan on 9.7 are to verify; the decision does not depend on them, because it reads the text.

## Rejected alternatives

- **Option (b)**, only explains with an equality in `WHERE`: const tables are also reached through `ON` conditions, derived tables and common table expressions, and one-row MyISAM tables are read with no condition; a lexical test fails open, and analysers explain real statements, which mostly have equalities anyway.
- **Option (c)**, `SHOW WARNINGS` as the read: MySQL 9.x JSON results, TREE and JSON conditions and the "Impossible WHERE" answer give values without it; `server_audit` with `QUERY_DML` does not log it; the `performance_schema` digest summary cannot tie it to its `EXPLAIN`; MariaDB shows nothing after a plain `EXPLAIN`, so the read would depend on a keyword (`EXTENDED`).
- **Option (d)**, keep it quiet: a table can be read row by row with no event (review M2).
- **Letting `min_rows` apply with no row count**: every explain would be dropped as soon as `min_rows` is set, and nothing in the console would show it.
- **Counting one row per explain** so that `min_rows` applies after aggregation: a walk paced below `min_rows` per window would stay unseen indefinitely, and the count would be a guess.
- **Running the explained statement's analysis as a write for `EXPLAIN UPDATE` / `DELETE`**: nothing is written; a write event would trip the agent's "never writes" rule (I4) for nothing and mislead write policies.
- **Exempting only the agent's three probe texts and digests**: the digest-only record has no account, so the exemption would apply to anyone sending the same shape anyway; a narrowly defined shape that reads no value says the same thing honestly and also covers tools that check privileges with the same statement.

## Open questions (answered)
Each answer is the recommendation of this ADR, accepted by the maintainer on 2026-10-10.

1. Option (a), every explain of a statement is a read of the relations it names, as proposed, or (b), (c) or (d)?
   **Answer (decided by the maintainer on 2026-10-10)**: (a). The verified servers read const and `system` tables through more paths than a lexical test can see, and give values without `SHOW WARNINGS`.
2. `min_rows`: always report explain events with no row count (decision 3), or count one row per explain and let the filter apply after aggregation, or let the filter drop them?
   **Answer (decided by the maintainer on 2026-10-10)**: always report, as ADR-0045 does for statement-text tables. No source gives a data row count for an `EXPLAIN`, so any filter on rows either drops them all or relies on a guess that a paced walk stays under.
3. The literal probe shape (decision 5): quiet for every account, or exempt only the agent's three probe texts (exact text, as today) and their three digests?
   **Answer (decided by the maintainer on 2026-10-10)**: the shape, for every account. It reads no column value on any verified server, a digest-only record has no account to restrict it to anyway, and a tight token shape is easier to test than a list of digests.
   **Refinement (security review of #195, H1; decided by the maintainer on 2026-10-10)**: the shape applies only to a schema-qualified `performance_schema.<table>` (decision 5, refinement): on any other name it could be a view, whose const reads happen while it is planned.
4. Explained writes (`EXPLAIN UPDATE` / `DELETE` / `INSERT … SELECT` / `REPLACE`): a read of every relation named, target included (decision 2), or of the source relations only?
   **Answer (decided by the maintainer on 2026-10-10)**: every relation named. The plan uses the target's index for the `WHERE` of an `UPDATE` / `DELETE`, a multi-table `UPDATE` reads its const tables, and the account needs `SELECT` on the columns the `WHERE` reads (verified, error 1143), so naming the target matches what the account can learn. It is also the simpler rule to test.
5. Monitoring and analyser noise: no agent-side allow-list, as decided for ADR-0045 (open question 2), or a per-target list of principals whose explains produce no event?
   **Answer (decided by the maintainer on 2026-10-10)**: no allow-list. Analysers that explain real statements read real rows, and their credentials are often shared; the console can scope or exclude principals.
6. A dedicated signal (for example `shape.explain`) so that console policies can tell an explain read from a `SELECT`?
   **Answer (decided by the maintainer on 2026-10-10)**: not in this ADR. It is a protocol change (`signals.json`, [ADR-0022](0022-protocol-capability-negotiation.md)); the principal and objects are enough for the first policies. Revisit if users ask to scope explains separately.

## Implementation note (2026-10-10)
Recorded with the implementation (`feat/p8-mysql-explain-as-read`), before its security review.

- **`performance_schema` only in the probe shape** (decision 5, refinement of 2026-10-10, security review of #195, H1).
- **Integer literals only in the probe shape.** Decision 5 says "one numeric literal". The lexer keeps plain decimal integers apart from every other literal; strings and decimal or exponent numbers share one token kind. The shape therefore takes an integer or the digest placeholder `?` only; `EXPLAIN SELECT 1.5 FROM t` is an explain of a statement (narrower, fail closed).
- **A probe shape the rule does not leave out is an explain of a statement.** When the table records of a probe-shaped statement read another table, or the probe shape is one statement of a longer text, the statement is reported as decision 1 says (always reported, never the agent's own). Inside a longer text, its relation is named with the others.
- **Objects with table records.** Decision 2 says "the same union as a read today", but a read with table records takes its objects from the records only. For an explain, the objects are the records' tables and the relations of the text, both filtered as for a read. This covers an `audit_log_filter` record set without a `performance_schema` table, and an explained write, which has no write record.
- **Relations of the explained statement only.** The relations are taken from the explained statement read on its own, from its keyword. `EXPLAIN TABLE t` and `EXPLAIN REPLACE t SELECT …` then name `t`, and the common table expressions of `EXPLAIN WITH c AS (…) SELECT … FROM c` are not taken for tables. The prefix (`FORMAT = x`, `INTO @var`) names nothing.
- **No signal of the explained statement, `INTO OUTFILE` included.** An explained `SELECT … INTO OUTFILE` writes no file. It sets no `signature.into_outfile`, and a failed one is not kept as an attempt. `volume.large_result` is not set either, since there is no row count.
- **`EXPLAIN (SELECT …)` adds `*`.** The unqualified-call rule of ADR-0045 part (b) reads `EXPLAIN (` as a call of a name that is not built in. Decision 7 keeps that rule unchanged, so the event names the explained relations and `*`.
- **Unreadable explain texts.** An explain text that does not lex (for example the multibyte rule on the file sources) is decided by its table records when they all read, as for any read. When its first word (after whitespace, opening parentheses and comments) is `EXPLAIN`, `DESCRIBE` or `DESC`, the event is handled like an explain: always reported, with no row count, never the agent's own (fail closed). Without table records it is a read of `*`, always reported, as before.
- **Variables named like keywords** (security review of #195, M1). A word right after `@` or `@@` is a variable name, never the `ANALYZE` or `FOR` keyword of the prefix: `EXPLAIN FORMAT=JSON INTO @analyze SELECT …` is an explain of a statement (before, it was analyzed as a `SELECT` that runs), and `INTO @for` is not `FOR CONNECTION`. A backquoted `` @`analyze` `` is not a word and was never taken for one.
- **`EXPLAIN ANALYZE` and MariaDB `ANALYZE` are always reported, with no row count** (security review of #195, M2). They run their statement, so decision 7 keeps their analysis as that statement (action, objects, signals), but they also show the const values a plain explain shows, and their row count is the plan's. Decision 3 is applied to them, writes included. This refines decision 7.
- **Comments before the explain word of an unreadable text** (security review of #195, L1). The first-word check skips whitespace, opening parentheses, `/* … */`, `#` and `-- ` comments, and reads inside executable comments (`/*!…`, `/*M!…`, after their version digits).
- **`EXPLAIN FOR SCHEMA | DATABASE name <statement>`** (MySQL; security review of #195, L2). Before, the `FOR` made it a plan of another connection (a read of `*`). It is now an explain of a statement whose unqualified relations are taken in `name`; the event also names `*` (what the server resolves is not proven), is always reported, has no row count and is never the agent's own. `FOR CONNECTION` after it keeps its rule.
- **`EXPLAIN` of a view needs `SHOW VIEW`.** Without it the server refuses the statement with error 1345, which is not in the list of errors raised before anything is read: such a refused explain is reported (fail closed).
- **Leading parentheses.** A statement written `(EXPLAIN SELECT …)` is not valid SQL. The analysis still treats it as an explain of a statement (fail closed).
- **Integration tests.** The tests run on MySQL 8.4 and MariaDB 11.4 (`performance_schema`), MariaDB 11.4 `server_audit` (`QUERY_DML` and `TABLE`) and Percona 8.4 `audit_log_filter`.
  - A second account walks a table with `EXPLAIN SELECT * … WHERE id = n` and `SHOW WARNINGS`. Each explain gives one read event naming the table, always reported, with no row count and no signal. Its `EXPLAIN SELECT 1 FROM t` on the table and on a merged view are reads too.
  - `DESCRIBE t` and `EXPLAIN SELECT 1 FROM performance_schema.threads` from that account give none, and the agent's probes give none on any source.
  - The `min_rows` filter and aggregation run in the agent core, not in the connector stream the tests read. The tests check the always-reported mark and count one event per explain; the core unit test `always_reported_events_pass_min_rows` covers the filter.
  - The engine-matrix pinning test of the verified server facts is not part of this change.
