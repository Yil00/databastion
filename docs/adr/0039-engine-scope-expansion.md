# ADR-0039: Engine scope expansion and supported-version policy

- **Status**: Proposed (decision 1, the end-of-life version policy, was decided by the maintainer on 2026-10-04; decision 8, new engines as capability tokens, was accepted by the maintainer on 2026-10-04 as implemented for `cas` in #137 and refined by [ADR-0042](0042-hold-items-of-unlisted-engines.md); the other decisions stay Proposed until their phase)
- **Date**: 2026-10-04
- **Context references**: ROADMAP phases 9 and 10; security review of this ADR (M1, M2, L1 to L4); [08-engine-capabilities.md](../08-engine-capabilities.md); [ADR-0002](0002-single-agent-connectors.md), [ADR-0003](0003-data-minimization-at-source.md), [ADR-0006](0006-target-discovery.md), [ADR-0009](0009-name-normalization-and-item-sanitization.md), [ADR-0022](0022-protocol-capability-negotiation.md), [ADR-0035](0035-discovery-pacing.md); `agent/deny.toml`

## Context
DataBastion supports PostgreSQL 14 to 18, MySQL 8.0 / 8.4 / 9.x, MariaDB 10.11 / 11.x, MongoDB 5.0+ (6.0 to 8.0 tested) and OpenLDAP 2.5 (README, "Supported databases"). The maintainer asked to cover at least the engines of Portabase, an open-source backup tool: PostgreSQL 12 to 18, MySQL 5.7 / 8 / 9, MariaDB 10 / 11, MongoDB 4 to 8, SQLite 3, Redis 2.8+, Valkey, Firebird and Microsoft SQL Server. The missing engines are **Microsoft SQL Server, SQLite, Redis, Valkey and Firebird**. The missing versions are PostgreSQL 12 and 13, MySQL 5.7 and MongoDB 4.x, all past their end of life.

A backup tool and a DLP do not need the same things from an engine. A backup tool needs a dump. DataBastion needs a least-privilege read-only account (I4), bounded sampling, and for Audit a native record of who read what. Each existing connector had to state honestly what its engine provides ([08-engine-capabilities.md](../08-engine-capabilities.md)); the new engines must be held to the same standard.

Facts from the repository that bear on versions:
- PostgreSQL: the `pg_stat_statements` Audit mode relies on the `pg_stat_statements_info` view (PostgreSQL 14+), pgaudit `jsonlog` needs PostgreSQL 15+, and the engine matrix dropped PostgreSQL 13 in #121.
- MySQL: the connector refuses servers older than 8.0.0 (`MIN_MYSQL` in `connector-mysql/src/conn.rs`), and role privileges are evaluated from 8.0.19.
- MongoDB: the connector refuses servers below wire version 13, MongoDB 5.0 (`MIN_WIRE_VERSION` in `connector-mongodb/src/conn.rs`).
- MariaDB: the connector accepts 10.6+ (`MIN_MARIADB`); 10.11 is the oldest version tested.

The protocol is also concerned. `Engine` is a closed enum (`postgres, mysql, mariadb, mongodb, openldap`) used in `TargetStatus`, `DetectedTarget` and `Location`, all agent → console fields; `Connector` is a closed enum and `ConnectorList` has `maxItems: 4`.

## Decision
1. **End-of-life engine versions are not supported** (decided by the maintainer on 2026-10-04). PostgreSQL 12 and 13, MySQL 5.7 and MongoDB 4.x are out of scope: they receive no security fixes, and the agent relies on features they lack (`pg_stat_statements_info`, MySQL 8 roles and `performance_schema` behavior, MongoDB wire version 13 and its authentication). For the new engines, the supported versions are those their vendor or community still maintains when the connector ships; a version that reaches its end of life is dropped from the engine matrix at the next minor release and listed as such in the CHANGELOG. A connector may keep refusing old servers at connection time (as MySQL and MongoDB do today). The same policy applies to existing engines: MariaDB 10.6, still accepted by `MIN_MARIADB`, reached its end of life in July 2026, and raising the minimum is a ROADMAP item.
2. **Target engines and order of delivery.** Wave 1 (ROADMAP phase 9): Microsoft SQL Server, then Redis and Valkey (one connector, two engines). Wave 2 (phase 10): SQLite, then Firebird. Each engine gets its own connector ADR before its implementation, as ADR-0015, 0018, 0026 and 0029 did; this ADR sets the frame those ADRs must respect, not their details.
3. **Expected ceilings.** No connector may report more than the ceiling below; its own ADR may lower it, and only proofs read from the engine (as in [ADR-0037](0037-postgresql-full-requires-pgaudit-log-rows.md)) may grant a level.

   | Engine | Discovery | Audit source to evaluate | Expected best level |
   |---|---|---|---|
   | Microsoft SQL Server (2019, 2022 and later supported releases) | Catalog (`sys.schemas`, `sys.tables`, `sys.columns`) and bounded `TOP (n)` sampling in short read-only transactions with `LOCK_TIMEOUT` SQL Server Audit (audit specifications with the `SELECT` action, created by the operator, read through `sys.fn_get_audit_file`) only where reading it needs no permission of the refusal list (decision 5): on versions where it needs `CONTROL SERVER` (before SQL Server 2022), SQL Server Audit is not a source, and an operator-created Extended Events session read with `VIEW SERVER STATE` / `VIEW SERVER PERFORMANCE STATE` is used, or the level is lower; whether SQL Server 2022's `VIEW SERVER SECURITY AUDIT` is enough is confirmed in the connector ADR | Partial; Full only if every read is proven logged with a row count, which the connector ADR must show per version. Statement text holds literals: treated like MySQL statement text ([ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md)); password-bearing DCL (`CREATE LOGIN … WITH PASSWORD =`, `ALTER LOGIN`) follows the end-to-end rule of #82 (the password never leaves the parser, and a test proves it) |
   | Redis and Valkey (maintained releases; Redis 6.0 is the technical floor for ACL users; Valkey 7.2+) | `SCAN` with `COUNT` and a key budget, `TYPE`, bounded sampling of values (strings by `STRLEN` then `GETRANGE 0 n`, never `GET`; `HRANDFIELD`, `SRANDMEMBER`, `ZRANDMEMBER`, `LRANGE` with a small range); key names normalized into patterns ([ADR-0009](0009-name-normalization-and-item-sanitization.md)) because they often embed identifiers or e-mail addresses | No audit log in either engine. `ACL LOG` (failed authentications and denied commands only, a small ring buffer), `SLOWLOG` (slow commands only), Valkey's command log of large replies where available, and the `sync_full` counter of `INFO stats` for full synchronizations such as `redis-cli --rdb` | Limited at best, None when only `ACL LOG` is readable. `MONITOR` is excluded: it streams every command with its arguments (values) to the agent and costs the server heavily. Keyspace notifications are excluded: they report writes and expirations, not reads |
   | SQLite 3 | Read-only open of a declared local file (`mode=ro`, no extension loading, `trusted_schema` off, bounded busy timeout), catalog from `sqlite_schema`, bounded sampling | None: SQLite has no server and no access log; reads happen inside the applications that open the file | None. The console shows "Discovery only" |
   | Firebird (4.0, 5.0; 3.0 if still maintained when the connector ships) | System tables (`RDB$RELATIONS`, `RDB$RELATION_FIELDS`) and `SELECT FIRST n` in a read-only transaction | Firebird trace / system audit session (`AuditTraceConfigFile`) writing a text log read locally | Partial at best, pending the connector ADR. Statement text and parameters hold literals |

   **Redis / Valkey Audit entries are reduced at parse time.** `SLOWLOG`, Valkey command log and `ACL LOG` entries carry command arguments, which hold values. The parser keeps only the command name (from a closed list), the normalized key pattern (decision 7) and counts; arguments are dropped before any buffering beyond the parser and are never logged. Failed-authentication user names are fingerprinted, as on the other engines.

4. **Client library criteria.** A connector's client, own or third party:
   - uses **rustls** for TLS; no OpenSSL, `native-tls` or system TLS library (`agent/deny.toml`);
   - has a license on the `agent/deny.toml` allow-list (Apache-2.0, MIT, BSD, ISC, Zlib, CC0, Unicode-3.0), checked by cargo-deny; copyleft (GPL, LGPL, MPL) clients are refused;
   - builds on the workspace MSRV (`rust-version`, 1.88 today), checked by the "Agent MSRV" job;
   - spawns no process (no `sqlcmd`, `redis-cli`, `isql` or `sqlite3` binary) and links no C client library, unless the connector ADR justifies it and the `security-reviewer` accepts it; SQLite is the expected exception (the bundled SQLite C library, as no maintained pure-Rust reader exists), fuzzed on hostile files;
   - can bound every reply (size, count, time) before allocation, and parses untrusted server data with property tests and a fuzz target.
   The project's precedent is an own bounded client for a closed protocol subset (MySQL [ADR-0018](0018-mysql-mariadb-grants-and-connector.md), MongoDB [ADR-0026](0026-mongodb-connector.md), OpenLDAP [ADR-0029](0029-openldap-connector.md)). Candidates are evaluated in each connector ADR: for TDS, an existing crate (with its rustls support, TDS 8.0 strict encryption and maintenance status checked) against an own client; for RESP, an own client is expected (a small protocol); for Firebird, a pure-Rust wire client, noting that Firebird's wire encryption is not TLS (decision 6).
5. **Least privilege per engine (I4).** Each connector ADR measures its grant set the way [ADR-0012](0012-postgresql-agent-grants.md) did, and `check()` reports an over-privileged account:
   - SQL Server: a login mapped to a database user with `SELECT` on the monitored schemas (or `db_datareader` as a documented, broader variant). Audit permissions are separate and granted by the operator only when Audit is configured; audit specifications and Extended Events sessions are created by the operator, never by the agent. **Refusal list**: the account is never a member of `sysadmin` or `db_owner` and never holds `CONTROL SERVER`, `ALTER ANY SERVER AUDIT` or `ALTER ANY DATABASE AUDIT`; `check()` reports such an account as over-privileged and Audit refuses to run with it;
   - Redis / Valkey: an ACL user with an explicit allow-list and nothing else: `-@all +scan +type +strlen +getrange +hlen +hstrlen +hrandfield +scard +srandmember +zcard +zrandmember +llen +lrange +info +slowlog|get +acl|log`, `resetchannels` (plus Valkey's command-log read where used), no `+get`. `check()` refuses the `default` user and reports a `default` user with `nopass`. Redis before 6.0 has no ACL users, only one password with full access, and is therefore refused;
   - SQLite: file read permission only, through the agent's Unix account; a file the agent can write is refused, as audit logs are ([ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md)). Hardening for the connector ADR: `SQLITE_DBCONFIG_DEFENSIVE`, `cell_size_check=ON`, `mmap_size=0`, lowered `SQLITE_LIMIT_*` values, a progress handler enforcing the time bound, tables only (no views, no virtual tables). A WAL database opened read-only needs an existing `-shm` file, and `immutable=1` is not acceptable on a live file: the connector ADR must resolve this. Symlinks are resolved when the configuration is loaded and the target is refused if they change; a path whose parent directory is writable by another non-root user is refused, as are paths under the agent's own state, identity and spool directories. SQLite errors map to closed codes, so the path never appears in `last_error`;
   - Firebird: a dedicated user with `SELECT` grants on the monitored tables, never `SYSDBA` nor the `RDB$ADMIN` role. Embedded access and direct reading of `.fdb` files are excluded: the agent goes through the server. The trace log follows the rule that a file the agent can write is refused.
6. **Transport and authentication.** Same rules as the existing connectors: TLS `verify_full` by default where the engine supports TLS (SQL Server, Redis 6+, Valkey); no cleartext password over an unencrypted network connection. **SQL Server**: TDS 8.0 strict encryption, or mandatory encryption with full certificate verification; login-only encryption (`ENCRYPT_OFF`) and NTLM are refused. **Firebird** has its own wire encryption (SRP authentication, ARC4 or ChaCha) and no TLS: its connector ADR decides whether to require a local or loopback connection, or Firebird 4+ ChaCha, whose trust model is SRP mutual authentication (the server proves it knows the verifier) rather than a certificate.
7. **I5, local detection and key names.** Targets stay declared in `agent.yaml`. Local detection ([ADR-0006](0006-target-discovery.md)) may add the local ports and processes of the new servers (1433 and `sqlservr`, 6379 and `redis-server` / `valkey-server`, 3050 and `firebird`). **SQLite targets are local file paths declared in `agent.yaml` only**: the agent never searches the file system for database files, and never sends the path to the console (the target's declared id and name identify it; the path can contain user or customer names). Redis Cluster and Sentinel topologies are not followed: one declared node per target, as MongoDB. **Redis / Valkey key names are normalized** before they leave the connector: any segment matched by a classifier, and any high-entropy segment (hex or base64 of 16 characters or more), is replaced by a placeholder, so `session:4f9a…` and `user:jane@example.com` become patterns.
8. **Protocol.** New engines are new values of the closed `Engine` and `Connector` enums in agent → console fields, and `ConnectorList.maxItems` must grow. Following [ADR-0022](0022-protocol-capability-negotiation.md) decision 4, each new engine value is a capability token (for example `engine.sqlserver`). Because `Engine` has no fallback value, an agent does not report a target, a detected target, a finding or an event of a new engine until the console lists its token; `check()` then logs that the console is too old. Widening `ConnectorList.maxItems` is negotiated the same way. These are compatible changes under ADR-0022 (with a `security-reviewer` review), not a v2. The `Location` mapping of each engine (for Redis: logical database, key pattern, hash field or `value`) is fixed by its connector ADR.
9. **Test obligations per engine**, before the engine is listed as supported in the README:
   - a `dev/` service with seeded fake data and entries in `dev/ground-truth.json` (Redis and Valkey: both images; SQLite: a seeded file);
   - connector integration tests against `dev/`, and an engine-matrix entry for each supported version (`.github/workflows/engine-matrix.yml`);
   - an end-to-end target with a Discovery scan, an Audit scenario where the level is above None, and the **I2 check** (no ground-truth value in clear in the console database); for Redis and Valkey, the seeded data includes keys whose names embed ground-truth values;
   - a load / database impact run in `e2e/load/` against the < 2 % CPU criterion, with Discovery pacing ([ADR-0035](0035-discovery-pacing.md));
   - fuzz targets for every parser of server data;
   - a section in [08-engine-capabilities.md](../08-engine-capabilities.md) and a README row written from what was measured, never from this table.

## Consequences
- Five engines and two connector waves; each engine costs a connector ADR, a dev service, CI time and an end-to-end target. The weekly engine matrix grows accordingly.
- Users of PostgreSQL 12 / 13, MySQL 5.7 or MongoDB 4.x get a clear answer (not supported, upgrade first) instead of a silently untested path.
- Redis, Valkey and SQLite will never reach Full or Partial Audit; their README rows must say so. For SQLite and, in practice, Redis, DataBastion is a Discovery tool.
- The Redis server license changed in 2024 and 2025 (RSALv2 / SSPL, then AGPLv3 as an option). The agent only speaks the protocol and links no Redis code, so this does not affect the agent's Apache 2.0 license; dev images use the engines as tools.
- The SQLite exception to "no C client library" needs a reviewed `deny.toml` / architecture-test change.
- Microsoft SQL Server targets are reached over the network from a Linux agent, so Audit sources read through a connection matter more than local files (SQL Server on Windows hosts has no local file the Linux agent can read).

## Rejected alternatives
- **Supporting the end-of-life versions to match Portabase**: no security fixes upstream, and several agent features would be unavailable or untested; a DLP that encourages running unpatched databases contradicts its purpose.
- **An ODBC bridge** (one connector through ODBC drivers): C driver managers and vendor drivers, OpenSSL in most of them, licenses outside the allow-list, and no control over what the driver sends or buffers.
- **Shelling out to the engines' CLI tools** (`sqlcmd`, `redis-cli`, `isql-fb`, `sqlite3`): process spawning, output parsing of tools that print values, credentials on command lines or in environment variables, and no bounds on what the tool reads.
- **`MONITOR` for Redis Audit**: every value crosses to the agent and the server's throughput drops; I2 and the < 2 % criterion both argue against it.
- **Scanning the file system for SQLite files**: breaks I5 and would read files no one declared.
