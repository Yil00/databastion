## Context
Phase 9 adds Redis and Valkey ([ROADMAP](../ROADMAP.md#phase-9--engine-scope-wave-1-microsoft-sql-server-redis-valkey)). The rules of the other connectors apply: read-only and bounded (I4), declared targets only (I5), credentials local (I3), masking before the uplink (I2), rustls only, honest `check()`, closed notes ([ADR-0022](0022-protocol-capability-negotiation.md)), no database resource held across `FindingSink::submit().await` ([05-security.md](../05-security.md#connector-obligations)). Redis and Valkey raise questions the other engines did not.

- **No schema, and names are data.** A Redis database is a flat keyspace. Applications build key names from values: `user:42:email`, `session:4f9a0c…`, `cart:jane@example.com`, `rate:203.0.113.7`. The key name is often the most sensitive string in the server, and every key name is a candidate for the uplink as a `Location` (ADR-0009). Hash field names can be data too (a hash keyed by e-mail address). The contract's `Identifier` forbids `:` and `/`, the two most common key separators.
- **No read-only mode.** Nothing on the server makes a session read-only: the ACL user's command list and the commands the client sends are the only controls (as for MongoDB).
- **No audit log.** Neither engine records who read what. What exists, checked on 2026-10-14 against the sources and documentation named below:
  - `SLOWLOG GET`: commands slower than `slowlog-log-slower-than` (10 ms by default; `0` logs every command, a negative value none), in a ring buffer of `slowlog-max-len` entries (128 by default). Each entry: a progressive id, a timestamp, the duration, **the arguments** (at most 32, each cut to 128 bytes: `SLOWLOG_ENTRY_MAX_ARGC` and `SLOWLOG_ENTRY_MAX_STRING` in Redis 7.4 `slowlog.h`), the client's `addr:port` and its client name. **No user name, no database index, no reply size.**
  - `ACL LOG`: denied commands, keys and channels, and failed authentications, in a ring buffer (`acllog-max-len`, 128 by default). Each entry: `count`, `reason` (`command`, `key`, `channel`, `auth`; Valkey 9.1 adds `db`), `context`, `object` (the command name, **the key or channel name**, or for `auth` the user name tried), `username`, `age-seconds`, `client-info` (the client's `CLIENT LIST` line); from Redis 7.2 and in Valkey also `entry-id`, `timestamp-created`, `timestamp-last-updated`. Repeated identical denials update one entry's `count`.
  - **Valkey's command log** (`COMMANDLOG GET <count> slow|large-request|large-reply`, since Valkey 8.1.0, flagged `ADMIN`; checked in `src/commands/commandlog-get.json` and the valkey-doc page): the slow log plus logs of **large requests** and **large replies**, with the same six fields as a slow-log entry (id, timestamp, duration or size in bytes, arguments, peer, client name).
  - `INFO stats` `sync_full`: the count of full synchronizations, which a replica's first sync and also `redis-cli --rdb` (a full copy of the dataset over the replication protocol) increase (the latter to verify per version).
  - `CLIENT LIST`: the connected clients with `addr`, `name`, `user`, `db` and the last command's name (no arguments); Valkey 8.0+ also per-client network counters (`tot-net-out`, to verify).
  - `MONITOR` streams every command with its arguments; keyspace notifications publish writes and expirations over pub/sub; `LATENCY` reports latency spikes by event class, with no client and no key.
- **ACL facts that matter here** (Redis 7.4 sources, `src/server.c`, `src/acl.c`, `src/commands/*.json`):
  - `HELLO` and `AUTH` carry the `NO_AUTH` flag and are never refused by an ACL (`ACLSelectorCheckCmd` skips `CMD_NO_AUTH` commands): `AUTH <user> <password>` followed by `HELLO 3 SETNAME <name>` authenticates, selects RESP3 and names the connection without any grant. Both carry `no-auth` but neither carries `no-slowlog` in Redis 6.2's command table; the 6.2 branch today redacts the `AUTH` arguments of both commands (`redactClientCommandArgument` in `acl.c` and `networking.c`), but from which 6.2 patch release is to verify.
  - `processCommand` checks the command's existence and arity, then the ACL, and only then queues a command inside `MULTI`; a refusal is written to `ACL LOG`.
  - `ACL DRYRUN <user> <command> [args]` (Redis 7.0+, in Valkey 7.2) evaluates a user's permissions (every selector) **without running the command and without writing to `ACL LOG`**.
  - `ACL GETUSER` and `ACL LIST` return users' password hashes (unsalted SHA-256). `ACL LOG RESET` is the same subcommand (`acl|log`) as reading the log: an ACL cannot grant one without the other.
  - `SCAN` and `KEYS` take no key argument: an ACL's key patterns do not filter the key names they return (to verify per version in the integration tests); they only restrict commands that name a key.
  - Read-only key permissions (`%R~<pattern>`) and selectors exist from Redis 7.0. Valkey 9.1 adds per-database permissions (`db=<ids>`, `alldbs`, `resetdbs`; present in the 9.1 branch's `acl.c`, absent from 9.0).
- **Telling the engines apart.** Valkey's `INFO server` has `server_name:valkey` and `valkey_version:<x.y.z>`, and keeps `redis_version` frozen at `7.2.4` for compatibility (Valkey `src/version.h` on the 7.2 branch and on `unstable`). Redis has neither `server_name` nor `valkey_version`.

## Decision
1. **Own client for a closed subset of RESP, no client crate** (ADR-0039 decision 4, as [ADR-0018](0018-mysql-mariadb-grants-and-connector.md) decision 3, [ADR-0026](0026-mongodb-connector.md) decision 1 and [ADR-0029](0029-openldap-connector.md) decision 1 did).
   - **Handshake** (security review H2). Two commands: `AUTH <user> <password>`, then `HELLO 3 SETNAME databastion-agent` **without credentials**. Both carry `no-auth` and need no grant (Context). Credentials never travel inside `HELLO`, so they cannot reach `SLOWLOG`, the command log or `MONITOR` through a `HELLO` argument on a version that does not redact it. Integration tests on every supported version prove it: with `slowlog-log-slower-than 0` (and the command log's thresholds at 0 on Valkey 8.1+), and with a `MONITOR` session open in the test, the password never appears in `SLOWLOG GET`, `COMMANDLOG GET` or the `MONITOR` stream. The `HELLO` reply map gives `server`, `version`, `proto`, `id` (the connection id, kept for decision 8's own-entry rule), `mode` and `role`. A server that refuses `HELLO 3`, or answers with another protocol version, is `unsupported` (every supported version has `HELLO` and RESP3; no RESP2 fallback, no inline commands).
   - **Requests** are arrays of bulk strings built in code. The command name and any subcommand come from a closed enum (decision 4's allow-list, nothing else, and no encoder for anything else: read-only by construction, I4); the arguments are key names and field names returned by the server, numbers and constants. Console-provided strings never reach a request (scan filters are applied to normalized names, in memory).
   - **Replies** are parsed by the connector's own decoder. The RESP3 types `+ - : $ * _ , # ! = ( % ~` are decoded; **push (`>`) and attribute (`|`) frames end the connection** (the agent never subscribes nor enables client tracking, so a push is a protocol error). Each request carries its own limits, checked on the header **before** any allocation: a line (simple string, number, error) at most 512 bytes; a bulk string at most the request's cap (4 KiB + 1 for a sampled value, 64 KiB for a key name or a log argument, 1 MiB for an `INFO` section); an aggregate at most the count the request asked for (plus a fixed slack for `SCAN`), never preallocated from a server-announced count; nesting at most 4 levels; at most 4 MiB per reply, except the Audit log reads, whose count is sized to fit their own cap (decision 8). Further decoder rules (security review L4): a blob error (`!`) is capped like a line and its text discarded; streamed lengths (`$?`, `*?` and `;` chunks) are refused; a negative length other than `-1` is refused; a map's count is checked as twice its pairs against the caps; the `modules` array of the `HELLO` reply is capped at 64 entries. **Oversized bulk strings** (security review M5): for the requests that allow it (a key name in a `SCAN` reply, an argument or object in a log entry), the decoder reads and discards the excess **without buffering it**, within a per-reply wire budget of 64 MiB, and returns a marker in place of the string (the key is counted `skipped_limit`, the argument becomes `*`); beyond that budget, or for any other request, a reply past a limit **closes the connection** (the stream cannot be resynchronized without reading the excess; the unit is counted per decision 6, and the next unit reconnects). Decoded values are then extracted into typed shapes that fail closed on any unexpected type.
   - **Error replies** are reduced to their first word compared with a closed list (`ERR`, `NOPERM`, `NOAUTH`, `WRONGPASS`, `WRONGTYPE`, `MOVED`, `ASK`, `LOADING`, `BUSY`, `MASTERDOWN`, `CLUSTERDOWN`, `TRYAGAIN`, `READONLY`, `EXECABORT`, `NOREPLICAS`, `MISCONF`; anything else is `ERR`), which becomes the contract `EngineCode`. The rest of the text is never kept, logged or sent: a `NOPERM` message names the key, a `WRONGTYPE` or `ERR` message may quote an argument. The one exception is `ACL DRYRUN`'s denial string, compared in memory with fixed prefixes per version (decision 4) and dropped.
   - **Timeouts.** Connection (TCP and TLS) at most 5 s; every exchange has a client-side deadline (the job's clamped statement timeout in Discovery, 3 s per command and 9 s in total in `check()`, 5 s per Audit poll command). Redis has no server-side cancel for an ordinary command: every command of the allow-list is bounded by construction (decision 6), and a deadline closes the connection.
   - **Pipelining** is bounded: at most 64 commands in flight (the `TYPE` of one `SCAN` batch, the `HSTRLEN` of one hash's fields).
   - **Secrets and buffers.** The password is read from its `agent.yaml` reference into zeroized memory and written into a zeroized request buffer; buffers that held sampled values or log entries are zeroized after use, as in the OpenLDAP and MongoDB connectors.
   - **No panic on input.** The crate denies `clippy::indexing_slicing` and `clippy::string_slice` outside tests; property tests cover the decoder (round trips through the encoder, every split of a valid stream into chunks, arbitrary bytes never panic and never allocate past the limits) and the entry parsers. **Fuzz targets**: the reply decoder, the `SLOWLOG` / `COMMANDLOG` entry parser, the `ACL LOG` entry parser (with its `client-info` line), the `INFO` section parser and the key-name normalizer, added to the nightly AddressSanitizer fuzz workflow (#179).
   - **Dependencies**: `tokio`, the workspace TLS crates (`rustls`, `tokio-rustls`, `rustls-native-certs`, `rustls-pki-types`), `zeroize`. No new license, no MSRV change.
2. **Versions and licenses** (ADR-0039 decision 1).
   - **Supported: the versions their project maintains when the connector ships**: today Redis 6.2, 7.2, 7.4 and 8.2 to 8.10, and Valkey 7.2, 8.0, 8.1, 9.0 and 9.1 (Context). A line that reaches its end of life (Redis 6.2 and 7.2 first, tied to the end of 7.4's support, date to verify) leaves the engine matrix at the next agent minor release and the CHANGELOG says so.
   - **Refused at connection time**: Redis below **6.2.0** and Valkey below **7.2.0**, as `unsupported`. **Redis 6.2 releases older than the first 6.2 patch that redacts `AUTH` arguments in `SLOWLOG` are refused too**, as `unsupported`, whatever `unevaluated_acl` says (re-review N1): on them the agent's own `AUTH` could reach the slow log. Finding that patch release, from the 6.2 changelog and a test against the releases around it, is an **implementation gate** (to verify). ADR-0039 named Redis 6.0 as the technical floor, because ACL users appear in 6.0; this ADR raises the refusal floor to 6.2 because 6.0 and 6.1 are no longer maintained (decision 1) and lack `HRANDFIELD` and `ZRANDMEMBER` (6.2), which decision 6 samples with. Redis before 6.0 has no ACL users (one password with full access) and is refused in any case. Redis 8.0 is accepted at connection but not tested (not maintained).
   - **Version-dependent features**, reported honestly rather than refused: Redis 6.2 has no `ACL DRYRUN` (the allow-list is then not evaluated, decision 4) and no read-only key permissions; Valkey's command log needs 8.1; per-database ACL permissions need Valkey 9.1.
   - **The server's license does not reach the agent's code.** The agent speaks the RESP wire protocol to a server someone else runs, as a client; it links no Redis or Valkey code, ships none, and copies none (the client is written from the protocol documentation, and no server source or test is ported into the repository). RSALv2 restricts offering Redis as a managed service or a commercial product built on it, SSPLv1 section 13 and AGPLv3 section 13 impose source obligations on whoever offers a (modified, for the AGPL) server to users over a network: none of this applies to a program that connects to a server. The agent's Apache-2.0 license and ADR-0005 are unaffected.
   - **Dev and CI images**: the dev environment and CI pull the upstream images by tag and digest, unmodified, and run them as test tools. The repository neither vendors nor redistributes them, and no release artifact (agent `.deb`, console image, deployment bundle) contains Redis or Valkey; `deploy/` gains no Redis (the console uses none, [02-architecture.md](../02-architecture.md)). Users who run `make dev` pull the images under their own licenses: `dev/README.md` names the license of each Redis line (BSD-3-Clause up to 7.2, RSALv2 / SSPLv1 for 7.4, RSALv2 / SSPLv1 / AGPLv3 from 8.0) and of Valkey (BSD-3-Clause). The default dev service of the pair is Valkey (BSD); the Redis service is there because the engine is supported.
3. **Transport and authentication** (ADR-0039 decision 6). `targets[].redis.tls`, `targets[].redis.ca_file`, as for the other engines:
   - `verify_full` (default): TLS 1.2 or 1.3 from the first byte (RESP has no in-protocol upgrade), certificate verified against the pinned `ca_file` (then the only trusted root) or the system store, host name (DNS or IP SAN) checked. **Client certificate**: optional, `redis.client_cert` and `redis.client_key` (PEM files owned by the agent's user, `0600` or `0640` with the agent's group, refused otherwise; the key file is opened with `O_NOFOLLOW` and its owner and mode are checked with `fstat` on the opened descriptor, as [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md) does for audit logs, so a swapped path cannot pass the check; the key is read into zeroized memory and never sent anywhere but the TLS handshake), because Redis's `tls-auth-clients` defaults to `yes`. The certificate does not replace the ACL user: the agent always authenticates with `AUTH`.
   - `disable`: a Unix socket (`socket`) or a loopback IP literal only (never `localhost`); a Unix socket requires it. On a Unix socket the agent checks the server's peer credentials (`SO_PEERCRED`, `peer_cred()`) against the uid declared in `redis.server_uid` before sending `AUTH` (security review L1). The default, the socket file's owner, is trusted only when no other user can write to the socket's parent directory (as with `/run/redis`, owned by the server's user) and when that owner is not the agent's own uid; if the parent directory is writable by others, world-writable and sticky `/tmp` included, an explicit `server_uid` is required and its absence is a configuration error (re-review N2). A loopback TCP port has no such check: another local process bound to the port first would receive the password (residual risk).
   - **No `disable_insecure`.** `AUTH` sends the password itself (no challenge, no SCRAM), as an LDAP simple bind does: cleartext on a network is refused outright ([ADR-0029](0029-openldap-connector.md) decision 2).
   - **The `default` user is never the agent's account**: `account: default` is a configuration error. The account is a named ACL user with a password (`account` and `secret` required; no `nopass` account). The server's own `default` user, when enabled without a password, is **reported, not refused** (decision 4).
4. **Account: an ACL user with an explicit allow-list** (ADR-0039 decision 5, I4). Recommended in [05-security.md](../05-security.md#recommended-database-accounts-read-only) once implemented:

   ```
   # Discovery (Redis 7.0+ and Valkey; on Redis 6.2: "~*" instead of "%R~*", and no +acl|dryrun)
   ACL SETUSER databastion reset on #<SHA-256 of a random password of 32 bytes or more> \
     -@all +select +scan +type +getrange +hrandfield +hstrlen +hmget \
     +srandmember +zrandmember +lrange +xrevrange +info +acl|dryrun \
     resetkeys %R~* resetchannels
   # Audit, added only when Audit is configured for the target
   ACL SETUSER databastion +slowlog|get +acl|log +client|list
   # Valkey 8.1+, Audit
   ACL SETUSER databastion +commandlog|get
   # Optional: Valkey 9.1+, the monitored databases only
   ACL SETUSER databastion resetdbs db=0
   # Optional: a Cluster replica declared as the target (decision 5)
   ACL SETUSER databastion +readonly
   # Recommended where the command exists (Redis 7.2+, Valkey): sampling leaves LRU / LFU untouched
   ACL SETUSER databastion +client|no-touch
   ```

   Each command and why it is needed:
   - `+select`: walk the logical databases listed by `INFO keyspace` (`SCAN` is per database).
   - `+scan`: list key names, `O(1)` per call with `COUNT` (decision 6). `KEYS` is never granted: one `O(N)` call that blocks the server for the whole keyspace.
   - `+type`: one `O(1)` call per key to choose how to sample it.
   - `+getrange`: strings, `GETRANGE key 0 4095`. `GET` is never granted, but the bound is the client's, not the server's: `GETRANGE key 0 -1` reads a whole string as `GET` does. Leaving out `GET` keeps the list to commands the connector sends; it is not a server-enforced limit, and docs/05 must not present it as one.
   - `+hrandfield`, `+hstrlen`, `+hmget`: hashes. `HRANDFIELD key n` (distinct field names, no values), then `HSTRLEN` per field, then `HMGET` of the fields whose value is at most 4 KiB: every hash value read is bounded before it is read. `HRANDFIELD … WITHVALUES` and `HGETALL` would return values of any size.
   - `+srandmember`, `+zrandmember`: sets and sorted sets, `n` distinct random members (positive count). Members cannot be measured first: their size is bounded by the client's reply cap (decision 1).
   - `+lrange`: lists, `LRANGE key 0 n-1` (the head; `O(n)` from the head).
   - `+xrevrange`: streams, `XREVRANGE key + - COUNT n` (the newest entries; `O(log N + n)`).
   - `+info`: `INFO server` (engine, version, mode), `INFO replication` (role), `INFO keyspace` (the databases that hold keys), `INFO stats` (Audit's `sync_full`), `INFO cluster`. An ACL cannot restrict `INFO` by section; the sections read are the ones listed, and `executable`, `config_file` and the replication peers' addresses are never kept or logged (they are compared, decision 5, or ignored).
   - `+acl|dryrun` (Redis 7.0+, Valkey): `check()`'s evaluation of the account below.
   - `+client|no-touch` (Redis 7.2+ and Valkey, to verify per version): the connector sends `CLIENT NO-TOUCH ON` after the handshake, so its reads do not change the keys' access time or frequency (and so the server's eviction choices). Lazy expiration still applies: on a **primary**, a `TYPE` or a read of an expired key deletes it, a write the agent causes without sending one; this is one more reason to declare a replica for Discovery (decision 5; security review L5). Without the grant, or on Redis 6.2, the command is not sent.
   - Audit only: `+slowlog|get`, `+acl|log`, `+commandlog|get` (Valkey 8.1+), and `+client|list` to attribute log entries to users (decision 8).
   - **Not granted, unlike ADR-0039's list**: `strlen` (`GETRANGE 0 4095` is already bounded), `hlen`, `scard`, `zcard`, `llen` (a positive count already returns at most the members that exist; the row estimate is a key count, decision 6), `ttl` (not needed to classify), `acl|whoami` (`AUTH <user>` names the user without ambiguity, and `ACL DRYRUN` takes that name), `client|setname` (`HELLO … SETNAME` needs no grant). **Added to ADR-0039's list**: `select`, `hmget`, `xrevrange`, `acl|dryrun`, `client|list`, `commandlog|get` (named there as "Valkey's command-log read") and the optional `readonly`.
   - **Never**: any write command; `GET`, `MGET`, `HGETALL`, `SMEMBERS`, `DUMP`, `KEYS`, `SORT`, `MONITOR`, `SYNC`, `PSYNC`; `CONFIG`, `DEBUG`, `MODULE`, `EVAL*`, `FCALL*`, `FUNCTION`, `SCRIPT`; `ACL GETUSER` / `ACL LIST` (password hashes) and every other `ACL` subcommand but `dryrun` and `log`; `SLOWLOG RESET`, `COMMANDLOG RESET`; `CLIENT KILL`; pub/sub (`resetchannels`).
   - **Key patterns and databases are declared, and the agent never sends a command that may be refused** (security review H3). Every refusal writes an `ACL LOG` entry, so refused commands would overwrite the 128-entry ring Audit reads and make the agent raise incidents about itself. The ACL's key patterns are `%R~*` (read-only key access to every key, Redis 7.0+ and Valkey), or narrower read patterns (`%R~app:*`) where only some prefixes are to be monitored; `~*` on Redis 6.2, which has no read-only patterns (no write command is granted anyway). When they are narrower than `*`, the operator **declares them in `agent.yaml`** (`redis.key_patterns`, globs with the server's syntax, at most 64; default `["*"]`), and likewise the databases the account may select on Valkey 9.1+ with `db=` (`redis.databases`, default every database). `SCAN` still lists every key (Context): the connector **filters the key names locally against the declared patterns before any `TYPE`**, and selects only declared databases. `check()` confirms the declaration with `ACL DRYRUN <own user> type <a constant key matching each declared pattern>` and, on Valkey 9.1+, `ACL DRYRUN … select <db>`; a declared pattern or database the account cannot read gives `privilege.declared_keys_not_readable` (count), and Discovery skips it. The first `NOPERM` met anyway (a declaration that does not match the ACL) **ends the walk of that database** (the database counts 1 in `skipped_not_readable`, as ADR-0035 decision 3 counts an unreached database) and reports `privilege.declared_keys_not_readable`, so a wrong declaration costs at most one `ACL LOG` entry per database and scan (re-review N4). Names of keys outside the declared patterns are dropped at once, never normalized nor kept.
   - **Password**: given as `#<sha256>` so the ACL file does not hold it in clear. Redis stores ACL passwords as unsalted SHA-256, so the password must be random and long (32 bytes or more), never a reused one.
   - **`check()` proves the allow-list without `ACL GETUSER`**, which would expose every user's password hash. On Redis 7.0+ and Valkey, it runs `ACL DRYRUN <own user> <command> <constant args>` for a closed list of representative commands, at most every 10 minutes per target: writes (`set`, `del`, `unlink`, `hset`, `lpush`, `sadd`, `zadd`, `xadd`, `expire`, `rename`, `restore`, `copy`, `move`, `flushdb`, `flushall`, `swapdb`, `migrate`), reads beyond Discovery (`get`, `mget`, `hgetall`, `hget`, `smembers`, `zrange`, `lpos`, `xread`, `dump`, `keys`, `sort`), administration (`config|get`, `config|set`, `debug`, `module|load`, `module|list`, `shutdown`, `replicaof`, `failover`, `save`, `bgsave`, `client|kill`, `acl|setuser`, `acl|getuser`, `acl|list`, `slowlog|reset`, `monitor`, `sync`, `psync`), scripting (`eval`, `evalsha`, `eval_ro`, `fcall`, `fcall_ro`, `function|load`, `script|load`) and pub/sub (`publish`, `subscribe` on a constant channel). `DRYRUN` runs nothing and logs nothing (Context). `OK` or a key- or channel-level denial means the command is allowed for some key or selector; only a command-level denial, recognized by its fixed prefix for that server version, counts as denied; any other answer counts as not evaluated (fail closed). Outcome, as closed notes with counts (decision 9): `privilege.write_actions`, `privilege.read_beyond_discovery`, `privilege.admin_commands`, `privilege.scripting`, `privilege.pubsub_channels`. On Redis 6.2 nothing can be probed without writing to `ACL LOG` (no `DRYRUN`): see the refusal list below.
   - **Refusal list** (security review M4). When the account can run any of `config|set`, `module|load`, `module|loadex`, `debug`, `acl|setuser`, `acl|deluser`, `acl|load`, `eval`, `eval_ro`, `evalsha`, `evalsha_ro`, `fcall`, `fcall_ro`, `function|load`, `replicaof`, `slaveof` (both probed: they are distinct commands), `migrate`, `cluster|meet` or `cluster|setslot` (each gives whoever holds the agent's credentials code execution, file writes, the dataset, the topology or every other account on the server), Discovery and Audit **do not run** for the target (`permission_denied` on the scan; Audit stays None with `audit.stream_not_available`) and `check()` reports `privilege.admin_commands` or `privilege.scripting`. **A refusal-list command whose evaluation is "not evaluated" counts as allowed** (fail closed). This is the counterpart of the SQL Server refusal list of ADR-0039 decision 5. The other over-privilege notes are reported without refusing. **Redis 6.2** has no `ACL DRYRUN`, so the refusal list cannot be evaluated there: a Redis 6.2 target is refused (`unsupported`, note `privilege.not_evaluated`) unless the operator opts in locally with `redis.unevaluated_acl: accept`, after which it runs with `privilege.not_evaluated` shown permanently (open question 3).
   - **The server's `default` user** is checked on a second, unauthenticated connection that sends only `HELLO 3` and closes: a success means the `default` user is enabled without a password, so anyone who reaches the port has its rights. It is **reported, not refused** (note `security.default_user_nopass`): it says nothing about the agent's own account. On Redis 7.0+ and Valkey the note is graded with `ACL DRYRUN default <command>` over the refusal-list commands (the count is the number allowed; 0 means an open but harmless `default`). No other command is sent unauthenticated, and the agent never acts as `default`.
5. **Topology: one declared node** (I5, ADR-0039 decision 7, as [ADR-0026](0026-mongodb-connector.md) decision 2).
   - The target is one `host`/`port` or one Unix `socket`. No connection pool, no monitoring connection: one connection per scan (replaced after an error that leaves it unusable, after a reply over a limit, or after 60 s idle), one per `check()`, one per Audit stream.
   - **Sentinel** (`mode` `sentinel` in `HELLO`, or `redis_mode:sentinel`) is `unsupported`: the agent never asks a Sentinel for a primary's address.
   - **Cluster** (`cluster_enabled:1`): the declared node is read alone (its slots); the agent never runs `CLUSTER SHARDS` / `CLUSTER NODES` and never follows a `MOVED` or `ASK` reply, which is counted `skipped_remote` for that key (keys of a slot being migrated). Scanning a whole cluster means declaring each node. The scan's coverage says the target is one node; the target note `coverage.cluster_node_only` (count = 1) makes it visible.
   - **Replicas.** Discovery puts read load on the node it reads, so **declaring a replica is recommended for Discovery** (`role:slave` / `role:replica` in `INFO replication`; replicas are read-only by default). A Cluster replica needs `READONLY` on the connection (`+readonly` in the ACL); the connector sends it only when the node reports itself a Cluster replica. Audit must read the node clients use: `SLOWLOG`, `ACL LOG` and the command log are per node. So a target may declare `redis.discovery_node` (`host`, `port` or `socket`, with the target's account and TLS settings): Discovery reads that node, `check()` and Audit read the target's node. Both are declared in `agent.yaml` (I5). The connector checks that the Discovery node reports a replica role, and reports a mismatch (`check.stage_failed`, label `stage_check`); it never connects to the `master_host` a replica reports, and that address is never kept.
6. **Discovery** (bounded, I4; paced by the core, [ADR-0035](0035-discovery-pacing.md)).
   - **Databases**: those listed by `INFO keyspace` (at most 16 read; a Cluster node has only `db0`, or more on Valkey 9 in cluster mode, to verify), filtered by the job's `databases` (as `db<index>`), rotated per scan. `SELECT <index>`.
   - **Keyspace walk**: `SCAN <cursor> COUNT 500`; the key names are filtered against the declared patterns (decision 4) and the CAS guard (below), then the `TYPE` of each remaining key is asked (one pipeline). Each such batch is one paced unit. Per database at most `redis.max_keys` keys are examined (default 100 000, range 1 000 to 10 000 000, a local limit the console cannot raise) and at most `4 × max_keys / 500` `SCAN` calls are made (a sparse or rehashing table can return few keys per call; security review L7); a walk stopped by either bound, by the scan's time budget or by the pattern bound below counts the database as **1** in `skipped_limit` (its remaining keys are unknown, ADR-0035 decision 3). The walk starts at a cursor derived from the scan's seed rather than at 0, so successive scans do not see the same first keys (ADR-0035 decision 4); because `SCAN` cursors follow the buckets in reverse-binary order, the walk can tell when it has come back to its start, but the call bound above is what ends it. A start other than 0 is allowed by the servers but outside `SCAN`'s documented guarantees; its behavior, in particular with Valkey 8.1's new hash table, is to verify in the integration tests, and the fallback is to start at 0. A key name over 64 KiB is read and discarded without buffering (decision 1) and counted `skipped_limit`; a `SCAN` reply that closes the connection ends **that database's walk** as `skipped_limit`: the connector never reconnects to retry the same cursor (security review M5). `KEYS`, `SCAN … TYPE` and `MATCH` filters built from console input are never used.
   - **Key patterns and what stays in memory** (security review M1): each key name is segmented and normalized as it arrives (decision 7); only the pattern is kept with its type, plus, for the cardinality and record-id rules, **at most 17 distinct surviving literal values per segment position and pattern prefix** (one more than the collapse threshold), in zeroized memory, until the walk of the database ends; and the `n` sample keys per pattern until they are sampled. **Patterns are emitted only after the walk**, when every position has been decided. A walk stopped early decides on the partial view it has (residual risk). Raw key names are never logged, never spooled, never sent. Per database at most 1 024 patterns; beyond, new patterns are not sampled and count `skipped_limit`.
   - **Sampling per pattern** (an "object" for the coverage counters; `n` = the job's `sample_rows`, at most `limits.max_sample_rows`), on the first `n` keys of the pattern met by the walk:
     - **string**: `GETRANGE key 0 4095`;
     - **hash**: `HRANDFIELD key 16`, `HSTRLEN` of each field, `HMGET` of the fields of at most 4 KiB (larger ones are skipped and counted);
     - **list**: `LRANGE key 0 15`; **set**: `SRANDMEMBER key 16`; **sorted set**: `ZRANDMEMBER key 16` (members only: scores are not read);
     - **stream**: `XREVRANGE key + - COUNT 16` (the field / value pairs of the newest entries; entry ids are not used);
     - **module types** (`ReJSON-RL`, `TSDB-TYPE`, `MBbloom--`, `vectorset`, and any other type outside the six above, including the modules bundled with Redis 8): not read; the pattern counts `skipped_unsupported` and the note `coverage.module_types_not_sampled` (count of patterns). JSON documents are a follow-up (open question 5).
     Every value is cut to 4 096 bytes on a character boundary, must be valid UTF-8 (otherwise skipped, as MongoDB binaries are), and goes only through `RawValue`, `ScanJob::classify` and `classifiers::masking` (I2). Per pattern and field at most `n` values are pooled.
   - **Cost on the server**: `SCAN` with `COUNT 500` is `O(1)` amortized per call; `TYPE`, `HSTRLEN` are `O(1)`; the random-member commands with a positive count `n` are `O(n)` (with a copy of the whole object only when it holds fewer than about `3n` members, so bounded by `3n`); `LRANGE 0 15` and `XREVRANGE … COUNT 16` are `O(16)` from the end they read; `GETRANGE 0 4095` is `O(4 KiB)`. No command is `O(N)` in the keyspace or in a big key. With pacing at the default 1 %, 100 000 keys take a few minutes of wall time and about 1 % of one server core while the scan runs.
   - **Big keys**: a big key costs no more than a small one, except for elements that are themselves big (set, sorted-set, list and stream members cannot be measured before reading). The client's reply cap closes the connection on an oversized reply; the server has still built that reply in its output buffer (`client-output-buffer-limit` for normal clients is unlimited by default), which is a residual risk. The key's pattern counts `skipped_limit` for that key, and the walk goes on after reconnecting.
   - **Coverage counters**: `objects_sampled` (patterns sampled), `skipped_not_readable` (declared patterns or databases the account cannot read, and a database whose walk an unexpected `NOPERM` ended, decision 4), `skipped_unsupported` (module types, CAS ticket keys), `skipped_limit` (key and call budgets, pattern bound, oversized key names and replies), `skipped_remote` (`MOVED` / `ASK`), `skipped_error` (any other failure on one key: a key deleted or retyped since `SCAN` gives no error worth reporting and is simply skipped).
   - **CAS store guard** (ADR-0041 decision 5 and its phase 9 forward obligation L7; security review M6): a key whose name contains the ticket-id shape `(TGT|ST|PT|PGT|OC|AT|RT|[A-Z]{2,4})-\d+-` **anywhere** (not only at the start of the name or of a segment) is **never read and never reported, not even as a pattern**; it is counted in `coverage.cas_guard_tripped`. The CAS Redis ticket registry's key prefix (the `CAS_TICKET` family, to confirm against CAS 8.0 before implementation, open question 9) and the patterns listed in `targets[].redis.cas_stores.ticket_registry` are guarded by name in the same way. With the registry's `crypto` enabled the ids in key names may be digests that the shape does not match: the name guard is what protects them. The **value tripwire** of the shared sampling path searches for the ticket-id shape anywhere in the first 4 KiB of a value, unanchored, for this connector; a match guards **that key** (its value is dropped before classification and the key is not read again), not the whole pattern, so one stray value cannot hide the pattern's other keys (re-review N5). `check()` asks `ACL DRYRUN <own user> getrange <a guarded key name>` and reports `privilege.ticket_credentials_readable` when the account could read a guarded key (Redis ACLs have no negative key patterns: on a server shared with a CAS ticket registry, the remedy is positive patterns for the application prefixes, declared as in decision 4). In Audit, a log entry naming a guarded key is reported as a read of the object `*` and is never dropped; the ticket id is never kept (decision 8). The signal `signature.cas_ticket_read` is set **only** on a name-guard match (the CAS prefix or `cas_stores`) or on the strict ticket prefixes `TGT|ST|PT|PGT|OC|AT|RT`; a match on the generic `[A-Z]{2,4}` shape alone gives the read of `*` without the signal, since that shape also matches unrelated identifiers (re-review N5).
7. **Key names, `Location` and fingerprints** (ADR-0039 decision 7, [ADR-0009](0009-name-normalization-and-item-sanitization.md)). This is the central I2 question of the connector.
   - **Segmentation.** A key name that is not valid UTF-8 becomes `*` as a whole, and so does any segment that is not (security review M1). A key name is split on a closed set of separators, `:`, `/`, `|` and `.`; the content of a Cluster hash tag (`{…}`) is a segment. Inside a segment, `_`, `-` and `#` separate **tokens**. The whole key is also scanned as one string, with `_`, `-`, `#` and the separators read as spaces, so a value split across segments is still found (as `names::normalize_path` does).
   - **A segment becomes `*`** when it: touches a classifier match (e-mail, IBAN, card, NIR, phone, AWS key id, password hash…); holds any digit run (record identifiers, which `Identifier` excludes, not only long ones: `user:42:email` becomes `user:*:email`); is high-entropy (hex or base64 of 16 characters or more, a UUID, a mix of letters and digits that looks generated); contains a character `Identifier` forbids; matches the first-name list; or is an IP address. The rules are those of `names.rs` with digit runs treated as values whatever their length.
   - **A position becomes `*` by cardinality**, as MongoDB's maps keyed by data do: under one pattern prefix, a segment position with more than 16 distinct surviving values across the keys of the walk is collapsed (`cache:home`, `cache:about`… become `cache:*`). The rule also applies **token by token** inside a segment (`order_jdupont_2024` and 16 other `order_<name>_…` keys give `order_*_*`). Patterns are compared and merged after the collapse; at most 4 rounds.
   - **Record-id rule** (security review M1): a segment position collapses as soon as **2 or more distinct values precede the same suffix template** (`session:jdupont` and `session:amartin`, or `user:jdupont:email` and `user:amartin:email`, give `session:*` and `user:*:email`), and likewise for a token position. This over-masks fixed names that share a suffix (`config:prod:url` and `config:test:url` give `config:*:url`), which ADR-0009 accepts: a lost name is a smaller harm than a leaked value. A position holding a single value across the whole walk is kept only if the other rules let it through.
   - **What leaves the agent** is the pattern only: never a raw key name, never a fingerprint of a key name (a fingerprint of a low-entropy key would be an oracle for its value). A finding's row estimate is the number of keys of the pattern seen by the walk (a lower bound when the walk stopped early).
   - **Values in key names are findings.** The segments replaced because a classifier matched them are classified like values, with masked samples and fingerprints of the **value** through `classifiers::masking` (I2), under the field `#key` of the pattern: a server whose keys embed e-mail addresses reports a `pii.email` finding on `user:*`, field `#key`. Hash field names replaced the same way are reported under the field `#field`.
   - **`Location`** (to be written into the contract's `Location` description, P9-C): `engine` = `redis` or `valkey`; `database` = `db<index>`; `schema` = the Redis type (`string`, `hash`, `list`, `set`, `zset`, `stream`), which also tells `value` of a string from a hash field named `value`; `object` = the normalized key pattern; `field` = `value` for strings and for list, set, sorted-set members; the normalized field name for hash fields and stream entry fields (field names go through the same rules, cardinality included, so a hash keyed by data gives `*`); `#key` or `#field` for values found in names.
   - **The contract cannot carry `user:*:email` today**: `Identifier` excludes `:` and `/` (they keep URLs and `key=value` out). Options: (a) a new `KeyPattern` schema for these engines; (b) rewriting `:` and `/` to `.` before the uplink. **Decision: (a)**, written in P9-C with a `security-reviewer` review (security review M2):
     - **Schema**: segments separated by `:` or `/` (and `|`, `.`), each non-empty (no `//`, no leading or trailing separator), each following `Identifier`'s plain-name rules (no `@ = ; \ ' "` backquote `< > ( ) ,` or control and format characters); the `Identifier` digit-run `not` rule applied **per segment** after splitting on `: / | .`; `maxLength` 256; a first segment that is a URL scheme (`javascript`, `data`, `vbscript`, `file`, `http`, `https`, `mailto`, compared without case) is refused, and the agent's normalizer turns such a segment into `*` first.
     - **Where**: in `Location`, `if engine in [redis, valkey] then object: KeyPattern else object: Identifier`; `ObjectRef` has no engine, so the console enforces the same rule from the target's engine. Tests: a PostgreSQL, MySQL, MongoDB or OpenLDAP item whose object contains `:` is still rejected, by the schema and by the console.
     - **Rendering rule** written into the contract: the console renders a key pattern only as escaped text, never as a link or `href`, never unescaped in e-mail HTML or in webhook payloads other than as a JSON string, and guards CSV exports against formula injection (a leading `= + - @`, tab or carriage return is prefixed).
     - Items of these engines are held until the console lists their engine token (ADR-0042), and a console that lists it implements the new schema, so no further capability is needed. The agent's item sanitizer replaces a pattern that matches neither schema with `*` (ADR-0009). (b) is rejected: `.` is itself a common separator and a frequent character inside segments, so the console would show patterns no application uses, and an operator could not search the server for them.
8. **Audit: Limited at best, from the servers' own logs** (ADR-0039 decision 3).
   - **Sources**, polled over the Audit stream's own connection every `redis.audit_poll_interval_s` (default 10 s, at least `limits.min_audit_poll_interval_s`):
     - **`SLOWLOG GET 512`** (Redis, and Valkey before 8.1) or **`COMMANDLOG GET 512 slow`** (Valkey 8.1+, where `SLOWLOG` reads the same log, to verify) (`audit_source` `redis_slowlog`);
     - **`COMMANDLOG GET 512 large-reply`** (Valkey 8.1+) (`redis_commandlog`): commands whose reply exceeded the server's threshold, with the reply size in bytes, which goes to the event's `bytes` (when the console takes that field);
     The counts are sized to the worst case (security review M5): an entry holds at most 32 arguments of at most 128 bytes plus its fixed fields, about 5 KiB with RESP framing, so 512 entries stay under 4 MiB; the request's cap is 4 MiB. An attacker who fills the log with large entries therefore cannot make a poll exceed its cap and blind Audit; entries beyond the 512 newest since the last poll are counted in `audit.records_dropped` (the id gap below).
     - **`ACL LOG 128`** (`redis_acl_log`): failed authentications, and denials of the agent's own user. The `object` of an entry is not cut by the server: an object over 64 KiB is discarded without buffering (decision 1) and becomes `*`;
     - **`INFO stats` `sync_full`** (`redis_sync`): full synchronizations.
     A cursor per log (the highest entry id read, persisted through the core) avoids reading an entry twice; entry ids are progressive, so **a gap between the cursor and the oldest entry returned means entries were lost** (ring buffer overrun between polls, or a `RESET`): counted for 24 h in `audit.records_dropped`. A server restart resets the ids (detected through `run_id` in `INFO server`, which is compared, never sent). On Redis before 7.2, `ACL LOG` entries have no id: they are recognized by their fields and `count`, and a grown `count` is reported as its delta. The first start reads from the newest entry (no history replay).
   - **Reduction at parse time** (ADR-0039 decision 3): from each log entry the parser keeps the command name (compared with a closed list; any other name is `unknown`), the key arguments at the positions the closed command table gives (below), an optional numeric argument where a signal needs it (`SCAN`'s `COUNT`), the client's IP (port dropped), the client name, the connection id from `ACL LOG`'s `client-info`, the timestamp and the size or duration. **Every other argument is dropped before any buffering beyond the parser** and is never logged: values, `AUTH` / `HELLO AUTH` / `ACL SETUSER` / `MIGRATE … AUTH` arguments (whether the server redacts them depends on the version; the agent does not rely on it), script bodies, channel names, and the arguments of `KEYS` and of `SCAN … MATCH`, which are glob patterns typed by a client and may hold values. `client-info` is reduced to `id`, `addr`, `name`, `user` and `db`.
   - **Key arguments become learned patterns, never normalizer output alone** (security review H1). A key read from a log entry (or an `ACL LOG` key `object`) is matched **segment by segment against the patterns learned by the last completed scan of the same database** (the current scan generation, persisted through the core with the patterns so a restart keeps them). A match gives that pattern. Without a match (no scan yet, a prefix the walk did not reach, a key outside the declared patterns, a key created since, or a prefix with too few keys for the cardinality rules to have spoken, such as `HGETALL session:jdupont`), the object is the longest learned **literal** prefix of the key followed by `*` (`session:*` if `session:` is a learned prefix), and `*` otherwise. The normalizer of decision 7 still runs on the result as a second gate, never as the first. An argument the server cut at 128 bytes is matched on its complete segments only. When the database of the entry is not known, only patterns learned in every scanned database with keys are used, else `*`.
   - **Key positions** come from the servers' own key specifications (the `key_specs` of the commands' JSON files in the Redis and Valkey sources, Redis 7.0+), turned into the closed command table at build time and checked per supported version by integration tests: commands whose keys sit at variable positions (`MIGRATE … KEYS`, `SORT … BY / GET / STORE`, `OBJECT <subcommand> <key>`, `XREAD` / `XREADGROUP … STREAMS`, `EVAL` / `FCALL` with `numkeys`, `GEORADIUS … STORE`, `ZUNIONSTORE` and friends with `numkeys`, `LMPOP` / `ZMPOP`, `BITOP`) are tested one by one. A command missing from the table, or whose arguments do not fit its specification, gives the object `*` and no argument is read: a wrong position would push a value through the normalizer.
   - **Actions**: a closed table maps command names to `read` (`GET`, `MGET`, `HGETALL`, `HGET`, `HMGET`, `HVALS`, `SMEMBERS`, `SUNION`, `ZRANGE…`, `LRANGE`, `XRANGE`, `XREAD`, `GETRANGE`, `DUMP`, `KEYS`, `SCAN` family, `SORT_RO`…), `write` (writes and deletions, `FLUSHALL`, `RESTORE`, `MIGRATE`), `ddl` (`CONFIG SET`, `MODULE LOAD`, `FUNCTION LOAD`, `SCRIPT LOAD`) and `dcl` (`ACL SETUSER`, `ACL DELUSER`). Scripts (`EVAL*`, `FCALL*`) are `write` of the object `*` and always reported (their keys are not reliably known, as server-side JavaScript on MongoDB). An unknown command name is a `read` of `*`, never dropped (fail closed). The database is `db<index>` when `INFO keyspace` shows a single database with keys, `*` otherwise (slow-log entries carry no database). `ACL LOG` `auth` entries are `auth_failure` events, the name tried always fingerprinted (core rule). Denials of **other** users give no event (nothing was read, as for MongoDB's `Unauthorized`); denials of the **agent's own user** are reported, with the command's action and no rows (someone else using the agent's credentials), **except** those whose `client-info` `id` is one of the agent's own connection ids (from each connection's `HELLO` reply, valid until the server restarts; security review H3): the agent sends no command that may be refused (decision 4), so such an entry is a declaration mismatch, reported through `check()` rather than as an incident. Own-user denials from any other connection are always reported. Reads of keys guarded by the CAS store guard are reported as a `read` of `*` with `signature.cas_ticket_read` (decision 6).
   - **Principal**: slow-log and command-log entries record no user. When a poll finds new entries, the stream runs one `CLIENT LIST` (reply capped at 4 MiB, otherwise not attributed) and maps each entry's `addr:port` to the `user` of the connection still open at that address, **only if that connection is older than the entry** (its `age` reaches back before the entry's timestamp, with a 2 s margin: a port reused by a newer connection is not attributed; security review L2); the rest of the listing is dropped at parse time. Entries whose connection has closed, and `sync_full` events, have **no recorded account**. The contract gets an explicit marker for it, a third branch of `Principal`'s `oneOf`: **`account_not_recorded: true`** (with `client_addr` and `application` when known), not `db_user` `*`, which means "several accounts" on CAS and is a legal Redis user name (security review M3; P9-C, compatible: such events are held until the engine token is listed). Console rules, written with P9-C and P9-E for [ADR-0021](0021-access-event-correlation.md) decision 6: the dedup key's principal part for such an event is `unknown:<SHA-256 of the client network>`, or `unknown:local`, or `unknown:none` without an address (the case of `sync_full` events with no replica entry); no per-principal baseline is built for them (the anomaly part of the score is not computed), as for fingerprinted principals without an address. Account names go through the usual rule (names that do not match `db_user`, and every failed authentication, are fingerprinted). `client_addr` follows the target's `client_addr` option; `application` is the sanitized client name (client names can hold values: accepted residual risk, security review L6).
   - **Full synchronizations**: when `sync_full` grows, the stream reads `INFO replication` and reports one `read` of `*` per synchronization with the new signal `signature.full_sync` and, when a replica entry not listed in `targets[].redis.replicas` (operator-declared replica addresses, compared only, never connected to) shows its address, that address. A full synchronization copies the whole dataset: a replica's first sync is routine, `redis-cli --rdb` or a rogue replica is an export.
   - **The agent's own account** (as [ADR-0027](0027-mongodb-audit.md) decision 7 and ADR-0029 decision 9): an entry is the agent's only when its connection is one of the agent's own, recognized by the agent's own connection ids or by its own local `addr:port` as the server reports it (security review L2), never by user or client name alone (any client can name itself `databastion-agent`, and anyone with the agent's credentials uses its user). Such an entry is left out only when it is one of the connector's own command shapes (decision 6) and the agent's reads of its pattern stay within `limits.max_sample_rows` per 24 h. Every other command with the agent's user, from any connection, is reported, and so is every write.
   - **Signals** (decision 12): `signature.full_sync`; `volume.large_reply` (a `large-reply` command-log entry; Valkey 8.1+); `shape.keyspace_enumeration` (`KEYS`, or a `SCAN` with a `COUNT` above 1 000, seen in a log entry; `redis-cli --scan` uses `COUNT 10` and is fast, so it never sets this signal); `signature.cas_ticket_read` (decision 6). The volume × sensitivity score has no rows to work with (no source gives a row count), so it relies on these signals, on `bytes` where present, and on the patterns' sensitivity.
   - **Levels** (`check()` and the stream use one rule):
     - **Limited** once a slow-log or command-log entry was read in the last 24 h (the log is enabled and readable), with the note `audit.slow_operations_only`;
     - **None** before that (`audit.limited_pending_first_record`), when only `ACL LOG` is readable (`audit.acl_log_only`: failed authentications only), when no source is readable (`audit.log_not_readable`), or with `audit.stream_not_available` when Audit is not configured or refused (decision 4);
     - **never Partial or Full**: no source records the account (only `CLIENT LIST` attribution, best effort), the database, or the rows returned; the slow log sees only what is slow, the large-reply log only what is large, and every log is a ring buffer. Setting `slowlog-log-slower-than 0` makes every command visible until the buffer overruns, still without account or volume: Limited.
   - **What is honestly not seen**, written in [08-engine-capabilities.md](../08-engine-capabilities.md) once measured: every fast read (with the default 10 ms threshold, almost every `GET`, `HGETALL` and `SCAN` of an export by `redis-cli --scan` and `GET` in a loop); reads inside scripts and transactions beyond the command name; reads on other nodes of a Cluster or on replicas not declared; entries overwritten between polls; reads by connections closed before the poll, without their account; `MONITOR` sessions themselves (unless slow); anything done through modules' own commands beyond their name.
   - **Excluded sources**: `MONITOR` (every command's arguments, values included, cross to the agent, and the server's throughput drops; ADR-0039); keyspace notifications (writes and expirations only, through pub/sub, which `resetchannels` forbids, and enabling them needs `CONFIG SET`); `LATENCY` (no client, no key).
9. **`check()`**: reachability (TCP or socket, peer credentials on a socket, TLS, `AUTH`, `HELLO 3`), engine and version (`INFO server`: Valkey when `server_name:valkey` or `valkey_version` is present, then its version from `valkey_version`; Redis otherwise, from `redis_version`), compared with the declared engine (`check.server_is_valkey` on a `redis` target, `check.server_is_redis` on a `valkey` target, as `check.server_is_mariadb` / `check.server_is_mysql` do; the target is still checked with the engine read); mode (Sentinel refused, Cluster noted); role and the Discovery node's role (decision 5); the privilege evaluation, refusal list and declared key patterns and databases of decision 4; the `default` user probe; the CAS guard's key privilege; the Audit sources' readability and the level of decision 8. Budget: 3 s per command, 9 s in total; the privilege report is recomputed at most every 10 minutes per target. Engine version and edition go to the agent's logs only.
10. **Errors** are reduced to a closed failure code, the error's first word as `EngineCode` (decision 1) and a closed stage: `WRONGPASS`, `NOAUTH` are `authentication_failed`; `NOPERM` is `permission_denied` (in a scan it ends that database's walk, decision 4); `LOADING`, `BUSY`, `MASTERDOWN`, `CLUSTERDOWN`, `TRYAGAIN` and connection failures are `target_unreachable`; a reply over a limit is `resource_limit`; a deadline is `timeout`; a refused version, Sentinel, a `HELLO 3` refusal and a protocol violation are `unsupported`.
11. **I1, I3, I5 and local detection.**
    - I1: the agent opens outbound connections to the declared node (and the declared Discovery node) only, never listens, never subscribes, and refuses push frames.
    - I3: the password, the client key and any CA material stay on the agent host; they are never logged, never sent to the console, and the password only ever travels inside TLS or over a Unix socket or loopback (decision 3).
    - I5 and [ADR-0006](0006-target-discovery.md): no topology following (decision 5). Port 6379 alone is reported as `redis` (it cannot tell the engines apart); a `valkey-server` process makes it `valkey`. The agent never connects to a detected server.

### Residual risks
- **Own parser.** RESP from a possibly hostile server is parsed by connector code: bounded before allocation, fail closed, property-tested and fuzzed, still code to maintain.
- **Server memory on oversized replies.** The client closes the connection on an oversized member, but the server has built the reply already; set, sorted-set, list and stream members cannot be measured before reading (open question 4).
- **Partial walks decide on a partial view** (security review M1). Patterns are emitted after the walk, from at most 17 values per position; a walk stopped by its budget decides with the keys it saw, so a position with values spread thinly can be emitted as a literal when 2 distinct values with the same suffix were not both seen. The second gate (the normalizer's value rules) still applies.
- **Audit objects are coarse.** Keys not covered by a learned pattern are reported under their longest learned literal prefix plus `*`, or `*` (decision 8): an incident may name less than what was read.
- **Loopback port squatting** (security review L1): with `disable` on a loopback TCP port, a local process that binds the port before the server receives the agent's password; a Unix socket with the peer-credential check avoids it.
- **What the Audit grants reveal** (security review L3, for [05-security.md](../05-security.md)): with `+slowlog|get`, `+commandlog|get` and `+client|list`, whoever holds the agent's credentials reads other clients' slow-command arguments (values, and on some versions secrets such as `CONFIG SET masterauth`) and the server's connection map (addresses, users, client names). The agent drops them at parse time; the credentials do not.
- **Client names** (security review L6) are client-declared and can hold values; they are sanitized and cut to 64 characters as `application`, not normalized. Accepted, as for `application_name` and `appName` on the other engines.
- **Key names in memory.** Raw key names (at most 17 values per position and prefix for the duration of a database's walk, decision 6) and other users' log arguments (one poll) are in the agent's memory, in zeroized buffers. Normalization has the gaps of [05-security.md](../05-security.md#masking-and-fingerprints): a surname alone, or a short identifier that survives the cardinality rule (16 or fewer distinct values at a position, such as a few customer codes), reaches the pattern.
- **`SCAN` lists names the account cannot read.** Key permissions do not hide names from `SCAN`; names outside the declared patterns are dropped at once, but they did cross to the agent.
- **`ACL DRYRUN` as an oracle.** Whoever holds the agent's credentials can ask which commands any user may run, and whether a user name exists. No password hash is exposed (unlike `ACL GETUSER`).
- **`ACL LOG RESET`.** `+acl|log` also allows `ACL LOG RESET`: stolen agent credentials can clear the failed-authentication log. The agent never sends it; a reset shows as a gap only if entries were lost.
- **Attribution by address.** `CLIENT LIST` attribution matches `addr:port` of connections still open; behind a proxy or NAT every client shares one address, and a short connection is gone before the poll.
- **Start cursor** (decision 6) relies on `SCAN`'s reverse-binary cursor order, outside the documented guarantee; the fallback (start at 0) loses the rotation.
- **Over-privileged accounts outside the refusal list** (for example `+get` or `+@read`) are reported, not refused.
- **Version-dependent server texts.** The `ACL DRYRUN` denial prefixes and the error words differ across versions; an unknown text is "not evaluated", never "denied".

## Rejected alternatives
- **The `redis` crate**: well maintained, but `xxhash-rust` (BSL-1.0) is a mandatory dependency outside the `deny.toml` allow-list, its parser has no bound on bulk strings or lines (a hostile server makes the agent buffer whatever it announces), server error texts (with key names) are kept in its errors, and cluster and Sentinel logic lives in the crate. Bounding replies would mean forking the parser.
- **The `fred` crate**: licenses pass, but no release for 19 months, 93 crates, cluster routing, reconnection and pooling compiled in, library logging, and no reply bounds found.
- **`ACL GETUSER` (granted `+acl|getuser`) to evaluate the account**: returns every user's unsalted SHA-256 password hash.
- **Probing denied commands inside `MULTI` / `DISCARD`**, on every version or only on Redis 6.2 for the refusal list: it runs nothing (the ACL is checked before a command is queued), and the own-connection-id rule could keep it out of incidents, but every probe still writes an `ACL LOG` entry into the 128-entry ring Audit reads (each probe command occupies an entry, refreshed at every round), and with selectors a denial is ambiguous. `ACL DRYRUN` does neither; Redis 6.2 is handled by a local opt-in instead (decision 4).
- **Probing with real writes on a constant key**: breaks the closed read-only command set (I4), as rejected for OpenLDAP.
- **`HSCAN`, `SSCAN`, `ZSCAN` for sampling**: on a small (listpack-encoded) object they ignore `COUNT` and return the whole object in one reply, and the encoding thresholds are server settings (`hash-max-listpack-entries`…) that can be raised; they also return the first members in table order, not a random sample.
- **`HRANDFIELD … WITHVALUES`, `HGETALL`, `GET`**: unbounded values.
- **`STRLEN` before `GETRANGE`, and the length commands**: not needed for a bounded read or for the row estimate.
- **`KEYS`**: `O(N)` and blocking.
- **Following Cluster or Sentinel topology**: connects to addresses the server chooses (I5).
- **`MONITOR`, keyspace notifications, `LATENCY`** as Audit sources: see decision 8.
- **Rewriting `:` and `/` to `.` in key patterns**: see decision 7.
- **Fingerprinting key names** so the console can tell keys apart: a fingerprint of a short, low-entropy name is an oracle for it, and the pattern is what the operator acts on.
- **A refusal floor at Redis 6.0**, as ADR-0039 wrote: 6.0 and 6.1 are not maintained, and decision 6's random sampling needs 6.2.
- **Redis 6.2 accepted with the refusal list unevaluated by default**: a `+@all` account would then be used silently. It is refused unless the operator opts in (decision 4).
- **`HELLO 3 AUTH <user> <password>` as the handshake** (the first draft): one round trip less, but the credentials travel as `HELLO` arguments, which `HELLO` does not keep out of the slow log (no `no-slowlog` flag) and only the server's redaction protects (security review H2).
- **Normalizing Audit key arguments directly** (the first draft): a key with few siblings, or one the scan never saw, goes through the value rules alone, and a login or a name that no rule recognizes reaches the console (security review H1).
- **`db_user` `*` for an account the source does not record**: `*` already means "several accounts" on CAS, and `*` is a legal Redis user name (security review M3).
- **Letting the server refuse reads outside the account's key patterns** (the first draft): every refusal is an `ACL LOG` entry (security review H3).

## Open questions for the maintainer
1. **Accept ADR-0039 decisions 3 to 7 and 9 for Redis and Valkey as refined here** (allow-list of decision 4 instead of ADR-0039's list; refusal floor Redis 6.2). *Recommendation*: accept, so the implementation is held to this ADR and nothing wider.
2. **Unknown account on Redis / Valkey events** (revised after security review M3). Slow-log entries of closed connections and full synchronizations have no account. Options: an explicit `account_not_recorded: true` branch of `Principal` (decision 8); making `Principal` optional for these engines; or dropping such events. `db_user` `*` is rejected (it means "several accounts" on CAS, and Redis accepts a user named `*`). *Recommendation*: the explicit branch, with the dedup and baseline rules of decision 8 (`unknown:<network>`, `unknown:local` or `unknown:none`, no per-principal baseline), in P9-C and P9-E; dropping them would hide the exports Audit exists for.
3. **Refusal list and Redis 6.2** (revised after security review M4). The list of decision 4 stops Discovery and Audit, and "not evaluated" counts as allowed. Redis 6.2 has no `ACL DRYRUN`, so the list cannot be evaluated there. Options for 6.2: refuse it outright; refuse it unless the operator opts in locally (`redis.unevaluated_acl: accept`, `privilege.not_evaluated` shown permanently); or probe the refusal-list commands inside `MULTI` / `DISCARD` with the own-connection-id rule. *Recommendation*: the local opt-in. 6.2 is still maintained, so refusing it outright drops a supported version; the `MULTI` probe would permanently occupy about 20 of the 128 `ACL LOG` entries Audit depends on; the opt-in makes the operator state, on the agent host, that the account was reviewed by hand.
4. **`MEMORY USAGE` before sampling aggregates** (`+memory|usage`, an estimate from 5 sampled elements): would let the connector skip big members before the server builds a large reply, at the cost of one more grant and of an estimate that can miss a single huge member. *Recommendation*: not in the first implementation; revisit after the load runs measure oversized replies.
5. **JSON documents** (RedisJSON, Valkey JSON; built into Redis 8): sampling with `JSON.GET key <path>` would need a grant per module command and a module-aware path walk. *Recommendation*: out of scope for phase 9; count them as `skipped_unsupported` with the note, and open a ROADMAP follow-up if users ask.
6. **`CLIENT LIST` as a volume source** (Valkey 8.0+ per-client `tot-net-out`, to verify): per-connection byte deltas between polls would give a per-user volume for long-lived connections. *Recommendation*: a phase 9 follow-up after measuring its cost on servers with many clients; the first implementation uses `CLIENT LIST` only to attribute log entries.
7. **Engine-matrix size** (13 versions). *Recommendation*: all maintained lines in the weekly matrix (each job takes about a minute), one Redis and one Valkey version in `ci.yml`.
8. **Default dev service.** *Recommendation*: Valkey (BSD) as the default `make dev` service, Redis as a second service in the same profile, both required by the end-to-end job.
9. **CAS Redis ticket registry key prefix** (security review M6). The name guard needs the exact prefix (the `CAS_TICKET` family, to confirm against CAS 8.0's Redis ticket registry source and a running CAS with the Redis registry, with and without `crypto`). *Recommendation*: confirm it in the P9-B implementation PR before the connector samples anything, with a dev CAS + Redis integration test; until then, a Redis target whose keyspace contains a key with that family's prefix counts it under the name guard.

## Implementation obligations (P9-B)
Security review Lows and test obligations the implementation must meet; the P9-F review of the implementation checks each.
- **L1**: on a Unix socket, check the server's peer credentials (`peer_cred()`) against the expected uid before `AUTH` (decision 3); loopback port squatting is a documented residual risk.
- **L2**: before attributing a log entry through `CLIENT LIST`, compare the entry's timestamp with the connection's `age`; recognize the agent's own entries by its own connection ids and local `addr:port` (decision 8).
- **L3**: [05-security.md](../05-security.md) states what the Audit grants expose (other clients' slow-command arguments, on some versions secrets such as `CONFIG SET masterauth`, and the connection map).
- **L4**: decoder rules: blob errors capped and their text discarded; streamed lengths (`$?`, `*?`, `;`) refused; negative lengths other than `-1` refused; map counts checked as twice the pairs; the `HELLO` reply's `modules` array capped (decision 1).
- **L5**: send `CLIENT NO-TOUCH ON` where the command exists and is granted; document that lazy expiration deletes expired keys on a primary, one reason to declare a replica (decision 4).
- **L6**: client names may hold values: accepted residual risk, documented.
- **L7**: bound the number of `SCAN` calls per database, not only the keys and the return to the start cursor (decision 6).
- **L8**: open `client_key` with `O_NOFOLLOW`, then check owner and mode with `fstat` on the opened file ([ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md); decision 3).
- **L9**: if `MEMORY USAGE` is adopted later (open question 4), never with `SAMPLES 0` (a full walk of the key).
- **H1 to H3 tests**: no password in `SLOWLOG`, `COMMANDLOG` or `MONITOR` on any supported version; no `ACL LOG` entry written by the agent with narrowed key patterns or Valkey 9.1 `db=`; Audit objects never hold a literal the scan did not learn; every variable key position of the command table tested per version.
- **M2 tests**: `KeyPattern` refusals (empty segments, URL schemes, digit runs per segment, length), and a non-Redis item with `:` still rejected by the schema and by the console.
- **N1 gate**: the first Redis 6.2 patch release that redacts `AUTH` arguments in `SLOWLOG` is established and becomes the 6.2 refusal floor (decision 2).
- **Single-key families** (residual risk): a family with a single key keeps its literal segments (`user:jdupont:email` when it is the only `user:` key): neither the cardinality nor the record-id rule can decide on one value, so only the value rules of decision 7 protect it. Documented in [05-security.md](../05-security.md#masking-and-fingerprints) with the other normalization gaps.
- **DRYRUN probe list**: it includes every refusal-list command of decision 4 (`module|loadex`, `acl|deluser`, `acl|load`, `evalsha_ro`, `slaveof`, `cluster|meet`, `cluster|setslot` among them), generated from the same constant as the refusal list so the two cannot drift.
- **`unevaluated_acl`** applies to Redis 6.2 only: set on a target that turns out to be Redis 7.0+ or Valkey, it is a configuration error (reported, target refused), and it never overrides a refusal proven by `ACL DRYRUN`. On 6.2 it also makes `check()` report `privilege.ticket_credentials_readable` and the declared-pattern check as not evaluated (`privilege.not_evaluated`), never as passed.
- **Local glob matcher**: the filter of decision 4 follows Redis glob semantics (`*`, `?`, `[…]` with ranges and negation, `\` escapes; byte-wise, case-sensitive) and is property-tested against the server's own matching (`SCAN … MATCH` in the integration tests only, never in production). Declared patterns are never sent to the console nor logged.
- **P9-C details for `account_not_recorded`**: the branch is `account_not_recorded` with `const: true` and `db_user` and `db_user_fingerprint` both absent, and the property is added to `Principal.properties` (which forbids additional properties); the console accepts it only on events of `redis` or `valkey` targets, judged from the target's engine, and never on `auth_failure` events (a failed authentication always names, or fingerprints, the name tried).
- **Release notes**: a future server version whose `ACL DRYRUN` texts the agent does not recognize makes the target refused (refusal-list commands not evaluated count as allowed, decision 4) until an agent release learns them; the release notes and docs/08 say so.
- **M6**: the CAS prefix confirmed before the connector samples anything (open question 9); the unanchored value tripwire tested on values that embed a ticket id after other text.


## Implementation notes (2026-10-15)
Facts of the implementation (P9-B lot 1 #237, lot 2 #239), recorded by the docs-keeper. They change no decision above; where the code differs from the text, the difference is stated for the maintainer.
- **`HRANDFIELD key 17`** (decision 6 writes `HRANDFIELD key 16`): the connector asks for one more field than the collapse threshold of decision 7 and reads at most 16 of them. A hash with more than 16 fields reports every field name as `*`, even when it is its pattern's only key, so the field names of a hash keyed by data never reach the cardinality rule alone (#237 review H2).
- **`TIME` is not used.** The attribution rule of decision 8 compares a connection's `age` with the entry's timestamp on the server's clock. `TIME` is not in the allow-list of decision 4, so `server_time_usec` is read from `INFO server`, in the same pipeline as `CLIENT LIST` (#239 review L4). No grant was added.
- **Redis floor: 6.2.7.** The N1 gate is applied as one constant at 6.2.7, as decided by the refinement of 2026-10-14 (accepted on 2026-10-15). It rests on the [measurements](../measurements/phase9-engine-facts.md#redis-and-valkey-adr-0052): 6.2.0 never slow-logs `AUTH` but logs other clients' `CONFIG SET masterauth` and `MIGRATE … AUTH2` passwords in clear; 6.2.7 and 6.2.24 redact them; 6.2.1 to 6.2.6 were not measured. Until the decision, decision 2's floor reads as 6.2.7 in the agent.
- **Over-masking cascade, accepted under decision 7.** The record-id rule applies at every position, the first included. So two-segment names with different first segments and a value-like second segment collapse to `*:*` (`phone:1` and `addressbook:2` give `*:*`), and many unrelated families merge into one pattern. Decision 7 accepts this: a lost name is a smaller harm than a leaked value. The families merged into one pattern share its sampling budget of decision 6 (the first keys met by the walk). Round-robin sampling across them is a [phase 9 follow-up](../ROADMAP.md#phase-9-follow-ups).
- **Start cursor.** The walk starts at cursor 0, which is the fallback of decision 6, not a cursor derived from the scan's seed. A walk cut by its bounds therefore sees the same first keys at each scan.
- **Own sessions' addresses (2026-10-15, `fix/p9-b-redis-own-slowlog`).** Slow-log entries carry no client id (decision 8), so on a target with Audit enabled (a stream running), every agent session to the target's node (Discovery, `check()`, probes) sends `CLIENT LIST ID <own id>` once after its handshake, when `+client|list` is known to be held, to learn the address the server sees for it. This qualifies "the agent sends no command that may be refused": a stale grant flag can cause at most one own `NOPERM` per server run and account, plus one per session opened concurrently before the first refusal is recorded (#244 re-review L2), counted as a declaration mismatch by `check()`, not raised as an incident. The request is best effort: an error reply (a `NOPERM`, or any other error) stops it for that server run and account; a transport failure or a timeout stops it too, and the session, whose stream may be out of step, is closed and replaced by a new one, which does not send the request again for that run. Without Audit, the command is never sent.
- **Own-read budget across databases (2026-10-16, `fix/p9-b-valkey-own-discovery`).** Slow-log and command-log entries carry no database, so when several databases hold keys their objects are matched against the patterns learned in every database (decision 8), mostly `*`. The own-read budget is still kept per pattern: an entry of one of the agent's own sampling shapes is charged to the pattern its key matches whole in each database where it does (`db<n>` / pattern), never to a learned prefix followed by `*`; when no database's patterns match it whole, it is charged to the event's object `*`. The reported object does not change. Found by the P9-D end-to-end test (Valkey 9.0.6), where the whole scan was charged to `*` and the agent's own reads came back once `limits.max_sample_rows` rows of all patterns together had been read.
- **Poll interval.** No `redis.audit_poll_interval_s` key exists (Consequences). The Audit stream polls at the Audit settings' `poll_interval_s` (default 10 s), with `limits.min_audit_poll_interval_s` as the floor, as the other polled sources do.

## Refinement (2026-10-14, accepted)

Source: the P9-D measurements in [phase9-engine-facts.md](../measurements/phase9-engine-facts.md) (`redis` 6.2.0, 6.2.7, 6.2.24, 7.2.16, 7.4.11, 8.2.10, 8.10.2; `valkey/valkey` 7.2.14, 8.0.11, 8.1.10, 9.0.6, 9.1.2; images pinned by digest; throwaway users with fake marker passwords). Nothing in the text above is edited: where an item and the text disagree, the item applies once accepted.

### 1. Redis 6.2 floor: the N1 gate and other clients' secrets in the slow log (decision 2, decision 8, N1 gate)

- **Context.** With `slowlog-log-slower-than 0` and a user with a marker password (measurements, "First Redis 6.2 patch that keeps `AUTH` / `HELLO … AUTH` arguments out of `SLOWLOG`"):
  - **Redis 6.2.0** does not slow-log `AUTH` or `HELLO` at all; **6.2.7 and 6.2.24** log them as `AUTH (redacted) (redacted)` and `HELLO 3 AUTH (redacted)`. No tested 6.2 release shows the password, so the N1 gate, as worded ("the first Redis 6.2 patch release that redacts `AUTH` arguments in `SLOWLOG`"), is met by every tested release, and decision 1's handshake (`AUTH`, then `HELLO 3` without credentials) never puts the agent's password in the slow log there.
  - **But 6.2.0 logs `CONFIG SET masterauth <value>` and `MIGRATE … AUTH2 <user> <password>` in clear**; 6.2.7 and later redact them, as do Valkey 9.0.6 and Redis 8.10.2 ("`AUTH` / `HELLO AUTH` in `SLOWLOG` on current versions").
  - **6.2.1 to 6.2.6 are untested** (the Redis repository and `download.redis.io` were not reachable from the measuring environment). So for them neither the `AUTH` behavior nor the other secrets are known: a release between 6.2.0 (not logged) and 6.2.7 (redacted) could have logged `AUTH` arguments in clear.
- **What the agent already does.** Decision 8 reduces every slow-log and command-log entry at parse time: `AUTH`, `HELLO AUTH`, `ACL SETUSER`, `MIGRATE … AUTH` arguments and every value are dropped before any buffering beyond the parser, never logged, never sent. Those secrets therefore **never leave the agent** (I2, I3 of other clients). They still **reach the agent's memory** (the zeroized reply buffer of one poll) and, independently of the agent, **every `SLOWLOG GET` reader**, including whoever holds the agent's Audit credentials (residual risk L3, "What the Audit grants reveal").
- **Options.**
  - **(a)** Keep the floor at 6.2.0, as the measured N1 gate allows: document that 6.2.0 to 6.2.6 servers expose other clients' replication and migration passwords to slow-log readers, the agent's Audit account included.
  - **(b)** **Raise the refusal floor to Redis 6.2.7**, the first tested release that redacts all three, or to the first 6.2 patch that the engine matrix proves passes the redaction test below (to verify on 6.2.1 to 6.2.6); a release below it is `unsupported`, whatever `unevaluated_acl` says.
  - **(c)** Refuse only Audit below 6.2.7 and allow Discovery (Discovery reads no log).
- **Decision (recommended): (b), the whole target refused below the proven floor, 6.2.7 until a lower one is proven.**
  - It closes the gap of the untested releases fail-closed: the N1 gate is met only where it was measured, and 6.2.1 to 6.2.6 were not.
  - Asking the operator for the slow-log grant on a server that writes other clients' passwords to it in clear would make the agent's Audit credential a password-collecting credential; refusing Audit alone (c) would leave the same server half-supported for a reason the console cannot show (no note says "your server leaks passwords to its slow log"), and Discovery on 6.2 already needs the `unevaluated_acl` opt-in.
  - Redis maintains the 6.2 line at its latest patch; 6.2.0 to 6.2.6 are superseded patches of a line in extended support, and ADR-0039 decision 1 does not support what its project no longer maintains. The remedy for an operator is a patch upgrade within 6.2, not a migration.
- **Consequences.**
  - **The redaction test** (security review L5) replaces the N1 implementation gate. With `slowlog-log-slower-than 0` (and the command log's thresholds at 0 on Valkey 8.1+) and a marker password, none of these may show the marker in `SLOWLOG GET`, `COMMANDLOG GET` or `MONITOR`: `AUTH <user> <pass>` and `AUTH <pass>`, `HELLO 3 AUTH <user> <pass>`, `ACL SETUSER <u> ><pass>` and `ACL SETUSER <u> #<hash>` (the hash too), `CONFIG SET requirepass`, `CONFIG SET masterauth`, `CONFIG SET masteruser` (the user name, recorded; a password never), `MIGRATE … AUTH <pass>` and `MIGRATE … AUTH2 <user> <pass>`. It runs on **every supported line**, the Redis 7.x lines (7.2, 7.4) and every Valkey line included, at the patch releases of the engine matrix, and the matrix keeps it.
  - **A supported release that fails any check of the test is refused** (`unsupported`, with the local detail naming the leaked argument), whatever its line; the floor of a line is the first patch that passes. Decision 2's sentence "Redis 6.2 releases older than the first 6.2 patch that redacts `AUTH` arguments in `SLOWLOG` are refused too" reads, once accepted: older than the first 6.2 patch **proven** to pass the redaction test; **6.2.7** until the matrix proves an earlier one (one run on 6.2.1 to 6.2.6 if their images can be pulled, only to lower the floor).
  - **Which floor applies** follows the engine identification of decision 9 (Valkey when `server_name:valkey` or `valkey_version` is present, its version from `valkey_version`; Redis otherwise, from `redis_version`): a Valkey server, whose `redis_version` is frozen at `7.2.4`, or a fork reporting `server_name` of its own, is never judged on `redis_version`. A server reporting neither Redis nor Valkey identification consistently (for example `server_name` with another value) is `unsupported`.
  - The refusal is `unsupported` with the local detail "Redis 6.2.<n> logs other clients' passwords in its slow log; upgrade to 6.2.7 or later". The release notes and docs/08 state the floor.
  - Decision 8's parse-time reduction stays the protection on every supported version: the agent never relies on the server's redaction, as written. Residual risk L3 is unchanged for supported versions (values and other secrets the server does not redact remain visible to slow-log readers) and loses its "on some versions secrets such as `CONFIG SET masterauth`" case for the versions the agent supports, as far as measured.

### 2. Other facts confirmed ("To verify" entries removed or narrowed)

- **`AUTH` in the slow log** ("To verify", third entry): answered by item 1. On 6.2.0 `AUTH` and `HELLO` are not slow-logged; from 6.2.7, and on Valkey 9.0.6 and Redis 8.10.2, they are logged redacted. The H2 test of decision 1 passes on the tested versions; the engine matrix keeps it on every supported version.
- **`SCAN` and key patterns** (decision 4, residual risk): `SCAN 0 COUNT 1000` as a user with `%R~customer:* %R~user:*` returned 76 key names outside its patterns on Valkey 9.0.6 and Redis 8.10.2. The local filter of decision 4 is required, as written; the engine matrix checks the other versions.
- **`ACL DRYRUN` denial texts** (decision 4): identical on every version that has the command (Redis 7.2.16 to 8.10.2, Valkey 7.2.14 to 9.1.2): `User <u> has no permissions to run the '<cmd>' command` (subcommands written `config|get`), `… to access the '<key>' key`, `… to access the '<chan>' channel`, and `OK` when allowed; Valkey 9.1.2 adds `User <u> has no permissions to access database <n>`, and the `resetdbs` / `db=` modifiers are refused elsewhere (`ERR Error in ACL SETUSER modifier 'resetdbs': Syntax error`). Redis 6.2 answers `ERR Unknown subcommand or wrong number of arguments for 'DRYRUN'. Try ACL HELP.` One prefix set serves every supported version, and the constants of decision 4 can be written now. **Still to verify**: which text is returned when several selectors deny differently.
- **`ACL LOG` failed authentications on 6.2** (decision 8): `reason auth` entries exist on 6.2.0, 6.2.7 and 6.2.24, as on 9.0.6 and 8.10.2 (`object AUTH`, `username` the name tried). Decision 8 stands on 6.2.
- **Valkey `SLOWLOG` and `COMMANDLOG … slow`** (decision 8): one sequence of entry ids shared by both reads, and `slowlog-log-slower-than` and `commandlog-execution-slower-than` hold the same value (Valkey 9.0.6; `COMMANDLOG` present on 8.1.10). Decision 8 reads only one of them on Valkey 8.1+, as written.
- **`COMMANDLOG` availability** (decision 4): absent on Valkey 7.2.14 and 8.0.11 and on every Redis; present from Valkey 8.1.10. `+commandlog|get` on Valkey 8.1+ only, as written.
- **`CLIENT NO-TOUCH`** (decision 4): present on Redis 7.2.16, 7.4.11, 8.2.10, 8.10.2 and on every tested Valkey (7.2.14 to 9.1.2), absent on Redis 6.2; `CLIENT NO-TOUCH ON` answers `OK` for the agent's user with the grant. The decision 4 comment reads "Redis 7.2+ and Valkey 7.2+".
- **TLS in the official images** (decision 13): the Valkey 9.0.6 and Redis 8.10.2 server binaries link `libssl.so.3` and serve TLS-only (`--tls-port`); neither image ships an `openssl` binary, so the dev CA is made by a one-shot container. This concerns the servers only; the agent keeps rustls.
- **Redis 8 modules** (decision 6, decision 13): the official 8.10.2 image loads only the built-in `vectorset`; the `redisearch`, `rejson`, `redistimeseries` and `redisbloom` libraries are in the image but not loaded. The dev Redis service runs without loaded modules; `vectorset` keys are a module type (`coverage.module_types_not_sampled`). **Still to verify**: the license terms of the bundled module libraries.
- **Not measured, still to verify**: `redis-cli --rdb` and `sync_full`; `SCAN` from a start cursor other than 0; Valkey 9 databases in cluster mode; Valkey 8.0 `CLIENT LIST` network counters; the distributions' socket paths; end-of-support dates; the CAS Redis ticket registry key prefix (open question 9 stays open; the dev keyspace has ticket-id-shaped keys for the shape guard only); that `redis` 1.7.1 and `fred` 10.1.0 build on Rust 1.88 (moot, both rejected).
