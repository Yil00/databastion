## Context

Phase 10 adds Firebird, the last engine of [ADR-0039](0039-engine-scope-expansion.md). ADR-0039 fixed the frame (ceiling Partial; a dedicated user with `SELECT` grants, never `SYSDBA` nor `RDB$ADMIN`; no embedded access and no direct reading of `.fdb` files; a pure-Rust wire client; the trace log follows the rule that a file the agent can write is refused; a capability token) and asked this ADR to decide the client, the transport and its trust model, the versions, the grants, the Discovery bounds, the Audit source and level, and the protocol additions.

Firebird differs from the engines already supported in ways that matter to the invariants:

- **No TLS.** The remote protocol (XDR-encoded operations over TCP, port 3050) has its own authentication plugins and its own **wire encryption** plugins (`WireCrypt = Disabled | Enabled | Required`, `WireCryptPlugin`), keyed by the session key the authentication plugin derives. The server is never authenticated by a certificate. On Linux there is no Unix-domain socket transport for the remote protocol (XNET is Windows only; to verify for 4.0 and 5.0); local access without the network goes through the embedded engine, which opens the database file directly and is excluded by ADR-0039 decision 5.
- **Authentication.** `Srp` / `Srp256` (SRP-6a with Firebird's own 1024-bit group, `g = 2`, SHA-1 for the internal hashes and the session key, SHA-256 for the client proof of `Srp256`) never sends the password. `Legacy_Auth` sends a DES `crypt(3)` hash of it, which is replayable and cheap to crack; protocol versions 10 to 12 send the password in clear (version 10) or that hash (11 and 12).
- **What the wire encryption gives**, read from the Firebird sources on 2026-10-24 (the `chacha` and `arc4` wire-crypt plugins, `src/remote/remote.cpp`, the SRP client; to confirm on the dev images, obligation 1):
  - `ChaCha` (Firebird 4.0+) is ChaCha20 with a 12-byte nonce and a 32-bit counter, `ChaCha64` (Firebird 4.0.1+, to verify) ChaCha20 with an 8-byte nonce and a 64-bit counter, both keyed from the SRP session key `K = SHA-1(S)`, with a nonce chosen by the server and sent in the clear key data; `Arc4` (every version since 3.0) is RC4 keyed with `K`, with RC4's known biases.
  - **No integrity**: neither cipher has a MAC, so an attacker on the path who knows plaintext at some offset can rewrite it (bit flipping), for example the agent's statement text or its transaction parameter buffer.
  - **No server authentication**: the server sends no proof of its own (there is no server proof `M2` in Firebird's SRP), and no certificate; the only server authentication is implicit: a server that does not know the verifier cannot derive `K`, so it cannot produce the first encrypted answer the client expects. Firebird's proof term differs from RFC 5054 (`H(N) ⊕ H(g)` is computed as a modular power in `srp.cpp`), so the client must be tested against real servers.
  - **Further keystream properties are under review** with the maintainer (security review N1); this ADR's decisions do not depend on them: the two properties above already rule out confidentiality and integrity on a network path an attacker can reach.
- **Statement timeout and read-only transactions.** Protocol 16 (Firebird 4.0) carries a per-statement timeout enforced by the server; transactions can be opened read-only (`isc_tpb_read`), and Firebird 4.0 adds `READ COMMITTED READ CONSISTENCY`. Readers never wait for writers' record versions (MVCC). There are no schemas before Firebird 6.0, no row-level security, no `SELECT` triggers; views, computed columns (`COMPUTED BY`), selectable procedures and database triggers (`ON CONNECT`, `ON TRANSACTION START`) run user code.
- **Audit.** Firebird has two trace mechanisms with one output format: the **system audit** (`AuditTraceConfigFile` in `firebird.conf`, a configuration in the `fbtrace.conf` syntax, written by the server to `log_filename`, rotated at `max_log_size`), and **user trace sessions** started through the services API (`isc_action_svc_trace_start`) whose output is read back over the services connection; a user session sees the attachments of other users only with the system privilege `TRACE_ANY_ATTACHMENT` (Firebird 4.0+) or as an administrator. The text format was read from `src/utilities/ntrace/TracePluginImpl.cpp` and `fbtrace.conf` (`v5.0-release`, 2026-10-24):
  - each record is written in one atomic append (the code says so), starting with a header line `YYYY-MM-DDTHH:MM:SS.ffff (<server pid>:<plugin instance address>) <EVENT>` in the server's local time, then an attachment line (`<database path> (ATT_<n>, <user>[:<role>], <charset>, <protocol>:<address>[/<port>])`), the client process line, a transaction line, then for statements `Statement <n>:`, a line of 79 `-`, **the statement text verbatim** (cut at `max_sql_length` with `...` appended), a line of 79 `^` and the plan **only when `print_plan` is on**, the parameters as `param<i> = <type>, "<value>"` (values verbatim, cut at `max_arg_length`), `<n> records fetched`, a performance line, and **with `print_perf` only**, a per-table block (a `Table … Natural Index Update Insert Delete Backout Purge Expunge` header, a line of `*`, one line per relation with its full name padded and eight right-aligned 10-character counters);
  - defaults that matter: `time_threshold = 100` (finish records of statements faster than 100 ms are **not written**), `max_sql_length = 300`, `max_arg_length = 80`, `max_arg_count = 30`, every `log_*` switch off, `print_perf = false`, `log_initfini = true`; `include_filter` / `exclude_filter` are `SIMILAR TO` expressions on the statement text; per-database sections match the database's file name or a `SIMILAR TO` pattern on its full path;
  - nothing in a record is escaped: statement texts, parameter values, error texts, the client process name (`isc_dpb_process_name`, set by any client) and quoted user and role names can hold newlines and any line of the format.
- **Statement text and parameters hold literal values** (I2), as on MySQL ([ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md)) and SQL Server ([ADR-0051](0051-sqlserver-connector.md) decision 6). Firebird has no server-side masking of passwords in `CREATE USER … PASSWORD` texts in the trace (to verify; the agent does not rely on it either way).

## Decision

### 1. Wire client: an own bounded client, no driver crate, no `fbclient`

The connector `connector-firebird` speaks a closed subset of the Firebird remote protocol itself, as `connector-mysql` ([ADR-0018](0018-mysql-mariadb-grants-and-connector.md) decision 3), `connector-mongodb`, `connector-openldap`, `connector-redis` ([ADR-0052](0052-redis-valkey-connector.md) decision 1) and `connector-sqlserver` ([ADR-0051](0051-sqlserver-connector.md) decision 1) do. No C client library is linked: the `fbclient` library, `rsfbclient-native` and any `*-sys` crate for Firebird are added to the `[bans]` of `agent/deny.toml` (reason: "no Firebird C client, ADR-0060 decision 1"), and `connector-firebird` joins the `CONNECTORS` list of the architecture test.

- **Protocol version 16 only.** `op_connect` (`CONNECT_VERSION3`, architecture generic, `ptype_batch_send`, no `pflag_compress`) offers exactly `PROTOCOL_VERSION16`. Version 16 is the floor that carries the statement timeout (decision 4); 17 to 19 add batches, scrollable cursors and inline blobs, which the connector does not use, so it does not offer them. An `op_accept*` naming another version ends the connection before anything derived from the password is computed. Whether every Firebird 4.0.x and 5.0.x server, and a future 6.0 server, accepts a client offering only 16 is verified on the matrix (obligation 2); if one does not, 17 or 18 is added to the offer, never anything below 16.
- **`op_connect` user identification** (sent in clear before encryption): `CNCT_login` (the account name), `CNCT_plugin_name` and `CNCT_plugin_list` both `Srp256`, `CNCT_specific_data` (the SRP public value `A`), `CNCT_client_crypt` = required. `CNCT_user` (the OS user) and `CNCT_host` (the host name) are **not sent**, as `HostName` is empty on SQL Server.
- **Operations sent**: `op_connect`, `op_cont_auth`, `op_crypt`, `op_attach`, `op_transaction`, `op_allocate_statement`, `op_prepare_statement`, `op_execute`, `op_fetch`, `op_free_statement`, `op_commit`, `op_rollback`, `op_cancel`, `op_info_sql` (describe and record counts), `op_detach`, `op_disconnect`. Never: `op_create`, `op_service_attach` and the services API (decision 6), `op_que_events` / `op_connect_request` (events need an **auxiliary connection to an address and port the server names**: I5), blob operations (`op_open_blob`, `op_get_segment`, `op_batch_*`; values are cut and converted on the server, decision 5), `op_transaction` with a write TPB, `op_ddl`, `op_execute_immediate`.
- **Operations parsed** from the server: `op_accept`, `op_accept_data`, `op_cond_accept`, `op_reject`, `op_response`, `op_fetch_response`, `op_sql_response`, `op_dummy` (skipped), `op_cont_auth` (only during authentication). Any other operation ends the connection: `op_crypt_key_callback` (a server asking the **client** for a database encryption key; the agent has none and sends none), `op_inline_blob`, `op_event`, `op_trusted_auth`, an unknown code. XDR has no framing beyond its own items, so an unknown operation cannot be skipped safely.
- **Closed type set.** The connector's statements are written so that every result column is `SQL_LONG`, `SQL_INT64`, `SQL_SHORT`, `SQL_BOOLEAN`, `SQL_VARYING` with character set `UTF8` (catalog names and converted values) or `OCTETS` (binary values, decision 5). The output message the client describes in BLR asks for exactly these; a describe answer (`isc_info_sql_describe_vars`) with another type, a blob, an array, a declared length above 32 765 bytes, or more columns than the statement selects makes the statement fail and the attachment be replaced (fail closed).
- **Bounds before allocation.** Every XDR length (opaque, string, status argument, info buffer, row value, null bitmap) is checked against the remaining budget of its item and against the declared maximum of its column before it is read; info buffers are requested with a client-chosen length (64 KiB at most) and an answer that claims more ends the connection; `op_fetch` asks for at most 64 rows per round, and a fetch answer with more rows, or a value longer than its column's declared length, ends the statement. Padding bytes are skipped by count, never trusted.
- **Server text is not data.** `op_response` status vectors are reduced while parsing to their GDS codes (`isc_arg_gds`, `isc_arg_number`) and SQLSTATE (`isc_arg_sql_state`, sent as `EngineCode`); `isc_arg_string`, `isc_arg_cstring` and `isc_arg_interpreted` arguments are skipped by length, never stored, logged or sent. Conversion errors quote values (`conversion error from string "…"`), so this is an I2 rule. The GDS codes map to the contract's `FailureCode` and check stage through **one closed table** (for example `isc_login` to `authentication_failed` at `stage_auth`, `isc_no_priv` to `permission_denied`, `isc_cancelled` to `cancelled`, `isc_cfg_stmt_timeout` / `isc_req_stmt_timeout` to `timeout`, `isc_io_error` and `isc_bad_db_format` on attach to `unknown_target`); a code outside the table is `internal`. After an authentication failure the connector stops retrying the target until the next heartbeat check, as on SQL Server; whether Firebird delays or locks an account after failed logins (`AuthServer` behaviour, the failed-login delay) is measured (obligation 9) and documented.
- **SRP-256**, implemented in the connector: the fixed Firebird group, `A = g^a mod N` with a fresh 128-byte random `a` from the operating system generator, checks on the server's answer before use (salt at most 32 bytes as hex, `B` at most 128 bytes, `B mod N ∉ {0, 1}`, the length checks of `SrpClient.cpp`), the scrambler `u = SHA-1(PAD(A) | PAD(B))` with the exchange **aborted when `u = 0`**, `x` from the salt, the upper-cased account and the password, then `S`, `K = SHA-1(S)` and the `Srp256` proof `M`. An answer that reports the client as authenticated **before `M` has been sent** ends the connection (`authentication_failed`): SRP must complete. The modular exponentiations over `a` and `x` use a **constant-time** big-integer implementation (`crypto-bigint`, Apache-2.0 OR MIT, MSRV 1.87, a new dependency checked by `cargo deny`), so the password-derived exponent does not leak through timing; `num-bigint` (variable time) is not used. The password, `x`, `a`, `S`, `K` and `M` live in zeroized buffers and are never written anywhere else (property test).
- **Wire encryption**: after `op_cont_auth` succeeds, `op_crypt` names `ChaCha64` when the server's key list offers it, else `ChaCha`, with the `Symmetric` key. `Arc4` is never chosen; a server that offers neither ChaCha plugin fails the connection with `target_unreachable` and a local detail; the wire-encryption negotiation is reported as the TLS stage of the contract (`check.stage_failed`, label `stage_tls`), as the `FailureCode` description asks for every engine. The ciphers come from the `chacha20` crate (`ChaCha20Legacy` for `ChaCha64`, `ChaCha20` for `ChaCha`), already in the agent's lock, always through `try_apply_keystream`: the `ChaCha` keystream ends at 256 GiB (32-bit counter), and its end closes the connection instead of panicking or wrapping. **Key confirmation**: the client sends no encrypted byte before it has decrypted the server's answer to `op_crypt` and found exactly the expected `op_response` structure (operation code, zero handles, an empty success status vector); anything else ends the connection with `target_unreachable` (label `stage_tls`, as a failed certificate check elsewhere; a wrong password is refused by the server before this point and reported `authentication_failed`). A server that does not know the verifier cannot pass this check, because it cannot derive the key.
- **Robustness duties** (ADR-0039 decision 4, the [connector obligations](../05-security.md#connector-obligations)): unit tests against a scripted fake server (as `connector-mysql/src/fake.rs`); property tests on every parser (no panic, bounded reads, the password and SRP secrets never outside their buffers); fuzz targets in `agent/fuzz/fuzz_targets/` for the XDR reader and the `op_accept*` / `op_response` / `op_fetch_response` parsers, the info-buffer (clumplet) parser, the SRP server data, the wire-crypt key list, the trace log record splitter and record parser, the trace configuration parser and the Firebird mode of the statement normalizer (decision 6); the nightly fuzz workflow runs them.

**Rationale.** Both crates pass the license criterion, and `firebirust` is maintained. Each is rejected for measured reasons that are project rules, not preferences:

1. `rsfbclient-rust` offers protocol versions 10 to 12, so a server or an attacker on the path that answers one of them receives the password in clear or as a DES hash; it offers no version with the statement timeout; it has Arc4 only; and it is blocking, so cancellation and the scan's deadlines would sit outside the tokio runtime the core relies on.
2. `firebirust` depends on `rust-crypto` 0.2.36, unmaintained since 2016, for its SHA and RC4 code; it panics on unexpected answers; it accepts Arc4 and an unencrypted connection; and it brings a second async runtime.
3. Neither bounds what a hostile server sends before allocating, as the project's own clients do, and both turn server status strings into error text, which can quote values.

The own client costs an estimated 2 500 to 3 500 lines plus tests and fuzz targets, and owns the robustness of its parsers, the residual every own client already carries. The decision is reviewed if a maintained pure-Rust crate offers only protocol 16+, `Srp256` only, ChaCha only, bounded parsing and no server text in errors; the table above is the checklist.

### 2. Supported versions

- **Firebird 4.0 and 5.0** (newest releases on 2026-10-24: 4.0.7 and 5.0.4), following [ADR-0039](0039-engine-scope-expansion.md) decision 1; lifecycle dates are to verify on firebirdsql.org before release (P10-G).
- **Firebird 3.0 is refused**, whatever its maintenance status (open question 1). It cannot meet this ADR's transport and bounds: it has only Arc4 (no ChaCha), protocol 15 at most (no server-side statement timeout), no `READ CONSISTENCY`, and none of the Firebird 4.0 system privileges and catalogs the refusal list reads (`RDB$SYSTEM_PRIVILEGE`, `RDB$ROLES.RDB$SYSTEM_PRIVILEGES`). Its server refuses the client's protocol offer (version 16 only), so it ends at connection with `unsupported`, before `op_cont_auth`, and nothing derived from the password reaches it.
- **Firebird 6.0 is refused until a refinement of this ADR** (open question 8): it adds SQL schemas (the `Location` mapping changes: decision 5), a new protocol version and catalog changes. Not released on 2026-10-24.
- **How the version is checked**: protocol 16 at `op_accept*`, then, on the attached session, `SELECT RDB$GET_CONTEXT('SYSTEM', 'ENGINE_VERSION') FROM RDB$DATABASE` (a constant text). A major version other than 4 or 5, or a value that does not parse, is refused as `unsupported` before any other read. The value is sent as `TargetStatus.server_version` (for example `5.0.4`).
- **Server modes**: `SuperServer` and `SuperClassic` are supported for Discovery and Audit; `Classic` (one process per attachment) is supported for Discovery, and for Audit only if the header-token rule of decision 6 holds there (to measure; Limited otherwise, open question 9).

### 3. Transport and authentication: loopback only, SRP-256, ChaCha required

- **Loopback only** (open question 2). The declared `host` must be an IP literal `127.0.0.1` or `::1` (no name: `localhost` resolution is not trusted, as an IP literal only counts in ADR-0023 decision 6). A target with another host is refused at configuration load, except in the tunnel mode below. Rationale: Firebird gives no server authentication and no integrity (Context), so on a network an active attacker can rewrite the agent's statements and transaction parameters, and the confidentiality of what crosses the path cannot be relied on. The Audit source is a local file on the server host (decision 6), so the agent runs there in any case.
- **The loopback threat model** (security review M1). Loopback is not a private channel for every process on the host: whoever holds `CAP_NET_RAW` or `CAP_NET_ADMIN` **in the network namespace** of the connection can capture or alter it. That includes root on the host, and also processes in containers that share the namespace (the other containers of a pod or of a Compose `network_mode: service:` group), which hold `NET_RAW` among Docker's default capabilities. From a passive capture such a process gets the SRP transcript, which allows offline guessing of the password, and must be assumed to get the sampled values; actively, it can flip bits in the agent's requests, the TPB included (a read-only transaction turned into a read-write one: the grants still refuse writes, decision 4). So the deployment rule is: **no other container shares the agent's and the server's network namespace, or every container in it drops `NET_RAW` and `NET_ADMIN`** (`cap_drop`); on a plain host, only root holds them. The user guide states it; the dev and E2E Compose files apply `cap_drop: [NET_RAW, NET_ADMIN]` to every container of the shared namespace (decision 9). The user guide also recommends `RemoteBindAddress = 127.0.0.1` in `firebird.conf` when no other client needs the network (security review N2).
- **Remote servers through an operator-run tunnel, an explicit opt-in** (security review M2, open question 2). An operator who needs Discovery of a Firebird server on another host runs a TLS or WireGuard tunnel (stunnel, `ssh -L`, WireGuard) that terminates on the agent host's loopback, declares the loopback end and sets the local option **`firebird.tunnel: true`**. That mode has its own `peer_uid` (the tunnel process's account, required), reports the permanent new note `security.firebird_tunnel` ("the target is reached through a tunnel the operator runs; its security is the operator's") at every check, and has no Audit (no local log): `audit.source_not_configured`. There is no `disable_insecure`-like remote mode.
- **Forwarders are detected** (M2). Without `tunnel: true`, a loopback endpoint must be the Firebird server itself, not a forwarder (a tunnel, `socat`, a userland port proxy): after attach, `check()` and every scan attachment read `MON$REMOTE_PROTOCOL`, `MON$REMOTE_ADDRESS` (and the remote port where the server reports it; to verify) of `MON$ATTACHMENTS` for `CURRENT_CONNECTION`, and compare them with the socket's local address and port. A mismatch (the server saw the connection come from somewhere else) ends the session with `target_unreachable` and a local detail.
- **The listening peer is checked** (security review L1). On loopback, an unprivileged local user can bind port 3050 while Firebird is down, then receive the agent's SRP exchange (an offline dictionary attack on the password from `M`) and feed it hostile data. Right after `connect()` returns and **before `op_connect` is sent**, the connector reads `/proc/net/tcp` **and** `/proc/net/tcp6` (world-readable, no privilege, no network traffic; IPv4-mapped IPv6 addresses handled), line by line with a bound on lines and time, and finds the server-side socket of **this connection** by its full 4-tuple (local = the declared address and port, remote = the agent's address and local port) in the `ESTABLISHED` or `SYN_RECV` state; its owner uid must be the declared `firebird.peer_uid`. Other rows are never logged or kept. A missing entry, two matching entries, another uid, uid 65534 (`nobody`, what a uid outside the reader's user namespace shows as), or a platform other than Linux ends the connection with `target_unreachable` and a local detail; there is no switch to turn the check off (open question 10).
  - `peer_uid` is a user name resolved at load (default `firebird`) or a number; **`peer_uid: 0` is refused** unless the local opt-in `firebird.peer_uid_root: true` is set (a root-owned socket is usually a proxy, and every root process matches it), reported in the local detail; **in a container** (the agent detects it from `/proc/1/cgroup` or `/.dockerenv`, to settle at implementation) the uid must be numeric, because names resolve against the agent image's own `/etc/passwd`.
  - In containers, the agent shares the server's network namespace (`network_mode: service:<firebird>`), as the dev and E2E environments do (decision 9), under the M1 deployment rule above.
  - The lookup has a property test (any 4-tuple and table content: the right row or none, never a panic) and a fuzz target over `/proc/net/tcp*` contents.
- **`Srp256` only.** `Srp` (SHA-1 proof), `Legacy_Auth`, `Win_Sspi` and any other plugin are never offered; a server that asks for another plugin (`op_cond_accept` naming it, or `op_cont_auth` switching to it) ends the connection before the password is used. The account is a user of the server's security database created with the `Srp` user manager (one verifier serves `Srp` and `Srp256`).
- **Wire encryption required**, `ChaCha64` or `ChaCha` (decision 1), checked once attached through `RDB$GET_CONTEXT('SYSTEM', 'WIRE_ENCRYPTED')` = `TRUE` and `'WIRE_CRYPT_PLUGIN'` naming the chosen plugin (context names to verify); a mismatch ends the session. `Arc4` is refused on loopback too: it costs nothing to require ChaCha on Firebird 4.0+, whose default `WireCryptPlugin` lists ChaCha first (to verify per version), and a server reconfigured to Arc4 only is a configuration change worth seeing. A server with `WireCrypt = Disabled` cannot be monitored (`target_unreachable`, local detail).
- **Compared with SQL Server** ([ADR-0051](0051-sqlserver-connector.md) decision 2): there, TLS with a verified certificate is mandatory everywhere because `LOGIN7` carries the password in a reversible form. Here SRP keeps the password off the wire on any transport, but integrity and server authentication cannot be had on a network, so the rule is about the path instead of the cipher: loopback, a checked peer, no forwarder unless declared, and the strongest cipher the server has.
- **Password.** The password is read from its `agent.yaml` secret reference (`secret: {env: …}` or a file, as for the other engines) into zeroized memory and used only to derive `x`; it never leaves the agent host (I3). The user guide asks for a random password of at least 32 characters: the SRP exchange given to an impersonating listener allows an offline guess per candidate, which a random password defeats.
- **Connection model**: one declared `host` / `port`, one attachment per declared database per scan and one per `check()`, replaced after an error that leaves it unusable or when idle for 60 s. Cancellation uses `op_cancel` (`fb_cancel_raise`) on the same connection (protocol 12+; to verify that it is handled while a fetch is pending in `ptype_batch_send`). The attachment sets `SET SESSION IDLE TIMEOUT 2 MINUTE` (Firebird 4.0+, a session-management statement, not a write) as the server-side safety net of the connector obligations. The DPB sends the account name, `isc_dpb_lc_ctype = UTF8`, SQL dialect 3, `isc_dpb_process_name = databastion-agent`, `isc_dpb_session_time_zone = UTC`; never a role (`isc_dpb_sql_role_name`), never `isc_dpb_no_db_triggers` or `isc_dpb_no_garbage_collect` (they need administrator rights the agent must not hold), never a password item. The lifetime of each attachment is recorded for the own-statement rule (decision 6): from `CURRENT_CONNECTION`'s read to a clean detach, or, for a **lost connection**, to the moment it was lost plus the statement timeout plus 5 s (security review L7).

### 4. Least-privilege account (I4), to be measured as in ADR-0012

**Proposed minimal variant** (default):

```sql
-- In the security database (isql connected as an administrator). The password
-- is typed from a prompt; the statement text holds it (decision 6 drops it).
CREATE USER DATABASTION_AGENT PASSWORD '<random, 32+ characters>' USING PLUGIN Srp;
-- In each monitored database: a role holding the table grants, granted as a
-- default role so it is active at every attachment without SET ROLE.
CREATE ROLE DATABASTION_READER;
GRANT SELECT ON TABLE CUSTOMERS TO ROLE DATABASTION_READER;   -- one per table
GRANT DATABASTION_READER TO USER DATABASTION_AGENT DEFAULT;
```

- **Per-table grants**: Firebird before 6.0 has no schema and no "all tables" grant short of a system privilege, so a new table needs a new grant (the PostgreSQL maintenance cost of ADR-0012). `check()` lists user tables without `SELECT` as not covered (`coverage.relations_without_select`, gaining `firebird`).
- **Extended variant (opt-in, `extended_grants: true`, open question 5)**: a role created `SET SYSTEM PRIVILEGES TO SELECT_ANY_OBJECT_IN_DATABASE`, granted `DEFAULT`; it reads every table, present and future, and is reported by `check()` as `privilege.extended_variant`. It is offered only together with the credential-relation rule of decision 5 (never sampled, and `check()` refusing an account that can read them), and only once obligation 3 shows what it widens (`MON$` visibility, security tables). Without the flag, the same privilege is over-privilege.
- **How `check()` reads privileges** (fail closed: a read that fails or is cut gives `privilege.not_evaluated`, and the refusal rule then applies to what was read):
  - **effective identity** on the attached session: `CURRENT_USER`, `CURRENT_ROLE`, `RDB$ROLE_IN_USE('RDB$ADMIN')`, and `RDB$SYSTEM_PRIVILEGE('<name>')` for every name of the lists below (it reflects mappings, default roles and the roles in use);
  - **every role the account could use**, not only the active ones (as [ADR-0025](0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) evaluates MySQL roles): rows of `RDB$USER_PRIVILEGES` with `RDB$PRIVILEGE = 'M'` whose grantee is the account or `PUBLIC`, followed through role-to-role grants (bounded at 64 roles); each role's `RDB$ROLES.RDB$SYSTEM_PRIVILEGES` bit mask decoded with a per-version closed table of bit positions checked by a drift test on each matrix image (an unknown bit set is treated as a refused privilege: fail closed). When this graph cannot be evaluated (catalog not visible, the bound reached, a read cut), `check()` reports `privilege.not_evaluated` with the new label `role_graph` (security review M6), and the residual "roles not active in the session not evaluated" applies to that target;
  - **object grants**: `RDB$USER_PRIVILEGES` rows whose grantee is the account, `PUBLIC` or one of those roles: privilege letter, object type and name, column (`RDB$FIELD_NAME`), `RDB$GRANT_OPTION`;
  - **ownership**: `MON$DATABASE.MON$OWNER` against `CURRENT_USER`, and `RDB$OWNER_NAME` of relations, procedures, functions and packages;
  - **the security database flag** `SEC$USERS.SEC$ADMIN` of the account's own row (a non-administrator sees its own row only; to verify);
  - visibility of these catalogs to the minimal account is measured on 4.0 and 5.0 (obligation 3).
- **What must be measured** (security review M6; P10-B, on 4.0 and 5.0, throwaway containers with fake markers, the table of results added to this ADR as ADR-0012's "Verification" section before it is accepted, as [ADR-0051](0051-sqlserver-connector.md) decision 4). Accounts: `min` (the minimal variant), `ext` (the extended variant), `none` (no grant at all), `sysdba_mapped` (a user mapped to `SYSDBA` or `RDB$ADMIN` through `RDB$AUTH_MAPPING`). Probes, each expected denied or empty for `min` unless stated:
  - **default DDL rights of a plain user**: `CREATE TABLE` (and `CREATE TABLE … EXTERNAL FILE`, a server-side file write and read primitive under `ExternalFileAccess`), `CREATE PROCEDURE` / `FUNCTION` / `PACKAGE`, `CREATE GLOBAL TEMPORARY TABLE`, `CREATE GENERATOR`; whichever a plain user holds by default is a residual of the account (as MySQL temporary tables) and is reported by `check()` as `privilege.beyond_select` when held through a grant;
  - **outbound primitives**: `EXECUTE STATEMENT … ON EXTERNAL DATA SOURCE` from `EXECUTE BLOCK` (an outbound connection from the server; not something the agent sends, but something a stolen agent credential can);
  - **server settings**, read through `RDB$CONFIG` where visible and reported in the local detail: `ExternalFileAccess`, `UdfAccess`, the UDR plugin settings, `WireCrypt`, `AuthServer`, `RemoteBindAddress`, `ServerMode`;
  - **system packages granted to `PUBLIC`** (`RDB$PROFILER`, `RDB$BLOB_UTIL`, `RDB$TIME_ZONE_UTIL`, and any other found) and what they expose;
  - **visibility** of `RDB$AUTH_MAPPING`, `SEC$GLOBAL_AUTH_MAPPING`, `SEC$USERS`, `RDB$USER_PRIVILEGES`, `RDB$ROLES`, and the `MON$` tables of **other attachments** (`MON$ATTACHMENTS`, `MON$STATEMENTS`, `MON$CONTEXT_VARIABLES`) for each account;
  - **the credential relations of decision 5** (`PLG$*`, `SEC$*`): readable by which account, in a database that is its own security database too.
- **Refusal list** ([ADR-0039](0039-engine-scope-expansion.md) decision 5, extended; reported as `privilege.refused` with the right's label). **Discovery and Audit both refuse to run** with such an account (open question 4, the [ADR-0051](0051-sqlserver-connector.md) open question 4 answer):
  - the user `SYSDBA` (by name and by effective `CURRENT_USER`, a mapping included), the database owner, the `RDB$ADMIN` role (granted in the database, held through `PUBLIC`, mapped by `RDB$AUTH_MAPPING` or a global mapping, or in use), the security-database administrator flag;
  - the system privileges (names from the Firebird 4.0 and 5.0 lists, to verify per version): `USER_MANAGEMENT`, `READ_RAW_PAGES`, `TRACE_ANY_ATTACHMENT` (decision 6: it reads every attachment's statements and parameter values over the network), `MONITOR_ANY_ATTACHMENT` (every attachment's statement texts in `MON$STATEMENTS`, context variables, and the cancellation of other attachments through `DELETE FROM MON$…`), `PROFILE_ANY_ATTACHMENT` (5.0), `ACCESS_SHUTDOWN_DATABASE`, `CHANGE_SHUTDOWN_MODE`, `IGNORE_DB_TRIGGERS`, `CHANGE_HEADER_SETTINGS`, `USE_GBAK_UTILITY`, `USE_NBACKUP_UTILITY`, `USE_GFIX_UTILITY`, `ACCESS_ANY_OBJECT_IN_DATABASE`, `MODIFY_ANY_OBJECT_IN_DATABASE`, `CHANGE_MAPPING_RULES`, `USE_GRANTED_BY_CLAUSE`, `GRANT_REVOKE_ON_ANY_OBJECT`, `GRANT_REVOKE_ANY_DDL_RIGHT`, `CREATE_PRIVILEGED_ROLES`, `CREATE_DATABASE`, `DROP_DATABASE`, `REPLICATE_INTO_DATABASE`, `MODIFY_EXT_CONN_POOL`, and any bit the per-version table does not know;
  - **a readable credential relation** (security review M5): `check()` probes, with a constant one-bit text (`SELECT CASE WHEN EXISTS (SELECT 1 FROM <relation>) THEN 1 ELSE 0 END FROM RDB$DATABASE`, no row content returned), whether each relation of decision 5's credential list that exists in the database is readable; a readable verifier or hash relation (`PLG$SRP`, `PLG$USERS`, their views) is a refusal, the others (`SEC$*` beyond the account's own row) the new label `credential_relation_readable` of `privilege.global_privileges`.
- **Over-privilege, warned** (existing notes gaining `firebird`: `privilege.beyond_select` for object rights, `privilege.grant_option`, `privilege.owner_of_objects`, and `privilege.global_privileges` with Firebird labels for the system privileges below, instead of a new code: security review L4): `INSERT`, `UPDATE`, `DELETE`, `REFERENCES` on any relation, `EXECUTE` on procedures, functions or packages, `USAGE` on generators, exceptions or domains, DDL privileges (`CREATE`, `ALTER ANY`, `DROP ANY`), `WITH GRANT OPTION`, ownership of any object, roles other than the reader role, and the system privileges `SELECT_ANY_OBJECT_IN_DATABASE` (without the flag), `USE_GSTAT_UTILITY`, `GET_DBCRYPT_INFO`, `CREATE_USER_TYPES`. Grants held through `PUBLIC` count as the account's (a write granted to `PUBLIC` is the account's write).
- **Transactions**: every unit of work runs in its own transaction with the TPB `isc_tpb_version3, isc_tpb_read, isc_tpb_read_committed, isc_tpb_read_consistency, isc_tpb_nowait`, committed before the unit's findings are submitted and before any pacing pause, so no transaction spans `FindingSink::submit().await` or a pause. Read-only read committed transactions do not hold back garbage collection (to verify in read consistency mode, obligation 4); the agent never waits for a lock (`nowait`: a conflict skips the table, `skipped_error`). After `op_transaction` the connector checks `RDB$GET_CONTEXT('SYSTEM', 'READ_ONLY')` = `TRUE` and `'ISOLATION_LEVEL'` = `READ COMMITTED` once per attachment (context names to verify); a mismatch ends the session.
- **Statement timeout**: every `op_execute` carries the job's clamped statement timeout (never 0; at most 30 s for a sampling statement, 3 s per `check()` statement and 9 s per `check()` in total), enforced by the server; the client keeps its own deadline as a backstop and sends `op_cancel`, then closes the connection if the cancelled statement's answer does not come within 5 s.
- **I4 summary**: read-only rests on (1) no write grant (checked, decision 4), (2) read-only transactions refused writes by the server, (3) a closed statement set built in code with quoted identifiers, (4) never reading what runs user code implicitly (decision 5), (5) server-side statement timeouts and client-side bounds. Database triggers are the exception: `ON CONNECT` and `ON TRANSACTION START` triggers run at every attachment and transaction of the agent; the read-only transaction blocks their writes except those in `IN AUTONOMOUS TRANSACTION` blocks (residual). `check()` reports them as `security.login_event_trigger` (gaining `firebird`; transaction-start triggers counted in the local detail).

### 5. Discovery

- **Databases**: the declared list only, `firebird.databases: [{name, attach}]`. `attach` is an alias of the server's `databases.conf` (recommended) or an absolute path; it is sent to the server inside the encrypted session and **never** leaves the agent otherwise: not in `Location`, not in `last_error`, not in logs (failures map to closed codes). `name` is the operator's label, normalized under ADR-0009 and sent as `Location.database`. Firebird has no server-wide catalog of databases a normal user can list, and the agent never asks for one (I5). The job's `databases` filter applies to the declared names; rotation per scan as ADR-0035.
- **Catalog per database**, with constant texts:
  - relations: `RDB$RELATIONS` with `COALESCE(RDB$SYSTEM_FLAG, 0) = 0`, reading `TRIM(TRAILING FROM RDB$RELATION_NAME)` (trailing padding only: a leading space is part of a quoted name; the client also trims trailing spaces, so a server-side mistake cannot merge names; security review L3), `RDB$RELATION_TYPE`, `RDB$VIEW_BLR IS NOT NULL` and `RDB$EXTERNAL_FILE IS NOT NULL` (booleans only: the external file path is never read); at most 16 384 relations per database;
  - **credential and system relations, never sampled** (security review M5): a closed list, checked by a drift test on each matrix image, of the relation names Discovery never samples **whatever their system flag** (a user can create a relation with any name, and a security database's `PLG$` tables are not system relations): every name starting `PLG$`, `SEC$`, `RDB$` or `MON$` in the tested images, plus `PLG$SRP`, `PLG$SRP_VIEW`, `PLG$USERS`, `PLG$PROF_*`. Such a relation found with system flag 0 is counted as `skipped_unsupported` and named in the local detail; the list, not the prefix, decides (a user table `RDB$X` absent from the list is sampled as any table, with the prefix noted in the local detail);
  - columns: `RDB$RELATION_FIELDS` joined to `RDB$FIELDS` on `RDB$FIELD_SOURCE`, reading the column name, position, `RDB$FIELD_TYPE`, `RDB$FIELD_SUB_TYPE`, `RDB$FIELD_SCALE`, `RDB$FIELD_LENGTH`, `RDB$CHARACTER_SET_ID`, `RDB$DIMENSIONS IS NOT NULL` and `RDB$COMPUTED_BLR IS NOT NULL`. Types are decided on `RDB$FIELD_TYPE` and `RDB$FIELD_SUB_TYPE` of the base field, never on a domain's name. The `*_SOURCE` columns (defaults, computed expressions, checks: source texts with literals) are never read;
  - the account's `SELECT` grants (decision 4) decide which relations and columns are readable; denied columns are left out of the select list;
  - **wide tables** (security review N3): the output message is bounded (64 KiB of described row, at most 255 sampled columns per statement); a table beyond it is sampled in column batches, one statement per batch with the same `FIRST n`, each batch a unit of work under pacing (rows of different batches are not joined: each column is classified on its own, as on every engine).
- **Sampled**: persistent tables only (`RDB$RELATION_TYPE = 0`, no view BLR, no external file). **Never sampled**: views (`coverage.views_not_sampled`), external-file tables (reading them makes the server read a file outside the database; new note `coverage.external_file_tables`), global temporary tables (types 4 and 5: their rows belong to other attachments and are invisible to the agent's; counted in the local detail), virtual tables (`MON$`, `RDB$` virtual), selectable procedures, computed columns (`COMPUTED BY` can call PSQL functions or UDRs: user code; `coverage.computed_columns_not_sampled`, gaining `firebird`), arrays, blobs of sub-types other than 0 and 1, and any type outside the conversion list below.
- **Sampling statement** (one per table):

  ```sql
  SELECT FIRST <n> CAST(SUBSTRING("C1" FROM 1 FOR 4000) AS VARCHAR(4000) CHARACTER SET UTF8), …
    FROM "TABLE"
  ```

  - `<n>` is the job's `sample_rows` (at most `limits.max_sample_rows`), an integer literal; `FIRST n` rather than `FETCH FIRST n ROWS ONLY` because it is accepted in every dialect and version supported (both are equivalent on 4.0 and 5.0). Identifiers come from the catalog and are quoted by one audited function (`"`, with `"` doubled), never from job parameters; there is no string literal in any sampling statement.
  - **Values are converted on the server with syntax-level built-ins only** (`CAST`, `SUBSTRING`, which no user function can shadow): `CHAR` / `VARCHAR` and `BLOB SUB_TYPE TEXT` of a declared character set to `VARCHAR(4000) CHARACTER SET UTF8` (the server transliterates; with `lc_ctype = UTF8` this is also what it would send); columns of character set `NONE` or `OCTETS` and `BLOB SUB_TYPE BINARY` to `VARCHAR(4000) CHARACTER SET OCTETS`, read as text only when valid UTF-8 without control characters (as [ADR-0026](0026-mongodb-connector.md) decision 9); integers, `INT128`, `NUMERIC` / `DECIMAL`, `DECFLOAT` as digits; `DATE` and `TIMESTAMP [WITH TIME ZONE]` as `YYYY-MM-DD`; `BOOLEAN` skipped; `FLOAT` / `DOUBLE PRECISION` integral values only, as on MongoDB and SQL Server. The exact forms (whether `CAST` of a blob substring to `VARCHAR` holds on 4.0 and 5.0, transliteration failures) are verified on the matrix (obligation 5). A statement that fails on a conversion (`isc_transliteration_failed`, `isc_malformed_string`, string truncation) skips the table with `skipped_error` and a local detail naming the column's type, never its values. The blob reads stay on the server: no blob id reaches the client.
  - **Order and bias**: `FIRST n` without `ORDER BY` reads the first records in storage order and stops (to verify that the natural scan stops early). Firebird has no `TABLESAMPLE` and no cheap row estimate; `SKIP m` would read and discard `m` rows. The sample is therefore biased to storage order (often the oldest rows), recorded as a residual (open question 14).
- **Byte budget**: at most 32 MiB of sampled values per table, checked per value as bytes arrive (XDR lengths precede the bytes; at most 16 000 bytes per converted value); reaching it sends `op_cancel` (decision 3).
- **Pacing**: every unit of work (a database's catalog, a table's sample) goes through `ScanJob::paced` ([ADR-0035](0035-discovery-pacing.md)); the attachment is detached before a pause that reaches 45 s, as MySQL.
- **Locations and names**: `Location` is `engine: firebird`, `database` (the declared name), `object` (the relation), `field` (the column), with no `schema`, as MySQL. Every name goes through [ADR-0009](0009-name-normalization-and-item-sanitization.md) normalization (quoted names can hold any character, including `.`, spaces and values) and the [ADR-0057](0057-identifier-hardening-agent-first.md) rules, with the [ADR-0056](0056-names-altered-by-normalization-marker.md) marker when normalization alters them.
  - **Case**: Firebird stores unquoted identifiers upper-cased (ASCII letters) and quoted ones as written, and compares stored names exactly: `CUSTOMERS`, `customers` written unquoted, and `"CUSTOMERS"` are one table; `"Customers"` is another. That is fixed by the engine, not by a setting, so no [ADR-0055](0055-agent-reported-name-case-semantics.md) `name_case` value is needed: Discovery sends catalog names as stored, and statement-text names are resolved as the server does (unquoted names upper-cased in ASCII, quoted names kept, `""` unescaped). The console must treat `firebird` as a **case-sensitive** engine for location exceptions ([ADR-0054](0054-case-sensitive-location-exceptions.md) decision 1, the PostgreSQL rule; open question 11).
  - **Trailing spaces**: catalog names are `CHAR(63)` padded with spaces (`CHAR(31)` before 4.0), so trailing spaces are never significant in a Firebird name (`"A "` and `"A"` are one table). The agent drops them from catalog and statement-text names; this is the engine's own rule, not an alteration, so no ADR-0056 marker is set for it. The console should add `firebird` to `TRAILING_SPACE_BLIND_ENGINES` (open question 11).
  - Own-account budget keys are the Unicode-lowercased names, as on every engine (merging budgets only reports sooner).
- **CAS store guard** ([ADR-0041](0041-cas-connector.md) decisions 5 and 6): applied as on the other SQL engines (ticket-registry names and column shapes counted, never sampled; the ticket-id tripwire before classification), although CAS is not known to ship a Firebird JPA configuration (to verify); it is cheap and fails closed.
- **Coverage**: `objects_sampled`, `skipped_not_readable` (no `SELECT`), `skipped_unsupported` (tables with no sampleable column, CAS ticket registries), `skipped_remote` (external-file tables), `skipped_limit`, `skipped_error`.

### 6. Audit

#### Source: the system audit trace log, read locally

| Source | `audit_source` | Read through | Permission | Best level |
|---|---|---|---|---|
| System audit trace (`AuditTraceConfigFile`), text log file on the server host | `firebird_audit_trace` | the core tailer, local file | file read by the agent's Unix account; no database grant | **Partial**, Limited until the proofs below hold |

- **User trace sessions through the services API are rejected** (open question 6). They need `TRACE_ANY_ATTACHMENT` or an administrator to see other users' attachments, a system privilege that lets the agent's credential (usable remotely if stolen) read every attachment's statement texts and **parameter values** in clear; the agent would create the trace it is supposed to prove (rejected for SQL Server in [ADR-0051](0051-sqlserver-connector.md)); the services connection is a second protocol surface; and a session's output is lost at a server restart and when the reader falls behind `MaxUserTraceLogSize` (to verify). `TRACE_ANY_ATTACHMENT` is on the refusal list (decision 4).
- **Configuration**: the operator sets `AuditTraceConfigFile` in `firebird.conf` and writes the trace configuration; the agent never writes either. `agent.yaml` names the log and the configuration: `firebird.audit {log, trace_config}`, both absolute paths on the agent host.
- **File rules** ([ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 8, [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md)): the log is opened by the core tailer with `O_NOFOLLOW`, one hard link, rotation detected with `lstat`, and refused when the agent's account could write it. The connector adds the CAS-style open check of ADR-0043 decision 5 (`Tailer::with_open_check`): the declared path still resolves where it did at load, the file has one link and no ancestor directory the agent can write, and the path names the handle before and after the checks. The trace configuration file is read with the same open rules (it decides the level, so a writable configuration is refused as a proof: Limited). Firebird rotates by renaming the full log with a date and time suffix and creating a new file (`max_log_size`); the tailer finishes the renamed file before switching (as for the other log sources). Whether the server creates the log group-writable (so an agent in the `firebird` group would be refused) is measured on the dev images and documented (obligation 6).
- **The configuration the server uses** (security review M3). The level depends on the configuration the server actually runs with, not on a file that merely exists:
  - `agent.yaml` also names `firebird.audit.firebird_conf` (absolute path), read under the same file rules with a closed key set; its `AuditTraceConfigFile` must resolve (relative names against the Firebird root directory, also declared) to the declared `trace_config`, and `ServerMode` is read from it (cross-checked with `RDB$CONFIG` where visible). A mismatch or an unreadable `firebird.conf`: not proven (Limited, `audit.trace_config_not_evaluated` with a label).
  - When the server reads the audit configuration (at process start only, or also when a database is first opened) is measured (obligation 11). If only at start: the agent finds the server process (the local `firebird` process of the declared `peer_uid`, through `/proc`) and its start time (`/proc/<pid>/stat`), and a `firebird.conf` or trace configuration whose `mtime` or `ctime` is later than that start time is **not proven** (the running server may use the earlier content). If the server runs in another pid namespace than the agent (its process is not visible), the binding is not proven either (Limited).
- **Database paths** (security review M4). The agent learns each declared database's file path from `MON$DATABASE.MON$DATABASE_NAME` on its own attachment and from its own read-back probe's attachment line (below), and keeps it on the agent host only. How the trace prints paths for aliases, `..`, `//`, symlinked directories, hard links and bind mounts is measured (obligation 12). Matching is exact on the printed path; fail closed: a record whose path differs from a declared database's path but has the same file name, or names a file whose `(st_dev, st_ino)` (from a `stat` without opening the file) equals a declared database's, is **ambiguous** (below), reported, and caps that database's level at Limited until the operator's configuration is fixed.
- **Records of undeclared databases** are dropped at parse and counted (I5: undeclared databases are not monitored), **only when they are well formed** (not ambiguous, rules below).

#### Parsing a hostile text log

Every client that can send SQL writes into this file: statement texts and parameter values are verbatim, unescaped, and can contain any line of the format, including a header line that starts a forged record. The **injection points** (security review H1) are the statement text (comments included), parameter values, error and warning texts (they quote values and names), the client process name (`isc_dpb_process_name`, any string a client sets), quoted user and role names, and quoted object names in the per-table block. The parser is built for that:

- **Record splitter**: a record starts at a line matching the closed header grammar (timestamp, `(<pid>:<hex address>)`, an event name from a closed list: `ATTACH_DATABASE`, `DETACH_DATABASE`, `FAILED ATTACH_DATABASE`, `UNAUTHORIZED ATTACH_DATABASE`, `START_TRANSACTION`, `COMMIT_TRANSACTION`, `ROLLBACK_TRANSACTION`, their `FAILED` / `UNAUTHORIZED` forms, `PREPARE_STATEMENT`, `EXECUTE_STATEMENT_START`, `EXECUTE_STATEMENT_FINISH`, `EXECUTE_STATEMENT_RESTART`, `EXECUTE_PROCEDURE_*`, `EXECUTE_FUNCTION_*`, `EXECUTE_TRIGGER_*`, `COMPILE_BLR`, `EXECUTE_BLR`, `EXECUTE_DYN`, `SET_CONTEXT`, `ERROR AT …`, `WARNING AT …`, `START_SERVICE`, `ATTACH_SERVICE`, `DETACH_SERVICE`, `QUERY_SERVICE`, `TRACE_INIT`, `TRACE_FINI`, and the sweep events; list to verify per version) and ends before the next such line. The splitter cannot tell a forged header from a real one, so it splits at forged headers too; the rules below make every such split **loud**, never a silent drop. A record is bounded at 1 MiB; a longer one is not parsed and produces one always-reported event naming `*` for the target (loud, never quiet), counted. **At end of file**, the last record is held until a following header arrives or the file has not grown for 2 s and is not rotated (a stable EOF), so a record being appended is never parsed half-written (security review L5).
- **Trailer first, on every record** (H1, fix 1). Every record, whatever its event, is parsed **from its end** for a trailer: the per-table block (relation name, then eight 10-character counters, read from the right so names with spaces parse), the performance line, `<n> records fetched`, then upwards the parameter lines, which are skipped without being buffered beyond the parser. The trailer lines of a finish record are written by the server **after** everything a client controls, so a client can forge text before them but cannot remove or rewrite them. Each event has an expected trailer shape (finish events of statements, procedures, functions, triggers and BLR requests: records fetched, performance line, per-table block when `print_perf` is on; attachment, transaction and service events: none). **A trailer shape that does not fit the event** (a trailer under an `ATTACH_DATABASE` header, none under an `EXECUTE_STATEMENT_FINISH`) makes the record ambiguous.
- **Objects come from the per-table counters and from the text**, united (as pgaudit relation records and text names on PostgreSQL), for records that are not ambiguous. **Ambiguous records take objects from the counters only, plus `*`, never from the text** (H1, fix 5). The counters name the relations the statement's execution touched, including those read inside procedures, functions and triggers it called (to verify, obligation 7), with natural and indexed reads. This makes `print_perf = true` a Partial proof (below).
- **Header tokens** (H1, fixes 4 and 7). The `(<pid>:<address>)` pair identifies the trace plugin instance that wrote the record. Its address part is a heap pointer: **not a secret**. It can be guessed (allocator layouts are regular), inferred (from earlier tokens, a crash report, a log the attacker once saw), and the pid is visible in `MON$ATTACHMENTS`. Its value is only that a forger who guesses wrong is **loud**. The parser keeps a token per database path **for every database in the log**, declared or not, changed only at a `TRACE_INIT` / `TRACE_FINI` boundary. A record whose token is not the current one for its database, a `TRACE_INIT` while the current token's instance has not ended, or a token seen for two databases, marks the records involved **ambiguous**. How tokens behave per server mode, at database close and reopen, and across restarts is measured first (obligation 8); the rule is revised before Audit ships if the measurement differs.
- **Missing trailers** (H1, fix 2). A statement, procedure, function, trigger or BLR **finish** record of a declared database without its trailer (no `records fetched`, or no per-table block while `print_perf` is proven on) is ambiguous: a forged header inside it has moved its real trailer into the next record.
- **Other ambiguity**: a statement text (between the `-` line and the trailer), a process name or a user or role name that holds a line matching the header grammar, the `-` or `^` separator lines, a `param<i> =` line, a `records fetched` line or a per-table header; a record with two trailers; an attachment line that does not parse (a user or role name holding `,` `:` `(` `)` or a newline); a text cut at `max_sql_length` (length at the configured limit and ending in `...`); a path that matches a declared database only by file name or inode (M4).
- **What an ambiguous record becomes** (H1, fix 3). It is always reported, never the agent's own, never dropped as belonging to an undeclared database, with `*` added, its counters' objects and its row counts. It is attributed to the declared database of the **preceding well-formed record** (the one the forged header most likely split), or, when there is none in the same read or that record is of an undeclared database, to **every declared database of the target**. A cut text names `*` and is never the agent's own. Ambiguous records are counted in the new note `audit.log_records_ambiguous` and cap the level (proof 8).
- **Per-record isolation and buffers** (L5): each record is parsed and converted under the per-record panic isolation of [ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md); a record whose handling panics is dropped alone and counted. Record buffers (which hold parameter values and texts) are zeroized after the record is handled, as the CAS audit lines.
- **Residual** (recorded below): a client can still forge records that look like other attachments' statements (over-reporting), and, by splitting its own record with a forged header that carries the right token, separate its real principal from its real trailer. The trailer keeps the true objects and row count, so the read stays reported; the principal attached to it can be wrong when the forger guessed or inferred the token.

#### What is kept (I2)

- **Kept**: the event name and result (`FAILED`, `UNAUTHORIZED`), the timestamp (server local time, converted with an offset learned from the agent's own read-back probe, re-learned at every probe, as the SQL Server Extended Events clock calibration; a DST change between probes shifts times until the next one), the attachment id, the user and role, the protocol and the remote address and port, the transaction id, the statement id, the statement text through the normalizer, the records fetched, the per-table counters (relation names and counts) and the performance line's time.
- **Dropped at parse**: parameter values (`param<i>` lines), `SET_CONTEXT` values (`RDB$SET_CONTEXT` records under `log_context`), the plan (`print_plan`) and BLR or DYN dumps (`print_blr`, `print_dyn`: BLR can hold literals), the database path (mapped to the declared name, then discarded), the client process path and pid (client-set, spoofable, and a path can hold a user name), error and warning message texts (only their GDS codes are kept), and service records' arguments (only the service name from a closed list and the user are kept: `Add User` / `Modify User` service records can carry passwords; to verify what the trace prints there).
- **Statement text**: a Firebird mode of the query normalizer in `classifiers` ([ADR-0007](0007-mask-access-events.md), the ADR-0023 decision 4 rules): every literal replaced (`'…'` with `''`; the alternate quoting `q'…'` / `Q'…'` with **every delimiter pair** the server accepts (`()`, `{}`, `[]`, `<>` and any other single character as both ends); `x'…'` / `X'…'` and `0x…` hexadecimal literals; `n'…'` / `N'…'` and introducers such as `_UTF8 '…'`; numbers; date and time literals), `--` and `/* … */` comments removed, `"…"` read as an identifier in dialect 3 and as a string in dialect 1 (the client's dialect is not in the log, so both readings are lexed and readings that differ keep only the statement kind, fail closed as `ANSI_QUOTES` on MySQL). **A literal left unterminated** (a text cut at `max_sql_length`, or malformed) drops everything after its opening quote (security review L10). Only DML text is kept after normalization; DDL and DCL keep their kind, never text. PSQL bodies (`EXECUTE BLOCK`, `CREATE PROCEDURE`, triggers, functions, packages) are program text the SQL lexer does not delimit: they take no object name from the text (ADR-0023 decision 7); an `EXECUTE BLOCK` names the counters' relations plus `*` and is always reported. Statement text never leaves the agent (the contract has no field for it).
- **Password-bearing statements** (the end-to-end rule of #82, ADR-0039 decision 3): `CREATE USER`, `ALTER USER`, `CREATE OR ALTER USER` and `ALTER CURRENT USER` with `PASSWORD`, `CREATE DATABASE … PASSWORD`, `CONNECT … PASSWORD`, `EXECUTE STATEMENT … ON EXTERNAL [DATA SOURCE] … AS USER … PASSWORD …` (in PSQL bodies and `EXECUTE BLOCK`), `CREATE` / `ALTER MAPPING` (no password, but identity), and the `Add User` / `Modify User` services keep their kind only; the password never leaves the parser. The #82 end-to-end marker test gains one case per form and asserts that no marker appears in any uplink payload, agent log line or metric.
- **Principals**: as on the other SQL engines ([ADR-0021](0021-access-event-correlation.md)); the user names of `FAILED` and `UNAUTHORIZED ATTACH_DATABASE` records are fingerprinted (a password typed in the user field ends up there), as on every engine, and count toward the failed-login flood cap. With `log_connections = false` the failed logins are not seen: `audit.failed_logins_not_audited` gains `firebird` (security review L4).

#### Levels and proofs (ADR-0039 decision 3)

**Full is never reported.** The trace sees what goes through a server attachment, and not: the database file copied at the file-system level (a backup of the `.fdb`, `nbackup`'s physical copy, a snapshot), embedded-engine access by a local process (the embedded engine reads its own configuration, which may have no audit), statements below `time_threshold`, statements excluded by filters, and **replication** (Firebird 4.0+ logical replication ships changes through replication journals and a replica, not through traced attachments: `check()` reads the `replication.conf` / `RDB$CONFIG` replication settings where visible and notes an enabled replication in the local detail; security review L6). Each of those needs no SQL.

**Partial** when all hold, re-evaluated every 5 minutes; otherwise **Limited** (a record of a declared database parsed in the last 24 h) or **None**:

1. the log, the trace configuration and `firebird.conf` are readable under the file rules, and the account is outside the refusal list;
2. **the configuration is bound to the running server** (M3): `AuditTraceConfigFile` resolves to the declared trace configuration, `ServerMode` is read from `firebird.conf`, and neither file changed after the server process started when obligation 11 shows the server reads them only at start; a server in another pid namespace: not proven;
3. the trace configuration parses with the agent's closed key set (an unknown key, a parse error or a writable file: not proven), and for each declared database the sections that apply are the default `database` section and sections whose pattern is a plain file name with no `SIMILAR TO` metacharacter, **`_` and `%` included** (a file name holding `_`, common in practice, is therefore not evaluated: open question 12); any other section caps the level at Limited with the new note `audit.trace_config_not_evaluated` (the agent does not reimplement Firebird's `SIMILAR TO` on paths). How sections match (file name or full path, case, order, the default section's interaction with others) is measured first (obligation 13);
4. in the applying section: `enabled = true`, `log_filename` equal to the declared log, `log_connections = true`, `log_statement_finish = true`, `log_blr_requests = true` (gbak and other BLR clients read through BLR requests, which statement records do not show), `log_procedure_finish`, `log_function_finish` and `log_trigger_finish` on, `log_errors = true`, `time_threshold = 0`, `print_perf = true`, no `include_filter` or `exclude_filter`, `connection_id = 0`; each missing setting is a label of the new note `audit.trace_settings_missing` (Limited);
5. `max_sql_length` at least 4 096 (else the existing note `audit.statement_text_limit_low`, gaining `firebird`; not a cap, since cut texts are reported as `*`);
6. the services section has `enabled = true` and `log_services = true` (services backups and user management); missing: the new note `audit.services_not_audited` (informational; the database section still sees the service's attachments, to verify);
7. **the read-back probe**: at each re-evaluation, `check()` runs a constant probe statement on its own attachment (`SELECT COUNT(*) FROM RDB$DATABASE`) and the stream must find, within 10 minutes, its `EXECUTE_STATEMENT_FINISH` record with the agent's attachment id, the exact text, `1 records fetched` and a per-table block. This shows that the server writes the declared log for that database, that a statement of about 0 ms is written, and that `print_perf` is on; it also gives the time offset and the database path. It does **not** show that the declared configuration is the one in use (a decoy configuration whose settings differ from the running one can coexist with a passing probe): proofs 2 to 4 do that part;
8. no gap in the last 24 h: no truncated or replaced log (the keyed tail-cursor fingerprints of #97), no rotated file lost before it was read, no header-token anomaly and no ambiguous record; otherwise `audit.records_dropped` (or `audit.log_records_ambiguous`) and Limited for 24 h;
9. a record parsed in the last 24 h (the ADR-0023 decision 2 freshness rule; `audit.partial_pending_first_record` gains `firebird`);
10. the server mode is `SuperServer` or `SuperClassic`, or `Classic` once obligation 8 shows the token rule holds there (and the peer-uid rule under Classic's per-connection processes, open question 9).

Not seen by the trace, documented in docs/08 whatever the level: file-level copies, embedded access, rows read by the agent's own Discovery (left out under its budget, below), and what the server does without an attachment.

#### The agent's own statements and the always-reported rules

- **Own attachments** (the ADR-0051 decision 6 model; `databastion_core::audit::own`): at every attachment the connector reads `CURRENT_CONNECTION` (constant text). Firebird attachment ids are allocated from a counter kept in the database header and are not reused while the database lives (to verify across backup and restore, which resets it: an id seen again after a restore is not the agent's). The own set (database, attachment id, remote port, lifetime: to a clean detach, or to a lost connection plus the statement timeout plus 5 s, decision 3) is persisted with the stream position, kept 48 h. A record is the agent's own only if **all** hold: its attachment id is in the set for that database and its time falls in the attachment's lifetime; its user is the agent's account and its role the reader role or none; its remote address and port are the agent's loopback address and the local port of that attachment; its text is one of the connector's constant texts or the exact generated sampling text of an object with an unexpired credit (the statement's deadline plus 5 minutes); it is not ambiguous, cut or split; it carries no signal; and its records fetched stay within the per-object row budget (a count above the credit's `sample_rows` is reported, as an anomaly).
- **Statement-text objects, always reported** (the counterpart of [ADR-0045](0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) part (a) and [ADR-0049](0049-postgresql-statement-text-views-as-reads.md); candidate list confirmed per image by a drift test): reads of `MON$STATEMENTS` (`MON$SQL_TEXT`), `MON$COMPILED_STATEMENTS` (5.0), `MON$CONTEXT_VARIABLES` (values), `MON$CALL_STACK`, the profiler's `PLG$PROF_*` tables and `RDB$PROFILER` calls (5.0), and service records `Start Trace Session` / `List Trace Sessions`, keep that name as their object, carry the always-reported mark and are never the agent's own except the agent's exact `MON$DATABASE` / `CURRENT_CONNECTION` reads.
- **Credential-bearing objects, always reported** (the counterpart of [ADR-0050](0050-postgresql-credential-and-value-bearing-catalogs-as-reads.md)): the credential list of decision 5 (`SEC$USERS`, `SEC$USER_ATTRIBUTES`, `SEC$GLOBAL_AUTH_MAPPING`, `RDB$AUTH_MAPPING`, `PLG$SRP`, `PLG$SRP_VIEW`, `PLG$USERS`: verifiers and legacy hashes, readable where a database is its own security database), `RDB$DB_CREATORS`, `RDB$CONFIG` (the server configuration). Never the agent's own, except its exact `SEC$USERS` own-row read and its one-bit readability probes of decision 4.
- **Source texts of user code** (`RDB$PROCEDURES.RDB$PROCEDURE_SOURCE`, `RDB$TRIGGERS.RDB$TRIGGER_SOURCE`, `RDB$FUNCTIONS.RDB$FUNCTION_SOURCE`, `RDB$PACKAGES` bodies, `RDB$RELATIONS.RDB$VIEW_SOURCE`, the `*_SOURCE` columns of `RDB$FIELDS` and `RDB$RELATION_FIELDS`) can hold literals, including `EXECUTE STATEMENT … PASSWORD` credentials, and are readable by every user. They are **not** always reported in this ADR (every administration tool reads them), which is a residual (open question 7, as `prosrc` in ADR-0050); Discovery never reads them.
- **Other system relations** (relations on the decision 5 list, or with a non-zero system flag in the catalog, outside the always-reported lists) are left out of the objects of reads (noise), as MySQL's `is_system_relation`; writes to them are reported. The list or the system flag decides, **never the name prefix alone** (security review M5): a user table named `RDB$X` that is on neither is an ordinary object.
- **Code that runs out of sight**: a call of a function that is not built in (an unqualified name outside a closed per-version list of Firebird built-in functions checked by a drift test, a UDF, a UDR, a PSQL function or a packaged `pkg.f(`) adds `*` and is always reported, as ADR-0045 part (b). `EXECUTE PROCEDURE p` and a selectable procedure in `FROM` name the procedure itself plus the counters' relations, under the filters (the [ADR-0051](0051-sqlserver-connector.md) open question 12 answer; open question 13), **only if obligation 7 shows that the counters include the reads inside called code**; otherwise, and whenever a record has no per-table block, `*` is added. `EXECUTE STATEMENT … ON EXTERNAL`, external-file table reads and `EXECUTE BLOCK` add `*` and are always reported.

#### Signals

Existing signals extended to `firebird` in `shared/protocol/signals.json`: `shape.full_table_read` (a read without top-level `WHERE`, aggregation or `FIRST` / `ROWS` / `FETCH FIRST` of at most 10 000 rows), `volume.large_result` (more than 10 000 records fetched by one statement; `records fetched` counts rows, not blob bytes, so a few rows of large blobs do not raise it: documented in docs/08, security review N5), `signature.backup_database` (a services `Backup Database` or `Incremental Backup Database` record, `ALTER DATABASE BEGIN BACKUP` (nbackup), `CREATE SHADOW` (a server-maintained full copy of the database file), `ALTER DATABASE ADD FILE` and `ALTER DATABASE ADD DIFFERENCE FILE` (security review L6), and BLR requests reading a whole relation from an attachment whose process name is `gbak`, a client-set hint like MySQL's `program_name`), and `signature.remote_data_access` (`EXECUTE STATEMENT … ON EXTERNAL [DATA SOURCE]`, reads of external-file tables, `CREATE TABLE … EXTERNAL FILE`). No new signal.

### 7. I1, I3, I5 and local detection

- **I1**: one outbound TCP connection per attachment, to the declared loopback port; no listener, no auxiliary connection (events refused, decision 1). `connector-firebird` depends on no crate of `BANNED_CONNECTOR_DEPS` (`socket2` included). The peer-uid and process checks read `/proc` only.
- **I3**: the password stays on the agent host, zeroized, never on the wire (SRP), never logged. The account name travels in clear in `op_connect`, on loopback only. The `agent.yaml` block has no field the console can set.
- **I5**: one declared host (loopback) and port per target, declared databases only, no database listing, no server-named host followed (no events, no `EXECUTE STATEMENT … ON EXTERNAL` from the agent), external-file tables never read, undeclared databases' audit records dropped. Local detection ([ADR-0006](0006-target-discovery.md)) adds the local TCP port 3050 and the `firebird` process as detected, unconfigured targets; no other port is probed.

## Consequences

- `agent/deny.toml` gains `[bans]` entries for Firebird C client crates; `crypto-bigint` joins the agent's dependencies (constant-time arithmetic for SRP); `sha1`, `sha2` and `chacha20` are already in the lock.
- A sixth own protocol client: about 3 000 lines whose robustness against a hostile server is the project's (fuzzed, property-tested), plus a second hostile-text parser (the trace log) and a configuration parser.
- **Loopback only.** A Firebird server can be monitored only by an agent on its host, with no other container in the shared network namespace unless every one drops `NET_RAW` / `NET_ADMIN` (or through an operator-run tunnel declared with `tunnel: true`, Discovery only); servers configured with `WireCrypt = Disabled` or Arc4 only, servers behind an undeclared forwarder, and Firebird 3.0, cannot be monitored.
- **Partial at best, and only with a demanding trace configuration** (`time_threshold = 0`, `print_perf`, BLR requests, no filters): the trace costs the server I/O on every statement; the load run measures it and docs/08 states it, so operators can weigh it.
- Discovery does not sample views, computed columns, external-file tables, GTTs, arrays or non-text blobs, and samples in storage order.
- The console (P10-E) must list `engine.firebird`, render its notes, signals and audit source, and add `firebird` to its case-sensitive and trailing-space-blind exception lists.
- `docs-keeper` (P10-G): [08-engine-capabilities.md](../08-engine-capabilities.md) row and sections written from the measurements (including that `records fetched` does not show blob volume); [05-security.md](../05-security.md#recommended-database-accounts-read-only) account block and the wire-encryption analysis (its keystream part only after the maintainer's disclosure decision); README "Supported databases"; `agent.example.yaml` (`firebird` block: loopback host, numeric `peer_uid` in containers, `databases`, `tunnel`, `audit.log`, `audit.trace_config`, `audit.firebird_conf`); the user guide (a random password of 32+ characters; the trace configuration with plain file-name sections; `RemoteBindAddress = 127.0.0.1`; the shared-namespace and `cap_drop` rule).

### Residual risks

- **Own parsers** of the Firebird wire protocol, the trace log and the trace configuration, from a possibly hostile server or writer; bounded, fail-closed and fuzzed, as the other own clients.
- **Firebird's wire encryption is weak by design** (no MAC, no server authentication, further keystream properties under review). Loopback only, the peer-uid check and the forwarder check contain it; a tunnel is the operator's.
- **Capture inside the network namespace** (M1): a holder of `CAP_NET_RAW` / `CAP_NET_ADMIN` in the namespace (root, or a container sharing it that did not drop them) can capture the SRP transcript and guess the password offline, must be assumed to read the sampled values, and can flip bits in the agent's requests. Contained by the deployment rule and a random password; root can read the database files anyway.
- **Impersonating listener**: the peer-uid check binds the connection to the declared server account, but a process running as that account (the Firebird server itself, or code it runs, such as a UDR) can always impersonate it; SRP then gives that process an offline guess per password candidate, defeated by a random password.
- **Forged trace records**: any client can write text that looks like other records. Every split is loud (ambiguous records are always reported, with `*`, attributed to a declared database), and the trailer-first parsing and the per-table counters keep the true objects and row counts of a statement reported; a forger who guesses or infers the header token can still attach a forged principal to them, and anyone can add forged events (over-reporting).
- **Roles not active in the session**: when the role graph cannot be evaluated (`privilege.not_evaluated`, `role_graph`), a refused right held through a non-default role may go unseen until the catalog becomes visible.
- **Configuration binding**: where the server re-reads its audit configuration, or the agent cannot see the server process, the binding is not proven and the level stays Limited; a configuration changed and reverted between two re-evaluations is not seen.
- **Source texts of user code** (procedure, trigger, view and default sources, readable by every user) can hold literals and credentials and are not always reported (open question 7).
- **Database triggers** run at every attachment and transaction of the agent; the read-only transaction blocks their writes except in autonomous transactions; reported, not prevented.
- **Not visible to the trace**: file-level copies of the database, embedded access, statements of databases whose applying configuration section the agent could not evaluate (Limited then).
- **Own-attachment window**: an attachment id is the agent's only within its lifetime and with its exact texts and credits; after a crash, the end of the last attachments is taken as the restart time, as on SQL Server.
- **Storage-order sampling bias**, and server-side conversions (`CAST`, `SUBSTRING`) running on sampled values (built-ins only).
- **The SRP group and hashes are Firebird's** (a fixed 1024-bit group, SHA-1 inside SRP and for the session key): the client cannot choose stronger ones.
- **Version facts** (lifecycle dates, system-privilege names and bits, context variable names, trace format details) are partly from the sources read on 2026-10-24 and partly as remembered, marked "to verify"; the obligations decide before each pull request.

## Rejected alternatives

- **`rsfbclient-rust`**: protocol 10 to 12 offered (clear password or DES hash on a downgrade), no protocol 16, Arc4 only, blocking I/O (decision 1).
- **`firebirust`**: `rust-crypto` 0.2.36 (unmaintained since 2016), panics on unexpected answers, Arc4 and unencrypted connections accepted, a second async runtime (decision 1).
- **`fbclient` through `rsfbclient-native`, ODBC or `isql`**: a C library (and OpenSSL-free only by luck of the build), process spawning, no control over what the library buffers or logs ([ADR-0039](0039-engine-scope-expansion.md) rejected alternatives).
- **Embedded access or reading `.fdb` files directly**: excluded by ADR-0039 decision 5; it bypasses the server's grants, and a hostile database file becomes a parser input.
- **Remote connections with ChaCha wire encryption** (the ADR-0039 decision 6 option "Firebird 4+ ChaCha with SRP mutual authentication"): no integrity and no server authentication on the path, so the agent's statements and transaction parameters are rewritable there and the confidentiality of the samples cannot be relied on (open question 2).
- **Arc4**: RC4 and its known biases, with the same missing integrity.
- **`Legacy_Auth` and `Srp` (SHA-1)**: a replayable DES hash; a SHA-1 proof where `Srp256` is available on every supported version.
- **User trace sessions through the services API**: `TRACE_ANY_ATTACHMENT` (every attachment's texts and parameter values over the network), the agent creating what it proves, output lost at restarts (decision 6).
- **The trace configuration proved by the read-back probe alone**: one probe cannot show the absence of filters or the BLR and procedure switches, nor that the declared configuration is the one the server runs with, so the configuration file and `firebird.conf` are read and bound to the running server process (decision 6, proof 2).
- **`print_plan` separators as the end of statement text**: forgeable and absent without `print_plan`; the trailer-first parse does not need them.
- **Sampling views, computed columns or selectable procedures**: runs user code on every read.
- **`SNAPSHOT` (concurrency) transactions**: they hold back garbage collection for their duration; read committed read-only transactions per unit do not.
- **Firebird 3.0 support with Arc4 on loopback**: loopback would contain Arc4, but 3.0 still lacks the server-side statement timeout and the system-privilege catalogs the refusal list needs (open question 1).

## Open questions (for the maintainer)

Each with the answer this ADR proposes; none is decided until the maintainer confirms it.

1. **Firebird 3.0**: ADR-0039's row says "3.0 if still maintained". Support it if its maintenance is confirmed?
   **Proposed**: no. Refuse it at connection (protocol 16 only), as ADR-0039 decision 1 allows: Arc4 only, no server-side statement timeout, no system-privilege catalogs. Record the amendment of ADR-0039's row.
2. **Remote Firebird servers**: loopback only (this ADR), or an opt-in remote mode with ChaCha and a documented risk note?
   **Proposed**: loopback only in phase 10; remote servers only through an operator-run TLS or WireGuard tunnel ending on the agent host's loopback, declared with the explicit local opt-in `firebird.tunnel: true` (its own `peer_uid`, a permanent `security.firebird_tunnel` note, Discovery only). Revisit if Firebird gains TLS or an authenticated wire cipher.
3. **Arc4 on loopback**: refuse it there too (this ADR)?
   **Proposed**: yes; Firebird 4.0+ always has ChaCha, and requiring it everywhere keeps one rule.
4. **Discovery with an account on the refusal list**: refuse both Discovery and Audit (this ADR), or Audit only?

   **Proposed**: left out in phase 10 and documented as a residual (as ADR-0050's `prosrc`), with a load measurement of how often tools read them; revisit with a no-source shape rule if needed.

13. **Procedures**: name the procedure plus the counters' relations, under the filters (this ADR), or add `*` and always report every call?

14. **Sampling order**: `FIRST n` in storage order (this ADR), or a random `SKIP m`?
    **Proposed**: storage order; `SKIP m` reads and discards `m` rows on the server, against the < 2 % criterion. Revisit if findings show the bias matters.

### R1. Header tokens are per attachment (obligation 8)

**Measured** (5.0.4 and 4.0.7):
- The header token `(<pid>:<address>)` is the server pid and a heap address.
- Within one server run the pid is constant; it changes only at a server restart.
- The address differs per attachment: one SuperServer log held 21 distinct tokens under a single pid, so many tokens are current at once for the same database.
- In SuperServer, `TRACE_INIT` / `TRACE_FINI` bracket the server run; in SuperClassic, each attachment writes its own `TRACE_INIT` / `TRACE_FINI`.

The accepted rule cannot stand. It kept "a token per database path … changed only at a `TRACE_INIT` / `TRACE_FINI` boundary", and made records ambiguous when a token was not the current one for its database, when a `TRACE_INIT` came before the current instance ended, or when a token was seen for two databases. Applied to the measured log, it would mark almost every record ambiguous, and its `TRACE_INIT` / `TRACE_FINI` boundary does not exist in SuperClassic.

**Proposed rules**, replacing the "Header tokens" and "Records of undeclared databases" paragraphs of decision 6. They apply to every database in the log, declared or not, as H1 fix 4 required. The token keeps the role of H1 fix 7: it is not a secret, and its value is that a wrong guess is loud. As security review H-1 showed, a forger needs no guess at all for some forgeries; the forger analysis below states what remains.

1. **Run identity.** A server run is identified by the pair (pid, process start time).
   - The pid comes from `MON$SERVER_PID`, read at every `check()` from the `MON$ATTACHMENTS` row of `CURRENT_CONNECTION` on the agent's own attachment (a constant text).
   - The start time comes from `/proc/<pid>/stat` of that process. Proof 2 already requires the server process to be in the agent's pid namespace, so that file can be read.
   - The agent's own records must carry the pid.
   - A server in another pid namespace is Limited under proof 2. There the rules below run with `MON$SERVER_PID` alone, as a fail-closed best effort.
   - The **current run** is the run so confirmed. A record whose pid is not the current run's pid is ambiguous, except as the confirmed start of a new run (rule 2).
2. **Run change, confirmed by the server, with bounded stops.** Every client can read its own `MON$SERVER_PID`, so a pid in a header proves nothing by itself.
   - **The stop.** When a record with a new pid arrives, the stream stops before it, without advancing its position (nothing is lost), and asks for an immediate `check()`.
   - **A confirmed change.** If `MON$SERVER_PID` and the start time then identify a new run whose pid is the record's pid, a new run starts at that record. Every binding of the old run ends, detached or not, and the own-attachment lifetimes of the old run close.
   - **A changed start time** with the same pid is a confirmed run change too (the pid was reused).
   - **After a confirmed change**, a record that carries the pid of an ended run is a new pid like any other. It is confirmed only if the current server process has that pid, with a start time later than the ended run's.
   - **A failed confirmation.** If the check reads another run, or does not answer within 60 s, the records with the unconfirmed pid are handled as ambiguous and the current run continues.
   - **Limits on stops** (security review M-3):
     - at most one unresolved stop at a time;
     - a pid that failed confirmation is remembered for the run (at most 64 pids), and its records are ambiguous at once, with no stop. Past 64 remembered pids, every further new pid is ambiguous without a stop, for the rest of the run (security review L-b);
     - after a failed confirmation, a 10-minute cooldown, during which records with any new pid are ambiguous without stopping the stream.
   - **Measuring stops.** The heartbeat metrics `firebird_audit_stream_stopped_seconds_total` and `firebird_audit_run_confirmations_failed_total` count the stops and the failed confirmations. When the stream has been stopped for more than 60 s within one hour, `audit.log_records_ambiguous` carries the new label `run_confirmation_stalled`.
   - **`TRACE_INIT` / `TRACE_FINI`.**
     - A `TRACE_FINI` ends nothing by itself: a forged one carries the known pid.
     - **A restart with the same pid** (security review N-2). A restarted server can get the same pid, which is common in containers. In SuperServer, a `TRACE_INIT` that carries the current pid therefore triggers the stop and the confirmation, like a new pid. The confirmation compares the pid and the start time:
       - a new start time confirms a run change at that `TRACE_INIT`;
       - an unchanged start time makes the `TRACE_INIT` ambiguous, as a second `TRACE_INIT` in the current run.

       These stops share the limits above: one unresolved stop at a time, and the cooldown. For these stops, the cooldown is keyed on the start time: after a failed confirmation, further `TRACE_INIT` records with the current pid are ambiguous without a stop for 10 minutes, as long as the start time read by `check()` is unchanged.
     - **A new start time found by a periodic `check()`.** Each `check()` records the stream position at which it confirmed the current run. When a periodic `check()` finds a new start time that no stop has confirmed (the restart's `TRACE_INIT` fell in a cooldown, or was not written), the run boundary is the first `TRACE_INIT` after the last confirmed position. With no such `TRACE_INIT`, the boundary is the confirmation itself. Every binding of the old run ends there. The records between that boundary and the confirmation are ambiguous.
     - In SuperServer, a second `TRACE_INIT` in the current run that the confirmation does not turn into a run change, or a record of the current run after its `TRACE_FINI`, is ambiguous.
     - **After a crash** there is no `TRACE_FINI`. The restarted server's `TRACE_INIT` carries a new pid, or the same pid with a new start time. It goes through the stop and the confirmation. Once confirmed, it ends the old run and its bindings, and a last record of the old run cut by the crash is ambiguous (H1 fix 2, or the held-at-EOF rule).
     - In SuperClassic, `TRACE_INIT` / `TRACE_FINI` records belong to attachments and **never trigger a stop**. They are checked against the run pid; their token is checked as measurement 8c settles (until then, against the run pid only). A SuperClassic restart with the same pid is found by the periodic `check()` (previous item).
   - **History walks.** When a history walk (a first start, or after a gap) reads earlier runs, those runs come from the log alone. A pid change starts a run only at a `TRACE_INIT` record in SuperServer, or at a `TRACE_INIT` or `ATTACH_DATABASE` record in SuperClassic; any other pid change is ambiguous. The first `check()` confirms the current run.
3. **Attachment binding.**
   - **Key.** An attachment is identified by its **database identity** and its attachment id, within a run. For a declared database, the identity is the declared database, whatever name the record prints: its path or any alias that maps to it (R2). For an undeclared database, it is a keyed hash of the printed name (rule 11).
   - **The binding.** The token on the attachment's `ATTACH_DATABASE` record is its **binding**, and the binding is **anchored**. It ends at a `DETACH_DATABASE` record that carries the same token, or with its run.
   - **Every record of the attachment** must carry the binding's token; a record that carries another token is ambiguous.
   - **Duplicate ids** (security review M-1). An attachment id is never reused within a database's life (obligation 10). A second `ATTACH_DATABASE` for the same database identity and id within one run, outside a confirmed restore (rule 5), **poisons both bindings**, whether or not the first has detached: all their records are ambiguous, and neither is the agent's own.
4. **One live binding per token.** A token held by a live binding is ambiguous on any other record: a record of another attachment, a `FAILED` / `UNAUTHORIZED ATTACH_DATABASE`, or a service record. Heap addresses are reused, so after its detach a token can come back for a new attachment, through that attachment's own `ATTACH_DATABASE` record.
5. **Attachments the stream did not see attach, and restores.**
   - **Learned bindings.** At a first start or after a gap, an attachment can predate the read position. Its binding is learned from its first record. After a mismatch on a learned binding, every later record of that attachment is ambiguous, because the first record may have been the forged one.
   - **Own attachments.** An attachment is the agent's own only when its binding is anchored and not poisoned. This is a new condition of the own-attachment rule; the agent reads its own `ATTACH_DATABASE` records anyway.
   - **Watermark** for declared databases. Attachment ids come from a counter in the database header, in order (obligation 10). The **watermark** is the id of the agent's first own attachment in the run whose `ATTACH_DATABASE` record the stream read. A record of an attachment with a higher id, but with no `ATTACH_DATABASE` record read for it, names an attachment that cannot predate the read position: it is ambiguous. Measurement 8e checks whether system attachments write such records, and in what order concurrent attaches write their `ATTACH_DATABASE` records.
   - **Restores** (security review M-1) are recognised from `check()` only, never from a log record. A restore is confirmed when:
     - the agent's own `CURRENT_CONNECTION` is below the watermark; or
     - `RDB$GET_CONTEXT('SYSTEM', 'DB_GUID')` or `MON$DATABASE.MON$CREATION_DATE` has changed since the last check.

     On a confirmed restore, that database's own-attachment set is cleared, its bindings end, and its watermark is set again from the agent's next own attachment.    - **Monotonic ids** (security review L-c):
     - **Out-of-order attaches.** An `ATTACH_DATABASE` in the log whose id is not above the highest id seen for its database identity in the run, without a confirmed restore, is ambiguous. Concurrent attaches may write their records slightly out of id order, so an id not seen before that falls within a small tolerance below the highest is accepted. The tolerance is set by measurement 8e; 16 is proposed.
     - **Which ids raise the highest.** Only ids at or below the agent's latest own `CURRENT_CONNECTION` plus a margin count. The margin is set from the load run; 4 096 is proposed.
     - **An id above that bound** is ambiguous and does not raise the highest. A forged record with a large id therefore cannot make later real attaches look out of order.
6. **Service sessions** are bound in the same way, from `ATTACH_SERVICE` to `DETACH_SERVICE`, within the run.
7. **Split windows** (H1 fixes 2 and 3, made explicit; security review M-1).
   - **Opening.** A finish record of a declared database that has no trailer (fix 2) opens a **window**.
   - **Ending.** The window ends only at a record of one of the agent's own anchored, unpoisoned bindings, or at the first record that the agent reads after 60 s of **reading time** since the record that opened the window (security review L-a). Reading time is counted on the agent's clock while the stream follows the log. Time while the stream is stopped (rule 2), back-pressured by the spool or the uplink, parked, or while the agent is down is not counted. The forged records of one append are read together, so they fall inside the window.
   - **Inside the window.** Every record of the window is ambiguous, and so is the record that ends it unless it is the agent's own. All of them, the ending one included, take the fix-3 attribution, and none is dropped as a record of an undeclared database. A binding created by an `ATTACH_DATABASE` inside the window is tainted: its records are ambiguous until it detaches.
8. **Records of undeclared databases** (security review H-1), amending "Records of undeclared databases" of decision 6:
   - **Under proof 11** (below), the server writes no record of an undeclared database into the declared log. A record that names one is therefore forged or misconfigured: it is ambiguous, with the fix-3 attribution, and never dropped.
   - **Without proof 11**, the level is Limited, with `audit.trace_config_not_evaluated` and the new label `foreign_databases_logged`. Records of undeclared databases that are not ambiguous are then dropped and counted, as the accepted text says (I5), and docs/08 states that, at Limited, a forged record of an undeclared database can hide a read.
9. **Remote 4-tuple corroboration**, conditional on measurement 8f. Under this rule, a new binding is ambiguous when the attachment line's `<protocol>:<address>/<port>`:
   - equals that of another live binding; or
   - has no matching server-side socket in `/proc/net/tcp` / `/proc/net/tcp6` (the same bounded lookup as decision 3) while the binding is live and its `ATTACH_DATABASE` record is read within 10 s of being written.

   It applies only if 8f shows that the remote address can be corroborated in this way. It raises the cost of a forged `ATTACH_DATABASE`, but does not remove it: a local forger can hold an extra TCP connection to the server port open without attaching, and use its port.
10. **Classic** server mode: each attachment is served by its own process, so the pid is not a per-run constant and rule 1 does not hold. Audit stays Limited there, with a local detail, until a later refinement. This refines the answer to open question 9: the "Partial if the token rule holds there" branch is withdrawn for now, and the peer-uid measurement under Classic stays open.
11. **Bounds and persistence** (security review M-4).
    - **Persisted state.** The live bindings, the current run, the remembered pids, the watermarks and the open window are persisted with the stream position, as the own-attachment set is.
    - **Names.** A printed database name longer than 4 KiB is ambiguous and is not kept. Undeclared names are kept only as a keyed hash (HMAC under the agent's local key), never in clear.
    - **Caps:**
      - 16 384 live bindings per declared database;
      - 4 096 per undeclared database identity;
      - 256 undeclared identities;
      - 1 024 service bindings;
      - one open window (overlapping windows merge);
      - a global cap of 16 MiB on the persisted state.
    - **Eviction** is fail closed. The oldest learned bindings and the bindings of undeclared databases go first; anchored bindings of declared databases are never evicted. A record of an evicted binding is ambiguous and counted.
    - **When nothing can be evicted**, a new binding is not kept, and its records are ambiguous. In particular, past 1 024 service bindings, a new service binding is not kept, and its records are ambiguous (security review L-b).
    - **Learned floor** (L-b). After a learned binding is evicted, no new learned binding is accepted, for that database identity in the run, at or below the highest evicted attachment id. Records of such attachments are ambiguous.
    - **Durable denial** (L-b), a residual stated in docs/08. Anchored bindings of declared databases are never evicted. Forged `ATTACH_DATABASE` records with fresh ids can therefore fill a declared database's anchored slots. From then on, every new binding's records are ambiguous, and the database has no Partial level until the server restarts (the run's end clears its bindings). This can deny the Partial level, but cannot hide a read.

**Fail closed, as before.** An ambiguous record follows H1 fix 3:
- it is always reported, never the agent's own, and never dropped as a record of an undeclared database;
- `*` is added, with its counters' objects and its row counts;
- it is counted in `audit.log_records_ambiguous`;
- it caps the level for 24 h (proof 8, whose "no header-token anomaly" now means a breach of rules 1 to 11).

H1 fixes 1 (trailer-first parse of every record), 2 (a finish record with no trailer is ambiguous), 5, 6 and 7 are unchanged. Fix 3 is strengthened by rules 7 and 8. Fix 4 becomes rules 3 to 5, applied to every database in the log.

**New Partial proof 11: the declared log holds only declared databases** (security review H-1). Every condition must hold, for each declared database, under the first-match semantics of R2 rule 4:
- **The default section** is disabled (`enabled = false`), or its `log_filename` is not the declared log.
- **Every named section whose `log_filename` is the declared log** has a pattern with no `SIMILAR TO` metacharacter that equals exactly:
  - the resolved path of a declared database; or
  - pending measurement 12b, an alias of the map that maps to one.
- **`log_filename`** (security review L-d). A relative `log_filename` is resolved against the declared Firebird root before it is compared with the declared log. This applies to proofs 4 and 11 alike. A `log_filename` with `\N` substitutions (a part of the database pattern) is not evaluated: Limited, with `audit.trace_config_not_evaluated`.
- **The declared database file has a single link** (`st_nlink` = 1, from a `stat` without opening the file).
  - A client that attaches through another path of the same file (a hard link) matches no section, so its records are not written to the declared log at all.
  - Otherwise the level is Limited, with `audit.trace_config_not_evaluated` and the new label `database_path_not_unique`.
  - Bind mounts of the database directory cannot be detected this way, and are a residual stated in docs/08.
  - **Case-folding directories** (security review L-c) are the same kind of residual, stated next to bind mounts. An ancestor directory with the case-folding attribute (`FS_CASEFOLD_FL`, ext4 and f2fs) lets a client attach through a case variant of the path, which matches no section. The user guide advises against case-folding directories for databases.
  - **A hard link created and removed between two checks** is not seen by the single-link condition, which is read at each re-evaluation. docs/08 states this next to "file-level copies".

**What a forger can do under these rules** (corrected after security review H-1). The forger is any client with no privilege that can put header-shaped lines into its own record (the H1 injection points), and cannot read the log.
- **What the forger knows and controls.** It knows the pid (its own `MON$ATTACHMENTS` row) and attachment ids (sequential; its own from `CURRENT_CONNECTION`). It controls all the text before its injected header, so it can **end its own record with a complete fake trailer** (a `^` line, `1 records fetched`, a performance line, a per-table block naming `RDB$DATABASE`). Its record then looks well formed, and no split window opens.
- **What it does not know**: the address of any live attachment, its own included, unless it can read the log or learns one from a leak (a crash report, an old copy of the log).
- **Hiding a read in an undeclared database.** The forged header names an undeclared database and an invented attachment, so the real trailer lands in a well-formed record of an undeclared database. Under proof 11 that record is ambiguous (rule 8): the read is reported with its real counters and row count. Without proof 11, the level is Limited, and the read can be dropped quietly (the stated Limited residual).
- **Misattribution on a declared database: quiet, and needs no guess.** The forger writes a fake trailer, then a forged `ATTACH_DATABASE` for a new attachment id above the watermark with a fresh token, then a forged finish header and attachment line for that attachment. The real trailer then lands under the forged principal.
  - No rule makes this ambiguous: the forged attachment is anchored, its id is new, and its token is not live.
  - The read **is reported, with its real objects and row count**. R4 folds nested records by maximum, so a forged finish record cannot lower them (security review N-1). Only the principal is wrong: the user, the role, the address and the attachment can name an invented principal, or another user's name.
  - The forger's real record appears as a small read of `RDB$DATABASE` under its true principal.
  - Policies and baselines keyed on the principal can therefore be evaded, or turned against another user. "Every read" policies and the volume and shape signals still apply.
  - Rule 9, if measurement 8f allows it, makes this harder (a live socket with no other binding is needed). Measurement 8f may show that the server escapes line breaks in some fields, which would close those injection points. Until then, misattribution is the stated residual of Partial, for the maintainer to accept or reject (open question 6).
- **A forged record of a live attachment** needs that attachment's address. A wrong guess is ambiguous (rules 3 and 4): loud.
- **A forged duplicate `ATTACH_DATABASE`**, including for the agent's predicted next id, poisons the bindings involved (rule 3). The agent's own reads are then reported as other reads: loud, not hidden.
- **Over-reporting** is unchanged: anyone can add forged events. Records forged with wrong tokens make records ambiguous and cap the level: this denies the Partial level, but does not hide a read.
- **A forged new pid** costs one stop of at most 60 s; after that its pid is remembered, and the cooldown applies (rule 2). A forged `TRACE_FINI` ends nothing.
- **Readers of the log** see every live token, and every password set through SQL (R4). The rules do not protect against them; proof 1 (R4, security review M-6) withholds Partial while anyone other than root, the server and the agent can read the log.

**Residual "Forged trace records", restated.** Once this refinement is accepted, this statement replaces the accepted residual of that name:

> Any client can write text that looks like other records. Every split that the parser can see is loud: ambiguous records are always reported, with `*`, attributed to a declared database. Under proof 11, a record of an undeclared database in the declared log is ambiguous. On a declared database, a client with no privilege can attribute its own real read to an invented principal, or to another user's name, with no ambiguous record, by ending its record with a fake trailer and forging an `ATTACH_DATABASE` and a finish header. The read is still reported with its real objects and row count, because nested records are folded by maximum, so a forged finish record cannot lower them; only the principal is wrong. Anyone can add forged events (over-reporting).

**New measurements before the Audit lot** (added to obligation 8):
- **8a**: the address is the same on every record of one attachment for its whole life, under concurrent load, in SuperServer and in SuperClassic (worker threads in both). If it is not (for example, if it changes per thread), rule 3 cannot stand, Partial is withheld, and this refinement is revised.
- **8b**: `DETACH_DATABASE` carries the attachment's token, and an address is reused after a detach.
- **8c**: the token carried by `TRACE_INIT` / `TRACE_FINI`, `FAILED ATTACH_DATABASE` and service records, in SuperServer and SuperClassic.
- **8d**: `MON$SERVER_PID` is readable by the minimal account on its own row and equals the header pid. `RDB$GET_CONTEXT('SYSTEM', 'DB_GUID')` and `MON$DATABASE.MON$CREATION_DATE` change at a restore.
- **8e**: the attachment ids consumed by system attachments (garbage collector, cache writer, sweep, profiler) and by failed attaches, and whether those write records without an `ATTACH_DATABASE` record (rule 5's watermark).
- **8f**: whether the server escapes line breaks or writes them verbatim, in:
  - the statement text;
  - `isc_dpb_process_name`;
  - the user name of a `FAILED ATTACH_DATABASE`;
  - error texts.

  Also, whether an attachment's `TCPv4:<address>/<port>` can be corroborated with `/proc/net/tcp` at read time (rule 9).

### R2. Database names: aliases (obligation 12)

**Measured**:
- The trace prints the attach string as the client gave it. A `databases.conf` alias is printed verbatim (`appalias`), while `MON$DATABASE_NAME` gives the resolved path (`/data/app.fdb`).
- Paths through a symlink, `..` or `//` are printed canonicalised, in the trace and in `MON$DATABASE_NAME` alike.
- A hard link is printed as the path used, in both.
- Under the accepted text, records of a client that attaches through an alias match no declared database, so they would be dropped as records of an undeclared database.

**Proposed rules**, refining "Database paths" of decision 6 (records of undeclared databases: R1 rule 8):

1. **The names of a declared database** are:
   - (a) its **resolved path**, from `MON$DATABASE.MON$DATABASE_NAME` read on the agent's own attachment at every `check()`: a constant text, a monitoring table, no file opened by the agent and no path in any statement;
   - (b) when `attach` is an alias, **the alias string exactly as written** in `agent.yaml`, byte for byte, with no case folding and no trimming.

   A record belongs to a declared database when its printed name equals one of these names exactly, or resolves to one through rule 2. A case-only variant of a declared alias (`APPALIAS` for `appalias`) is not equal: it is ambiguous, never dropped, pending measurement 12c. The path and the alias stay on the agent host (decision 5).
2. **Other aliases of the same file.** Another client can attach through another alias of the same file, and that alias cannot be matched to the file without the alias map.
   - **Reading the map.** `agent.yaml` names `firebird.audit.databases_conf`. Its path must equal `<root>/databases.conf`, where `<root>` is the declared Firebird root directory (decision 6, M3). The file is read under the file rules of [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md): `O_NOFOLLOW`, one hard link, no ancestor directory the agent can write, and the `with_open_check` check that the path still names the handle.
   - **Grammar.** The grammar is closed: `alias = path` lines, comments, and per-database `{ … }` blocks with a closed key set. An `include`, an unknown key, a parse error or a writable file means the map is not evaluated.
   - **Macros** (security review L-4). The `$(root)` and `$(dir_*)` macros of a closed list, checked per image by a drift test, are resolved against the declared root. An entry that uses any other macro is an alias with an unknown path: its printed name is ambiguous, but the rest of the map stays evaluated.
   - **Resolving a printed name.** A printed name that is not an absolute path is looked up exactly in the map:
     - an alias that maps to a declared database's resolved path belongs to that database;
     - an alias that maps to another path names an undeclared database (R1 rule 8 decides what becomes of its records), and that path goes through rule 3;
     - a name that is not in the map is ambiguous, and never dropped.
   - **Without an evaluated map**, every non-absolute printed name other than a declared alias is ambiguous, and the level is Limited with `audit.trace_config_not_evaluated` and the new label `databases_conf`.
3. **M4 is kept.** After alias resolution, a name that is not one of a declared database's names is ambiguous, and caps that database at Limited until the operator's configuration is fixed, when it either:
   - has the same file name as the declared database; or
   - names a file whose `(st_dev, st_ino)` (from a `stat` of the resolved path, without opening the file) equals the declared database's.

   Proof 11 (R1) adds the single-link condition, because under it a client that attaches through a hard link is not logged at all.
4. **Trace sections, restated with the measured semantics** (obligations 12 and 13; security review M-5). This replaces the section rule of proof 3.
   - **When a named section applies.** It applies to a declared database only when its pattern contains no `SIMILAR TO` metacharacter (`_` and `%` included) and **equals the full resolved path**, or, pending measurement 12b, the alias string. A plain file name is **not** a match: the measurement matched sections on the full path. A section whose pattern the agent cannot evaluate (a `SIMILAR TO` pattern, or a plain file name) caps the level when it comes **before** the first matching section, because the server might apply it instead.
   - **The effective settings** are the default section's, overridden by those of the first matching named section. Measurement 13b verifies this inheritance. Proofs 3, 4 and 11 are evaluated on the effective settings.
   - **First match.** Only the first matching named section applies (measured). A section after it is never reached, so it does not cap the level and is named in the local detail. With the restatement above, this relaxation of the accepted proof 3 is sound.
   - **Aliases.** It was not measured whether, for an attach through an alias, the server matches sections against the alias string or the resolved path (measurement 12b). Until it is, proofs 3, 4 and 11 are evaluated for the resolved path **and** for every alias that maps to it, the declared alias included. If the effective settings differ between these names, the level is Limited (`audit.trace_config_not_evaluated`). A client that uses an alias absent from the map is ambiguous (rule 2).
5. **`databases.conf` changed while the server runs.** It was not measured whether the server applies a changed `databases.conf` without a restart, for example at the next attach (measurement 12c). Until it is, the rule is fail closed:
   - `databases.conf` follows proof 2: a file changed after the server process started is not proven (Limited, label `databases_conf`) until the next server restart;
   - the agent checks the file's `mtime` and `ctime` with a `stat` before each read cycle. After a change it re-reads the map, and the records it handles between the change and the re-read and re-evaluation that use a non-absolute name are ambiguous;
   - a declared alias that the operator points at another file shows at the next `check()` as a new resolved path, which is treated as the same change. Discovery follows the alias as declared, and the local detail notes the change.

**New measurements**:
- **12b**: section matching for an attach through an alias (alias string or resolved path).
- **12c**: when the server applies a changed `databases.conf` (at restart only, or at the next attach), whether alias lookup is case-sensitive, and which per-database keys of `databases.conf` can change what the trace logs.
- **13b** (extends obligation 13): on 4.0 and 5.0, in SuperServer and SuperClassic, with an enabled default section:
  - the inheritance of default settings by a named section;
  - whether a plain file-name pattern matches;
  - the case sensitivity of path matching.

### R3. The extended variant and `RDB$CONFIG` (obligation 3)

**Measured**:
- With `SELECT_ANY_OBJECT_IN_DATABASE`, the `ext` account reads the whole server configuration from `RDB$CONFIG`: 77 rows on 5.0 and 73 on 4.0, including `ExternalFileAccess`, `UdfAccess`, `AuthServer`, `WireCrypt`, `RemoteBindAddress` and `ServerMode`.
- `min` and `none` read 0 rows, with no error.
- The privilege does not reveal other attachments in `MON$ATTACHMENTS`, nor other users' rows in `SEC$USERS`.

The answer to open question 5 assumed that the variant "exposes nothing beyond user tables and the already public `RDB$` tables". That assumption does not hold.

**Options**:
- **(a) Keep the variant opt-in, with the exposure stated, and contain it** (proposed):
  - **Never sampled.** `RDB$CONFIG` is named in the closed list of relations never sampled (decision 5, M5), so the drift test asserts that it is listed. It is a virtual table and is not sampled under decision 5 already; naming it keeps that from depending on its system flag.
  - **No findings on it.** Its values are the server's settings (paths, addresses, plugin names), not user data. Classified, they would produce findings that say nothing about the data the operator protects, and would send masked samples of server paths and addresses to the console.
  - **A note when readable.** `check()` probes whether `RDB$CONFIG` is readable with the one-bit form of decision 4 (`SELECT CASE WHEN EXISTS (SELECT 1 FROM RDB$CONFIG) THEN 1 ELSE 0 END FROM RDB$DATABASE`; the minimal account gets 0). When it is readable, `check()` reports `privilege.global_privileges` with the new label `server_config_readable` at every check, with or without `extended_grants: true`. This is the stated cost of the variant, next to `privilege.extended_variant`.
  - **The agent's own reads.** Decision 4 reads the server settings "through `RDB$CONFIG` where visible", and decision 6 lists `RDB$CONFIG` as always reported. The agent reads it only when the probe returns 1, with one constant text that names a closed list of keys: the decision 4 settings, and `ServerMode` for the proof 2 cross-check. The values go to the local detail only, never to the console.
  - **Own-read exceptions.** That exact text and the probe join the own exceptions of the credential-bearing list. A record is the agent's own only when every condition holds (security review L-1):
    - the own-attachment rule holds: the binding is anchored and not poisoned, and the record is not ambiguous;
    - the text is exactly the constant one;
    - the per-table block names exactly the relations the matrix records for that constant text: `RDB$CONFIG` for the read, `RDB$DATABASE` for the probe (measurement 3b confirms whether virtual relations appear in the counters);
    - `records fetched` is at most the number of keys in the closed list (1 for the probe).

    Any other read of `RDB$CONFIG` stays always reported. A forged duplicate `ATTACH_DATABASE` for the agent's predicted id makes the agent's attachment non-own (R1 rule 3), so its reads are then reported: loud, not hidden.
  - **Drift test** (measurement 3b). On the matrix, per image, it lists the `RDB$CONFIG` key names and every relation whose visible rows differ between `min` (with its table grants) and `ext`. It fails on a key or a relation outside the reviewed list, so that a later version cannot widen the variant without notice. It runs on a **populated** state (security review L-6):
    - other attachments live;
    - other users in the security database;
    - context variables set;
    - a profiler session running;
    - a database that is its own security database;

    and it covers every `MON$`, `SEC$`, `PLG$` and virtual relation of the image.
- **(b) Drop the extended variant**: only per-table grants. This is simpler, and a stolen agent credential never shows the server configuration. On the other hand, every new table needs a grant (the ADR-0012 maintenance cost), and operators with many tables or changing schemas lose the variant.

**Recommendation: (a).** The exposure is the server's configuration, not user data. The parameters on it that matter to an attacker (`ExternalFileAccess`, `UdfAccess`, the bind address, the authentication plugins) are reconnaissance for someone who already holds the agent's credential. The variant is opt-in, reported, and never samples the relation. The drift test listing the key names is the condition: if a key appears that carries a credential, the recommendation is reopened.

### R4. Measured facts that refine the text, and their handling

- **The trace log holds secrets.** `CREATE USER … PASSWORD '…'` is written verbatim in the statement text; the server does not mask it. The internal `PLG$SRP_VIEW` update that follows carries the verifier and the salt as parameters. With every client's parameter values (decision 6), this makes the audit log a **secret-bearing file**: whoever can read it reads the passwords set through SQL, and every live header token (R1). The threat model of docs/05 states this. Decision 6 already treats statement text and parameters as literals (I2), and parameter lines are dropped at parse.
  - **Handling the record buffers** (security review L-5):
    - record buffers are reserved once at the 1 MiB record bound, or are `Zeroizing` buffers, so that no reallocation leaves an unzeroized copy;
    - the tailer's read chunks, the skip path of an oversized record, and the record held at EOF are zeroized as well;
    - parse errors, panic payloads and `tracing` fields carry offsets and kinds only, never record content.
  - **The #82 end-to-end marker test must cover**, asserting that no marker appears in any uplink payload, agent log line, metric (the `audit_own_*` metrics included) or spool file:
    - `CREATE USER … PASSWORD` and `ALTER USER … PASSWORD`;
    - a literal cut at `max_sql_length`;
    - `EXECUTE BLOCK` with `EXECUTE STATEMENT … ON EXTERNAL … AS USER … PASSWORD`;
    - a marker in the user field of a `FAILED ATTACH_DATABASE` (fingerprinted, never in clear);
    - a marker in `isc_dpb_process_name`;
    - the `PLG$SRP_VIEW` parameter record.
- **Access to the log.** The server creates the audit log `0600`, owned by `firebird:firebird`, so an agent in the `firebird` group cannot read it. The operator grants the agent read access explicitly.
  - **The user guide's setup.** The user guide recommends a default ACL on the log directory that gives the agent's user read only, so that the files the server creates at rotation inherit it. It advises against adding the agent to the `firebird` group, whose members can often write the database and security database files. The file rules (decision 6) still refuse a log the agent can write. That rotated files inherit the default ACL is confirmed in the dev service (P10-D).
  - **Proof 1 gains a readers check** (security review M-6):
    - **What is inspected.** At every re-evaluation, `check()` inspects the log, the rotated files it still tracks, and the log directory: the mode bits, the owner and group, and the ACLs (`system.posix_acl_access` and `system.posix_acl_default`, with the mask applied).
    - **Group members.** The members of every group that has read access are enumerated from `/etc/group` and `/etc/passwd`. A group whose membership cannot be enumerated (for example through NSS) counts as readable by others.
    - **Identity files that are not the host's** (security review L-e). The agent's `/etc/passwd` and `/etc/group` may not be the host's: the agent runs in a container (detected as in decision 3), or in a user namespace (`/proc/self/uid_map` is not the identity map). In that case the readers check proves nothing, and the log counts as readable by others. An agent in a container therefore gets no Partial level from a Firebird target. Whether to let an operator declare the host's identity files, mounted read only, is left to a later refinement.
    - **The finding.** Read access for any uid other than root, the server's account and the agent's account is reported with the new note `audit.log_readable_by_others` (the local detail names the uids and groups), and Partial is withheld while it lasts.
    - **Documentation.** The docs/05 follow-up (P10-G) states the check.
- **Roles.** A role granted `DEFAULT` is in use (`RDB$ROLE_IN_USE` is `TRUE` and its grants work) while `CURRENT_ROLE` is `NONE`, and the trace's attachment line shows the role `NONE`.
  - `check()` decides which roles are in use with `RDB$ROLE_IN_USE` and `RDB$SYSTEM_PRIVILEGE`, never `CURRENT_ROLE`. `CURRENT_ROLE` is read for the local detail only.
  - `RDB$SYSTEM_PRIVILEGE` takes an unquoted keyword, not a string.
  - The own-attachment rule's "role the reader role or none" matches the `NONE` shown.
- **Counters of nested reads** (obligation 7; this answers open question 13 in the affirmative). The per-table block of a top-level `EXECUTE_STATEMENT_FINISH` includes relations read two call levels deep. Procedures are therefore named together with the counters' relations, under the filters, with no forced `*`. `*` is still added when a record has no per-table block.
  - **No double counting.** The `EXECUTE_PROCEDURE_FINISH` records (and the function and trigger ones) carry the same aggregated block, so the agent must not count the same reads twice.
  - **Rule, folding by maximum** (security review N-1). A procedure, function or trigger finish record is folded into the next statement finish record of the same attachment and transaction. Folding adds its object name and the relations of its counters (a union). The event's counters for each relation and its row count are the **maximum** of the statement record and the folded records.
    - **No double count.** Taking the maximum does not count the same reads twice, because the statement's counters already include the nested reads.
    - **No lowered count.** A forged statement finish with `0 records fetched` cannot lower the row count of a real nested record that carries a moved trailer, so `volume.large_result` still applies.
  - **When a nested record is not folded.** A nested record is folded only into a statement finish of the same binding, and only when that binding's `ATTACH_DATABASE` record and the transaction's `START_TRANSACTION` record were both read, in that order, before the nested record. In two cases the nested record becomes an event of its own, with its own counters and row count:
    - it comes from a binding created after the statement's own `START_TRANSACTION` or `ATTACH_DATABASE` record;
    - it comes from an attachment whose transaction start was not read.
  - **No statement finish follows.** When no statement finish record of that attachment and transaction follows (for example an `ON CONNECT` trigger, or an attachment that detaches first, or after 10 minutes), the record also becomes an event of its own, with its own row count.
  - **Measurement 7b**: nested finish records are written before the finish record of their statement.
- **Unquoted identifiers are ASCII only** (security review L9, open question 11). `CREATE TABLE café` is a syntax error on 4.0 and 5.0, whatever the client character set and the user. A quoted `"café"` is stored as written. ASCII upper-casing of unquoted names is therefore sufficient, which confirms the answer to open question 11. The matrix test of decision 9 stays, as a regression test.
- **When the configuration is read** (obligation 11). In SuperServer, a change to the trace configuration without a restart had no effect: the configuration is read when the trace session starts with the server process. The "changed after the server process started" branch of proof 2 applies. In SuperClassic, where each attachment starts its own trace session (R1), the configuration may be read again at each attachment. The same rule is fail closed there: any change after the server process started is not proven.
- **First match only** (obligation 13). Only the first matching named section applies; sections do not accumulate. Proof 3 is restated on that basis in R2, rule 4.
- **Failed logins.** After three rapid failed logins from one loopback source, the fourth was delayed about 8 s. Later attempts were fast again, and a correct login then succeeded (a delay, not a lockout). The rule of decision 1 (no retry until the next heartbeat check after an authentication failure) keeps the agent from triggering the delay. The mapping `isc_login` → `authentication_failed` is confirmed.

## Implementation note (2026-10-26): lot 1

Recorded after the merge of lot 1 of the connector (#365, at `21518f5` on `dev`: the `connector-firebird` crate with its own wire client, SRP-256, ChaCha wire encryption, `check()` and the core's C1 rules); not released yet. No decision changes; the accepted text above is unchanged, and the corrections below take precedence over it where they differ.

**Protocol facts measured on 4.0.7 and 5.0.4.** They differ from the forms written in decision 1 and are recorded as protocol facts; the lot 1 security review judged them not a weakening.

- **SRP-256 forms**: `k = SHA1(N | PAD(g))`; `u = SHA1(min(A) | min(B))`, from the minimal big-endian bytes of `A` and `B` (not padded); the salt is hashed as its hex text (1 to 64 hex characters, checked); `M = SHA256(H(N) xor H(g) | SHA1(user) | salt | A | B | K)`, Firebird's own form.
- **Wire keys** arrive in the `op_response` that follows `op_cont_auth`. The cipher key is `SHA-256(K)`. The `ChaCha64` plugin data is an 8-byte nonce; the `ChaCha` plugin data is 16 bytes, a 12-byte nonce then a big-endian 32-bit initial counter.
- **The accepted protocol version** comes back sign-extended (`0xFFFF8010` for protocol 16).

**Obligations.**

- **Obligation 2, first half, done**: 4.0.7 and 5.0.4 accept an offer of protocol 16 only; 3.0.14 answers `op_reject` before any password-derived data is sent. **Second half still open**: `op_cancel` during a pending fetch on a real server, to run on the engine matrix before lot 2's sampling relies on it.
- **Obligation 14, done**: `MON$REMOTE_ADDRESS` shows a `socat` forwarder on loopback as the forwarder's address, so the forwarder check of decision 3 works.
- **System privileges**: bit *n* of `RDB$ROLES.RDB$SYSTEM_PRIVILEGES` is the privilege at position *n* of the server's list. A drift test pins the list: 26 bits on 4.0.7, 27 on 5.0.4.

**Correction to decision 5 (lot 1 review L1): the `attach` name is sent in clear.** Decision 5 says `attach` is sent inside the encrypted session. It is not: the name (alias or path) travels in `op_connect`, before wire encryption starts, because the server selects the per-database `AuthServer` and `WireCrypt` settings of `databases.conf` by that name. Measured: with an empty name, a server whose `databases.conf` alone sets `Srp256` fails the login with `isc_login_error`, and a server whose `databases.conf` alone requires `WireCrypt` sends no wire key. The name travels on loopback only (decision 3) and is still never sent to the console, logged or put in `last_error`. Operators should declare a `databases.conf` alias rather than a path that names a person.

**Corrections to decision 4.**

- **The default-role grant**: the form that works on 4.0 and 5.0 is `GRANT DEFAULT DATABASTION_READER TO USER DATABASTION_AGENT;`. The example in decision 4, `GRANT DATABASTION_READER TO USER DATABASTION_AGENT DEFAULT;`, is a syntax error on both versions; the user and security documentation use the working form.
- **The server's account and `peer_uid`**: the official image runs the server as root, so the default `peer_uid: firebird` fails against it. Run the server as its own account (uid 84 in the image) and declare that uid, rather than setting `peer_uid_root: true`: a root-owned socket matches any root process, which leaves the forwarder check as the only guard.
- **Containers**: a numeric `peer_uid` is required when the agent runs in a container, detected by `/.dockerenv`, its cgroup, a `uid_map` that is not the identity, `KUBERNETES_SERVICE_HOST`, an overlay root filesystem or `/proc/1/sched` (this settles the "to settle at implementation" of decision 3).

**Implementation decisions of lot 1.**

1. **C1** (P10-C review): a `firebird` target status at `audit_level` `full` is rewritten to `partial`, the ceiling (decision 6), before spooling and before sending.
2. **`check()` covers every declared database** (at most 64): it attaches to each, and the check fails as a whole if one attachment fails.
3. **Fail closed on unreadable account facts**: an unreadable own `SEC$USERS` row, unreadable object grants or authentication mappings, or rows with NULL key columns block Discovery and Audit. The role graph not evaluated stays the non-blocking `role_graph` note of decision 4.
4. **Other roles (review N4, decided)**: roles other than the reader role get no note of their own.
5. **Authentication mappings**: entries of `RDB$AUTH_MAPPING` and `SEC$GLOBAL_AUTH_MAPPING` whose target is the user `SYSDBA` or the role `RDB$ADMIN` and whose source can match the account are refused (labels `sysdba` and `rdb_admin`). A database condition on a mapping is treated as a match, which may over-refuse; a failed read of either table blocks.
6. **Role memberships held `WITH ADMIN OPTION`** give `privilege.grant_option`.
7. **`discover` and `audit_stream` refuse** until a `check()` has cleared the target.

**Residuals from the lot 1 re-review (notes A to C).**

- **(A) `SEC$GLOBAL_AUTH_MAPPING` visibility is not measured**: whether a plain account sees other users' global mappings is not known. A read that returns no row cannot be told from "no mapping"; if the table is not filtered, any global mapping makes every account report `credential_relation_readable`. To measure on the engine matrix, then keep the probe with this residual stated, or drop the table from the probe list.
- **(B) Chained mappings**: the mapping match compares the source with `CURRENT_USER`, the name after mapping, so a chain of mappings from the original login name is not followed. Mappings in effect are still caught through `CURRENT_USER` and `RDB$ROLE_IN_USE`.
- **(C) Mappings to other roles**: a mapping to a role other than `RDB$ADMIN` that holds refused system privileges is caught only while that role is in use, the same residual as the role graph (decision 4).

User tables named `RDB$…` or `MON$…` are allowed and carry system flag 0; a trailing space in a quoted name is not stored; neither server lets a client create a name that is not valid UTF-8.

**Clarifications of decision 5.**

- **The byte budget (lot 2 review L1, a deviation judged equivalent or better)**: at 32 MiB the connector stops requesting rows at the current round (at most 64 rows of at most 64 KiB each in flight, parsed row by row and zeroized), then closes the cursor (`DSQL_drop`) instead of sending `op_cancel`: no fetch is pending at that point, and a cancel could reach the next request. `op_cancel` stays the answer to the client deadline.
- **`BLOB SUB_TYPE BINARY`** (sub-type 0) is sampled as `OCTETS` and kept only when it is valid UTF-8 without control characters, as decision 5's conversion text says. The Consequences line "non-text blobs" means blob sub-types above 1 (user sub-types and the other system sub-types), which are never read.
- **Catalog names are read as raw bytes** (`CAST … CHARACTER SET OCTETS`): trailing `0x20` bytes are dropped, then strict UTF-8 and the identifier rules are checked per row. A bad relation row makes that relation `skipped_error` alone; a bad column row skips its relation; any dropped row leaves the CAS store guard incomplete (`privilege.not_evaluated`). Local details give counts only.
- **The never-sampled list** holds every system relation of both images (`RDB$CONFIG` included) and the prefixes `PLG$SRP*`, `PLG$USERS*` and `PLG$PROF_*`, with drift tests over a user database and the image's own `security<N>.fdb` (more than 40 names). Residual: profiler tables created by `RDB$PROFILER` are covered only by the `PLG$PROF_` prefix.

**Refinement of decision 3: the peer-uid lookup (lot 1 review L1).** A lookup that sees 0 or 2 matching rows is repeated, at most 3 times 20 ms apart, under one overall deadline of 2 s; the last read decides and must show exactly one row for the full 4-tuple, owned by `peer_uid`. A wrong uid, 65534, root without the opt-in or a cut read fails at once. Cause, measured: while a concurrent connection completes its handshake, its socket moves from the listener's `SYN_RECV` entry to an `ESTABLISHED` entry during the `/proc/net/tcp` read (7 of 22 integration runs failed without the retry, 0 of 40 with it). The security review found that a local process cannot add a row for the agent's 4-tuple under another uid.

**The CAS store guard.** Firebird `SELECT` is granted per table only, so a readable ticket registry always raises `privilege.ticket_credentials_readable`. `check()` reads the catalog of every declared database at each heartbeat, bounded by the check deadline and failing closed; its cost is to measure in the P10-D load run.

### R5. `TRACE_INIT` / `TRACE_FINI` are per attachment in every mode (measurement 8c)

**Measured** (4.0.7 and 5.0.4, SuperServer, SuperClassic and Classic): every attachment, the server's own `<internal>` attachments included, every service session and every failed or unauthorized attach is preceded by a `TRACE_INIT` and followed by a `TRACE_FINI`, both on that attachment's token. Nothing brackets a server run: one 5.0.4 SuperServer run held 77 `TRACE_INIT` records for 70 `ATTACH_DATABASE`, 3 `ATTACH_SERVICE`, 1 `UNAUTHORIZED ATTACH_DATABASE`, 1 `CREATE_DATABASE` and 2 Garbage Collector attachments. `MON$SERVER_PID` equals the header pid on the minimal account's own row, and `/proc/<pid>/stat` (field 22, the start time) is readable by another uid in the same pid namespace (8d).

R1 rule 2's SuperServer branch (a `TRACE_INIT` that carries the current pid triggers a stop and a confirmation; a second `TRACE_INIT` in the run is ambiguous) would stop the stream at every attachment, or, during the cooldown, make every attachment ambiguous.

**Proposed**, amending R1 rule 2:

1. **One rule for every mode.** In SuperServer, as R1 already said for SuperClassic, `TRACE_INIT` and `TRACE_FINI` belong to the attachment, service session or failed attach whose token they carry. They **never trigger a stop** and never start or end a run. The SuperServer items of R1 rule 2 that rely on a run-wide `TRACE_INIT` (the stop on a `TRACE_INIT` with the current pid, the cooldown keyed on the start time, "a second `TRACE_INIT` in the current run", "a record of the current run after its `TRACE_FINI`", and the boundary "at the first `TRACE_INIT` after the last confirmed position") are withdrawn.
2. **How the two records are checked.** They carry no objects and produce no event.
   - A `TRACE_INIT` is well formed when it carries the current run's pid, its body is the fixed session line the matrix records per version (measurement 8h), and its token is held by no live binding. Otherwise it is ambiguous.
   - A `TRACE_FINI` is well formed when it carries the current run's pid and the fixed session line, and either its token's binding ended at the previous record that carried that token (`DETACH_DATABASE`, `DROP_DATABASE`, `DETACH_SERVICE`, a `FAILED` or `UNAUTHORIZED ATTACH_DATABASE`), or its token is held by a live **internal binding** (R6), which that `TRACE_FINI` ends. The internal binding is the one binding a `TRACE_FINI` ends. Otherwise it is ambiguous.
3. **A new pid** still goes through R1 rule 2's stop and confirmation, with its limits (one unresolved stop at a time, at most 60 s, remembered failed pids, the 10-minute cooldown). The run boundary of a restart with a new pid is the first record that carries the new pid. Unchanged.
4. **A restart with the same pid is found from the start time only**, and placed in the log by log positions (security review M1).
   - **Samples.** The stream reads `/proc/<run pid>/stat` at stream start and before and after each read cycle (a read of one file, no SQL, no network), and records each sample with its log position. `check()` reads `MON$SERVER_PID` and the start time at every re-evaluation, as R1 rule 1 says, and records its sample the same way.
   - **The ambiguous interval.** When a sample shows a start time that differs from the current run's, the restart happened between the last sample with the unchanged start time and this one. The **interval** is the log range from the end-of-file offset of that last unchanged sample to the end-of-file offset of the detecting sample.
   - **Before the interval**, the parser keeps the old run's state: its bindings, its own-attachment lifetimes and its watermarks. Records there are judged as before.
   - **Inside the interval**, every record is ambiguous (always reported, with `*`, under the fix-3 attribution).
   - **When the read position passes the end of the interval**, the old run ends there: every binding of the old run ends, the own-attachment lifetimes of the old run close, and the new run's state applies. The stream asks for an immediate `check()` to confirm the new run.
   - **At stream start**, when the first sample shows a start time other than the persisted run's, the interval runs from the persisted read position to the end-of-file offset of that first sample.
   - **An `ATTACH_DATABASE` inside the interval** creates a binding that is **tainted**: its records are ambiguous until both hold: `check()` has confirmed the new run, and the stream has read, past the interval, the agent's own `ATTACH_DATABASE` of the new run (matched by its attachment id and its local port). From then on its later records are judged normally. Any token conflict with another binding, of the old run or the new one, poisons it (R1 rule 3).
   - **Until the new run is confirmed** by `check()` (the same pid and the new start time, or a new pid), records are handled as R1 rule 2 handles an unconfirmed pid: ambiguous, the stream not stopped.
   - **A process that is not visible** (another pid namespace, or `/proc` mounted with `hidepid=2`, security review N2) is not read as "the process is gone": no run change is inferred from it. Proof 2 is not proven (Limited), and R1 rule 1's best effort applies, under which a restart with the same pid is not detected.
5. **History walks.** In every mode, a pid change in a history walk starts a run only at a `TRACE_INIT` record; any other pid change is ambiguous. A restart with the same pid inside a walked history, before the persisted read position's first sample, cannot be seen from the log: the old run's bindings are then never ended, and a reused token makes its records ambiguous (R1 rule 4).

**Alternatives considered.** (a) Keep a run-wide boundary from the log, for example the first `TRACE_INIT` after a gap in time: forgeable by any client and not written by the server. (b) Stop the stream at every `TRACE_INIT` and confirm: one stop per attachment, unusable. (c) Read the start time only at `check()` (every 5 minutes): the interval would cover up to 5 minutes of records; reading one `/proc` file per read cycle costs nothing. (d) Apply the change at the read position: when the agent lags, records written before the restart would be judged with the new run's state and records written after it with the old one's (M1).

**Residual risks.**
- **A restart within one clock tick.** `/proc/<pid>/stat` counts the start time in clock ticks (usually 10 ms). A restart with the same pid is missed only if the new process starts in the same tick as the old one, so only if the old run lived less than one tick (security review N2): no server run that wrote records the agent relies on lives that short. Even then the old run's bindings stay live, a reused token is ambiguous (loud), and the agent's own attachments are closed by the lost-connection rule of decision 3. Nothing is hidden.
- **Local processes that run Firebird's embedded engine** with write access to the log (8e: root or the server's account, whose client fell back to its embedded provider) write records under their own pid. Each such pid costs one stop, then is remembered (R1 rule 2). These processes can write the log anyway and are outside what the parser can defend against (proof 1, R4).

**Effect.** No change to the levels, notes or protocol. The metrics `firebird_audit_stream_stopped_seconds_total` and `firebird_audit_run_confirmations_failed_total` and the label `run_confirmation_stalled` stay as R1 defined them.

### R6. The server's internal attachments: the Garbage Collector (measurement 8e)

**Measured**: in SuperServer only, each time the server opens a database (the first attachment after it was closed), a `Cache Writer` and a `Garbage Collector` system attachment (`MON$SYSTEM_FLAG = 1`) take the two attachment ids before the opening attachment. The Cache Writer writes nothing. The Garbage Collector writes a `TRACE_INIT`, then `START_TRANSACTION` and `COMMIT_TRANSACTION` records with the attachment line `<database> (ATT_<n>, Garbage Collector, NONE, <internal>)` (no `:role`), on a token no live binding holds, and **no `ATTACH_DATABASE` record**. SuperClassic and Classic have neither attachment. Under R1 rule 5's watermark, the Garbage Collector's records name an id above the watermark with no `ATTACH_DATABASE` read for it: ambiguous at every database open.

**Proposed**, amending R1 rules 3 and 5:

1. **The internal shape.** A record has the internal shape when all hold:
   - the server mode, proven by proof 2, is SuperServer;
   - its event is `TRACE_INIT`, `START_TRANSACTION`, `COMMIT_TRANSACTION`, `ROLLBACK_TRANSACTION` or `TRACE_FINI`;
   - its attachment line (for the transaction events) is exactly `<name> (ATT_<n>, Garbage Collector, NONE, <internal>)`, byte for byte: the process name exactly `Garbage Collector`, the only entry of the closed list; the character set field `NONE`; the protocol field exactly `<internal>`; no `:role`, no address, no port. `Cache Writer` is not on the list (security review L1): it writes nothing, so a record with that name is ambiguous until measurement 8h shows a real one;
   - its other lines are exactly the lines the matrix records for that shape per version (the transaction line, and a client-process line if the server writes one; measurement 8h), with no statement, no separator line, no parameter, no trailer;
   - `<name>` belongs to a declared database (R2), or, without proof 11, to an undeclared one.
2. **The internal binding.** The first record of an id with the internal shape (its `TRACE_INIT`, matched to the following transaction record by its token) creates an **internal binding**, anchored like an `ATTACH_DATABASE` binding, with these limits:
   - **its id**: until measurement 8h, it must be above the highest id seen for the database identity in the run and within R1 rule 5's margin, or below the highest within R7's bounds (256 ids and 10 s of reading time); it raises the highest id as an `ATTACH_DATABASE` would. If 8h shows that the Garbage Collector's `TRACE_INIT` always comes before the opening attachments' records, also in a burst, the binding is made **structural** (security review L3): it is accepted only when the next `ATTACH_DATABASE` of the database identity, read within R7's 10 s, has the id the measurement gives (the internal id plus 1 or plus 2); otherwise its records are ambiguous and it ends;
   - at most **one** live internal binding per database identity at a time; a second is ambiguous;
   - it ends at its `TRACE_FINI` (R5 item 2) or with its run.
3. **What the internal binding allows.** Only records of the internal shape, on its token. Any other record that carries its id or its token (a statement, procedure or BLR record, a per-table block, an `ATTACH_DATABASE`, a service record, another process name) is ambiguous and **poisons** the internal binding: every later record of it is ambiguous too.
4. **What the internal records become.** Well-formed internal records produce no access event (transaction records carry no object) and are not the agent's own. They count as records parsed for proof 9.
5. **Anything else** with `<internal>` in the protocol field, or a process name outside the closed list (the Cache Writer, an automatic sweep worker, a replication or profiler worker, if a version writes one), is ambiguous until a measurement adds its shape to the list.

**Can a client forge the shape?** Yes. Line breaks are written verbatim in the statement text, the process name, the user name of an attachment (created by an administrator), the role of a failed attach and user exception messages (8f), so any client can write lines with the internal shape.
- **Inside its own finish record**, the forged header captures the real trailer that the server writes after the client's text: a trailer under a transaction event does not fit the event (H1 fix 1), so the forged record is ambiguous, and the read stays reported with its real counters.
- **In a record without a trailer** (an `ERROR` record carrying a user exception message, a client-process line), a forged internal record parses as well formed. It carries no object and no row count, so it cannot hide a read. What it can do: take the internal slot of its database, so that the real Garbage Collector of the next database open is ambiguous, or raise the highest id within the margin, so that later real attaches are out of order and ambiguous (loud; R7 bounds how far).

**Alternatives considered.** (a) Leave R1 rule 5 as written: every database open in SuperServer caps the level for 24 h. (b) Ignore every record of an id with no `ATTACH_DATABASE`: a forger could then put a real trailer under such an id and have it dropped. (c) Recognise the Garbage Collector from `MON$ATTACHMENTS`: the minimal account sees only its own row (first round, obligation 3), so it cannot.

**Residual risk** (for docs/08; restated after security review L3): a client can forge an internal Garbage Collector record that carries no read. It hides no read. Until the structural binding of item 2 applies, a forged internal binding that receives no `TRACE_FINI` holds its database's internal slot **until the run ends**, so the real Garbage Collector of every later open of that database is ambiguous: a durable denial of the Partial level for the rest of the run, loud (each such record is counted in `audit.log_records_ambiguous`).

**Effect.** No new note, label or protocol change. Measurement 8h pins the exact lines and the order at an open.

### R7. Attach order at a database open (measurement 8e)

**Measured**: on an open database, bursts of 16, 32 and 64 concurrent attaches wrote `ATTACH_DATABASE` records at most 11 ids out of order (4.0.7 SuperServer; at most 7 on 5.0.4, at most 6 in SuperClassic). When a burst of 30 concurrent attaches **opens** the database, 4.0.7 SuperServer wrote them up to 30 ids out of order (the whole burst), the late records about 1 s after those of higher ids; 5.0.4 SuperServer up to 12, SuperClassic 2 to 6. R1 rule 5's constant tolerance of 16 does not hold: on 4.0.7 the inversion grows with the burst.

**Proposed**, replacing the tolerance of R1 rule 5 ("Out-of-order attaches"). An `ATTACH_DATABASE` whose id is below the highest id seen for its database identity in the run, whose id was not seen before (otherwise R1 rule 3's duplicate poisoning applies), outside a confirmed restore, is **accepted in order** when both hold:

- **count**: its id is at most **256** below the highest id;
- **time**: it is read within **10 s of reading time** (as R1 rule 7 counts it: stops, back-pressure, parking and downtime not counted) of the record that first raised the highest id above its id.

Otherwise it is ambiguous and taints its binding, as R1 rule 5 says. The bounds are the same for every version and mode: the measured worst case (30 ids, about 1 s) is well inside them, and one rule is easier to test than a table. The P10-D load run checks them (measurement 8g: bursts of 256 concurrent attaches that open the database on 4.0.7 and 5.0.4). If 8g exceeds them, the bounds are raised in an implementation note before the Audit lot ships, never removed.

R1 rule 5's other parts stay: the highest id is raised only by ids at or below the agent's latest own `CURRENT_CONNECTION` plus the margin (4 096), and an id above that bound is ambiguous.

**Why widening the tolerance adds no power to a forger.** An accepted late id must be unseen. The unseen ids below the highest are: ids of real attachments whose `ATTACH_DATABASE` is still to come (forging one makes the real one a duplicate, which poisons both: loud), the Garbage Collector's id (an `ATTACH_DATABASE` on an id held by an internal binding poisons it, R6), and the Cache Writer's id, which writes nothing. A forged attachment on a Cache Writer id is a fresh binding, which is what the accepted misattribution residual (R1, open question 6) already allows with a fresh id above the watermark.

**Alternatives considered.** (a) A per-version count table (16 on 5.0, 64 on 4.0): the 4.0.7 inversion is bounded only by the burst size. (b) Time only, with the server's header timestamps: forgeable. (c) No tolerance at a database open: every application start that opens the database with a connection pool would cap the level for 24 h.

**Effect.** No change to levels, notes or protocol.

### R8. Records without a per-table block, and the agent's own statements (measurement 3b)

**Measured** (as `ext`, 4.0.7 and 5.0.4): reads of only virtual relations (`SELECT … FROM RDB$CONFIG`, `COUNT(*) FROM RDB$CONFIG`, `COUNT(*) FROM MON$ATTACHMENTS`, the agent's `MON$SERVER_PID` own-row read) and an `EXECUTE BLOCK` that reads no table have **no per-table block**: their finish record ends with `records fetched` and a performance line (`0 ms`, no fetch count). The decision 4 probe `SELECT CASE WHEN EXISTS (SELECT 1 FROM RDB$CONFIG) THEN 1 ELSE 0 END FROM RDB$DATABASE` has a block naming `RDB$DATABASE` only. The first `MON$` read of an attachment named `RDB$DATABASE` and `RDB$RELATIONS` (metadata loading), later ones nothing.

So R3's own-read condition (a block naming `RDB$CONFIG`) cannot hold, and under H1 fix 2 (a statement finish without a per-table block while `print_perf` is proven on is ambiguous) and R1 rule 7, every such statement, the agent's own reads at every `check()` included, would open a split window.

**Proposed**, amending H1 fix 2 ("Missing trailers"), proof 5, R3's own-read exceptions and "The agent's own statements and the always-reported rules":

1. **A second trailer shape for statement finish records.** An `EXECUTE_STATEMENT_FINISH` whose trailer is exactly `<n> records fetched` followed by a performance line, with no per-table block, has the **block-less** shape. It is well formed (it opens no split window, and it is not ambiguous for that reason) when the record is otherwise not ambiguous (header, token, binding, attachment line, no header-shaped line in the text, text not cut), its text **parses**, and it falls into one of these cases:
   - **(a) virtual relations only**: the relations its text names are all on the closed per-version list of **virtual relations**, and the text holds no call of a function outside the built-in list of decision 6, no procedure (`EXECUTE PROCEDURE`, a selectable procedure in `FROM`) and no `EXECUTE STATEMENT` (security review M2);
   - **(b) a statement kind that cannot read**: its kind is on a closed per-version list of statements that read no relation and produce no event (security review L6): `ALTER SESSION RESET`, `SET TRANSACTION`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE SAVEPOINT`, `SET BIND`, `SET TIME ZONE`, `SET DECFLOAT`, `SET SESSION IDLE TIMEOUT`, `SET STATEMENT TIMEOUT` and the other session-management statements the matrix lists per image;
   - **(c) code**: its text names no relation outside the virtual list but calls code: `EXECUTE BLOCK`, a procedure, a function outside the built-in list, or `EXECUTE STATEMENT`.

   **What "parses" means** (security review L4): the normalizer reads the whole text with no unterminated comment, string literal or quoted identifier, and the dialect 1 and dialect 3 readings (decision 6) give the same relation set; anything else does not parse. **The virtual list** is explicit names, per version, from the drift test that checks each listed name has relation type 3 (virtual) on the image (`MON$ATTACHMENTS`, `MON$STATEMENTS`, `MON$DATABASE`, `RDB$CONFIG`, the virtual `SEC$` relations and the like). No prefix decides: a user table named `MON$X` (system flag 0, allowed by both versions, lot 2) is not on it.

   A block-less finish whose text names a relation outside the virtual list (a persistent table, a view, `RDB$DATABASE`), or that does not parse, stays ambiguous under H1 fix 2 and opens a window, as now: a block was expected and is missing.
2. **Block-less nested finish records** (security review M4). Procedure, function and trigger finish records of routines that read no table may be block-less too (measurement 3e checks this per version). A block-less nested finish record is accepted when R4 folds it into a following statement finish of the same binding and transaction. Because the folding is decided only when that statement finish arrives, the parser holds the block-less nested record and the records after it until the decision, bounded by 256 records, 1 MiB and 10 s of reading time. A nested record that is not folded within that bound, or that R4 does not fold, keeps H1 fix 2: it is ambiguous and opens a window at its own position, so the held records fall inside the window.
3. **What a well-formed block-less record becomes.**
   - **Case (a)**: its objects are the virtual relations its text names. They are system relations, left out of the objects of reads as noise, **except** those on the always-reported lists (`MON$STATEMENTS`, `MON$COMPILED_STATEMENTS`, `MON$CONTEXT_VARIABLES`, `MON$CALL_STACK`, `RDB$CONFIG`, the `SEC$` credential relations), which keep their name and the always-reported mark. A record with no object left after the filters produces no event.
   - **Case (b)**: no event.
   - **Case (c)**: `*` is added and the event is always reported, with the virtual relations of the text under the case (a) filters ("whenever a record has no per-table block, `*` is added"; `EXECUTE BLOCK`, procedures and non-built-in calls as decision 6 says). No split window opens: the record is well formed, and its trailer is the one the server writes for code that read no table. Measurement 7c records, per version, the outer block and the trace records written when a PSQL function or procedure runs `EXECUTE STATEMENT` (and when a UDR reads a table, if measurable), so that docs/08 can state what the `*` stands for.
4. **The agent's own statements, restated** (replacing R3's own-read exceptions and the own-read exceptions of the two always-reported lists; security review L5, M3 and L7). A record is the agent's own only when the own-attachment rule holds (decision 6, with R1's anchored, unpoisoned binding) **and** all of the following:
   - **its text is in the connector's closed statement set**: exactly the constant texts of `sql::STATEMENTS` in `connector-firebird`, enforced by a test that the own-statement table and that set are the same, for `check()` attachments and scan attachments alike (`SET SESSION IDLE TIMEOUT 2 MINUTE`, the `CURRENT_CONNECTION` / `MON$SERVER_PID` / `MON$REMOTE_ADDRESS` own-row read, the `MON$DATABASE` reads, `MON$SEC_DATABASE` (R9), the `RDB$GET_CONTEXT` reads, the `SEC$USERS` own-row read, the one-bit probes, the `RDB$CONFIG` read of R3, the `RDB$AUTH_MAPPING` and `SEC$GLOBAL_AUTH_MAPPING` reads of the lot 1 mapping refusal, the catalog reads of decisions 4 and 5, the read-back probe), or the exact generated sampling text of a sampling credit (below);
   - **its trailer** is the shape the matrix records for that text and version (measurement 3d): block-less, or a block whose relations, after removing the per-version **metadata-loading set** (`RDB$DATABASE` and `RDB$RELATIONS` as measured), are exactly the expected set (`RDB$DATABASE` for the probes; the sampled table for a sampling text);
   - **its `records fetched`** is at most the bound the table gives for a constant text (1 for own-row reads and probes, the key count for the `RDB$CONFIG` read, the catalog bounds of decisions 4 and 5), and, for a sampling text, exactly the number of rows the connector counted for that execution;
   - **it consumes one execution credit.** The connector records one credit per execution of a statement: (attachment, text, transaction), and for a sampling statement also the row count it fetched. This replaces, for sampling statements, decision 6's credit by time window (the deadline plus 5 minutes) and per-object row budget, which stays as an outer bound. A matching record consumes the credit. A record on the agent's attachment whose text is in the statement set or is a sampling text but which finds **no credit left** is **ambiguous** (always reported, with `*`): a forged copy of an agent statement cannot become a second own record, and is loud.
5. **What is not the agent's own.** Any other record of the agent's attachments that misses one condition other than the credit is handled as any client's record: read objects are reported, always reported where the lists say so, and reads of noise relations (system relations outside the always-reported lists) produce no event.
6. **Statement texts must fit the log** (amending proof 5; security review L7). The agent's own records are recognised only by their whole text, and a cut text is ambiguous. So Partial also requires `max_sql_length` at least the length of the longest constant text of `sql::STATEMENTS`; below it, `audit.statement_text_limit_low` is reported and, unlike the accepted proof 5, the level is **Limited**, since every own read would be cut and ambiguous. The connector also keeps each generated sampling text within the effective `max_sql_length` read from the trace configuration, by sampling in more column batches when needed (decision 5, wide tables).

**Alternatives considered.** (a) Keep H1 fix 2 for every statement finish: every `check()` opens a window of 60 s of reading time, so Partial holds nowhere. (b) Accept every block-less finish as well formed: a forger's record that names a persistent table would then hide that its real block moved. (c) Exempt only the agent's own texts: other clients' monitoring reads (`MON$` dashboards) would still open windows constantly. (d) Keep the time-window credit for sampling statements: two records of one sampling text within the window would both be own (M3).

**Residual risks.**
- **Block-less records do not show volume or relations** beyond what the text names. A read of virtual relations is reported from the text, with the `records fetched` count; this is what the server writes, not a parser choice. For case (c), the `*` stands for what the code may have read (7c).
- **The forger's view.** A forger can end its own record with a block-less fake trailer when its text is of case (a) or (b); the real trailer then lands in the forged record that follows. This gives nothing beyond the fake full trailer that H-1 already showed; the real trailer is handled by R1 rules 3, 4 and 8, unchanged.
- **The agent's own reads under a guessed token.** 8b shows that few addresses occur (10 to 19 per run), so guessing the token of a live agent attachment is not hard. A forger who also knows the agent's attachment id and transaction could make one block-less read of its own look like one of the agent's constant reads, but only by consuming the credit of the agent's real execution, within that text's row bound, and only for a text whose expected trailer is block-less. The agent's real record then finds no credit and is ambiguous (loud). A read of a persistent table cannot be hidden this way: its block names the table.

**Effect.** No new note, label or protocol change. `audit.statement_text_limit_low` caps the level in the case of item 6. The never-sampled list (decision 5, lot 2) is unchanged.

### R9. A database that is its own security database (measurement 3b, open item of the refinement of 2026-10-25)

**Measured** (`databases.conf` `selfsec = /data/self.fdb { SecurityDatabase = selfsec }`, 4.0.7 and 5.0.4):
- `PLG$SRP` is a persistent user table (system flag 0, relation type 0), readable by `ext`: 4 rows, every user's SRP verifier and salt. R3's "server configuration, not user data" does not hold there; decision 4 refuses `ext` there, which is right.
- `PUBLIC` holds `SELECT` on `PLG$SRP_VIEW`, which shows each account its own verifier row: `min` and `none` read 1 row. Decision 4's one-bit probe ("a readable verifier or hash relation (`PLG$SRP`, `PLG$USERS`, their views) is a refusal") therefore refuses **every** account, the minimal one included, under the label `verifier_relation_readable`, which then names a right the account does not hold beyond its own row.
- `PLG$USERS` (the legacy user manager) was not measured.
- In such a database, the server's verifier lookups for every login (`SELECT PLG$VERIFIER, PLG$SALT FROM PLG$SRP WHERE PLG$USER_NAME = ? AND PLG$ACTIVE`, the attempted name as a parameter) and the verifier updates of `CREATE USER` are records **of the declared database**.

**Proposed**: a declared database that is its own security database is **out of scope** in phase 10, for Discovery and Audit alike, and is **excluded on its own** (security review M5). This amends lot 1 implementation decision 2 ("the check fails as a whole if one attachment fails") for this case only:

- `check()` excludes that database: Discovery does not scan it, and the Audit stream treats it as an undeclared database (under proof 11 its records are ambiguous, never dropped; without proof 11 the level is Limited, R1 rule 8). The other declared databases of the target keep running.
- `check()` reports the new note **`coverage.security_database_excluded`** ("{count} declared Firebird database(s) excluded: their own security database, or not shown not to be one; not read by Discovery or Audit"), with a local detail naming each excluded database (its operator label) and the rule that excluded it.
- The refusal of the account (decision 4) is evaluated on the other databases only; the one-bit probe is not run on an excluded database, so `verifier_relation_readable` is not raised for an own-row view.

**Detection**, fail closed (security review L8: a failed or cut read of any source below excludes the database):

1. `MON$DATABASE.MON$SEC_DATABASE` on the agent's own attachment reads `Self` (to verify on both versions, measurement 3c); any value other than `Default` or `Other`, a failed read or a cut read excludes it;
2. the catalog of the declared database, which Discovery and the CAS guard already read, holds the **security-database shape**: a relation `PLG$SRP` with the columns `PLG$USER_NAME`, `PLG$VERIFIER` and `PLG$SALT`, whatever its system flag. A bare `PLG$USERS` or `PLG$VIEW_USERS` name (the legacy schema, not measured) also excludes the database, with its own local detail ("legacy user-manager relation name found"). A failed or cut catalog read excludes the database. Rule 2 sees only the declared database's own catalog: it cannot tell whether another database uses this one as its security database;
3. the evaluated `databases.conf` (R2 rule 2) gives the declared database a `SecurityDatabase` key that names itself (its alias or its resolved path); a map that is not evaluated, or a failed read, excludes the database when the target has Audit configured (where R2 already reads the map). Unchanged in substance from the first version.

In every other database, decision 4's probe stays as written (no `PLG$` verifier relation exists there, so a readable one is still a refusal), and the never-sampled list stays (it covers `PLG$SRP*` and `PLG$USERS*` whatever the flag, lot 2). The shared security database (`security<N>.fdb`) cannot be attached remotely at all (first round, obligation 3).

**Alternatives considered.**
- **(b) A probe that tells the own row from every row**, such as `SELECT CASE WHEN EXISTS (SELECT 1 FROM PLG$SRP_VIEW WHERE PLG$USER_NAME IS DISTINCT FROM CURRENT_USER) THEN 1 ELSE 0 END FROM RDB$DATABASE`, together with the unchanged probe of `PLG$SRP` itself, would let Discovery run. Not proposed for phase 10: Audit of such a database would see the server's verifier lookup at every login in the declared log (an always-reported read of `PLG$SRP` by an internal attachment at each login, needing another internal shape in R6, with client-chosen user names as parameters), and the configuration is uncommon (embedded-style deployments). Revisit if operators ask.
- **(c) Refuse the whole target** (the first version of this refinement, with `unsupported`): one such database would stop Discovery and Audit of every other declared database of the target (M5).
- **(d) No note, a local detail only**: the operator would not see on the console why a declared database has no findings.

**Residual risks.** A user database holding a user table named `PLG$USERS` or `PLG$VIEW_USERS` is excluded although it is not a security database: an over-exclusion, stated in docs/08, which the operator fixes by renaming the table. The agent cannot see the security database's own content, so it does not tell an operator which users exist there.

**Effect.** One new note code, `coverage.security_database_excluded`, in the same unreleased contract revision as `engine.firebird` ("Protocol" below). docs/08 and the user guide (P10-G) state that a self-security database is not monitored.

### R10. Failed logins are not in the trace of the target database

**Measured** (4.0.7 and 5.0.4, SuperServer and SuperClassic, `log_connections = true`, `AuthServer` = `Srp256`, `Srp256, Srp` and `Srp256, Srp, Legacy_Auth`): a wrong password, for an existing user or an unknown one, writes **no `FAILED ATTACH_DATABASE` record** for the target database. The only trace is the server's own attachment to its security database (the verifier lookup with the attempted name as a parameter), written only where a section applies to the security database's path, so **never under proof 11**, whose sections apply to declared databases only. `FAILED ATTACH_DATABASE` is written when an authenticated attach fails (a missing file), `UNAUTHORIZED ATTACH_DATABASE` when remote access is refused. A failed service login writes nothing (8c). The first round's obligation 9 note was wrong on this point.

**Proposed**, amending decision 6, "Principals":

1. **Failed logins are not audited on Firebird.** `check()` reports `audit.failed_logins_not_audited` (an existing code whose engines already include `firebird`) for every Firebird target whose Audit source is configured, at every check, whatever `log_connections` says; with `log_connections = false` it is reported as well, and `log_connections` stays a label of `audit.trace_settings_missing` (proof 4).
2. **Not required for Partial**, as for SQL Server ([ADR-0051](0051-sqlserver-connector.md) decision 6: `FAILED_LOGIN_GROUP` "not required for Partial"). The level rests on reads and their objects; a wrong password reads nothing. docs/08 states the limitation in the Firebird Audit section: wrong passwords and failed service logins are not seen; password guessing against a Firebird server is visible only in the server's own failed-login delay (first round, obligation 9) and in host logs outside the agent.
3. **What stays.** `FAILED ATTACH_DATABASE` and `UNAUTHORIZED ATTACH_DATABASE` records are still parsed: their user names are fingerprinted, never sent in clear, and they count toward the failed-login flood cap. They are authenticated failures (a wrong file, remote access refused), not password failures, and docs/08 says so. An attachment line holding a role with a line break (8f, failed attaches) is ambiguous as any attachment line that does not parse.
4. **The registry text** of `audit.failed_logins_not_audited` names only "Firebird trace: log_connections off". It is made accurate in the same unreleased contract revision as `engine.firebird` (P10-C, `security-reviewer` review): "Firebird trace: a wrong password writes no record of the target database". See "Protocol" below.

**Alternatives considered.**
- **(b) An optional section for the security database**, written to its own declared log (`firebird.audit.security_log`), so that proof 11 still holds for the declared log. It would show the verifier lookups of failed logins, but: the attempted user name is a parameter, today dropped at parse unread (decision 6, I2), and this would make the parser read it and fingerprint it, a new I2 path with its own marker tests; a wrong password is not written as such, only inferred (a lookup with no following `ATTACH_DATABASE` on the same internal attachment, an unknown user as `0 records fetched`), and that inference is forgeable, because the attempted name is client-chosen text that may hold line breaks (8f); and the log would also carry `CREATE USER` verifier updates (secrets, R4). Not proposed for phase 10; a later refinement may take it up if the maintainer wants failed-login visibility.
- **(c) Withhold Partial without failed logins**: inconsistent with SQL Server, and it would make Firebird Audit Limited at best for a fact that says nothing about reads.

**Residual risk.** Failed logins against Firebird targets are not seen by the agent; the documentation says so in docs/08 and in the user guide.

**Effect.** No level change. A registry description is amended (P10-C); no new code or label for this part.

### R11. Confirmations and smaller amendments

- **7b confirmed**: nested procedure, function and trigger finish records come before their statement's finish record, on the same attachment and token, innermost first. R4's folding by maximum stands (R8 item 2 relies on it for block-less nested records).
- **8a, 8b confirmed**: an attachment's records always carry one token, `DETACH_DATABASE` carries it, and addresses are reused only after a detach. R1 rules 3 and 4 stand. Few addresses occur (10 to 19 per run in SuperServer, two in Classic): H1 fix 7's "guessable" is restated as "guessable in a few tries". Each wrong guess is ambiguous (loud); a right guess on a live attachment is covered by the R1 forger analysis and R8's residual.
- **8c, other records, confirmed**: `FAILED` and `UNAUTHORIZED ATTACH_DATABASE` records take a fresh token of their own, never a live one (R1 rule 4); service records share one token from `ATTACH_SERVICE` to `DETACH_SERVICE` (R1 rule 6); `SWEEP_START` / `SWEEP_FINISH` carry the sweeping attachment's id and token and are bound like any of its records.
- **8d confirmed, and restores through the services API**: R1 rules 1 and 5 stand (`MON$SERVER_PID`, the start time, `DB_GUID` and `MON$CREATION_DATE` changed by a restore). A services restore writes `DROP_DATABASE` (on the service's database attachment) and then `CREATE_DATABASE` on the same token, with no `ATTACH_DATABASE`. Amending R1 rules 3 and 5:
  - `DROP_DATABASE` ends its binding, as `DETACH_DATABASE` does;
  - `CREATE_DATABASE` anchors a binding, as `ATTACH_DATABASE` does, and its token may be the token whose binding the `DROP_DATABASE` just ended;
  - the restored database's ids restart low, so its `CREATE_DATABASE` and the next attaches are out of order and ambiguous until `check()` confirms the restore (restores are recognised from `check()` only, R1 rule 5);
  - a `DROP_DATABASE` of a declared database asks for an early `check()` (a request, not a stop and not a confirmation), so that the ambiguous interval lasts about one check instead of up to 5 minutes. Requests are merged: at most one such check per target every 30 s, and never while a check of the target runs; a request in that time is served by the next check (security review L9). A forger who writes `DROP_DATABASE` records therefore costs at most one extra check per 30 s.
- **8f confirmed**: line breaks are written verbatim in statement texts, process names, user and role names and user exception messages (escaped only inside the quoted value of a conversion error). The misattribution residual of R1 stands, as the maintainer accepted it (open question 6 of the refinement of 2026-10-25), and R1 rule 9 (remote 4-tuple corroboration) applies: the record was in the log about 40 ms after the statement, and a held TCP connection that never attaches writes nothing, which is the limit R1 already states. **Amending R1 rule 9's "read within 10 s of being written"** (security review L11): the time is the tailer's own observation, never the record's header timestamp, which a forged record sets freely. A record counts as read within 10 s when it lies past the end-of-file offset that the tailer recorded at a read cycle less than 10 s of agent time earlier. When the agent lags (the record lies before that offset), the socket condition of rule 9 is not evaluated for that binding: the binding is not made ambiguous for a missing socket, and rule 9's other condition (the same 4-tuple as another live binding) still applies.
- **12b, per-version section matching**: on 4.0.7, a section `database = <alias>` applies to attaches through that alias only; on 5.0.4, to attaches through the alias and through the resolved path. A section naming the path applies to path attaches only, on both, and attaches through an alias are then written nowhere. Amending R2 rule 4: the agent evaluates which section applies to each name of a declared database (its resolved path and every alias of the map that maps to it) with the matching rule of the server's version, from a table keyed by the **exact tested versions** (security review L10): 4.0.7 (alias sections match the alias only) and 5.0.4 (the alias and its resolved path), each checked by a matrix drift test. For any other version, 4.0.x and 5.0.x patch releases included, the fail-closed evaluation of R2 rule 4 (both readings, Limited when they differ) applies until the table gains it. A name whose effective settings miss proof 4, or that no section covers, caps the level at Limited (R2 rule 4, unchanged).
- **12c, alias case and live changes**:
  - Alias lookup is case-sensitive (a case variant is opened as a file name). R2 rule 1's "a case-only variant of a declared alias is ambiguous, pending 12c" becomes: a case variant is not the alias; as a non-absolute name not in the map, it is ambiguous under R2 rule 2 (the same effect, now measured).
  - A changed `databases.conf` takes effect at the next attach, without a restart. Amending R2 rule 5: the restart branch ("a file changed after the server process started is not proven until the next server restart") is withdrawn for `databases.conf`, because the file on disk is what the server applies. The agent `stat`s the file before and after each read cycle and records each sample with its log position (security review M1). When a sample shows a change, the **interval** runs from the end-of-file offset of the last unchanged sample to that of the detecting sample. Records before the interval are resolved with the old map, records inside it that use a non-absolute name are ambiguous, and records after it are resolved with the new map, which the agent re-reads and re-evaluates before the read position leaves the interval. At stream start, a map changed since the persisted state gives an interval from the persisted read position to the first sample. A new alias of a declared database that no section covers then caps the level at Limited from the re-evaluation on (R2 rule 4). `firebird.conf` and the trace configuration keep proof 2's restart rule (obligation 11).
  - No per-database key of `databases.conf` changes what the trace logs (`AuditTraceConfigFile` is ignored there); the closed key set of R2 rule 2 lists the keys measured per image, `SecurityDatabase` and `RemoteAccess` included (R9 uses the first).
- **13b confirmed**: effective settings are the default section's, overridden by the first matching named section's; a disabled matching section stops the search; a plain file name does not match; path matching is case-sensitive. R2 rule 4 stands.
- **True Classic mode**: one process per connection, a new `MON$SERVER_PID` for each, two addresses shared by every child. R1 rule 10 stands: Audit is Limited in Classic. The peer-uid rule of decision 3 holds under Classic (the connection's socket is owned by uid 84); Classic under socket activation by a service manager is still not measured.
- **Lot 1 residual A, `SEC$GLOBAL_AUTH_MAPPING`**: every account sees every global mapping (4.0.7 and 5.0.4). Amending decision 4 ("a readable credential relation"): `SEC$GLOBAL_AUTH_MAPPING` leaves the probe list of `credential_relation_readable`, whose readability it would make universal. Global mappings are then a fact visible to every account, not a credential; `RDB$AUTH_MAPPING`, readable by every account as well (first round), was never on the probe list. The lot 1 mapping refusal, which reads both tables, is unchanged, and both tables stay on decision 6's always-reported list, with the agent's own reads of them matched under R8 item 4.
