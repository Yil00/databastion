## Context

Phase 10 adds Firebird, the last engine of [ADR-0039](0039-engine-scope-expansion.md). ADR-0039 fixed the frame (ceiling Partial; a dedicated user with `SELECT` grants, never `SYSDBA` nor `RDB$ADMIN`; no embedded access and no direct reading of `.fdb` files; a pure-Rust wire client; the trace log follows the rule that a file the agent can write is refused; a capability token) and asked this ADR to decide the client, the transport and its trust model, the versions, the grants, the Discovery bounds, the Audit source and level, and the protocol additions.

Firebird differs from the engines already supported in ways that matter to the invariants:

- **No TLS.** The remote protocol (XDR-encoded operations over TCP, port 3050) has its own authentication plugins and its own **wire encryption** plugins (`WireCrypt = Disabled | Enabled | Required`, `WireCryptPlugin`), keyed by the session key the authentication plugin derives. The server is never authenticated by a certificate. On Linux there is no Unix-domain socket transport for the remote protocol (XNET is Windows only; to verify for 4.0 and 5.0); local access without the network goes through the embedded engine, which opens the database file directly and is excluded by ADR-0039 decision 5.
- **Authentication.** `Srp` / `Srp256` (SRP-6a with Firebird's own 1024-bit group, `g = 2`, SHA-1 for the internal hashes and the session key, SHA-256 for the client proof of `Srp256`) never sends the password. `Legacy_Auth` sends a DES `crypt(3)` hash of it, which is replayable and cheap to crack; protocol versions 10 to 12 send the password in clear (version 10) or that hash (11 and 12).
- **What the wire encryption gives**, read from the Firebird sources on 2026-10-24 (the `chacha` and `arc4` wire-crypt plugins, `src/remote/remote.cpp`, the SRP client; to confirm on the dev images, obligation 1):
  - `ChaCha` (Firebird 4.0+) is ChaCha20 with a 12-byte nonce and a 32-bit counter, `ChaCha64` (Firebird 4.0.1+, to verify) ChaCha20 with an 8-byte nonce and a 64-bit counter, both keyed from the SRP session key `K = SHA-1(S)`, with a nonce chosen by the server and sent in the clear key data; `Arc4` (every version since 3.0) is RC4 keyed with `K`, with RC4's known biases.
  - **No integrity**: neither cipher has a MAC, so an attacker on the path who knows plaintext at some offset can rewrite it (bit flipping), for example the agent's statement text or its transaction parameter buffer.
  - **No server authentication**: the server sends no proof of its own (there is no server proof `M2` in Firebird's SRP), and no certificate; the only server authentication is implicit: a server that does not know the verifier cannot derive `K`, so it cannot produce the first encrypted answer the client expects. Firebird's proof term differs from RFC 5054 (`H(N) ⊕ H(g)` is computed as a modular power in `srp.cpp`), so the client must be tested against real servers.
  - **Further keystream properties are under review** with the maintainer (security review N1); this ADR's decisions do not depend on them: the two properties above already rule out confidentiality and integrity on a network path an attacker can reach.
- **Statement timeout and read-only transactions.** Protocol 16 (Firebird 4.0) carries a per-statement timeout enforced by the server; transactions can be opened read-only (`isc_tpb_read`), and Firebird 4.0 adds `READ COMMITTED READ CONSISTENCY`. Readers never wait for writers' record versions (MVCC). There are no schemas before Firebird 6.0, no row-level security, no `SELECT` triggers; views, computed columns (`COMPUTED BY`), selectable procedures and database triggers (`ON CONNECT`, `ON TRANSACTION START`) run user code.
- **Audit.** Firebird has two trace mechanisms with one output format: the **system audit** (`AuditTraceConfigFile` in `firebird.conf`, a configuration in the `fbtrace.conf` syntax, written by the server to `log_filename`, rotated at `max_log_size`), and **user trace sessions** started through the services API (`isc_action_svc_trace_start`) whose output is read back over the services connection; a user session sees the attachments of other users only with the system privilege `TRACE_ANY_ATTACHMENT` (Firebird 4.0+) or as an administrator. The text format was read from `src/utilities/ntrace/TracePluginImpl.cpp` and `fbtrace.conf` (`v5.0-release`, 2026-10-24):
  - each record is written in one atomic append (the code says so), starting with a header line `YYYY-MM-DDTHH:MM:SS.ffff (<server pid>:<plugin instance address>) <EVENT>` in the server's local time, then an attachment line (`<database path> (ATT_<n>, <user>[:<role>], <charset>, <protocol>:<address>[/<port>])`), the client process line, a transaction line, then for statements `Statement <n>:`, a line of 79 `-`, **the statement text verbatim** (cut at `max_sql_length` with `...` appended), a line of 79 `^` and the plan **only when `print_plan` is on**, the parameters as `param<i> = <type>, "<value>"` (values verbatim, cut at `max_arg_length`), `<n> records fetched`, a performance line, and **with `print_perf` only**, a per-table block (a `Table … Natural Index Update Insert Delete Backout Purge Expunge` header, a line of `*`, one line per relation with its full name padded and eight right-aligned 10-character counters);
  - defaults that matter: `time_threshold = 100` (finish records of statements faster than 100 ms are **not written**), `max_sql_length = 300`, `max_arg_length = 80`, `max_arg_count = 30`, every `log_*` switch off, `print_perf = false`, `log_initfini = true`; `include_filter` / `exclude_filter` are `SIMILAR TO` expressions on the statement text; per-database sections match the database's file name or a `SIMILAR TO` pattern on its full path;
  - nothing in a record is escaped: statement texts, parameter values, error texts, the client process name (`isc_dpb_process_name`, set by any client) and quoted user and role names can hold newlines and any line of the format.
- **Statement text and parameters hold literal values** (I2), as on MySQL ([ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md)) and SQL Server ([ADR-0051](0051-sqlserver-connector.md) decision 6). Firebird has no server-side masking of passwords in `CREATE USER … PASSWORD` texts in the trace (to verify; the agent does not rely on it either way).

## Decision

### 1. Wire client: an own bounded client, no driver crate, no `fbclient`

The connector `connector-firebird` speaks a closed subset of the Firebird remote protocol itself, as `connector-mysql` ([ADR-0018](0018-mysql-mariadb-grants-and-connector.md) decision 3), `connector-mongodb`, `connector-openldap`, `connector-redis` ([ADR-0052](0052-redis-valkey-connector.md) decision 1) and `connector-sqlserver` ([ADR-0051](0051-sqlserver-connector.md) decision 1) do. No C client library is linked: the `fbclient` library, `rsfbclient-native` and any `*-sys` crate for Firebird are added to the `[bans]` of `agent/deny.toml` (reason: "no Firebird C client, ADR-0060 decision 1"), and `connector-firebird` joins the `CONNECTORS` list of the architecture test.

- **Protocol version 16 only.** `op_connect` (`CONNECT_VERSION3`, architecture generic, `ptype_batch_send`, no `pflag_compress`) offers exactly `PROTOCOL_VERSION16`. Version 16 is the floor that carries the statement timeout (decision 4); 17 to 19 add batches, scrollable cursors and inline blobs, which the connector does not use, so it does not offer them. An `op_accept*` naming another version ends the connection before anything derived from the password is computed. Whether every Firebird 4.0.x and 5.0.x server, and a future 6.0 server, accepts a client offering only 16 is verified on the matrix (obligation 2); if one does not, 17 or 18 is added to the offer, never anything below 16.
- **`op_connect` user identification** (sent in clear before encryption): `CNCT_login` (the account name), `CNCT_plugin_name` and `CNCT_plugin_list` both `Srp256`, `CNCT_specific_data` (the SRP public value `A`), `CNCT_client_crypt` = required. `CNCT_user` (the OS user) and `CNCT_host` (the host name) are **not sent**, as `HostName` is empty on SQL Server.
- **Operations sent**: `op_connect`, `op_cont_auth`, `op_crypt`, `op_attach`, `op_transaction`, `op_allocate_statement`, `op_prepare_statement`, `op_execute`, `op_fetch`, `op_free_statement`, `op_commit`, `op_rollback`, `op_cancel`, `op_info_sql` (describe and record counts), `op_detach`, `op_disconnect`. Never: `op_create`, `op_service_attach` and the services API (decision 6), `op_que_events` / `op_connect_request` (events need an **auxiliary connection to an address and port the server names**: I5), blob operations (`op_open_blob`, `op_get_segment`, `op_batch_*`; values are cut and converted on the server, decision 5), `op_transaction` with a write TPB, `op_ddl`, `op_execute_immediate`.
- **Operations parsed** from the server: `op_accept`, `op_accept_data`, `op_cond_accept`, `op_reject`, `op_response`, `op_fetch_response`, `op_sql_response`, `op_dummy` (skipped), `op_cont_auth` (only during authentication). Any other operation ends the connection: `op_crypt_key_callback` (a server asking the **client** for a database encryption key; the agent has none and sends none), `op_inline_blob`, `op_event`, `op_trusted_auth`, an unknown code. XDR has no framing beyond its own items, so an unknown operation cannot be skipped safely.
- **Closed type set.** The connector's statements are written so that every result column is `SQL_LONG`, `SQL_INT64`, `SQL_SHORT`, `SQL_BOOLEAN`, `SQL_VARYING` with character set `UTF8` (catalog names and converted values) or `OCTETS` (binary values, decision 5). The output message the client describes in BLR asks for exactly these; a describe answer (`isc_info_sql_describe_vars`) with another type, a blob, an array, a declared length above 32 765 bytes, or more columns than the statement selects makes the statement fail and the attachment be replaced (fail closed).
- **Bounds before allocation.** Every XDR length (opaque, string, status argument, info buffer, row value, null bitmap) is checked against the remaining budget of its item and against the declared maximum of its column before it is read; info buffers are requested with a client-chosen length (64 KiB at most) and an answer that claims more ends the connection; `op_fetch` asks for at most 64 rows per round, and a fetch answer with more rows, or a value longer than its column's declared length, ends the statement. Padding bytes are skipped by count, never trusted.
- **Server text is not data.** `op_response` status vectors are reduced while parsing to their GDS codes (`isc_arg_gds`, `isc_arg_number`) and SQLSTATE (`isc_arg_sql_state`, sent as `EngineCode`); `isc_arg_string`, `isc_arg_cstring` and `isc_arg_interpreted` arguments are skipped by length, never stored, logged or sent. Conversion errors quote values (`conversion error from string "…"`), so this is an I2 rule. The GDS codes map to the contract's `FailureCode` and check stage through **one closed table** (for example `isc_login` to `authentication_failed` at `stage_auth`, `isc_no_priv` to `permission_denied`, `isc_cancelled` to `cancelled`, `isc_cfg_stmt_timeout` / `isc_req_stmt_timeout` to `timeout`, `isc_io_error` and `isc_bad_db_format` on attach to `unknown_target`); a code outside the table is `internal`. After an authentication failure the connector stops retrying the target until the next heartbeat check, as on SQL Server; whether Firebird delays or locks an account after failed logins (`AuthServer` behaviour, the failed-login delay) is measured (obligation 9) and documented.
- **SRP-256**, implemented in the connector: the fixed Firebird group, `A = g^a mod N` with a fresh 128-byte random `a` from the operating system generator, checks on the server's answer before use (salt at most 32 bytes as hex, `B` at most 128 bytes, `B mod N ∉ {0, 1}`, the length checks of `SrpClient.cpp`), the scrambler `u = SHA-1(PAD(A) | PAD(B))` with the exchange **aborted when `u = 0`**, `x` from the salt, the upper-cased account and the password, then `S`, `K = SHA-1(S)` and the `Srp256` proof `M`. An answer that reports the client as authenticated **before `M` has been sent** ends the connection (`authentication_failed`): SRP must complete. The modular exponentiations over `a` and `x` use a **constant-time** big-integer implementation (`crypto-bigint`, Apache-2.0 OR MIT, MSRV 1.87, a new dependency checked by `cargo deny`), so the password-derived exponent does not leak through timing; `num-bigint` (variable time) is not used. The password, `x`, `a`, `S`, `K` and `M` live in zeroized buffers and are never written anywhere else (property test).
- **Wire encryption**: after `op_cont_auth` succeeds, `op_crypt` names `ChaCha64` when the server's key list offers it, else `ChaCha`, with the `Symmetric` key. `Arc4` is never chosen; a server that offers neither ChaCha plugin fails the connection with `target_unreachable` and a local detail; the wire-encryption negotiation is reported as the TLS stage of the contract (`check.stage_failed`, label `stage_tls`), as the `FailureCode` description asks for every engine. The ciphers come from the `chacha20` crate (`ChaCha20Legacy` for `ChaCha64`, `ChaCha20` for `ChaCha`), already in the agent's lock, always through `try_apply_keystream`: the `ChaCha` keystream ends at 256 GiB (32-bit counter), and its end closes the connection instead of panicking or wrapping. **Key confirmation**: the client sends no encrypted byte before it has decrypted the server's answer to `op_crypt` and found exactly the expected `op_response` structure (operation code, zero handles, an empty success status vector); anything else ends the connection with `target_unreachable` (label `stage_tls`, as a failed certificate check elsewhere; a wrong password is refused by the server before this point and reported `authentication_failed`). A server that does not know the verifier cannot pass this check, because it cannot derive the key.
- **Robustness duties** (ADR-0039 decision 4, the [connector obligations](../05-security.md#connector-obligations)): unit tests against a scripted fake server (as `connector-mysql/src/fake.rs`); property tests on every parser (no panic, bounded reads, the password and SRP secrets never outside their buffers); fuzz targets in `agent/fuzz/fuzz_targets/` for the XDR reader and the `op_accept*` / `op_response` / `op_fetch_response` parsers, the info-buffer (clumplet) parser, the SRP server data, the wire-crypt key list, the trace log record splitter and record parser, the trace configuration parser and the Firebird mode of the statement normalizer (decision 6); the nightly fuzz workflow runs them.

**Rationale.** Both crates pass the license criterion, and `firebirust` is maintained. Each is rejected for measured reasons that are project rules, not preferences:

1. `rsfbclient-rust` offers protocol versions 10 to 12, so a server or an attacker on the path that answers one of them receives the password in clear or as a DES hash; it offers no version with the statement timeout; it has Arc4 only; and it is blocking, so cancellation and the scan's deadlines would sit outside the tokio runtime the core relies on.
2. `firebirust` depends on `rust-crypto` 0.2.36, unmaintained since 2016, for its SHA and RC4 code; it panics on unexpected answers; it accepts Arc4 and an unencrypted connection; and it brings a second async runtime.
3. Neither bounds what a hostile server sends before allocating, as the project's own clients do, and both turn server status strings into error text, which can quote values.

The own client costs an estimated 2 500 to 3 500 lines plus tests and fuzz targets, and owns the robustness of its parsers, the residual every own client already carries. The decision is reviewed if a maintained pure-Rust crate offers only protocol 16+, `Srp256` only, ChaCha only, bounded parsing and no server text in errors; the table above is the checklist.

### 2. Supported versions

- **Firebird 4.0 and 5.0** (newest releases on 2026-10-24: 4.0.7 and 5.0.4), following [ADR-0039](0039-engine-scope-expansion.md) decision 1; lifecycle dates are to verify on firebirdsql.org before release (P10-G).
- **Firebird 3.0 is refused**, whatever its maintenance status (open question 1). It cannot meet this ADR's transport and bounds: it has only Arc4 (no ChaCha), protocol 15 at most (no server-side statement timeout), no `READ CONSISTENCY`, and none of the Firebird 4.0 system privileges and catalogs the refusal list reads (`RDB$SYSTEM_PRIVILEGE`, `RDB$ROLES.RDB$SYSTEM_PRIVILEGES`). Its server refuses the client's protocol offer (version 16 only), so it ends at connection with `unsupported`, before `op_cont_auth`, and nothing derived from the password reaches it.
- **Firebird 6.0 is refused until a refinement of this ADR** (open question 8): it adds SQL schemas (the `Location` mapping changes: decision 5), a new protocol version and catalog changes. Not released on 2026-10-24.
- **How the version is checked**: protocol 16 at `op_accept*`, then, on the attached session, `SELECT RDB$GET_CONTEXT('SYSTEM', 'ENGINE_VERSION') FROM RDB$DATABASE` (a constant text). A major version other than 4 or 5, or a value that does not parse, is refused as `unsupported` before any other read. The value is sent as `TargetStatus.server_version` (for example `5.0.4`).
- **Server modes**: `SuperServer` and `SuperClassic` are supported for Discovery and Audit; `Classic` (one process per attachment) is supported for Discovery, and for Audit only if the header-token rule of decision 6 holds there (to measure; Limited otherwise, open question 9).

### 3. Transport and authentication: loopback only, SRP-256, ChaCha required

- **Loopback only** (open question 2). The declared `host` must be an IP literal `127.0.0.1` or `::1` (no name: `localhost` resolution is not trusted, as an IP literal only counts in ADR-0023 decision 6). A target with another host is refused at configuration load, except in the tunnel mode below. Rationale: Firebird gives no server authentication and no integrity (Context), so on a network an active attacker can rewrite the agent's statements and transaction parameters, and the confidentiality of what crosses the path cannot be relied on. The Audit source is a local file on the server host (decision 6), so the agent runs there in any case.
- **The loopback threat model** (security review M1). Loopback is not a private channel for every process on the host: whoever holds `CAP_NET_RAW` or `CAP_NET_ADMIN` **in the network namespace** of the connection can capture or alter it. That includes root on the host, and also processes in containers that share the namespace (the other containers of a pod or of a Compose `network_mode: service:` group), which hold `NET_RAW` among Docker's default capabilities. From a passive capture such a process gets the SRP transcript, which allows offline guessing of the password, and must be assumed to get the sampled values; actively, it can flip bits in the agent's requests, the TPB included (a read-only transaction turned into a read-write one: the grants still refuse writes, decision 4). So the deployment rule is: **no other container shares the agent's and the server's network namespace, or every container in it drops `NET_RAW` and `NET_ADMIN`** (`cap_drop`); on a plain host, only root holds them. The user guide states it; the dev and E2E Compose files apply `cap_drop: [NET_RAW, NET_ADMIN]` to every container of the shared namespace (decision 9). The user guide also recommends `RemoteBindAddress = 127.0.0.1` in `firebird.conf` when no other client needs the network (security review N2).
- **Remote servers through an operator-run tunnel, an explicit opt-in** (security review M2, open question 2). An operator who needs Discovery of a Firebird server on another host runs a TLS or WireGuard tunnel (stunnel, `ssh -L`, WireGuard) that terminates on the agent host's loopback, declares the loopback end and sets the local option **`firebird.tunnel: true`**. That mode has its own `peer_uid` (the tunnel process's account, required), reports the permanent new note `security.firebird_tunnel` ("the target is reached through a tunnel the operator runs; its security is the operator's") at every check, and has no Audit (no local log): `audit.source_not_configured`. There is no `disable_insecure`-like remote mode.
- **Forwarders are detected** (M2). Without `tunnel: true`, a loopback endpoint must be the Firebird server itself, not a forwarder (a tunnel, `socat`, a userland port proxy): after attach, `check()` and every scan attachment read `MON$REMOTE_PROTOCOL`, `MON$REMOTE_ADDRESS` (and the remote port where the server reports it; to verify) of `MON$ATTACHMENTS` for `CURRENT_CONNECTION`, and compare them with the socket's local address and port. A mismatch (the server saw the connection come from somewhere else) ends the session with `target_unreachable` and a local detail.
- **The listening peer is checked** (security review L1). On loopback, an unprivileged local user can bind port 3050 while Firebird is down, then receive the agent's SRP exchange (an offline dictionary attack on the password from `M`) and feed it hostile data. Right after `connect()` returns and **before `op_connect` is sent**, the connector reads `/proc/net/tcp` **and** `/proc/net/tcp6` (world-readable, no privilege, no network traffic; IPv4-mapped IPv6 addresses handled), line by line with a bound on lines and time, and finds the server-side socket of **this connection** by its full 4-tuple (local = the declared address and port, remote = the agent's address and local port) in the `ESTABLISHED` or `SYN_RECV` state; its owner uid must be the declared `firebird.peer_uid`. Other rows are never logged or kept. A missing entry, two matching entries, another uid, uid 65534 (`nobody`, what a uid outside the reader's user namespace shows as), or a platform other than Linux ends the connection with `target_unreachable` and a local detail; there is no switch to turn the check off (open question 10).
  - `peer_uid` is a user name resolved at load (default `firebird`) or a number; **`peer_uid: 0` is refused** unless the local opt-in `firebird.peer_uid_root: true` is set (a root-owned socket is usually a proxy, and every root process matches it), reported in the local detail; **in a container** (the agent detects it from `/proc/1/cgroup` or `/.dockerenv`, to settle at implementation) the uid must be numeric, because names resolve against the agent image's own `/etc/passwd`.
  - In containers, the agent shares the server's network namespace (`network_mode: service:<firebird>`), as the dev and E2E environments do (decision 9), under the M1 deployment rule above.
  - The lookup has a property test (any 4-tuple and table content: the right row or none, never a panic) and a fuzz target over `/proc/net/tcp*` contents.
- **`Srp256` only.** `Srp` (SHA-1 proof), `Legacy_Auth`, `Win_Sspi` and any other plugin are never offered; a server that asks for another plugin (`op_cond_accept` naming it, or `op_cont_auth` switching to it) ends the connection before the password is used. The account is a user of the server's security database created with the `Srp` user manager (one verifier serves `Srp` and `Srp256`).
- **Wire encryption required**, `ChaCha64` or `ChaCha` (decision 1), checked once attached through `RDB$GET_CONTEXT('SYSTEM', 'WIRE_ENCRYPTED')` = `TRUE` and `'WIRE_CRYPT_PLUGIN'` naming the chosen plugin (context names to verify); a mismatch ends the session. `Arc4` is refused on loopback too: it costs nothing to require ChaCha on Firebird 4.0+, whose default `WireCryptPlugin` lists ChaCha first (to verify per version), and a server reconfigured to Arc4 only is a configuration change worth seeing. A server with `WireCrypt = Disabled` cannot be monitored (`target_unreachable`, local detail).
- **Compared with SQL Server** ([ADR-0051](0051-sqlserver-connector.md) decision 2): there, TLS with a verified certificate is mandatory everywhere because `LOGIN7` carries the password in a reversible form. Here SRP keeps the password off the wire on any transport, but integrity and server authentication cannot be had on a network, so the rule is about the path instead of the cipher: loopback, a checked peer, no forwarder unless declared, and the strongest cipher the server has.
- **Password.** The password is read from its `agent.yaml` secret reference (`secret: {env: …}` or a file, as for the other engines) into zeroized memory and used only to derive `x`; it never leaves the agent host (I3). The user guide asks for a random password of at least 32 characters: the SRP exchange given to an impersonating listener allows an offline guess per candidate, which a random password defeats.
- **Connection model**: one declared `host` / `port`, one attachment per declared database per scan and one per `check()`, replaced after an error that leaves it unusable or when idle for 60 s. Cancellation uses `op_cancel` (`fb_cancel_raise`) on the same connection (protocol 12+; to verify that it is handled while a fetch is pending in `ptype_batch_send`). The attachment sets `SET SESSION IDLE TIMEOUT 2 MINUTE` (Firebird 4.0+, a session-management statement, not a write) as the server-side safety net of the connector obligations. The DPB sends the account name, `isc_dpb_lc_ctype = UTF8`, SQL dialect 3, `isc_dpb_process_name = databastion-agent`, `isc_dpb_session_time_zone = UTC`; never a role (`isc_dpb_sql_role_name`), never `isc_dpb_no_db_triggers` or `isc_dpb_no_garbage_collect` (they need administrator rights the agent must not hold), never a password item. The lifetime of each attachment is recorded for the own-statement rule (decision 6): from `CURRENT_CONNECTION`'s read to a clean detach, or, for a **lost connection**, to the moment it was lost plus the statement timeout plus 5 s (security review L7).

### 4. Least-privilege account (I4), to be measured as in ADR-0012

**Proposed minimal variant** (default):

```sql
-- In the security database (isql connected as an administrator). The password
-- is typed from a prompt; the statement text holds it (decision 6 drops it).
CREATE USER DATABASTION_AGENT PASSWORD '<random, 32+ characters>' USING PLUGIN Srp;
-- In each monitored database: a role holding the table grants, granted as a
-- default role so it is active at every attachment without SET ROLE.
CREATE ROLE DATABASTION_READER;
GRANT SELECT ON TABLE CUSTOMERS TO ROLE DATABASTION_READER;   -- one per table
GRANT DATABASTION_READER TO USER DATABASTION_AGENT DEFAULT;
```

- **Per-table grants**: Firebird before 6.0 has no schema and no "all tables" grant short of a system privilege, so a new table needs a new grant (the PostgreSQL maintenance cost of ADR-0012). `check()` lists user tables without `SELECT` as not covered (`coverage.relations_without_select`, gaining `firebird`).
- **Extended variant (opt-in, `extended_grants: true`, open question 5)**: a role created `SET SYSTEM PRIVILEGES TO SELECT_ANY_OBJECT_IN_DATABASE`, granted `DEFAULT`; it reads every table, present and future, and is reported by `check()` as `privilege.extended_variant`. It is offered only together with the credential-relation rule of decision 5 (never sampled, and `check()` refusing an account that can read them), and only once obligation 3 shows what it widens (`MON$` visibility, security tables). Without the flag, the same privilege is over-privilege.
- **How `check()` reads privileges** (fail closed: a read that fails or is cut gives `privilege.not_evaluated`, and the refusal rule then applies to what was read):
  - **effective identity** on the attached session: `CURRENT_USER`, `CURRENT_ROLE`, `RDB$ROLE_IN_USE('RDB$ADMIN')`, and `RDB$SYSTEM_PRIVILEGE('<name>')` for every name of the lists below (it reflects mappings, default roles and the roles in use);
  - **every role the account could use**, not only the active ones (as [ADR-0025](0025-mysql-mariadb-role-privileges-and-heartbeat-checks.md) evaluates MySQL roles): rows of `RDB$USER_PRIVILEGES` with `RDB$PRIVILEGE = 'M'` whose grantee is the account or `PUBLIC`, followed through role-to-role grants (bounded at 64 roles); each role's `RDB$ROLES.RDB$SYSTEM_PRIVILEGES` bit mask decoded with a per-version closed table of bit positions checked by a drift test on each matrix image (an unknown bit set is treated as a refused privilege: fail closed). When this graph cannot be evaluated (catalog not visible, the bound reached, a read cut), `check()` reports `privilege.not_evaluated` with the new label `role_graph` (security review M6), and the residual "roles not active in the session not evaluated" applies to that target;
  - **object grants**: `RDB$USER_PRIVILEGES` rows whose grantee is the account, `PUBLIC` or one of those roles: privilege letter, object type and name, column (`RDB$FIELD_NAME`), `RDB$GRANT_OPTION`;
  - **ownership**: `MON$DATABASE.MON$OWNER` against `CURRENT_USER`, and `RDB$OWNER_NAME` of relations, procedures, functions and packages;
  - **the security database flag** `SEC$USERS.SEC$ADMIN` of the account's own row (a non-administrator sees its own row only; to verify);
  - visibility of these catalogs to the minimal account is measured on 4.0 and 5.0 (obligation 3).
- **What must be measured** (security review M6; P10-B, on 4.0 and 5.0, throwaway containers with fake markers, the table of results added to this ADR as ADR-0012's "Verification" section before it is accepted, as [ADR-0051](0051-sqlserver-connector.md) decision 4). Accounts: `min` (the minimal variant), `ext` (the extended variant), `none` (no grant at all), `sysdba_mapped` (a user mapped to `SYSDBA` or `RDB$ADMIN` through `RDB$AUTH_MAPPING`). Probes, each expected denied or empty for `min` unless stated:
  - **default DDL rights of a plain user**: `CREATE TABLE` (and `CREATE TABLE … EXTERNAL FILE`, a server-side file write and read primitive under `ExternalFileAccess`), `CREATE PROCEDURE` / `FUNCTION` / `PACKAGE`, `CREATE GLOBAL TEMPORARY TABLE`, `CREATE GENERATOR`; whichever a plain user holds by default is a residual of the account (as MySQL temporary tables) and is reported by `check()` as `privilege.beyond_select` when held through a grant;
  - **outbound primitives**: `EXECUTE STATEMENT … ON EXTERNAL DATA SOURCE` from `EXECUTE BLOCK` (an outbound connection from the server; not something the agent sends, but something a stolen agent credential can);
  - **server settings**, read through `RDB$CONFIG` where visible and reported in the local detail: `ExternalFileAccess`, `UdfAccess`, the UDR plugin settings, `WireCrypt`, `AuthServer`, `RemoteBindAddress`, `ServerMode`;
  - **system packages granted to `PUBLIC`** (`RDB$PROFILER`, `RDB$BLOB_UTIL`, `RDB$TIME_ZONE_UTIL`, and any other found) and what they expose;
  - **visibility** of `RDB$AUTH_MAPPING`, `SEC$GLOBAL_AUTH_MAPPING`, `SEC$USERS`, `RDB$USER_PRIVILEGES`, `RDB$ROLES`, and the `MON$` tables of **other attachments** (`MON$ATTACHMENTS`, `MON$STATEMENTS`, `MON$CONTEXT_VARIABLES`) for each account;
  - **the credential relations of decision 5** (`PLG$*`, `SEC$*`): readable by which account, in a database that is its own security database too.
- **Refusal list** ([ADR-0039](0039-engine-scope-expansion.md) decision 5, extended; reported as `privilege.refused` with the right's label). **Discovery and Audit both refuse to run** with such an account (open question 4, the [ADR-0051](0051-sqlserver-connector.md) open question 4 answer):
  - the user `SYSDBA` (by name and by effective `CURRENT_USER`, a mapping included), the database owner, the `RDB$ADMIN` role (granted in the database, held through `PUBLIC`, mapped by `RDB$AUTH_MAPPING` or a global mapping, or in use), the security-database administrator flag;
  - the system privileges (names from the Firebird 4.0 and 5.0 lists, to verify per version): `USER_MANAGEMENT`, `READ_RAW_PAGES`, `TRACE_ANY_ATTACHMENT` (decision 6: it reads every attachment's statements and parameter values over the network), `MONITOR_ANY_ATTACHMENT` (every attachment's statement texts in `MON$STATEMENTS`, context variables, and the cancellation of other attachments through `DELETE FROM MON$…`), `PROFILE_ANY_ATTACHMENT` (5.0), `ACCESS_SHUTDOWN_DATABASE`, `CHANGE_SHUTDOWN_MODE`, `IGNORE_DB_TRIGGERS`, `CHANGE_HEADER_SETTINGS`, `USE_GBAK_UTILITY`, `USE_NBACKUP_UTILITY`, `USE_GFIX_UTILITY`, `ACCESS_ANY_OBJECT_IN_DATABASE`, `MODIFY_ANY_OBJECT_IN_DATABASE`, `CHANGE_MAPPING_RULES`, `USE_GRANTED_BY_CLAUSE`, `GRANT_REVOKE_ON_ANY_OBJECT`, `GRANT_REVOKE_ANY_DDL_RIGHT`, `CREATE_PRIVILEGED_ROLES`, `CREATE_DATABASE`, `DROP_DATABASE`, `REPLICATE_INTO_DATABASE`, `MODIFY_EXT_CONN_POOL`, and any bit the per-version table does not know;
  - **a readable credential relation** (security review M5): `check()` probes, with a constant one-bit text (`SELECT CASE WHEN EXISTS (SELECT 1 FROM <relation>) THEN 1 ELSE 0 END FROM RDB$DATABASE`, no row content returned), whether each relation of decision 5's credential list that exists in the database is readable; a readable verifier or hash relation (`PLG$SRP`, `PLG$USERS`, their views) is a refusal, the others (`SEC$*` beyond the account's own row) the new label `credential_relation_readable` of `privilege.global_privileges`.
- **Over-privilege, warned** (existing notes gaining `firebird`: `privilege.beyond_select` for object rights, `privilege.grant_option`, `privilege.owner_of_objects`, and `privilege.global_privileges` with Firebird labels for the system privileges below, instead of a new code: security review L4): `INSERT`, `UPDATE`, `DELETE`, `REFERENCES` on any relation, `EXECUTE` on procedures, functions or packages, `USAGE` on generators, exceptions or domains, DDL privileges (`CREATE`, `ALTER ANY`, `DROP ANY`), `WITH GRANT OPTION`, ownership of any object, roles other than the reader role, and the system privileges `SELECT_ANY_OBJECT_IN_DATABASE` (without the flag), `USE_GSTAT_UTILITY`, `GET_DBCRYPT_INFO`, `CREATE_USER_TYPES`. Grants held through `PUBLIC` count as the account's (a write granted to `PUBLIC` is the account's write).
- **Transactions**: every unit of work runs in its own transaction with the TPB `isc_tpb_version3, isc_tpb_read, isc_tpb_read_committed, isc_tpb_read_consistency, isc_tpb_nowait`, committed before the unit's findings are submitted and before any pacing pause, so no transaction spans `FindingSink::submit().await` or a pause. Read-only read committed transactions do not hold back garbage collection (to verify in read consistency mode, obligation 4); the agent never waits for a lock (`nowait`: a conflict skips the table, `skipped_error`). After `op_transaction` the connector checks `RDB$GET_CONTEXT('SYSTEM', 'READ_ONLY')` = `TRUE` and `'ISOLATION_LEVEL'` = `READ COMMITTED` once per attachment (context names to verify); a mismatch ends the session.
- **Statement timeout**: every `op_execute` carries the job's clamped statement timeout (never 0; at most 30 s for a sampling statement, 3 s per `check()` statement and 9 s per `check()` in total), enforced by the server; the client keeps its own deadline as a backstop and sends `op_cancel`, then closes the connection if the cancelled statement's answer does not come within 5 s.
- **I4 summary**: read-only rests on (1) no write grant (checked, decision 4), (2) read-only transactions refused writes by the server, (3) a closed statement set built in code with quoted identifiers, (4) never reading what runs user code implicitly (decision 5), (5) server-side statement timeouts and client-side bounds. Database triggers are the exception: `ON CONNECT` and `ON TRANSACTION START` triggers run at every attachment and transaction of the agent; the read-only transaction blocks their writes except those in `IN AUTONOMOUS TRANSACTION` blocks (residual). `check()` reports them as `security.login_event_trigger` (gaining `firebird`; transaction-start triggers counted in the local detail).

### 5. Discovery

- **Databases**: the declared list only, `firebird.databases: [{name, attach}]`. `attach` is an alias of the server's `databases.conf` (recommended) or an absolute path; it is sent to the server inside the encrypted session and **never** leaves the agent otherwise: not in `Location`, not in `last_error`, not in logs (failures map to closed codes). `name` is the operator's label, normalized under ADR-0009 and sent as `Location.database`. Firebird has no server-wide catalog of databases a normal user can list, and the agent never asks for one (I5). The job's `databases` filter applies to the declared names; rotation per scan as ADR-0035.
- **Catalog per database**, with constant texts:
  - relations: `RDB$RELATIONS` with `COALESCE(RDB$SYSTEM_FLAG, 0) = 0`, reading `TRIM(TRAILING FROM RDB$RELATION_NAME)` (trailing padding only: a leading space is part of a quoted name; the client also trims trailing spaces, so a server-side mistake cannot merge names; security review L3), `RDB$RELATION_TYPE`, `RDB$VIEW_BLR IS NOT NULL` and `RDB$EXTERNAL_FILE IS NOT NULL` (booleans only: the external file path is never read); at most 16 384 relations per database;
  - **credential and system relations, never sampled** (security review M5): a closed list, checked by a drift test on each matrix image, of the relation names Discovery never samples **whatever their system flag** (a user can create a relation with any name, and a security database's `PLG$` tables are not system relations): every name starting `PLG$`, `SEC$`, `RDB$` or `MON$` in the tested images, plus `PLG$SRP`, `PLG$SRP_VIEW`, `PLG$USERS`, `PLG$PROF_*`. Such a relation found with system flag 0 is counted as `skipped_unsupported` and named in the local detail; the list, not the prefix, decides (a user table `RDB$X` absent from the list is sampled as any table, with the prefix noted in the local detail);
  - columns: `RDB$RELATION_FIELDS` joined to `RDB$FIELDS` on `RDB$FIELD_SOURCE`, reading the column name, position, `RDB$FIELD_TYPE`, `RDB$FIELD_SUB_TYPE`, `RDB$FIELD_SCALE`, `RDB$FIELD_LENGTH`, `RDB$CHARACTER_SET_ID`, `RDB$DIMENSIONS IS NOT NULL` and `RDB$COMPUTED_BLR IS NOT NULL`. Types are decided on `RDB$FIELD_TYPE` and `RDB$FIELD_SUB_TYPE` of the base field, never on a domain's name. The `*_SOURCE` columns (defaults, computed expressions, checks: source texts with literals) are never read;
  - the account's `SELECT` grants (decision 4) decide which relations and columns are readable; denied columns are left out of the select list;
  - **wide tables** (security review N3): the output message is bounded (64 KiB of described row, at most 255 sampled columns per statement); a table beyond it is sampled in column batches, one statement per batch with the same `FIRST n`, each batch a unit of work under pacing (rows of different batches are not joined: each column is classified on its own, as on every engine).
- **Sampled**: persistent tables only (`RDB$RELATION_TYPE = 0`, no view BLR, no external file). **Never sampled**: views (`coverage.views_not_sampled`), external-file tables (reading them makes the server read a file outside the database; new note `coverage.external_file_tables`), global temporary tables (types 4 and 5: their rows belong to other attachments and are invisible to the agent's; counted in the local detail), virtual tables (`MON$`, `RDB$` virtual), selectable procedures, computed columns (`COMPUTED BY` can call PSQL functions or UDRs: user code; `coverage.computed_columns_not_sampled`, gaining `firebird`), arrays, blobs of sub-types other than 0 and 1, and any type outside the conversion list below.
- **Sampling statement** (one per table):

  ```sql
  SELECT FIRST <n> CAST(SUBSTRING("C1" FROM 1 FOR 4000) AS VARCHAR(4000) CHARACTER SET UTF8), …
    FROM "TABLE"
  ```

  - `<n>` is the job's `sample_rows` (at most `limits.max_sample_rows`), an integer literal; `FIRST n` rather than `FETCH FIRST n ROWS ONLY` because it is accepted in every dialect and version supported (both are equivalent on 4.0 and 5.0). Identifiers come from the catalog and are quoted by one audited function (`"`, with `"` doubled), never from job parameters; there is no string literal in any sampling statement.
  - **Values are converted on the server with syntax-level built-ins only** (`CAST`, `SUBSTRING`, which no user function can shadow): `CHAR` / `VARCHAR` and `BLOB SUB_TYPE TEXT` of a declared character set to `VARCHAR(4000) CHARACTER SET UTF8` (the server transliterates; with `lc_ctype = UTF8` this is also what it would send); columns of character set `NONE` or `OCTETS` and `BLOB SUB_TYPE BINARY` to `VARCHAR(4000) CHARACTER SET OCTETS`, read as text only when valid UTF-8 without control characters (as [ADR-0026](0026-mongodb-connector.md) decision 9); integers, `INT128`, `NUMERIC` / `DECIMAL`, `DECFLOAT` as digits; `DATE` and `TIMESTAMP [WITH TIME ZONE]` as `YYYY-MM-DD`; `BOOLEAN` skipped; `FLOAT` / `DOUBLE PRECISION` integral values only, as on MongoDB and SQL Server. The exact forms (whether `CAST` of a blob substring to `VARCHAR` holds on 4.0 and 5.0, transliteration failures) are verified on the matrix (obligation 5). A statement that fails on a conversion (`isc_transliteration_failed`, `isc_malformed_string`, string truncation) skips the table with `skipped_error` and a local detail naming the column's type, never its values. The blob reads stay on the server: no blob id reaches the client.
  - **Order and bias**: `FIRST n` without `ORDER BY` reads the first records in storage order and stops (to verify that the natural scan stops early). Firebird has no `TABLESAMPLE` and no cheap row estimate; `SKIP m` would read and discard `m` rows. The sample is therefore biased to storage order (often the oldest rows), recorded as a residual (open question 14).
- **Byte budget**: at most 32 MiB of sampled values per table, checked per value as bytes arrive (XDR lengths precede the bytes; at most 16 000 bytes per converted value); reaching it sends `op_cancel` (decision 3).
- **Pacing**: every unit of work (a database's catalog, a table's sample) goes through `ScanJob::paced` ([ADR-0035](0035-discovery-pacing.md)); the attachment is detached before a pause that reaches 45 s, as MySQL.
- **Locations and names**: `Location` is `engine: firebird`, `database` (the declared name), `object` (the relation), `field` (the column), with no `schema`, as MySQL. Every name goes through [ADR-0009](0009-name-normalization-and-item-sanitization.md) normalization (quoted names can hold any character, including `.`, spaces and values) and the [ADR-0057](0057-identifier-hardening-agent-first.md) rules, with the [ADR-0056](0056-names-altered-by-normalization-marker.md) marker when normalization alters them.
  - **Case**: Firebird stores unquoted identifiers upper-cased (ASCII letters) and quoted ones as written, and compares stored names exactly: `CUSTOMERS`, `customers` written unquoted, and `"CUSTOMERS"` are one table; `"Customers"` is another. That is fixed by the engine, not by a setting, so no [ADR-0055](0055-agent-reported-name-case-semantics.md) `name_case` value is needed: Discovery sends catalog names as stored, and statement-text names are resolved as the server does (unquoted names upper-cased in ASCII, quoted names kept, `""` unescaped). The console must treat `firebird` as a **case-sensitive** engine for location exceptions ([ADR-0054](0054-case-sensitive-location-exceptions.md) decision 1, the PostgreSQL rule; open question 11).
  - **Trailing spaces**: catalog names are `CHAR(63)` padded with spaces (`CHAR(31)` before 4.0), so trailing spaces are never significant in a Firebird name (`"A "` and `"A"` are one table). The agent drops them from catalog and statement-text names; this is the engine's own rule, not an alteration, so no ADR-0056 marker is set for it. The console should add `firebird` to `TRAILING_SPACE_BLIND_ENGINES` (open question 11).
  - Own-account budget keys are the Unicode-lowercased names, as on every engine (merging budgets only reports sooner).
- **CAS store guard** ([ADR-0041](0041-cas-connector.md) decisions 5 and 6): applied as on the other SQL engines (ticket-registry names and column shapes counted, never sampled; the ticket-id tripwire before classification), although CAS is not known to ship a Firebird JPA configuration (to verify); it is cheap and fails closed.
- **Coverage**: `objects_sampled`, `skipped_not_readable` (no `SELECT`), `skipped_unsupported` (tables with no sampleable column, CAS ticket registries), `skipped_remote` (external-file tables), `skipped_limit`, `skipped_error`.

### 6. Audit

#### Source: the system audit trace log, read locally

| Source | `audit_source` | Read through | Permission | Best level |
|---|---|---|---|---|
| System audit trace (`AuditTraceConfigFile`), text log file on the server host | `firebird_audit_trace` | the core tailer, local file | file read by the agent's Unix account; no database grant | **Partial**, Limited until the proofs below hold |

- **User trace sessions through the services API are rejected** (open question 6). They need `TRACE_ANY_ATTACHMENT` or an administrator to see other users' attachments, a system privilege that lets the agent's credential (usable remotely if stolen) read every attachment's statement texts and **parameter values** in clear; the agent would create the trace it is supposed to prove (rejected for SQL Server in [ADR-0051](0051-sqlserver-connector.md)); the services connection is a second protocol surface; and a session's output is lost at a server restart and when the reader falls behind `MaxUserTraceLogSize` (to verify). `TRACE_ANY_ATTACHMENT` is on the refusal list (decision 4).
- **Configuration**: the operator sets `AuditTraceConfigFile` in `firebird.conf` and writes the trace configuration; the agent never writes either. `agent.yaml` names the log and the configuration: `firebird.audit {log, trace_config}`, both absolute paths on the agent host.
- **File rules** ([ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md) decision 8, [ADR-0043](0043-audit-logs-opened-without-following-a-final-symlink.md)): the log is opened by the core tailer with `O_NOFOLLOW`, one hard link, rotation detected with `lstat`, and refused when the agent's account could write it. The connector adds the CAS-style open check of ADR-0043 decision 5 (`Tailer::with_open_check`): the declared path still resolves where it did at load, the file has one link and no ancestor directory the agent can write, and the path names the handle before and after the checks. The trace configuration file is read with the same open rules (it decides the level, so a writable configuration is refused as a proof: Limited). Firebird rotates by renaming the full log with a date and time suffix and creating a new file (`max_log_size`); the tailer finishes the renamed file before switching (as for the other log sources). Whether the server creates the log group-writable (so an agent in the `firebird` group would be refused) is measured on the dev images and documented (obligation 6).
- **The configuration the server uses** (security review M3). The level depends on the configuration the server actually runs with, not on a file that merely exists:
  - `agent.yaml` also names `firebird.audit.firebird_conf` (absolute path), read under the same file rules with a closed key set; its `AuditTraceConfigFile` must resolve (relative names against the Firebird root directory, also declared) to the declared `trace_config`, and `ServerMode` is read from it (cross-checked with `RDB$CONFIG` where visible). A mismatch or an unreadable `firebird.conf`: not proven (Limited, `audit.trace_config_not_evaluated` with a label).
  - When the server reads the audit configuration (at process start only, or also when a database is first opened) is measured (obligation 11). If only at start: the agent finds the server process (the local `firebird` process of the declared `peer_uid`, through `/proc`) and its start time (`/proc/<pid>/stat`), and a `firebird.conf` or trace configuration whose `mtime` or `ctime` is later than that start time is **not proven** (the running server may use the earlier content). If the server runs in another pid namespace than the agent (its process is not visible), the binding is not proven either (Limited).
- **Database paths** (security review M4). The agent learns each declared database's file path from `MON$DATABASE.MON$DATABASE_NAME` on its own attachment and from its own read-back probe's attachment line (below), and keeps it on the agent host only. How the trace prints paths for aliases, `..`, `//`, symlinked directories, hard links and bind mounts is measured (obligation 12). Matching is exact on the printed path; fail closed: a record whose path differs from a declared database's path but has the same file name, or names a file whose `(st_dev, st_ino)` (from a `stat` without opening the file) equals a declared database's, is **ambiguous** (below), reported, and caps that database's level at Limited until the operator's configuration is fixed.
- **Records of undeclared databases** are dropped at parse and counted (I5: undeclared databases are not monitored), **only when they are well formed** (not ambiguous, rules below).

#### Parsing a hostile text log

Every client that can send SQL writes into this file: statement texts and parameter values are verbatim, unescaped, and can contain any line of the format, including a header line that starts a forged record. The **injection points** (security review H1) are the statement text (comments included), parameter values, error and warning texts (they quote values and names), the client process name (`isc_dpb_process_name`, any string a client sets), quoted user and role names, and quoted object names in the per-table block. The parser is built for that:

- **Record splitter**: a record starts at a line matching the closed header grammar (timestamp, `(<pid>:<hex address>)`, an event name from a closed list: `ATTACH_DATABASE`, `DETACH_DATABASE`, `FAILED ATTACH_DATABASE`, `UNAUTHORIZED ATTACH_DATABASE`, `START_TRANSACTION`, `COMMIT_TRANSACTION`, `ROLLBACK_TRANSACTION`, their `FAILED` / `UNAUTHORIZED` forms, `PREPARE_STATEMENT`, `EXECUTE_STATEMENT_START`, `EXECUTE_STATEMENT_FINISH`, `EXECUTE_STATEMENT_RESTART`, `EXECUTE_PROCEDURE_*`, `EXECUTE_FUNCTION_*`, `EXECUTE_TRIGGER_*`, `COMPILE_BLR`, `EXECUTE_BLR`, `EXECUTE_DYN`, `SET_CONTEXT`, `ERROR AT …`, `WARNING AT …`, `START_SERVICE`, `ATTACH_SERVICE`, `DETACH_SERVICE`, `QUERY_SERVICE`, `TRACE_INIT`, `TRACE_FINI`, and the sweep events; list to verify per version) and ends before the next such line. The splitter cannot tell a forged header from a real one, so it splits at forged headers too; the rules below make every such split **loud**, never a silent drop. A record is bounded at 1 MiB; a longer one is not parsed and produces one always-reported event naming `*` for the target (loud, never quiet), counted. **At end of file**, the last record is held until a following header arrives or the file has not grown for 2 s and is not rotated (a stable EOF), so a record being appended is never parsed half-written (security review L5).
- **Trailer first, on every record** (H1, fix 1). Every record, whatever its event, is parsed **from its end** for a trailer: the per-table block (relation name, then eight 10-character counters, read from the right so names with spaces parse), the performance line, `<n> records fetched`, then upwards the parameter lines, which are skipped without being buffered beyond the parser. The trailer lines of a finish record are written by the server **after** everything a client controls, so a client can forge text before them but cannot remove or rewrite them. Each event has an expected trailer shape (finish events of statements, procedures, functions, triggers and BLR requests: records fetched, performance line, per-table block when `print_perf` is on; attachment, transaction and service events: none). **A trailer shape that does not fit the event** (a trailer under an `ATTACH_DATABASE` header, none under an `EXECUTE_STATEMENT_FINISH`) makes the record ambiguous.
- **Objects come from the per-table counters and from the text**, united (as pgaudit relation records and text names on PostgreSQL), for records that are not ambiguous. **Ambiguous records take objects from the counters only, plus `*`, never from the text** (H1, fix 5). The counters name the relations the statement's execution touched, including those read inside procedures, functions and triggers it called (to verify, obligation 7), with natural and indexed reads. This makes `print_perf = true` a Partial proof (below).
- **Header tokens** (H1, fixes 4 and 7). The `(<pid>:<address>)` pair identifies the trace plugin instance that wrote the record. Its address part is a heap pointer: **not a secret**. It can be guessed (allocator layouts are regular), inferred (from earlier tokens, a crash report, a log the attacker once saw), and the pid is visible in `MON$ATTACHMENTS`. Its value is only that a forger who guesses wrong is **loud**. The parser keeps a token per database path **for every database in the log**, declared or not, changed only at a `TRACE_INIT` / `TRACE_FINI` boundary. A record whose token is not the current one for its database, a `TRACE_INIT` while the current token's instance has not ended, or a token seen for two databases, marks the records involved **ambiguous**. How tokens behave per server mode, at database close and reopen, and across restarts is measured first (obligation 8); the rule is revised before Audit ships if the measurement differs.
- **Missing trailers** (H1, fix 2). A statement, procedure, function, trigger or BLR **finish** record of a declared database without its trailer (no `records fetched`, or no per-table block while `print_perf` is proven on) is ambiguous: a forged header inside it has moved its real trailer into the next record.
- **Other ambiguity**: a statement text (between the `-` line and the trailer), a process name or a user or role name that holds a line matching the header grammar, the `-` or `^` separator lines, a `param<i> =` line, a `records fetched` line or a per-table header; a record with two trailers; an attachment line that does not parse (a user or role name holding `,` `:` `(` `)` or a newline); a text cut at `max_sql_length` (length at the configured limit and ending in `...`); a path that matches a declared database only by file name or inode (M4).
- **What an ambiguous record becomes** (H1, fix 3). It is always reported, never the agent's own, never dropped as belonging to an undeclared database, with `*` added, its counters' objects and its row counts. It is attributed to the declared database of the **preceding well-formed record** (the one the forged header most likely split), or, when there is none in the same read or that record is of an undeclared database, to **every declared database of the target**. A cut text names `*` and is never the agent's own. Ambiguous records are counted in the new note `audit.log_records_ambiguous` and cap the level (proof 8).
- **Per-record isolation and buffers** (L5): each record is parsed and converted under the per-record panic isolation of [ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md); a record whose handling panics is dropped alone and counted. Record buffers (which hold parameter values and texts) are zeroized after the record is handled, as the CAS audit lines.
- **Residual** (recorded below): a client can still forge records that look like other attachments' statements (over-reporting), and, by splitting its own record with a forged header that carries the right token, separate its real principal from its real trailer. The trailer keeps the true objects and row count, so the read stays reported; the principal attached to it can be wrong when the forger guessed or inferred the token.

#### What is kept (I2)

- **Kept**: the event name and result (`FAILED`, `UNAUTHORIZED`), the timestamp (server local time, converted with an offset learned from the agent's own read-back probe, re-learned at every probe, as the SQL Server Extended Events clock calibration; a DST change between probes shifts times until the next one), the attachment id, the user and role, the protocol and the remote address and port, the transaction id, the statement id, the statement text through the normalizer, the records fetched, the per-table counters (relation names and counts) and the performance line's time.
- **Dropped at parse**: parameter values (`param<i>` lines), `SET_CONTEXT` values (`RDB$SET_CONTEXT` records under `log_context`), the plan (`print_plan`) and BLR or DYN dumps (`print_blr`, `print_dyn`: BLR can hold literals), the database path (mapped to the declared name, then discarded), the client process path and pid (client-set, spoofable, and a path can hold a user name), error and warning message texts (only their GDS codes are kept), and service records' arguments (only the service name from a closed list and the user are kept: `Add User` / `Modify User` service records can carry passwords; to verify what the trace prints there).
- **Statement text**: a Firebird mode of the query normalizer in `classifiers` ([ADR-0007](0007-mask-access-events.md), the ADR-0023 decision 4 rules): every literal replaced (`'…'` with `''`; the alternate quoting `q'…'` / `Q'…'` with **every delimiter pair** the server accepts (`()`, `{}`, `[]`, `<>` and any other single character as both ends); `x'…'` / `X'…'` and `0x…` hexadecimal literals; `n'…'` / `N'…'` and introducers such as `_UTF8 '…'`; numbers; date and time literals), `--` and `/* … */` comments removed, `"…"` read as an identifier in dialect 3 and as a string in dialect 1 (the client's dialect is not in the log, so both readings are lexed and readings that differ keep only the statement kind, fail closed as `ANSI_QUOTES` on MySQL). **A literal left unterminated** (a text cut at `max_sql_length`, or malformed) drops everything after its opening quote (security review L10). Only DML text is kept after normalization; DDL and DCL keep their kind, never text. PSQL bodies (`EXECUTE BLOCK`, `CREATE PROCEDURE`, triggers, functions, packages) are program text the SQL lexer does not delimit: they take no object name from the text (ADR-0023 decision 7); an `EXECUTE BLOCK` names the counters' relations plus `*` and is always reported. Statement text never leaves the agent (the contract has no field for it).
- **Password-bearing statements** (the end-to-end rule of #82, ADR-0039 decision 3): `CREATE USER`, `ALTER USER`, `CREATE OR ALTER USER` and `ALTER CURRENT USER` with `PASSWORD`, `CREATE DATABASE … PASSWORD`, `CONNECT … PASSWORD`, `EXECUTE STATEMENT … ON EXTERNAL [DATA SOURCE] … AS USER … PASSWORD …` (in PSQL bodies and `EXECUTE BLOCK`), `CREATE` / `ALTER MAPPING` (no password, but identity), and the `Add User` / `Modify User` services keep their kind only; the password never leaves the parser. The #82 end-to-end marker test gains one case per form and asserts that no marker appears in any uplink payload, agent log line or metric.
- **Principals**: as on the other SQL engines ([ADR-0021](0021-access-event-correlation.md)); the user names of `FAILED` and `UNAUTHORIZED ATTACH_DATABASE` records are fingerprinted (a password typed in the user field ends up there), as on every engine, and count toward the failed-login flood cap. With `log_connections = false` the failed logins are not seen: `audit.failed_logins_not_audited` gains `firebird` (security review L4).

#### Levels and proofs (ADR-0039 decision 3)

**Full is never reported.** The trace sees what goes through a server attachment, and not: the database file copied at the file-system level (a backup of the `.fdb`, `nbackup`'s physical copy, a snapshot), embedded-engine access by a local process (the embedded engine reads its own configuration, which may have no audit), statements below `time_threshold`, statements excluded by filters, and **replication** (Firebird 4.0+ logical replication ships changes through replication journals and a replica, not through traced attachments: `check()` reads the `replication.conf` / `RDB$CONFIG` replication settings where visible and notes an enabled replication in the local detail; security review L6). Each of those needs no SQL.

**Partial** when all hold, re-evaluated every 5 minutes; otherwise **Limited** (a record of a declared database parsed in the last 24 h) or **None**:

1. the log, the trace configuration and `firebird.conf` are readable under the file rules, and the account is outside the refusal list;
2. **the configuration is bound to the running server** (M3): `AuditTraceConfigFile` resolves to the declared trace configuration, `ServerMode` is read from `firebird.conf`, and neither file changed after the server process started when obligation 11 shows the server reads them only at start; a server in another pid namespace: not proven;
3. the trace configuration parses with the agent's closed key set (an unknown key, a parse error or a writable file: not proven), and for each declared database the sections that apply are the default `database` section and sections whose pattern is a plain file name with no `SIMILAR TO` metacharacter, **`_` and `%` included** (a file name holding `_`, common in practice, is therefore not evaluated: open question 12); any other section caps the level at Limited with the new note `audit.trace_config_not_evaluated` (the agent does not reimplement Firebird's `SIMILAR TO` on paths). How sections match (file name or full path, case, order, the default section's interaction with others) is measured first (obligation 13);
4. in the applying section: `enabled = true`, `log_filename` equal to the declared log, `log_connections = true`, `log_statement_finish = true`, `log_blr_requests = true` (gbak and other BLR clients read through BLR requests, which statement records do not show), `log_procedure_finish`, `log_function_finish` and `log_trigger_finish` on, `log_errors = true`, `time_threshold = 0`, `print_perf = true`, no `include_filter` or `exclude_filter`, `connection_id = 0`; each missing setting is a label of the new note `audit.trace_settings_missing` (Limited);
5. `max_sql_length` at least 4 096 (else the existing note `audit.statement_text_limit_low`, gaining `firebird`; not a cap, since cut texts are reported as `*`);
6. the services section has `enabled = true` and `log_services = true` (services backups and user management); missing: the new note `audit.services_not_audited` (informational; the database section still sees the service's attachments, to verify);
7. **the read-back probe**: at each re-evaluation, `check()` runs a constant probe statement on its own attachment (`SELECT COUNT(*) FROM RDB$DATABASE`) and the stream must find, within 10 minutes, its `EXECUTE_STATEMENT_FINISH` record with the agent's attachment id, the exact text, `1 records fetched` and a per-table block. This shows that the server writes the declared log for that database, that a statement of about 0 ms is written, and that `print_perf` is on; it also gives the time offset and the database path. It does **not** show that the declared configuration is the one in use (a decoy configuration whose settings differ from the running one can coexist with a passing probe): proofs 2 to 4 do that part;
8. no gap in the last 24 h: no truncated or replaced log (the keyed tail-cursor fingerprints of #97), no rotated file lost before it was read, no header-token anomaly and no ambiguous record; otherwise `audit.records_dropped` (or `audit.log_records_ambiguous`) and Limited for 24 h;
9. a record parsed in the last 24 h (the ADR-0023 decision 2 freshness rule; `audit.partial_pending_first_record` gains `firebird`);
10. the server mode is `SuperServer` or `SuperClassic`, or `Classic` once obligation 8 shows the token rule holds there (and the peer-uid rule under Classic's per-connection processes, open question 9).

Not seen by the trace, documented in docs/08 whatever the level: file-level copies, embedded access, rows read by the agent's own Discovery (left out under its budget, below), and what the server does without an attachment.

#### The agent's own statements and the always-reported rules

- **Own attachments** (the ADR-0051 decision 6 model; `databastion_core::audit::own`): at every attachment the connector reads `CURRENT_CONNECTION` (constant text). Firebird attachment ids are allocated from a counter kept in the database header and are not reused while the database lives (to verify across backup and restore, which resets it: an id seen again after a restore is not the agent's). The own set (database, attachment id, remote port, lifetime: to a clean detach, or to a lost connection plus the statement timeout plus 5 s, decision 3) is persisted with the stream position, kept 48 h. A record is the agent's own only if **all** hold: its attachment id is in the set for that database and its time falls in the attachment's lifetime; its user is the agent's account and its role the reader role or none; its remote address and port are the agent's loopback address and the local port of that attachment; its text is one of the connector's constant texts or the exact generated sampling text of an object with an unexpired credit (the statement's deadline plus 5 minutes); it is not ambiguous, cut or split; it carries no signal; and its records fetched stay within the per-object row budget (a count above the credit's `sample_rows` is reported, as an anomaly).
- **Statement-text objects, always reported** (the counterpart of [ADR-0045](0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) part (a) and [ADR-0049](0049-postgresql-statement-text-views-as-reads.md); candidate list confirmed per image by a drift test): reads of `MON$STATEMENTS` (`MON$SQL_TEXT`), `MON$COMPILED_STATEMENTS` (5.0), `MON$CONTEXT_VARIABLES` (values), `MON$CALL_STACK`, the profiler's `PLG$PROF_*` tables and `RDB$PROFILER` calls (5.0), and service records `Start Trace Session` / `List Trace Sessions`, keep that name as their object, carry the always-reported mark and are never the agent's own except the agent's exact `MON$DATABASE` / `CURRENT_CONNECTION` reads.
- **Credential-bearing objects, always reported** (the counterpart of [ADR-0050](0050-postgresql-credential-and-value-bearing-catalogs-as-reads.md)): the credential list of decision 5 (`SEC$USERS`, `SEC$USER_ATTRIBUTES`, `SEC$GLOBAL_AUTH_MAPPING`, `RDB$AUTH_MAPPING`, `PLG$SRP`, `PLG$SRP_VIEW`, `PLG$USERS`: verifiers and legacy hashes, readable where a database is its own security database), `RDB$DB_CREATORS`, `RDB$CONFIG` (the server configuration). Never the agent's own, except its exact `SEC$USERS` own-row read and its one-bit readability probes of decision 4.
- **Source texts of user code** (`RDB$PROCEDURES.RDB$PROCEDURE_SOURCE`, `RDB$TRIGGERS.RDB$TRIGGER_SOURCE`, `RDB$FUNCTIONS.RDB$FUNCTION_SOURCE`, `RDB$PACKAGES` bodies, `RDB$RELATIONS.RDB$VIEW_SOURCE`, the `*_SOURCE` columns of `RDB$FIELDS` and `RDB$RELATION_FIELDS`) can hold literals, including `EXECUTE STATEMENT … PASSWORD` credentials, and are readable by every user. They are **not** always reported in this ADR (every administration tool reads them), which is a residual (open question 7, as `prosrc` in ADR-0050); Discovery never reads them.
- **Other system relations** (relations on the decision 5 list, or with a non-zero system flag in the catalog, outside the always-reported lists) are left out of the objects of reads (noise), as MySQL's `is_system_relation`; writes to them are reported. The list or the system flag decides, **never the name prefix alone** (security review M5): a user table named `RDB$X` that is on neither is an ordinary object.
- **Code that runs out of sight**: a call of a function that is not built in (an unqualified name outside a closed per-version list of Firebird built-in functions checked by a drift test, a UDF, a UDR, a PSQL function or a packaged `pkg.f(`) adds `*` and is always reported, as ADR-0045 part (b). `EXECUTE PROCEDURE p` and a selectable procedure in `FROM` name the procedure itself plus the counters' relations, under the filters (the [ADR-0051](0051-sqlserver-connector.md) open question 12 answer; open question 13), **only if obligation 7 shows that the counters include the reads inside called code**; otherwise, and whenever a record has no per-table block, `*` is added. `EXECUTE STATEMENT … ON EXTERNAL`, external-file table reads and `EXECUTE BLOCK` add `*` and are always reported.

#### Signals

Existing signals extended to `firebird` in `shared/protocol/signals.json`: `shape.full_table_read` (a read without top-level `WHERE`, aggregation or `FIRST` / `ROWS` / `FETCH FIRST` of at most 10 000 rows), `volume.large_result` (more than 10 000 records fetched by one statement; `records fetched` counts rows, not blob bytes, so a few rows of large blobs do not raise it: documented in docs/08, security review N5), `signature.backup_database` (a services `Backup Database` or `Incremental Backup Database` record, `ALTER DATABASE BEGIN BACKUP` (nbackup), `CREATE SHADOW` (a server-maintained full copy of the database file), `ALTER DATABASE ADD FILE` and `ALTER DATABASE ADD DIFFERENCE FILE` (security review L6), and BLR requests reading a whole relation from an attachment whose process name is `gbak`, a client-set hint like MySQL's `program_name`), and `signature.remote_data_access` (`EXECUTE STATEMENT … ON EXTERNAL [DATA SOURCE]`, reads of external-file tables, `CREATE TABLE … EXTERNAL FILE`). No new signal.

### 7. I1, I3, I5 and local detection

- **I1**: one outbound TCP connection per attachment, to the declared loopback port; no listener, no auxiliary connection (events refused, decision 1). `connector-firebird` depends on no crate of `BANNED_CONNECTOR_DEPS` (`socket2` included). The peer-uid and process checks read `/proc` only.
- **I3**: the password stays on the agent host, zeroized, never on the wire (SRP), never logged. The account name travels in clear in `op_connect`, on loopback only. The `agent.yaml` block has no field the console can set.
- **I5**: one declared host (loopback) and port per target, declared databases only, no database listing, no server-named host followed (no events, no `EXECUTE STATEMENT … ON EXTERNAL` from the agent), external-file tables never read, undeclared databases' audit records dropped. Local detection ([ADR-0006](0006-target-discovery.md)) adds the local TCP port 3050 and the `firebird` process as detected, unconfigured targets; no other port is probed.

### P10-B implementation obligations

Facts this ADR could not confirm, each measured on the dev images or the matrix before the pull request that relies on it; a result that contradicts a decision makes this ADR be refined before that pull request merges.

1. **Wire encryption**: capture a ChaCha64, a ChaCha and an Arc4 session on 4.0 and 5.0, confirm that no MAC protects either direction, and examine the keystream properties under review (Context). The result goes to the maintainer first (security review N1); docs/05 and this ADR record it after the maintainer's disclosure decision.
2. **Protocol offer**: every 4.0.x and 5.0.x image accepts a client offering protocol 16 only; `op_cancel` works during a pending fetch in `ptype_batch_send`.
3. **Catalog visibility and grants** for the minimal account, the extended variant and the refused accounts: `RDB$USER_PRIVILEGES`, `RDB$ROLES.RDB$SYSTEM_PRIVILEGES`, `SEC$USERS` own row, `MON$DATABASE`, `RDB$CONFIG`; the system-privilege names and bit positions per version; what `SELECT_ANY_OBJECT_IN_DATABASE` exposes beyond user tables.
4. **Transactions**: the TPB is honoured (read-only, read committed, read consistency) and checked through the context variables (names to verify); a read-only read committed transaction does not hold the oldest active transaction back.
5. **Conversions**: the server-side `CAST` / `SUBSTRING` forms per type, the transliteration failure cases, and that `FIRST n` stops a natural scan early.
6. **Log file modes**: the mode Firebird creates the audit log and its rotated files with, under the image's default umask; the documented operator setting that lets the agent read without write.
7. **Per-table counters**: they are present for every finish event the Partial proofs rely on (statements, procedures, functions, BLR requests), include the relations read inside called procedures, functions and triggers, and name relations without truncation on 4.0 and 5.0.
8. **Header tokens**: the `(pid:address)` behaviour per server mode, at database close and reopen, at server restart and at log rotation; the rule of decision 6 is confirmed or revised.
9. **Trace text facts and failed logins**: whether service records print arguments (passwords of `Add User`), whether `CREATE USER … PASSWORD` texts are written as sent, the attachment line's format on 4.0 and 5.0; and the server's behaviour after repeated failed logins (delay, lockout) for the GDS mapping of decision 1.
10. **Attachment ids** are never reused within a database's life, and are reset by a restore.
11. **When the server reads its audit configuration** (`firebird.conf` and the trace configuration): at process start only, or also at a database's first open; per server mode (security review M3).
12. **Database paths in the trace** for aliases, `..`, `//`, symlinked directories, hard links and bind mounts, against `MON$DATABASE_NAME` (security review M4).
13. **Section matching** in the trace configuration: file name or full path, case, `_` and `%` in names, order and the default section (security review L5).
14. **`MON$ATTACHMENTS` remote address and port** of the current connection on loopback, through a forwarder and through a tunnel (security review M2).
15. **The I4 measurement plan** of decision 4 (security review M6).

## Consequences

- `agent/deny.toml` gains `[bans]` entries for Firebird C client crates; `crypto-bigint` joins the agent's dependencies (constant-time arithmetic for SRP); `sha1`, `sha2` and `chacha20` are already in the lock.
- A sixth own protocol client: about 3 000 lines whose robustness against a hostile server is the project's (fuzzed, property-tested), plus a second hostile-text parser (the trace log) and a configuration parser.
- **Loopback only.** A Firebird server can be monitored only by an agent on its host, with no other container in the shared network namespace unless every one drops `NET_RAW` / `NET_ADMIN` (or through an operator-run tunnel declared with `tunnel: true`, Discovery only); servers configured with `WireCrypt = Disabled` or Arc4 only, servers behind an undeclared forwarder, and Firebird 3.0, cannot be monitored.
- **Partial at best, and only with a demanding trace configuration** (`time_threshold = 0`, `print_perf`, BLR requests, no filters): the trace costs the server I/O on every statement; the load run measures it and docs/08 states it, so operators can weigh it.
- Discovery does not sample views, computed columns, external-file tables, GTTs, arrays or non-text blobs, and samples in storage order.
- The console (P10-E) must list `engine.firebird`, render its notes, signals and audit source, and add `firebird` to its case-sensitive and trailing-space-blind exception lists.
- `docs-keeper` (P10-G): [08-engine-capabilities.md](../08-engine-capabilities.md) row and sections written from the measurements (including that `records fetched` does not show blob volume); [05-security.md](../05-security.md#recommended-database-accounts-read-only) account block and the wire-encryption analysis (its keystream part only after the maintainer's disclosure decision); README "Supported databases"; `agent.example.yaml` (`firebird` block: loopback host, numeric `peer_uid` in containers, `databases`, `tunnel`, `audit.log`, `audit.trace_config`, `audit.firebird_conf`); the user guide (a random password of 32+ characters; the trace configuration with plain file-name sections; `RemoteBindAddress = 127.0.0.1`; the shared-namespace and `cap_drop` rule).

### Residual risks

- **Own parsers** of the Firebird wire protocol, the trace log and the trace configuration, from a possibly hostile server or writer; bounded, fail-closed and fuzzed, as the other own clients.
- **Firebird's wire encryption is weak by design** (no MAC, no server authentication, further keystream properties under review). Loopback only, the peer-uid check and the forwarder check contain it; a tunnel is the operator's.
- **Capture inside the network namespace** (M1): a holder of `CAP_NET_RAW` / `CAP_NET_ADMIN` in the namespace (root, or a container sharing it that did not drop them) can capture the SRP transcript and guess the password offline, must be assumed to read the sampled values, and can flip bits in the agent's requests. Contained by the deployment rule and a random password; root can read the database files anyway.
- **Impersonating listener**: the peer-uid check binds the connection to the declared server account, but a process running as that account (the Firebird server itself, or code it runs, such as a UDR) can always impersonate it; SRP then gives that process an offline guess per password candidate, defeated by a random password.
- **Forged trace records**: any client can write text that looks like other records. Every split is loud (ambiguous records are always reported, with `*`, attributed to a declared database), and the trailer-first parsing and the per-table counters keep the true objects and row counts of a statement reported; a forger who guesses or infers the header token can still attach a forged principal to them, and anyone can add forged events (over-reporting).
- **Roles not active in the session**: when the role graph cannot be evaluated (`privilege.not_evaluated`, `role_graph`), a refused right held through a non-default role may go unseen until the catalog becomes visible.
- **Configuration binding**: where the server re-reads its audit configuration, or the agent cannot see the server process, the binding is not proven and the level stays Limited; a configuration changed and reverted between two re-evaluations is not seen.
- **Source texts of user code** (procedure, trigger, view and default sources, readable by every user) can hold literals and credentials and are not always reported (open question 7).
- **Database triggers** run at every attachment and transaction of the agent; the read-only transaction blocks their writes except in autonomous transactions; reported, not prevented.
- **Not visible to the trace**: file-level copies of the database, embedded access, statements of databases whose applying configuration section the agent could not evaluate (Limited then).
- **Own-attachment window**: an attachment id is the agent's only within its lifetime and with its exact texts and credits; after a crash, the end of the last attachments is taken as the restart time, as on SQL Server.
- **Storage-order sampling bias**, and server-side conversions (`CAST`, `SUBSTRING`) running on sampled values (built-ins only).
- **The SRP group and hashes are Firebird's** (a fixed 1024-bit group, SHA-1 inside SRP and for the session key): the client cannot choose stronger ones.
- **Version facts** (lifecycle dates, system-privilege names and bits, context variable names, trace format details) are partly from the sources read on 2026-10-24 and partly as remembered, marked "to verify"; the obligations decide before each pull request.

## Rejected alternatives

- **`rsfbclient-rust`**: protocol 10 to 12 offered (clear password or DES hash on a downgrade), no protocol 16, Arc4 only, blocking I/O (decision 1).
- **`firebirust`**: `rust-crypto` 0.2.36 (unmaintained since 2016), panics on unexpected answers, Arc4 and unencrypted connections accepted, a second async runtime (decision 1).
- **`fbclient` through `rsfbclient-native`, ODBC or `isql`**: a C library (and OpenSSL-free only by luck of the build), process spawning, no control over what the library buffers or logs ([ADR-0039](0039-engine-scope-expansion.md) rejected alternatives).
- **Embedded access or reading `.fdb` files directly**: excluded by ADR-0039 decision 5; it bypasses the server's grants, and a hostile database file becomes a parser input.
- **Remote connections with ChaCha wire encryption** (the ADR-0039 decision 6 option "Firebird 4+ ChaCha with SRP mutual authentication"): no integrity and no server authentication on the path, so the agent's statements and transaction parameters are rewritable there and the confidentiality of the samples cannot be relied on (open question 2).
- **Arc4**: RC4 and its known biases, with the same missing integrity.
- **`Legacy_Auth` and `Srp` (SHA-1)**: a replayable DES hash; a SHA-1 proof where `Srp256` is available on every supported version.
- **User trace sessions through the services API**: `TRACE_ANY_ATTACHMENT` (every attachment's texts and parameter values over the network), the agent creating what it proves, output lost at restarts (decision 6).
- **The trace configuration proved by the read-back probe alone**: one probe cannot show the absence of filters or the BLR and procedure switches, nor that the declared configuration is the one the server runs with, so the configuration file and `firebird.conf` are read and bound to the running server process (decision 6, proof 2).
- **`print_plan` separators as the end of statement text**: forgeable and absent without `print_plan`; the trailer-first parse does not need them.
- **Sampling views, computed columns or selectable procedures**: runs user code on every read.
- **`SNAPSHOT` (concurrency) transactions**: they hold back garbage collection for their duration; read committed read-only transactions per unit do not.
- **Firebird 3.0 support with Arc4 on loopback**: loopback would contain Arc4, but 3.0 still lacks the server-side statement timeout and the system-privilege catalogs the refusal list needs (open question 1).

## Open questions (for the maintainer)

Each with the answer this ADR proposes; none is decided until the maintainer confirms it.

1. **Firebird 3.0**: ADR-0039's row says "3.0 if still maintained". Support it if its maintenance is confirmed?
   **Proposed**: no. Refuse it at connection (protocol 16 only), as ADR-0039 decision 1 allows: Arc4 only, no server-side statement timeout, no system-privilege catalogs. Record the amendment of ADR-0039's row.
2. **Remote Firebird servers**: loopback only (this ADR), or an opt-in remote mode with ChaCha and a documented risk note?
   **Proposed**: loopback only in phase 10; remote servers only through an operator-run TLS or WireGuard tunnel ending on the agent host's loopback, declared with the explicit local opt-in `firebird.tunnel: true` (its own `peer_uid`, a permanent `security.firebird_tunnel` note, Discovery only). Revisit if Firebird gains TLS or an authenticated wire cipher.
3. **Arc4 on loopback**: refuse it there too (this ADR)?
   **Proposed**: yes; Firebird 4.0+ always has ChaCha, and requiring it everywhere keeps one rule.
4. **Discovery with an account on the refusal list**: refuse both Discovery and Audit (this ADR), or Audit only?
   **Proposed**: both, as for SQL Server: nothing in Discovery needs those rights, and running with them would make the agent's credential the most powerful one on the server.
5. **`SELECT_ANY_OBJECT_IN_DATABASE` as the opt-in extended variant** (`extended_grants: true`)?
   **Proposed**: yes, only together with the M5 rule (credential and system relations never sampled whatever their flag, and `check()` refusing an account that can read verifiers), and once obligation 3 shows it exposes nothing beyond user tables and the already public `RDB$` tables; over-privilege without the flag.
6. **`TRACE_ANY_ATTACHMENT` and user trace sessions**: reject them and put the privilege on the refusal list (this ADR)?
   **Proposed**: yes; the system audit file gives the same records without a network-usable privilege.
7. **Source texts of user code** (`RDB$PROCEDURE_SOURCE` and the other `*_SOURCE` columns): always reported, or left out as noise?
   **Proposed**: left out in phase 10 and documented as a residual (as ADR-0050's `prosrc`), with a load measurement of how often tools read them; revisit with a no-source shape rule if needed.
8. **Firebird 6.0**: refuse it until a refinement of this ADR (this ADR)?
   **Proposed**: yes; schemas change the `Location` mapping and the catalog queries, and the protocol changes. Write the refinement once 6.0 is released and on the matrix.
9. **`Classic` server mode for Audit**: Partial only if obligation 8 shows the header-token rule holds there?
   **Proposed**: yes; Limited with a local detail otherwise. Also measure the peer-uid rule under Classic, where each connection is served by its own process (and, with socket activation, accepted by a socket the service manager owns). `SuperServer` (the default) and `SuperClassic` as planned.
10. **The peer-uid check on loopback**: mandatory with a configurable uid and no off switch (this ADR)?
    **Proposed**: yes. `peer_uid: 0` refused unless `peer_uid_root: true`; a numeric uid in containers; containers share the server's network namespace under the `cap_drop` rule; deployments where no server-side socket is visible (a userland port proxy owned by root) are not supported rather than unchecked.
11. **Console name rules for `firebird`**: case-sensitive exceptions (the ADR-0054 `matchCase` list) and trailing spaces ignored (`TRAILING_SPACE_BLIND_ENGINES`), with no `name_case` field?
    **Proposed**: yes, both, in P10-E, with the L9 matrix test confirming how the server upper-cases unquoted identifiers (non-ASCII letters included); the engine's rules are fixed and need no agent-reported value.
12. **Trace configuration sections with `SIMILAR TO` patterns**: cap at Limited (this ADR), or implement Firebird's `SIMILAR TO` matching of database paths in the agent?
    **Proposed**: cap at Limited in phase 10; `_` and `%` count as metacharacters, so a section for a file name holding `_` caps at Limited too. Operators can use plain file-name sections without them, which the user guide shows.
13. **Procedures**: name the procedure plus the counters' relations, under the filters (this ADR), or add `*` and always report every call?
    **Proposed**: name the procedure plus the counters' relations (the SQL Server answer) **only if obligation 7 shows that the counters include the reads inside called code**; otherwise add `*` to every call. `*` in any case when no per-table block is written.
14. **Sampling order**: `FIRST n` in storage order (this ADR), or a random `SKIP m`?
    **Proposed**: storage order; `SKIP m` reads and discards `m` rows on the server, against the < 2 % criterion. Revisit if findings show the bias matters.
