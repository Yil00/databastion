# ADR-0027: MongoDB Audit: sources, levels, grants, normalization and dump signatures

- **Status**: Accepted
- **Date**: 2026-09-29
- **Refines**: [ADR-0026](0026-mongodb-connector.md) (which stays Accepted): decision 1 (closed command set, one command and one `find` shape added), decision 10 (audit level) and the "Audit grants are decided with P5-B / P5-C" part of decision 5; [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md) (which stays Accepted): decision 6 (the agent's own account), and the PostgreSQL own-account rule of P4-A ([docs/08](../08-engine-capabilities.md#the-agents-own-account)), whose exclusion now covers reads and connections only (decision 7)
- **Context references**: P5-B, P5-C and the `mongodump` / `mongoexport` detection item of phase 5, branch `feat/p5-b-mongodb-audit` (`agent/crates/connector-mongodb/src/audit/`, `agent/crates/connector-mongodb/src/check.rs`, `agent/crates/core/src/config.rs`, `shared/protocol/signals.json`, `shared/protocol/target-notes.json`); the MongoDB counterpart of [ADR-0015](0015-postgresql-connector-decisions.md) decision 4 (PostgreSQL) and [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md) (MySQL / MariaDB); events follow [ADR-0007](0007-mask-access-events.md) and are correlated by the console as in [ADR-0021](0021-access-event-correlation.md)

## Context
[docs/08](../08-engine-capabilities.md#matrix) planned three MongoDB rows: Enterprise and Percona Server for MongoDB with `auditLog` (Full, "profiler for volumes"), and Community with the structured JSON server log plus the profiler ("Limited → Partial"). ADR-0026 shipped Discovery with the audit level None and the note `audit.stream_not_available`, and left the Audit grants open.

What each source actually records, checked against the MongoDB 5.0 to 8.0 formats:

- **`auditLog`** (Enterprise; Percona Server for MongoDB), `destination: file`, `format: JSON`, schema `mongo`: one document per event with `atype`, `ts`, `local`, `remote` (`ip`, `port`), `users` (`user`, `db`), `roles`, `param`, `result`. Reads and writes appear as `atype: authCheck` with `param: {command, ns, args}` **only when `auditAuthorizationSuccess` is true**; otherwise only refused commands are logged. `args` is the whole command document: filters, update documents and inserted documents, **with their literal values**. `authenticate` records carry `param: {user, db, mechanism}` and `result` (0, or 18 for a failure). DDL and user / role changes have their own `atype` (`createCollection`, `dropCollection`, `createUser`, `grantRolesToUser`…). No record carries a row count. MongoDB Enterprise 8.0 can also write the OCSF schema, and both editions can write BSON.
- **The structured JSON server log** (every edition, MongoDB 4.4 and later): one JSON object per line (`t`, `s`, `c`, `id`, `ctx`, `msg`, `attr`). Operations slower than `slowms` (and sampled by `slowOpSampleRate`) are logged as `id: 51803` ("Slow query") with `attr: {type, ns, appName, command, originatingCommand, planSummary, docsExamined, nreturned, ninserted, nModified, ndeleted, errCode, remote, …}`. `command` and `originatingCommand` are command documents **with literals** (filters, `errMsg` can quote values too). A slow-query line has **no user**: the user of a connection is on its authentication line (`id: 5286306` "Successfully authenticated", `id: 5286307` "Failed to authenticate", 20250 / 20249 on 4.4), the application name on its `id: 51800` "client metadata" line, all of them tied by the `ctx` (`conn<N>`).
- **The profiler** (`<db>.system.profile`, every edition, per database, per node): a capped collection (1 MiB by default, so a ring buffer) with one document per profiled operation: `ts`, `op`, `ns`, `command`, `originatingCommand`, `nreturned`, `ninserted`, `nModified`, `ndeleted`, `docsExamined`, `appName`, `client` (address), `user` (`name@db`), `errCode`. Level 1 profiles operations slower than `slowms`; level 2 profiles every operation, at a cost ([docs/08](../08-engine-capabilities.md#cost-for-the-monitored-database)). Reading it needs `find` on `system.profile`, which also exposes every other user's profiled command documents, literals included.

None of these sources gives every read with its row count: `auditLog` has every authorized command but no count; the log and the profiler have counts but only for the operations the server chooses to record (slow, sampled; the profiler also overwrites itself). The MongoDB tools declare themselves: `mongodump` and `mongoexport` set the driver's application name to their own name (`appName`), which the log, the profiler and, when the server writes it, the `auditLog` client metadata record show. Like `program_name` for MySQL, it is client-declared.

The agent's Discovery account (ADR-0026 decision 5) has no privilege that shows the server's audit, profiler or log settings: `getCmdLineOpts`, `getParameter` and `profile` need cluster or `enableProfiler` privileges the agent must not hold. Levels must therefore be proven from what the agent can read, never predicted from settings (the ADR-0026 rejected alternative).

## Decision
1. **Sources and preference.** Three sources, chosen by one rule (`audit::choose`) shared by `check()` and the Audit stream, re-evaluated every 5 minutes while the stream runs:
   - the **`auditLog` JSON file** (`audit_source` `mongodb_audit_log`): `targets[].mongodb.audit_log: {path, format: audit_log}`; used when the file is readable by the agent and `buildInfo` reports MongoDB Enterprise or Percona Server for MongoDB;
   - the **structured JSON server log** (`mongodb_log`): `targets[].mongodb.audit_log: {path, format: server_log}` (`systemLog.path`, `systemLog.destination: file`); used when readable, on any edition;
   - the **profiler** (`mongodb_profiler`), read over the agent's connection: used when no file source is usable, the target is not a `mongos` (a router has no profiler for data operations), and the account holds `find` on `system.profile` of at least one database (decision 5).

   One file per target (one `audit_log` block). The `auditLog` BSON format, the OCSF schema and the `syslog` / `console` destinations are not supported: their records do not parse and are counted as dropped (`audit.records_dropped`). Only the declared node's activity is seen: the log and the profiler are per node, and the connector never follows the replica-set topology (ADR-0026 decision 2); on a sharded cluster the `auditLog` of a `mongos` covers the commands it routes.
2. **Levels.** **Full is never reported for MongoDB.**
   - **`auditLog`: Partial** when the stream parsed a **successful `authCheck` record** in the last 24 h (proof that `auditAuthorizationSuccess` is on and reads are logged); **Limited** before that (after a restart, when nothing was read for 24 h, or when only authentications, DDL, user changes and refused commands are logged), with the note `audit.authcheck_success_pending`. Never Full: no row count (`audit.log_without_row_counts`), so volume-based detection does not work on this source. A configured `auditLog` on a Community server is not used (`audit.auditlog_on_community`).
   - **Server log and profiler: Limited at most**, with the note `audit.slow_operations_only`, and **None until the stream has parsed a record of the source in the last 24 h** (a server-log line of a known `id`, a profiler entry), with the note `audit.limited_pending_first_record`: a readable source that records nothing proves nothing (the same freshness rule as ADR-0023 decision 2). The source is still read meanwhile. The agent cannot read `slowms`, `slowOpSampleRate` nor the profiling level, and even at level 2 or `slowms: 0` the profiler is a ring buffer and the log is sampled. docs/08's "Limited → Partial" for Community is not adopted.
   - **None** when no source is usable, with the note `audit.source_not_configured` (and `audit.log_not_readable` when a configured file cannot be read).
3. **What is kept from a record: closed-shape fields only (I2, ADR-0007).** From every source the connector keeps the time, the command **name** (compared with a closed list, never kept as text), the namespace (database and collection, normalized like Discovery names: `normalize_database`, `normalize_collection`; `$cmd` or no collection is `*`), the user (`name@authdb`), the client address (an IP literal only, the port dropped), the application name (reduced by `EventPrincipal::with_application`), the document counts (`nreturned`, or `ninserted` + `nModified` + `ndeleted`), whether the operation failed (a numeric code), and three shape facts of the command: whether its filter has any key (a count of keys, never a key or a value), its numeric `limit`, and its aggregation stage operators compared with a closed list. **Never kept, logged or sent**: `param.args`, `command`, `originatingCommand`, `planSummary`, `errMsg`, `errName`, the `auditLog` `applicationMessage` text, index names, update or inserted documents, or any other field.
   - **Files** (`auditLog`, server log): records go through the core tailer (zeroized buffers, bounded records) and a `serde` reader that visits the command document without materializing its values (`IgnoredAny`), so filters and literals are skipped, not copied. A record that does not parse, or is not an object, is dropped and counted. Skipping a value (`IgnoredAny`) is iterative in `serde_json`, with no depth limit, so a deeply nested command document is skipped without being followed; only the few levels the reader itself visits (the record, `attr` / `param`, the command document, a pipeline stage) count toward `serde_json`'s recursion limit (128 levels). A record is dropped only when an identity or namespace field is invalid; an invalid descriptive field (an application name with a NUL or over 1 KiB) is dropped alone and the operation is still reported. The names of failed authentications are held in zeroized buffers.
   - **Profiler**: the closed-shape facts are **computed by the server** in a fixed projection (`$objectToArray` / `$size` / `$map` on `command`, `originatingCommand` and `pipeline`, see decision 8), so command documents and their literals never cross the wire; only the projected fields are read.
4. **Actions.**
   - `read`: `find`, `aggregate` (without `$out` / `$merge`), `getMore`, `count`, `distinct`, `mapReduce`. `write`: `insert`, `update`, `delete`, `findAndModify`, `bulkWrite`, `aggregate` with `$out` / `$merge` (profiler `op` `insert` / `update` / `remove` too). `ddl`: `create`, `drop`, `dropDatabase`, `createIndexes`, `dropIndexes`, `renameCollection`, `collMod`, `convertToCapped` (and the `auditLog` DDL `atype`s). `dcl`: user and role commands (`createUser`, `updateUser`, `dropUser`, `grantRolesToUser`, `createRole`…, and their `auditLog` `atype`s); DCL events name no object (as in ADR-0023 decision 7). `connect` / `auth_failure`: `auditLog` `authenticate`, the log's authentication lines. Every other command (`hello`, `ping`, `listCollections`, `buildInfo`, `saslStart`, `killCursors`, `endSessions`…) is metadata and yields no event.
   - `auditLog`: reads and writes come from successful `authCheck` records (`result: 0`); a refused `authCheck` (`Unauthorized`) read nothing and is skipped; DDL and DCL come from their own `atype`s (logged whatever `auditAuthorizationSuccess`), and `authCheck` records of DDL / DCL commands are skipped so they are not counted twice. `logout`, `clientMetadata` and every other `atype` yield no event.
   - Server log: operations come from slow-query lines of `type: command`; the per-statement write lines (`type: update` / `remove`) are skipped (the command line covers them). Lines not tied to a client connection (`ctx` not `conn<N>`: internal threads such as session refresh or TTL) and `auditLog` records of the server's own system user are skipped.
   - A failed operation is reported only when it returned documents (a failure after a partial read); one refused before reading anything (unauthorized, unknown namespace, bad command) is skipped, as in ADR-0023 decision 4.
5. **Grants.**
   - **File sources need no database grant.** The agent reads the file on its own host through the core tailer (regular file only, rotation and truncation followed, cursor persisted); the file ACL is the operator's job: the agent's user needs read access to the log directory, never to the data directory (`dbPath`). The mongod log and the `auditLog` both hold literals of other users' commands: they must not be world-readable (`0640` with a dedicated group; the dev environment's permissive files are a dev-only convenience).
   - **The profiler needs `find` on `system.profile` of each database to audit**, in its own role, and nothing else:

     ```js
     db.getSiblingDB("admin").createRole({
       role: "databastionAuditProfiler",
       privileges: [
         { resource: { db: "app", collection: "system.profile" }, actions: ["find"] }
       ],
       roles: []
     });
     db.getSiblingDB("admin").grantRolesToUser("databastion", [{ role: "databastionAuditProfiler", db: "admin" }]);
     ```

     Least privilege versus coverage: this grant lets anyone holding the agent's credentials read every profiled command of the database, literals included, over the network; the agent's projection limits what the agent fetches, not what the credentials allow. The file sources carry the same literals but stay on the database host behind a file ACL. The **file sources are therefore preferred**, and the profiler grant is recommended only when the agent cannot read the files (an agent that does not run on the database host). Turning the profiler on (`profile` level, `slowms`) needs `enableProfiler`, which the agent never holds: it is the operator's job.
   - **`check()`** counts `find` on `<db>.system.profile` (a named, non-system database, `find` only) as the Audit grant while an Audit stream runs with the profiler as its source; otherwise (no stream, or a file source) it is reported as `privilege.system_collections`, like any other access to system collections (ADR-0026 decision 5). Every other privilege on `system.profile` stays over-privilege.
6. **Principal and connection correlation.**
   - The account is `name@authdb` (the profiler's `user`, the `auditLog` `users[0]`, the log's authentication line), so `alice` of `admin` and `alice` of `app` stay apart; the core sends it in clear when it matches the contract pattern, a fingerprint otherwise, and always a fingerprint for an `auth_failure` (ADR-0007).
   - **Server log**: the connector follows connections by `ctx` (`conn<N>`): the client address from the accept line, the user from the authentication line, the application name from the client metadata line; a connection ended line forgets it. At most 4096 connections are followed (oldest forgotten first). An operation on a connection authenticated **before** the agent started reading the log (a pooled connection after an agent restart or on the first start) has no known user: it is reported as an unidentified account (`EventPrincipal::unidentified`), with its client address and application name.
   - **`auditLog`**: the user is on every record; the application name comes from a `clientMetadata` record of the same client address and port when the server writes one (at most 4096 followed).
7. **The agent's own account.** Its operations are left out only when all of these hold (`databastion_core::audit::own`, as for PostgreSQL and MySQL): the account is `<account>@<auth_source>` of the target, the application name is `databastion-agent` when the source shows one (the connector's `hello`, ADR-0026 decision 3), the client address is the agent's own address as the server sees it (the `whatsmyuri` command, re-read at each re-probe; only an IP literal counts, so a Unix socket leaves nothing out), no signal, and the documents it read stay within `limits.max_sample_rows` per collection over a rolling 24 h.
   - **Reads and connections only, for every engine.** Writes, DDL and DCL by the agent's account are always reported: the agent never writes (I4), so any such event with its identity is someone else using it. This rule lives in the shared core (`OwnAccount::routine`, commit `35c6459`) and so also applies to PostgreSQL and MySQL / MariaDB: it refines ADR-0023 decision 6 and the PostgreSQL rule of P4-A, which did not restrict the exclusion by action. DCL events name no object, so the row budget never charged them before this change. The PostgreSQL table-less allow-list (#65) is unchanged.
   - **Unknown counts** (the `auditLog`): only a `find` with a numeric limit in `1..=max_sample_rows` is left out, charged that limit; any other read (an `aggregate`, including the agent's own `$sample`, a `find` without a limit) is reported.
   - **Uncharged**: the agent's `count` without a filter (it reads no document), and, **on the profiler source only**, its own profiler polls with their exact shape (a `find` on `system.profile` with a one-key filter and `limit: 1000`, or the newest-entry probe with no filter and `limit: 1`), which would otherwise report themselves at every poll (`routine_unbudgeted`, same identity rules), and **no more of them per database than the polls the stream actually sent**: each poll (or probe) the stream sends grants one credit for its database (at most 64 unused credits kept), a poll-shaped read with the agent's identity uses one, and one without a credit is charged like any read. Any other read of `system.profile` with the agent's identity is charged like any read, and a read of it by any other account is reported.
8. **Bounds (I4).**
   - Files: the core tailer (at most 8 MiB per poll, 1 MiB per record, oversized and damaged records skipped and counted), the `serde_json` nesting limit, at most 4096 followed connections or client metadata entries.
   - Profiler: per poll and per database, one `find` on `system.profile` built in code: `filter: {ts: {$gt: <last ts>}}` (a date from the connector), the fixed projection of decision 3, `sort: {$natural: 1}`, `limit: 1000`, `singleBatch: true` (no cursor left open, no `getMore`), `maxTimeMS` from the audit statement timeout (never `0`), at most 64 databases per poll (those with the grant; `admin`, `local` and `config` are never polled). The read position (the last `ts` per database) is kept in memory; the first poll starts at the newest entry (no history replay). No other command is added to the ADR-0026 set but `whatsmyuri` (no privilege, no data).
9. **Signals.** Registered in `shared/protocol/signals.json` (append-only, compatible change):
   - `signature.mongodump` (new): a read of a collection (`find`, `aggregate`, `getMore`) by a client whose application name is `mongodump` (alone, or followed by a space, `/`, `-` or a version);
   - `signature.mongoexport` (new): the same with `mongoexport`;
   - `shape.full_table_read` (engines + `mongodb`): a `find` whose filter has no key, without a limit or with a limit above 10 000, or an `aggregate` whose stages are all pass-through stages (`$project`, `$addFields`, `$set`, `$unset`, `$sort`, `$replaceRoot`, `$replaceWith`) or that has none; a `getMore` carries the shape of the operation that opened its cursor when the source shows it (log, profiler);
   - `volume.large_result` (engines + `mongodb`): more than 10 000 documents returned or written by one operation (log and profiler only).

   These are heuristics: the application name is client-declared, and a tool run under another name, or a dump in many small filtered reads, only has the shape and volume signals (evadable by design, as ADR-0023 says of `signature.mysqldump`).
10. **`check()`.** Reachability, edition from `buildInfo`, the privilege report, the source and level of decision 2 with their closed notes, and the dropped-record count of the last 24 h; `audit.stream_not_available` is no longer sent (the code stays registered: the registry is append-only). The heartbeat `audit_source` is the chosen source. New note codes, `mongodb` only: `audit.auditlog_on_community`, `audit.authcheck_success_pending`, `audit.slow_operations_only`, `audit.source_not_configured`, `audit.limited_pending_first_record`; `mongodb` is added to the engines of `audit.log_not_readable`, `audit.log_without_row_counts` and `audit.records_dropped`. No new `TargetNoteLabel`, so no capability token ([ADR-0022](0022-protocol-capability-negotiation.md) decision 4).
11. **Time and delivery.** Timestamps are read from the source (ISO 8601 with `Z` or an offset, or epoch milliseconds, in the files; a BSON date in the profiler) and converted to UTC; the core clamps event times to the agent clock (#72). Delivery is at most once, as for the other connectors: a file cursor advances once the events are handed to the core, and the profiler position is in memory.

## Consequences
- MongoDB targets report Partial at best (`auditLog` with `auditAuthorizationSuccess`), Limited on Community. docs/08 must replace its three MongoDB rows (Full / Full / "Limited → Partial") and the "as implemented" paragraph (`docs-keeper`); docs/05 gains the profiler role and the log file ACL.
- `agent.yaml` gains `targets[].mongodb.audit_log: {path, format}` with `format` `audit_log` or `server_log`.
- **No row counts on the `auditLog`**: the console scores those events 0 (ADR-0021); only signatures, shapes, sensitive objects and principal conditions raise incidents there.
- **Unknown users on the log source** after an agent restart, for connections that predate it: they count as one unknown principal per client network in the console (ADR-0021 decision 6) until the client reconnects.
- The console shows the new note codes from its generated phrase catalog and the new signals from its generated signal registry (`console/src/generated/protocol/`), regenerated from the registries.

### Residual risks
- **Community sees slow operations only.** A fast `mongodump` of a small collection, or any read under `slowms`, is invisible unless the operator sets `slowms` low (with its cost); a sampled log (`slowOpSampleRate` < 1) misses operations at random. This is what Limited means, and the console shows it.
- **Profiler ring buffer.** Entries overwritten between two polls are lost without a trace (the capped collection keeps no count); a larger `system.profile` or a shorter poll interval reduces the risk.
- **`auditLog` filters are the operator's**: an `auditLog.filter` that leaves out some reads, or `auditAuthorizationSuccess` turned off after the last successful `authCheck`, is only detected when no successful `authCheck` is parsed for 24 h.
- **Signal evasion**: the application name is client-declared; a dump tool can rename itself, and `getMore` batches split a large read into operations below the volume threshold (the console baseline still sees the aggregated rows). The shape rule is cheap to evade: a filter that selects everything (`{_id: {$exists: true}}`), or an `aggregate` with `{$match: {}}` or a large `$sample`, is not a "whole-collection" shape.
- **Signal stripping on the `auditLog`**: `getMore` records carry no filter, so only the application-name signatures apply to them; the shape is carried by the opening `find`.
- **Own-account residual**, as in P4-A and P4-B: someone holding the agent's credentials on the agent host, spoofing its application name and reading at most the budget per collection and day stays unreported (on the `auditLog`, with `find`s whose limits add up to the budget; on the profiler source, a poll-shaped read of `system.profile` is uncharged only while the stream has sent a matching poll whose own entry was not seen yet, so such a client can at most take the place of the agent's own polls, a few batches of 1000 entries per database, before its reads are charged and reported; the agent's own polls are then charged instead). Writes, DDL and DCL with the agent's identity are always reported. Behind a proxy or NAT, every client has the same address.
- **Log literals on the agent host**: the agent reads files that hold other users' literals (in memory only, zeroized buffers, never logged or sent); a compromised agent host can read them anyway through the file ACL it was given.
- **At-most-once delivery** and in-memory profiler positions: an agent crash within the aggregation window loses events already read; an agent restart skips what the profiler recorded while it was stopped.

## Rejected alternatives
- **Report Full for `auditLog` + profiler** (docs/08): the profiler records only slow operations and overwrites itself, so volumes would be known for some operations only; every read with its row count is not visible.
- **Report Partial for Community at profiler level 2 or `slowms: 0`**: the agent cannot read these settings without `enableProfiler` or cluster privileges, and the log is sampled; the level would be a guess.
- **Read `param.args` / `command` to name more objects or detect more shapes**: they carry the literals of other users' commands (I2). Only the closed-shape facts of decision 3 are extracted, and on the profiler they are computed server-side.
- **Join the `auditLog` with the server log or the profiler for row counts**: correlating records across files by time and connection is fragile and would still not count fast operations; left for a later ADR if needed.
- **The profiler as the preferred Community source**: the grant exposes every profiled literal to the agent's network credentials, and the profiler is a ring buffer; the log file needs no database grant.
- **`clusterMonitor` or `read` for the profiler**: `find` on `system.profile` of every database, `inprog`, change streams; decision 5's per-database role is enough.
- **`getCmdLineOpts` / `getParameter` to read the audit and profiler settings**: cluster privileges the Discovery account must not hold (ADR-0026 decision 5).
- **Edit ADR-0026 or ADR-0023 in place**: the ADR convention does not allow editing an accepted ADR.

## Refinement (2026-10-10, phase 8 follow-ups)
- **Decision 7, the agent's own account** (security reviews of #196 and #197). The engine-agnostic own-account rule of [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md#refinement-2026-10-10-phase-8-follow-ups) (refinement of decision 6) applies here too: every read with the agent's identity is charged at least one row, aggregates `max(r, 1) + n - 1`, and budget keys ignore case.
