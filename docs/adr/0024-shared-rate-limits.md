# ADR-0024: Console rate limits shared through PostgreSQL

- **Status**: Accepted
- **Date**: 2026-09-29
- **Refines**: [ADR-0017](0017-alerting.md) (which stays Accepted), the test-send item of decision 9 "Volume bounds" ("These limiters are in memory, per process") and the residual risk "Test-send limits are per process"; [ADR-0021](0021-access-event-correlation.md) (which stays Accepted), the consequence "Per-process rate limits"
- **Context references**: P4-D (ROADMAP item "Shared-storage rate limiters when the console runs more than one process") and the P3-D test-send item, branch `feat/p4-d-shared-rate-limits` (commits a8016aa and fbc906b, then the security review follow-ups H1, M1, L1 to L4: `console/src/server/rate-limit.ts`, `console/README.md` "Shared rate limits", migrations `0029_p4d_rate_limit_counters.sql` and `0030_p4d_rate_limit_grants.sql`, worker queue in `console/src/worker/queues.ts`)

## Context
Until P4-D every console rate limiter kept its counters in memory, per web process. [ADR-0017](0017-alerting.md) records this for channel test sends, and [ADR-0021](0021-access-event-correlation.md) for the `/events` request and stored-batch rates; the same held for agent authentication failures, `/enroll`, `/rotate` and its late retries, the `/findings` rates, the integrity and failed-enrollment audit budgets and failed logins. With N web replicas, each limit was applied N times: an attacker spreading requests over the replicas got N times the budget (password guessing, agent-secret guessing, enrollment tokens). The limits must hold across processes, and the shared counters must not become a new store of IPs, usernames as typed (possibly a password) or agent ids, nor a single point whose failure either opens every limit or locks every agent out.

## Decision
1. **Storage.** Every shared limiter keeps its counters in the console PostgreSQL, table `rate_limit_counters` (migration `0029`): one row per (limiter, key), primary key `(limiter, key_hash)`. Each row is one fixed window anchored at the first hit of the key, like the previous in-memory limiter, reset in place by the first hit after `expires_at`. Window instants come from the database clock; `Retry-After` is the rest of the window as the database sees it. Each decision is one statement:
   - a hit is one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`;
   - a reservation (check and count) is the same upsert guarded by `count < limit` (or an expired window), so concurrent requests from any process cannot overrun the limit;
   - a refund is one `UPDATE` that decrements the count only while the window it was counted in is still the current one (matched on its start instant); refunds are idempotent and keep their previous semantics (a successful login or authentication, and a duplicate, rejected or failed findings or events batch give their slot back);
   - the three agent-authentication limits (failures per (agent, IP), argon2id-backed failures per IP, cheap failures per IP) are checked with one `SELECT`.
   The runtime role gets `SELECT, INSERT, UPDATE, DELETE` on the table and nothing else (migration `0030`).
   The statements run on a **dedicated pool** of 3 connections (`lock_timeout` 1.5 s, `statement_timeout` 2 s, 2 s to get a connection), never on the main pool: contention on one hot counter row cannot starve the rest of the console, and a statement the limiter gives up on is cancelled by the server.
2. **Keys.** The stored key is `HMAC-SHA256` of `limiter \0 key` under the server-key subkey `rate-limit-keys.v1`, never the clear key (usernames as typed, IPs, device nonces, agent ids); the table enforces a 64-hex-character `key_hash`. Without a usable server key (in production only under the explicit `DATABASTION_ALLOW_MISSING_ENCRYPTION_KEY=1` override):
   - the limiters whose key is derived from what a user typed in the username field (`login.failures_per_user_ip`, `login.failures_per_user`, `login.degraded_failures`) are **not shared**: they stay per process, as before P4-D, so no unkeyed hash of a possible password is ever stored. The startup error of the override says so ("(4) login rate limits keyed by username are per process only");
   - the other limiters (IP buckets, device nonces, agent ids, fixed keys) store a domain-separated SHA-256 (`databastion.rate-limit-keys.v1 \0 limiter \0 key`): unkeyed, so a database dump then allows testing guesses of those keys.
   Processes running with different server keys, or a server-key rotation, derive different hashes: the counters are then split between the keys, or reset by the rotation (limits at most as loose as one window per key in use).
3. **In-memory pre-check and negative entries.** Each shared limiter still counts this process's own hits in memory and refuses early when they alone reach the limit, without a database round-trip. These hits are a subset of the shared ones, so the pre-check can only refuse earlier, never admit more. When the store reports a key at its limit (a refused reservation; a hit or a check at the limit), the process records the key as limited until the end of the store's window, and a hit on a key already limited in the process is not sent to the store. A flood on one key therefore costs each process at most about `limit + 1` statements per window, however many requests it receives. A refund made in another process is seen by a process holding such an entry only when the window ends, which is what its `Retry-After` announced. An agent secret exempt from the authentication failure limits without a database read (in the 25 s verified cache, or known good per the in-memory hint) skips the shared check.
4. **Failure mode.** A store operation that errors (including a server-side lock or statement timeout), gets no connection within 2 s, or does not answer within 5 s (client-side guard, longer than the server-side timeouts) is a store failure. It is logged at most once per minute per limiter (limiter name, failure mode and error summary, never the key) and counted in `databastion_console_rate_limit_store_errors_total`. Each limiter declares its mode:
   - **Fail closed** for authentication and user actions: agent authentication failures (`agent_auth.failures_per_agent_ip`, `agent_auth.failures_per_ip`, `agent_auth.cheap_failures_per_ip`), `/enroll` (`enroll.per_ip`), `/rotate` (`rotate.per_agent`), logins (`login.*`) and channel test sends (`channel_test.per_user`, `channel_test.per_channel`). A reservation or check is refused with `429` and `Retry-After: 5`; a hit reports the key as limited; a charge (which never refuses) and a count fall back to the per-process counters. During a store outage, only an agent secret verified by this process less than 25 s ago, or known good per this process's in-memory hint, still authenticates (decision 3); an agent known good only per its database row gets `429` until the store answers.
   - **Per-process fallback** for ingest and budgets: the `/findings` and `/events` request and stored-batch rates (`findings.requests_per_agent`, `findings.batches_per_agent`, `events.requests_per_agent`, `events.batches_per_agent`), the agent-integrity and failed-enrollment audit budgets (`integrity.writes_per_agent`, `enroll.failure_audit`). The in-memory counters decide, which is the pre-P4-D per-process limit. Ingestion and audit rows use the same database: failing closed would make every agent back off on a limiter hiccup, failing open would drop the bound.
   - **Exception: `rotate.stale_retries_per_agent`** (late `/rotate` retries with a stale secret, [ADR-0011](0011-late-rotation-retry.md)) also uses the per-process fallback, although it is on an authentication path. Over this limit the agent is locked (revocation and re-enrollment to recover), so failing closed would turn a transient store error into an irreversible lock. The path is only reached with a verified previous secret, and the per-process fallback still bounds the retries.
5. **Login timing.** Every login reserves the unknown-username budget (`login.failures_unknown_user`), concurrently with the user lookup; a known user gives the reservation back (or ignores a refusal). Known and unknown usernames thus pay the same store latency, and the store use does not reveal whether a username exists.
6. **IPv6 bucket of the cheap limit.** `agent_auth.cheap_failures_per_ip` buckets IPv6 sources by /48 (the argon2id-backed per-IP and per-(agent, IP) limits keep /64): one IPv6 allocation cannot multiply the cheap budget, nor the rows it writes, by rotating /64s. It only gates reaching argon2id, and exempt agent secrets are not held by it, so agents sharing the /48 are not locked out by it.
7. **Pruning.** The worker queue `rate_limits.prune` (every 5 minutes, `stately`) deletes expired windows in chunks of 10 000 rows within a 20 s budget, and re-queues itself when expired rows remain. Pruning changes no decision: an expired window is reset by the next hit of its key anyway. The table size (expired rows included, counted up to 1 000 000) is exported as `databastion_console_rate_limit_counters_rows`, for alerting on floods of distinct keys between two prunes.

## Consequences
- N web replicas enforce one limit per (limiter, key), not N.
- The `/events` check order and its `Retry-After` values are unchanged (`30` for back-pressure, 1 to 60 s for the rate limits); the existing tests pass unmodified.
- Only a per-process log de-duplication (integrity suppression warnings) stays in memory; it is not a rate limit.

### Residual risks
- **Row growth.** The table holds at most one row per key seen in the last window (15 minutes at most) plus the expired rows not yet pruned; growth is bounded by the pruning, not by the limits themselves. A flood of distinct keys (e.g. spoofed usernames) writes one row each until pruned; `databastion_console_rate_limit_counters_rows` makes it visible.
- **A timed-out operation committing late.** Before the security review, the client-side timeout did not cancel the statement: a reservation answered as a store failure could still be counted later. That only made a limit stricter, but for `rotate.stale_retries_per_agent` a stricter limit locks the agent earlier. The dedicated pool's `lock_timeout` and `statement_timeout` (decision 1), shorter than the client-side guard, now make the server cancel such a statement, so it is not committed; only a statement that completes in the instant the guard fires can still count.
- **Known-good lookup skipped when the store fails.** When the cheap per-IP check fails closed, the database lookup of an agent's known-good fingerprint is skipped, so only secrets exempt without a read (verified cache, in-memory known-good hint) keep authenticating. An agent known good only per its database row (e.g. first request to a freshly started replica) gets `429` until the store answers again.
- **Pool saturation.** The counters use their own pool of 3 connections (decision 1), so they cannot starve the main pool, and the negative entries (decision 3) cap the statements a flood on one key can cause. A flood of many distinct keys can still saturate that pool: operations then get no connection within 2 s or hit the lock timeout, and the fail-closed limiters answer `429` (logins, enrollment, rotation, non-exempt agent authentication, test sends) until it recovers; the rest of the console is not affected.
- **Unkeyed hashes without a server key.** See decision 2: IP buckets, device nonces and agent ids only; username-derived keys are never stored then.
- **Refunds across processes are delayed** for a process that already refused the key (decision 3): it may refuse until the end of the window although another process gave a slot back. This only refuses earlier, never admits more.

## Rejected alternatives
- **Keeping per-process limits and documenting "one web process"**: the limits would silently multiply with the replica count.
- **Storing the keys in clear**: the table would record IPs, usernames as typed (possibly a password), device nonces and agent ids.
- **Failing open on store failure**: a database outage or saturation would remove every bound on password and secret guessing.
- **Failing closed everywhere**: a limiter hiccup would make every agent back off on ingest, and the stale-retry limiter would lock agents irreversibly.
