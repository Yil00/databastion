# ADR-0031: Incident dedup of fingerprinted principals, alert on stopped Audit streams, OpenLDAP residuals

- **Status**: Accepted
- **Date**: 2026-09-29
- **Refines**: [ADR-0021](0021-access-event-correlation.md) decisions 6 and 7 (dedup scope of fingerprinted principals, events after a false positive) and [ADR-0029](0029-openldap-connector.md) (principal grouping and panic isolation consequences, decision 7 object order); both stay Accepted. Adds a system alert to the set of [ADR-0017](0017-alerting.md) decision 5.
- **Context references**: end-of-phase-6 security review on `0475510` (findings M1, M2, L3, L4, I3); `console/src/lib/event-model.ts` (`coarsePrincipal`, `eventDedupKey`), `console/src/server/event-engine.ts` (dedup key and false-positive linking), `console/src/server/dropped-batches.ts` (the `agent.batches_dropped` pattern), `agent/crates/core/src/runtime.rs` (panic guard, `connector_panics_total`, `run_audit` resuming from the persisted cursor), `agent/crates/core/src/audit.rs` (cursor and settings files), `agent/crates/connector-openldap/src/audit/mod.rs` (`Position`), `agent/crates/connector-openldap/src/audit/events.rs` (event objects)

## Context
The end-of-phase-6 security review found two Medium issues that are not OpenLDAP code bugs but consequences of combining the OpenLDAP connector ([ADR-0029](0029-openldap-connector.md): principals fingerprinted, no client address in the log, core panic isolation) with earlier decisions.

**M1: one coarse principal for a whole directory.** ADR-0021 decision 6 keys incidents by `policy | agent | target | principal | database | hour`, and uses a coarse principal `unknown:<SHA-256 of the client network>` for every fingerprinted account and every `auth_failure`. The intent was that random account names or rotating addresses count as one principal. On SQL engines and MongoDB, a fingerprinted account mostly comes from a failed login. On OpenLDAP, ADR-0029 fingerprints **every** principal except `anonymous`, the agent's own DN and `clear_principals`, and the access log records no client address, so nearly all OpenLDAP events share `unknown:sha256("-")` per policy, database and hour. Two consequences:

- once one such incident is marked a false positive, every other user's events of that policy, database and hour are only linked to it (ADR-0021 decision 7 opens a new incident only after a *resolved* incident, never after a false positive);
- a second user's dump is merged into the first user's open incident instead of raising its own.

**M2: a stopped Audit stream raises no alert.** Since #79 the core runs every connector call through a panic guard. An Audit stream that panics 3 times in a row (a 10-minute run resets the count) is stopped until Audit is reconfigured or the agent restarts; the target reports level None with the note `audit.stream_stopped`. This holds for every engine. The console only shows the note on the target; nobody is notified, although Audit of that target has stopped. [05-security.md](../05-security.md) said "a panic fails that call only", which is inaccurate for a panic that repeats on the same record. Reconfiguring Audit or restarting the agent does not skip that record either: the cursor file is kept (only the settings file is removed when Audit is disabled), and the stream resumes from the persisted cursor, so a record that always panics stops the stream again after 3 more panics.

The review also asked to record residuals of the OpenLDAP connector (L3, L4) and to clarify the object order of ADR-0029 decision 7 (I3).

## Decision
1. **Dedup principal (refines ADR-0021 decision 6).** The principal part of the dedup key is coarse (`unknown:<SHA-256 of the client network>`, networks as in ADR-0021) **only for `auth_failure` events**. Every other event is keyed by its `principal_key`, which is the SHA-256 of the account name or of the fingerprint sent in its place. Distinct OpenLDAP users (distinct fingerprints) therefore get distinct incidents.
   - **Unidentified principals** (an account the source cannot name: an OpenLDAP SASL bind, a MySQL `performance_schema` statement whose session ended) are sent by the agent as the fingerprint of an empty name. The console cannot recognize that fingerprint (the key is agent-local, contract `Fingerprint`) and does not need to: all unidentified events of one agent carry the same fingerprint, so keyed by it they form one group per policy, agent, target, database and hour. Unlike today, that group is no longer split by client network.
   - Random names are still bounded: they come from failed logins (coarse), and any remaining spread is bounded by the per-target hourly cap and overflow incident of ADR-0021 decision 8.
2. **A clearly worse event after a false positive (refines ADR-0021 decision 7).** A later event of the key of a false-positive incident, in the same hour, opens a new incident (`reopened_from` set to the false-positive incident) when it is **clearly worse**: it carries a `signature.*` signal the false-positive incident did not have, or its score is higher than the incident's highest score. Optionally, an event is also clearly worse when the rows linked to the false-positive incident since it was marked, this event included, exceed the incident's own row total (`eventRows`), so a large read split into many small events within the hour still opens an incident. Otherwise it is only linked to it, as today. The rule applies to false-positive overflow incidents (ADR-0021 decision 8) as well. Being above the baseline or a new `shape.*` / `volume.*` signal alone does not count here (they do after a *resolved* incident, decision 7 unchanged). The hourly cap and its severe-event bypass apply to that new incident as to any other.
3. **Alert on a stopped Audit stream (adds to ADR-0017 decision 5).** When a heartbeat reports a target with the note `audit.stream_stopped`, the console records a `security_events` row `agent.audit_stream_stopped` (medium), an audit entry (system) and notifies the `system_alerts` channels, **at most once per agent and hour**, following the `agent.batches_dropped` pattern (conditional update on an "alerted at" column; stops seen within the hour are counted in the next alert, raised by the next heartbeat or by the worker). The alert is **raised again every hour while the stream stays stopped**, so a stop is not forgotten after the first notification. The row carries console ids, the count of targets and the note's `count` only; no text written by the agent. Optionally, the same mechanism may alert on a rise of the agent's `connector_panics_total` metric (panics that did not stop a stream), under its own event id and the same hourly bound; this part is not required for v0.1.0.
4. **Object order on OpenLDAP events (clarifies ADR-0029 decision 7).** "At most 16, sorted" means: the first 16 matching objects **in the order of the console's `sensitive_objects`**: the operator's manual objects first, then the derived objects most-sensitive first. The agent does not re-sort them by name. This keeps the most sensitive objects when the list is cut, and it is what the code does.
5. **Residual risks recorded until implemented.** M1 and M2 remain residual risks in [05-security.md](../05-security.md#openldap-connector) and [08-engine-capabilities.md](../08-engine-capabilities.md#known-limits-3) until decisions 1 to 3 are implemented. Decisions 1 and 3 are **v0.1.0 release gates** (ROADMAP phase 7). Until then, operators should list the application and service DNs that read the directory in `openldap.clear_principals`, so those principals are keyed by name. Also recorded:
   - **L3, CSN floor after a restart**: a restarted OpenLDAP stream skips every record whose CSN is at or below the persisted cursor (the floor). A record committed out of CSN order, with a CSN below the cursor but written to the log after the cursor was saved, is lost. The 10 s overlap covers this within a run only.
   - **A record that always panics** (review L1 of the documentation update): until decision 6 is implemented, reconfiguring Audit or restarting the agent retries from the persisted cursor, and the stream stops again.
   - **L4, container names**: the normalized container (`schema`) keeps `ou`, `o`, `dc`, `c`, `l` and `st` values that do not look like data; a container named after a person or a customer that the normalization does not recognize reaches the console.
6. **Skip a record that always panics.** After repeated panics (3 in a row) at the same persisted cursor position, the stream skips that record or search round instead of stopping on it for good: the cursor moves past it, the skip is counted (`audit.records_dropped` or a dedicated skipped counter) and reported to the console, and the alert of decision 3 reports it. The exact threshold and counter are those of the implementation (branch `fix/p7-agent-followups`, in progress). Skipping loses the events of that record or round; this is preferred to a target whose Audit stays stopped until an operator acts, since operator action alone does not get past the record (Context).

## Consequences
- OpenLDAP incidents become per user (per fingerprint). The real bound on the number of incidents is the per-target hourly cap and its overflow incident (ADR-0021 decision 8), not the principal key. Per-user keys reach the cap sooner: a noisy insider with several accounts can push other users' **non-severe** events of that target and hour into the overflow incident; severe events (`signature.*`, above the baseline, a score above the overflow incident's highest) still open their own incident. MySQL / MariaDB already key anonymous accounts per name, with the same exposure.
- Unidentified principals of one agent share one group across client networks: one false positive on them covers all unidentified events of that policy, database and hour, unless a later one is clearly worse (decision 2).
- A false positive no longer hides a later `pg_dump`, `mysqldump`, `mongodump` or a higher-scoring read of the same key within the hour, on every engine, **unless the false positive already carried that signature**.
- Decision 2 is judged per event: a large read split into many small events within the hour, each scoring below the false positive, stays linked to it unless the optional row-total rule is implemented (it is being implemented on the console branch). Without it, this is a residual risk.
- The dedup key of existing open incidents changes for fingerprinted non-`auth_failure` events: events after the upgrade may open a new incident where they would have joined an older one within the same hour. This is accepted: it happens at most once per key.
- A stopped Audit stream is visible to the operators who receive system alerts, on every engine, every hour while it stays stopped. Stream restarts that do not reach 3 panics stay silent unless the optional panic-count alert is implemented.
- `console-engineer` implements decisions 1 to 3; the contract is unchanged (the `Principal` description is only made precise about LDAP fingerprints). No agent change is needed for decisions 1 to 4; `agent-engineer` implements decision 6.

## Rejected alternatives
- **An agent-side flag for unidentified principals** (a contract field telling the console the fingerprint is of an empty name): a protocol change for a group the fingerprint already forms by itself.
- **Keep the coarse key and rely on `clear_principals`**: operators would have to list every user DN to get per-user incidents, which defeats the fingerprinting of ADR-0029.
- **Open a new incident for any worse event after a false positive** (the resolved rule): a false positive would stop being useful for routine activity above the baseline.
- **Restart a stopped stream automatically after a delay**: a panic that repeats on the same record would loop, since the stream resumes from the same cursor. Decision 6 skips the record instead, and the alert makes it visible.
- **Rely on operator action (reconfigure or restart) to get past the record**: it does not, since the cursor file is kept and the stream resumes from it.
- **Raise the stop as an incident**: incidents come from policies on findings and access events; agent health goes through `security_events` and `system_alerts` (ADR-0017 decision 5).
