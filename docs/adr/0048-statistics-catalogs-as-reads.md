# ADR-0048: PostgreSQL and MySQL / MariaDB Audit report reads of the statistics catalogs that hold column values

- **Status**: Proposed
- **Date**: 2026-10-10
- **Refines**: for MySQL / MariaDB, [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md) (which stays Accepted), decision 4 (what the statement analysis takes from a text) and decision 6 (the agent's own account), as already refined by [ADR-0027](0027-mongodb-audit.md) decision 7, [ADR-0045](0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) and [ADR-0047](0047-mysql-mariadb-explain-as-a-read.md); for PostgreSQL, the catalog rule of the Audit connector (P4-A, #58, #65), which no ADR records and which [08-engine-capabilities.md](../08-engine-capabilities.md#postgresql-audit) describes. Levels and sources are unchanged on both engines. [ADR-0012](0012-postgresql-agent-grants.md) obligation 1 (the connector never reads these catalogs) is unchanged.
- **Context references**: security review of #197, finding M1; ROADMAP [phase 8 follow-ups](../ROADMAP.md#phase-8-follow-ups); [08-engine-capabilities.md, PostgreSQL Audit, Known limits](../08-engine-capabilities.md#known-limits) and [MySQL / MariaDB Audit, Known limits](../08-engine-capabilities.md#known-limits-1) ("Statistics catalogs hold values", "Statistics tables hold values"); `agent/crates/connector-postgres/src/audit/events.rs` (`is_catalog`, `CatalogRule`, the pgaudit catalog-only skip, the `pg_stat_statements` event builder), `agent/crates/connector-postgres/src/sql.rs` (`no_statement_touches_the_catalog_denylist`), `agent/crates/connector-postgres/src/check.rs` (`AuditProbe::pgaudit_log_catalog`); `agent/crates/connector-mysql/src/audit/events.rs` (`is_system_schema`, `is_internal_table`, `is_system_relation`, `STATEMENT_TEXT_TABLES`); `agent/crates/classifiers/src/masking.rs` (`MaskedEvent::always_report`); `agent/crates/core/src/audit.rs` (`reportable`)

## Context

### What the agent does today

Read from the code at `586e9f5` (`dev`):

- **PostgreSQL.** A relation in `pg_catalog`, `information_schema`, `pg_toast` or a temporary schema is a catalog (`is_catalog`). A read whose relations are all catalogs produces no event, on both sources: with pgaudit, the part is marked `catalog_only` and skipped; with `pg_stat_statements`, a statement that names relations but none outside the catalogs returns no event. An unqualified `pg_*` name counts as a catalog, except with pgaudit and `pgaudit.log_catalog = off`, where pgaudit must name it in `pg_catalog` for the same statement. This applies to every account.
- **MySQL / MariaDB.** Objects in `information_schema`, `performance_schema` and `sys` are dropped from the objects of reads (`is_system_schema`), and so are the internal statistics tables `mysql.table_stats`, `column_stats`, `index_stats`, `innodb_table_stats` and `innodb_index_stats` (`is_internal_table`), from the text and from table records alike. A read left with no object produces no event. The exception is the statement-text tables of ADR-0045. Writes to all of these are reported (#168).
- **The agent itself.** The PostgreSQL connector never sends a statement that names `pg_statistic*` or `pg_stats*`: ADR-0012 obligation 1, checked by the unit test `no_statement_touches_the_catalog_denylist` over every statement of `sql.rs`. The MySQL / MariaDB connector names neither `COLUMN_STATISTICS` nor a `mysql.*_stats` table in any statement (`sql.rs`). The MongoDB and OpenLDAP connectors have no equivalent catalog (below).

The security review of #197 (M1) found that some of these catalogs hold column values in clear, so a read of them is a read of personal data that no source reports, for any account.

### What the servers do (verified on 2026-10-10)

Throwaway containers from the pinned images: PostgreSQL 17.11 (`dev/docker-compose.yml`, without pgaudit, see below), MySQL 8.0.46, 8.4.11 and 9.7.2, Percona Server 8.4.11-11 with the `audit_log_filter` component in JSON, MariaDB 10.11.19, 11.4.13 and 11.8.9. Tables of fake e-mail addresses, IBANs and cities, as in the dev seed. Accounts: `app` with `SELECT` on the table, `other` with no privilege on it, a column-only account with `SELECT (id, city)`, and, on PostgreSQL, a table owner, a `pg_read_all_data` member and a `pg_read_all_stats` + `pg_monitor` member.

**PostgreSQL 17.11.**

| Catalog | What it holds | Who reads values |
|---|---|---|
| `pg_stats` (view) | `most_common_vals` (up to the statistics target, 100 by default, for low-cardinality columns: every city), `histogram_bounds` (101 raw values for unique columns: e-mail addresses and IBANs in clear), `most_common_elems` | **Any account with `SELECT` on the column** (`has_column_privilege`): `app` saw every column, the column-only account only `id` and `city`, `other` nothing. A table with row-level security active for the reader is hidden. Materialized views and partitioned tables (`inherited = true`) are listed too; statistics of expression indexes are not (no column privilege on an index) |
| `pg_stats_ext` (view) | `most_common_vals` of `CREATE STATISTICS … (mcv)` objects: value combinations (`{o0@example.org,C0}`) | **The table owner only** (`pg_has_role(relowner, 'USAGE')`); `app`, `pg_read_all_data` and `pg_read_all_stats` saw no row |
| `pg_stats_ext_exprs` (view) | `most_common_vals`, `histogram_bounds` of statistics on expressions (`lower(email)`) | The table owner only |
| `pg_statistic` (table) | `stavalues1` to `stavalues5`: the raw values behind `pg_stats`, every column and expression index | Superusers and **`pg_read_all_data`** (verified: also the statistics of a table whose row-level security hid all but 2 rows from that account, so `pg_read_all_data` reads values past RLS through it); denied to `app`, owners and `pg_read_all_stats` |
| `pg_statistic_ext_data` (table) | `stxdmcv` (`pg_mcv_list`, decoded with `pg_mcv_list_items()`: `{o0@example.org,C0}`), `stxdexpr` | Superusers and `pg_read_all_data`; denied to the others |

**When they are filled.** Autovacuum's auto-analyze filled `pg_stats` with no explicit command once the table passed its threshold (50 rows plus 10 % by default: nothing after 40 rows, histograms 6 s after 1 000 more rows with `autovacuum_naptime = 1`); `ANALYZE` fills them at once. Extended statistics exist only after `CREATE STATISTICS`. On a live database the statistics are therefore always present, and they follow the data.

**MySQL 8.0.46, 8.4.11, 9.7.2 and Percona 8.4.11-11.** `information_schema.COLUMN_STATISTICS` (`SCHEMA_NAME`, `TABLE_NAME`, `COLUMN_NAME`, `HISTOGRAM` JSON) is empty until `ANALYZE TABLE … UPDATE HISTOGRAM ON … [WITH n BUCKETS]`; a plain `ANALYZE TABLE` creates none. Singleton histograms list every distinct value (`["base64:type254:TGlsbGU=", 0.334]`, that is `Lille`); equi-height histograms give the lower and upper value of each bucket. String values are base64-encoded with their type (`base64:type254:dXNlcjFAZXhhbXBsZS5vcmc=` is `user1@example.org`), numbers are in clear. On 8.4, a histogram created with `AUTO UPDATE` was rebuilt after 300 inserts without a command (`last-updated` changed). **Visibility is per table, not per column**: on the three MySQL series, the column-only account (`SELECT (id)`), an account with `INSERT` only on the table, and one with `UPDATE (city)` only, all read the histograms of every column of the table, including columns they cannot `SELECT` (error 1143). The data dictionary table behind it, `mysql.column_statistics`, is refused to every account, root included (error 3554).

**MariaDB 10.11.19, 11.4.13, 11.8.9.** `mysql.column_stats` holds `min_value` and `max_value` in clear on every series (`123-45-6789` / `987-65-4321` for a two-row SSN column), and a histogram whose type follows `histogram_type`: `JSON_HB` (the default on 11.4 and 11.8) keeps raw bucket start values (`"start": "user1@example.org"`), `DOUBLE_PREC_HB` (the default on 10.11) keeps positions between the minimum and the maximum. It is filled by `ANALYZE TABLE … PERSISTENT FOR …`, or by a plain `ANALYZE TABLE` when `use_stat_tables` is `PREFERABLY` or `COMPLEMENTARY` (verified with a session setting); the default on the three series is `PREFERABLY_FOR_QUERIES`, where a plain `ANALYZE TABLE` collects nothing. Reading it needs `SELECT` on `mysql.column_stats` (`app` got error 1142). `mysql.table_stats` (`cardinality`) and `mysql.index_stats` (`avg_frequency`) hold numbers only. MariaDB has no `information_schema.COLUMN_STATISTICS`; its `TABLE_STATISTICS`, `INDEX_STATISTICS`, `USER_STATISTICS` and `CLIENT_STATISTICS` are counters.

### What the audit sources record

| Source | A read of a statistics catalog | Verified on |
|---|---|---|
| `pg_stat_statements` | One entry per normalized text, under the reader's role, with literals as `$n`: `SELECT histogram_bounds FROM pg_stats WHERE schemaname = $1 AND tablename = $2 AND attname = $3`; `TABLE pg_stats` with 399 rows (the catalog lists the statistics of `pg_catalog`'s own tables too) | PostgreSQL 17.11 |
| pgaudit, `pgaudit.log_catalog = on` (the default) | A `READ` record with the statement text; with `pgaudit.log_relation`, a record naming `pg_catalog.pg_stats` | **Not run**: the pgaudit packages and sources could not be fetched here (the egress proxy refused `apt.postgresql.org` and GitHub). From pgaudit's documentation and the agent's own handling (`events.rs`, `confirmed` names); whether the view's base `pg_catalog.pg_statistic` gets its own relation record is to verify |
| pgaudit, `pgaudit.log_catalog = off` | **No record** for a statement whose relations are all in `pg_catalog`; a statement that also reads an application table is logged, and its relation records leave out the `pg_catalog` relations | Same: from pgaudit's documentation, not run |
| `performance_schema` digests | `` SELECT COLUMN_NAME , `min_value` , `max_value` FROM `mysql` . `column_stats` WHERE TABLE_NAME = ? ``; on MySQL, `` … FROM `information_schema` . `COLUMN_STATISTICS` WHERE SCHEMA_NAME = ? AND TABLE_NAME = ? `` with the literal text in `QUERY_SAMPLE_TEXT`. The catalog is named; the table it describes is a `?` | MySQL 8.4.11, MariaDB 11.4.13 |
| MariaDB `server_audit`, `QUERY` + `TABLE` | The `QUERY` record with the literal text and a `READ,mysql,column_stats` table record. **Also**, after `FLUSH TABLES` (or any first open of a table), a plain `SELECT … FROM hr.customers` by `app` wrote `READ,mysql,table_stats`, `READ,mysql,column_stats` and `READ,mysql,index_stats` records under `app`'s account: the server loading its own statistics | MariaDB 11.4.13 |
| Percona `audit_log_filter`, JSON | A `general` `status` record with `sql_command` `select` and the full text; **no `table_access` record** for `information_schema.COLUMN_STATISTICS` | Percona 8.4.11-11 |

So on every source the statement text (or its digest) names the catalog; MariaDB table records name it too, but also for the server's internal loads, which no statement asked for.

### Who reads these catalogs routinely

From the tools' documentation and common practice, not measured here:

- **Bloat estimates.** The usual PostgreSQL table and index bloat queries (check_postgres `bloat`, pgwatch's bloat metrics, the widely copied ioguix queries) read `pg_stats.avg_width` and `null_frac` on a schedule: no value column, but the relation is `pg_stats`.
- **Monitoring and tuning tools.** pganalyze collects column statistics through its helper function (`pganalyze.get_column_stats()`, per its documentation without the value columns; to verify); index advisors (Dexter, PoWA with HypoPG) read `n_distinct` and related columns; pgAdmin shows a column's `pg_stats` row, values included, on demand. Prometheus `postgres_exporter` and PMM do not read `pg_stats` with their default collectors.
- **Dumps.** `mysqldump` 8.0 and later with `--column-statistics` reads `COLUMN_STATISTICS` (column names and bucket counts) for each dumped table; `mariadb-dump` dumps `mysql.column_stats` when asked for system tables (`--system=stats`, `all`).
- **Query planners and ORMs** do not read them through SQL: the planner and optimizer use the statistics internally (PostgreSQL's syscache; MariaDB's loads, which `server_audit` shows as table records, above). ORMs and drivers read the dictionary (`information_schema.COLUMNS`, `pg_attribute`), not the statistics.

Readers are therefore mostly a few monitoring accounts on a schedule, plus DBAs on demand.

### Other engines and catalogs

- **PostgreSQL**: no other catalog with column values was found. The `pg_stat_*` views hold counters, except `pg_stat_activity.query` and `pg_stat_statements` utility texts, which hold statement texts (ADR-0012's grants table); that is the PostgreSQL counterpart of ADR-0045, outside this ADR (open question 8).
- **MySQL / MariaDB**: `mysql.innodb_table_stats` and `innodb_index_stats` hold counts and column names, and `information_schema.STATISTICS` is index metadata; none holds a value.
- **MongoDB** keeps no persisted value statistics (no histograms; `$collStats` and `$indexStats` are counters). Its query-shape stores (`$planCacheStats`, `config.sampledQueries` for shard key analysis) are statement-text counterparts, not checked here.
- **OpenLDAP** `cn=monitor` holds counters and connection data, not attribute values (not checked on a server).
- **Apereo CAS**: not applicable (files only).

## Options

- **(a) A closed list of value-bearing statistics relations**, named as objects in read events, always reported and never the agent's own, as ADR-0045 does for statement-text tables.
- **(b) The same, but naming the base table** the statistics describe, taken from the statement's `WHERE` (`pg_stats.tablename = 'customer'`, `COLUMN_STATISTICS.TABLE_NAME = …`, `column_stats.table_name = …`).
- **(c) A signal** (for example `shape.statistics_read`) on events that read these catalogs.
- **(d) Document only** (the current state).

(b) does not hold. `pg_stat_statements` and the `performance_schema` digests replace the table name by `$n` / `?` (verified), clients with bound parameters do the same on every source, and a reader does not need a `WHERE` at all (`TABLE pg_stats`, a join on `starelid = 'crm.customer'::regclass`, `LIKE 'cust%'`). Worse for I2: a literal from the text would become an object name, and the text is untrusted: `WHERE tablename = 'alice@example.org'` would send a value to the console as a table name. (c) is a protocol change (`signals.json`, [ADR-0022](0022-protocol-capability-negotiation.md)) and still needs the catalog named as an object for policies and baselines to see it; with (a) the object already says it. (d) leaves values of every analyzed column readable with no event, by any account that can `SELECT` the column (PostgreSQL), that has any privilege on the table (MySQL), or that can read the `mysql` schema (MariaDB).

## Decision: option (a)

1. **The value-bearing statistics relations.** Reads of these relations keep their objects, named as listed:

   | Engine | Relation | Value columns | Readable by (verified) |
   |---|---|---|---|
   | PostgreSQL | `pg_catalog.pg_stats` | `most_common_vals`, `histogram_bounds`, `most_common_elems` | `SELECT` on the column |
   | PostgreSQL | `pg_catalog.pg_stats_ext` | `most_common_vals` | the table owner |
   | PostgreSQL | `pg_catalog.pg_stats_ext_exprs` | `most_common_vals`, `histogram_bounds`, `most_common_elems` | the table owner |
   | PostgreSQL | `pg_catalog.pg_statistic` | `stavalues1` to `stavalues5` | superuser, `pg_read_all_data` |
   | PostgreSQL | `pg_catalog.pg_statistic_ext_data` | `stxdmcv`, `stxdexpr` | superuser, `pg_read_all_data` |
   | MySQL, Percona | `information_schema.COLUMN_STATISTICS` | `HISTOGRAM` | any privilege on the table |
   | MariaDB | `mysql.column_stats` | `min_value`, `max_value`, `histogram` | `SELECT` on it (`mysql.*`, global `SELECT`) |

   Not listed: `mysql.table_stats`, `mysql.index_stats`, `mysql.innodb_table_stats`, `mysql.innodb_index_stats`, `information_schema.STATISTICS` and the counter views (no value), and `mysql.column_statistics` (refused to every account). As in ADR-0045, a table one flavor lacks is still listed for both MySQL and MariaDB, because the flavor comes from a version string a proxy can rewrite. Names are compared ASCII-case-insensitively on MySQL / MariaDB, and after the analyzer's identifier folding on PostgreSQL (a quoted `"PG_STATS"` is another relation).
2. **Recognized from the text, and from pgaudit's names.**
   - **PostgreSQL.** A listed relation named by the text, qualified with `pg_catalog` or unqualified, or named by a pgaudit relation record in `pg_catalog`, is kept as an object instead of counting as a catalog. An unqualified listed name is reported as `pg_catalog.<name>` (`pg_catalog` comes first in the search path unless a session lists it explicitly later; a relation shadowing it is over-reported, never missed). A read of a listed relation is a read event even when every other relation of the statement is a catalog. The rest of the catalog rule is unchanged.
   - **MySQL / MariaDB.** A listed relation named by the text (resolved in the current database when unqualified, as today) is kept as an object, like a statement-text table. A MariaDB `server_audit` table record of `mysql.column_stats` is **not** enough on its own: the server writes one under the reader's account each time it loads a table's statistics (verified), so a record whose statement text does not name a listed relation stays dropped, as today. Percona's `audit_log_filter` writes no table record for `information_schema` (verified), so the text decides there too. The rules for texts that cannot be read, cut texts and table records without a statement record (ADR-0045, refinement of decision 11) are unchanged: they already add `*`.
3. **Always reported.** A read event that names a listed relation carries the agent-internal always-reported mark (`MaskedEvent::always_report`), so the `audit.configure` filter (`min_rows`, `sensitive_objects`) never drops it. One row of `pg_stats` can hold 101 values, the file sources have no row count, and a `min_rows` setting would otherwise drop exactly these reads. The row count, when the source has one, is kept: it counts statistics rows, which is what was read. No signal is added.
4. **The agent's own account.** A read naming a listed relation with the agent's identity is **never** left out as its own and never charged to the per-object budget: the agent sends no such statement. The PostgreSQL unit test `no_statement_touches_the_catalog_denylist` already proves it for `sql.rs`; the MySQL / MariaDB every-agent-statement test is extended to the listed names. The internal statistics loads that MariaDB records under the agent's account during Discovery sampling stay dropped (decision 2), so the agent's own scans give no new event.
5. **`pgaudit.log_catalog`.** With `pgaudit.log_catalog = off`, pgaudit writes no record for a statement whose relations are all in `pg_catalog`, so a read of `pg_stats` alone is invisible on that source; a statement that also reads an application table is logged and reported with the listed relation (decision 2).
   - **Documentation**: [10-user-guide.md](../10-user-guide.md) recommends keeping `pgaudit.log_catalog = on` (the pgaudit default) on monitored databases. [08-engine-capabilities.md](../08-engine-capabilities.md#known-limits) stops offering `log_catalog = off` as a way to close the "shadowing an unqualified catalog name" residual: `pgaudit.log_relation = on` closes it and keeps statistics reads visible.
   - **`check()`**: the probe already reads `pgaudit.log_catalog` (`AuditProbe::pgaudit_log_catalog`). When it is proven off in a monitored database while pgaudit is the source, `check()` says so in the agent's local detail (which names the setting and the database). The level is unchanged: Full and Partial describe row counts and the read class (ADR-0037), and statistics reads are one kind of read among others that a pgaudit configuration can leave out (`pgaudit.log` classes, per-role settings).
   - **No target note.** None of the registered codes fits: `audit.pgaudit_read_class_missing` is about the `read` class of `pgaudit.log` and would misstate the cause, and the others concern loading, the log file and row counts. A new code would be an addition to `shared/protocol/target-notes.json` with its console phrase and a security review; this ADR does not make it (open question 5).
6. **I2.** Only names leave the agent: the fixed names of decision 1, through the existing normalization ([ADR-0009](0009-name-normalization-and-item-sanitization.md)). The agent reads no statistics value, takes no name from a literal (option (b) rejected), and keeps no statement text beyond what it keeps today. The `AccessEvent` contract is unchanged: no new field, signal or note.

## Consequences

- **Code** (`agent-engineer`, `security-reviewer` review):
  - `connector-postgres/src/audit/events.rs`: a `STATISTICS_RELATIONS` list; `is_catalog` false for a listed relation in `pg_catalog` or unqualified; the pgaudit and `pg_stat_statements` builders name it as `pg_catalog.<name>`, mark the event always reported, and never leave it out as the agent's own (`own_text`, budget); `check.rs`: the local detail of decision 5.
  - `connector-mysql/src/audit/events.rs`: a `STATISTICS_TABLES` list beside `STATEMENT_TEXT_TABLES`; the text path keeps listed names as it keeps statement-text tables; the table-record path keeps dropping internal statistics records whose text does not name them; the always-reported mark; never the agent's own.

  No `shared/protocol/` change.
- **Tests**:
  - unit tests on every source (pgaudit with and without `log_relation`, with `log_catalog` on and off; `pg_stat_statements`; `server_audit` with and without `TABLE` records; `audit_log` / `audit_log_filter` JSON; `performance_schema` full text and digest): each listed relation, qualified, unqualified, in a join with an application table, in a subquery, with `TABLE pg_stats`, reported, always reported with `min_rows` set, never charged to the agent; a quoted `"PG_STATS"` and a `public.pg_stats` read through a qualified name are not listed relations; a MariaDB `SELECT` on an application table with internal `READ,mysql,column_stats` records gives the application table only; dictionary reads (`pg_attribute`, `information_schema.COLUMNS`, `mysql.table_stats`) stay quiet.
  - integration tests: PostgreSQL 17 with pgaudit (`log_catalog = on` for the test database) and with `pg_stat_statements`, a second role reads `pg_stats` and gets a read event naming `pg_catalog.pg_stats`; MySQL 8.4 and MariaDB 11.4 (`performance_schema` and `server_audit`) and Percona 8.4 (`audit_log_filter`), a second account reads `COLUMN_STATISTICS` / `mysql.column_stats` and gets a read event naming it; on MariaDB, `FLUSH TABLES` then a read of an application table gives no statistics object; the agent's own scans give none on any source. The dev environment sets `pgaudit.log_catalog=off` (`dev/docker-compose.yml`, `dev/postgres/local-cluster.sh`): the test sets it on for its database, or the dev setting changes (open question 6; `dev/` is owned by `agent-engineer`).
  - **Drift tests** (engine matrix, every image): on PostgreSQL, every `pg_catalog` relation with a column of type `anyarray`, `pg_mcv_list` or `pg_statistic[]`, or a column named `most_common_vals`, `histogram_bounds` or `most_common_elems`, must be listed; on MySQL / MariaDB, every relation of `information_schema`, `performance_schema`, `sys` and `mysql` with a column named `HISTOGRAM`, `min_value` or `max_value` must be listed or on a commented exception list. The pinning facts above (who reads values, base64 encoding, the MariaDB internal records) get one assertion each, so that a server change is seen.
  - **Load harness** (`e2e/load/`): a monitoring-like account running a bloat query on `pg_stats` every 10 s, and on MariaDB a `mysql.column_stats` reader; the run must show at most one event per principal, object set and aggregation window, Audit events still equal to the application statements, and no change in agent CPU and memory beyond noise.
- **Noise.** Events now come from accounts that read these catalogs: scheduled bloat checks and monitoring helpers, `mysqldump --column-statistics`, and DBAs on demand. Aggregation bounds each to one event per principal, object set, action and source per `aggregation_window_s` (default 60 s), under the console's per-target hourly cap ([ADR-0021](0021-access-event-correlation.md)): a bloat check every minute on one target is at most 1 440 events per day. As in ADR-0045 (open question 2) and ADR-0047 (open question 5), there is no agent-side allow-list; the console can scope or exclude principals.
- **Documentation** (`docs-keeper`, after the implementation): in [08-engine-capabilities.md](../08-engine-capabilities.md), the two known limits become described behaviour (the list, the always-reported mark, the MariaDB internal records, the noise note), and the shadowing residual's `log_catalog = off` advice is replaced (decision 5); [10-user-guide.md](../10-user-guide.md) recommends `pgaudit.log_catalog = on` and gives a sample policy on the statistics relations; [05-security.md](../05-security.md#recommended-database-accounts-read-only) notes the MySQL per-table visibility of `COLUMN_STATISTICS` and that `pg_read_all_data` reads `pg_statistic`, past row-level security.
- **Estimated size.** About 150 lines of production code (80 PostgreSQL, 70 MySQL / MariaDB), 450 lines of unit tests, 200 lines of integration tests, the two drift tests and the load scenario; 2 days with one review round. PostgreSQL and MySQL / MariaDB are independent and can be two PRs.
- **Residual risks.**
  - With pgaudit and `pgaudit.log_catalog = off`, a statement that reads only catalogs is not logged, so a read of `pg_stats` alone gives no event (decision 5).
  - A read through a user view, a function or a procedure over a listed relation is named by what the statement shows (the view, or `*` for a function call), not by the listed relation. With `pg_stat_statements.track = top` (the default), the body of a function is not recorded at all.
  - The event names the catalog, not the table it describes: a policy cannot tell a read of the statistics of `crm.customer` from those of another table.
  - The values are a sample, but a large one: up to the statistics target per column (100 by default, up to 10 000 when raised with `ALTER TABLE … SET STATISTICS`), up to 1 024 buckets on MySQL, 254 by default on MariaDB `JSON_HB`, and every distinct value of low-cardinality columns.
  - Server-side exposure that no audit rule changes: on MySQL, any privilege on a table shows the histograms of all its columns, including columns the account cannot `SELECT`; on PostgreSQL, `pg_read_all_data` reads `pg_statistic` past row-level security. The events show who read the catalog; the remedy is in the grants and in which columns get histograms (documentation).
  - Selectivity estimates (PostgreSQL `EXPLAIN` row estimates, MySQL `filtered`) answer value guesses from the same statistics without reading a listed relation; this ADR does not cover them.
  - pgaudit behaviour (decision 5, the relation records) was not run here; the integration test confirms it before the implementation is merged.

## Rejected alternatives

- **Option (b)**, naming the base table from the `WHERE`: the table name is `$n` / `?` on `pg_stat_statements`, on `performance_schema` digests and with bound parameters, readers often have no `WHERE` on it, and a literal from untrusted text would leave the agent as an object name (I2).
- **Option (c)**, a signal: a protocol change that adds nothing a named object does not already give policies and baselines.
- **Option (d)**, document only: every analyzed column readable with no event (review M1).
- **Reporting every catalog read** on PostgreSQL, or every system-schema read on MySQL / MariaDB: the noise the catalog rule exists for (drivers, ORMs, `psql`, admin tools), for relations that hold no value.
- **Using MariaDB's `mysql.column_stats` table records alone**: the server writes them for its own statistics loads under the reader's account, so every first read of an analyzed table would become a statistics read.
- **Reporting only reads that name a value column** (`most_common_vals`, `histogram_bounds`, `HISTOGRAM`, `min_value`…), to spare bloat queries: whole-row references (`SELECT s FROM pg_stats s`, `row_to_json(s)`, `TABLE pg_stats`, `*`) read every column without naming one, so a column test fails open (open question 4).
- **Charging the agent's budget** for these reads, as for sampled tables: the agent never reads them, so its budget would only hide reads made with a stolen agent credential.

## Open questions
Each question has the answer this ADR recommends; the maintainer decides.

1. Option (a), a closed list named as objects, as proposed, or (b), (c) or (d)?
   **Recommended answer**: (a). The text names the catalog on every source (verified on all but pgaudit), the base table is not reliably in the text, and taking it from a literal would break I2.
2. PostgreSQL scope: list `pg_statistic` and `pg_statistic_ext_data`, which only superusers and `pg_read_all_data` can read, and `pg_stats_ext` / `pg_stats_ext_exprs`, which only owners can read, or `pg_stats` alone?
   **Recommended answer**: all five. `pg_read_all_data` is a common grant for reporting and backup accounts, and it reads `pg_statistic` past row-level security (verified); owners are application accounts, whose credentials are the ones most often stolen.
3. Always report these reads, whatever `min_rows` and `sensitive_objects` say (decision 3), or let the filter apply?
   **Recommended answer**: always report, as ADR-0045 and ADR-0047 do. One statistics row carries up to the statistics target's number of values, and the file sources have no row count, so a `min_rows` setting would drop them silently.
4. Noise: report every read of a listed relation, or only those that name a value column (sparing bloat queries that read `avg_width` and `null_frac`)?
   **Recommended answer**: every read. Whole-row references read every column without naming one, so a column test fails open; aggregation bounds a scheduled bloat check to one event per window, and the console can exclude its principal.
5. `pgaudit.log_catalog = off`: a new target note (for example `audit.pgaudit_catalog_not_logged`), or the agent's local detail and documentation only (decision 5)?
   **Recommended answer**: local detail and documentation only in this ADR, no protocol change. No existing code fits, the setting's default is on, and the gap is one more choice of what pgaudit logs, like its classes, which have no note beyond the `read` class. Revisit if users run with `log_catalog = off` and the console needs to show it.
6. The dev environment and the end-to-end harness run pgaudit with `log_catalog=off`: switch them to on (the recommended configuration), or set it per test database?
   **Recommended answer**: switch the dev and end-to-end configuration to on, so that they run what the documentation recommends; keep the existing unit tests of the `log_catalog = off` rule for unqualified `pg_*` names. The load run shows the cost in pgaudit log volume.
7. MariaDB: ignore `server_audit` table records of `mysql.column_stats` unless the text names a listed relation (decision 2), or report them?
   **Recommended answer**: ignore them. The server writes them under the reader's account whenever it loads a table's statistics (verified after `FLUSH TABLES`), so reporting them would turn ordinary reads into statistics reads; the statement text names the relation whenever a client reads it.
8. PostgreSQL statement-text views (`pg_stat_activity.query`, the utility texts of `pg_stat_statements`), which hold other sessions' literals and are catalog reads today: in this ADR, or a separate follow-up modelled on ADR-0045?
   **Recommended answer**: a separate ROADMAP follow-up with its own ADR. Their readers (`pg_read_all_stats`, `pg_monitor`, the agent's own `pg_stat_statements` source) and the agent's own polls need their own own-account rule, as ADR-0045 decision 4 did on MySQL / MariaDB.
9. MySQL's per-table visibility of `COLUMN_STATISTICS` (any privilege on a table shows every column's histogram): a `check()` note, or documentation only?
   **Recommended answer**: documentation only, in 05-security. It concerns other accounts' grants, which the agent's minimal account cannot read, and the remedy (no histograms on sensitive columns, or no partial grants on their tables) belongs to the operator.
