# ADR-0040: Prevention mode scope: response in Community, data-path prevention in Enterprise

- **Status**: Accepted
- **Date**: 2026-10-04
- **Decided by**: decided on delegation from the maintainer (2026-10-04)
- **Context references**: ROADMAP phase 12; security review (M1, L1, L2); [EDITIONS.md](../EDITIONS.md); [ADR-0005](0005-open-core-license.md) (open core, I7); [ADR-0017](0017-alerting.md) (alerting, signed webhooks); invariant I4

## Context
The project summary planned a "real-time Prevention mode" for after the MVP ([01-overview.md](../01-overview.md), [02-architecture.md](../02-architecture.md): "proxy or hooks to block certain operations"), and the former "After the MVP" table of the ROADMAP listed "Prevention mode (proxy)" next to Helm and mTLS. [EDITIONS.md](../EDITIONS.md) puts "Advanced Prevention mode (proxy, blocking)" in the Enterprise edition, which lives in a separate private repository with no code in this one (I7, [ADR-0005](0005-open-core-license.md)). The two documents disagreed on where prevention belongs, and nothing defined what part of it, if any, is Community.

Two invariants frame the answer:
- **I4**: the agent only reads, with a dedicated least-privilege account. Killing a session, revoking a grant or rewriting a query are writes to the target.
- **I7**: no Enterprise code in this repository, including interfaces that only an Enterprise build would use.

The console already notifies incidents through e-mail and HMAC-signed webhooks ([ADR-0017](0017-alerting.md)); the webhook body is JSON with `"version": 1` and the events `incident.opened` and the system alerts.

## Decision
1. **Community (this repository) offers detection-side response only, never in the data path.**
   - **Recommended actions** attached to incidents: generated by the console from the incident and the target's facts (for example "revoke role X from account Y", "rotate the credentials of account Y", "enable `pgaudit.log_rows`"), shown in the console and included in notifications, **never executed by DataBastion**. A recommended action is a closed `action` id (from a registry in the repository) with typed parameters (account, role, object, engine), never executable command text: notifications and webhook payloads carry the id and the parameters only. A human-readable command is rendered only in the console UI, with engine-specific identifier quoting, and labeled as advice to review before running. Parameters are built from normalized names and the target's facts, never from engine text or sampled values (I2), and are data that receivers must escape.
   - **Response hooks**: the existing signed webhooks, with a documented and versioned incident payload (a JSON Schema in the repository, the `version` field kept; additions are optional fields, any other change bumps the version), so that external tooling (a SOAR, a script, a ticketing system) can act on its own credentials and responsibility. The payload never carries masked samples, value fingerprints or engine text: it carries ids, classifier ids, normalized location names, counts and principals (fingerprinted where the access-event rules say so). The schema is closed (`additionalProperties: false`) for the console's own contract test; receivers are told to ignore unknown fields, so optional additions do not break them.
   - **No agent action writes to a target.** I4 stays absolute in Community: the agent gets no session-kill, grant-change or blocking capability, behind a flag or otherwise.
2. **Enterprise (separate private repository, not here)**: everything that sits in the data path or changes a target: the blocking or inline proxy, session kill, automatic grant revocation, query rewriting. This repository contains no Enterprise code, no interface stubs that serve only Enterprise, and no "coming soon" toggles for these features.
3. **ROADMAP**: "Prevention mode (proxy)" is removed from the Community roadmap. Phase 12 becomes "Response: recommended actions and response hooks", owned by `console-engineer` with a `security-reviewer` review.

## Consequences
- I4 is unchanged; so are I1 to I3 and I5 to I7.
- The webhook payload becomes a public, versioned interface: its schema is documented and tested, and receivers can validate it.
- Automatic execution of a recommended action by a receiver is the operator's choice and responsibility. Receivers must verify the HMAC signature and deduplicate on the delivery id, and should require human confirmation for any action that changes a target.
- Recommended actions are advice: their quality depends on the target facts the agent already reports (`check()` results, target notes, audit level). Wrong advice cannot harm a database by itself, since nothing runs it.
- [EDITIONS.md](../EDITIONS.md) gets a pointer to this ADR. This clarifies the split; no Community feature moves to Enterprise (allocation rule 3).
- Users who need blocking get it from the Enterprise edition or from their own tooling through the hooks; the Community edition says so plainly rather than promising prevention.

## Rejected alternatives
- **A Community "monitor-only" proxy**: still in the data path, with its latency and availability risk for every query, and it blurs the line with the Enterprise proxy.
- **Agent-side session kill behind a flag**: breaks I4; a compromised console could then act on every database through the agents.
- **Leaving the scope undecided**: the ROADMAP and EDITIONS.md would keep contradicting each other, and Community work could drift into Enterprise scope.
