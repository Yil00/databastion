## Context

Phase 9 adds Microsoft SQL Server, the first engine of [ADR-0039](0039-engine-scope-expansion.md) wave 1. ADR-0039 fixed the frame (ceiling Partial, Full only with proofs; a refusal list of permissions; TDS 8.0 strict or mandatory encryption with full certificate verification; `ENCRYPT_OFF` and NTLM refused; a capability token) and asked this ADR to decide the client, the authentication, the versions, the grants, the Discovery bounds, the Audit source and level, and the protocol additions.

SQL Server differs from the engines already supported in ways that matter to the invariants:

- **The wire protocol** is TDS (MS-TDS, a public Microsoft specification). Before TDS 8.0, TLS is negotiated in clear `PRELOGIN` packets and the TLS handshake itself travels inside TDS packets; with TDS 8.0 "strict" encryption (SQL Server 2022 and later), TLS comes first, with the ALPN value `tds/8.0`, and `PRELOGIN` runs inside it.
- **SQL logins send the password itself.** `LOGIN7` carries the password "obfuscated" (each byte's nibbles swapped then XORed with `0xA5`), which is reversible: whoever terminates the transport reads the password. There is no challenge-response for SQL logins, unlike SCRAM (PostgreSQL, MongoDB) or `caching_sha2_password` (MySQL). Only TLS with a verified certificate protects it.
- **There is no server-side read-only session or transaction mode** for a normal login (as on MongoDB, [ADR-0026](0026-mongodb-connector.md)), and **no server-side statement timeout** a login can set for itself: a query timeout is a client-side deadline followed by an `ATTENTION` packet.
- **User code runs implicitly on reads**: views, computed columns calling scalar functions, row-level security predicates (inline table-valued functions), CLR types. Linked servers, synonyms and external tables (PolyBase) make the server connect to other hosts (I5).
- **SQL Server Audit is permission-check based.** A read through a view or a procedure whose owner also owns the table (ownership chaining) is recorded on the view or procedure, not on the table. Its records carry no row count for SELECT on boxed SQL Server (to verify, decision 6). Reading the audit through `sys.fn_get_audit_file` needs `CONTROL SERVER` before SQL Server 2022, which is on the ADR-0039 refusal list.
- **Targets are remote by default.** Most SQL Server instances run on Windows; a Linux agent reaches them over the network. Local files are only an option for SQL Server on Linux on the agent's host.

## Decision

### 1. TDS client: an own bounded client (option B), no driver crate

The connector `connector-sqlserver` speaks a closed subset of TDS itself, as `connector-mysql` ([ADR-0018](0018-mysql-mariadb-grants-and-connector.md) decision 3), `connector-mongodb` ([ADR-0026](0026-mongodb-connector.md) decision 1) and `connector-openldap` ([ADR-0029](0029-openldap-connector.md)) do.

- **Messages sent**: `PRELOGIN` (version, encryption, `INSTOPT` empty, `THREADID`, `MARS` off; no `FEDAUTHREQUIRED`, no nonce), the TLS handshake (wrapped in `PRELOGIN` packets before TDS 8.0, raw in strict mode), `LOGIN7` (SQL authentication only, decision 2; `AppName` `databastion-agent`; no `FEATUREEXT` at all: no session recovery, no column encryption, no federated authentication, no UTF-8 support, no data classification; `fReadOnlyIntent` **not** set, since it only matters for availability-group read-only routing, which the connector refuses; `ClientID` (the client MAC address field) all zeros; `HostName` empty: the agent's host name is not sent, and no identity rule relies on it, decision 6), `SQLBatch` (one statement per batch, decision 5), `RPC` to `sp_executesql` only (by its well-known procedure id 10, used by the Audit polls so their text stays constant, decision 6), and `ATTENTION`.
- **Tokens parsed** from the server: `LOGINACK`, `ENVCHANGE`, `ERROR`, `INFO`, `COLMETADATA`, `ROW`, `NBCROW`, `DONE` / `DONEPROC` / `DONEINPROC`, `RETURNSTATUS`, `RETURNVALUE` (skipped, bounded), `ORDER` (skipped). Any other token (`FEATUREEXTACK`, `SSPI`, `FEDAUTHINFO`, `TABNAME`, `COLINFO`, `SESSIONSTATE`, `DATACLASSIFICATION`, an unknown byte) ends the connection: a token stream has tokens without a length prefix, so an unknown token cannot be skipped safely.
- **`ENVCHANGE`**: database, language, collation and packet size are read (the packet size is accepted between 512 and 32 767 bytes, otherwise the connection ends); a transaction `ENVCHANGE` (begin, commit, rollback, enlist) ends the connection (the connector never opens a transaction, decision 5); **routing (type 20) ends the connection** and is reported as `unsupported`: the connector never connects to a host named by the server (I5, as MongoDB's replica-set discovery in ADR-0026 decision 2). The database-mirroring partner (type 13) is ignored, never connected to. Unknown `ENVCHANGE` types are skipped by their length.
- **Closed type set.** The connector's statements are written so that every result column has one of a closed set of types: `INTN` (1, 2, 4, 8 bytes), `BITN`, `NVARCHAR` (non-`max`, except the one Extended Events `event_data` column of decision 6; Discovery converts every sampled value to `nvarchar(4000)` on the server, decision 5), `DATETIME2N`, and `BIGVARBIN` non-`max` only if binary columns are sampled (decision 5). Any collation is accepted on `NVARCHAR` (UTF-16 does not depend on it); the collation only matters for single-byte types, which the connector never asks for. `COLMETADATA` with any other type, another `max` length, or a UDT / XML / `sql_variant` type info makes the statement fail and the session be replaced (fail closed). The type-info parser still reads every type info of MS-TDS to locate the column boundaries, so a hostile server cannot desynchronize it, and it is fuzzed.
- **Bounds before allocation**: packet length checked against the negotiated packet size before the packet body is read; a message (sequence of packets up to `EOM`) bounded per statement kind (`LOGINACK` exchange 64 KiB, catalog results by their row limits, sampled values by the byte budget of decision 5); a `B_VARCHAR` / `US_VARCHAR` / `NVARCHAR` length checked against the remaining bytes of the enclosing token; at most 4 096 columns in `COLMETADATA` (the server's own limit for a `SELECT` list), at most the statement's declared column count.
- **Server text is not data.** `ERROR` and `INFO` tokens are reduced to the error number, state and class while parsing; the message, server name and procedure name are never stored, logged or sent. Conversion errors quote values (`Conversion failed when converting the nvarchar value '…' to data type int`), so this is an I2 rule, not hygiene.
- **TLS**: the workspace's `rustls` with the `ring` provider, `tokio-rustls`, `rustls-native-certs`, as the other connectors. The `PRELOGIN` wrapper is a small `AsyncRead` / `AsyncWrite` adapter that frames TLS records in `PRELOGIN` packets until the handshake completes, then passes TLS records through.
- **Robustness duties** (ADR-0039 decision 4, the [connector obligations](../05-security.md#connector-obligations)): unit tests against a scripted fake server (as `connector-mysql/src/fake.rs`); property tests on every parser (no panic, bounded reads, the password never written outside the `LOGIN7` buffer); fuzz targets in `agent/fuzz/fuzz_targets/` for the packet reassembly, `PRELOGIN` response, the token stream (with `COLMETADATA` and rows), `ENVCHANGE`, the Audit record conversion and the T-SQL statement analysis; the nightly fuzz workflow runs them.

**Rationale, measured.** Option A (`tiberius` 0.13.0) passes the license, MSRV and ban checks, supports TDS 8.0 strict and is maintained again since September 2026. It is rejected for four measured reasons, each a project rule rather than a preference:

1. It compiles a second, C-based crypto provider into the agent (`aws-lc-sys`, with `cmake` and `jobserver` at build time) whatever features are chosen, against the "no C library unless justified" criterion of ADR-0039 decision 4 and the single `ring` provider of the workspace. As a consequence of this decision, `aws-lc-rs` and `aws-lc-sys` join the `[bans]` of `agent/deny.toml` (reason: "single `ring` provider, ADR-0051 decision 1"), so no dependency brings them in unnoticed; lifting the ban needs a `security-reviewer` review, as every ban.
2. Its trust configuration cannot pin a CA as the only root (ADR-0015 decision 1, applied to every connector since): `trust_cert_ca` adds to the OS store, and no caller-built rustls configuration is accepted.
3. It buffers a value up to 2 GiB and decodes every SQL type, where the project's connectors bound what they read before allocating and fail closed on what they did not ask for. Wrapping it does not help: the bound must hold inside the decoder.
4. Its errors carry server message text and it emits its own `tracing` events, which the agent's subscriber would receive; the agent would have to trust that no event of a 38 000-line crate ever quotes a value.

Option B costs an estimated 2 500 to 3 500 lines plus tests and fuzz targets (the MySQL and MongoDB protocol layers are about 2 000 lines each), and owns the robustness of the parsers, which is the residual risk every own client already carries. `mssql-tds` is excluded outright (OpenSSL and `native-tls` on Linux, `socket2`). The decision is reviewed if `tiberius` gains a caller-provided rustls configuration and an optional crypto provider; the comparison table above is the checklist.

### 2. Authentication and transport

- **SQL logins only.** `LOGIN7` with SQL Server authentication. The password is read from its `agent.yaml` reference into zeroized memory, obfuscated into the `LOGIN7` buffer, which is zeroized after the write; it is never written anywhere else (property test).
- **TLS is mandatory on every transport, loopback included**, because `LOGIN7` carries the password in a reversible form. There is **no `disable` and no `disable_insecure` mode** for SQL Server, unlike [ADR-0015](0015-postgresql-connector-decisions.md) decision 1: on PostgreSQL, MySQL and MongoDB those modes still keep the password out of the wire (challenge-response); here they would send it.
- **An operator-installed certificate that names the host is required** (security review M9). When no certificate is configured, SQL Server (on Windows and on Linux) encrypts with a fallback self-signed certificate that has no subject alternative name and is **regenerated at each service start** (to verify per version and platform): it can neither pass a host-name check nor be pinned, because the pin would break at the next restart. The operator installs a certificate issued by a CA the agent trusts (the system store, or a private CA pinned with `ca_file`) whose SAN names the host or IP literal the target declares, loopback included (`127.0.0.1` as an IP SAN). The fallback certificate fails the connection with `tls_failed` and a local detail saying so; there is no "pin this exact certificate" mode.
- **`targets[].sqlserver.tls`**:
  - `strict` (TDS 8.0): TLS from the first byte with ALPN `tds/8.0`, TLS 1.2 or 1.3 (to verify: SQL Server 2022 offers TLS 1.3 only in strict mode). SQL Server 2022 and later only.
  - `mandatory` (the only mode SQL Server 2019 offers): `PRELOGIN` with `ENCRYPT_REQ`; the server must answer `ENCRYPT_ON` or `ENCRYPT_REQ`, and the whole session is then encrypted. `ENCRYPT_OFF` (login-only encryption) and `ENCRYPT_NOT_SUP` are refused before `LOGIN7` is built.
  - `auto` (proposed default, open question 3; ordering after the security review, L6): **`strict` first**. If the strict TLS handshake fails before any TDS byte is exchanged (the server does not speak TLS first: a 2019 server, or a 2022+ server answering in TDS 7.x framing), the connector falls back **once** to `mandatory` on a new connection, with full certificate verification. A target that has completed one authenticated `strict` session is marked **"strict seen"**, persisted per target in the agent's state directory with the target's declared host and port; from then on `auto` behaves as `strict`, and a later strict failure fails the connection instead of falling back (an attacker on the path cannot downgrade a known strict server to `PRELOGIN` in clear). The mark is cleared only by changing the target's host, port or `tls` setting. Both outcomes keep the password inside verified TLS; the fallback only exposes the `PRELOGIN` fields, which are never trusted (below).
  - Every mode verifies the certificate as `verify_full` does elsewhere: the pinned CA file (`sqlserver.ca_file`, then the only trusted root) or the system store, and the host name (DNS name or IP SAN) checked against the declared host. There is no "trust server certificate" mode.
- **The `PRELOGIN` response is untrusted** before TDS 8.0 (it travels in clear): its version field is ignored for any decision; the version is read after login (decision 3).
- **Refused**: Windows integrated authentication (NTLM and Kerberos through SSPI / GSSAPI; NTLM is on the ADR-0039 decision 6 refusal list, and Kerberos would need a C GSSAPI library or the pure-Rust `sspi` crate, which also implements NTLM), Microsoft Entra ID (federated authentication, `FEDAUTH`; Azure only, decision 3), client certificate authentication, contained database users (follow-up, open question 5), the SQL Server Browser service (UDP 1434: the port is declared, named instances are reached by their port; the agent sends nothing to a host it was not told to connect to, and an unauthenticated UDP reply would choose the port), and MARS.
- **Connection model**: one declared `host` / `port` (no default instance resolution, no Browser), one connection per scan and one per `check()`, replaced after an error that leaves it unusable or when idle for 60 s. Cancellation needs no second connection: `ATTENTION` is sent on the same connection (TDS has no separate cancel connection, unlike MySQL `KILL QUERY`). Account option recommended to the operator: `CHECK_POLICY = ON`; there is no per-login connection limit in SQL Server (a logon trigger can impose one; not recommended, decision 7). With `CHECK_POLICY = ON`, the Windows or Linux account lockout policy applies to the login: repeated failures (a wrong password in `agent.yaml`, or someone else guessing it) lock the agent out. The connector stops retrying a target after an authentication failure until the next heartbeat check, and reports a locked login (error 18486, to verify) as `authentication_failed` with the local detail "login locked out" (a locked login cannot log in, so the error number is the only evidence; documented in the user guide).

### 3. Supported versions and editions

- **Versions**: SQL Server 2019 (15.x), 2022 (16.x) and 2025 (17.x), following [ADR-0039](0039-engine-scope-expansion.md) decision 1. Lifecycle dates (Microsoft lifecycle pages, **to verify** before release): 2019 mainstream support ended on 2025-02-28 and extended support runs to 2030-01-08; 2022 mainstream to 2028-01-11, extended to 2033-01-11; 2025 is generally available (the `2025-CU9` images exist on 2026-10-14). **SQL Server 2017** (14.x) is still in extended support until 2027-10-12 (to verify) but is **not supported**: it has no TDS 8.0, ends within a year of the connector shipping, and the ROADMAP lists 2019 as the floor (open question 1).
- **How the version is checked**: the `LOGINACK` token's TDS version (at least 7.4) and program version give a first value inside TLS; then `SELECT CONVERT(int, SERVERPROPERTY('EngineEdition')), CONVERT(nvarchar(128), SERVERPROPERTY('ProductVersion')), CONVERT(nvarchar(128), SERVERPROPERTY('ProductMajorVersion'))` on the authenticated session decides. A major below 15 is refused as `unsupported` before any catalog read (as `MIN_MYSQL` and `MIN_WIRE_VERSION`).
- **Editions**: `EngineEdition` 2 (Standard), 3 (Enterprise, including Developer and Evaluation) and 4 (Express) are accepted; 1 (Personal / Desktop) is accepted only if seen in the matrix (to verify that it can still be returned). **Azure SQL Database (5), Azure Synapse (6, 11), Azure SQL Managed Instance (8), Azure SQL Edge (9) and any other value are refused** (`unsupported`) in this ADR (values to verify against Microsoft's `SERVERPROPERTY` page): their authentication (Entra ID), gateway redirection (`ENVCHANGE` routing), audit storage (blob storage) and permission model differ, and Audit through `fn_get_audit_file` there needs `CONTROL DATABASE`. Azure is a later ADR (open question 2).
- **Platform**: SQL Server on Windows and on Linux alike, reached over TCP. The version is sent as `TargetStatus.server_version` (`ProductVersion`, for example `16.0.4305.5`, which matches the field's pattern; security review L10), as the other connectors do; the edition goes to the agent's local detail only.

### 4. Least-privilege grant set (I4), to be measured as in ADR-0012

**Proposed minimal variant** (default), per monitored database:

```sql
-- Once per server. The password is typed in a client that does not log it; the
-- statement text holds it (decision 6 drops it from what the agent derives).
CREATE LOGIN databastion_agent WITH PASSWORD = '<from a prompt>',
  CHECK_POLICY = ON, DEFAULT_DATABASE = [app];
-- Per monitored database
USE [app];
CREATE USER databastion_agent FOR LOGIN databastion_agent;   -- grants CONNECT
GRANT SELECT ON SCHEMA::[crm] TO databastion_agent;          -- current and future objects of the schema
-- Audit, only when Audit is enabled for the target (decision 6), one of:
--   SQL Server 2022+, SQL Server Audit source:
--     USE [master]; GRANT VIEW SERVER SECURITY AUDIT TO databastion_agent;
--   Extended Events source (2019, or 2022+ without SQL Server Audit):
--     2019:  GRANT VIEW SERVER STATE TO databastion_agent;
--     2022+: GRANT VIEW SERVER PERFORMANCE STATE TO databastion_agent;
```

- **Schema-level `SELECT`** covers the schema's present and future tables (unlike PostgreSQL's per-table grants and default privileges), so the PostgreSQL maintenance cost of ADR-0012 does not apply; a new schema still needs a grant, and `check()` lists schemas with no `SELECT` as not covered (decision 5).
- **No `VIEW DEFINITION`.** Metadata visibility gives the agent the names, columns and types of the objects it holds a permission on, which is all Discovery needs (to measure). `VIEW DEFINITION` would expose module definitions (`sys.sql_modules.definition`: procedure, view and function bodies, which can hold literals) for nothing.
- **Extended variant (opt-in, `extended_grants: true`)**: membership of `db_datareader` per database (every table of every schema, present and future), reported by `check()` as `privilege.extended_variant`, as on PostgreSQL and MySQL. Without the flag, the same membership is over-privilege.
- **Never granted, and `check()` reports them.** Two complementary reads, both compared with a closed allow-list (anything outside it is reported):
  - **effective permissions**: the built-ins `fn_my_permissions(NULL, 'SERVER')` and `fn_my_permissions(NULL, 'DATABASE')`, `IS_SRVROLEMEMBER` and `IS_ROLEMEMBER`;
  - **securable-level grants** (security review M3), which `fn_my_permissions` on the server and database does not list: rows of `sys.server_permissions` and of `sys.database_permissions` (per database) whose grantee is the agent's principal or one of its server or database roles (`sys.server_role_members`, `sys.database_role_members`, followed recursively, bounded at 64 roles), for example `IMPERSONATE ON LOGIN::[x]`, `CONTROL ON USER::[y]`, `ALTER ON ROLE::[z]`, `TAKE OWNERSHIP`. The visibility of other principals' rows to the agent is to measure; the agent's own rows and its roles' rows are expected visible.
  - **Every accessible database is checked, not only the monitored ones** (security review M3): `db_owner` membership, `CONTROL` on the database and `IMPERSONATE` grants are read in every database where `HAS_DBACCESS(name) = 1`. A `db_owner` of any `TRUSTWORTHY` database can reach server-level rights through a module signed or executed as its owner, so a refusal-list right in an unmonitored database is as serious as in a monitored one.

  The lists:
  - **Refusal list** ([ADR-0039](0039-engine-scope-expansion.md) decision 5, extended): membership of `sysadmin` or `db_owner` (in any accessible database); `CONTROL SERVER`, `ALTER ANY SERVER AUDIT`, `ALTER ANY DATABASE AUDIT`, `CONTROL` on any accessible database; the event-session rights (they stop, edit or redirect an Extended Events source, decision 6): `ALTER ANY EVENT SESSION` and its SQL Server 2022 granular forms `ALTER ANY EVENT SESSION ENABLE`, `… DISABLE`, `… ADD EVENT`, `… DROP EVENT`, `… ADD TARGET`, `… DROP TARGET`, `… OPTION`, and `CREATE ANY EVENT SESSION`, `DROP ANY EVENT SESSION` (names **to verify** against the 2022 permission hierarchy); the identity rights: `ALTER ANY LOGIN`, `ALTER ANY SERVER ROLE`, membership of `securityadmin` and of `##MS_LoginManager##`, `IMPERSONATE ANY LOGIN`, and `IMPERSONATE` or `CONTROL` on any login or database user (they let the account act as another principal, which decision 6's own-statement rule must never confuse with the agent); `VIEW ANY CRYPTOGRAPHICALLY SECURED DEFINITION` (2022; to verify that it exposes `password_hash` and key material); and the SQL Server 2022 `##MS_*##` roles that hold any of these (list to measure). **Audit refuses to run** with such an account (ADR-0039), and **Discovery refuses too** (proposed, open question 4): with these rights the account bypasses dynamic data masking and reads password hashes and audit files, and nothing in Discovery needs them. Reported as `privilege.refused` with the right's label.
  - **Over-privilege, warned** (notes reused per security review L10: `privilege.global_privileges` for server rights, `privilege.beyond_select` for database rights, `privilege.owner_of_objects` for ownership, `privilege.grant_option`): `VIEW ANY DEFINITION` (module bodies everywhere), `ADMINISTER BULK OPERATIONS` / `bulkadmin` (server-side file reads through `BULK INSERT` / `OPENROWSET(BULK …)`), `ALTER ANY LINKED SERVER` / `setupadmin` (outbound connections, I5), `ALTER TRACE`, `SHUTDOWN`, any other fixed server role, any server permission other than `CONNECT SQL`, `VIEW ANY DATABASE` (granted to `public` by default) and the Audit permission while an Audit stream uses it (as ADR-0023 decision 3 treats `SELECT ON performance_schema.*`: expected while it is the source, `privilege.audit_grant_without_audit` otherwise); any database permission beyond `CONNECT` and `SELECT` (including `UNMASK`, `VIEW DEFINITION`, `VIEW DATABASE STATE`, `EXECUTE`, `SHOWPLAN`, any write), `WITH GRANT OPTION`, ownership of any object or schema, database roles other than `public` (and `db_datareader` with the flag). Labels for SQL Server rights are new `TargetNoteLabel` values, sent only once the console lists the `target_status.note_labels.<revision>` that includes them ([ADR-0022](0022-protocol-capability-negotiation.md)), `other` before.
  - **Probe**: `check()` also reads `password_hash` of its own row in `sys.sql_logins` (`WHERE principal_id = SUSER_ID()`, a constant text, decision 6; to verify that a login sees its own row, otherwise the probe reads `LOGINPROPERTY(SUSER_SNAME(), 'PasswordHash')` the same way) and requires it to be `NULL`, as a direct test that no grant path (a role, `VIEW ANY CRYPTOGRAPHICALLY SECURED DEFINITION`, `CONTROL SERVER`) exposes hashes; a non-`NULL` value is a refusal (`privilege.refused`) whatever the permission reads said. The value read is never kept, logged or compared beyond `IS NULL`, and the statement is written so the server returns only a bit (`SELECT CASE WHEN password_hash IS NULL THEN 0 ELSE 1 END …`).
- **What must be measured** (P9-A, on 2019, 2022 and 2025, throwaway containers with fake markers, the table of results added to this ADR as ADR-0012's "Verification" section before it is accepted). Accounts: `min` (the minimal variant), `dr` (`db_datareader`), `aud` (min + `VIEW SERVER SECURITY AUDIT`, 2022+), `xe19` (min + `VIEW SERVER STATE`), `xe22` (min + `VIEW SERVER PERFORMANCE STATE`), `none` (`CONNECT` only). Probes, each expected denied or empty for `min` unless stated:
  - credential-bearing catalogs: `sys.sql_logins.password_hash`, `LOGINPROPERTY(name, 'PasswordHash')`, `sys.credentials`, `sys.database_scoped_credentials`, `sys.linked_logins`, `sys.servers` (provider strings, data sources), `sys.master_key_passwords`, `sys.symmetric_keys` / `sys.asymmetric_keys` / `sys.certificates` and `CERTPRIVATEKEY`, `msdb.dbo.sysmail_server`, `msdb.dbo.sysproxies`, `msdb.dbo.sysssispackages`;
  - statement text of other sessions: `sys.dm_exec_requests` with `sys.dm_exec_sql_text`, `sys.dm_exec_input_buffer`, `sys.dm_exec_query_stats`, `sys.dm_exec_cached_plans` with `sys.dm_exec_query_plan` (compiled parameter values), Query Store `sys.query_store_query_text`, `DBCC INPUTBUFFER`, and for `xe19` / `xe22` which of them become readable (expected: all of them for `VIEW SERVER STATE`; to measure for `VIEW SERVER PERFORMANCE STATE`);
  - Audit, **first** (security review M3, open question 10): `sys.fn_get_audit_file` per account and version (expected: `CONTROL SERVER` before 2022, `VIEW SERVER SECURITY AUDIT` on 2022+; **to verify**, it decides decision 6), what `VIEW SERVER SECURITY AUDIT` and `VIEW DATABASE SECURITY AUDIT` each expose beyond the audit files (which catalogs, whether any secret-bearing column becomes readable; `password_hash` must stay `NULL`), whether `VIEW SERVER SECURITY AUDIT` lets `fn_get_audit_file` read any `.sqlaudit` path the server's service account can read, or only the audits' own folders; the readability of `sys.server_audits`, `sys.server_file_audits`, `sys.server_audit_specifications` and `_details`, `sys.database_audit_specifications` and `_details`, `sys.dm_server_audit_status` with each grant (expected to need `VIEW ANY DEFINITION`, `ALTER ANY SERVER AUDIT` or, on 2022, `VIEW ANY SECURITY DEFINITION` / `VIEW SERVER SECURITY STATE`; to verify);
  - Extended Events: `sys.fn_xe_file_target_read_file`, `sys.dm_xe_sessions` (drop counters), `sys.dm_xe_session_targets`, `sys.server_event_sessions` and `_events` (predicates) with `xe19` and `xe22`;
  - Discovery metadata with `min`: `sys.schemas`, `sys.tables`, `sys.columns`, `sys.types`, `sys.partitions.rows`, `sys.masked_columns`, `sys.security_policies` / `sys.security_predicates`, `sys.columns.encryption_type`, `sys.synonyms`, `sys.external_tables`, `HAS_PERMS_BY_NAME` at column level, `HAS_DBACCESS`;
  - read-only behavior: `INSERT` denied; a procedure executable by `public`; a view calling a scalar function that writes through `EXEC` of an extended procedure (to verify what a function can do); a computed column calling a scalar function; a row-level security predicate function; `CREATE TABLE #t` (expected allowed for every login: a residual, as MySQL temporary tables); `xp_dirtree` / `xp_fileexist` (executable by `public` by default on some versions: a server-side outbound SMB connection primitive, to measure; not something the agent sends, but something a stolen agent credential can);
  - dynamic data masking: what `min` reads from a masked column; whether `sys.masked_columns.masking_function` is visible (it can hold a partial-mask literal).
- **I4 summary**: read-only rests on (1) no write permission, (2) a closed statement set built in code with quoted identifiers, (3) never reading an object that runs user code implicitly (decision 5), (4) client-side bounds (decision 5). Unlike PostgreSQL and MySQL, there is no read-only transaction to back them up; the residual is the same as MongoDB's.

### 5. Discovery

- **Databases**: `sys.databases` (visible through `VIEW ANY DATABASE`, granted to `public` by default; the connected database is always visible) filtered on `HAS_DBACCESS(name) = 1`, `state = 0` (online), `source_database_id IS NULL` (no database snapshots), not readable secondaries skipped, and never `master`, `model`, `msdb`, `tempdb`, `distribution`, `SSISDB`, `ReportServer*` (closed list) nor any database where `is_distributor = 1`; then the job's `databases` filter. At most 1 024 databases (beyond: one `skipped_limit`). Rotation per scan as ADR-0035.
- **Catalog per database**, with three-part names (`[db].sys.tables`…; no `USE`, so every statement stands alone, which decision 6 relies on): schemas (`sys.schemas`), tables (`sys.tables` with `type = 'U'`, `is_ms_shipped = 0`, `is_external = 0`, `is_filetable = 0`; at most 16 384 per database), columns (`sys.columns` joined `sys.types` on `user_type_id`), the row estimate (`SUM(sys.partitions.rows)` for `index_id IN (0, 1)`, metadata, no scan; visible with the table's permission, to measure), and per table `HAS_PERMS_BY_NAME(…, 'OBJECT', 'SELECT')` plus the column-level form (SQL Server has column `DENY`: a statement naming a denied column fails as a whole, so denied columns are left out of the select list).
- **Never sampled**:
  - views, synonyms (`sys.synonyms`; often a four-part name on a linked server), table-valued functions, external tables (PolyBase, `skipped_remote`), Stretch Database tables (`is_remote_data_archive_enabled = 1`: rows can live in Azure, so reading them connects out; `skipped_remote`), FileTables, memory-optimized table types, graph internal columns (`graph_type IS NOT NULL`), and any object of a system schema (`sys`, `INFORMATION_SCHEMA`, `guest`, the `db_*` role schemas);
  - **computed columns** (`is_computed = 1`; a scalar function in the expression runs on read: user code), **sparse column sets** (`is_column_set = 1`, computed XML), **CLR types** (`hierarchyid`, `geometry`, `geography`, user CLR types), `xml`, `sql_variant`, `timestamp` / `rowversion`, `image`, `vector` and any type outside the allow-list of the bullet "Values" below; counted per table in the local detail;
  - **tables with an enabled row-level security policy** (a `sys.security_predicates` row of an enabled `sys.security_policies` entry naming the table; the predicate is an inline table-valued function, user code that runs on every read, and it hides rows silently): skipped, `skipped_row_level_security`, note `coverage.relations_rls_skipped`. A predicate function can itself call scalar user functions, so sampling such a table runs arbitrary user code in the agent's session. **If the security policy catalog is not visible to the account** (security review M7; visibility to measure: metadata visibility may hide policies on tables the account can read), the connector cannot tell a protected table from an unprotected one. Decision: **every table of that database is skipped** (`skipped_row_level_security`), with the new note `coverage.rls_not_verifiable` (count of databases) and a local detail naming the database and the measured grant that would make the catalog visible. Sampling anyway with a note was rejected: it would run predicate code the agent cannot see, and the coverage would silently omit the rows the predicate hides. If the matrix shows the catalog is invisible with the minimal variant on some version, the ADR is revised with the smallest grant that makes it visible before Discovery ships there (open question 6, also on an allow-list of predicates as ADR-0015 decision 3);
  - **Always Encrypted columns** (`encryption_type IS NOT NULL`): the server holds ciphertext only, the agent never enables column encryption (no `FEATUREEXT`) and would classify random bytes; not sampled, counted in the new note `coverage.encrypted_columns`;
  - the **CAS store guard** of [ADR-0041](0041-cas-connector.md) decisions 5 and 6 applies as on the other SQL engines (ticket registries counted per `type`, never sampled; the ticket-id tripwire before classification; `privilege.ticket_credentials_readable`, `security.ticket_registry_unencrypted` and `coverage.cas_guard_tripped` gain the `sqlserver` engine): CAS's JPA registries support SQL Server.
- **Dynamic data masking**: the agent never holds `UNMASK`, so masked columns come back masked (`aXXX@XXXX.com`, `xxxx`, `0`). They are sampled as they come (the value is what the agent's account sees, as with any account), and counted in the new note `coverage.masked_columns`, so a classifier that found nothing on a masked column is not read as "no sensitive data". Name hints still apply. Masked values are a weak signal by design; the column's masking is itself evidence that the data is sensitive.
- **Temporal tables**: the current table and its history table are two `type = 'U'` tables and are sampled separately (the history holds past values); `FOR SYSTEM_TIME` is never used. Ledger tables are sampled like any table; their history views are views.
- **Sampling statement** (one per table, one statement per `SQLBatch`):

  ```sql
  SELECT TOP (<n>) CONVERT(nvarchar(4000), LEFT([c1], 4000)), CONVERT(nvarchar(64), [c2], <style>), …
    FROM [db].[schema].[table] [TABLESAMPLE SYSTEM (<p> PERCENT)]
    OPTION (MAXDOP 1)
  ```

  - `<n>` is the job's `sample_rows` (at most `limits.max_sample_rows`), an integer literal; identifiers come from the catalog and are quoted by one audited function (`[` … `]`, `]` doubled), never from job parameters; there is no string literal in any sampling statement.
  - **Values** are converted on the server to `nvarchar` with built-ins only (`CONVERT`, `LEFT`; built-in names cannot be shadowed by user functions in T-SQL, because scalar user functions must be called with a schema), so the client decodes one type: character types (`char`, `varchar`, `nchar`, `nvarchar`, `text`, `ntext`, any collation, UTF-8 collations included) cut to 4 000 characters; exact numerics and integers as digits; `date`, `datetime`, `datetime2`, `smalldatetime` as `YYYY-MM-DD` (style 23); `money` and `float` / `real` (integral values only, as MongoDB doubles) to be confirmed in implementation; `uniqueidentifier` skipped (as MongoDB UUIDs); `binary` / `varbinary` either fetched as non-`max` bytes cut to 4 000 with `LEFT` (`BIGVARBIN`, decision 1) and read as text only when valid UTF-8 without control characters (as ADR-0026 decision 9), or not sampled, decided in implementation; `json` (SQL Server 2025) as text, to verify on the wire. The server-side work on the value is a residual (as MySQL's `LEFT()`).
  - **`TABLESAMPLE SYSTEM`** only when the row estimate is above 20 × `n` and above 1 000 rows, with `<p>` chosen to target about 4 × `n` rows (bounded to [0.01, 100]); otherwise `TOP (n)` in storage order. Caveats recorded: `TABLESAMPLE` samples pages, not rows, so a sample can be empty or clustered on a few pages; it does not apply to views (never read anyway); and it is not supported on memory-optimized tables (to verify), which then use `TOP (n)`. There is no second read when a sample comes back short (as MongoDB: one statement per object).
  - `OPTION (MAXDOP 1)`: one scheduler per sampling statement, so the ADR-0035 duty cycle bounds the server's CPU as on the other engines (the PostgreSQL parallel-worker residual does not apply).
- **Session settings**, sent once per connection as one constant batch and checked by reading them back (`@@OPTIONS`, `@@LOCK_TIMEOUT`): `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; SET LOCK_TIMEOUT 2000; SET IMPLICIT_TRANSACTIONS OFF; SET XACT_ABORT ON; SET DEADLOCK_PRIORITY LOW; SET NOCOUNT OFF; SET QUOTED_IDENTIFIER ON; SET ANSI_NULLS ON; SET ROWCOUNT 0; SET TEXTSIZE 8000; SET LANGUAGE us_english; SET DATEFORMAT ymd`.
  - **`READ UNCOMMITTED`** (proposed, open question 7): the agent takes no shared row or page locks, so it never blocks a writer and never waits for one; it still takes schema-stability locks, which `LOCK_TIMEOUT` bounds (error 1222 skips the table, `skipped_error`). The price is that an uncommitted value can be sampled (it existed in the database); errors 601 / 605 from concurrent data movement skip the table. `READ COMMITTED` (locking) would make the agent wait on writers and hold short shared locks; `SNAPSHOT` needs a database option the operator may not have set.
  - The connector never sends `BEGIN TRANSACTION`, and a transaction `ENVCHANGE` ends the connection (decision 1): there is no transaction to hold across `FindingSink::submit().await` by construction, and each table's result is fully read (or cancelled) before its findings are submitted.
- **Timeouts and cancellation**: no server-side statement timeout exists for the login, so every statement has a client-side deadline from the job's clamped statement timeout (never 0); at the deadline, or when the per-table byte budget is reached, or when the scan is cancelled, the client sends `ATTENTION` and reads until the `DONE` with `DONE_ATTN` within 5 s; otherwise it closes the connection (the server aborts the batch when it notices the disconnect) and the next table uses a new connection. `check()` uses 3 s per statement and 9 s in total, as MongoDB.
- **Byte budget**: at most 32 MiB of sampled values per table, checked **per value as bytes arrive** (the own client knows each value's length before reading it), so the single-row peak of the PostgreSQL residual is bounded here by the select list: at most 8 000 bytes per value, at most the sampled columns of one row.
- **Pacing**: every unit of work (a database listing, a database's catalog, a table's sample) goes through `ScanJob::paced` ([ADR-0035](0035-discovery-pacing.md)); the connection is closed before a pause that reaches 45 s, as MySQL.
- **Locations and names**: `Location` is `engine: sqlserver`, `database`, `schema`, `object` (table), `field` (column), the four levels PostgreSQL uses. Every name goes through [ADR-0009](0009-name-normalization-and-item-sanitization.md) normalization; bracketed names can hold any character, including `.` and values, so the existing rules (value-like segments, dots in names, CJK numerals) apply unchanged. Own-account budget keys are lower-cased as on every engine (SQL Server collations are usually case-insensitive).
- **Coverage**: `objects_sampled`, `skipped_not_readable` (no `SELECT`), `skipped_row_level_security`, `skipped_remote` (external tables), `skipped_unsupported` (CAS ticket registries, tables with no sampleable column), `skipped_limit`, `skipped_error`; schemas without `SELECT` listed as not covered in the local detail (no SQL Server analogue of `pg_namespace` for objects the login cannot see: as MySQL's `information_schema`, invisible objects cannot be counted).

### 6. Audit

#### Sources

| Source | `audit_source` | Read through | Permission | Expected level |
|---|---|---|---|---|
| SQL Server Audit, `FILE` target | `sqlserver_audit` | `sys.fn_get_audit_file` over the agent's connection | `VIEW SERVER SECURITY AUDIT` (SQL Server 2022+; to verify) | **Partial**, Limited until a record was read in the last 24 h |
| Extended Events session, `event_file` target | `sqlserver_xevents` | `sys.fn_xe_file_target_read_file` | `VIEW SERVER STATE` (2019), `VIEW SERVER PERFORMANCE STATE` (2022+; to verify) | **Partial** with the proofs below, Limited otherwise |
| Plan cache statistics | `sqlserver_query_stats` | `sys.dm_exec_query_stats` with `sys.dm_exec_sql_text` | same as Extended Events | **Limited** (no principal, aggregated, lost on plan eviction) |

- **Preference** (one rule shared by `check()` and the stream, as ADR-0023's `choose`): SQL Server Audit when usable, then Extended Events, then plan cache statistics, then none. Re-evaluated every 5 minutes.
- **SQL Server Audit is not a source on SQL Server 2019**: `fn_get_audit_file` needs `CONTROL SERVER` there, which is on the refusal list (ADR-0039 decision 5). A 2019 server with an enabled audit gets the note `audit.sqlserver_audit_needs_control_server` and uses Extended Events if configured.
- **Local `.sqlaudit` files are rejected as a source**: the format is binary and, as far as could be checked, not publicly specified (to verify); only SQL Server on Linux on the agent's host could use it; and parsing an undocumented binary format from a hostile writer is the riskiest parser this project could add. The `APPLICATION_LOG` / `SECURITY_LOG` targets are Windows event logs, out of reach of a Linux agent.
- **Query Store is rejected**: per-database `VIEW DATABASE STATE` grants, no principal, aggregation per interval, and its plans hold compiled parameter values.
- **SQL Trace** (`fn_trace_gettable`) is deprecated and needs `ALTER TRACE`: rejected.
- **Configuration**: the operator creates the server audit, the audit specifications and the Extended Events session; the agent never creates, alters, starts or stops them (ADR-0039 decision 5). `agent.yaml` names them: `sqlserver.audit {source: sqlserver_audit | sqlserver_xevents | auto, audit_name, xe_session}`. The file path passed to `fn_get_audit_file` / `fn_xe_file_target_read_file` is read from `sys.server_file_audits.log_file_path` / the session's target definition, never from `agent.yaml` or the console (the function reads files as the server's service account: a path from configuration would turn the agent into a file-read primitive).
- **Polling** (security review M1). Each poll is one RPC `sp_executesql` whose text is constant **for a given catalog state**, with typed parameters for the position only:
  - **The file pattern is a literal in the text**, never a parameter: `SELECT … FROM sys.fn_get_audit_file(N'<pattern>', @file, @offset)` or `SELECT … FROM sys.fn_xe_file_target_read_file(N'<pattern>', NULL, @file, @offset)`, where `<pattern>` is built from `sys.server_file_audits.log_file_path` and the audit's name and GUID (or from the session's `event_file` target definition), quoted by the audited string-literal function. The text is rebuilt when the catalog value changes (checked at each 5-minute re-probe), and the set of poll texts the agent has sent is kept per target (bounded at 16, with the time window each was in use) for the own-statement rule below. Only `@file` (`initial_file_name`) and `@offset` (`audit_record_offset` / `initial_offset`) are parameters.
  - **Why**: with the pattern as a parameter, a stolen agent credential could send the agent's exact text with any pattern, read any audit-format file the server's service account can read, and be left out as the agent's own (an unseen file-read primitive).
  - **The ADR-0050 decision 5 test** (no own-statement exemption on a source that hides values which change what is read): the poll is exempt only if `@file` and `@offset` cannot widen the set of files read beyond those the literal pattern matches. Whether `initial_file_name` must match the pattern, or can name a file outside it, is **to verify** per version. If it can widen the set, the poll is **not exempt** on any source where the parameter values are not recorded, and is reported (always reported, as a statement-text read); the stream then reads its own polls back, so the connector keeps one poll every 5 s at most and accepts that noise until a fix is found (fail closed, loud).
  - **Which record is matched.** On SQL Server Audit, the record of the poll is the one whose `statement` is the inner text of the `sp_executesql` call (to verify what the `statement` field holds for an RPC; if it holds the outer call with parameter values, those records are matched on the outer text with the parameter list reduced to its names, and the values are dropped at parse). On Extended Events, the matched event is the inner **`sp_statement_completed`**, whose `statement` is the inner text with `@file` and `@offset` as names (to verify); the paired **`rpc_completed`**, whose `statement` holds the call **with the parameter values** (`exec sp_executesql N'…', N'@file nvarchar(260), …', @file = N'…'`), is context only (M5 below): its text is never analysed, its parameter values are dropped at parse, and it is never an event on its own.
- **Position and gaps** (security review M4). The position (file name and offset, plus the session or audit identity below) is persisted per target, as the other polled sources since #88. At most 1 000 records per poll. Gaps are detected and reported, as the L1 / #97 precedent did for truncated logs:
  - **File lost to rollover before it was read**: the persisted file no longer exists, or the earliest file the pattern lists is newer than the persisted one (`MAX_ROLLOVER_FILES` / `max_rollover_files` deleted it). The stream restarts at the earliest file, and reports `audit.records_dropped` and the level Limited for 24 h.
  - **Restart of the session or the audit**: at every poll the connector compares `sys.dm_xe_sessions.create_time` (Extended Events) or `sys.dm_server_audit_status.status_time` (SQL Server Audit; visibility to verify, decision 4 measurements) with the persisted value. A change means the source was stopped and started: whatever happened in between was not recorded. The stream reports `audit.records_dropped`, Limited for 24 h, and a local detail with the two times. An unreadable status view fails this proof (Limited).
- **Statement text length**: Audit's `statement` column is `nvarchar(4000)`; longer statements span several records with a `sequence_number`, which the connector reassembles up to 64 KiB, then treats as cut (to verify). A cut text is never the agent's own.

#### What is kept (I2)

- **SQL Server Audit**: `event_time` (UTC), `action_id`, `succeeded`, `class_type`, `session_id`, `server_principal_name`, `session_server_principal_name`, `database_principal_name`, `database_name`, `schema_name`, `object_name`, `statement` (through the normalizer below), `client_ip`, `application_name`, `sequence_number`, `file_name` / `audit_file_offset` (position only). Dropped at parse: `additional_information` (XML: T-SQL stack, can hold names and literals), `data_sensitivity_information`, `host_name`, `user_defined_information`, `permission_bitmask`, `target_*` names except as principals of DCL events. `affected_rows` and `response_rows` are read **only if** the matrix shows boxed SQL Server fills them (they are documented for Azure SQL; **to verify**); until then the source has no row count (`audit.log_without_row_counts` gains `sqlserver`).
- **Extended Events**: `row_count`, `duration`, `statement` (normalizer), `object_name` (for `rpc_completed`), and the actions `server_principal_name`, `session_server_principal_name`, `client_app_name`, `database_name`, `session_id`, and the causality identifier of `TRACK_CAUSALITY = ON` (`attach_activity_id`, to verify). `client_hostname` is **not** collected (security review H1: client-set, spoofable, and no identity rule uses it); `batch_text` of `sql_batch_completed` and the `statement` of `rpc_completed` are dropped at parse (M5). The event XML is parsed by a bounded reader (closed element and attribute names; any other content skipped by length; fuzzed); `event_data` is requested as `nvarchar(max)`, the one `max` column the client accepts, bounded at 64 KiB per event (larger: the event keeps no text and names `*`).
- **Extended Events, one event per statement** (security review M5): only the statement-level events, `sql_statement_completed` and `sp_statement_completed`, produce access events. `sql_batch_completed` and `rpc_completed` are **context only**: they are grouped with the statement events of the same request by (`session_id`, causality activity id; to verify, otherwise `session_id` and event sequence), and only give the procedure name of an `rpc_completed` that is not `sp_executesql`, `sp_prepexec`, `sp_execute` or `sp_cursor*` (open question 12). Without this rule a statement would be counted two or three times (statement, batch, RPC). The load run (decision 9) checks that the events equal the statements issued, as #93 did for MariaDB.
- **Parameterized application traffic**: ORM and driver traffic is mostly `sp_executesql` (or `sp_prepexec`) RPCs. It is analysed on the **inner statement text** of `sp_statement_completed` (Extended Events) or of the audit record (SQL Server Audit, to verify), which names its tables and holds `@p0`-style parameter names instead of values. So parameterized application queries keep their objects and do not all become `*`; only literal `EXEC('…')` / `sp_executesql N'…'` written **inside** a batch or procedure (dynamic SQL in text) loses its inner text to the normalizer and names `*`.
- **Statement text**: through a T-SQL mode of the query normalizer in `classifiers` (ADR-0007, ADR-0012 obligation 5, ADR-0023 decision 4): every literal form replaced (`'…'` with `''`, `N'…'`, `0x…`, numbers, `$12.50` money literals), comments removed (T-SQL block comments **nest**), `[ident]` with `]]` and `"…"` lexed both as identifiers and as strings (the session's `QUOTED_IDENTIFIER` is unknown), readings that differ keeping only the statement kind (fail closed, as `ANSI_QUOTES` on MySQL); only DML text is kept after normalization; DDL and DCL keep their kind and the objects of the audit record, never text. Dynamic SQL in text (`EXEC('…')`, `sp_executesql N'…'` inside a batch) is a string literal: the inner text is lost to normalization, so the event names `*` and is always reported. **Every argument of an `EXEC` / `EXECUTE` of a procedure is a value, never an identifier**, quoted or not (`EXEC sp_addlogin jane, Pa55word` passes `Pa55word` unquoted): the normalizer replaces every argument token after the procedure name, so no unquoted argument survives as a name. Statement text never leaves the agent (the contract has no field for it).
- **Password-bearing statements** (the end-to-end rule of #82, ADR-0039 decision 3; list extended by the security review, M6). The statement keeps its kind only, never text, and the password never leaves the parser, whatever the server's own masking, which the agent does not rely on (whether SQL Server Audit and `dm_exec_sql_text` mask these texts is **to verify** per version):
  - logins and users: `CREATE LOGIN … WITH PASSWORD`, `ALTER LOGIN … WITH PASSWORD … OLD_PASSWORD`, `CREATE USER … WITH PASSWORD` and `ALTER USER … WITH PASSWORD` (contained users), `sp_addlogin`, `sp_password`;
  - application roles: `CREATE` / `ALTER APPLICATION ROLE … PASSWORD`, `sp_setapprole`, `sp_addapprole`, `sp_approlepassword`;
  - credentials and external access: `CREATE` / `ALTER [DATABASE SCOPED] CREDENTIAL … SECRET`, `CREATE` / `ALTER EXTERNAL DATA SOURCE`, `sp_addlinkedsrvlogin`, `sp_addlinkedserver` (`@provstr`), `sysmail_add_account_sp` / `sysmail_update_account_sp` (`@password`);
  - keys and certificates: `CREATE` / `ALTER` / `BACKUP` / `RESTORE MASTER KEY … PASSWORD`, `OPEN MASTER KEY`, `BACKUP SERVICE MASTER KEY`, `sp_control_dbmasterkey_password`, `CREATE SYMMETRIC KEY … KEY_SOURCE` / `IDENTITY_VALUE` / `BY PASSWORD`, `OPEN SYMMETRIC KEY … BY PASSWORD`, `CREATE` / `ALTER ASYMMETRIC KEY … PASSWORD`, `CREATE` / `ALTER` / `BACKUP CERTIFICATE … PASSWORD`;
  - functions taking a password or passphrase: `PWDCOMPARE`, `PWDENCRYPT`, `ENCRYPTBYPASSPHRASE`, `DECRYPTBYPASSPHRASE`, `DECRYPTBYCERT`, `DECRYPTBYASYMKEY`, `SIGNBYCERT`, `SIGNBYASYMKEY`, `DECRYPTBYKEYAUTOASYMKEY`: a DML statement calling one of them keeps its kind and objects, no text.
  
  The #82 end-to-end marker test gains one case per bullet (a fake password marker in each form, including an unquoted `EXEC` argument), and asserts that no marker appears in any uplink payload, agent log line or metric.
- **Principals**: as on the other SQL engines ([ADR-0021](0021-access-event-correlation.md)); failed-login names (`FAILED_LOGIN_GROUP`, error 18456; a password typed in the login field ends up there) are fingerprinted, as on every engine.

#### Levels and proofs (ADR-0039 decision 3)

**Full is never reported** in this ADR. SQL Server Audit has no row count for reads on boxed SQL Server (to verify), and records reads through views and procedures under ownership chaining on the view or procedure only; Extended Events has row counts but is lossy by design (`ALLOW_SINGLE_EVENT_LOSS` is the default retention mode), can be altered or restarted without a record of its own, and its statements name objects only through their text. A later refinement may propose Full with measured proofs (open question 8).

- **SQL Server Audit, Partial** when all hold, else **Limited** (a record read in the last 24 h) or **None**:
  1. the version is 2022 or later and `fn_get_audit_file` succeeds with the agent's grant, the account being outside the refusal list;
  2. the named server audit exists, `is_state_enabled = 1`, its target is `FILE`, and it has **no `WHERE` predicate** (`sys.server_audits.predicate IS NULL`); a predicate can exclude principals or objects, so it gives the note `audit.server_audit_filtered` and Limited (fail closed; open question 9);
  3. **read coverage for every monitored database**: an enabled server audit specification with `SCHEMA_OBJECT_ACCESS_GROUP`, or, per monitored database, an enabled database audit specification with `SCHEMA_OBJECT_ACCESS_GROUP` or the `SELECT` action on `DATABASE::[db]` by `public`; a database without it is named in the local detail and gives the existing note `audit.reads_not_logged` (Limited; security review L10);
  4. **`AUDIT_CHANGE_GROUP` in an enabled server audit specification** (security review M4: required, no longer a note): without it, the audit can be stopped, filtered and restarted with no record, and the restart check of the "Position and gaps" bullet sees only the restart, not what changed. Missing: the new note `audit.audit_changes_not_audited`, Limited;
  5. no gap in the last 24 h ("Position and gaps": no file lost to rollover, no restart of the audit);
  6. a record parsed in the last 24 h (the ADR-0023 decision 2 freshness rule; `audit.partial_pending_first_record` gains `sqlserver`);
  7. if the specification catalogs are not readable with the agent's grant (decision 4 measurements), conditions 2 to 4 are not proven and the level is Limited, with a note naming the missing visibility; whether to accept another grant for it is open question 10.
  
  Not required for Partial, reported as notes when missing: `FAILED_LOGIN_GROUP` (`audit.failed_logins_not_audited`), `ON_FAILURE = CONTINUE` with a non-zero failure in `sys.dm_server_audit_status` (`audit.records_dropped`).
- **Extended Events, Partial** when all hold, else Limited or None. The `xe_*` notes are defined here (security review L10):
  1. the named session exists and is running (`sys.dm_xe_sessions`), with an `event_file` target; otherwise the existing note `audit.source_not_configured` (its registry text made engine-neutral in P9-C), and no Extended Events source;
  2. it has `sql_statement_completed`, `sp_statement_completed`, `rpc_completed` and `sql_batch_completed`, each with the actions `server_principal_name`, **`session_server_principal_name`** (security review H1), `client_app_name`, `database_name` and `session_id`, and the session option `TRACK_CAUSALITY = ON` (to verify that it gives the grouping key of M5); a missing event, action or option gives the new note **`audit.xe_events_missing`** ("the Extended Events session lacks events, actions or options the agent needs: {count}"), Limited;
  3. **no predicate** on those events; a predicate gives the new note **`audit.xe_session_filtered`** ("the Extended Events session filters the events the agent reads, so some statements are not recorded"), Limited;
  4. `dropped_event_count` and `dropped_buffer_count` have not grown since the previous probe, and no gap ("Position and gaps": file lost to rollover, `create_time` changed) in the last 24 h; otherwise `audit.records_dropped` and Limited for 24 h;
  5. a record parsed in the last 24 h.
  
  `sp_statement_completed` records the statements run inside procedures and functions, so reads hidden from SQL Server Audit by ownership chaining show up here as statement texts. `row_count` sets `volume.large_result`.
- **Plan cache statistics, Limited**: per-plan deltas of `execution_count` and `total_rows`, events with an unidentified principal (the DMV has none), the statement text through the normalizer. Its value is low (no principal); it is implemented only if the end-to-end Audit scenario shows it detects an export by volume (open question 11). No statement on this source is ever the agent's own (no session or principal to tie it to): the agent's own statements appear there and are reported.

#### The agent's own statements and the always-reported rules

- **The agent's own sessions** (security review H1; [ADR-0023](0023-mysql-mariadb-audit-sources-and-levels.md) decision 6 and its refinements, `databastion_core::audit::own`). Login, application and host names are set or chosen by whoever connects, and `EXECUTE AS LOGIN = 'databastion_agent'` by an account holding `IMPERSONATE` makes a record carry the agent's login. So "own" is tied to the **sessions the agent itself opened**:
  - at every connection, right after login, the connector reads its own `@@SPID` and `login_time` (`SELECT @@SPID, login_time FROM sys.dm_exec_sessions WHERE session_id = @@SPID`, a constant text; a session sees its own row without `VIEW SERVER STATE`, to verify), and records the session's **lifetime**: from `login_time` to the moment the connector closed or lost the connection, plus the statement timeout and 5 s;
  - the list of own sessions is kept per target in memory and **persisted** with the Audit position (bounded at 4 096 entries and 48 h), so after an agent restart the records of the agent's earlier sessions are still recognized; a session whose end is unknown (crash) is closed at the restart time;
  - a record is the agent's own only if **all** hold: its `session_id` is one of the agent's sessions and its `event_time` falls inside that session's lifetime (a `session_id` is reused by the server after the session ends, hence the time window); `server_principal_name` **and** `session_server_principal_name` are both the agent's login (a record made under `EXECUTE AS` has the impersonator as `session_server_principal_name`, so it is never the agent's own); on SQL Server Audit, `client_ip` is the agent's address as the server saw it at connect (`CONNECTIONPROPERTY('client_net_address')`, read in the same statement as `@@SPID`; only an IP literal counts); `application_name` / `client_app_name` is `databastion-agent` (an extra key, not relied on); it carries no signal; and it stays within the per-object row budget (SQL Server Audit has no row count, so each statement is charged the whole budget, as the MySQL log files). `client_hostname` is not used (dropped at parse).
  - **Exact text** on top of the session: the connector's own constant statements (session settings, the `@@SPID` read, `check()` probes including the `password_hash` bit of decision 4, catalog reads, the `sys.dm_xe_sessions` / `sys.dm_server_audit_status` / `sys.dm_xe_session_targets` reads, and the Audit polls of the set kept above) are matched by **exact text** against `sql.rs` constants or the generated text, never by prefix or shape; sampling statements are matched by their exact generated text for the object they name. A **cut** text (reassembly bound, `nvarchar(4000)` split) is never the agent's own.
  - **Sampling credits** (security review L5): each sampling statement sent registers a credit for (session, object, exact text) that expires with the statement's deadline plus the source's delivery delay (the audit `QUEUE_DELAY`, the XE `MAX_DISPATCH_LATENCY`, at most 5 minutes); a record that matches no unexpired credit is not the agent's own, even with the right text and session.
  - **Restart residual**: what the agent did between a crash and the persisted state is reported (loud), as on the other engines.
- **Statement-text objects, always reported** (the counterpart of [ADR-0045](0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) part (a) and [ADR-0049](0049-postgresql-statement-text-views-as-reads.md); list extended by the security review, M2): a read naming any of `sys.dm_exec_sql_text`, `sys.dm_exec_input_buffer`, `sys.dm_exec_query_stats`, `sys.dm_exec_cached_plans`, `sys.dm_exec_query_plan`, `sys.dm_exec_text_query_plan`, `sys.dm_exec_query_statistics_xml`, `sys.dm_exec_query_plan_stats`, `sys.fn_get_sql`, `sys.query_store_query_text`, `sys.query_store_plan`, `sys.fn_get_audit_file`, `sys.fn_xe_file_target_read_file`, `sys.dm_xe_session_targets`, `sys.fn_trace_gettable`, `DBCC INPUTBUFFER`, `sp_readerrorlog` / `xp_readerrorlog` (the error log holds failed statements and login names), `msdb.dbo.sysjobsteps` (`command`: job step texts, often with credentials) or `msdb.dbo.sysmail_mailitems` (bodies and attached query results) keeps that name as its object (the closed list is confirmed per image by a drift test before implementation), carries the always-reported mark (`MaskedEvent::always_report`, so `audit.configure` filters never drop it), and is never the agent's own except the exact texts of its Audit polls and status reads from its own sessions.
- **Credential-bearing objects, always reported** (the counterpart of [ADR-0050](0050-postgresql-credential-and-value-bearing-catalogs-as-reads.md); extended by M2): `sys.sql_logins`, `sys.syslogins`, `LOGINPROPERTY(… 'PasswordHash')`, `sys.credentials`, `sys.database_scoped_credentials`, `sys.linked_logins`, `sys.servers`, `sys.external_data_sources`, `sys.master_key_passwords`, `sys.symmetric_keys`, `sys.key_encryptions`, `sys.column_master_keys`, `sys.column_encryption_key_values`, `CERTPRIVATEKEY`, `PWDCOMPARE`, the DAC-only `sys.syslnklgns` and `sys.sysoledbusers`, `msdb.dbo.sysmail_server`, `msdb.dbo.sysmail_account`, `msdb.dbo.sysproxies`, `msdb.dbo.sysssispackages`, and in `SSISDB` `catalog.environment_variables` and the `internal.*` tables holding sensitive parameter values (names to verify) (candidate list; whether a no-secret shape can stay quiet, as ADR-0050 decision 2, is decided with the drift test). Never the agent's own, except the exact `password_hash` bit probe of decision 4 from its own sessions (it returns one bit, and no parameter changes what it reads, so it passes the ADR-0050 decision 5 test).
- **Value-bearing statistics and storage, always reported** (the counterpart of [ADR-0048](0048-statistics-catalogs-as-reads.md), M2): `DBCC SHOW_STATISTICS` and `sys.dm_db_stats_histogram` (histogram step values are column values) name the table whose statistics they read (`*` when the text does not name it); `DBCC CLONEDATABASE` (copies statistics, and is an extraction, see Signals) names `*`; `fn_dblog`, `fn_dump_dblog` and `DBCC PAGE` (raw log records and pages hold row values of every table) are reads of `*`. All always reported, never the agent's own.
- **Code that runs out of sight**: a call of a user function (a two- or three-part name followed by `(`, outside the closed per-version list of `sys` built-ins, P9-A obligation L4; T-SQL requires a schema for scalar user functions, so an unqualified call is a built-in or, in `FROM`, a table-valued function resolved in the default schema, to verify) adds `*` and is always reported, as ADR-0045. `EXECUTE` of a user procedure names the procedure itself as the object (procedures share the object namespace with tables in `sys.objects`) and is under the filters; it does not add `*` (proposed, open question 12). Dynamic SQL in text, `OPENROWSET`, `OPENDATASOURCE`, `OPENQUERY`, `EXEC … AT`, four-part names and `xp_cmdshell` add `*` and are always reported.
- **Measurement obligation** (M2): per source (SQL Server Audit with the specifications of the Partial proof, Extended Events with its required events) and per version, the drift test reads each object of the three lists above once with a low-privilege account and once with a privileged account, and checks that the read produces a record. Where it does not (expected for some DMVs on SQL Server Audit, which audits permission checks on schema objects, not every `sys` view; to verify), the list entry is kept, and `check()`'s local detail for that source says that reads of those objects are **invisible** there; docs/08 lists them per source.

### 7. I1, I3, I5 and local detection

- **I1**: the connector only opens outbound TCP connections to the declared target; no listener. It depends on no crate of `BANNED_CONNECTOR_DEPS` (`socket2` included), which the architecture test checks once `connector-sqlserver` is added to its `CONNECTORS` list.
- **I3**: the password stays on the agent host (zeroized, never logged); `LOGIN7` reaches only the verified TLS peer (decision 2). The `agent.yaml` block has no field the console can set.
- **I5**: one declared `host` / `port` per target; no SQL Server Browser, no `ENVCHANGE` routing, no `MultiSubnetFailover`, no availability-group topology following (an availability group is scanned by declaring the replica to read); remote objects (linked servers through synonyms, external tables, four-part names) are never read. Local detection ([ADR-0006](0006-target-discovery.md)) adds the local TCP port 1433 and the `sqlservr` process (SQL Server on Linux) as detected, unconfigured targets; no other port is probed.
- **Logon triggers** run at every login of the agent's account, before the connector can do anything (as MySQL `init_connect`): `check()` reports enabled server logon triggers (`sys.server_triggers`, `is_disabled = 0`, visibility to measure) as the existing note `security.login_event_trigger` (security review L10; its registry text made engine-neutral in P9-C).

### P9-A implementation obligations

From the security review of the proposal (Low findings). Each is an acceptance criterion of the P9-A pull request it belongs to; the ones that change a decision are already folded into it (L6 in decision 2, L10 in decisions 3, 4, 6 and 8, L11 in the status lines, L12 in decision 1), and so are L5, L7 and L8 (decisions 6, 1 and 2, and 5 and 6) and the M7 and M8 items the review allowed here (decisions 5 and 6).

1. **L1, parser bounds.** PLP values (the one `nvarchar(max)` column of Extended Events) are checked **chunk by chunk** against the cap before each chunk is buffered; on overflow the client sends `ATTENTION` (or closes the connection if the stream cannot be resynchronized). `RETURNVALUE` tokens are bounded like a row and skipped. A `ROW` beyond the statement's declared row limit, or a `COLMETADATA` with more columns than the statement selects, ends the statement and replaces the session. UTF-16 with lone surrogates is decoded lossily (U+FFFD), never rejected in a way that skips a value silently, and never panics. Fuzz targets for the TLS-in-`PRELOGIN` framing and for PLP reassembly join those of decision 1. Audit records are converted with **per-record panic isolation** ([ADR-0032](0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md)), as the other polled sources since #88.
2. **L2, collations.** Any collation is accepted on `NCHAR` / `NVARCHAR` (decision 1).
3. **L3, deprecated large types and type identity.** `text` and `ntext` are cut with `SUBSTRING([c], 1, 4000)` (they do not accept `LEFT`) before `CONVERT`; column types are decided on `sys.columns.system_type_id`, never on the type name or `user_type_id` (alias types, `CREATE TYPE … FROM nvarchar(…)`, would otherwise hide the base type).
4. **L4, built-in list.** A closed, per-version list of the `sys` built-in functions (the ADR-0045 part (b) pattern), checked by a drift test on each matrix image, so that a two-part `sys.f(` is a built-in only when listed; anything else with a schema is a user function (`*`, always reported).
5. **L5, sampling credits.** Decision 6 ("The agent's own sessions"): credits with expiry; a cut text is never the agent's own.
6. **L7, `LOGIN7` fields and lockout.** Decisions 1 and 2: no `fReadOnlyIntent`, a zero `ClientID`, mirroring `ENVCHANGE` 13 ignored, `CHECK_POLICY` lockout documented and a locked login reported.
7. **L8, Stretch tables and own status reads.** Decision 5 (Stretch tables are `skipped_remote`) and decision 6 (the `sys.dm_xe_session_targets`, `sys.dm_xe_sessions` and `sys.dm_server_audit_status` reads are exact own texts).
8. **L9, per-table deadline and schema locks.** The per-table sampling deadline is the job's statement timeout, **bounded at 30 s** whatever the job asks. Documented in docs/08: a sampling read holds a schema-stability (Sch-S) lock for its duration, which blocks a schema-modification (Sch-M) lock (`ALTER TABLE`, index rebuilds offline, partition switches): a DDL statement waits up to 30 s behind the agent, and statements queued behind that DDL wait too. `LOCK_TIMEOUT` makes the agent give up when it is the one waiting, not when it holds the lock.
9. **L13, dev secrets and refusal test.** The dev and CI `sa` password (`MSSQL_SA_PASSWORD`) is a fake value, generated per run or fixed as a fake marker, never logged by the harness and never used by the agent. An integration test proves that `check()` refuses an `sa` / `sysadmin` login (`privilege.refused`; no Discovery, no Audit), and one each for `db_owner` in an unmonitored database, `IMPERSONATE ON LOGIN`, and `ALTER ANY EVENT SESSION`.
10. **M7, RLS when the catalog is invisible.** Decision 5: skip the database's tables, note `coverage.rls_not_verifiable`; the matrix measures the catalog's visibility first.
11. **M8, signal lists.** Decision 6, Signals: `signature.remote_data_access` and `signature.backup_database` include the listed procedures and statements; a test per entry.

## Consequences

- `agent/deny.toml` gains `aws-lc-rs` and `aws-lc-sys` in `[bans]` (decision 1, security review L12).
- A fifth own protocol client: about 3 000 lines whose robustness against a hostile server is the project's (fuzzed, property-tested), and no new crate in the agent's lock (no `aws-lc`, no `encoding_rs`: the server converts to `nvarchar`).
- **TLS everywhere, including loopback, with an operator-installed certificate that names the host** (decision 2, security review M9). Servers that still use SQL Server's fallback self-signed certificate (no SAN, regenerated at each start) cannot be monitored until a certificate is installed; there is no way around it. The E2E harness, which uses `disable_insecure` for other engines, needs a dev CA for SQL Server.
- **No Audit on SQL Server 2019 through SQL Server Audit**; 2019 Audit needs an Extended Events session and `VIEW SERVER STATE`, which exposes every session's statement text to the agent's account (as `pg_read_all_stats` on PostgreSQL), contained by the normalizer and the always-reported rules.
- **Partial at best**, never Full, in this ADR; reads through procedures and views under ownership chaining are attributed to the procedure or view on SQL Server Audit.
- Discovery does not sample views, computed columns, RLS tables, Always Encrypted columns, CLR types or remote objects, and reports masked columns: coverage is visible through notes and counters.
- Azure SQL Database, Managed Instance, Entra ID and Windows authentication are not supported.
- `docs-keeper` (P9-G): [08-engine-capabilities.md](../08-engine-capabilities.md) matrix row and sections written from the measurements; [05-security.md](../05-security.md#recommended-database-accounts-read-only) account block (the minimal variant); README "Supported databases"; [03-tech-stack.md](../03-tech-stack.md) (own TDS client); `agent.example.yaml` (`sqlserver` block).
- `console-engineer` (P9-E): the `sqlserver` engine, its notes, signals and audit sources rendered.

### Residual risks

- **Own parser** of TDS, the Extended Events XML and T-SQL texts from a possibly hostile server or writer; bounded, fail-closed and fuzzed, as the other own clients.
- **No server-side read-only mode or statement timeout**: read-only rests on grants and the closed statement set; a statement that the server keeps running after an `ATTENTION` was lost is stopped only when the connection closes.
- **`READ UNCOMMITTED`** can sample a value that is rolled back later; it is masked like any value.
- **`#temp` tables and `tempdb`** are writable by every login; the agent never writes, the residual is the account's, as MySQL's temporary tables.
- **Server-side conversion** (`CONVERT`, `LEFT`) runs on sampled values; built-ins only.
- **`TABLESAMPLE` bias**: page sampling, clustered values, possibly short samples.
- **Dynamic data masking** limits what Discovery classifies on masked columns, by design of the agent's grants.
- **Ownership chaining** hides table reads from SQL Server Audit behind the procedure or view; Extended Events sees the statements but is lossy.
- **Logon triggers** run before the connector acts; reported, not prevented.
- **Own-session window.** Within the lifetime of one of the agent's sessions, its `session_id` belongs to the agent alone; a record from that session with both principal names equal to the agent's login is the agent's (or comes from code the agent's statements ran implicitly, which decision 5 avoids). After an agent crash, the end of the last sessions is taken as the restart time, so a short window of another client reusing such a `session_id` before the restart could be taken for the agent's; bounded by the exact-text and credit rules.
- **Poll parameters** (decision 6): until the matrix verifies that `initial_file_name` cannot widen the set of files read beyond the literal pattern, the polls are not exempt and are reported (noisy, fail closed).
- **Invisible reads per source**: reads of some always-reported objects may produce no record on SQL Server Audit (decision 6 measurement obligation); `check()` says which, per source.
- **Version facts** (lifecycle dates, permission names per version, Audit columns filled on boxed SQL Server) are from Microsoft documentation as remembered and marked "to verify"; the matrix measurements decide before acceptance.

## Rejected alternatives

- **`tiberius`** (option A): see decision 1 (a C crypto provider compiled in, no pinned-CA-only trust, 2 GiB per value and every type decoded, server text in errors and its own `tracing` events). Reconsidered if it gains a caller-provided rustls configuration and an optional crypto provider.
- **`mssql-tds`**: OpenSSL and `native-tls` on Linux, `socket2`; banned.
- **An ODBC driver (msodbcsql) or `sqlcmd`**: C libraries, OpenSSL, process spawning ([ADR-0039](0039-engine-scope-expansion.md) rejected alternatives).
- **`disable` / `disable_insecure` modes**: `LOGIN7` carries the password in a reversible form; an unencrypted mode would send it.
- **Accepting `ENCRYPT_OFF`** (login-only encryption): the samples and statements would travel in clear after login, and an active attacker can take over the session.
- **NTLM, or Kerberos through `sspi`**: NTLM is refused by ADR-0039; Kerberos needs keytab handling and a library that also carries NTLM, for a first version that SQL logins serve.
- **SQL Server Audit through `fn_get_audit_file` on 2019** with `CONTROL SERVER`: on the refusal list; the agent's credential would control the server.
- **Reading local `.sqlaudit` files**: undocumented binary format (to verify), same-host Linux only.
- **Creating the audit or the Extended Events session from the agent**: needs `ALTER ANY SERVER AUDIT` / `ALTER ANY EVENT SESSION` (refusal list), and the agent would configure what it is supposed to prove.
- **`db_datareader` as the default**: every schema, present and future, of every monitored database; kept as the opt-in extended variant.
- **`VIEW DEFINITION` for richer metadata**: exposes module bodies with their literals.
- **Sampling views, computed columns or RLS tables**: runs user code with the definer's or the policy's logic on every read.
- **`READ COMMITTED` (locking)**: the agent would wait on and briefly block writers; `NOLOCK` hints per table instead of the session level: the same effect, more text to match exactly.
- **Own statements identified by login, application name and client address** (the first revision): application and host names are set by the client, Extended Events has no client-address action, and `EXECUTE AS LOGIN` makes a record carry the agent's login (security review H1); replaced by the agent's own sessions and both principal names (decision 6).
- **The audit file pattern as a poll parameter**: a stolen agent credential could replay the exact poll text with another pattern and read any audit-format file unseen (security review M1).
- **Sampling a database whose security policy catalog is invisible, with a note**: runs predicate code the agent cannot see and silently omits the rows it hides (security review M7).
- **Counting batch and RPC events on Extended Events**: each statement would be counted two or three times, and `rpc_completed` text holds parameter values (M1, M5).
- **Report Full with Extended Events row counts**: lossy by default, alterable without proof, objects only from text; not proven (open question 8).

## Open questions (for the maintainer)

Each with the recommendation of this ADR; none is decided until the maintainer confirms it.

1. **SQL Server 2017** is in extended support until 2027-10-12 (to verify). Support it until then?
   **Recommended**: no. It ends within a year of the connector shipping, has no TDS 8.0, and the ROADMAP sets 2019 as the floor; the connector refuses majors below 15.
2. **Azure SQL Database / Managed Instance**: in scope for phase 9?
   **Recommended**: no; refused by `EngineEdition`. A later ADR covers gateway redirection (routing to a host named by the service, I5), Entra ID, `CONTROL DATABASE` for `fn_get_audit_file` and audit to blob storage.
3. **Default TLS mode**: `strict`, `mandatory` or `auto`?
   **Recommended** (revised after the security review, L6): `auto` as decision 2 describes it: **strict first**; one fallback to `mandatory` (still fully encrypted, certificate verified) only when the strict handshake fails before any TDS byte; "strict seen" persisted per target, after which no fallback happens. Both modes keep the password inside verified TLS; strict also protects `PRELOGIN`. If 2019 support is dropped before the connector ships, make `strict` the only mode.
4. **Discovery with an account on the refusal list** (`sysadmin`, `db_owner`, `CONTROL SERVER`, audit administration): refuse Discovery too, or only Audit (ADR-0039's text)?
   **Recommended**: refuse both, with `privilege.refused`. Such an account unmasks masked columns, reads password hashes and audit files and can rewrite the audit; Discovery needs none of it, and running anyway would make the agent's credential the most powerful one on the server.
5. **Contained database users** (`CREATE USER … WITH PASSWORD` in a contained database, no login): support them?
   **Recommended**: later, as a follow-up; `LOGIN7` is the same, but the account is per database and its permission checks differ.
6. **Row-level security tables**: skip them (this ADR), or sample them when the predicate function passes an allow-list, as [ADR-0015](0015-postgresql-connector-decisions.md) decision 3?
   **Recommended**: skip in phase 9; an allow-list of inline TVF bodies would need `VIEW DEFINITION` on the function and a T-SQL expression walker, and predicates can call further user functions. Revisit if users report large RLS gaps. **When the security policy catalog is not visible** to the account (security review M7), skip every table of that database with `coverage.rls_not_verifiable` (decision 5) rather than sample with a note; if the matrix shows the minimal variant cannot see the catalog on some version, revise the grant before Discovery ships there.
7. **Isolation level**: `READ UNCOMMITTED` (this ADR) or `READ COMMITTED`?
   **Recommended**: `READ UNCOMMITTED`. The agent never blocks or waits on writers, which matters more on SQL Server than elsewhere because locking `READ COMMITTED` is its default (without RCSI); an uncommitted sampled value is no I2 issue (masked as any other).
8. **Full for SQL Server**: pursue a later refinement (Extended Events with `NO_EVENT_LOSS` and row counts, possibly merged with SQL Server Audit's principals and objects)?
   **Recommended**: not in phase 9. Measure first, after the Partial sources run; propose it only with proofs per version, as ADR-0037 did for PostgreSQL.
9. **Server audit `WHERE` predicate**: any predicate caps at Limited (this ADR), or accept a predicate that only excludes the agent's own login?
   **Recommended**: any predicate caps in phase 9 (fail closed); a parser for predicates that provably exclude only the agent's login can come later, if operators ask.
10. **Visibility of the audit specification catalogs**: which grant, if any, to accept for the Partial proof?
   **Recommended** (revised after the security review, M3): **measure `VIEW SERVER SECURITY AUDIT` and `VIEW DATABASE SECURITY AUDIT` first** (decision 4); if they make the server audit and the specification catalogs visible, nothing else is accepted. Only if they do not, consider `VIEW ANY SECURITY DEFINITION` (2022+), accepted only if the measurements show it exposes no secret and `password_hash` stays `NULL` through it. `VIEW ANY CRYPTOGRAPHICALLY SECURED DEFINITION` is on the refusal list and `VIEW ANY DEFINITION` (module bodies everywhere) on the over-privilege list; neither is ever an Audit grant. Otherwise the level stays Limited.
11. **Plan cache statistics source** (`sqlserver_query_stats`, Limited, no principal): implement it in phase 9?
   **Recommended**: only if the end-to-end scenario shows it raises an incident on an export by volume; otherwise drop it and report None when neither SQL Server Audit nor Extended Events is usable.
12. **`EXECUTE` of a user procedure**: name the procedure (this ADR), or also add `*` and always report (the ADR-0045 rule for stored functions)?
   **Recommended**: name the procedure, under the filters, and document the ownership-chaining residual. Most SQL Server applications read through procedures; `*` on each call would drown the always-reported class. Functions keep the ADR-0045 rule (`*`, always reported). **Documented consequence** (security review): on SQL Server Audit, a procedure that reads statement texts or other listed objects (for example the community `sp_WhoIsActive`, which reads `sys.dm_exec_sql_text` and `sys.dm_exec_requests`) is recorded and reported by the procedure's name only: under ownership chaining or module signing its inner reads of the always-reported objects produce no record of their own, so those reads are not always reported on that source. Extended Events records the inner statements (`sp_statement_completed`), so there they are. docs/08 says so, and operators can scope a policy on such procedure names.
13. **Developer edition EULA for CI**: the maintainer reads the license terms (not reachable from this environment) and accepts them for the project's dev environment and CI; or should CI use Express?
   **Recommended**: Developer, once the maintainer has confirmed that the terms allow automated testing on hosted CI runners (development and test use, no production); Express as the fallback, and one Express job in the matrix in any case to test edition detection.
