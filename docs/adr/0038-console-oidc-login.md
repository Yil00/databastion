# ADR-0038: Console login with OpenID Connect

- **Status**: Proposed (the proposed defaults of decision 16 are pending maintainer confirmation)
- **Date**: 2026-10-04
- **Context references**: ROADMAP P8-A; [EDITIONS.md](../EDITIONS.md) (OIDC is Community, allocation rule 1); [05-security.md](../05-security.md#authentication-rate-limits); [ADR-0024](0024-shared-rate-limits.md) (shared rate limits); security review of this ADR (M1 to M4, L1 to L10)

## Context
Console users are local only today. The `users` table holds a lowercased username (`^[a-z0-9][a-z0-9._-]{0,63}$`), an argon2id hash (`password_hash`, not null) and one role of the `user_role` enum, `admin` or `analyst` (`console/src/db/schema.ts`). The only way to create a user is `pnpm admin:bootstrap`, which creates the first administrator and refuses to run once a user exists. Sessions are cookie sessions (`console/src/server/auth/session.ts`): 256 random bits, SHA-256 stored, `HttpOnly`, `SameSite=Strict`, `__Host-` prefixed and `Secure` in production, 12 h absolute lifetime, 2 h idle timeout, HMAC-derived CSRF token. Logins are rate limited per IP, per (username, IP) and per username, with device cookies, in counters shared through PostgreSQL ([ADR-0024](0024-shared-rate-limits.md)). Every login and logout is written to the console audit log (`user.login`, `user.logout`).

[EDITIONS.md](../EDITIONS.md) puts OIDC in the Community edition (baseline security), and SAML, SCIM, multi-tenancy and fine-grained RBAC in the Enterprise edition. The maintainer asked for an OIDC login "inspired by what Grafana did", tested with Keycloak.

Grafana's Generic OAuth integration (`[auth.generic_oauth]`) is the reference most operators know. It maps an identity provider's claims to Grafana attributes with JMESPath expressions (`login_attribute_path`, `email_attribute_path`, `name_attribute_path`, `groups_attribute_path`, `role_attribute_path`), can refuse a login whose role expression yields nothing (`role_attribute_strict`), filters by `allowed_groups` and `allowed_domains`, controls user creation (`allow_sign_up`), can redirect straight to the provider (`auto_login`), refreshes tokens (`use_refresh_token`), uses PKCE (`use_pkce`), logs out at the provider (`signout_redirect_url`) and can leave roles to the Grafana UI (`skip_org_role_sync`). Two Grafana lessons matter here:
- Grafana's Generic OAuth takes explicit `auth_url`, `token_url` and `api_url` settings. OIDC discovery from the issuer removes three settings that operators get wrong.
- Grafana used to match an OAuth login to an existing user by e-mail. With providers where the e-mail claim is not unique or not verified, this allowed account takeover (CVE-2023-3128, Azure AD). Grafana then disabled e-mail lookup by default (`oauth_allow_insecure_email_lookup`).

DataBastion's console holds the map of where sensitive data lives, the incidents, and the right to start scans and change Audit settings. Its login must not be weaker than the local login it complements.

## Decision
1. **Protocol: OpenID Connect Authorization Code flow with PKCE (S256), confidential client.** Only `response_type=code` with the `query` response mode; `form_post`, the implicit and hybrid flows, and plain OAuth 2.0 without an `id_token` are refused. PKCE is always used, even though the client is confidential. The client authenticates at the token endpoint with `client_secret_basic` (default) or `client_secret_post`, documented as weaker (the secret travels in the request body, where proxies and provider logs are more likely to record it); `private_key_jwt` can come later as a compatible addition.
2. **Discovery from the issuer URL.** The console reads `<issuer>/.well-known/openid-configuration` and requires its `issuer` to equal the configured one exactly. The issuer and every endpoint must be `https://`. A plain-HTTP issuer is accepted only on a loopback address and outside production, as for the SMTP rule ([ADR-0017](0017-alerting.md)). When the provider advertises `authorization_response_iss_parameter_supported`, the `iss` of the authorization response is checked too (RFC 9207). The configuration comes from the console's environment only, never from a user request, so discovery is not an SSRF vector. Every call to the provider (discovery, JWKS, token, userinfo, revocation) follows **no redirect**, has a 5 s timeout and a size cap checked before parsing (discovery 64 KiB, JWKS 256 KiB, token and userinfo responses 64 KiB); the provider hosts are logged at startup. A provider unreachable at startup does not stop the console: the local login works (decision 11), and discovery is retried with backoff.
3. **TLS to the provider is always verified.** There is no "skip verify" option. `DATABASTION_OIDC_CA_FILE` adds a private CA for the provider's endpoints only.
4. **`id_token` validation.** An `id_token` is required in the token response. Its signature is checked with the provider's JWKS. The allowed algorithms are the intersection of `DATABASTION_OIDC_ID_TOKEN_ALGS` (default `RS256,PS256,ES256`) and the provider's `id_token_signing_alg_values_supported`; `none` and the `HS*` algorithms are always refused. The JWK selected by `kid` must have a `kty` matching the header's algorithm, an `alg` equal to it when present, and `use` absent or `sig`. The JWKS cache honors `Cache-Control` up to 24 h, is refetched at least every hour, and at most once per minute on an unknown `kid`. Then: `iss` equal to the issuer, `aud` containing the client id (and `azp` equal to it when `aud` has several values), `exp` in the future, `nbf` (when present) in the past, `iat` not in the future and not older than 10 minutes, with 60 s clock skew, and `nonce` equal to the one sent. The userinfo endpoint is called only when `DATABASTION_OIDC_USE_USERINFO=1`; its `sub` must equal the `id_token`'s `sub`, and its claims are merged under those of the `id_token`.
5. **State, nonce, CSRF and landing page.** `GET /api/auth/oidc/start` creates a 256-bit `state`, a 256-bit `nonce` and the PKCE verifier, kept in a cookie encrypted with AES-256-GCM under a new HKDF subkey `oidc-state.v1` of `DATABASTION_ENCRYPTION_KEY`: `__Host-` prefixed, `HttpOnly`, `Secure` (production), `SameSite=Lax`, 10-minute lifetime. `Lax` is needed because the callback is a cross-site top-level navigation from the provider; the session cookie itself stays `SameSite=Strict`. **Single use** is enforced server side: the callback records the hash of the consumed state (kept until the cookie's expiry) and refuses a state already recorded. A callback without a matching, unexpired, unused state is refused and audit logged. The callback answers with a same-origin page that navigates to the console, not with a cross-site redirect chain, so the `Strict` session cookie is sent on the first page load. A successful login always lands on `/agents`, as the local login does: there is **no `return_to`** parameter. If one is added later, it lives in the encrypted state cookie only, and is a same-origin path (a single leading `/`, never `//` or `/\`, parsed against `DATABASTION_PUBLIC_URL` and refused if its origin differs). A callback carrying an `error` parameter shows a generic failure page; the provider's `error_description` is never echoed.
6. **Identity key: (`iss`, `sub`), never the e-mail.** OIDC identities live in a new table (`user_identities`: issuer, subject, user id, unique on (issuer, subject)). A login finds its user by (`iss`, `sub`) only. The e-mail, the login claim and the name are attributes, refreshed at each login. There is **no automatic linking** of an OIDC identity to an existing local user by e-mail or by username, verified or not: the e-mail claim is chosen or edited by the user at many providers, and the Grafana CVE above shows the outcome. **Linking is self-service only**: a local user, in an authenticated local session, chooses "Link single sign-on"; the console starts the OIDC flow and binds the returned (`iss`, `sub`) to the current user, provided that identity is not bound already. An administrator cannot link an identity to someone else's account; administrators approve pending logins only as **new** users (decision 8). Each link is audit logged with the session method and the (`iss`, `sub`).
7. **Claim mapping with JMESPath expressions**, as in Grafana, evaluated on the merged claims (decision 4):
   - `DATABASTION_OIDC_LOGIN_ATTRIBUTE_PATH` (default `preferred_username`), `DATABASTION_OIDC_EMAIL_ATTRIBUTE_PATH` (default `email`), `DATABASTION_OIDC_NAME_ATTRIBUTE_PATH` (default `name`): display attributes only.
   - `DATABASTION_OIDC_GROUPS_ATTRIBUTE_PATH` (default unset) and `DATABASTION_OIDC_ROLE_ATTRIBUTE_PATH`: an expression that must yield `admin` or `analyst` (e.g. `contains(groups[*], 'databastion-admins') && 'admin' || 'analyst'`).
   - **Authorization reads only provider-controlled claims.** The role, groups and allow-list expressions must read claims that only the provider's administrators set (groups, roles). The documentation forbids `email`, `preferred_username`, `name` and any attribute a user can edit at the provider; the Keycloak test realm includes a user who edits those attributes to try to gain `admin`, and the test expects it to fail.
   - An evaluation error, a non-string result, or anything other than exactly `admin` or `analyst` (case-sensitive) counts as **no role**.
   - `DATABASTION_OIDC_ROLE_ATTRIBUTE_STRICT=1`: a login whose expression yields no role is refused. Without it, such a login gets `analyst`, never `admin`.
   - The login claim is lowercased and must match the console's username pattern, otherwise the login is refused (no silent rewriting that could make two identities collide on one display name). Uniqueness of OIDC users rests on (`iss`, `sub`). A login claim equal to an existing username is refused, not merged.
   - Bounds: expressions at most 1 KiB, claims payload at most 64 KiB, groups at most 256 entries of at most 256 characters, evaluated with a JMESPath library under the console's license gate.
8. **Who may log in.**
   - `DATABASTION_OIDC_ALLOWED_GROUPS`: comma-separated; when set, at least one mapped group must match.
   - `DATABASTION_OIDC_ALLOWED_DOMAINS`: comma-separated; when set, `email_verified` must be `true` and the domain after the **last** `@` must equal one of the listed domains exactly (case-insensitive). It is never a suffix match: `example.com` admits neither `evil-example.com` nor `sub.example.com`.
   - `DATABASTION_OIDC_ALLOW_SIGN_UP`: when on, an unknown (`iss`, `sub`) that passes the filters and the role mapping becomes a console user. When off, the attempt is refused and recorded as a **pending login**. The pending-login view shows the issuer and subject first, then the mapped login, e-mail, groups and time, and flags `email_verified: false`. An administrator can approve it as a new user bound to that (`iss`, `sub`), choosing its role, or discard it. Pending logins expire after 7 days and are capped at 1000; evictions at the cap are counted and shown in the view.
   - A user disabled in the console (`disabled_at`) cannot log in by any method.
9. **Role synchronization.** The mapped role is applied at every login, and at every token refresh when refresh is on. `DATABASTION_OIDC_SKIP_ROLE_SYNC=1` keeps roles managed in the console instead (Grafana's `skip_org_role_sync`); a user created by sign-up then starts with the mapped role under strict mode, else `analyst`, never `admin` by default. When no role expression is set, roles are managed in the console and role sync is implicitly off. A demotion applied at login or refresh ends the user's other sessions. Each role change is audit logged with its source (`oidc` or `user`).
10. **Only the two existing roles.** OIDC maps to `admin` or `analyst`. Fine-grained RBAC (per target or per team), team synchronization from groups, multi-organization mapping, SAML and SCIM are Enterprise features ([EDITIONS.md](../EDITIONS.md)) and are not built here, not even as stubs.
11. **Local login and break-glass.** `DATABASTION_LOCAL_LOGIN` takes `enabled` (all local users), `admins` (local users with the `admin` role only, the break-glass path) or `disabled` (`/api/auth/login` answers `404`, the form is hidden; recovery means changing the variable and restarting, which requires host access). Users without a local password cannot use the local login. With `admins`, the console logs an error at startup if no enabled local administrator with a password exists. While OIDC is enabled, every successful local administrator login raises a system alert `user.local_login`, so break-glass use is visible.
12. **`DATABASTION_OIDC_AUTO_LOGIN=1`** sends unauthenticated users straight to the provider. `/login?local=1` still shows the local form when the local login is not `disabled`.
13. **Sessions.** An OIDC login creates the same console session as a local login (2 h idle), tagged with its method and the provider's `sid` when present. Its absolute lifetime is `DATABASTION_OIDC_SESSION_MAX_AGE` (default 12 h, never above 12 h). Without refresh, a user disabled at the provider keeps their console session until it expires: a documented residual risk. With `DATABASTION_OIDC_USE_REFRESH_TOKEN=1`, the console stores the refresh token encrypted at rest (AES-256-GCM under a new HKDF subkey `oidc-tokens.v1` of `DATABASTION_ENCRYPTION_KEY`) and refreshes it at most every 5 minutes on user activity; a failed refresh ends the session. **Without a usable server key, the console refuses to start** when OIDC is enabled (the state cookie needs `oidc-state.v1`, and refresh needs `oidc-tokens.v1`). Access tokens and `id_token`s are not kept. Back-channel logout (OIDC Back-Channel Logout 1.0, by `sid`) is a planned compatible addition.
14. **Logout.** Logout stays a `POST` with the CSRF token. It deletes the session; when a refresh token is held and the provider advertises a `revocation_endpoint`, the console revokes it there (RFC 7009), then deletes it. When the provider advertises an `end_session_endpoint`, the console then performs RP-initiated logout with `client_id`, `logout_hint` (no `id_token` is kept, so no `id_token_hint`) and `post_logout_redirect_uri`, unless `DATABASTION_OIDC_SIGNOUT_REDIRECT_URL` overrides the target.
15. **Rate limits and audit log.** `/api/auth/oidc/start` and `/api/auth/oidc/callback` are rate limited per client IP (when known), and failed callbacks also against a global budget, through the shared counters ([ADR-0024](0024-shared-rate-limits.md)), fail closed like the other authentication limits. New audit actions: `user.login` with `method: oidc`, `user.login_denied` with a reason from a closed list (`state`, `nonce`, `iss`, `token`, `id_token`, `provider_error`, `rate_limited`, `group`, `domain`, `email_unverified`, `role`, `sign_up`, `disabled`, `username`), `user.signup`, `user.pending_login_approve`, `user.identity_link`, `user.role_change`, and the system alert `user.local_login` (decision 11). Entries reference the user id, not only the display username. Tokens, codes, the state, the nonce and raw claims are never logged nor stored outside decision 13. The client secret and the contents of `_FILE` variables never appear in startup errors or logs.
16. **Configuration** by environment variables, in the console's existing style (secrets as `_FILE` for Docker secrets). The defaults marked *proposed* are pending maintainer confirmation:

17. **Tests and dev environment.** A Keycloak service in `dev/` with a seeded realm: a confidential client, an admin group, an analyst user, a user with an unverified e-mail, and a user allowed to edit their username, e-mail and name, who tries to gain `admin` through them (decision 7). It is used by console integration tests and by an end-to-end scenario (login, role mapping, refused group, pending login, self-service link, logout). The OIDC client library and the JMESPath library are chosen in the implementation PR, under the console license gate (Apache 2.0 compatible).

## Consequences
- The schema changes: `users.password_hash` becomes nullable (with a check that local users keep one), new `user_identities`, `oidc_pending_logins` and consumed-state tables, sessions tagged with their method. Versioned migrations, as usual.
- A user management page becomes necessary (approve pending logins, change roles when role sync is off, disable users), with a "Link single sign-on" action on the user's own profile. Local user creation by an administrator comes with it; it does not exist today.
- **Pending maintainer confirmation**: the proposed defaults of decision 16 (`ALLOW_SIGN_UP=0`, `ROLE_ATTRIBUTE_STRICT=1`, `LOCAL_LOGIN` `admins` when OIDC is on). `admins` can surprise an install whose only administrator logs in through OIDC without a local password; the startup error of decision 11 points it out. This ADR moves to Accepted once the maintainer confirms or changes them.
- One provider per console. Several providers would multiply the configuration; the identity key already supports them (the issuer is part of it), so this can be added later without a schema change.
- Residual risks: without refresh or back-channel logout, a user disabled at the provider keeps the console for up to the session maximum age; a provider compromise gives console access up to the mapped role (the break-glass local admin does not prevent this); the role expression is operator-written and can be wrong (strict mode and the provider-controlled-claims rule limit the damage).
- No change to the agent protocol or to the agents (I1 to I7 unaffected).

## Rejected alternatives
- **Generic OAuth 2.0 without OIDC** (Grafana's `api_url` user-info pattern): no signed, audience-bound identity token, so the console would trust an access token meant for another client; and three endpoint settings instead of one issuer.
- **Matching or linking users by e-mail** (even "verified"), or administrator-driven linking of an identity to an existing account: account takeover when the provider lets users set or change their e-mail, or when several tenants share one provider (CVE-2023-3128), and an administrator cannot verify who holds a `sub`.
- **SAML in Community**: an Enterprise feature per [EDITIONS.md](../EDITIONS.md); OIDC covers the baseline-security need.
- **Trusted proxy authentication header** (`X-Forwarded-User` from an auth proxy): safe only with a strict trust configuration (a proxy the console alone can be reached through, and a header the proxy always overwrites); a misconfiguration gives login as anyone. It could be a separate ADR later, with a mandatory shared secret or mTLS to the proxy.
- **A TLS "skip verify" option for the provider**: the token exchange would then be open to an attacker on the path; a private CA file covers the legitimate need.
- **Storing access and ID tokens in the browser** (stateless sessions): logout and disablement could not be enforced server side, and the console already has server-side sessions.
- **`form_post` response mode**: needs a cross-site `POST` to the callback, which the `SameSite` cookie rules and the console's Origin check are designed to refuse.
