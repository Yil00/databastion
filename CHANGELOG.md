# Changelog

All notable changes to DataBastion are recorded here.

The notes of the next release are curated by hand in the "Unreleased" section; at each release they are moved automatically under the new version, and become the GitHub release notes, see [RELEASE.md](RELEASE.md). Do not edit the released sections by hand.
The project follows [semantic versioning](https://semver.org/).

## Unreleased

### ⚠️ Upgrade notes
- **End-of-life PostgreSQL and MariaDB servers are refused** ([ADR-0039](docs/adr/0039-engine-scope-expansion.md) decision 1). The PostgreSQL connector now refuses servers older than PostgreSQL 14 (`server_version_num` below 140000), and the MySQL / MariaDB connector MariaDB servers older than 10.11 (MariaDB 10.6 reached its end of life in July 2026), at connection time, as it already did for MySQL older than 8.0.
  - **Impact**: a PostgreSQL 12 or 13 target, or a MariaDB 10.6 target, that an older agent accepted shows as unreachable with the failure code `unsupported` after the agent upgrade, and the agent logs "server version not supported (PostgreSQL 14+)" or "server version not supported (MySQL 8.0+ or MariaDB 10.11+)". Nothing is sampled and no Audit runs on it.
  - **Before upgrading the agent**: upgrade those servers to PostgreSQL 14+ or MariaDB 10.11+, or leave the agent that monitors them on its current version until then.
- **Do not downgrade the console once it has stored SQLite findings** (P10-E). An older console (0.9 or earlier) does not know the `sqlite` engine nor the target scope of SQLite location exceptions: its worker would apply exceptions that are not scoped to a target to every SQLite file. To downgrade, first delete those findings (for example `DELETE FROM findings WHERE engine = 'sqlite';` as the console's owner role, after a backup), and expect migration `0048`'s column to stay unused.

- **Agent: the SQLite connector, Discovery only** ([ADR-0059](docs/adr/0059-sqlite-connector.md), ROADMAP P10-A; not released yet: results reach a console that lists `engine.sqlite` only, P10-E). A `sqlite` target is one declared database file (`targets[].sqlite.path`, with `max_statement_ms` and `rollback_mode`; no host, account or secret): no directory, glob or search, and the path is never sent nor logged. The file is read by the bundled SQLite 3.53.2 (`rusqlite` 0.40, a reviewed exception to "no C client library") **only in a sandboxed reader process**: the agent binary in its hidden `sqlite-reader` mode, its environment cleared, no new privileges, not dumpable, resource limits, Landlock read access to the file's directory only, and a seccomp filter without sockets, processes or writes, killed at its deadline; a reader that crashes costs one unit, never the agent. Read-only by layers: no file the agent could write is read, the file system must be mounted read-only for the agent, no symlink, one hard link, no network or FUSE file system, every descriptor checked read-only. Audit is `none`. Requirements: a Linux kernel with Landlock enabled; under the systemd unit, the unit now also allows the `@sandbox` system calls (`landlock_*`, `seccomp`). WAL databases are read while their application holds them open; rollback-journal files only with `rollback_mode: read`.
- **Console: SQLite targets** ([ADR-0059](docs/adr/0059-sqlite-connector.md), ROADMAP P10-E; not released yet). The console lists `engine.sqlite`, so agents send their SQLite targets and findings. An exception without either still applies to the other engines. SQLite names are compared with case, and trailing spaces count (ADR-0059 decision 6). Migration `0048` adds `policy_exceptions.cross_target`. With several console replicas, set `DATABASTION_AGENT_TOKENS_HOLD=0.9` during the upgrade (new value): a 0.9 replica refuses SQLite targets and findings. Remove the hold only once every replica and every worker runs the new build; at its first start, a worker of this build evaluates the stored SQLite findings again, once (audit entry `findings.reevaluate_target_scoped`).

- **Agent: the Firebird connector, lot 1: the wire client and `check()`** ([ADR-0060](docs/adr/0060-firebird-connector.md) decision 10, ROADMAP P10-B; not released yet: Firebird targets reach a console that lists `engine.firebird` only, P10-E). A `firebird` target is a loopback IP literal (`127.0.0.1` or `::1`) with `firebird.databases` (`name`, the label sent, and `attach`, an alias or path never sent to the console; the server receives it in clear on loopback before wire encryption starts, so prefer an alias), `firebird.peer_uid` (default `firebird`; numeric when the agent runs in a container, detected by its marker files, its cgroup, a user or pid namespace, an overlay root or `KUBERNETES_SERVICE_HOST`; `0` only with `peer_uid_root: true`), `firebird.tunnel` for an operator-run tunnel and `firebird.extended_grants`. The agent's own client speaks the remote protocol 16 only (no `fbclient`, no driver crate), authenticates with `Srp256` only (constant-time arithmetic, the password never sent) and requires `ChaCha64` or `ChaCha` wire encryption (Arc4 and unencrypted sessions refused), with key confirmation before the first encrypted byte. Before anything is sent, the server side of the connection must be owned by `peer_uid` (`/proc/net/tcp`), and once attached the server must see the agent's own socket (no forwarder) unless `tunnel: true`. `check()` refuses Firebird 3.0 and 6.0, checks the wire encryption and the read-only transaction as the server reports them, and evaluates the account against the refusal list (`SYSDBA`, `RDB$ADMIN`, the database owner, the security-database administrator, the system privileges through every role the account could use, readable verifier relations, and local or global authentication mappings to `SYSDBA` or `RDB$ADMIN` that the account's login could match) and the over-privilege list (`server_config_readable` when `RDB$CONFIG` is readable). Discovery and Audit come with lots 2 and 3; the Audit level is `none` (`audit.source_not_configured`). The core enforces the contract's Firebird rules (P10-C review C1): a `firebird` target status is never `full` and has no `edition` or `name_case`, Firebird-only notes go to `firebird` targets only, a `firebird` location with a `schema` is dropped and counted, a `firebird_audit_trace` event never carries `principal.application` and an object `schema` becomes `*`, and a `firebird` detected target never carries a `unix_socket`.

The trace log's record grammars (trailer first, bounded and zeroized records, no value, parameter, BLR text or returned value kept), the Firebird mode of the statement analysis, and the single-record event rules: objects from the per-table counters and the text under the noise filter, the always-reported lists, `shape.full_table_read`, `volume.large_result`, `signature.remote_data_access` and `signature.backup_database` (every backup event a read of `*`, always reported, the four DDL forms included). - **Agent: Firebird Audit for an agent in a container, from declared host identity files** ([ADR-0060](docs/adr/0060-firebird-connector.md) refinement of 2026-10-31, R43 to R52, ROADMAP P10-B; not released yet, as lot 3; no protocol change). `firebird.audit.host_identity` (`passwd`, `group`, `nsswitch`, optional `subuid`, `subgid`, `server_account` and `agent_account`) declares the host's identity files, bind-mounted read-only file by file into the agent's container; it is refused at load on the bare host, and a check that detects no container fails the readers check (`/run/systemd/container`, `/run/host/container-manager` and a non-identity `gid_map` are new container signals). At every check each declared file is opened without any symbolic or magic link (`openat2`), must have one hard link, be owned by root, have no group or other write bit and not be writable by the agent, and must be the root of its own read-only bind mount, found by its mount id in `/proc/self/mountinfo`; a mount left stale by a host-side rename is refused until the agent's container restarts. The uid and gid maps must be the identity map (no user namespace). The readers check now reads its identity files under bounded strict grammars on the bare host too (passwd keeps the name, uid and gid only; symbolic link chains followed only when root-owned under `/etc`), takes `files` from `nsswitch.conf` everywhere and `systemd` on `passwd:` only (another group source opens every group that grants read, another passwd source fails the check), refuses 65534, 4294967294 and 4294967295 and the subordinate and systemd id ranges for the server's and the agent's uids and the groups that grant read, and, in a container, a server or agent uid that the host's passwd file gives to another name. Rotated files are examined without following links, a symbolic link counting as open. One local `info` line when a target's readers check switches between the host's files and declared files. The dev service's trace log moves to the server-owned `0600` layout with the agent's named-user ACLs; `dev/firebird/it.sh` checks the rules on real single-file bind mounts; a new fuzz target `firebird_host_identity`; the agent image ships nothing under `/run/databastion`, checked in its build.
- **Agent: the Firebird Audit parser checkpoint** ([ADR-0060](docs/adr/0060-firebird-connector.md) R25 items 7 and 9 and R39 (a), the first part of the R39 follow-up lot, ROADMAP P10-B; not released yet, as lot 3; no protocol change). With a state directory, the `firebird_audit_trace` stream persists, beside its cursor, the parser state as it was at the position the cursor is saved at (bindings and header tokens, seen ids and floors, block-ful pending fold groups with their dependent mark, the split window, the confirmed clock offset, the DDL invalidation state; undeclared databases as a keyed hash) in `<target>.firebird_audit_trace.checkpoint` (at most 14 MiB), and the agent's own attachments and execution credits in `<target>.firebird_ledger.counters` (at most 2 MiB, also written on a blocking thread soon after every own session ends): keyed tags of statement texts and database names, never a statement text, a parameter or a relation, routine or database name in clear (a pending group is restored without its names, as `*` and always reported). Both are `0600`, sealed with a keyed tag under the agent key's audit sub-key, and refused whole when they do not verify, decode within their bounds, or belong to the current boot, server run, declared databases and exact resumed log position. A database whose check results (dependent set, views, external-file tables) changed while the agent was stopped counts every relation as dependent for the records re-read up to the log's length at the restart (maintainer decision of 2026-11-01, [ADR-0060 refinement of 2026-11-01](docs/adr/0060-firebird-connector.md#refinement-2026-11-01-decided-by-the-maintainer-on-2026-11-01-check-results-across-an-agent-restart)). Deduplication keys a group's events by its members, and a log truncation or rotation drops every recorded position. A checkpoint is written only once every event before it is spooled, and the restarted stream sends nothing again for a position whose events were spooled (deduplication by position); past the cap, the oldest pending groups end first and deduplication positions are dropped (sent again), and a checkpoint is never written truncated. This fixes the agent-restart residual of the [implementation note of 2026-10-31 c](docs/adr/0060-firebird-connector.md#implementation-note-2026-10-31-c-the-e2e-firebird-job-and-the-tailer-fixes): after a restart, the agent's own reads are credited again and a `TRACE_FINI` of a token seen before the restart is not ambiguous. Without a usable checkpoint the stream starts with no state and re-sends, as before, and its cursor no longer passes an event the core does not have spooled. The server process's start is now taken from `/proc/uptime` (it could be up to a second early from `btime`, which excluded the declared database at random when the Firebird root had been filled just before the server started: the intermittent `e2e-firebird` Discovery failure). The core gains the durable-event count of `EventSink`, `CursorStore::checkpoint` and `Tailer::take_resumed`; fuzz target `firebird_checkpoint` in the nightly workflow.
- **Agent: the Firebird checkpoint follow-ups** ([ADR-0060](docs/adr/0060-firebird-connector.md) R60, the refinement of 2026-11-01, ROADMAP P10-B; not released yet, as lot 3; no protocol change, no new grant). Where Audit is configured, `check()` reads two more constant texts on each declared database, readable by the minimal account on 4.0.7 and 5.0.4: `RDB$DATABASE.RDB$LINGER` (R30 item 3) and the restore state of R1 rule 5 (`DB_GUID` and `MON$CREATION_DATE` in UTC). The stream expects the Garbage Collector's end within the linger plus 10 s when the linger is known and above 0, instead of a constant 10 s (with no linger, a linger above 24 h, or a linger not read, the 10 s bound stays: a later Garbage Collector record is ambiguous, fail closed). A restore is confirmed when a check reads another `DB_GUID` or creation date than the previous check, or when the agent's persisted ledger holds an own attachment of the database with a higher id registered more than 120 s before the check's (a new database life; maintainer decision of 2026-11-01; across stream and agent restarts too): the database's bindings and DDL waits end, its watermark, highest and seen ids start again, its dependent sets are invalidated until the next check, and the earlier life's own attachments and credits are forgotten, so the restored database's attachments are no longer out of order or duplicates (ambiguous) until the server restarts. The linger and the restore state join the keyed check digest of the parser checkpoint (R58), so a database restored while the agent was stopped from a backup with the same schema, or whose linger changed, is invalidated for the re-read. A computed server start later than the time now (virtualised `btime` and `/proc/uptime`) is rejected: proof 2 is not proven (`audit.trace_config_not_evaluated` with `server_process_not_visible`).
- **Agent: the Firebird Audit stream stops before a record of a new server pid** ([ADR-0060](docs/adr/0060-firebird-connector.md) R1 rule 2 with R5 items 3 and 4, R39 (b), ROADMAP P10-B; not released yet, as lot 3; no protocol change). A record whose pid is not the confirmed run's stops the stream before it, without advancing its position, and asks for an immediate `check()` (not merged with the early checks). A check started after the stop that reads that pid confirms it: the run changes at that record (the old run's bindings end, its own attachments close in the ledger) and the new run's records are judged normally, where before every record between a server restart and the next periodic check was ambiguous. A check that reads another pid, or none within 60 s, fails it: the pid is remembered for the run (at most 64), its records are ambiguous, and a 10-minute cooldown starts during which any new pid is ambiguous without a stop. A run a check reads before the stream reaches its records changes at the first record of its pid, with no stop. Before the first check, or past 64 remembered pids, no stop. Stopped time is not reading time (split windows, fold groups, holds and the order rule's bounds move with it). The stop is not persisted: after an agent restart the record is read again and stops again if it must. A start-time change of the same pid is sampled after each read as well as before it, and asks for an immediate check. Heartbeat metrics `firebird_audit_stream_stopped_seconds_total` and `firebird_audit_run_confirmations_failed_total`; the label `run_confirmation_stalled` on `audit.log_records_ambiguous` after more than 60 s stopped within an hour.
- **Agent: the Firebird own-record error follow-ups** ([ADR-0060](docs/adr/0060-firebird-connector.md) R22 items 5 to 8 and R35, R39 (e), ROADMAP P10-B; not released yet, as lot 3; no protocol change). A credited own record leaves one error follow-up on its binding: the server's statement timeout (`335544794` and `335545129` at `JResultSet::fetchNext`, after a `FAILED` finish of a credit ended by it), the connector's answered cancel (`335544794` alone, at `JStatement::openCursor` or `JResultSet::fetchNext`), a stale cancel met by the `DSQL_drop` (the same shape; its location is not measured), and the row-limit cut whose extra request reaches the end of the result (`335544364` alone at `JResultSet::fetchNext`; the connector now records the cut in the credit). The next record of that binding, if it is an `ERROR` record of exactly that shape (attachment, client and location lines, one line per code, no other line, no trailer), consumes it with no event; a second record of a follow-up shape once it is consumed is ambiguous (always reported, `*`). Any other error record of the agent's binding is handled as any client's (no event of its own), never as the agent's. Follow-ups are not persisted (a restart loses one: the real record then gives no event, nothing hidden). The checkpoint and ledger format version is 2 (the ledger's credits carry the cut): files written by earlier builds of this unreleased lot are refused once, and the stream starts with no state.
- **Agent: Firebird local external data sources** ([ADR-0060](docs/adr/0060-firebird-connector.md) R29 with R18 item 3, R39 (c), ROADMAP P10-B; not released yet, as lot 3; no protocol change). An `ATTACH_DATABASE` whose line is exactly `<name> (ATT_<n>, <user>:<role>, NONE, <internal>)` with no client line, on the current run's pid, anchors an external-source binding under that user and role (R1 rules 3 to 5 and R7 apply; never the agent's own, never an internal binding). Its events are held until its transaction's end, at most 10 minutes of reading time per binding and 16 384 events and 4 MiB per stream, in memory only: the persisted position is held back at its attach, and the checkpoint is the state before it. They are emitted as judged only when a caller exists: another binding with a transaction open at the attach that wrote a finish record of code (a procedure, a function outside the built-in list, `EXECUTE BLOCK`, `EXECUTE STATEMENT`, or a routine finish record) before the external transaction's end. Otherwise (no caller, a bound reached, the binding gone first, the run's end, a rotation) every record of the binding is ambiguous, always reported with `*`, as before. So a routine's use of a local external data source on a declared database no longer caps the level each time.
- **Agent: Firebird remote 4-tuple corroboration** ([ADR-0060](docs/adr/0060-firebird-connector.md) R1 rule 9 with the R11 8f amendment (security review L11) and R32 item 4, R39 (d), ROADMAP P10-B; not released yet, as lot 3; no protocol change, no new grant). A new TCP binding is ambiguous (its records always reported with `*` until it detaches, never the agent's own) when another live binding holds the same client address and port, or when its `ATTACH_DATABASE` lies past an end of file the stream saw less than 10 s of agent time before, the binding is still live (no `DETACH_DATABASE` of its token later in the same read), and the server's connection table (`/proc/net/tcp` and `/proc/net/tcp6`, read once per read that holds such an attach, after it, bounded at 1 048 576 lines and 2 s) has no connection to the server's port, in any state but `LISTEN` and from either side, with that client end. When the agent lags, or the table cannot be read whole, the socket condition is not evaluated (counted). The client end is kept with the binding as a keyed hash, in the parser checkpoint too. Local external data sources (`<internal>`, R29) and the server's internal attachments have no address and are not checked.
- **Agent: the core enforces the `sqlite` contract rules** (P10-C review R1): a `sqlite` location names the database `main` and no schema (dropped and counted otherwise, before spooling; a spooled batch breaking it is never sent), and a `sqlite` target status is always `audit_level: none` without `audit_source`, `server_version`, `edition` or `name_case`.

### ⚠️ Upgrade notes
From 0.8.x, upgrade the console first, then the agents, as for every release. A 0.9 console accepts 0.9 and 0.8 agents ([RELEASE.md](RELEASE.md#compatibility)). This release adds new fields that one side sends only when the other lists them. With several console replicas, one more step is needed so that the replicas agree on which fields they list.

**Upgrade procedure, from 0.8.x, in this order**
1. **Webhook receivers.** If a receiver rejects unknown keys, update it before the console: the `incident.opened` access payload gains `access.objects_overflowed` ([ADR-0053](docs/adr/0053-overflowed-event-objects-flag.md)). If a receiver assumed at most 20 for `agent.target_mismatch`'s `details_count`, update it to accept up to 64 (below).
2. **Every console replica.** `migrate` applies migrations `0041` to `0047` on start (below). **With several replicas** behind your own load balancer:
   - Before you roll out 0.9.0, set `DATABASTION_AGENT_TOKENS_HOLD=0.8` in the environment of every web process of the new build.
   - Check that each replica's `/metrics` shows `databastion_console_agent_tokens_hold{release="0.8"} 1`.
   - Roll the new image out replica by replica.
   - Once **every** replica runs 0.9.0, remove the variable, restart the replicas, and check that every replica's gauge is back to `0`.
   - Procedure: [deploy/README.md](deploy/README.md#rolling-upgrade-of-several-console-replicas).
   - Without the hold, an agent that learns a new token from an upgraded replica sends the new field to every replica. An older replica answers `400`, and the agent resends those items without the field: the overflow flag, the name case or the altered-name marker is lost for those items ([ADR-0022](docs/adr/0022-protocol-capability-negotiation.md) decisions 8 and 9).
   - **Do not leave the hold set.** While it is set, no agent sends the held fields, so the ADR-0053, ADR-0055 and ADR-0056 rules do not apply to new items.
   - The bundled Compose file runs one web process and needs none of this.
3. **The agents**, once every console replica runs 0.9.0 and the hold is removed. They send the new fields as soon as a heartbeat answer lists their tokens.
4. **Rescan Discovery** of each target after its agent is upgraded ([ADR-0057](docs/adr/0057-identifier-hardening-agent-first.md)).
   - The upgraded agent sends more names as `*` (see Security).
   - A sensitive object derived from a finding whose name is now masked keeps its old name until a new Discovery scan derives it again.
   - Until then, the agent's `sensitive_objects` filter matches the old name only. Under `min_rows`, it drops reads of that object.
5. **Review the exceptions and false positives** that the new rules change (behaviour changes below):
   - the policies page's card "Exceptions affected by case-sensitive names", filled at the worker's first start after the upgrade ([ADR-0054](docs/adr/0054-case-sensitive-location-exceptions.md));
   - the agent page's "Names compared" column and its per-target inventory, filled once the agents report the name case ([ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md));
   - false positives reset with reason `names_altered`, which must be marked again if they still are false positives ([ADR-0056](docs/adr/0056-names-altered-by-normalization-marker.md)).

**Do not downgrade an agent below 0.9.0 with findings or events in its spool.** An agent of 0.8.2 or older refuses spooled batches that carry `objects_overflowed` or `altered` as corrupt and moves them to `spool/quarantine/`, so their items are lost (details below). Before a downgrade, let the spool drain: the heartbeat's `spool.batches` at 0, with the console reachable.

**Behaviour changes on existing targets**
- **Location exceptions compare names with case on PostgreSQL, MongoDB, Redis, Valkey and Apereo CAS** (console, [ADR-0054](docs/adr/0054-case-sensitive-location-exceptions.md)).
  - **The rule**: on these engines, and on a target whose engine is unknown, an exception's `database`, `schema`, `object` and `field` patterns cover a name only when they match it both without case (as before) and with case.
  - **Example**: an exception for `crm.customers` no longer suppresses a distinct `crm."Customers"`, a `Customers` collection, a `Customers:*` key pattern or a `Portal` service.
  - **Unchanged**: SQL Server, MySQL, MariaDB and OpenLDAP exceptions, policy conditions, sensitivity and scores.
  - **When it applies**: at upgrade, with no data migration. An exception written in another case than the real name (`useraccounts` for `userAccounts`, `CRM.Customers` for `crm.customers`) stops covering it. Findings raise incidents at their next evaluation, and events from the upgrade on.
  - **Inventory**: at its first start after the upgrade, the worker lists the exceptions concerned. It compares them against the stored findings (false positives included) and the access events within the retention. The result goes to the worker's log and to one `policy_exception.case_inventory` audit entry, with exception ids and counts only. The policies page shows the exceptions with their counts (upper bounds) and lets an administrator queue another run, which the worker performs. A failed run is audited and shown there too.
  - **What to do**: review the listed exceptions after upgrading. The affected names are the mixed-case ones (camelCase MongoDB collections, Redis / Valkey key prefixes, quoted PostgreSQL identifiers, CAS service names), whatever the case of the exception. To cover two spellings, write one exception per spelling, or put a `?` in place of the letter that differs.
- **Location exceptions on SQL Server, MySQL and MariaDB targets follow the server's name case settings once the agent reports them** (console and agent, [ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md); contract `TargetStatus.name_case`, token `target_status.name_case`).
  - **What the agent reports**: how the server compares names. On MySQL / MariaDB this is `lower_case_table_names`; on SQL Server, the server and database catalog collations. The console keeps the value per target.
  - **The rule**:
    - an exception's `database` pattern compares with case when database names do;
    - its `schema` and `object` patterns (and `field` on SQL Server) compare with case when the object names of the item's database do;
    - `unknown` counts as with case;
    - an event object of the database `*` takes the strictest value;
    - MySQL / MariaDB column names never compare with case.
  - **Before the agents are upgraded**: nothing changes. A target whose heartbeat carries no `name_case` (every agent before 0.9.0) keeps the rule of 0.8.x, without case, and its row on the agent page says "not reported".
  - **After the agents are upgraded**: on case-sensitive servers and databases (MySQL / MariaDB with `lower_case_table_names = 0`, SQL Server `_CS_` and binary collations, and every database reported `unknown`), exceptions written in another case than the stored names stop covering them. This applies to findings at their next evaluation and to events from then on.
  - **Inventory**: each change of a target's rule (its first value, a change, or its loss) runs the ADR-0054 inventory for that target in the worker. It runs at most once per target and hour (changes within the hour are coalesced), is recorded in one `policy_exception.name_case_inventory` audit entry with exception ids and counts only, and is shown on the agent page.
  - **Unchanged**: policy conditions, scores, the incident dedup key, the trailing-space rule and the agent's sensitive objects. OpenLDAP and the other engines ignore the field.
  - **New in heartbeats**: the agent's heartbeat may now name SQL Server databases that never appeared in findings or events, at most 32 per target, normalized like every name.
- **Location exceptions no longer cover names that the agent's normalization altered, and false positives on such findings must be marked again** (console and agent, [ADR-0056](docs/adr/0056-names-altered-by-normalization-marker.md) decision 3; contract `Location.altered` / `ObjectRef.altered`, tokens `location.altered` and `object_ref.altered`).
  - **What counts as altered**: a name changed by the agent's normalization. That covers invisible or formatting characters removed, compatibility forms such as fullwidth letters folded, and CAS definition keys converted to snake_case.
  - **The rule**: an altered part is covered only by an exception whose pattern for that part is absent or exactly `*` (`\*` does not cover it). An exception on the enclosing database or schema still covers it.
  - **Effect**: findings and access events from upgraded agents may reopen incidents that an exception suppressed through an altered name.
  - **False positives**: a false positive marked on a finding before its location was reported altered is reset (audited `finding.false_positive_reset`, reason `names_altered`). Mark it again if it still is a false positive.
  - **Unchanged**: rows stored before the upgrade carry no marker, and nothing changes for agents before 0.9.0, which do not send it.
- **Access events whose objects overflowed can raise more incidents** (console and agent, [ADR-0053](docs/adr/0053-overflowed-event-objects-flag.md)).
  - **What changes**: a statement that reaches more objects than the 15 an event names is flagged. Each of its `*` objects is then retained by object-scoped policies and counted as the most sensitive object of its database (Features).
  - **Who triggers it**: reporting jobs and ORMs that touch many tables in one statement.
  - **What to do**: exclude their accounts with `exclude_principals` on the policies concerned.
  - **Payloads**: the `incident.opened` access payload gains `access.objects_overflowed` (step 1 above).
- **Incidents of one MySQL, MariaDB or SQL Server database with trailing spaces are merged** (console, [ADR-0021](docs/adr/0021-access-event-correlation.md) implementation note of 2026-10-18).
  - **The rule**: on these engines, the access-event incident dedup key now drops trailing spaces from the database name, as location exceptions do. Events on `crm ` and `crm` in the same hour add to one incident per policy and principal.
  - **Unchanged**: case is kept on every engine (`CRM` and `crm` stay two incidents, since case can tell databases apart), and other engines are unchanged.
  - **At upgrade**: an incident open across the upgrade keeps its events. In the hour of the upgrade, the other spelling may open one more incident, once.
- **SQL Server Extended Events: `ddl` policies no longer match `DROP LOGIN` or `ALTER ROLE … ADD MEMBER`, and `dcl` policies do.** Principal changes are now DCL on this source, as on SQL Server Audit (Bug Fixes).
- **MySQL / MariaDB Audit: table names written without backquotes keep the case they are written in** (`crm.Customers`, no longer `crm.customers`; [ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decision 3; Bug Fixes).
- **`agent.target_mismatch` webhooks: `details_count` can exceed 20** (console, #277).
  - **New count**: every target whose `audit_source` does not serve its engine, up to the contract's 64 per heartbeat, as `target_ids` lists them.
  - **Unchanged**: the first `pointer` / `keyword` and the stored error details. No key is added.
  - **Receivers** that assumed at most 20 should accept up to 64. Rows written before the upgrade keep their capped count.
- **Redis / Valkey key patterns as sensitive objects need a 0.9.0 console and a 0.9.0 agent** (phase 9 follow-ups, contract `SensitiveObject`).
  - **Which agents get them**: the console sends key patterns in a target's Audit settings only to an agent that announces `sensitive_object.key_pattern`. An older agent still gets them left out and counted, as in 0.8.x.
  - **When an agent is upgraded**: as soon as the agent's heartbeat lists the token, the console queues the Audit settings of its Redis / Valkey targets again with their key patterns, on its own.
    - The change is audited as a system `audit.configure`.
    - Only the key patterns change; the plain names stay as sent.
    - At most 4 such changes per agent and hour are made; past that, an `agent.accepts_flapping` integrity event is raised, and the change is deferred, not lost (Bug Fixes).
  - **When an agent is downgraded below 0.9.0**: the key patterns are removed the same way.
    - The console queues the settings again without key patterns and leaves a "removed objects" warning on the target.
    - A job fetched by an agent that no longer lists the token is delivered without them, and this is marked on the target's Audit settings page.
    - Until the agent is upgraded again, accesses to those key patterns are only reported with a signal or without `min_rows`.

**Agent spool and state files**
- **Event batches carry `objects_overflowed` and `bytes` in the spool** ([ADR-0053](docs/adr/0053-overflowed-event-objects-flag.md) decision 2, contract review L3).
  - **What changes**: the agent spools every access event in full. When it sends a batch to a console that does not list their tokens, it strips the gated fields `AccessEvent.objects_overflowed` and `AccessEvent.bytes`.
  - **Downgrades**: an agent built before the contract change #295 (every 0.8.x agent and older) does not know `objects_overflowed`. It refuses a spooled batch carrying it as corrupt and moves the file to `spool/quarantine/`. The file is never read again, by that agent or by a later upgraded one, so its events are lost.
  - **Upgrades**: nothing to do; older spools are read as before.
  - **Hold before sending**: some event batches that carry a gated field wait for the next heartbeat answer before they are sent, with or without the field.
    - When: after the agent starts, or after a console answers `400` on a gated field (at most once per 600 s).
    - Which batches: every batch that carries a gated field, except those with a `signature.*` signal.
    - How long: at most 600 s after the last heartbeat attempt that could not reach the console (until `/events` or `/findings` answers), and 1 h in all.
  - **Replacement marker**: the spool now marks a batch being replaced with a `<file>.replaced` file. An agent of 0.8.2 or older moves such a marker to `spool/quarantine/`. After a crash during a replacement, such an agent sends both the old batch and its replacements.
- **Findings batches carry `Location.altered`, and Redis / Valkey learned patterns are saved in a new form** ([ADR-0056](docs/adr/0056-names-altered-by-normalization-marker.md) decision 2).
  - **Spool**: as for `objects_overflowed`, an older agent quarantines the spooled findings and events batches that carry the marker.
  - **Learned patterns, downgrade**: an older agent reads this release's learned-patterns file (`v2`) as not understood. It learns the patterns again at the next scan of each database; until then, its Redis / Valkey Audit objects are `*`.
  - **Learned patterns, upgrade**: a learned-patterns file of an earlier agent is read with no pattern marked until the next full Discovery walk of each database.
  - **Sending**: the agent strips both fields at send time until the console lists `location.altered` and `object_ref.altered`.

**Console migrations** (all applied by `migrate` on start; none rewrites a table)
- `0041` adds `agents.accepts` (the agent tokens the console knows) and `jobs.delivered_without_key_patterns`. Catalog-only.
- `0042` adds nullable columns on `access_events` and `incidents` for ADR-0053, and `0043` grants updates on them to the runtime role. Catalog-only, nothing to validate.
- `0044` adds nullable columns and a bounded `CHECK` to `agent_targets` for ADR-0055. The table has one row per declared target, so the check is validated in the migration.
- `0045` adds `agents.audit_requeue_due_at`, for the deferred Audit settings requeue. Catalog-only.
- `0046` and `0047` add `findings.altered` and `findings.false_positive_altered` (nullable `text[]`) and `findings.altered_job_id` (a nullable `uuid`, the scan job whose items `altered` holds), for ADR-0056. Catalog-only, nothing to validate.

### ✨ Features

**Console**
- **`DATABASTION_AGENT_TOKENS_HOLD`, a capability token hold for rolling upgrades of several replicas** ([ADR-0022](docs/adr/0022-protocol-capability-negotiation.md) decision 8; end-of-phase-9 security review L1; #339).
  - **Values**: set to a release line (`0.8`, the only value today), the console lists in its heartbeat answers only the tokens that release listed. It still accepts and stores every field it knows. Unset or empty, every token is listed. Any other value stops the web and worker processes at startup.
  - **What `0.8` holds back**: the tokens added after 0.8.2, which are `access_event.objects_overflowed`, `target_status.name_case`, `location.altered`, `object_ref.altered` and `target_status.note_labels.2026_10_c`.
  - **Monitoring**: each web process reports the hold on `/metrics` as `databastion_console_agent_tokens_hold` (`1` with the `release` label while held, `0` when unset). It logs a warning at startup, then at most once an hour while it answers agents.
  - Procedure: [deploy/README.md](deploy/README.md#rolling-upgrade-of-several-console-replicas).
- **Objects left out of an access event are no longer invisible to object- and sensitivity-scoped policies** ([ADR-0053](docs/adr/0053-overflowed-event-objects-flag.md) decisions 1 and 3; contract `AccessEvent.objects_overflowed`, token `access_event.objects_overflowed`).
  - **Which events**: a flagged event is one whose access reached more objects than the 15 it names, or went past a connector's own bound. The console lists the token and stores the flag.
  - **The rule**: every `*` object of a flagged event counts as possibly any object of its database (of the target, for the database `*`). On Redis / Valkey, a real `*` key pattern of a flagged event counts too.
  - **`objects` conditions** retain such a `*` when their database glob matches.
  - **Bound score**: `min_sensitivity`, `min_score` and the choice of the incident's database use a bound score, in which each such `*` counts as the most sensitive object of its database. The findings used are those of the event's target only, false positives excluded, with names compared without case or trailing spaces (also on a `C`-ctype console database).
  - **Named score**: incidents, the hourly cap bypass, the "worse than resolved / false positive" checks and the baselines keep comparing the score of the named objects only, so the bound never hides a later access.
  - **Exceptions**: a location exception covers such a `*` only when it covers the whole database (`schema` and `object` absent or `*`).
  - **Display**: the events table and the incident page say that the event lists fewer objects than it reached, and show the bound as "up to …". The alert e-mail says so too.
  - **Older agents**: events of agents before 0.9.0, which do not send the flag, are evaluated exactly as before.
- **Per-target name case semantics for SQL Server, MySQL and MariaDB location exceptions** ([ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decisions 5 to 8).
  - **Storage**: the console accepts `TargetStatus.name_case` and stores it in canonical form (databases sorted, one entry per name with the stricter value). A compare-and-set in the heartbeat transaction compares the canonical forms, so one replica sees each change. An `except` list past 8 KiB is stored as `objects: unknown`, never refused.
  - **Comparison**: location exceptions compare each part per the target's rule on these three engines only. Each cover is always a subset of the one before.
  - **Agent page**: it shows how each target's names are compared ("with case", "without case", "per database", "unknown, treated as with case", "not reported"), with the latest per-target inventory.
  - **Exception form**: it says that these engines follow the server's settings.
- **Names altered by the agent's normalization are marked, and location exceptions cover them only with `*` or an absent pattern** ([ADR-0056](docs/adr/0056-names-altered-by-normalization-marker.md) decision 3).
  - **Event objects** keep `ObjectRef.altered` as sent.
  - **Finding rows** hold the union of the altered parts of every item of their location within one scan job. The union spans one batch and that job's other batches, and is replaced by the first batch of a new job. So a look-alike reported before or after the plain table keeps the row marked, and a later scan without it clears the mark.
  - **Unchanged**: policy conditions, sensitivity, scores, the dedup key and the overflow `*` bound.
  - **Display**: the findings, events and incident views say that the name was altered by normalization, so the administrator can check the database for look-alike names. Notifications are unchanged.
- **Redis / Valkey key patterns as Audit sensitive objects** (phase 9 follow-ups; contract `SensitiveObject.object` as an `ObjectName`; a compatible change negotiated on the agent token `sensitive_object.key_pattern`, [ADR-0022](docs/adr/0022-protocol-capability-negotiation.md) decision 3; #280).
  - **Console**: it sends the key patterns of a Redis / Valkey target's findings (`user:*:email`), and those typed by hand, as sensitive objects to agents that list the token in their heartbeat. It checks the list again when it delivers the job. For older agents it still leaves them out, counted in `skipped_key_patterns`.
  - **Agent checks**: the agent checks each key pattern against the whole `KeyPattern` schema, and refuses one for a target of another engine (`invalid_params`).
  - **Agent matching**: the agent keeps an event whose key pattern overlaps a listed one.
    - Both are read as Redis globs, where `*` spans any characters. A listed `user:*:email` keeps the events named `user:*:email`, `user:*`, `*:email` and `*`.
    - The database `*` matches any database.
    - Case is ignored, and names are compared with and without trailing spaces.
    - The match runs only when `min_rows` is set.
  - **Effect**: with `min_rows` set, Redis / Valkey reads and writes that overlap a listed pattern are no longer dropped ([docs/08](docs/08-engine-capabilities.md#objects-per-event-and-sensitive-objects-every-engine)).
- **Warning for minimum rows on Redis / Valkey targets** (#235 review N2, #274). Saving Audit settings with `min_rows` on a key-pattern target still works. It now returns `min_rows_warning: "no_row_counts"`, which is recorded in the audit entry and shown on the target's Audit settings page. These events carry no row count, so the threshold drops those without a signal.
- **`agent.target_mismatch` has its own integrity write budget** (#235 review N1, #274).
  - **Budget**: one row per agent and hour while the set of targets whose `audit_source` does not serve their engine stays the same. A row is written at once when that set changes, at most 12 an hour per agent, with the target ids in its details. The heartbeats in between are counted in `suppressed_before`.
  - **Separate from the other events**: it no longer uses the per-agent budget of the other agent-integrity events (20 rows per 10 minutes).

**Agent**
- **`AccessEvent.objects_overflowed` sent to consoles that list `access_event.objects_overflowed`** ([ADR-0053](docs/adr/0053-overflowed-event-objects-flag.md) decision 2).
  - **Which events**: an event whose objects were left out under a bound (the core's 15 named objects, or a connector's own bound) now carries the flag. It always names a `*`: the sanitizer adds one, and never clears the flag.
  - **When the gate applies**: the decision moved from conversion to send time, for `bytes` too. An event converted before the first heartbeat answer, or while the capabilities were cleared, no longer loses its gated fields for good.
  - **Sending**: a batch is sent as spooled to a console that lists every token it needs. Otherwise it is sent under a new `batch_id`, without the unlisted fields only (heartbeat metric `gated_fields_stripped_at_send_total`).
  - **After a `400` on a gated field**: every gated field is still dropped, once (ADR-0022 decision 9).
  - **After a `400` `contains` / `if` on a flagged event** (the console found no `*`): the agent resends it once without the flag and keeps the capabilities (`overflow_flags_refused_total`).
- **How MySQL, MariaDB and SQL Server targets compare names, sent as `TargetStatus.name_case`** ([ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decisions 2 to 4; contract token `target_status.name_case`; no grant changes).
  - **When it is sent**: once the console lists the token, in every heartbeat status of a `mysql`, `mariadb` or `sqlserver` target, the `/rotate` probe heartbeat included. It is sent also when `check()` fails, times out or is skipped: then the value last read on the server, else `unknown` for both parts. It is never sent for another engine, and never to a console that does not list the token.
  - **MySQL / MariaDB**: `check()` reads `@@GLOBAL.lower_case_table_names` and `lower_case_file_system`, which needs no grant (one new constant among the agent's own texts).
    - 0 is `sensitive`, also on a file system that ignores case (the local check detail says so).
    - 1 and 2 are `insensitive`.
    - Anything else, or a failed read, is `unknown`.
  - **SQL Server, the statement**: one new allow-listed statement reads every `sys.databases` row, at most 1 024, including snapshots, offline databases and databases the login cannot enter.
  - **SQL Server, the values**:
    - database names follow the server collation, and schema, object and column names each database's catalog collation;
    - a `ComparisonStyle` without the ignore-case bit is `sensitive`;
    - `catalog_collation_type` 2 is `insensitive`, as are 0 or 1 on a contained database (refinement of 2026-10-21, measured on SQL Server 2019, 2022 and 2025);
    - another type, an offline database, or one whose collation cannot be read is `unknown`.
  - **SQL Server, the `except` list**: the databases that differ from the server collation are listed in `except`.
    - Each entry is a normalized name, and a name matched by a classifier is `*`. Entries are sorted, one per name with the stricter value.
    - The list holds at most 32 entries and 8 KiB.
    - `objects` is `unknown` with no list past those bounds, without `VIEW ANY DATABASE`, past 1 024 databases, or without `catalog_collation_type`.
  - **Closed and never-seen databases**: an `AUTO_CLOSE` database closed between two checks keeps its last value on the same server run (server name and `tempdb` creation time) instead of turning `unknown`. A database never seen open is `unknown`; SQL Server Express turns `AUTO_CLOSE` on for every new database.
  - **Refused `/rotate` probe**: a `/rotate` probe heartbeat refused with `400` on an unknown field is sent once more without the gated `notes` and `name_case` fields, so such a refusal never costs a rotation (#301 contract review I-3, ADR-0022 decision 9).
- **Names altered by normalization are marked: `Location.altered` on findings and `ObjectRef.altered` on event objects** ([ADR-0056](docs/adr/0056-names-altered-by-normalization-marker.md) decision 2; tokens `location.altered` and `object_ref.altered`).
  - **When a part is marked**: when the agent's first normalization step changed the name as read from the engine. That step strips control and format characters and applies NFKC: a table `customers<U+200B>` or `ｃｕｓｔｏｍｅｒｓ` is sent as `customers`. A part sent as `*` is never marked.
  - **Redis / Valkey**: a part is marked when NFKC changed a key segment kept in the pattern.
    - A Discovery finding carries the marker of the pattern learned from its keys.
    - An Audit object carries the marker of the learned pattern it maps to, or its own key name's. A key mapped to `*` is never marked.
    - The markers of learned patterns are kept across restarts.
  - **Apereo CAS**: a part is marked when the snake case conversion changed a definition key (`userName`, not `user_name`). This is 5 of the 14 positive registry locations of the dev ground truth.
  - **Content of the lists**: they carry no character and no count (I2), name each part once in contract order, and are never empty.
  - **Merged names unite their markers**: a duplicate object, aggregated events, a `*` standing for overflowed objects, pooled MongoDB paths, OpenLDAP containers and attributes, CAS registry fields, and Redis / Valkey hash and stream fields.
  - **OpenLDAP Audit**: a sensitive object reached through an altered search base or container is named with its schema marked.
  - **Events**: spooled in full and stripped per token at send time, with the ADR-0053 hold while the console's capabilities are not known.
  - **Findings**: `Location.altered` is the first gated finding field. Findings are spooled in full and stripped per token at send time, and never held.
    - A findings batch sent while the capabilities are not known goes at once without the field. Each such finding (not each batch) is counted in the new heartbeat metric `findings_stripped_capabilities_unknown_total`.
    - "Not known" lasts from the start until the first heartbeat answer, and from any clear until the next answer.
    - `gated_fields_stripped_at_send_total` keeps counting batches stripped for a token that a known console does not list.
    - A `400` that reports the field as unknown clears the capabilities, and the findings are resent once without it (ADR-0022 decision 9).
  - **Unchanged**: the agent's `sensitive_objects` filter.
  - **#308 final review N8, agent part**: a MySQL / MariaDB user database `performance_ſchema`, `ſys` or `MYſQL` reaches the console with `database` in `altered`.
- **SQL Server Extended Events: reads of up to 2 000 events after a full read** ([ADR-0051](docs/adr/0051-sqlserver-connector.md) refinement of 2026-10-22, option (b); implementation note of 2026-10-22; #332).
  - **Before**: reads were at most 500 events. At every read, the server skips again the events of the current buffer already read, so a buffer of a few thousand small events cost about twice its reading time.
  - **Read size**:
    - After a full read, the next read now asks up to 2 000 events. This `N` was set from a read-cost measurement on SQL Server 2022: about 1 840 events a second of reading time, against 1 250 in reads of 500.
    - The read asks fewer events when the last read held large events: at most 75 % of the 12 MiB response bound, never below 500.
    - The first read, and the read after any read that is not full, ask 500.
  - **Responses above 12 MiB**: such a read is asked again at half the size, and the reduced size is kept for 10 minutes. As since 0.8.1, the reduced size is also kept for that position across a stream restart, until a read there succeeds. After that success, it is kept for the 10 minutes, no longer doubled at once as in 0.8.1.
  - **Cancels and timeouts**: a cancel or a client-side statement timeout of a read above 500 events keeps the reads at 500 for 10 minutes. An `info` line goes to the agent's log, at most every 10 minutes per target.
  - **Unchanged**: the 12 MiB bound, the 15 s statement timeout and `MAXDOP 1`. SQL Server Audit keeps reads of 500 records.
  - **Measured**: load run 40003873141 on SQL Server 2019 drained 30 000 of 30 000 workload `SELECT`s in about 38 s, with no read cancelled ([docs/08](docs/08-engine-capabilities.md#load-and-database-impact-measured)).
- **SQL Server: `audit.failed_logins_not_audited` for an Extended Events session without `error_reported`** (phase 9 follow-ups).
  - **Registry text**: the note's text now names both sources: SQL Server Audit without `FAILED_LOGIN_GROUP`, and an Extended Events session without `error_reported`.
  - **When the Extended Events source sends it**: when the session has no `error_reported`, and also while an `error_reported` with a predicate has not been proven by an 18456 recorded in the last 24 h (by event time, not from the agent's own account). The agent never reads predicates.
  - **Before**: that case was only a line in the agent's log.
  - **Level**: not required for Partial, as before.
- **SQL Server: the label `on_failure_probe` for `ON_FAILURE = CONTINUE`** (phase 9 follow-ups; note-label revision `target_status.note_labels.2026_10_c`, negotiated on its own token like `2026_10_b`). The `privilege.not_evaluated` note of a server audit whose failure counter the agent's grants do not read now carries `on_failure_probe` instead of `other`, once the console lists the token.

### 🐛 Bug Fixes

**SQL Server Audit and Extended Events**
- **A stream behind its source catches up with paced reads** (found by load run 39687119269; [ADR-0051](docs/adr/0051-sqlserver-connector.md) implementation note of 2026-10-22; #311).
  - **Before**: a stream slept a whole poll interval after every 20 reads. An Extended Events stream in its history read under 1 000 events/s at the 10 s default, and never caught up with a server writing 1 500/s.
  - **Now**: full reads follow one another for up to 20 s of reading time per cycle, or 10 s while a first start walks its history.
  - **Pauses**: after that, the stream pauses a quarter of that time (half, at least 1 s, in the history). The pause is at most 20 s or the poll interval.
  - **Bound**: a cycle never starts sooner than a poll interval after the last one started, so `limits.min_audit_poll_interval_s` still bounds the catch-up.
  - **What counts**: only the time spent in the poll statements, not the wait for the agent's event queue.
  - **Logging**: a stream that is behind logs one `info` line per minute at most.
  - **Measured**: 30 000 of 30 000 workload `SELECT`s stored on SQL Server 2022, against 15 028 before ([docs/08](docs/08-engine-capabilities.md#load-and-database-impact-measured)).
- **The CAS store guard's `check()` read no longer shows up as reads by the agent's own login** (#293, found by load run 39453966277; present since 0.8.0).
  - **Before**: for the CAS store guard, `check()` called a column-level `HAS_PERMS_BY_NAME` on every column of every user table in each monitored database, and SQL Server Audit writes one `SL` record on each table such a call checks. On a database with more than 15 user tables, the agent's own statement went over the event bound (15 named objects and `*`, always reported).
  - **Effect**: at every check, on SQL Server Audit targets only, the agent's login was reported reading 15 tables and `*`. Those events matched "every read" policies (deduplicated per hour). Each check also wrote one record per user table into the operator's audit file.
  - **Now**: the guard reads only table and column names. It checks column `SELECT` only on the tables it recognizes as CAS stores, one table per statement, at most 64 per database. Past that, or when a table's answer is empty or holds no permission (`NULL`), it reports `privilege.not_evaluated` (`cas_store_guard_probe`).
  - No grant changes ([ADR-0041](docs/adr/0041-cas-connector.md#implementation-note-2026-10-20-the-sql-server-guard-check-one-table-at-a-time) implementation note of 2026-10-20).
  - **No security advisory**: the events named only the agent's own login and table names (maintainer decision of 2026-10-20).
- **A Discovery scan of a database of more than 15 user tables no longer shows up as the agent's own read of `*`** (SQL Server Audit; phase 9 follow-up of #293, #309; present since 0.8.0).
  - **Before**: Discovery's table list called an object-level `HAS_PERMS_BY_NAME` on every table in one statement, which SQL Server Audit records as one `SL` record per table. The statement then named more objects than an event keeps, and was always reported. At each scan it also wrote one record per user table into the operator's audit file: 20 records before, 0 now, measured on 2022.
  - **Now**: the table list checks no permission. Each table's `SELECT` comes from its per-table column statement, as before.
  - **Counter change**: a table with table `SELECT` and every column denied now counts in `skipped_not_readable` instead of `skipped_unsupported`.
- **Principal changes on Extended Events are DCL** (found by the Extended Events end-to-end jobs of #279; [ADR-0051](docs/adr/0051-sqlserver-connector.md) implementation note of 2026-10-18; #281).
  - **Which statements**: `CREATE`, `ALTER` and `DROP` of a login, user, role, application role, server role, credential or database scoped credential, and `ALTER AUTHORIZATION`. They are now reported as `dcl`, as on SQL Server Audit.
  - **Before**: a statement of this kind whose text the server keeps was reported as `ddl`. Examples: `DROP LOGIN x`, `ALTER ROLE r ADD MEMBER u`, and the inner statements of `sp_addrolemember`, `sp_addsrvrolemember`, `sp_dropuser` and `sp_droplogin`.
  - **Password-bearing forms**: the server records them as `-- CREATE LOGIN` or `-- ALTER LOGIN` (measured on 2022). They were already DCL, and the password never reaches the agent.
- **A client's statistics build is no longer reported when a read boundary falls before its statement** (Extended Events; [ADR-0051](docs/adr/0051-sqlserver-connector.md) refinement of 2026-10-18, accepted by the maintainer; found by an intermittent `xe_statistics_builds_match_the_fixture` failure; #282).
  - **The pairing**: on the allow-listed builds, a statistics build is left out when the same request holds a statement naming its table.
  - **Before**: that pairing was done within one read. A build whose statement reached the event file in the next read was reported as a read of its table by the client, and its internal statement as an always-reported read of `*`.
  - **Deferral**: such a build is now deferred to the next read, like the agent's own case 2 builds.
    - It is deferred once per build, for at most the smaller of `MAX_DISPATCH_LATENCY` and two poll intervals, and never more than 60 s.
    - At most 4 096 builds are remembered. A build still unpaired after that is reported.
  - **Which reads defer**: only a read that reached the end of the event file. A full read whose build may have its pair in the rows not fetched yet ends before the build and reads on at once.
  - **Bound on the delay**: once the stream has been held behind deferrals for 60 s, nothing is deferred until it has caught up. Every event is handled within 60 s plus two poll intervals of being written, plus the time to read the rows behind it (when the agent reads faster than the server writes).
  - **Never skipped**: a deferred build is never skipped. The position stays before it, also across a restart.
- **The failed-login proof of a filtered `error_reported` follows changes of the session and ignores clock skew** (Extended Events; #280 re-review L-b, and the engine-matrix follow-up of #316).
  - **Ageing**: the 18456 that proves failed logins are recorded is aged on the server's clock, against the agent's own session's read-back, and kept for 24 h on the agent's clock.
  - **What clears the proof**:
    - a change of the session's events, actions or the presence of a predicate;
    - a restart of the session, a new file set, or changed event facts;
    - a statement read by the stream that may create, alter or drop an event session (dynamic SQL included);
    - a statement event whose text was not read whole.
  - **What proves it again**: only a failed login stamped after the change.
  - **Effects**, all failing closed (`audit.failed_logins_not_audited` stays longer, never shorter):
    - the note can come back after an operator changes the session;
    - a server clock stepped back keeps the note until a failed login is stamped after the change;
    - the first stream after each agent start clears the proof at its first probe, with the server's time as the floor. Failed logins of the history that stream walks no longer prove it; only one recorded after the start does.
- **A name case kept from before a server restart is reset** (phase 9 follow-up, the #303 residual; [ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decision 2; #309). Each new session of either Audit stream reads the server run: the server name and `tempdb`'s creation time, through one new constant statement on `sys.databases`, with no new grant. A `name_case` read on another run is sent as `unknown` until the next `check()`. This also holds when a check that read on the earlier run ends after the stream saw the new one.
- **Sampling credits and the 24 h gap memory are persisted** (end-of-phase-9 review L5, #276).
  - **Sampling credits**: the newest 1 024 are saved as 128-bit HMAC tags of their texts, under a per-target salt; no text is stored. Before, a Discovery sample whose record was read after an agent restart was always reported. Now this happens only past those 1 024 credits.
  - **Gap memory**: the 24 h gap memory (Limited after a gap, `audit.records_dropped`) is saved by both streams in `<state_dir>/audit/<target>.sqlserver_gap.counters`. An agent restart no longer shows Partial again before the 24 h are over ([docs/08](docs/08-engine-capabilities.md#known-limits-6)).
- **Reads out of file order are a gap** (#253 review L1, #276). Every read of either source is checked to be in the files' order at run time. A read out of order is a gap (Limited, `audit.records_dropped`), and a file name without an order key fails closed.
- **`sys.sysaudacts` joins the agent's own statistics builds that are left out** (Extended Events, on the allow-listed builds; [ADR-0051](docs/adr/0051-sqlserver-connector.md) note of 2026-10-18, accepted by the maintainer; #276, measured on 2022 and 2025). In 0.8.x, the build that the agent's `audit_specifications` proof causes on a new server was reported.
- **A read whose re-probe finds a new file set or a restarted session ends there** (Extended Events; #276 re-review N1, #278). It no longer writes back the position computed before the re-probe, which could report a second gap or a refused position. The next read starts from the new position.

**MySQL / MariaDB**
- **Table and database names taken from statement text keep the case they are written in** (Audit; [ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decision 3, security review H1; #300).
  - **Where**: the statement-text analysis used for `server_audit` `QUERY` records, the Percona `audit_log` text, and `performance_schema` texts and digests.
  - **Before**: this analysis lowercased every unquoted identifier. Under `lower_case_table_names = 0` (the Linux default), a read of `crm.Customers` written without backquotes was reported as `crm.customers`, another table.
  - **Now**: unquoted names are kept as written, like backquoted ones and like the names of table records. Keywords, function names, the built-in lists, the agent's own texts and the dump signature still match without case.
  - **System schemas**:
    - `information_schema` and `performance_schema` are matched in any case, and named in lower case.
    - Reads of `sys` and of the `mysql` statistics tables are left out only when written in lower case, since `SYS` or `MySQL` is another database under `lower_case_table_names = 0`. With 1 or 2, such a read is now reported.
  - **Own-read budget**: it still folds names, so two tables that differ by case share one budget, which only reports sooner.
  - **Name heuristics** see the names as written too: a first name in any case (`JoHn`) and an `MD5` hash in upper case are still replaced by `*`.
  - **Residual**: the agent's event groups key on names as written. With `min_rows` set, reads of one table written in two cases under `lower_case_table_names = 1` or `2` are compared with the threshold one spelling at a time. They can then be dropped where their sum would pass, as backquoted names in another case already were.
- **User databases named `SYS` or `MySQL` are covered** (Discovery and the CAS store guard; #300 follow-up, #308, #318).
  - **Before**: Discovery's table list and the CAS store guard left out every database named `mysql` or `sys` in any case. Under `lower_case_table_names = 0`, `SYS` and `MySQL` are user databases, distinct from the system schemas, so they were never sampled and their CAS ticket tables never guarded.
  - **`mysql` and `sys`**: now left out only as written.
  - **`information_schema` and `performance_schema`**: still left out in any ASCII case, since no user table can exist under such a spelling. MySQL refuses such a database. MariaDB accepts `CREATE DATABASE Performance_Schema` but refuses a table in it, reads the system schema through it, and 11.8 lists the system tables under it.
  - **Non-ASCII spellings**: a spelling such as `performance_ſchema` is not folded; it is a user database on MySQL.
  - **System objects**: whatever the database's name, catalog rows of system objects (engine `PERFORMANCE_SCHEMA`, type `SYSTEM VIEW`) are never sampled.
  - **Audit's always-reported lists** also match names spelled with characters that the servers fold to them: `performance_ſchema` reads the system schema on MariaDB. These lists cover the statement-text and statistics tables, `mysql.audit_log_*` and system-schema writes. When a list matches only through this wider rule, the event keeps the object as written next to the listed system name (#318).
  - **Reads of `performance_schema`**: Audit now leaves them out only as written, as for `sys` and `mysql`; `information_schema` in any case. A read written `PERFORMANCE_SCHEMA.t` is reported as an application read.
- **The reported name case is reset on a new server run on the audit-log file sources** (Audit; [ADR-0055](docs/adr/0055-agent-reported-name-case-semantics.md) decision 2, #303 residual; #308).
  - **Which sources**: the MariaDB `server_audit` log, or a Percona / MySQL Enterprise JSON log.

### 🔒 Security
- **Agent: more names sent as `*`. Every normalized name follows the contract rule `IdentifierProduced`** ([ADR-0057](docs/adr/0057-identifier-hardening-agent-first.md) section 2, the agent-first part; #334).
  - **Scope**: the agent applies the digit-run, address and escape rules of `KeyPattern` to every other name it sends: databases, schemas, tables, collections, columns, field paths, and LDAP containers and attributes.
  - **What is sent as `*`**: a segment, or an LDAP RDN value, that holds any of the following:
    - a run of 9 or more digits and separators that starts and ends with a digit (`v1_2_3_4_5`, `06_12_34_56_78`);
    - only 9 or more digits, spaces, `_`, `+` and `-`;
    - an IPv4 address as whole segments;
    - a dashed or dotted MAC address (`001a.2b3c.4d5e`; `face.cafe.beef` is kept);
    - a percent escape;
    - a code point unassigned in the agent's Unicode tables.
  - **Example**: `device.001a.2b3c.4d5e.port` is sent as `device.*.port`.
  - **When the rules are read**: on the name as the engine gives it, before array indices become `[]`. So `host.10.0.0.1` is now sent as `host.*`, no longer as `host[][][][]`.
  - **Already masked before**: the dashed MAC form, percent escapes and longer digit runs.
  - **Measured**: on the names of the dev ground truth, seeds and init scripts, the connectors' integration tests, the CAS fixtures and the load seed, none of 4 163 names is sent differently.
  - **The contract schema**: the rules are stated in `shared/protocol/identifier-produced.schema.json`, which no request, response or generator uses (a compatible change).
  - **Unchanged**: the agent's decoding of `SensitiveObject.object`.
  - **Later release**: the console-side masking.
  - **After upgrading**: rescan Discovery (Upgrade notes).
- **Agent: SQL Server statements checked against an allow-list at run time** (end-of-phase-9 review L1, #276).
  - **Before**: the run-time check was the deny-list only.
  - **Now**: the session also checks every `SQLBatch` and RPC against the allow-list before sending it, after the deny-list. A text must be a constant exactly, or a template whose slots hold what the quoting functions produce. Any other text is refused before it is sent (`internal`).
- **Agent: tokio 1.54.1** (RUSTSEC-2026-0386: unsound `AsyncFd` constructors). The agent does not use `AsyncFd` itself; found by the end-of-phase-9 security review (L2; #337). Dev and release tooling only:

## [0.8.2](https://github.com/Yil00/databastion/compare/0.8.1...0.8.2) (2026-10-23)

A security fix release after 0.8.1: the agent (an IBAN detector panic, `rustls-webpki`) and the console (Next.js). No migration, protocol or grant change. Upgrade the console and the agents; a 0.8.x console accepts this agent.

### 🔒 Security
- **Security fix**, agent (Discovery, every engine): a sampled value holding an ASCII letter, then `ſ` (U+017F), then two digits (for example `xſ12`) panicked the IBAN detector. Its case-insensitive start pattern matched `ſ` as a letter and the two-byte country-code slice then cut it in half. The agent's panic guard kept the agent running, but it failed the whole Discovery call of the target: every table, collection or column after that value in scan order was left unclassified, at every rescan. Anyone who can write a sampled value (an application user too) could hide a target's sensitive data from Discovery. No value was ever logged or sent (the panic message is not logged). The start pattern now takes ASCII letters only (every country code is), the country code is read without a slice that can panic, the same IBANs are found, and a property test checks that the detectors and the column classifier never panic on printable text. The Kelvin sign (U+212A) was a second trigger in the detector, unreachable because sampled values are normalized to NFC first.
  - **Affected**: agent 0.1.0 to 0.8.1, Discovery of every target.
  - **Workaround on 0.8.1 and earlier**: none by configuration (every detector runs whatever the scan's classifiers). A target hit by it fails its Discovery scans with an internal error at every run and raises `connector_panics_total`; upgrade its agent.
- **Console: Next.js 16.4.1** (GHSA-2464-fhr4-w9xw and GHSA-673q-mjm6-r5xr, critical; GHSA-p3m5-59mp-jv5r, high; Next.js 16.0.0 to 16.4.0). We know of no exposure of the console (image optimization off, no `use cache` function, no Server Action), but every console from 0.1.0 to 0.8.1 ships an affected version: upgrade.
- **Agent: `rustls-webpki` 0.103.16** (RUSTSEC-2026-0382): certificate paths through the distrusted emSign intermediates are refused, on the agent's TLS to the console and to the databases.

### ✅ Tests
- The holdout seed is rotated (183917532), since this release changes a classifier.

## [0.8.1](https://github.com/Yil00/databastion/compare/0.8.0...0.8.1) (2026-10-23)

A security fix release after 0.8.0, agent only: no console, migration, protocol or grant change. Upgrade the agents that read SQL Server Audit through Extended Events; a 0.8.x console accepts this agent.

### 🔒 Security
- **Security fix**, agent (Microsoft SQL Server Audit, Extended Events source): a run of large statements stopped the Audit stream at their position. A read of the Extended Events session asks for at most 500 events and accepts at most 12 MiB in answer; above that bound the read was meant to be cancelled and asked again from the same position with half as many events, down to 16, then back up. In 0.8.0 the halving never ran: its condition tested a flag that every client-side bound sets. The read failed, the stream restarted after its backoff and failed again at the same position, and nothing past it was reported until the session's files rolled over that position (then counted as a gap, `audit.records_dropped`). About 100 events near the 128 KiB that a read takes per event (statements of about 60 000 characters) within 500 events of the session's files are enough, and any login whose statements the session records can write them: a client could hide its later reads, and everyone else's, from Audit for as long as the files kept that position. The read now halves whenever the session is still in step after the cancel, and the stream moves past such events with nothing lost or reported twice (unit tests, and the integration test `xe_large_events_are_read_by_halving` on SQL Server 2022 and 2019). A variant was also examined: a read past the 15 s statement timeout is not halved, but 500 events of about 1.2 MB, the largest a buffer of the session holds, read in about 1 s on 2019 and 2022, so it was measured as not reachable; events above 131 072 bytes are read without their text and reported as reads of `*`. This fix was prepared in the open: the defect was found and fixed on a public branch before the advisory, which is published with this release.
  - **Affected**: agent 0.8.0, SQL Server targets whose Audit runs on an Extended Events session (`sqlserver.audit.source: sqlserver_xevents`, or `auto` with an `xe_session` when SQL Server Audit is not usable; the only source on SQL Server 2019). The SQL Server Audit source (`sqlserver_audit`) had the same condition, but its records (about 9.3 KiB at most) cannot reach 12 MiB within 500, so it is not reachable in practice.
  - **Workaround on 0.8.0**: on SQL Server 2022 and 2025, read Audit through SQL Server Audit (`sqlserver.audit.audit_name` with `source: sqlserver_audit`, or `auto`, which prefers it when usable; [user guide](docs/10-user-guide.md#microsoft-sql-server-targets); that source needs its own grants and an operator-configured `FILE` audit, and its coverage differs: [docs/08](docs/08-engine-capabilities.md#microsoft-sql-server-audit)). On SQL Server 2019, alert on a growing `audit_stream_failures_total` heartbeat metric of the agent, or on repeated `audit stream failed; restarting` warnings with `code=resource_limit` for the target in the agent's logs, and review the session's files for that period by other means.
  - **Restarts keep the halved size** (security review L1 of the fix): when the server does not acknowledge the cancel of such a read within 5 s, the session is out of step and the stream ends; the agent now keeps the halved size for that target, source and position (in memory, until the agent restarts), so the restarted stream reads fewer events from the same position (nothing skipped) instead of starting again at 500, and a recurring failure there still walks down to 16. The kept size ends with the next successful read. Both SQL Server sources.

## [0.8.0](https://github.com/Yil00/databastion/compare/0.7.0...0.8.0) (2026-10-17)

Planned for the next minor release (0.8.0), with phase 9: Microsoft SQL Server, Redis and Valkey. The entries below are merged on `dev`. The end-of-phase-9 security review is done (no Critical or High finding); every release gate is met ([RELEASE.md](RELEASE.md#open-release-gates)).

### ⚠️ Upgrade notes
From 0.7.x: upgrade the console first, then the agents, as for every release (a console `X.Y` accepts agents `X.Y` and `X.(Y-1)`, [RELEASE.md](RELEASE.md#compatibility)). This release adds three engines (Microsoft SQL Server, Redis and Valkey) and one console migration. Existing targets keep their grants; two Audit behaviour changes apply to every engine (the first two notes below), and two settings are recommended: a UTF-8 character type for the console database and a longer MySQL / MariaDB digest length.

**Behaviour changes on existing targets**
- **An event with more than 15 objects is now always reported (behaviour change, end-of-phase-9 security review G7, #262).** In 0.1.x to 0.7.x, an event kept at most 16 objects and the rest were dropped without a sign: on PostgreSQL (pgaudit relation records, failed and cancelled statements, `pg_stat_statements` and `pg_stat_activity` texts), on MySQL / MariaDB (audit-log table records, multi-statement texts) and for OpenLDAP containers. A sensitive object named after 16 others was then hidden from object-scoped policies, and with `min_rows` the event could be dropped. From 0.8.0 an event names at most 15 objects plus `*`; past that it names `*`, is always reported (never dropped by `min_rows` or `sensitive_objects`) and is never left out as the agent's own read. Expect more events for statements that touch many tables. This was a detection gap, not an exposure of data; no security advisory is published for it ([docs/08](docs/08-engine-capabilities.md#objects-per-event-and-sensitive-objects-every-engine)).
- **Object names are matched without case or trailing spaces (behaviour change, review N1, agent #262, console #261).** The agent's sensitive-object filter (`audit.configure`) and the console's policies, exceptions and per-object sensitivity compare names after dropping trailing spaces and folding case (Unicode lowercase, final sigma `ς` read as `σ`). Events whose names differ from Discovery's only by case, for example `CRM.CUSTOMERS` on MySQL / MariaDB with `lower_case_table_names` other than 0, now pass the filter and get the sensitivity of `crm.customers`; this can only report more events. Policy conditions and scores ignore trailing spaces on every engine; **exceptions** ignore them only on SQL Server, MySQL and MariaDB targets, so on MySQL and MariaDB an exception for `customers` now also covers `customers `. Review your exceptions with this in mind.
- **Console database: use a UTF-8 character type (recommended, #261).** The console folds non-ASCII names partly with PostgreSQL `lower`, which folds only ASCII under a `C` or `POSIX` `LC_CTYPE`. The bundled PostgreSQL image uses `en_US.utf8`. With your own PostgreSQL, check `SELECT datctype FROM pg_database WHERE datname = current_database();`. Under `C` / `POSIX` matching stays correct, but the worker reads every finding of an agent for each batch of events that names a non-ASCII object, which is slower on large installations ([deploy/README.md](deploy/README.md#1-console)).
- **Own-read budget keys read the final sigma as sigma (#262).** The agent's own-read budget now uses the same fold, so a name spelt with `ς` and with `σ` shares one 24 h budget. The counters saved by a 0.7.x agent are folded the same way when the 0.8.0 agent starts, so their charges are kept.

**Upgrade steps**
- **Upgrade the console before the agents.** An agent of this release keeps Redis / Valkey items spooled until its console lists `engine.redis` and `engine.valkey`, and SQL Server items until it lists `engine.sqlserver` ([ADR-0042](docs/adr/0042-hold-items-of-unlisted-engines.md)).
- **Upgrade every console replica before any agent sees the note-label token `target_status.note_labels.2026_10_b`** (#245). Each replica lists the token in its heartbeat answer, and an agent sends the revision's labels as soon as one answer lists it; a replica that does not know these labels would reject them ([ADR-0022](docs/adr/0022-protocol-capability-negotiation.md) decision 8). Before that, the agent sends `other` in their place.
- **Console migration `0040`** adds the `account_not_recorded` principal to stored access events. The `access_events_principal` check is re-added `NOT VALID` and validated after the migration ([ADR-0028](docs/adr/0028-online-constraint-validation.md)), so it holds no long lock.
- **MySQL / MariaDB: raise the digest length to 2048** (recommended, #256). Set the server start options `performance_schema_max_digest_length` and `max_digest_length` to 2048, so that the agent's poll digests (about 1036 bytes rendered on MySQL 8.4.11) are not cut at the default 1024 and its exact-text rule applies to them. At the default, an interrupted own poll is left out only under the narrower rule of the [ADR-0045](docs/adr/0045-mysql-mariadb-statement-text-tables-and-unqualified-calls.md) refinement of 2026-10-16 ([docs/08](docs/08-engine-capabilities.md#statement-text-tables)).
- **New heartbeat metric `audit_own_polls_interrupted_total`** (#256): rows of the agent's own MySQL / MariaDB `performance_schema` polls that were interrupted (`KILL QUERY` when a stream stops, or the statement timeout) and kept by the server with a cut digest only, now left out instead of reported as reads of `*.*` by the agent's login. The `metrics` map is open-keyed: no contract change.

**New engines: Microsoft SQL Server, Redis and Valkey**
- **New connectors, opt-in.** Nothing changes for existing targets until you declare a `sqlserver`, `redis` or `valkey` target in `agent.yaml`, each with its own dedicated account ([user guide](docs/10-user-guide.md#microsoft-sql-server-targets), [Redis / Valkey](docs/10-user-guide.md#redis--valkey-targets); accounts in [docs/05](docs/05-security.md#recommended-database-accounts-read-only)). The notes below apply to these targets.
- **SQL Server Discovery samples nothing with the minimal grant.** No table-level flag tells a table with a row-level security policy from one without, and the minimal account cannot see the policy catalog, so every database is skipped with `coverage.rls_not_verifiable` unless the target declares `sqlserver.rls_visibility: view_definition` and the account holds database `VIEW DEFINITION`. That grant makes the module bodies of the database (procedures, views, functions, triggers) readable by whoever holds the agent's credentials ([user guide](docs/10-user-guide.md#microsoft-sql-server-targets)).
- **SQL Server Audit needs an operator-created audit and two permissions** (#247). Create a server audit with a `FILE` target and no `WHERE` predicate, and a server audit specification with `SCHEMA_OBJECT_ACCESS_GROUP` and `AUDIT_CHANGE_GROUP`; grant the agent's login `VIEW SERVER SECURITY AUDIT` and `VIEW ANY SECURITY DEFINITION` (SQL Server 2022 and later, only where Audit runs; never `VIEW SERVER SECURITY STATE` or `CONTROL SERVER`); name the audit in `sqlserver.audit.audit_name`. The agent never creates or alters the audit. Held while no Audit stream reads the target, the two permissions are reported as `privilege.audit_grant_without_audit` ([user guide](docs/10-user-guide.md#sql-server-audit)).
- **SQL Server Audit through Extended Events needs an operator-created session and `VIEW SERVER STATE` (SQL Server 2019) or `VIEW SERVER PERFORMANCE STATE` (2022 and later), which exposes every statement text on the server** (#249). With that permission, the agent's credentials read every statement text with its literals, the Extended Events files with the parameter values of every RPC, and the other sessions: grant it only where Audit runs, and protect the password like the data. Create a session with `sql_statement_completed`, `sp_statement_completed` and `rpc_completed`, each with the actions `server_principal_name`, `session_server_principal_name`, `client_app_name`, `database_name` and `session_id`, no predicate on them, and an `event_file` target; `error_reported` (error 18456) for failed logins and `TRACK_CAUSALITY = ON` are recommended. Name it in `sqlserver.audit.xe_session`, with `source: sqlserver_xevents` or `auto`. The agent never creates, alters, starts or stops the session ([user guide](docs/10-user-guide.md#sql-server-audit-through-extended-events)).
- **Minimum rows on SQL Server Audit targets.** SQL Server Audit events carry no row count (Extended Events events do): a `min_rows` value in the Audit settings of a SQL Server target read through SQL Server Audit drops every read and write event that carries no signal and is not always reported, except on the objects listed as sensitive. List the sensitive tables as `sensitive_objects`, or leave `min_rows` unset on these targets.
- **Minimum rows on Redis / Valkey targets** (#235 review N2). Their events carry no row count, and key patterns cannot be Audit sensitive objects yet. A `min_rows` value in the Audit settings of a key-pattern target therefore drops every read and write event of that target that carries no signal, and a policy's `min_rows` condition never matches them. Leave `min_rows` unset on these targets; a console warning is a [phase 9 follow-up](docs/ROADMAP.md#phase-9-follow-ups).
- **Policies with `exclude_principals: ["*"]`** do not hide Redis / Valkey events whose account is not recorded (`account_not_recorded`), by design (#235 review).
- **Redis / Valkey own-read budget, scaled** (#252, [ADR-0052](docs/adr/0052-redis-valkey-connector.md) refinement of 2026-10-16). The agent's own sampling reads are left out per learned key pattern and database, within `max_sample_rows × per_key_max` rows per pattern and 24 h (`per_key_max` is 49 today), so that one Discovery scan fits; keys no learned pattern matches keep the plain `max_sample_rows`. **Residual**: through address reuse, or by anyone holding the agent's connection, up to that many rows per pattern and 24 h (49 000 with the default `max_sample_rows` of 1 000) can be left out, only in the agent's own sampling command shapes. A second scan of the same pattern within 24 h has the agent's reads reported once the budget is spent ([docs/05](docs/05-security.md#redis--valkey-connector)).

### ✨ Features
- **Redis / Valkey connector (phase 9, P9-B, [ADR-0052](docs/adr/0052-redis-valkey-connector.md); #237, #239).** Discovery and a Limited Audit for Redis 6.2.7+ and Valkey 7.2+. The 6.2.7 floor comes from the ADR-0052 refinement of 2026-10-14, accepted on 2026-10-15. Redis 6.2 runs only with the local opt-in `redis.unevaluated_acl: accept`.
  - **Client and transport**: the agent's own bounded RESP3 client. `AUTH`, then `HELLO 3` without credentials. TLS `verify_full` by default; cleartext only on a Unix socket (server uid checked) or a loopback address.
  - **Account checks**: the ACL user's rights are evaluated with `ACL DRYRUN`, never `ACL GETUSER`. Accounts that can run a refusal-list command (`CONFIG SET`, `MODULE LOAD`, scripting, `ACL SETUSER`, `REPLICAOF`, `MIGRATE`…) are refused.
  - **Discovery**: a bounded `SCAN` walk with local filtering against the declared `redis.key_patterns`, and bounded sampling per type. Key names leave the agent only as normalized key patterns (`user:*:email`); values found in names are reported under `#key` / `#field`.
  - **Audit**, Limited at best: `SLOWLOG` (Valkey 8.1+: `COMMANDLOG`), Valkey's large-reply log, `ACL LOG` and `sync_full`. Every log entry is reduced at parse time to the command, learned key patterns and counts. Accounts come from `CLIENT LIST`, best effort, and `account_not_recorded` is used otherwise.
  - **Signals and guard**: `signature.full_sync`, `volume.large_reply`, `shape.keyspace_enumeration`, `signature.cas_ticket_read`. The CAS store guard applies to key names and values.

- **Protocol (P9-C, #234)**, a compatible change. New engines `sqlserver`, `redis` and `valkey`, each behind an `engine.*` capability token. The Redis / Valkey connector and sources need both tokens. Also new: Redis / Valkey and SQL Server `AuditSource` values; the `KeyPattern` object name for Redis / Valkey; the `account_not_recorded` principal (Redis / Valkey sources only, never on `auth_failure`); SQL Server note labels (revision `target_status.note_labels.2026_10`); 7 signals and 25 target notes. Existing note texts are now engine-neutral.
- **SQL Server connector, lot 1: `check()` and Discovery (phase 9, P9-A, [ADR-0051](docs/adr/0051-sqlserver-connector.md) and its refinement of 2026-10-14; #242, #243).** SQL Server 2019, 2022 and 2025 (Standard, Enterprise, Developer, Express; Azure refused), SQL logins only. Audit: below (#247).
  - **Client and transport**: the agent's own bounded TDS client, no driver crate. TLS on every connection, loopback included, with the certificate verified against `sqlserver.ca_file` or the system store and the declared host; no unencrypted mode. `tls: auto` (default) tries TDS 8.0 strict encryption first and falls back once to `mandatory` only when the strict handshake fails before any TDS byte; after one strict session, a persisted "strict seen" mark stops the fallback for that target. SQL Server's self-signed fallback certificate is refused.
  - **Account checks**: the effective and securable-level permissions of the login in every accessible database, against a refusal list (`sysadmin`, `db_owner`, `CONTROL SERVER`, the audit-alteration rights, the server and database event-session rights, the identity rights…) and an over-privilege list, a one-bit probe for other logins' password hashes, logon triggers, and the CAS store guard. A refused account, or a refusal list that cannot be read completely, stops Discovery.

Sampled types: character types, `text` / `ntext`, `int`, `bigint`, `decimal`, `numeric`, `date`, `datetime`, `datetime2` and `smalldatetime`; other types (binary, `money`, floats, `uniqueidentifier`, `time`, `datetimeoffset`, `xml`, `json`…) are not sampled. Never sampled either: views, computed columns, Always Encrypted columns, and tables with row-level security. Masked, encrypted and computed columns and views are counted in target notes.
  - See [docs/08](docs/08-engine-capabilities.md#microsoft-sql-server-discovery) and the [user guide](docs/10-user-guide.md#microsoft-sql-server-targets).
- **SQL Server Audit, lot 2 (phase 9, P9-A, [ADR-0051](docs/adr/0051-sqlserver-connector.md) decision 6 and its refinement, option (a'), accepted on 2026-10-15; #247).** On SQL Server 2022 and 2025, the agent reads the operator's SQL Server Audit (`FILE` target) through `sys.fn_get_audit_file` (`audit_source` `sqlserver_audit`). Partial at best, never Full; Limited until the first record; None on SQL Server 2019 (`audit.sqlserver_audit_needs_control_server`).

- **SQL Server Audit, lot 3: Extended Events (phase 9, P9-A, [ADR-0051](docs/adr/0051-sqlserver-connector.md) decision 6 and its refinements of 2026-10-15 and 2026-10-16, accepted by the maintainer; #249).** The agent reads the operator's Extended Events session (`event_file` target) through `sys.fn_xe_file_target_read_file` (`audit_source` `sqlserver_xevents`): the only Audit source on SQL Server 2019, and the source on 2022 and 2025 when SQL Server Audit is not usable (with `source: auto`). A restart of the session, grown drop counters or a file lost to rollover is a gap: `audit.records_dropped` and Limited for 24 h.
  - **Events**: one per statement (`rpc_completed` context only, its parameter values dropped), row counts (`volume.large_result`), objects from the statement text through a fail-closed relation pass: `*` and always reported whenever the text may not name every object, and for every DDL and DCL statement. ### 🐛 Bug Fixes
- Agent (PostgreSQL Audit, `csvlog`): a stream that started without a cursor while PostgreSQL was writing a large record in pieces could begin inside a quoted field and stay out of step with the CSV quoting for as long as it ran: no further record was ever split, so the stream reported nothing, with no warning. Found by an intermittent integration failure before 0.8.0, present in 0.1.x to 0.7.x; no security advisory is published (maintainer decision). Upgrade the agent to 0.8.0. The tailer now checks every quote against the CSV quoting rules: on a first start inside a file, records are dropped until a quote settles the state (within one PostgreSQL record), a state that only fits inverted is flipped, and a record damaged in the middle is dropped, with the record that follows it, and counted once in `audit.records_dropped` with a warning (a damaged log only: PostgreSQL doubles the quotes of statement texts). `jsonlog` and the other line-based logs recovered at the next line and were not affected
- **Audit: objects past the 16th of a statement are no longer lost (end-of-phase-9 security review, G7).** In 0.1.x to 0.7.x, a statement reaching more than 16 objects on PostgreSQL (pgaudit relation records, failed multi-statement texts) and on MySQL / MariaDB (file-source table records, multi-statement texts) could lose object names silently, and so could OpenLDAP containers past 16 (Low). A sensitive object past the 16th was then hidden from object-scoped policies, and with `min_rows` the event could be dropped. This was a detection gap, not a data exposure. From 0.8.0, past 15 named objects an event names `*` and is always reported, on every engine ([docs/08](docs/08-engine-capabilities.md#objects-per-event-and-sensitive-objects-every-engine)).
- **Audit: the sensitive-object match ignores case and trailing spaces (end-of-phase-9 security review, N1; agent #262, console #261).** Names taken from a statement text keep its spelling, so on SQL Server (case-insensitive collation) and MySQL / MariaDB with `lower_case_table_names` other than 0, `CRM.CUSTOMERS` or `[customers ]` was not matched against the sensitive `crm.customers` and could be dropped by `min_rows`. The agent now compares these names case-insensitively (final sigma `ς` read as `σ`), without trailing spaces, on every engine; this can only report more events. The SQL Server connector also drops trailing spaces from the names it sends, so Audit objects and Discovery locations agree. The console matches event and finding objects against policies, exceptions and per-object sensitivity with the same fold, so such an event also gets the sensitivity of `crm.customers` and matches its policies. Policy conditions and scores ignore trailing spaces on every engine; exceptions ignore them only on SQL Server, MySQL and MariaDB targets, where identifiers compare that way, so an exception never covers more on PostgreSQL, MongoDB, Redis or Valkey. The console database should have a UTF-8 character type (`LC_CTYPE`, the bundled image's default); under `C` / `POSIX` matching stays correct but slower, reading every finding of an agent for a batch of events naming a non-ASCII object ([deploy/README.md](deploy/README.md#1-console)).
- **SQL Server Audit: no record lost in large audit buffers (#253).** A buffer can hold more than 500 records (770 to 1 047 measured on 2022), and the agent dropped the rest of such a buffer after skipping 500 handled records on its side: the P9-D load run lost 0.24 to 0.32 % of the statements at 300 statements/s, visible only as `audit.records_dropped`. The handled records of a buffer are now skipped on the server (`OFFSET … FETCH`), as on Extended Events. A position saved before this fix reads its buffer again once: records may be reported twice, never lost.
- **SQL Server Audit: no `audit.records_dropped` on a normal first start (#255).** The first-start history boundary now goes by the order of the records read, on both sources, so a large backlog stays history however long it takes to skip; a step back of the server's clock beyond the tolerance (the delivery delay, at least 5 s) is still counted as dropped.
- **Redis / Valkey Audit: the agent's own Discovery reads are no longer reported during a scan under Audit (#252)** when keys are spread over several databases: the own-read budget is charged per learned pattern and database (see Upgrade notes).
- **MySQL / MariaDB Audit: interrupted own polls are no longer reported (#256)** as reads of `*.*` by the agent's login (MySQL 8.4 keeps a killed or timed-out poll with no text and a cut digest; ADR-0045 refinement of 2026-10-16, accepted). Each poll session is also noted right after its own-thread probe, so a stream stopped during its start leaves its probes recognized.
- **`agent.yaml` parse errors name the SQL Server Audit keys, the Redis / Valkey `replicas` key and the spool keys, and their path (#251)**, which they left out before; a test checks every key of the schema against the list.
- **Redis / Valkey Audit: the agent's own short-lived sessions are no longer reported as other clients' reads (#244).** Slow-log entries carry no client id, and a session that opened and closed between two `CLIENT LIST` polls was missed. While an Audit stream runs for the target, each agent session now sends `CLIENT LIST ID <own id>` once to learn the address the server sees for it, only when `+client|list` is known to be held. No grant is added ([ADR-0052](docs/adr/0052-redis-valkey-connector.md) implementation note).

### ⚠️ Known limitations
- Redis / Valkey: Audit sees only slow commands (and, on Valkey 8.1+, large replies), with no row count. Accounts are best effort, and Unix-socket clients are never attributed: on a socket target, the agent's own slow entries come back as `account_not_recorded`. Many two-segment key names are over-masked to `*:*`. The CAS Redis ticket registry prefix is not confirmed. End-to-end tests and load runs on Valkey 9.0.6 and Redis 8.10.2. Details: [docs/08](docs/08-engine-capabilities.md#redis--valkey-audit).
- SQL Server: Audit is Partial at best: SQL Server Audit (2022 and 2025) has no row counts, and Extended Events (every version, the only source on 2019) is lossy by design and names objects only through the statement text. The records of an agent session's last statement are left out up to 250 ms after the session's clean end (same exact text only); on Extended Events, also the session's last 16 texts up to 20 ms after it (clock skew measured up to 3.5 ms; Windows not measured). Sampling credits are not persisted: a Discovery sample whose record is read after an agent restart is reported. Reads through views or procedures under ownership chaining are recorded on the view or procedure only. With the minimal grant, Discovery samples nothing (see Upgrade notes). Strict encryption is available on Linux from SQL Server 2025 only: use `tls: mandatory` for 2022 on Linux. Windows integrated authentication, Microsoft Entra ID and contained database users are not supported. The end-to-end and load tests run SQL Server Audit on 2022 Express only. The server's own telemetry process reads audited objects under the principal `<host name>$` (observed on Linux): those reads are reported, and match policies on every read; exclude that principal in such policies if they are noise. Details: [docs/08](docs/08-engine-capabilities.md#microsoft-sql-server-discovery), [Audit](docs/08-engine-capabilities.md#microsoft-sql-server-audit).
- SQL Server Extended Events (#249): object names are taken from the statement text, chosen by the client and protected only by the name normalization; another session whose files match the poll's file pattern in the same folder is read too; a restart of a session within 500 ms of its start is not detected; an RPC procedure name is attached only when its `rpc_completed` is in the same read; a refused `xp_cmdshell` leaves no event; statistics builds are counted on builds outside the allow-list, and a build on `sys.sysaudacts` is reported. The plan cache is not a source. This source is not in the end-to-end or load tests. Details: [docs/08](docs/08-engine-capabilities.md#extended-events-known-limits).
- SQL Server Extended Events statistics builds (end-of-phase-9 review M3): the server's internal `StatMan` statements are left out only on three exact builds, 15.0.4500.2, 16.0.4305.5 and 17.0.5015.4. On any other build, a newer cumulative update included, every automatic statistics build is reported as a read of its table by whichever client triggered it, its empty internal statements as always-reported reads of `*`, and, on a new server, the agent's own catalog reads as reads of system base tables by its login. Expect this noise there. Do not exclude the agent's account in policies (that would also hide reads made with a stolen copy of its credential); keep any exclusion narrow, per table and target. The build list is refreshed per release ([user guide](docs/10-user-guide.md#sql-server-audit-through-extended-events)).
- SQL Server: the 24 h gap memory (Limited after a gap, `audit.records_dropped`) is kept in memory only, so after an agent restart a target can show Partial again before the 24 h are over ([docs/08](docs/08-engine-capabilities.md#known-limits-6)).

## [0.7.0](https://github.com/Yil00/databastion/compare/0.6.0...0.7.0) (2026-10-13)

### ⚠️ Upgrade notes
From 0.6.x: upgrade the console first, then the agents, as for every release (a console `X.Y` accepts agents `X.Y` and `X.(Y-1)`, [RELEASE.md](RELEASE.md#compatibility)). This release changes mainly the agent. The console only gains the two new target-note codes in its registry (below) and dependency updates; **no console migration**. The protocol change is compatible: two codes appended to `shared/protocol/target-notes.json` and a fixture, no new protocol version. **No grant is added on any engine** ([05-security.md](docs/05-security.md#recommended-database-accounts-read-only)): the new PostgreSQL checks read `pg_db_role_setting`, `pg_proc` and, on PostgreSQL 15+, `pg_parameter_acl`, which every role can read by default. Most changes below make Audit report more, as events that no `min_rows` setting drops: **review the policies and baselines of PostgreSQL, MySQL / MariaDB and MongoDB targets after the upgrade**; scope them by object, and exclude known tool principals there, never an agent account. Check these points before upgrading the agents:
- **PostgreSQL targets at Full**: `log_min_messages` and `log_min_error_statement` at `error` or lower (the defaults), with no per-role, per-database or per-function override above `error` and, on PostgreSQL 15+, no `SET` or `ALTER SYSTEM` grant on them to a role other than superusers (a grant to the agent's role is reported as an over-privilege); `pg_db_role_setting` readable by the agent's role (through `PUBLIC`, the default: check with `SELECT pg_catalog.has_table_privilege('databastion_agent', 'pg_catalog.pg_db_role_setting', 'SELECT')`, with your agent role's name). Otherwise the target shows Partial after the upgrade, and the agent's local detail names the setting. Keep `pgaudit.log_catalog = on` (the pgaudit default), and declare in `postgres.databases` every database that monitoring tools connect to, `postgres` included ([user guide](docs/10-user-guide.md#8-audit-prerequisites-and-levels)).
- **MySQL / MariaDB targets**: keep the `performance_schema` `statements_digest` consumer enabled, and `server_audit_query_log_limit` and `performance_schema_max_sql_text_length` at 1024 or more; both are now reported as target notes (below). Give each agent its own database account: two agents sharing one account on one server report each other's ended poll and Discovery sessions as reads by an unidentified principal.
- **Policies and agent accounts**: the new always-reported events are never left out as the agent's own, except the agent's own statements recognized by their exact text. Do not quiet them by excluding an agent account in a policy: the exclusion would also hide reads made with a stolen copy of its credential.
- **PostgreSQL Audit reports failed and cancelled reads (fixed; behaviour change, [ADR-0037 refinement of 2026-10-12](docs/adr/0037-postgresql-full-requires-pgaudit-log-rows.md#refinement-2026-10-12-accepted-failed-and-cancelled-statements); security reviews of #197, L1, and of #213).** With `pgaudit.log_rows = on` (needed for Full), pgaudit writes a statement's records when it ends, so a read that ended in an error or a cancel, including one that already streamed rows to the client, a client cancel, a statement timeout and a connection lost mid-result, gave no event at Full, from any role (a known issue of 0.4.0 to 0.6.x; **on 0.6.x, the workaround stays `pgaudit.log_rows = off`**, Partial with no row counts). When the pgaudit log is the source, the agent now also reads the server's `ERROR` lines, and the `FATAL` lines that carry a statement, of client backends, from the same file, by SQLSTATE only: their message, detail, hint, context and internal query, which can quote the value read, are never copied, logged or sent. A failure whose code says nothing of a value (classes `42`, `3F`, `0A`, `25`, timeouts, cancels, lost connections…) is a read of the statement's relations; any other code is the statement's action; both **with no row count and always reported** (never dropped by `min_rows` or `sensitive_objects`), a plain failed `INSERT … VALUES` aside; a statement rejected before it ran (`25P02` in an aborted transaction, a syntax error in a text that does not lex, a refused connection) gives none. With `pgaudit.log_rows = off`, the line repeats the record written at the start and is not reported twice. **Full now also requires `log_min_messages` and `log_min_error_statement` at `error` or lower** in the monitored databases (the PostgreSQL defaults): above, or not readable, the target shows Partial and the agent's local detail names the setting (no new target note, no protocol change). **Expect events from applications whose queries fail** (a missing table or column, a constraint violation on an `UPDATE`, a statement timeout), one per principal, action, objects and aggregation window; the agent's own sampling statements cancelled at the byte budget are charged its whole own-read budget for that relation ([docs/08](docs/08-engine-capabilities.md#failed-and-cancelled-statements)).
- **PostgreSQL Audit reports reads of the catalogs that hold credentials and stored values (behaviour change, [ADR-0050](docs/adr/0050-postgresql-credential-and-value-bearing-catalogs-as-reads.md)).** A read of `pg_authid`, `pg_shadow`, `pg_roles`, `pg_user`, `pg_db_role_setting`, `pg_user_mapping`, `pg_user_mappings`, `pg_foreign_server`, `pg_subscription` or `pg_proc` that may select a secret column (`rolpassword`, `passwd`, `useconfig`, `rolconfig`, `setconfig`, `umoptions`, `srvoptions`, `subconninfo`, `proconfig`; `*`, a whole row, a column alias list, `NATURAL`, `COPY <entry>`, a call that is not built in, an application relation next to it), and any read of `pg_largeobject`, `pg_file_settings` (and `pg_show_all_file_settings()`), `pg_hba_file_rules` (and its function) and `information_schema.user_mapping_options`, `_pg_user_mappings`, `foreign_server_options`, `_pg_foreign_servers`, was a catalog read, never reported: it is now a read event naming the catalog, from every role, the agent's included, **never dropped by `min_rows` or `sensitive_objects`**. With pgaudit relation records, an entry's record next to a user view, materialized view or foreign table is one too: **a user view over `pg_roles`, even without a secret column, is reported**. Reads without the secret columns (`\du`, exporters, ORMs, `SELECT r.rolname FROM pg_roles r`) stay quiet. **Expect events from `pg_dump` / `pg_dumpall`, PgBouncer's default `auth_query` on `pg_shadow` (one per pooler and window), admin tools that show role or function properties (pgAdmin, DBeaver) and `psql`'s `\drds`, `\deu+`, `\dRs+`**; there is no allow-list: scope the policies by object or exclude the principal there. Keep `pgaudit.log_catalog = on`. The connector's own catalog statements were rewritten without column alias lists so that they stay quiet (their `pg_stat_statements` texts change once) ([docs/08](docs/08-engine-capabilities.md#credential-bearing-catalogs), [05-security.md](docs/05-security.md#recommended-database-accounts-read-only): who reads these catalogs).
- **PostgreSQL Full also requires no per-role, per-database or per-function override of `log_min_messages` / `log_min_error_statement` above `error`, and no grant on them (behaviour change, [ADR-0012 refinement of 2026-10-12](docs/adr/0012-postgresql-agent-grants.md#refinement-2026-10-12-accepted-a-two-key-read-of-pg_db_role_setting)).** The agent's session did not see another role's `ALTER ROLE … SET log_min_messages = fatal` (or `IN DATABASE`), nor a function's `SET` clause, which hide that role's failed reads (or their text) from the log while the target showed Full. While a target's level would be Full and no `pg_stat_statements` stream of it runs, `check()` and the stream's 5-minute probe now read these two keys of `pg_db_role_setting.setconfig` and `pg_proc.proconfig`, **filtered by the server** (no other setting reaches the agent: the only exception to the catalog denylist, its texts held by a unit test), and, on PostgreSQL 15+, the `SET` and `ALTER SYSTEM` grants on them (`pg_parameter_acl`). An override above `error`, a grant to a role other than superusers and the agent's, or a refused read (`pg_db_role_setting` revoked from `PUBLIC`) **caps the target at Partial**, with a local detail naming the database, the setting and the roles or functions (no target note, no protocol change); a grant to the agent's own role is reported as an over-privilege. The two-key reads are left out of the events as the agent's own by exact text on pgaudit only. A `FATAL` line without a statement from a role with such an override is now a read of `*`, and so is every role's while the stream has seen an `ALTER ROLE`, `ALTER DATABASE`, parameter grant or function DDL since the last probes. No grant is added: both catalogs are readable by `PUBLIC` ([docs/08](docs/08-engine-capabilities.md#failed-and-cancelled-statements), [user guide](docs/10-user-guide.md#8-audit-prerequisites-and-levels)).
- **PostgreSQL Audit reports reads of the views that hold other sessions' statement texts (behaviour change, [ADR-0049](docs/adr/0049-postgresql-statement-text-views-as-reads.md) part 1).** A read of `pg_stat_activity` (or `pg_stat_get_activity(…)`, `pg_stat_get_backend_activity(…)`) or of the `pg_stat_statements` view or function that may select the statement text is a read event naming `pg_catalog.pg_stat_activity` or `<schema>.pg_stat_statements`, from every role, the agent's included, always reported (never dropped by `min_rows` or `sensitive_objects`). Reads that provably select no text (`SELECT state, count(*) FROM pg_stat_activity GROUP BY state`, `postgres_exporter`'s activity query, `SELECT queryid, calls FROM pg_stat_statements`) stay quiet. `pg_stat_monitor`, `pg_store_plans`, `pg_show_plans` and `pg_qualstats*` are always text reads. A call of `query_to_xml` and the other SQL-running XML and text-search functions, `pg_read_file`, `pg_read_binary_file`, `pg_logical_slot_*_changes` or the large-object functions adds `*`, also next to catalogs only. The agent's own `pg_stat_statements` text query is left out by exact text only, and with pgaudit only for records written while a `pg_stat_statements` stream of the target ran. Expect events from query-sampling tools (Datadog Database Monitoring, pganalyze, PMM, PoWA, pgAdmin's dashboard) and DBAs' scripts; scope or exclude their principals in the console. `check()` says in its local detail when the agent's role holds `pg_read_all_stats` while pgaudit is the source. A statement that also calls a schema-qualified function outside `pg_catalog` (`SELECT a.pid, public.f() FROM pg_stat_activity a`) is a text read.
- **PostgreSQL Audit reports user code next to catalogs only (behaviour change, [ADR-0049](docs/adr/0049-postgresql-statement-text-views-as-reads.md) decision 8).** A statement whose relations are all catalogs, which gave no event, is now a read of `*`, from every role, always reported, when it calls a function, applies an operator or casts to a type that is not built in for that database (also through `PREPARE … AS`, `EXPLAIN`, `DECLARE … CURSOR FOR` and `CREATE TABLE / MATERIALIZED VIEW … AS`, the latter's DDL event included): a function qualified with another schema than `pg_catalog` (`SELECT crm.f() FROM pg_class`) or not on the built-in list of the server's version, an unqualified function or operator that a user overload shadows there (`SELECT length(42) FROM pg_class` once a role created `"$user".length(integer)`, the CVE-2018-1058 class), a cast to a user type or domain, every catalog-only statement of a database with an implicit user-function cast between built-in types, and every parameterized catalog-only statement of a database with a user domain whose `CHECK` runs non-C code (the agent's own statements excepted by exact text). `check()` runs one more catalog query per declared database at every heartbeat (the collision probe; names kept in the agent's memory only), and after a function, operator, type, cast or extension DDL the stream reports unqualified calls, operators and casts next to catalogs as `*` until two heartbeats have probed again. Expect events from catalog queries that call extension or user functions, a burst after migrations, events for catalog queries in databases the target does not declare (declare the databases monitoring tools connect to, `postgres` included: [user guide](docs/10-user-guide.md#6-declare-targets)), and with `hstore`, unqualified `->` next to catalogs. `psql`'s describe queries, `postgres_exporter` and the agent's own statements stay quiet. The connector's own SQL now writes every operator as `OPERATOR(pg_catalog.…)` and every array of constants as one literal (`'{r,p,m}'::pg_catalog."char"[]`, which PostgreSQL 18's `pg_stat_statements` does not squash), so its `pg_stat_statements` texts change once.
- **MySQL / MariaDB Audit reports `EXPLAIN` / `DESCRIBE` / `DESC` of a statement as a read (behaviour change, [ADR-0047](docs/adr/0047-mysql-mariadb-explain-as-a-read.md)).** The optimizer reads the rows of `const` tables (a primary or unique key lookup) while it plans, and MySQL and MariaDB show their values (`SHOW WARNINGS`, JSON and TREE plans) or answer a value guess in the plan. Such an explain is now a read event naming every relation its statement names (an explained `UPDATE`, `DELETE`, `INSERT … SELECT` or `REPLACE` names its target too), from every account, the agent's included, **never dropped by `min_rows`**, with no row count. **Developers' and DBAs' tools (Workbench, phpMyAdmin, DBeaver), ORM explain helpers and query analysers (PMM Query Analytics, `pt-query-digest --explain`) now produce events**; there is no allow-list: scope the policies by object or exclude the analyser's principal there. `EXPLAIN ANALYZE` and MariaDB `ANALYZE` are now always reported too, with no row count. `DESCRIBE t`, `EXPLAIN t`, `SHOW COLUMNS` and the literal shape `EXPLAIN SELECT 1 FROM performance_schema.<table>` (the agent's readability probes) stay quiet ([docs/08](docs/08-engine-capabilities.md#explains-of-a-statement)).
- **MySQL / MariaDB Audit: reads into variables are always reported, and `CREATE … AS SELECT` names its sources (behaviour change, phase 8 follow-ups).** A read whose values go into session variables (`SELECT … INTO @v`, classic or trailing, `INTO` local variables, an `@v := …` assignment, `SET @v = (SELECT …)`, `DO` with a subquery) counts at most one row (`ROWS_SENT` 1 for `INTO`, 0 for `SET` / `DO` on `performance_schema`, no count on the file sources), so `min_rows` dropped a key walk: such reads are now **never dropped by `min_rows`**, carry no row count when they sent no row (one that sent rows keeps them), and are never the agent's own. `CREATE TABLE … [AS] SELECT` / `TABLE` / `VALUES`, MariaDB `CREATE OR REPLACE TABLE … SELECT`, and `CREATE` / `ALTER VIEW … AS SELECT` are now one `ddl` event naming the created table or view and the tables the query reads (before: a `ddl` event with no object), as an `INSERT … SELECT` write names its sources ([docs/08](docs/08-engine-capabilities.md#reads-into-variables-and-create--as-select); refines [ADR-0023](docs/adr/0023-mysql-mariadb-audit-sources-and-levels.md) decision 7). Policies on these tables now also match these events. A failed read that sent no row (its error or warning text can show a value, `EXTRACTVALUE(…)` error 1105) is now always reported too.
- **Audit: every read of the agent's own account is charged at least one row to its own-account budget (behaviour change, phase 8 follow-ups).** The budget that leaves the agent's own Discovery reads out (`limits.max_sample_rows` rows per object and 24 h) charged a read that returned no row nothing, so reads with the agent's identity that show values without returning rows (a MySQL / MariaDB conversion warning 1292, an error after one, a filter walk) went unreported without limit. Each such statement now costs one row (an aggregated `pg_stat_statements` delta of `n` calls and `r` rows costs `max(r, 1) + n - 1`), on PostgreSQL, MySQL / MariaDB, MongoDB and OpenLDAP alike, and budget keys ignore the case of names, so `` `HR`.`Customers` `` no longer gets a budget of its own: past the budget such reads are reported, when `audit.configure` lets 0-row reads through (the object in `sensitive_objects`, or no `min_rows`). This covers the reads the source records: `pg_stat_statements` gives no event for a failed read that returned nothing, for any account, so value walks through error messages stay unseen there (the MongoDB profiler and server log now report them, below). The agent's own Discovery stays within the budget (an empty table or LDAP container costs one row per scan; on PostgreSQL the plain read after a short `TABLESAMPLE` now takes only what the sample left, and keeps both samples unless the plain read saw the whole relation, below) ([docs/08](docs/08-engine-capabilities.md#the-agents-own-account); refines [ADR-0023](docs/adr/0023-mysql-mariadb-audit-sources-and-levels.md) decision 6).
- **PostgreSQL and MySQL / MariaDB Audit report reads of the statistics catalogs that hold column values (behaviour change, [ADR-0048](docs/adr/0048-statistics-catalogs-as-reads.md)).** PostgreSQL `pg_stats`, `pg_stats_ext`, `pg_stats_ext_exprs`, `pg_statistic` and `pg_statistic_ext_data` (qualified with `pg_catalog` or unqualified; named `pg_catalog.<name>`), MySQL `information_schema.COLUMN_STATISTICS` and MariaDB `mysql.column_stats` keep sampled column values (most common values, histogram bounds, minimum and maximum). A read of them was a catalog or system read, never reported; it is now a read event naming the catalog, from every account, the agent's included (it never reads them), **never dropped by `min_rows` or `sensitive_objects`**, including whole-row reads and reads that name no value column. **Bloat checks and monitoring tools that read `pg_stats` on a schedule (check_postgres, pgwatch), `mysqldump --column-statistics` and `mariadb-dump --system=stats` now produce events**; there is no allow-list: scope the policies by object or exclude the principal there. On MariaDB, the `server_audit` `READ` records of `mysql.column_stats` that the server writes when it loads a table's statistics stay ignored unless the statement text names the table. On MariaDB `server_audit`, such a record names `mysql.column_stats` when the text cannot be read whole or runs code out of sight (`CALL`, `EXECUTE`, a stored function call, a version comment), for a `HANDLER` read, when the record comes without the load's `table_stats` record, and when the text names a relation with no record of exactly its name (a view over it, then named too; a name written in another case over-reports under `lower_case_table_names = 1`); a `CALL` or other out-of-sight code now adds `*` whatever its table records, on `server_audit` and `audit_log_filter`, and a statement-text or statistics table the text names is named next to the table records of a join on `audit_log_filter`. On PostgreSQL, **application statements naming 16 or more relations now carry `*` and are always reported** when the text decides (`pg_stat_statements`, pgaudit without relation records or without `pg_catalog` records), `CREATE TABLE … AS` included, **reads and writes against `*` are always reported**, `U&"…"` identifiers are compared decoded, and statements copying statistics (`INSERT … SELECT`, `CREATE TABLE … AS`) name them. **With pgaudit, keep `pgaudit.log_catalog = on`** (the pgaudit default; the dev environment and the end-to-end harness now use it): with `off`, a read of the statistics catalogs alone is not logged, and `check()` says so in the agent's log only (no target note, level unchanged). The advice to set `log_catalog = off` against shadowed unqualified `pg_*` names is withdrawn: `pgaudit.log_relation = on` closes that residual ([docs/08](docs/08-engine-capabilities.md#statistics-catalogs), [05-security.md](docs/05-security.md#recommended-database-accounts-read-only): MySQL histograms are visible to any account with a privilege on the table, and `pg_read_all_data` reads `pg_statistic` past row-level security).
- **MongoDB Audit reports failed operations that returned no document (behaviour change, phase 8 follow-ups, security review of #197, L1).** An error text can show the values an operation read (`{$toInt: "$email"}` fails with `ConversionFailure` 241 quoting the address; so do other expression errors, a JavaScript `throw` in `$where`, a duplicate key built from a stored value), and such a read returns no document, so on the profiler and the server log it gave no event at all, for any account. A failed operation is now classified by its numeric `errCode` only (`errMsg` is never read; a non-integer code or `ok: 0` without one counts as telling): refused before reading (`Unauthorized` 13, `NamespaceNotFound` 26, `CommandNotFound` 59, parser errors 40414 / 40415) still gives no event; a quiet failure whose text holds no value (time limits such as `MaxTimeMSExpired`, not the network time limits, interruptions, killed cursors, `WriteConflict`, topology changes, memory limits) is an operation of 0 documents under the `audit.configure` filters, and from the agent's identity a read charged one document to its budget; **any other code is always reported (with its count when it returned documents first), never dropped by `min_rows` or `sensitive_objects`, and never left out as the agent's own** for reads, writes that select or compute from stored documents (`update`, `delete`, `findAndModify`, `bulkWrite`, `$out` / `$merge`) and DDL; a failed `insert` and DCL are ordinary events. **Applications whose queries fail (bad conversions, `$where` errors, duplicate keys on updates) now produce always-reported events**, one per principal, object set and window. The `auditLog` source is unchanged ([docs/08](docs/08-engine-capabilities.md#what-is-kept)).
- **MongoDB Audit reports operations that run server-side JavaScript, always (behaviour change, phase 8 follow-ups, security review of #207, M3; [ADR-0027 refinement of 2026-10-12](docs/adr/0027-mongodb-audit.md#refinement-2026-10-12-accepted), accepted).** A conditional sleep in `$where` or `$function` under `maxTimeMS` answers one yes / no question per operation, and both outcomes (`MaxTimeMSExpired`, or a success with no document) read 0 documents: `min_rows` dropped them for every account, and from the agent's identity they were left out within its budget. An operation whose command holds a key `$where`, `$function`, `$accumulator` or `$_internalJs…` (what `mapReduce` compiles to, which a client can write) at any depth below 64 (filters, `$expr`, projections, `$match` / `$group` stages, `$lookup` / `$facet` / `$unionWith` sub-pipelines, update pipelines, `findAndModify`, `count`, `distinct`, `explain`, `$out` / `$merge`), whose cursor's command or view pipeline does, a `mapReduce` (or its `explain`), or an operation on `system.js`, is now **always reported (never dropped by `min_rows` or `sensitive_objects`) and never left out as the agent's own**, with its usual action, objects and count, on the server log, the profiler and the `auditLog`; refused before running, it still gives no event. Deeper nesting, more than 64 KiB of command documents (a `getMore` of a large `find`, a read through a view with a large pipeline), a `getMore` whose opening command is not shown, and a command the server cut where a key could have been cut count as JavaScript (fail closed); `insert` documents never do. Only key names are compared: the JavaScript code and literals are never read, kept or logged, and on the profiler the server computes one boolean (the poll command grows by about 10 KiB). Whether the server allows JavaScript cannot be read with the agent's grants and is not shown. **Applications that use `$where`, `$function`, `$accumulator` or `mapReduce` now produce always-reported events**, one per principal, object set and window ([docs/08](docs/08-engine-capabilities.md#what-is-kept)).
- **OpenLDAP Discovery caps the pooled sample of containers that normalize to one name (behaviour change, phase 8 follow-ups, security review of #197, L3).** Containers whose DNs normalize to one name (`ou=<person>,ou=teams,…` all become `ou=*,ou=teams,…`) share one own-read budget in the Audit stream, so a directory with more than `limits.max_sample_rows` of them got the agent's own scans reported. Discovery now reads at most `sample_rows` entries per normalized name and scan (each search asks for what is left, an empty container counts one); the containers past the cap are not searched and are counted `skipped_limit`, with one warning per name, and the containers of a name are rotated from scan to scan so that later scans sample them ([docs/08](docs/08-engine-capabilities.md#the-agents-own-account-3)).
- **PostgreSQL Audit reports statements that wrap a query as that query (behaviour change, phase 8 follow-ups, security review of #199, L3; [ADR-0048](docs/adr/0048-statistics-catalogs-as-reads.md#refinement-2026-10-12-accepted-statements-that-wrap-a-query) refinement, accepted on 2026-10-12).** On `pg_stat_statements`, a read through a cursor (`DECLARE … CURSOR FOR SELECT …` then `FETCH`, what psql's `FETCH_COUNT` sends), an `EXPLAIN ANALYZE` and the `EXECUTE`s of a prepared statement (counted under the `PREPARE` text) gave no event, statistics catalogs and statement-text views included. `EXPLAIN [ANALYZE]`, `DECLARE … CURSOR … FOR` and `PREPARE … AS` are now events naming the relations of their query, with every rule of a bare query, on both sources: a plain `EXPLAIN` is a read (it shows estimates from the statistics, as on MySQL / MariaDB), explained writes included (pgaudit's `WRITE` record of a plain `EXPLAIN DELETE` too); `EXPLAIN ANALYZE`, a cursor and a prepared statement act as their query (`EXPLAIN ANALYZE DELETE` is a write). **Explains and cursors are always reported, with no row count** (pgaudit counted 0 for a cursor read and the plan's rows for an `EXPLAIN ANALYZE`, so `min_rows` dropped them); a prepared statement's executions keep their rows. None is ever the agent's own. `FETCH` and `MOVE` give no event. **Admin tools' explain buttons, ORM explain helpers, monitoring tools that explain slow queries and psql users with `FETCH_COUNT` now produce events** ([docs/08](docs/08-engine-capabilities.md#statements-that-wrap-a-query)).
- **New target notes on MySQL / MariaDB targets**: `audit.digest_consumer_disabled` and `audit.statement_text_limit_low` (Features, below). A 0.6.x console shows them as raw codes; upgrade the console first.

### 🐛 Bug Fixes
- **Audit (PostgreSQL, MySQL / MariaDB): the first relation of a parenthesized join is named ([ADR-0049](docs/adr/0049-postgresql-statement-text-views-as-reads.md) refinement of 2026-10-11, accepted).** The statement analysis missed the first item of `FROM (a JOIN b ON …)`, so a read through that form did not name `a` on the sources where the text decides; and PostgreSQL `ROWS FROM (…)` was read as a relation named `rows`. Both are fixed.
- **MySQL / MariaDB Audit (`performance_schema`): the agent's own ended sessions are no longer unknown principals (phase 8 follow-ups, security reviews of #186, L1, and of #197, M3).** A statement read after its session ended has no account. The probes and polls of the agent's earlier poll sessions (a reconnected or restarted stream, or another target's stream on the same server) were reported as reads of the statement-text tables by an unknown principal: each poll session now notes its own thread id with the server's identity and start time (both read on the server), and every stream of the agent on that server drops that thread's own probe and poll statements (any other statement of it is reported as before). ### ⚠️ Known limitations
- PostgreSQL Audit: a failed or cancelled read has no row count, and `pg_stat_statements` (Limited) counts no failed statement; a superuser's session `SET` or startup option that raises `log_min_messages` / `log_min_error_statement` is not seen, and an override created between two probes (5 minutes at most) can hide failures until the next probe; a backend killed or crashed mid-read writes nothing (the postmaster's line is not read); native code (C extensions, untrusted languages) that raises 25P02 or 42601 without a context after rows were sent is refused (no event); with `pgaudit.log_catalog = off`, a read of a catalog alone (statistics, statement-text views, credential-bearing catalogs) is not logged; a view, function or procedure over a listed catalog is named by what the statement shows; reads that select no secret column or no statement text stay quiet, so every role can read role names and attributes or the other columns of `pg_stat_activity` unreported; function bodies (`pg_proc.prosrc`), FDW options at wrapper, table and column level, and session settings are not listed ([docs/08](docs/08-engine-capabilities.md#known-limits))
- MySQL / MariaDB Audit: reads of the other system tables (dictionary views, digest summaries, `performance_schema.error_log`, the replication error tables) produce no event; an explain event names relations, not the rows the optimizer read; a warning on a statement that succeeds (warning 1292 read with `SHOW WARNINGS`) and a failed read that sent rows before its error stay under `min_rows`; after an agent restart, the last polls' statements are reported as reads by an unidentified principal; whoever holds the agent's credential at its address can replay its constant `performance_schema` poll unreported ([docs/08](docs/08-engine-capabilities.md#known-limits-1))
- MongoDB Audit: timing oracles without JavaScript (a catastrophic `$regex` or a costly expression under `maxTimeMS`) remain quiet failures, under the `audit.configure` filters and charged one document each from the agent's identity (deferred by the maintainer to after 0.7.0, [ROADMAP](docs/ROADMAP.md#phase-8-follow-ups)); failed operations are not visible on the `auditLog`; whether the server allows JavaScript is not shown ([docs/08](docs/08-engine-capabilities.md#known-limits-2))

### 🔒 Security
- Agent (Apereo CAS): YAML service definitions are read by the agent's own parser of the subset the pre-scanner accepts, without `unsafe-libyaml` ([ADR-0046](docs/adr/0046-cas-yaml-registry-parser-without-unsafe-libyaml.md), refining [ADR-0041](docs/adr/0041-cas-connector.md) decisions 4 and 13; #169 review L5). `unsafe-libyaml` is a machine translation of libyaml's C into `unsafe` Rust, archived by its author, and any CAS administrator who can write a registry file could feed it. The pre-scanner, run again on the blanked copy, now also emits libyaml's tokens; an event builder (libyaml's parser state machine) and a `serde::Deserializer` feed the same closed visitor; all under `#![forbid(unsafe_code)]`, with no new crate. A class hint alone on a line after its `:`, `-`, `[` or `,` now refuses the file (libyaml refused such a file anyway when the hint was less indented than its block, as a second document; a hint alone on a later line is now refused in every case, which Jackson never writes; on the raw bytes it moved the indentation the pre-scanner saw, which could swap the top-level `clientSecret` form, a residual since #169; security review of #187, M1). ## [0.1.0](https://github.com/Yil00/databastion/releases/tag/0.1.0) (2026-09-30)

### ⚠️ Known limitations
Details and rationale are in [docs/05-security.md](docs/05-security.md), [docs/08-engine-capabilities.md](docs/08-engine-capabilities.md) and the ADRs linked below; this list only points to them.
- **Upgrade the console and the agents together** for 0.1.0. Agent builds from before #60 cannot decode `HeartbeatResponse.accepts` ([ADR-0022](docs/adr/0022-protocol-capability-negotiation.md), consequences; [RELEASE.md § 7](RELEASE.md#7-pre-release-checklist)).
- **Audit levels differ per engine** (Full / Partial / Limited / None, reported by each target's `check()`): MySQL / MariaDB are never Full, **MongoDB is never Full**, OpenLDAP and PostgreSQL reach Full only with the prerequisites of the [matrix](docs/08-engine-capabilities.md#matrix).
- **Audit records lost while the agent is stopped** ([docs/08](docs/08-engine-capabilities.md#audit-log-files-and-failing-streams-every-engine)): the rest of a log file rotated by rename is not read; MySQL / MariaDB statements held in a rotated file are lost ([one event per statement](docs/08-engine-capabilities.md#one-event-per-statement-audit-log-files)); what `performance_schema` history no longer holds after it wrapped is lost and counted ([MySQL / MariaDB known limits](docs/08-engine-capabilities.md#known-limits-1)). A log truncated in place while the agent was stopped used to be read from the middle of its new content; this is fixed by #97 (Bug Fixes below).
- **Discovery is slow by default**: at the default 1 % duty cycle and 3600 s budget, a scan covers about 36 s of query time, so large targets show "partial coverage" and scans take about 100 times longer than unpaced ([ADR-0035](docs/adr/0035-discovery-pacing.md), [docs/08](docs/08-engine-capabilities.md#discovery-load-on-the-monitored-database-every-engine), [user guide](docs/10-user-guide.md#9-discovery-scans-and-findings)). Since #98 the console delivers one scan per agent at a time, so a full pass over N targets of one agent takes about N × the scan budget, and a scan still waiting 24 h after its request expires ([ADR-0036](docs/adr/0036-console-discovery-scan-scheduling.md)).
- **PostgreSQL statement text on the agent host**: with `pg_read_all_stats`, the agent account can read other users' raw statement text, including passwords typed as literals; `pg_stat_statements` keeps DCL passwords in clear. Nothing of it leaves the agent, but the credentials are sensitive ([docs/05](docs/05-security.md#recommended-database-accounts-read-only), [docs/08](docs/08-engine-capabilities.md#known-limits)). On `pg_stat_statements`, a holder of the agent's credentials can run the agent's allow-listed table-less statements, with any constants, without them being reported ([the agent's own account](docs/08-engine-capabilities.md#the-agents-own-account)).
- **Failed-login flood**: an attacker can keep 100 junk names above root's count, at about 100 times root's volume (visible in `auth_failures_overflowed_total`), and an events flood can evict findings from the spool down to a quarter of its bounds ([agent README](agent/README.md#failed-login-flood), [docs/08](docs/08-engine-capabilities.md#known-limits-1)).
- **MongoDB abandoned authentications** (since #100): a MongoDB authentication abandoned before any proof (result 337) gives no event, so a client that knows account names can confirm they exist and collect their SCRAM salt and iteration count without being reported; it cannot verify a password without sending a proof, and every wrong proof is reported ([docs/08](docs/08-engine-capabilities.md#known-limits-2)).
- **Records dropped by per-record isolation** reach the counters (`audit.records_dropped`, `audit_record_panics_total`) and the `agent.audit_stream_stopped` alert, not the policies; a masked "conversion failed" event is a v0.1.x item ([ADR-0032](docs/adr/0032-audit-stream-panic-isolation-and-openldap-probe-refresh.md)).
- **Carried forward**: name-normalization gaps ([ADR-0009](docs/adr/0009-name-normalization-and-item-sanitization.md), [docs/05](docs/05-security.md#masking-and-fingerprints)); OpenLDAP `check()` does not probe `userPKCS12`; e-mail notifications are plain text only; the system-alert budget holds only with the same `DATABASTION_SYSTEM_ALERTS_MAX_PER_HOUR` on every console process ([ADR-0033](docs/adr/0033-system-alert-budget.md)); webhook and e-mail consumers must escape principals ([docs/05](docs/05-security.md#alerting)).
- **Release trust**: a single maintainer approves releases ([RELEASE.md § 6](RELEASE.md#repository-configuration-one-time)).

### 🐛 Bug Fixes
- Console: policy and notification wake-ups were not sent by the production build; process-wide state now lives in `processGlobal` / `processSlot`, and the build checks the wake-up functions (#63)
- Agent: the PostgreSQL connector's own table-less statements are no longer reported as access events; other agent-account events on unknown objects are always reported; pgaudit counts as loaded only when its `pgaudit.log_catalog` setting is in `pg_settings`; `pg_stat_statements` counts as a catalog only in the extension's schema (#65)
- Agent: a scan's terminal status no longer overtakes its findings: it waits up to 120 s for the console to answer the scan's findings batches (no wait for a cancelled scan, a parked `/findings` or a spool worker in backoff), otherwise it is counted in `scan_status_before_flush_total` (#70, ADR-0025)
- Agent: writes, DDL and DCL by the agent's own database account are always reported as access events, on PostgreSQL, MySQL / MariaDB and MongoDB; the own-account exclusion now covers only reads (within the Discovery budget) and connections, since the agent never writes (#76, ADR-0027 decision 7)
- Agent: access event `ts` / `ts_last` are clamped to the agent clock in the core, so a database server clock ahead of the agent no longer gets batches rejected with `400` (`formatMaximum`), raising an integrity event and losing the events; dev and E2E agent accounts raised to 5 connections (ADR-0025 decision 11) (#72)
- Agent: heartbeat target checks run concurrently under one 10 s deadline instead of one after the other (N slow targets delayed the heartbeat by up to N × 10 s), taking turns per database account; a check that misses the deadline is reported `timeout` with `check.timed_out` (#70, ADR-0025)
- Agent: a panic in a connector no longer stops the agent: every connector call (`check`, `discover`, `audit_stream`) runs through a panic guard in the core that fails that call (`connector_panics_total`); an Audit stream that panics is restarted from its persisted cursor and, after 3 panics in a row, stopped (level None, note `audit.stream_stopped`; the console raises `agent.audit_stream_stopped` since #81); reconfiguring Audit or restarting the agent retries from the same cursor (ADR-0031; since #83 a record that panics is dropped alone and the stopping thresholds are those of the #83 entry below); the panic hook logs the code location, thread and a panic id, never the panic message (#79, ADR-0029 decision 1)
- Console: `migrate` applies migration `0027` itself on installs at `0026`: the `bytes` column and the `access_events_bytes` CHECK `NOT VALID` in a short transaction recorded with `0027`'s hash, then `VALIDATE CONSTRAINT` on its own, so the upgrade no longer scans `access_events` under an `ACCESS EXCLUSIVE` lock; constraints listed in `DEFERRED_VALIDATIONS` and still `NOT VALID` are validated on every run; final schema unchanged; concurrent `migrate` runs are serialized by an advisory lock (#75, ADR-0028)
- Console: incident dedup keyed by the principal (account name or fingerprint) for every event but `auth_failure`, so fingerprinted OpenLDAP users no longer share one incident; after a false positive, an event with a new `signature.*` signal, a higher score or more rows linked since the mark than the incident's total opens a new incident (#81, ADR-0031)
- Agent: audit records are parsed and converted in isolation on the log-file sources, the MongoDB profiler and the OpenLDAP accesslog (on `pg_stat_statements` and `performance_schema` since #88, below): a record that makes a connector panic is dropped alone and counted (`audit.records_dropped`, heartbeat metric `audit_record_panics_total`); the OpenLDAP stream locates and skips a record that keeps ending the stream (isolation mode, `audit_records_skipped_total`); streams stop only after 7 panics at one position, more than 8 skips or 64 panics per hour (#83, ADR-0032)
- Agent: PostgreSQL role and account statements (`CREATE` / `ALTER` / `DROP` `ROLE` / `USER` / `GROUP`…) are classified `dcl`, not `ddl`, on the `pg_stat_statements` source, as pgaudit does; the `pg_stat_statements` and `performance_schema` statements are analyzed and converted in isolation, so a statement that makes the agent panic is dropped alone instead of stopping the stream; on `pg_stat_statements` such a statement is cached as poisoned and counted once in `audit_record_panics_total` while it stays in the analysis cache (#88); its later deltas, which #88 dropped, are reported since #90, each as a read of `*` with its calls and rows, built from the counters, role and database only, never treated as the agent's own and never budgeted (#90)
- Agent: the PostgreSQL connector's own table-less statements are recognized as the agent's own on `pg_stat_statements` by their exact stored text (constants as `$n`, the connector's bound parameters present), and only for the agent's role, at top level, in a database where the connector runs them, under the first `queryid` seen there (the same text from another role or database, nested or under another `queryid` is reported); own-account row charges not saved yet are flushed every 30 s (#90)
- Agent: OpenLDAP failed-operation proof re-run at every report with a probe DN unique to each probe (only the latest answer counts), proofs no longer borrowed from nested naming contexts, overlap CSNs persisted across restarts (`v2` cursor, the phase-6 format still read); MongoDB `auditLog` None until a record is parsed in the last 24 h, truncated profiler commands reported with an unknown shape, map collapse fail closed on unobserved levels, application names forgotten on logout; MySQL `check()` fails closed when `APPLICABLE_ROLES` cannot be read; audit log files owned or writable by the agent's account are refused (`audit.log_not_readable`); SCRAM and failed-login intermediates zeroized (#83, ADR-0030, ADR-0032)
- Agent: MySQL / MariaDB audit-log records are grouped per connection id and query id instead of by adjacency, so concurrent sessions whose records interleave no longer have about 12 % of their statements counted twice; a statement split by the poll bound or a log rotation is one event; held statements survive a restart (cursor rewound and replayed); late tables of a statement reported early are reported as a continuation; the grouping state is bounded in bytes (16 MiB pending, 8 MiB of hashes, early reports forgotten after 10 minutes) and its evictions are counted in `audit_pending_evicted_total` (#93)
- Agent: Discovery pacing rotates the PostgreSQL databases and the OpenLDAP naming contexts per scan, as MongoDB did, so one slow object in the first database no longer runs every scan out of time before the later databases or suffixes (#93)
- Agent: a scan stopped by Discovery pacing before its deadline is reported `failed` (`timeout`) instead of `succeeded` when the console does not take the coverage counters (`job_progress.coverage`), so the gap is not hidden (#93)
- Agent: a MariaDB / MySQL audit statement replayed after a restart is timed from its log time, so an agent restarting more often than every 5 minutes no longer pins its cursor to it (#93)
- Agent: a poisoned `pg_stat_statements` statement, whose deltas are reported as reads of `*`, is no longer counted in `audit.records_dropped` nor logged as dropped (#93)
- Agent: an audit log truncated in place while the agent was stopped is detected through keyed fingerprints in the tail cursor and read from its start instead of resuming mid-file (`audit_cursor_reset_total`) (#97)
- Console: one Discovery scan per agent at a time: a pending `discovery.scan` is delivered only after the agent's previous scan reaches a terminal state (which wakes the agent's held poll), so scans requested together no longer time out in the agent's queue before they start; claims serialized by a per-agent advisory lock taken in one lock order with revocation, the rotation-conflict lock, scan requests and Audit settings; dead scans swept at claim; a held scan of an online agent kept from expiring (refreshed to now + 1 h, at most 24 h after the request) and shown as "pending (waiting for the previous scan of this agent)"; `expires_at` raised to at least now + 1 h at delivery; a scan rejected by the contract check no longer holds the next one; `GET /jobs` limited to 20 requests per agent per 20 s (`429` + `Retry-After`) (#98, ADR-0036)
- MongoDB: an authentication abandoned before any proof (result 337, e.g. a driver closing its pool mid-handshake) is no longer reported as a failed login (#100)
- Deploy: fetch the agent dependencies before the release version bump (#109)
