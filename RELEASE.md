# Release process – DataBastion

Inspired by how [Portabase](https://github.com/Portabase/portabase) works: `main` / `dev` branches, Conventional Commits, changelog generated by `release-it`, release triggered by merging `dev` into `main`. Adapted to a monorepo that ships **two artifacts**: the console and the agent.

## 1. Branches

| Branch | Role | Protected | Branches from | Merges into |
|---------|------|----------|---------|------------|
| `main` | Released code. Each merge = one release | Yes: PR required, green `CI result` check, no direct push or force-push (only the admin bypasses, for the release commit) | — | — |
| `dev` | Integration of the next version | Yes: PR required, green `CI result` check, no force-push, no deletion — **no bypass, not even for admins** | `main` | `main` (release PR) |
| `feat/<id>-<slug>` | New feature | No | `dev` | `dev` |
| `fix/<id>-<slug>` | Bug fix | No | `dev` | `dev` |
| `docs/…`, `chore/…`, `ci/…`, `refactor/…`, `perf/…`, `test/…` | According to the Conventional Commits type | No | `dev` | `dev` |
| `hotfix/<slug>` | Urgent fix on the released version | No | `main` | `main`, then back-ported to `dev` |
| `release/<X.Y>` | Maintenance of an older minor version (**from 1.0 only**) | Yes | tag `X.Y.0` | — |

- `<id>` = lowercase ROADMAP identifier when there is one: `feat/p2-b-pg-discovery`.
- Work branches are deleted after merge.
- Merge strategy: **squash** for work branches into `dev` (one Conventional commit per PR, the PR title becomes the message); **merge commit** from `dev` into `main` (keeps the release history) and for the `main` → `dev` back-merge.
- `dev` is never deleted: the "delete branch on merge" setting cannot remove it because its ruleset has no bypass.

## 2. Versions

### A single version for the whole repository
The console and the agent share **the same version number** and are released together. That way a user knows that console `0.3.1` and agent `0.3.1` go together.

The **protocol version** (`/api/agent/v1`) is independent: it only changes on an incompatible change, with an ADR (see [AGENTS.md](AGENTS.md#protocol-sharedprotocol)).

### SemVer
`MAJOR.MINOR.PATCH`, computed automatically from the commits:

| Commits since the last release | Before 1.0 | From 1.0 |
|------------------------------------|-----------|-----------------|
| `fix:`, `perf:` | patch | patch |
| `feat:` | minor | minor |
| `feat!:` or `BREAKING CHANGE:` | **minor** | major |

Before 1.0, a breaking change bumps the minor (`0.3.x` → `0.4.0`) and must be flagged at the top of the release notes.

### Compatibility
- A console `X.Y` accepts agents `X.Y` and `X.(Y-1)`.
- Upgrade the **console first**, then the agents.

## 3. Tags

| Type | Format | Example | Created by | Effect |
|------|--------|---------|----------|-------|
| Release | `X.Y.Z` | `0.1.0` | CI, on `dev` → `main` merge | GitHub release + `X.Y.Z`, `X.Y`, `latest` images + `.deb` |
| Pre-release | `X.Y.Z-alpha.N`, `-beta.N`, `-rc.N` | `0.1.0-rc.2` | Maintainer, on `dev` | GitHub pre-release + `X.Y.Z-rc.N` and `next` images (**never `latest`**) |

Rules:
- No `v` prefix (like Portabase): the git tag is identical to the Docker tag.
- Pre-release with a **dot** (`-rc.2`, not `-rc2`): SemVer ordering stays correct after `-rc.9`.
- **Annotated** tags. Pre-release tags created by hand are also signed (`git tag -s`). Release tags are created by the CI; their integrity is guaranteed by the cosign signature of the images.
- A published tag is **never** moved or deleted. In case of a mistake: a new patch version.
- MVP stages: `0.1.0-alpha.N` (end of phase 2) → `0.1.0-beta.N` (phases 3 to 6) → `0.1.0-rc.N` (phase 7) → `0.1.0`.

## 4. Published artifacts

| Artifact | Name | Architectures |
|----------|-----|---------------|
| Console image (web + worker) | `ghcr.io/yil00/databastion-console:<tag>` | amd64, arm64 |
| Agent image | `ghcr.io/yil00/databastion-agent:<tag>` | amd64, arm64 |
| Agent package (phase 7) | `databastion-agent_<X.Y.Z>_<arch>.deb` | amd64, arm64 |
| Deployment bundle (phase 7) | `databastion-deploy-<X.Y.Z>.tar.gz` (`deploy/` at the tag) | — |
| Image references (phase 7) | `image-digests.txt` (`<image>:<tag>@sha256:<digest>`) | — |
| Checksums (phase 7) | `SHA256SUMS` + cosign bundle `SHA256SUMS.cosign.bundle` | — |

Images are published to GHCR, built natively on amd64 and arm64 runners, signed with cosign in *keyless* mode (GitHub OIDC), with SBOM and provenance attestation. An image is only built if its `Dockerfile` exists. The `.deb` files are built from the binary of the signed agent image; `SHA256SUMS` covers them, the deployment bundle and `image-digests.txt`, and is signed with `cosign sign-blob` (`SHA256SUMS.cosign.bundle`). [publish.yml](.github/workflows/publish.yml) verifies every signature right after signing, and moves `next` / `X.Y` / `latest` only after that.

**Signing identity** ([ADR-0034](docs/adr/0034-release-signing-from-tag-push.md)): everything is signed by `publish.yml` in the run triggered by the **push of the release tag**, and only there. The identity is therefore exact for each version:
```bash
VERSION=0.1.0
cosign verify ghcr.io/yil00/databastion-console:$VERSION \
  --certificate-identity "https://github.com/Yil00/databastion/.github/workflows/publish.yml@refs/tags/$VERSION" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-github-workflow-trigger push
# Same three options for `cosign verify-blob SHA256SUMS --bundle SHA256SUMS.cosign.bundle`.
```
All the checks, in order: [deploy/README.md](deploy/README.md#verify-the-artifacts).

## 5. Release walkthrough

### Regular release
1. On `dev`, CI is green and the ROADMAP is up to date.
2. (Optional) Create an `X.Y.Z-rc.N` tag on `dev` to test the candidate images.
3. Open a `dev` → `main` PR titled `release: X.Y.Z`.
   release-it computes the version from the commits since the last tag: a `feat` commit gives a minor version (`0.1.0` → `0.2.0`), only `fix` commits a patch version. The "Release version" PR check (`pr-checks.yml`, PRs to `main` only) runs release-it on the PR merge commit, shows the version in the run summary and fails until the title is exactly `release: X.Y.Z` with that version, or carries `[skip-release]` (0.2.0 was planned as 0.1.1 before this check). Without `[skip-release]`, it also fails while the "Unreleased" section of [CHANGELOG.md](CHANGELOG.md) is empty: the curated notes written there during the cycle are the release notes. A second step of the same check fails while the holdout seed (`SEED` in `dev/holdout/generate.py`) is the one of the previous final release tag, or of any earlier release: rotate it on `dev` first ([§ 8](#8-holdout-seed-rotation)), or add `[skip-holdout]` to the title under the conditions given there.
4. On merge (the push of the merge commit to `main`), the CI ([release.yml](.github/workflows/release.yml), `release-it`, config [.release-it.json](.release-it.json)) waits for the maintainer's approval of the `release-it` environment, then:
   - computes the version from the commits and the latest tag,
   - updates the version numbers with [scripts/bump-version.mjs](scripts/bump-version.mjs) (`package.json` + `package-lock.json`, `console/package.json`, `agent/Cargo.toml` + `Cargo.lock`, `agent/fuzz/Cargo.lock` since #112, later the Helm chart),
   - moves the curated "Unreleased" notes of [CHANGELOG.md](CHANGELOG.md), verbatim, under a new `## [X.Y.Z]` section below the introduction (dated, and linked to the comparison `PREV...X.Y.Z`), PREV being the latest final `X.Y.Z` tag (pre-release tags are ignored), and leaves an empty "Unreleased" section ([scripts/changelog-release.mjs](scripts/changelog-release.mjs), `after:bump` hook); the release fails before any commit, tag or push when "Unreleased" is empty or missing. The commit list generated by `@release-it/conventional-changelog` is used for the version computation only, no longer written to the file,
   - commits `chore(release): X.Y.Z` under the owner's noreply identity, creates the `X.Y.Z` tag and pushes it with `RELEASE_TOKEN`,
   - creates a **draft GitHub release** whose notes are the same curated notes, with their relative links made absolute (`https://github.com/Yil00/databastion/blob/X.Y.Z/…`).
5. The tag push starts [publish.yml](.github/workflows/publish.yml). For a final version it asks for **no approval**: the `release-it` approval of step 4 is the only human step ([ADR-0058](docs/adr/0058-release-automation-one-approval.md#implementation-note-2026-10-24-publishyml-without-approvals-before-the-hard-gate)). Instead, its `prepare` and `release-tree` jobs check, before anything is built or signed ([check-final-release.sh](.github/scripts/check-final-release.sh)), and stop the run on the first failure:
   - the release `X.Y.Z` is not published, and no final tag above `X.Y.Z` exists: an old run re-run, or a release on an older line, must not re-sign a version or move `X.Y` / `latest` back. `manifest` checks this again right before it signs and before it moves `X.Y` / `latest`. A hotfix on an older line is therefore refused by `publish.yml`;
   - the tag `X.Y.Z` is an annotated tag with the message `DataBastion X.Y.Z` on the commit of the run, `T`;
   - `T` is reachable from `main`, its subject is exactly `chore(release): X.Y.Z`, its author and committer are the release identity (`RELEASE_GIT_EMAIL`, or the owner's noreply address) and it is signed off;
   - `T` has one parent `P`, a merge commit;
   - between `P` and `T`, only files the release hooks change are modified (`CHANGELOG.md`, `package.json`, `package-lock.json`, `console/package.json`, `agent/Cargo.toml`, `agent/Cargo.lock`, `agent/fuzz/Cargo.lock`, `helm/databastion/Chart.yaml`), `CHANGELOG.md` and `package.json` among them;
   - exactly one `release.yml` run on the push of `P` to `main` exists, its `release-it` job concluded `success` and was approved in the `release-it` environment, and `T`'s committer time falls within that job's start and end (2 minutes of slack). `prepare` waits up to 20 minutes, the job's own timeout, for the job to finish (release-it pushes the tag before it creates the draft), and fails if it has not;
   - in the `release-tree` job, whose token can only read the contents: `T`'s tree is exactly what the two `after:bump` hooks produce when run on `P` (with Node 24 and Rust 1.88.0, as in `release.yml`).

   It then builds and signs the images, the `.deb` files and `SHA256SUMS`, attaches them to the draft, and runs the installation test with them. A pre-release tag skips these checks and waits for one approval instead ([Pre-release](#pre-release)).

   **Re-runs need the approval.** Write access is enough to re-run a publish run for 30 days, and the checks above are about past facts, so they would pass again. Any re-run of a final version (`github.run_attempt` above 1) therefore waits for the approval job `prerelease-approval` in the `release` environment, like a pre-release; `build`, `manifest` and `release-assets` do not run without it. *Re-run failed jobs* does not re-run the approval job, which was skipped in the first attempt, so the jobs it re-runs are skipped and nothing is signed: use *Re-run all jobs*, which runs the checks again and asks for the approval. A version already published, or below another final tag, is refused on a re-run too.

   **First releases with these checks.** If `prepare` or `release-tree` fails, read its log: each failed check prints an `::error::` naming what differs. Never edit `publish.yml` at the tag to get past a check (the signing identity names the tag, and a tag is never moved): fix the cause on `dev`, or release a new patch version. Two points are not verified yet against a real run: that `GET /actions/runs/{id}/approvals` is readable with `actions: read`, and that an administrator bypass of the `release-it` approval leaves no `approved` record (then the check fails: approve, do not bypass). `release-tree`, which runs the release hooks of the tagged code, has a token that can only read the contents.

   **Concurrency.** Publish runs are serialized (`concurrency: publish`, none cancelled while running), but GitHub keeps only one pending run per group: when a third tag is pushed while one run is running and another is pending, the pending one is cancelled. This fails safe (nothing of it is built or signed), but silently: its run shows as cancelled. Re-run it (*Re-run all jobs*); as a re-run, it needs the approval.
6. The maintainer reviews the draft (assets present, publish run green, release notes as curated), adds upgrade notes if needed, and **publishes** the release. Assets are only ever attached to a draft.
   The CHANGELOG section and the draft notes need no hand edit any more (until 0.3.0 the maintainer moved the notes and pasted them into the draft). A correction found after the release goes to `dev` through a PR, like any other CHANGELOG change, and to the published release notes by hand. To preview both before merging: `make release-dry` on a local `main` branch, or `node scripts/changelog-release.mjs preview X.Y.Z` (writes nothing).
   A pre-release version computed by release-it (`X.Y.Z-rc.N`; pre-releases are normally tagged by hand, below) leaves CHANGELOG.md as it is: the notes stay in "Unreleased" for the final release, and the draft pre-release gets them as its notes.
7. Open a PR `main` → `dev` titled `chore: back-merge X.Y.Z into dev` and merge it with a **merge commit**, to bring back the version commit.

To merge into `main` without publishing (CI, documentation…): add `[skip-release]` to the PR title, as on Portabase (GitHub copies the title into the merge or squash commit message, which `release.yml` reads: keep the default commit messages). **Required as long as there is no code**: without a `feat`/`fix` commit, release-it would publish an empty patch version.

### Pre-release
```bash
git switch dev && git pull
git tag -s 0.1.0-alpha.1 -m "DataBastion 0.1.0-alpha.1"
git push origin 0.1.0-alpha.1
```
Pushing the tag triggers [publish.yml](.github/workflows/publish.yml) (`0.1.0-alpha.1` and `next` images). Its `prerelease-approval` job waits for **one** approval in the `release` environment (*Review deployments*); the builds, the signature and the release assets follow without another prompt. The final-version checks of step 5 above do not apply to pre-release tags, but a pre-release is refused when any version tag is above it in SemVer precedence (`0.9.1-rc.10` above `0.9.1-rc.9`, a final `0.9.1` above every `0.9.1-…`), in `prepare` and again in `manifest` right before signing and before moving `next`: an old pre-release run that is re-run cannot move `next` back. A *Re-run failed jobs* of a pre-release keeps the first approval: before ADR-0058's implementation note, the signing jobs asked for it again. The run creates a **draft** GitHub pre-release with the `.deb` files and the signed `SHA256SUMS`. Review it, then publish it (`gh release edit 0.1.0-alpha.1 --draft=false`). Only a maintainer allowed by the tag ruleset (below) can push the tag.

### Hotfix
1. `hotfix/<slug>` from `main`, PR to `main` with a `fix:` commit.
2. Merge it with a **merge commit**, never a squash: release-it reads commit headers only, and a squash commit's header is the PR title (`release: X.Y.Z`), so its `fix:` lines would not count (0.8.1: #320 and #321 were squashed and released nothing). The merge publishes `X.Y.(Z+1)`; `release.yml` fails when a merge without `[skip-release]` computes no version.
3. Back-merge `main` into `dev` through a PR (merge commit), as for a regular release.

### Security fix
Follow [SECURITY.md](SECURITY.md): fix prepared privately (GitHub Security Advisory), released as a hotfix, security advisory published at the same time as the release.

## 6. Automation (GitHub Actions)

| Workflow | Trigger | Role |
|----------|-------------|------|
| [ci.yml](.github/workflows/ci.yml) | push and PR on `main` / `dev` | Doc links, gitleaks, console, agent, protocol (each job only runs if its component exists); aggregated `CI result` check |
| [pr-checks.yml](.github/workflows/pr-checks.yml) | PR | Conventional Commits title, DCO sign-off on each commit; on PRs to `main`, "Release version": the version release-it will compute, curated CHANGELOG notes and a rotated holdout seed ([§ 5](#5-release-walkthrough)) |
| [release.yml](.github/workflows/release.yml) | push to `main` (a merged PR), except `[skip-release]` and release-it's own commit; runs in the `release-it` environment | release-it: version, changelog, `X.Y.Z` tag pushed with `RELEASE_TOKEN`, draft release (no signing) |
| [publish.yml](.github/workflows/publish.yml) | push of an `X.Y.Z` or `X.Y.Z-*` tag only; final versions checked as release-it's release commit of an approved `release.yml` run, neither published nor superseded, no approval on the first attempt; pre-release tags and re-runs behind one `prerelease-approval` job in the `release` environment | Signed multi-arch GHCR images (signature and attestations verified), agent `.deb` files, signed `SHA256SUMS` on the draft release, installation test with the published artifacts |
| [packaging.yml](.github/workflows/packaging.yml) | call from `ci.yml` (packaging files changed) and `publish.yml` | Reproducible `.deb`, install checks in Debian 12 / Ubuntu 24.04 containers, "Installation < 15 min" test ([deploy/README.md](deploy/README.md#installation-test-under-15-minutes)) |
| [advisories.yml](.github/workflows/advisories.yml) | daily, and push / PR on `main` / `dev` touching a lockfile | Dependency advisories: `cargo-deny` (agent), `pnpm audit` (console), `npm audit` (root release tooling); not a required check |
| [fuzz-nightly.yml](.github/workflows/fuzz-nightly.yml) | daily, and on demand (`workflow_dispatch`) | AddressSanitizer fuzz campaign on nightly Rust (cargo-fuzz 0.13.2) over every parser target of [agent/fuzz](agent/fuzz/README.md), seeded from the committed fake fixtures: 10 min for `cas_registry_yaml` and `cas_registry_yaml_diff`, 5 min for `cas_registry` and `cas_audit_log`, 3 min for each MongoDB and OpenLDAP target; Redis / Valkey: 5 min for `redis_resp_decoder`, `redis_key_pattern`, `redis_slowlog_entry` and `redis_learned_patterns`, 3 min for `redis_acl_log_entry`, 2 min for `redis_info`; SQL Server: 5 min for `sqlserver_token_stream`, `sqlserver_tsql` and `sqlserver_xe_xml`, 3 min for `sqlserver_plp`, `sqlserver_audit_records` and `sqlserver_xe_records`, 2 min for `sqlserver_packets`, 1 min for `sqlserver_prelogin_tls`; the core's CSV log splitter: 3 min for `core_csv_splitter`; a crashing input is uploaded as an artifact (a mutation of fake fixtures or random bytes, no secret); not a required check |
| [dependabot.yml](.github/dependabot.yml) | weekly | Updates to actions and tooling, PRs to `dev` |

Third-party actions are pinned by commit SHA (Dependabot updates them).

### Repository configuration (one-time)
**These settings must be in place before the change that introduced them (ADR-0034, PR #86) is merged into `main`**, and before any release. `release.yml` and `publish.yml` check them at the start of every run and stop when one is missing (`.github/scripts/check-release-settings.sh`): a defence against a forgotten or undone setup only, since whoever can edit a workflow can remove the check.

Why: `RELEASE_TOKEN` can push to `main` and create version tags (it bypasses the tag ruleset), and any version tag starts a signing run. The token must therefore be readable only by the `release-it` job on `main`, and tag creation must be limited to it and the maintainers.

Maintainer steps, in this order:
1. **`release-it` environment**: *Settings → Environments → New environment*, name `release-it`.
   - *Required reviewers*: the maintainer(s) (leave *Prevent self-review* off while there is a single maintainer). **Uncheck** *Allow administrators to bypass configured protection rules* (checked by default; the settings check refuses it unless the repository variable `RELEASE_ALLOW_ADMIN_BYPASS` is `true`, see the residual risk below).
   - *Deployment branches and tags*: *Selected branches and tags* → *Add deployment branch or tag rule* → *Ref type: Branch*, name `main`. No other rule.
   - *Environment secrets → Add environment secret*: `RELEASE_TOKEN` = the owner's *fine-grained* token (*Settings → Developer settings → Fine-grained tokens*), limited to this repository, **Contents: read and write** only. It lets the release commit pass `main`'s protection and pushes the tag (a push made with the default `GITHUB_TOKEN` would not start `publish.yml`).
   - Preferred replacement for the admin token: a **GitHub App** installed on this repository only (Contents: read and write), its token minted in the job (`actions/create-github-app-token`), the app's private key as the environment secret, and the app, not *Repository admin*, in the bypass lists of `main` and of the tag ruleset.
2. **`release` environment**: *New environment* `release`. *Required reviewers*: the maintainer(s), same settings as above (since ADR-0058's implementation note of 2026-10-24, only the `prerelease-approval` job of `publish.yml` declares this environment: its reviewers approve pre-release tags only; final versions go through the checks of [§ 5](#regular-release), step 5), *Allow administrators to bypass configured protection rules* **unchecked** (same exception). *Deployment branches and tags*: *Selected branches and tags* → *Add deployment branch or tag rule* → *Ref type: Tag*, pattern `[0-9]*.[0-9]*.[0-9]*`; no branch rule. No secret (keyless signing).
3. **Delete the repository-level secret**: *Settings → Secrets and variables → Actions → Repository secrets* → `RELEASE_TOKEN` → *Remove*. From then on, no branch workflow can read the token.
4. **Tag ruleset**: *Settings → Rules → Rulesets → New ruleset → New tag ruleset*. Name `release tags`, enforcement *Active*. *Target tags → Add target → Include by pattern*: `*.*.*` (covers `X.Y.Z` and `X.Y.Z-…`). Rules: *Restrict creations*, *Restrict updates*, *Restrict deletions*, *Block force pushes*. *Bypass list*: *Repository admin* only (the maintainers; release-it's tag push goes through the owner's token), or the release GitHub App of step 1, whose app id then goes into the repository variable `RELEASE_APP_ID`. No other team, app or deploy key: the settings check refuses them (when the bypass list is visible to the workflow token; otherwise it warns and this is to be checked by hand). No *Exclude* pattern at all, and no other include pattern than `*.*.*`, `*` or `[0-9]*.[0-9]*.[0-9]*` (or *All tags*): the settings check accepts only these. Save.
5. **Merge methods**: *Settings → General → Pull Requests*: allow **merge commits** and **squash merging**, disable **rebase merging** (a rebase merge keeps the original commit messages, so `[skip-release]` in the PR title would not reach `main`), and keep the default commit messages (they carry the PR title).
6. Check once with a pre-release tag: the publish run passes its settings check, waits for the one approval of `prerelease-approval`, and `cosign verify` with the exact identity above succeeds.

- Optional variables `RELEASE_GIT_NAME` / `RELEASE_GIT_EMAIL`: identity of the release commit (by default, the owner's noreply address). `RELEASE_APP_ID`: see step 4. `RELEASE_ALLOW_ADMIN_BYPASS`: see the residual risk below.

**Residual risk, while there is a single maintainer.** The maintainer is on the tag ruleset's bypass list and is also the reviewer of the `release` environment (the `prerelease-approval` gate). They can therefore push a pre-release tag (`X.Y.Z-…`) on **any** commit, including a branch on which `publish.yml` was edited, approve its jobs themselves, and obtain artifacts signed with the exact documented identity `publish.yml@refs/tags/<version>`. The signature proves that the artifact came from this repository's publish workflow at that tag, not that the tag points at reviewed code on `main` or `dev`. Nothing in the repository prevents this; it rests on the maintainer's account (two-factor authentication, no shared tokens) and on the public record: the tag, its commit and the publish run are visible, and a tag is never moved. A second maintainer as required reviewer, with *Prevent self-review*, removes the self-approval part.
- **Final versions without a `release` approval, while agents act as the administrator (maintainer decision of 2026-10-24, [ADR-0058](docs/adr/0058-release-automation-one-approval.md#implementation-note-2026-10-24-publishyml-without-approvals-before-the-hard-gate)).** Agent sessions use the maintainer's administrator credential, with bypass on the tag ruleset and on `main`, so the hard gate of ADR-0058 decision 6.1 is not met. With that credential, an agent could already push a final-version tag on a commit whose `publish.yml` has no environment and no checks, and get artifacts signed with the exact identity: the `release` approvals never stopped that. For an administrator, removing them adds no such power, but it removes the pause on the honest path for final tags: once the `release-it` approval is given, the signed artifacts follow with no other human step. For a collaborator with *Write* only, the approvals were a real control on re-runs: *Write* is enough to re-run an old publish run for 30 days, which would sign the version again and move `X.Y` / `latest`. Re-runs of final versions therefore still need the approval, and `prepare` and `manifest` refuse a version that is published or below another final tag (§ 5, step 5). The checks of [§ 5](#regular-release), step 5 refuse a final tag pushed by hand only when the reviewed `publish.yml` runs. The draft is still published by hand.
- **Administrator bypass on the environments (maintainer's choice).** With the repository variable `RELEASE_ALLOW_ADMIN_BYPASS` set to `true`, the settings check accepts `release-it` and `release` environments that let administrators bypass their protection rules, and prints a warning on every run. While the single maintainer is both the only administrator and the only required reviewer, this changes little: an administrator can already approve their own runs, and the bypass is still a deliberate action of an administrator's session, never of a workflow token. It removes the approval step as a forced pause, though, so it must be switched off (variable removed, box unchecked) as soon as a second maintainer joins. Set it as a **repository** variable only: an environment variable of the same name would override it in the `release-it` job, so when switching it off, also check that no environment (or organization) variable of that name remains. Whether the administrator bypass also lets an administrator deploy to an environment from a ref its deployment rule does not admit (for `release-it`, a branch other than `main`, which would expose `RELEASE_TOKEN` to that branch's code) is not documented clearly by GitHub: treat it as possible, and never bypass a run whose ref is not `main` (for `release-it`) or a version tag (for `release`).
- As long as there is only one maintainer, no approval is required on PRs (you cannot approve your own PR). Switch to 1 approval as soon as a second maintainer joins.

## 7. Pre-release checklist
Every item is checked on the `dev` commit that becomes the release (and on the `-rc.N` tag when there is one). It extends the [Definition of Done](AGENTS.md#definition-of-done) of each task to the whole release.

### Every release
- [ ] **CI green on `dev`**: the `CI result` check of the release commit (lint, tests and builds of every component, protocol checks, the blocking holdout classifier gate, doc links, gitleaks; [ci.yml](.github/workflows/ci.yml)). Advisories workflow green on the release commit (it is not a required check; [advisories.yml](.github/workflows/advisories.yml): agent, console and root release tooling)

## 8. Holdout seed rotation
The classifier gate of the CI scores the classifiers on a held-out corpus generated from a fixed seed ([dev/holdout/README.md](dev/holdout/README.md)). Whoever has seen its failing columns while working on the classifiers has partly seen the test set, so the seed is rotated **once per release**. This only concerns the holdout seed: the dev seed (`dev/seed/generate.py`, which produces [dev/ground-truth.json](dev/ground-truth.json) for the containers, the integration tests and the end-to-end I2 test) is not a held-out set and is not rotated.

**When.** On `dev`, after the last classifier change of the release is merged and before the release candidate (the `-rc.N` tag, or the `dev` → `main` release PR when there is no candidate). The release is then measured on values nobody tuned against, and the new seed stays in place for the next development cycle. First rotation: v0.1.0.

**Who.** Preferably someone who did not change the classifiers during the cycle. In any case the rotation PR touches `dev/holdout/` only: whoever changes the classifiers does not change the corpus in the same PR (independence rule). The CI output of the rotation PR (aggregates plus the ids and tags of the failing columns, never a value) is public, like every CI log.

**How.**
1. Branch from `dev` (for example `test/p7-holdout-seed-0.1.0`).
2. Pick a new seed, e.g. `python3 -c 'import secrets; print(secrets.randbelow(10**9))'`. It must differ from the dev seed `20260928` (a unit test enforces it) and from the previous holdout seeds: `git log -p -- dev/holdout/generate.py | grep '^[-+]SEED ='`.
3. Set `SEED` in [dev/holdout/generate.py](dev/holdout/generate.py), then regenerate and check:
   ```sh
   python3 dev/holdout/generate.py            # rewrites labels.json (new corpus_sha256) and the git-ignored corpus.json
   python3 dev/holdout/generate.py --check
   python3 -m unittest discover -s dev/holdout -v
   ```
4. Update the seed and the counts that `generate.py` prints in [dev/holdout/README.md](dev/holdout/README.md) ("Files" table and "Counts" section).
5. Run the gate as the CI does, from `agent/`: `cargo test -p databastion-classifiers --test holdout --all-features --locked -- --ignored --nocapture`.
6. Commit `generate.py`, `labels.json` and `README.md` only (`corpus.json` stays git-ignored), open the PR to `dev` and let the CI run the blocking holdout gate.

**Release PR check.** The "Release version" check of a PR to `main` ([pr-checks.yml](.github/workflows/pr-checks.yml)) reads `SEED` at the PR merge commit and fails when it equals the `SEED` of the previous final release tag (the latest `X.Y.Z` tag reachable from the PR's base commit on `main`, `git describe --tags --abbrev=0 --match '[0-9]*.[0-9]*.[0-9]*' --exclude '*-*'`; pre-release tags are ignored), or when a rotation brings back the seed of an earlier release. A PR with `[skip-release]` in its title is not checked. The check is a reminder against a forgotten step, not a control: it runs the PR's own code, which can change it.

**`[skip-holdout]`.** A release may keep the previous release's seed only when no classifier code changed since that release: the corpus would then measure exactly the classifiers it measured last time, so a rotation adds no independence, and a hotfix or security fix released from `main` ([§ 5](#hotfix)) need not wait for a rotation PR on `dev`. End the release PR title with ` [skip-holdout]` (`release: X.Y.Z [skip-holdout]`; the version check ignores that suffix) and say why in the PR description. The check accepts it only when `git diff <previous tag> <merge commit> -- agent/crates/classifiers` is empty, and refuses it otherwise. A previous tag whose `SEED` cannot be read fails the check (check it by hand). It is never a way to release classifier changes on a seed that people tuned against; the next release that changes the classifiers rotates the seed as usual.

**If the gate fails on the new seed**, the release waits: do not change the corpus back, and do not tune the classifiers against the failing columns. Fix the classifiers in a separate PR, against the dev seed or examples of your own ([dev/holdout/README.md](dev/holdout/README.md#independence-rule)), then check the gate again. The person who rotated the seed, and has seen the failing columns, does not write that fix. If a fix is nevertheless made while looking at the new seed's failures, record in the release notes or the ROADMAP that this release's holdout result is no longer independent, and rotate the seed again at the start of the next cycle.
